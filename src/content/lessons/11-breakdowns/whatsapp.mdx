## The problem

Alice types "running late" and presses send. Bob's phone is in his pocket. Within about a second it should buzz. If Bob is on a train with no signal, the message must still arrive when he gets signal back. Alice must see whether it left her phone, reached his phone, or was read.

Two ideas are new here. First, the server must **push** to a phone that never asked. Second, the server must know which of thousands of machines holds Bob's connection. The rest comes from earlier lessons.

## Requirements

Follow the six-step method from lesson [0.3](/learn/00-orientation/design-method/).

**Functional, above the line:**

1. Send and receive 1:1 messages in real time.
2. Show delivery state: sent, delivered, read.
3. Deliver to a user who is offline when the message is sent.
4. Group chats, up to about 100 members (an assumption).

**Below the line:** media upload (lesson [9.6](/learn/09-patterns/large-blobs/) covers the pattern). The rest are voice and video calls, end-to-end encryption, sign-up, "last seen", and spam control.

**Non-functional.** The numbers are interview assumptions, not company figures:

- Delivery to an online recipient in under 500 ms.
- No silent loss. A message is delivered, or the sender can see that it is not.
- The server keeps a message only until it is delivered, and for 30 days at most.
- Scale: 500 million daily users, 40 messages sent per user per day. The Numbers section derives the load.

## Core entities

- **Chat**: `chat_id`, type (1:1 or group), members.
- **Message**: `message_id`, `chat_id`, `sender_id`, `client_msg_id`, body, server time, `seq`.
- **Device**: `device_id`, user, last sequence seen per chat. A user can have a phone and a laptop.
- **Receipt**: message, device, state.
- **Inbox entry**: device, message. It means "this device has not acked this message yet".

`client_msg_id` is made by the sender's app. It lets the server recognize a retry (lesson [3.4](/learn/03-api-design/idempotency/)). `seq` is a number the server assigns, one counter per chat. Order by `seq`, never by a phone's clock.

## API

Messaging runs over a WebSocket, because the server must push (lesson [2.5](/learn/02-networking/real-time-transport/)). The frames are:

- Client to server: `send {chat_id, client_msg_id, body}`. The server answers `sent {message_id, seq}`.
- Server to client: `message {message_id, chat_id, seq, body}`.
- Client to server: `ack {message_id, state}` where state is `delivered` or `read`.
- On connect: `hello {device_id, last_seq per chat}`. The server replays what is missing.

A plain HTTP `GET /chats/{id}/messages?after_seq=` also exists for history and resync.

There is no data-flow section. Each message is one request with one reply, not a pipeline.

## Deep dives

### Routing a message to the right server

Server A needs to reach server B. There are two common ways.

**Direct forward.** Look up the recipient in the session map, then call server B. One lookup, one hop. You need a connection mesh between chat servers and care when the entry is stale.

**Pub/sub doorbell.** Pub/sub means publish and subscribe: a sender posts a message to a named channel, and everyone listening on that channel gets a copy. Each chat server subscribes to a channel named for itself. Server A publishes to the channel of the target server. A subscribed server gets it at once. This is simple to run, and lesson [9.3](/learn/09-patterns/real-time-updates/) covers the pattern.

Redis pub/sub is at-most-once (the Redis docs say a message is delivered once if at all). So a published message can be lost if the subscriber is briefly gone. That is fine only because the message is already in the store and inbox. The push is a doorbell. The inbox is the mailbox. The per-chat `seq` shows a gap if a doorbell was missed. Lesson [6.3](/learn/06-async/delivery-semantics/) explains why the sender and receiver cannot tell loss from slowness.

**Why not one topic per user?** Every user would need a topic, a queue, or a consumer group of their own. Hundreds of millions of tiny topics is a bad fit for a log broker. That broker is built around a few thousand partitions (lesson [6.2](/learn/06-async/pubsub-logs/)). A map of user to server is a far cheaper way to say "where is Bob".

### Dead sockets and silent loss

<WhatsappAckCompare client:visible />

TCP does not tell you the phone vanished. A phone that loses signal sends no close frame. The server's next write often succeeds, because it only fills a buffer. So the server needs three tools of its own:

- A **heartbeat**: a small ping on a timer. A missed reply means a dead socket (lesson [2.5](/learn/02-networking/real-time-transport/)).
- An **app-level ack** for every pushed message. Only that ack means delivered.
- A **replay on reconnect**, driven by the last `seq` the phone saw.

Together these give at-least-once delivery. The sender's retry and the server's replay can both create duplicates. The phone drops a repeat by `message_id`. The result is an effectively-once display.

### Offline users, many devices

Each device has its own inbox, because a laptop can be online while the phone is not. An entry lives until that device acks it, or for 30 days at most. Reconnect is a pull: the device reports its `last_seq`, and the server sends the gap.

"Delivered" needs a product rule with several devices. A common choice is to mark it when the first device acks, and "read" when any device reports it. State the rule you pick. The wrong move is to wait for all devices, because one old tablet would block the ticks forever.

### Group fan-out

A message to a 100-member group is one write to the store and up to 99 deliveries. Fan-out on write means the sender does the delivery work once, at send time, for every recipient. It is right here. The reason is that the work is bounded by the group size limit. The lesson on the news feed, [11.5](/learn/11-breakdowns/news-feed/), shows what goes wrong when the work is not bounded. Each member's device gets either a push or an inbox entry. Receipts for a group come from many devices, so the sender usually sees one tick set that means "reached some members", with per-member detail in the message info view.

## Numbers

All inputs are assumptions. The method is lesson [1.4](/learn/01-one-machine/estimation/).

- **Messages.** 500M users × 40 messages = 20B messages per day. That is 20B / 86,400 s ≈ 231,000 per second on average. Assume peak is twice the average, so about 460,000 per second.
- **Deliveries.** Say 80% of messages go to one person and 20% to groups of 10. Average recipients = 0.8 × 1 + 0.2 × 10 = 2.8. Deliveries ≈ 231,000 × 2.8 ≈ 650,000 per second.
- **Sockets.** Say 30% of users are connected at once: 150M sockets. At 100,000 sockets per server, that is 1,500 servers. At 10 KB of memory per socket, 100,000 sockets use about 1 GB of RAM. Sockets are mostly idle, so memory and file descriptors matter more than CPU. A file descriptor is the handle the operating system gives a program for each open connection or file, and each machine has a limit on how many it allows.
- **Heartbeats.** One ping per socket every 30 s: 150M / 30 = 5M pings per second across the fleet, about 3,300 per server. Heartbeat interval is a real cost knob.
- **Storage.** At 1 KB per message, keeping everything for 30 days needs this much storage. The math is 20B × 1 KB = 20 TB per day × 30 = 600 TB. Instead, delete after the ack. If 3% of messages wait for an offline device, the standing store is 0.03 × 20B = 600M per day × 30 days × 1 KB = 18 TB. That is an upper bound, since most waits are short.

One company data point, and it is dated. WhatsApp's own blog said it had sent just over 1 billion messages in a single day in late 2011. It put that at 11,574 per second. Our assumed 20B per day is about 20 times that. I found no primary source for current figures, so I quote none.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| WebSocket push | Low latency, server can start a send | Stateful servers, reconnect storms (lesson [2.5](/learn/02-networking/real-time-transport/)) | Real-time two-way messaging |
| Direct forward through a session map | One hop, no broker | Server mesh, stale entries | Fewer, larger chat servers |
| Pub/sub doorbell | Easy routing | At-most-once, so a store must back it | Many servers, simple ops |
| Save before ack | No silent loss | One write on the hot path | Always, for chat |
| Inbox deleted after ack | Low retention, small store | A replay path to build | Privacy and cost matter |
| Fan-out on write for groups | Fast reads, simple delivery | Cost grows with group size | Groups are capped |

## Interview lens

<Callout type="tip">
Say the order out loud. "The server saves the message, then acks the sender, then pushes to the recipient. The server then waits for the recipient's ack. Delivered is an ack from the phone, not a successful socket write. If the phone is offline, the entry waits in its inbox and replays by sequence number." That one paragraph covers most probes.
</Callout>

<Callout type="mistake">
Three common slips. Saying "TCP will tell us if the phone is gone" (it will not; use heartbeats and acks). Using the sender's clock for order (use a server-side `seq`). Treating sent, delivered, and read as one flag (they are three acks from three places).
</Callout>

<Callout type="deep" title="What if the same message arrives twice?">
Two retries can overlap: the sender resends after a lost `sent` ack, and the server replays after a reconnect. Both are safe if every write is keyed by `client_msg_id` on the way in and by `message_id` on the way out. Exactly-once on the wire is not possible (lesson 6.3). Exactly-once in effect is just a dedupe key.
</Callout>
