A chat assistant is unlike most web services. A request does not take 20 milliseconds. It takes 10 seconds or more, and it produces its answer one piece at a time. The machine that does the work is a **GPU**. A GPU is a chip built to do huge amounts of simple math in parallel. Running a trained model to produce an answer is called **inference**. GPUs are costly, and there are never enough of them. The new ideas: streaming tokens as they are made (with server-sent events, or SSE), GPU inference as a scarce resource with queues and batching, limits per user tier, conversation storage, and a request that outlives its connection.

A **token** is a chunk of text, roughly three-quarters of an English word. A model makes one token per step, and each step needs the whole conversation so far as input. Cost, time, and limits are all counted in tokens.

## Requirements

**Functional.**

1. A user sends a prompt and gets a generated answer.
2. A user opens past chats and continues them. Earlier messages go into the prompt.

**Below the line.** Editing or branching messages, images, audio, tool calls, web browsing, sharing, and searching history.

**Non-functional.** The scale below is my assumption. I do not use any company's user count here. The reason is that I could not get a figure I could verify and date. If you quote one in an interview, say where and when it was published.

- **Time to first token** matters more than total time. The user sees words in about a second, then reads as they arrive.
- GPUs are the scarce, costly resource. Allocate them on purpose.
- A dropped connection must not lose the answer. The user can reconnect and continue.
- A heavy user must not starve the others. Paid tiers get more.

## Core entities

- **Conversation.** Id, owner, model, created time.
- **Message.** Conversation, role (`user` or `assistant`), text, token count. Append-only.
- **Run.** One generation: conversation, state (`queued`, `running`, `done`, `cancelled`), the GPU worker.
- **Tier.** Per user: request and token budgets.

## API

- `POST /v1/conversations/{id}/messages` with the prompt. Returns a stream of events, then the message id.
- `GET /v1/runs/{id}/stream` with `Last-Event-ID`, a header that carries the number of the last event the client saw. Resumes a stream.
- `POST /v1/runs/{id}/cancel` stops a generation.
- `GET /v1/conversations/{id}` and `GET /v1/conversations` return messages and the chat list.

### Why SSE and not a WebSocket

Data flows one way: tokens go from server to client. The client sends one prompt, then waits. Server-sent events (SSE, lesson [2.5](/learn/02-networking/real-time-transport/)) fit this. The server keeps one HTTP response open and writes small events into it, like a person reading a letter aloud one line at a time. It is plain HTTP, and it passes through proxies and load balancers. It has a built-in resume: each event may carry an `id`, and a browser that reconnects sends `Last-Event-ID`. OpenAI's API docs describe streaming over server-sent events with `stream=true`. They also say that without it, the API generates the whole output before it sends anything.

A WebSocket works too, but you must build reconnect and resume yourself. Choose it only if the client sends frequent messages in the middle of a run.

## Deep dives

### GPU scheduling

A GPU runs a model one **iteration** at a time. Each iteration makes one token for every request in the current batch. Batching matters because the cost of an iteration grows slowly with batch size. The model weights are the learned numbers that make up the model, and they can be many gigabytes. Each iteration must read all of them from GPU memory. That read is the slow part. A batch reads the weights once and uses them for every request in it. Think of a bus: the trip costs nearly the same with 2 riders or 30, so a full bus moves more people per litre of fuel. A bigger batch means more tokens per second per GPU.

The simple way is **static batching**: fill a batch, run it until every request finishes, then start the next. It wastes capacity, because requests differ in length. Step through both ways.

<ChatgptBatching client:visible />

The Orca research paper (2022) named the better scheme **iteration-level scheduling**. The scheduler decides again after every iteration, so a finished request leaves at once and a waiting one joins. Other systems call it continuous batching. The paper describes the static problem in the same terms: requests that finish early cannot return to the client. New requests wait for the whole batch.

Memory is the second limit. For each running request the GPU holds a cache of the attention data for every token so far. This cache is called the **KV cache**. Long conversations use more of it. So the number of requests a GPU can hold at once depends on memory and context length. Speed is not the only factor. The scheduler admits a request only if there is room.

Three more rules finish the picture.

- **Priority by tier, with aging.** Paid requests go first, but a free request that has waited long moves up. Otherwise the free tier starves.
- **Shed load on purpose.** If the queue wait would pass a limit, answer a free-tier request with a polite "busy" and a retry time. A user told "try in 30 seconds" is better off than one who stares at a spinner for two minutes.
- **Cancel frees the slot.** When the user presses stop, or the connection stays gone past a grace period, the worker stops that request. Otherwise a closed tab keeps burning a GPU slot.

### Streaming that survives a drop and a deploy

If the stream is tied to one connection and one process, then a phone that changes network, or a deploy that restarts a gateway, kills the answer, and the GPU time is wasted.

Separate the **run** from the **connection**. This is the long-running task pattern of lesson [9.7](/learn/09-patterns/long-running-tasks/).

1. The API creates a run with an id and returns it.
2. The GPU worker writes each token to a buffer under that run id, with an increasing sequence number. Any fast, append-only store serves: a log, or a Redis stream. Redis is an in-memory data store that answers in about a millisecond (lesson [8.2](/learn/08-technologies/redis/)).
3. The stream gateway reads the buffer and sends each token as an SSE event. The gateway uses the sequence number as the event `id`.
4. The connection dies. The run does not. The worker keeps writing.
5. The client reconnects, to any gateway, with `Last-Event-ID: 212`. The gateway reads the buffer from 213 and continues.
6. When the run ends, the final message is written once to the conversation store, keyed by the run id. So a retry cannot store the message twice (lesson [3.4](/learn/03-api-design/idempotency/)).

A gateway deploy now costs a reconnect, not an answer. Keep the buffer for some minutes after the run ends, so a late reconnect still gets the tail.

### Limits per tier

Counting requests is not enough. One request with a 100,000-token prompt costs a thousand times more than one with 100. OpenAI's rate-limit guide lists limits in requests per minute, requests per day, and tokens per minute. The guide says you can hit any of them first. These are API limits, but the lesson is general: limit what costs money.

Use two token buckets per user (lesson [7.4](/learn/07-reliability/rate-limiting/)), one for requests and one for tokens. The token cost is unknown until the answer ends. So charge a worst-case amount at admission. That amount is prompt tokens plus the maximum answer length. Refund the unused part when the run ends. The buckets live in Redis, which is fast enough to check on every request. An empty bucket gets the HTTP status `429` ("too many requests") with a `Retry-After` header that says how many seconds to wait, as OpenAI's guide describes.

### Conversation storage and context cost

Messages are written once and read in order. The access pattern fits a wide-column or key-value store (lessons [8.3](/learn/08-technologies/cassandra/) and [8.4](/learn/08-technologies/dynamodb/)). Use the conversation id as the partition key, which decides the machine that stores the row, so one chat stays together. Use a sequence number as the sort key, which keeps messages in order inside it. The chat list is a second table keyed by user, sorted by last activity.

The model has no memory. Each turn, the context builder sends the history again, as part of the prompt. The most text a model can read in one go is its **context window**. That is the cost driver. Suppose 20 turns, each adding about 300 tokens (a question and an answer). Turn n sends about 300 x n tokens. The total over 20 turns is 300 x (1 + 2 + ... + 20). That is 300 x 210 = 63,000 tokens, but only 6,000 are new. That is 10.5 times the new text.

Keep the history inside a budget. Drop the oldest turns, or replace them with a short summary. Say the price out loud: the model forgets what you trimmed, and a summary can lose detail.

Storage is small next to compute. At 1 billion prompts and 1 billion answers a day, that is 2 billion messages. At 2 KB each, that is 4 TB a day, or about 1.5 PB a year. It is large, but it is cold, append-only data.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| SSE | Plain HTTP, built-in resume | One-way only | Server-to-client streams |
| WebSocket | Two-way messages in a run | Build reconnect and resume yourself | The client interrupts or steers mid-run |
| Static batching | Simple scheduler | Idle slots, long waits | Small, uniform jobs |
| Continuous batching | High GPU use, short waits | A scheduler that tracks memory | Variable-length generation |
| Charge worst case, refund later | Cannot overspend a budget | Brief over-counting | Cost unknown until the end |
| Summarize old turns | Lower cost per turn | The model may forget detail | Long conversations |

<Callout type="tip">
Lead with the scarce resource: "The GPU is the bottleneck, so the design is a queue and a scheduler in front of it." Then the user-facing parts: SSE for tokens, a run id for resume, token buckets for fairness. Quote the Little's law step: concurrency equals rate times time.
</Callout>

<Callout type="mistake">
Do not answer "add more GPUs" first. Queue and batching come before that. Do not count only requests in the limiter, because cost follows tokens. Do not tie the generation to one HTTP connection. And do not call a WebSocket necessary for streaming just because it sounds more real-time.
</Callout>

<Callout type="deep" title="Time to first token and the prompt">
The first token is slow because the model must read the whole prompt before it can write anything. This step is called prefill. After it, each new token needs one iteration. A 60,000-token prompt makes prefill long. The later steps, one new token per iteration, are called decode. Prefill running on a GPU can slow the decode iterations of other requests in the same batch. Some systems run the two phases on different machines for this reason. For an interview, one sentence is enough: first-token time grows with prompt length, and long prompts are the expensive ones.
</Callout>
