Ten thousand units of a budget phone go on sale at 12:00 IST. Ten million people want them. Most systems spread load over many rows and many servers. Here every request wants the same row. Adding servers does not help, because the bottleneck is one number. The new ideas: extreme contention on one counter, an atomic decrement in Redis, a waiting room, and a reconcile step back to the database. **Atomic** means one step that nothing can interrupt: it happens fully or not at all, and no other request sees it half done. To **decrement** is to subtract 1. To **reconcile** is to compare two records of the same fact and fix the one that is wrong. Redis is a very fast in-memory store for small values such as counters.

## Requirements

**Functional.**

1. Users view the sale item and see whether stock remains.
2. Users reserve one unit for a short time while the sale is on.
3. Users pay by UPI or card for the reserved unit.

**Below the line.** Catalog search, shipping, returns, refunds, order history, and the admin screen that sets up a sale.

**Non-functional.** The sizes below are assumptions, chosen to be hostile.

- **Zero oversell.** Never sell a unit that does not exist.
- 10,000 units. 10 million users arrive within seconds of the start.
- An abandoned reservation returns its unit to stock. No unit is held forever.
- The admission rule is fair and stated in advance. The rule is arrival order, or a lottery among everyone who joined before the start.
- The database and the payment provider must not fall over.

For a sense of real peaks: Shopify's engineering team wrote that on its cloud in 2021 its Black Friday and Cyber Monday peak "surpassed 32 million app server requests per minute", and that one flash sale used over 20% of its total computing capacity at its peak. That is hundreds of thousands of requests per second across all merchants. Our single sale is a spike of the same order, aimed at one item.

## Core entities

- **Sale.** Item, start time, end time, stock.
- **Stock counter.** The number of units left. Lives in Redis.
- **Reservation.** Sale, user, expiry time, status: `held`, `paid`, or `expired`.
- **Order.** A paid reservation plus the payment reference.

## API

- `GET /v1/sales/{id}` returns the item and `open`, `sold_out`, or `not_started`.
- `POST /v1/sales/{id}/reservations` returns a reservation id and `expires_at`, or `409` when sold out.
- `POST /v1/reservations/{id}/pay` takes a payment token and returns the order.
- `GET /v1/sales/{id}/queue` returns the waiting-room position and, when it is your turn, an admission token.

## Deep dives

### Never oversell

Start with the obvious design, then the fix.

<FlashSaleOversell client:visible />

The naive design reads, checks, and writes in three steps. Between the read and the write, the world changes. This is the check-then-act race from the [Dealing with Contention](/learn/backend/09-patterns/contention/) lesson. Making the row lock bigger is the usual first fix: `SELECT ... FOR UPDATE` on the product row. It is correct. It is also a queue of one. Only one reservation can hold the lock at a time, so the best case is one reservation per hold time. With a hold of a few milliseconds, that is only a few hundred reservations per second. For 10 million users that is hopeless.

Redis (the [Redis](/learn/backend/08-technologies/redis/) lesson) runs commands one at a time on one thread. So a single `DECR` (decrement by 1 and return the new value) is atomic, and it takes microseconds, not milliseconds. Two buyers sending `DECR` at the same instant get two different answers, never the same one. A few details matter.

- **Seed the key first.** Redis docs say that if the key does not exist, it is set to 0 before the decrement. An unseeded counter starts at -1. Set it to 10,000 before the sale opens.
- **A negative result means "none left".** The API sends `INCR` to put the unit back, and answers `409`. The counter dips below zero for a moment, but nobody is ever given a unit from it.
- **A Lua script avoids the dip.** Lua is a small scripting language that Redis can run inside the server. The Redis docs guarantee that a script runs atomically, with other activity blocked while it runs. This script does the check and the decrement in one step.

```lua
local left = tonumber(redis.call('GET', KEYS[1]))
if left and left > 0 then
  return redis.call('DECR', KEYS[1])
end
return -1
```

- **One per person.** Before the decrement, run `SET reserved:sale:user NX`. The `NX` flag means "only if the key does not exist yet". So it succeeds only for a first attempt. A second attempt gets `409` without touching the counter.

### Holding stock while someone pays

Payment can take 10 seconds or more. Do not hold a database lock for that time. The reservation row is the hold. It has an `expires_at`, set to about 5 minutes from creation.

Two things can happen to a `held` reservation, and they can happen at the same moment. The user pays, or the sweeper expires it. Make both moves conditional on the status. Payment runs `UPDATE ... SET status='paid' WHERE id=? AND status='held'`. The sweeper runs `SET status='expired' WHERE status='held' AND expires_at < now()`. Whichever statement runs first wins. The other changes zero rows. The sweeper is a background job that runs every few seconds. It adds 1 to the counter only for rows it changed.

### Surviving the burst

Ten million users, each reloading every few seconds, send millions of requests per second. The CDN (the [CDN and Proxies](/learn/backend/02-networking/cdn-proxies/) lesson) absorbs page views. But every user also wants to press reserve at 12:00:00.

A **waiting room** is admission control at the edge, the way a metro gate lets people in a few at a time so the room never overfills. Users who arrive get a place in line, and a token when their turn comes. The Sale API accepts only requests with a valid token, so the API and Redis see the rate we choose. It is a rate limiter (the [Rate Limiting Algorithms](/learn/backend/07-reliability/rate-limiting/) lesson) that holds users in a queue instead of rejecting them.

Pick the rate from the slowest part. Say Redis and the reservation table can take a few thousand reservations per second with room to spare. Then the waiting room admits that many users per second, and no more.

Fairness is a policy, so state it. Arrival order rewards fast connections and bots. A lottery is more fair: everyone who joined the room before the sale starts gets a random position. When the counter reaches zero, the waiting room stops admitting. It tells everyone still in line "sold out" at once, so they do not wait for nothing.

### When the counter is wrong

Redis replication is asynchronous (the [Redis](/learn/backend/08-technologies/redis/) lesson). If the primary dies, a replica may be missing the latest decrements. The counter then reads higher than the truth, and units can be reserved twice.

Defend in two layers.

1. **A last gate in the database.** Before an order is created, run `UPDATE sales SET sold = sold + 1 WHERE id = ? AND sold < stock`. Only 10,000 payments ever reach this statement, so one row can take it. If it changes zero rows, the payment is refunded. A rare unlucky buyer gets a refund, but we never sell a 10,001st pair.
2. **A reconciler.** Every minute it counts paid orders and live reservations in the database. It sets the counter to stock minus that sum. The database is the record. Redis is a fast copy.

## Numbers

The sale is a short, huge spike. The edge sees millions of requests per second, so the CDN and the waiting room must take them. The waiting room admits only what the slowest part can take, so the stock is gone within seconds. After that every request is "sold out" and needs no call to Redis. Unpaid reservations return to stock later, so there is a small second wave. The waiting room stays open and announces the restock.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| `FOR UPDATE` on one row | Simple, correct, no new system | A few hundred reservations/s at best | Small sales |
| Redis `DECR` or Lua | Atomic, microseconds per call | Extra system, async replication risk | Large sales |
| Reservation with expiry | No lock during payment | A sweeper and a status race to handle | Always for slow payment |
| Waiting room | The load is the rate you choose | Users wait. Needs a fairness rule | Demand far beyond capacity |
| DB last gate plus reconciler | No oversell after Redis failover | A rare refund | Zero oversell is a hard rule |

<Callout type="tip">
Say the numbers first: "10,000 units, 10 million users: 99.9% must be rejected cheaply." Then the three tools in order: an atomic counter for correctness, a reservation with expiry for slow payment, a waiting room for the burst. Close with the layered check: "Redis is the fast gate, the database is the last gate."
</Callout>

<Callout type="mistake">
Do not answer "just add more servers". The bottleneck is one counter. Do not read the stock, then write it. Do not forget to seed the counter. Do not claim Redis is durable enough to be the only record. And do not hold a database lock open while a card is charged.
</Callout>

<Callout type="deep" title="Sharding the counter">
If one Redis shard is still the limit, split the stock: 10 shards with 1,000 units each. A request picks a random shard and falls through to the next if it is empty. Contention drops tenfold. The cost: the last units are scattered. A request may see "empty" on one shard while another has 3 left. Use this only when one counter truly cannot keep up. When the waiting room already limits admissions to what one counter can take, it cannot be the answer.
</Callout>
