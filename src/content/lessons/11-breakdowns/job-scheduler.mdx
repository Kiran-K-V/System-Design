Billing runs on the first of the month. A report goes out every morning at 10:00. A reminder fires 24 hours after sign-up. All of these are "run this later". A job scheduler is the system that remembers and does it. This case study follows the six steps of [lesson 0.3](/learn/00-orientation/design-method/).

This design comes from first principles and the earlier lessons, not from one company's write-up. Treat the numbers as assumptions. The new ideas are the **time-bucketed scan** that finds due jobs, and **leases** that make execution survive crashes. A lease is a time-limited right to do something, like a library loan: you hold it until the due date, and it returns to the shelf if you do not renew it. Both ideas are explained below.

## Requirements

**Functional.**

1. A user schedules a job to run now, at a future time, or on a repeat rule. For example, a repeat rule can say every day at 10:00.
2. A user checks the status of a job and its runs.

**Below the line.** Cancelling or editing a job, priorities, job dependencies (one job after another), and per-user quotas. Say so. Dependencies lead to workflow engines, which lesson [8.9](/learn/08-technologies/temporal/) covers.

**Non-functional.**

- A due job starts within 2 seconds of its time (assumption).
- A job never gets lost. We accept that a job may run more than once (at-least-once).
- Highly available: a machine failure does not stop the clock.
- Scale: 10,000 job runs start per second at peak (assumption).

### Scale, derived

- Runs due in one minute: one **bucket**. At peak that is hundreds of thousands of runs. Each is just an id and a time, so one bucket fits in the memory of one process. The scheduler can hold the whole next minute in memory.
- Run history: a run row is small, but there are hundreds of millions of runs a day. Keep a few days. Old runs are deleted or moved out.
- Concurrency: apply Little's Law (lesson [1.4](/learn/01-one-machine/estimation/)). Jobs in flight equal the start rate times the average job time. That is tens of thousands of running jobs, so hundreds of workers.
- Heartbeats: a heartbeat is a small "I am still alive" message that a worker sends on a timer. Every running job renews its lease on a timer, so heartbeats are a steady write load of thousands per second.

## Core entities

- **Task**: a reusable unit of work, named in code, such as `send_invoice`.
- **Job**: a task plus parameters plus a schedule. It has a `next_run_at` time.
- **Run**: one execution of a job for one due time. It has a status, an attempt number, a worker id, and a lease end time.

Why split job and run? A job lives for months. A run lives for one execution and can be retried. Status, retries, and leases belong to the run.

## API

```
POST /jobs        { task, params, run_at | cron }   -> { jobId }
# cron: a repeat rule such as "0 10 * * *" (every day at 10:00)
GET  /jobs/{id}   -> { job, lastRuns: [{ dueAt, status, attempts }] }
```

## Data flow

Job rows sit in a store. A scheduler turns "due soon" rows into runs. Runs travel through a queue to workers. Workers write their result back to the run row.

## High-level design

Three decisions need a reason.

**The store is indexed by time.** The scheduler asks one question over and over: "which jobs are due?" Keep an index on `next_run_at` (lesson [4.3](/learn/04-data/indexing/)). The job store can be a normal sharded database.

**The scheduler advances the schedule, not the worker.** When it creates a run, it also moves a repeating job to its next time, in one transaction. A transaction is a group of database writes that all happen or none do. A slow job then cannot push the next run later. You choose a policy for overlap: skip the next run if the last one is still going, or let them overlap. Say which one you pick.

**A queue sits between scheduler and workers.** Scheduling is cheap and exact in time. Work is slow and uneven. The queue (lesson [6.1](/learn/06-async/queues/)) lets each side scale on its own and absorbs a burst.

## Deep dives

### Finding due jobs fast

**Naive:** poll the whole table every second with `WHERE next_run_at <= now`. With a very large table, even an index range scan every second is wasteful. Many scheduler processes would also scan the same rows.

**Better:** a **time-bucketed scan with look-ahead**.

1. Cut time into buckets of one minute (assumption).
2. Shortly before a bucket starts, the scheduler reads the whole bucket from the store with one indexed range query. At peak that is hundreds of thousands of rows, read once.
3. It holds them in memory, ordered by time, and pushes each job to the ready queue when its time arrives. The 2-second target is met by the in-memory timer, not by a database poll.
4. A job created for less than a minute ahead is sent straight to the scheduler that owns it, and also saved in the store. Otherwise it would miss its bucket load.

The database sees one big read per minute per shard instead of a scan per second. The cost is memory (a small bucket per scheduler) and a small chance that a scheduler dies holding a bucket. The next section handles this.

### Many schedulers, one owner per shard

One scheduler is a single point of failure. Two schedulers reading the same bucket would start every job twice. So divide the job store into shards by job id (lesson [4.7](/learn/04-data/sharding/)). Each shard has exactly one **owner** scheduler at any time.

Ownership is a **lease** held in a small coordination service such as etcd or ZooKeeper, whose nodes agree on every answer even when some fail (lesson [8.8](/learn/08-technologies/zookeeper/)). The owner renews it. If the owner dies, the lease expires and another scheduler takes the shard and reloads its bucket from the store. A short gap is possible. Because the store is the truth and buckets are read ahead, the new owner can reload jobs that were due during the gap and run them late rather than lose them.

A rare mistake remains. A scheduler that is paused for a long time may wake up and push jobs after it lost ownership. The queue can then hold a duplicate. The run row decides: a worker must win a conditional update on the run before it works. Duplicates in the queue are harmless.

### Running a job: leases and heartbeats

This is the heart of the design. Compare two ways to claim a job.

<JobSchedulerCompare client:visible />

With **mark done first**, a crash after the claim loses the job. With a **lease**, the claim is a record that says "worker W has this until time T". The worker does the work, and then marks the run done. A heartbeat renews T while the work goes on. If the worker dies, no heartbeat comes, T passes, and another worker claims the run.

The claim is a conditional write on the run row. For example, the write says "set worker and lease end where the run is waiting, or its lease has ended". Only one worker can win it. This is a compare-and-set: write only if the value is still what you last saw. It is the same trick as the lock in lesson [8.2](/learn/08-technologies/redis/).

Choose the lease length from the job. Short leases recover fast but cause false timeouts when a worker is only slow. The queue lesson showed the same trade with visibility timeouts. A common rule is to renew at one third of the lease. For jobs that run for hours, see lesson [9.7](/learn/09-patterns/long-running-tasks/): use heartbeats plus progress checkpoints so a retry resumes, not restarts.

A worker that lost its lease but keeps running is a **zombie**. Give each claim an attempt number. When the worker writes its result, the store accepts it only if the attempt number is still current. This is a fencing token: a number that grows with each claim, so storage can refuse a stale holder. Lesson 8.8 explains it.

### At-least-once and idempotent tasks

Exactly-once execution is not on offer. A worker can finish the side effect and crash before it writes "done". The lease then expires and a second worker repeats the work. So the contract is **at-least-once**, and the task must be safe to repeat.

Make it safe with an idempotency key (lesson [3.4](/learn/03-api-design/idempotency/)). The key is the run id, or the pair (job id, due time). Pass it to every downstream call. "Send invoice email" becomes "send the invoice email with key `job42:2026-10-01`, and skip if that key was already used".

## Numbers

The load is a steady stream of starts, a large pool of running jobs, and a constant trickle of heartbeats. Heartbeats are a real write load. Batch them per worker if they grow.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Poll the table every second | Very simple | Load grows with table size; duplicate scans | Tiny scale |
| Time bucket with look-ahead | One read per bucket, exact in-memory timing | Memory, ownership logic | This scale |
| Mark done before running | No duplicate runs | Lost jobs on a crash | Almost never |
| Lease and heartbeat | No lost jobs | Duplicate runs, so tasks must be idempotent | Default |
| Short lease | Fast recovery | False timeouts for slow jobs | Short jobs |
| Long lease plus heartbeat | Few false timeouts | Heartbeat load, slower crash recovery | Long jobs |
| Workflow engine such as Temporal | Retries and state handled for you | A new system to run | Multi-step jobs |

## Interview lens

<Callout type="tip">
Say the contract first: "At-least-once, because a worker can crash between the work and the write. So every task takes an idempotency key." Interviewers listen for that sentence. Then show how due jobs are found: "A time bucket, read ahead, held in memory."
</Callout>

<Callout type="mistake">
Do not promise exactly-once execution. Do not run cron on every server, because every server will run the job. Do not poll the whole jobs table. Do not delete or mark a job before it has run.
</Callout>

<Callout type="deep" title="Why not a delay queue only?">
Some queues support delayed messages. They are enough for "run in 30 seconds". Long delays, such as a reminder in six months, strain them, and you cannot easily list or inspect pending jobs. A store with a time index keeps the long-range plan. The queue only carries the near future.
</Callout>
