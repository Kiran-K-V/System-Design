A stock trading app like a Zerodha-style or Groww-style broker looks like one system. It is two. The price side moves a huge number of tiny messages and can lose some. The order side moves few messages and can lose none. Good answers treat them separately. The new ideas here: fan-out from one exchange feed to many clients, an order that crosses to a system you do not control, an order state machine, and buying power that stays correct.

## Requirements

**Functional.**

1. Users see live prices for stocks.
2. Users place market and limit orders, and cancel them. A market order buys at the best price now. A limit order buys only at or below a price the user sets.
3. Users see the status of their orders.

**Below the line.** Trading outside market hours, ETFs, options, crypto, and a live order book view. Name them and set them aside.

**Non-functional.** I have found no public scale figure I can check for this design, so these are assumptions.

- Prices on screen are fresh within about 1 second.
- An order is never sent to the exchange twice.
- Buying power never goes negative because of accepted orders.
- Every change to an order is recorded for audit.

## Core entities

- **Account.** Cash and buying power. Buying power is the money the user may still spend on new orders: cash minus what open orders have already set aside.
- **Order.** Symbol, side, type, quantity, limit price, state, an idempotency key, and the exchange's order id.
- **Hold.** Money set aside for one open order.
- **Position.** How many shares of a symbol an account owns.
- **Execution.** One fill: quantity, price, time. A fill is a report from the exchange that some or all of your order has traded. An order can have several, such as 30 shares now and 70 later.
- **Quote.** The latest price of a symbol. A symbol is the short code of a stock, such as RELIANCE for Reliance Industries. Kept in a cache, not stored per tick.

## API

- `GET /v1/quotes/{symbol}` for a snapshot.
- `WS /v1/market/stream` opens a WebSocket, a connection that stays open so the server can push data at any time. Use it to subscribe to symbols and receive ticks.
- `POST /v1/orders` with an `Idempotency-Key` header. Returns `201` (the HTTP status code for "created") with the order in state `new`.
- `DELETE /v1/orders/{id}` asks for a cancel. Returns `202` (the status code for "accepted for processing, not done yet"), because the exchange has not agreed yet.
- `GET /v1/orders/{id}` returns the state and the fills.

The key header comes from the [Idempotency](/learn/backend/03-api-design/idempotency/) lesson. A phone on a weak signal will retry a `POST`. Without a key, a retry is a second purchase.

## High-level design

The diagram uses a few words that the sections below explain in full. The exchange is the market that matches buyers and sellers. It is run by someone else, such as NSE or BSE. A tick is one small price update. A fill is the exchange telling us that an order traded. The order side of the diagram handles money, so it is built for correctness. The price side is built for speed.

### Prices: one feed, many clients

An exchange sends a feed of trades. Each record names a symbol, a price, and a size. One reader consumes it. That is one stream in and, say, 2 million phones out. This is the "one to many" shape of the [Real-time Updates](/learn/backend/09-patterns/real-time-updates/) lesson.

Three choices keep it cheap.

- **Subscribe by symbol.** A phone watches maybe 5 symbols. Sending it all 5,000 would waste 99.9% of the bytes. The gateway keeps a map from symbol to sessions, and sends a tick only to sessions in the map.
- **Coalesce.** A busy symbol may trade many times a second. A human eye cannot use that. The gateway keeps the latest price per symbol and sends it once per second. Old ticks for the same symbol are dropped, not queued. The newest price is the only one that matters.
- **Push over a persistent connection.** WebSocket or SSE (the [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson). The alternative is each phone polling a database every second. That is 2 million reads a second, to learn nothing most of the time.

A new phone must see a price at once, before the next tick. That is the job of the quote cache: on subscribe, the gateway reads the latest price and sends it.

### Orders: the exchange is not yours

The order service does not decide whether a trade happens. The exchange does. So an order passes through states, and the state changes when the exchange speaks.

| State | Meaning | Next states |
|---|---|---|
| `new` | We stored it and placed a hold | `accepted`, `rejected`, `cancelled` |
| `accepted` | The exchange has it | `partially_filled`, `filled`, `cancelled` |
| `partially_filled` | Some shares traded | `partially_filled`, `filled`, `cancelled` |
| `filled` | All shares traded | none |
| `cancelled`, `rejected` | Over. The hold is released | none |

Three rules make the machine safe.

1. **Only legal moves.** A `filled` order cannot become `accepted`. The update is conditional on the current state, the same way as a conditional write in the [Transactions and Isolation](/learn/backend/04-data/transactions/) lesson.
2. **Messages repeat and arrive late.** The exchange gateway sees an acknowledgement twice, or sees a fill before the ack. Key every update by the exchange order id and fill id, so a repeat changes nothing. This is idempotency (the [Idempotency](/learn/backend/03-api-design/idempotency/) lesson) on the inbound side.
3. **A timeout is not a failure.** If the gateway sends an order and the reply never comes, the order may be live. Never resend blindly. Look it up by the id you sent first. Only resend if the exchange has no record.

A cancel follows the same path. It is a request, and the order is `cancelled` only when the exchange says so. A fill may win the race with the cancel. The user sees whichever one the exchange confirms.

## Deep dives

### The audit log

The non-functional list says every change to an order is recorded. The audit log does this job. It is an append-only table: rows are added and never edited or deleted. Think of a bank's paper ledger written in pen. Each row says what changed, the old state, the new state, the time, and which message caused it (for example, the exchange's fill id). Write the row in the same transaction as the state change, so no change exists without its record.

It exists for three reasons. Support can answer "what happened to my order?" Regulators can ask for a full history, and a broker must be able to give it. And engineers can replay the log to find a bug in the state machine. The size is small. Orders arrive at hundreds a second at peak (~600), and each makes a handful of rows. That is easy for one database.

### Keeping buying power correct

A user has ₹1,00,000 of buying power and sends two orders of ₹80,000 at the same time. Only one may pass.

<RobinhoodHold client:visible />

The conditional update is one case of the idea in the [Dealing with Contention](/learn/backend/09-patterns/contention/) lesson. This idea turns check-then-act into one atomic step. That step works on the row that is the source of truth. In SQL it reads `UPDATE accounts SET power = power - 80000 WHERE id = ? AND power >= 80000`, and the service reads the number of changed rows. In PostgreSQL's default isolation level (READ COMMITTED, where a statement sees only data that other transactions have already committed), a second update waits for the first. That second update re-checks its `WHERE` clause against the new row, so the second order sees ₹20,000. The hold row and the order row are inserted in the same transaction. Either both exist, or neither does.

The hold has a life cycle:

- On `new`, subtract the cost from buying power and record the hold.
- On `cancelled` or `rejected`, add it back and mark the hold released.
- On a fill, turn that part of the hold into a real debit and update the position.

A market order has no price. Hold an estimate: the last price plus a margin, say 5%. After the fill, release the difference. State that margin as your design choice.

If one account is very busy, a second way exists to get one order at a time. This way is a single writer per account (a partition keyed by account id). For a retail app, row-level conditional updates are enough. One account rarely makes more than a few orders a second.

### Where the load really is

The two halves differ by orders of magnitude, and so do their designs.

The price side is a fan-out problem. Millions of open sessions each watch a few symbols, and each symbol is sent about once a second. That adds up to millions of messages a second. So the price tier is its own set of stateless gateways, scaled by session count.

The order side is small by comparison: hundreds of orders a second at peak (~600). One relational database can take it. The order side is hard because of correctness, not volume.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Coalesce ticks to 1 per second | Large cut in outbound messages | Short spikes are hidden | Retail display. Not for algorithmic traders |
| Subscribe by symbol | Bytes only for watched symbols | Gateway keeps a subscription map | Always |
| Hold before sending | No overdraft, simple reasoning | A held amount is unavailable until released | Any app with limited buying power |
| One database for orders and cash | Hold and order commit together | One store to scale and fail over | Hundreds of orders a second |
| Wait for exchange confirm on cancel | Truthful state | The user sees `pending cancel` for a moment | Always. The exchange has the last word |

<Callout type="tip">
Split the problem out loud: "Prices are a fan-out problem. Orders are a consistency problem." Then give one number for each side and one mechanism: "ticks coalesce to one a second and go to symbol subscribers; orders hold buying power with a conditional update." Say the exchange is the source of truth for order state.
</Callout>

<Callout type="mistake">
Do not send every tick to every client. Do not treat the first HTTP response as the final order state. Do not read the balance, check it in code, and then write it. Do not retry an order after a timeout without an idempotency key and a lookup. And do not get pulled into building an order book unless the interviewer asks: it is below the line.
</Callout>

<Callout type="deep" title="Why a timeout is the worst case">
A reply that says `rejected` is clear. A reply that never arrives is not. The order may have reached the exchange, been filled, and lost its acknowledgement on the way back. If you release the hold and let the user retry, they can buy twice. The safe state for an unknown order is "pending, hold kept". A reconciliation job (a periodic check that compares our records with the exchange's and fixes any difference) later asks the exchange for its record, and moves the order to a final state.
</Callout>

## Further reading

- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html): in the default isolation level, a second `UPDATE` waits for the first. Then the second update re-checks its `WHERE` clause on the new row. This is why the conditional hold works.
- [Server-sent events (MDN)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events): the one-way push used for prices.
