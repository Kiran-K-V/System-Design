## The problem

A streamer goes live. A few hundred thousand people watch. Every viewer can type a comment. Each viewer sees the comments of all the others, within a second or two.

One comment is one write. But it must be shown to every viewer, so one write becomes hundreds of thousands of deliveries. The write path is easy. The **fan-out** (copying one item to many receivers) is the hard part.

This is the opposite of the previous case study. In the WhatsApp lesson ([WhatsApp](/learn/backend/11-breakdowns/whatsapp/)) each message has one or a few readers and must never be lost. Here each comment has a huge audience, and losing one is fine.

## Requirements

**Functional, above the line:**

1. A viewer posts a comment on a live video.
2. Viewers of that video see new comments as they are posted.
3. A viewer who joins late sees the most recent comments.

**Below the line:** replies, reactions, moderation, spam checks, searching old comments.

**Non-functional.** These are assumptions, not company figures:

- A comment shows up for other viewers in about a second.
- Availability beats consistency (the [CAP and PACELC](/learn/backend/04-data/cap-pacelc/) lesson). A viewer may miss a comment, or see two comments in a slightly different order than another viewer.
- Order only matters inside one video.
- Very different sizes at once: most videos have a few hundred viewers, a few have a million.

## Core entities

- **LiveVideo**: `video_id`, status.
- **Comment**: `comment_id`, `video_id`, `user_id`, text, `seq`. The `seq` is a number that grows within one video. It gives viewers a place to resume from.
- **Subscription** (in server memory only): `video_id` to the open connections for it.

## API

- `POST /videos/{id}/comments` with `{text}`. Returns `{comment_id}`.
- `GET /videos/{id}/comments?before=<seq>&limit=10`. A page of history (the [Pagination](/learn/backend/03-api-design/pagination/) lesson on cursors).
- `GET /videos/{id}/stream`. An SSE stream. SSE (server-sent events) is one long HTTP response that the server keeps open and writes new items into, like a tap that keeps dripping. After a drop, the browser reconnects with `Last-Event-ID` and the server resumes from there.

No data-flow section is needed. This is request-response plus one long-lived stream.

## High-level design

### Why SSE and not a WebSocket

Look at the direction of the data. Viewers send a comment now and then, and that is an ordinary POST. The server sends a constant stream down. Server-sent events (SSE) are made for this (the [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson).

| | SSE | WebSocket |
|---|---|---|
| Direction | Server to client | Both ways |
| Reconnect and resume | Built in, with `Last-Event-ID` | You build it |
| Transport | Plain HTTP, so proxies and CDNs understand it | Upgraded protocol, its own rules |
| Cost | A held HTTP response | A held socket plus framing state |
| Watch for | 6 connections per browser per domain on HTTP/1.1 (MDN) | More code and more moving parts |

A WebSocket would work here. It is not wrong. It is just more machinery than a one-way feed needs, and you would write the resume logic yourself. If the product later adds two-way features, revisit the choice. An example is live polls that viewers answer in the same socket.

## Deep dives

### Who receives which comment

A simple first idea is one topic for all comments, with every stream server subscribed. See what that does.

<LiveCommentsFanout client:visible />

The fix is the pub/sub rule from the [Pub/Sub and Logs](/learn/backend/06-async/pubsub-logs/) lesson: a **channel per video**. A stream server joins a channel only while it has a viewer of that video. This is a routing problem, so the [Consistent Hashing](/learn/backend/04-data/consistent-hashing/) lesson applies in one place. If one pub/sub node cannot carry all the channels, spread channels over nodes by `hash(video_id)`. Redis can run this layer (the [Redis](/learn/backend/08-technologies/redis/) lesson). Its pub/sub is at-most-once. That means a message is delivered zero or one times and is never retried, so a subscriber that is briefly disconnected misses it. That is acceptable here, because the comment is already saved and a missed comment costs the viewer only a moment.

### The hot video

Per-video channels fix the many-videos case. They do not fix the one-huge-video case. Picture a video with a million viewers and thousands of comments per second.

- Naive fan-out sends every comment to every viewer. That is billions of pushes per second. No fleet does that.
- No person can read thousands of comments per second anyway. A screen shows only a handful per second.
- So each viewer should receive about what a screen can show, not what the chat produces. That cuts the fan-out by hundreds of times, to a load a fleet can carry.

How do you cut it? **Sample**. A small aggregator keeps a small slice of the comments, such as one in a few hundred. The stream servers fan out only the sample. Everyone sees a lively, slightly thinned stream. Moderators and the store still see every comment.

When even the sample is too costly, drop push and use the CDN. A job writes the latest 100 to 200 comments as a small snapshot object once a second. Viewers poll the CDN edge (the [CDN and Proxies](/learn/backend/02-networking/cdn-proxies/) lesson). The origin serves one snapshot per edge location per second, which is almost nothing. The edge absorbs all the viewer polls. The price is delay: a second for the snapshot plus the poll interval, so a few seconds in total.

The write side can be hot too. A partition is one slice of the store, kept on one machine. If you assign slices by `video_id`, every comment of a popular video lands on the same machine, so that machine gets all 2,000 writes per second while the others sit idle (the [Sharding](/learn/backend/04-data/sharding/) lesson). The fix is a composite key, which joins two fields into one key, such as `(video_id, minute)`. Now each minute of a video can live on a different machine, and a read of recent comments touches only one or two slices. Order inside a video comes from time-sortable ids, not from a single counter (the [Distributed IDs and Time](/learn/backend/10-advanced/ids-and-time/) lesson).

### Disconnects and late joins

Phones drop connections. SSE gives you the resume: each event carries an `id` equal to the comment `seq`. The browser sends `Last-Event-ID` on reconnect. The server needs a short buffer of recent events to answer from. A time window is fine for a normal video. For the hot video it would be huge. So bound the buffer by count (say the last 200). If the viewer is further behind than that, skip ahead and reload the latest page. That is a graceful gap, and it is acceptable by the requirements.

If a stream server dies, all its viewers reconnect at once. Backoff (wait longer after each failed try) and jitter (add a random delay so clients do not retry in step) prevent a storm (the [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson).

Late joiners read the recent-comment cache (the [Scaling Reads](/learn/backend/09-patterns/scaling-reads/) lesson for the read pattern), then subscribe. Order matters here. Picture a viewer who reads history first and subscribes second. A comment posted between those two steps is in neither place, so the viewer never sees it. So subscribe first, then read history, and drop duplicates by `seq`. Now the worst case is that one comment arrives twice, and the `seq` number lets the client ignore the second copy.

## Numbers

All inputs are assumptions. The method is the [Back-of-Envelope Estimation](/learn/backend/01-one-machine/estimation/) lesson. The shape matters more than the figures.

- **Mega-stream push.** A million viewers times a few comments each per second is millions of pushes per second. That is heavy, but a fleet can do it.
- **Servers.** Each server holds a large number of connections, so a mega-stream needs only a handful of stream servers.
- **Sampling rate.** The sample is a small slice of the comments, sized to what a screen can show.
- **CDN snapshot.** Viewers poll the edge, not the origin. Origin load stays almost flat.
- **Everyday video.** A few hundred viewers and one comment per second is a trivial load. One server does it.

I found no primary source for any live-comment platform's real numbers, so none are quoted.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| SSE | Resume built in, plain HTTP | One way, browser connection limits | Feed flows server to client |
| WebSocket | Two-way, one channel | Resume and heartbeats are yours | Viewers also send often over the same link |
| One global topic | Trivial setup | Every server reads everything | Almost never |
| Channel per video | Servers read only what they serve | A subscribe step per viewer set | Many videos at once |
| Sampling | Bounded cost per viewer | Viewers do not see every comment | Mega-streams |
| CDN snapshots | Origin load almost flat | About 3 s delay, no push | Largest streams |

## Interview lens

<Callout type="tip">
Start by naming the direction: "Posting is a normal request. Seeing is a server push, so SSE." Then name the cost that explodes: "The write is one, the fan-out is a million. So I partition channels by video and I cap what each viewer receives." Offer the sampling or CDN fallback before you are asked.
</Callout>

<Callout type="mistake">
Three slips. Polling every second from every viewer (a million requests per second for data that mostly did not change). One global topic that every server reads. Promising exact order and no loss across the whole site (the requirements allow eventual and per-video order, and each demand costs a lot).
</Callout>

<Callout type="deep" title="Why drop comments on purpose?">
It feels wrong to drop data. But the screen is the limit. A viewer can only read a few comments per second, so sending 2,000 does not add value. The comment store and moderators still get all of them. You are choosing what to show, not what to keep.
</Callout>
