## The problem

A video site wants a page that shows the most viewed videos right now. A product team asks for "top 1,000 videos in the last hour, the last day, the last month, and all time". Views arrive all day. The list must stay fresh.

This is a **stream aggregation** problem. A stream is an endless flow of events. Aggregation turns many events into a few numbers. Here the numbers are one count per video, and a ranking on top of those counts.

The case adds three ideas to what you already know.

- Counts are kept per **time window**, so old views must leave the count.
- Exact counts are the default. An **approximate count** trades a small error for much less memory.
- The ranking is **precomputed**. Nobody sorts billions of rows on a request.

The mechanisms come from earlier lessons. Kafka is the [Kafka](/learn/backend/08-technologies/kafka/) lesson. Flink and its windows are the [Flink](/learn/backend/08-technologies/flink/) lesson. The sketch data structures are the [Big-data Structures](/learn/backend/10-advanced/big-data-structures/) lesson. This page shows how they fit together.

## Requirements

**Functional.**

1. A client asks for the top K videos, with K at most 1,000, for all time.
2. A client asks for the top K for the last hour, the last day, and the last month.

**Below the line.** Arbitrary time ranges, such as "last 37 minutes", and arbitrary start and end points. Say so out loud. They need a different design, such as a time-series database (the [Time Series Databases](/learn/backend/10-advanced/time-series/) lesson).

**Non-functional.** Every number below is an interview assumption, not a measured fact.

- Freshness: a view appears in the lists within about 1 minute.
- Read latency: tens of milliseconds.
- Precision: exact counts first. Approximation is a deep dive.
- Scale: 70 billion views per day and 4 billion videos.

### Derive the load

Use the method from the [Back-of-Envelope Estimation](/learn/backend/01-one-machine/estimation/) lesson. Three facts matter.

- The view rate is huge: ~810,000 views per second on average (70B a day, assumed). Peaks are higher.
- The counter table, one row per video, is small enough for one database (~64 GB). One count row per video is cheap. The write rate is the hard part.
- One database instance takes only about 10,000 writes per second in this model (assumption). One write per view would need dozens of instances.

The 70 billion figure is an assumption for a very large video site. We do not know the real number. The method matters more than the number.

## Deep dives

### Write volume: batch in the stream

The naive design runs `UPDATE counts SET views = views + 1` for every view. At that rate it needs dozens of instances and wastes most of the work. Many views hit the same video inside one second.

The stream job fixes this. It groups events by video id for one minute and writes one partial count per video. Many views hit the same videos, so one minute holds far fewer distinct videos than views. The store sees about **ten times fewer writes**. That is a handful of instances, not dozens.

The job keeps its sums in memory, in what Flink calls state (the [Flink](/learn/backend/08-technologies/flink/) lesson). A **checkpoint** is a saved copy of that state, taken every so often, like a save point in a game. A Kafka **offset** is the position of the last event the job has read in the log. The checkpoint stores the offset too. If the job crashes, it reloads the last checkpoint and reads the log again from that offset, so no view is lost or counted twice.

Some events arrive late. An example is a view sent by a phone that was offline. A **watermark** is the job's rule for how long to wait for stragglers before it closes a minute. Choose a delay of a few seconds. A longer delay means better counts and a slower list.

Shard the count store by video id (the [Sharding](/learn/backend/04-data/sharding/) lesson). One video belongs to one shard, so its count never needs a cross-shard sum. One very hot video is still one **hot key**: a single key that gets far more traffic than the others, so its shard becomes the bottleneck. A viral video may get more writes than one instance can take. The stream job already merges its views into one write per minute. That is why batching also solves the hot key here.

### Reading the top K

<TopkRead client:visible />

The better design gives up a little freshness. Readers see a list up to one refresh old. The assumption is 30 seconds, so the total delay stays inside the 1 minute goal.

The job keeps a **min-heap** of size K: a structure whose smallest item is always at the top. For each count, compare it with the smallest item in the heap. If it is bigger, swap it in. One pass over N counts costs about N log K steps. Memory is only K entries.

### Time windows

Two kinds of window are easy to mix up.

A **tumbling window** [mid] has a fixed size and no overlap. "10:00 to 11:00" is one. Each event belongs to exactly one window.

A **sliding window** [mid] has a fixed size and moves by a smaller step. "The last 60 minutes, updated every minute" is one. Each event belongs to several windows. In Flink, an event falls into size / slide windows. With size 60 minutes and slide 1 minute that is 60 windows. With hundreds of thousands of views a second, naive sliding means tens of millions of window updates a second. That is far too many.

The cheap method uses buckets.

1. The job writes one bucket per minute, as in the diagram.
2. For the last-hour list, keep a running count per video. Each minute, **add** the newest bucket and **subtract** the bucket that just left the window.
3. Do the same with hourly buckets for the day and month lists.

You pay for subtraction: you must keep the old buckets until they expire. For one hour that is 60 minute-buckets. That is a few GB in our model, which is fine.

<Callout type="mistake" title="One sorted set for every window">
A single sorted set (a Redis structure that keeps items ordered by a score, here the count; the [Redis](/learn/backend/08-technologies/redis/) lesson) of counts has no way to forget old views. Give each window its own key and let old buckets expire. Otherwise the last-hour list slowly turns into the all-time list.
</Callout>

### Approximate counts: heavy hitters

Exact counts fit here, which is fine. The trouble starts when the key space has no useful limit, such as every search query or every URL. Then exact counting does not fit in memory.

A **heavy hitter** [mid] is an item that makes up a large share of the total count. Top-K asks for exactly these items. You do not need exact counts for the long tail of rare items.

A **count-min sketch** [senior] is a grid of counters with `d` rows and `w` columns. Each row has its own hash function. To add an item, hash it once per row and add 1 to one counter in each row. To read an item, hash it the same way and return the **minimum** of its `d` counters. The [Big-data Structures](/learn/backend/10-advanced/big-data-structures/) lesson built this; here is a tiny run with `d = 2` and `w = 3`.

| Item | True views | Row 1 cell | Row 2 cell |
|---|---|---|---|
| A | 5 | 0 | 1 |
| B | 2 | 0 | 2 |
| C | 1 | 1 | 2 |

Row 1 ends as [7, 1, 0]: cell 0 holds A and B together. Row 2 ends as [0, 5, 3]: cell 2 holds B and C. The estimates are:

- A: min(7, 5) = 5. Correct.
- B: min(7, 3) = 3. The truth is 2, so B is **overcounted**.
- C: min(1, 3) = 1. Correct.

Collisions only add. So the minimum can overcount and can never undercount. Choose the size from two knobs: how much error you accept, and how sure you want to be. A wider grid gives a smaller error. More rows give higher confidence. The error is a share of the total count in the window, so it grows with traffic. In our model a sketch of a few MB keeps the error small enough that a video in the top 1,000 still ranks with confidence.

A sketch answers "how many views for video X". It cannot list the top K by itself. So pair it with a small heap of K candidates. On each event, update the sketch and read the estimate. Push the item into the heap if the estimate beats the heap minimum.

<Callout type="deep" title="Why not always use a sketch?">
At this scale exact counts are affordable and give a ranking nobody can argue with. A sketch adds error and a second structure to explain. Use it when the key space, not the event rate, is the problem. Say how much memory it saves when you propose it.
</Callout>

## Numbers

Treat every figure as an assumption. The shape matters. Views arrive at a rate no single database can take one by one. The count table itself is small. Batching per minute cuts writes by about ten times. A naive sliding window multiplies the work by the number of windows each event falls in.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| One write per view | Simple, always current | Dozens of instances, hot keys | Small traffic |
| Batch per minute in a stream job | Far fewer writes | Up to a minute of delay, a stream system to run | Large traffic, freshness of a minute is fine |
| Precomputed cached list | Fast reads, cheap | Lists are a refresh old | Read-heavy, small K |
| Exact counts | Exact ranking | Memory grows with keys | Keys fit in memory or on disk |
| Count-min sketch plus heap | Fixed memory | Overcounts, tail is fuzzy | Huge or unbounded key space |
| Bucket add and subtract | Cheap sliding windows | Keep old buckets | Rolling windows |

## Interview lens

<Callout type="tip">
Start with "reads are rare compared to views, so I precompute". Then give the write story: "views arrive at hundreds of thousands a second, so I batch in a stream job and write one partial count per video per minute". Name the freshness cost out loud. Offer the sketch last, and only if the interviewer widens the key space.
</Callout>

<Callout type="mistake">
Do not run `GROUP BY` and `ORDER BY` on every request. Do not say a count-min sketch can undercount. It can only overcount. Do not treat a sliding window as a tumbling window: the first overlaps, the second does not.
</Callout>
