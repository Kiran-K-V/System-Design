## The problem

A customer clicks "Pay". The server calls a card network through a **payment service provider** (PSP). A PSP is a company such as Stripe that talks to card networks and banks for you. The call takes two seconds. The customer's phone loses signal and the app retries.

If the design is careless, the customer is charged twice. Or the PSP takes the money and our server crashes before it saves anything. Then money has moved and nobody has a record.

Most systems can lose a like or show a stale count. A payment system cannot. This case study shows four ideas that make money safe. They are **idempotency keys**, a **state machine** with a saga, a **double-entry ledger**, and **reconciliation**. Each one is defined below, at first use.

## Requirements

**Functional.**

1. A merchant starts a payment for an amount.
2. A customer pays with a card.
3. The merchant sees the status: pending, succeeded, or failed.

**Below the line.** Saved cards, refunds, subscriptions, payouts to merchants, other payment methods, and reports.

**Non-functional.** The numbers are our assumptions.

- Peak load of 10,000 payments per second.
- No money is lost and no customer is charged twice, even if a service crashes at any moment.
- Every money movement is an auditable record that is never edited.
- Raw card numbers never reach our servers. The PSP gives us a **token**, a stand-in for the card.
- The status shown to a merchant may lag by a few seconds. The ledger must always be exact.

Notice the shape of the trade-off. This is a consistency-first system. It accepts slower and more careful steps to avoid one wrong cent.

## Core entities

- **Payment**: id, merchant, amount in the smallest unit (cents), currency, status, idempotency key, PSP reference.
- **Ledger entry**: id, payment, account, debit, credit, time. Entries are never updated.

A **ledger** is a list of every money movement, one line per entry, like a bank statement. Each entry has two money columns. A **debit** is an amount written in the left column. A **credit** is an amount written in the right column. Each entry fills one of the two. The one rule that matters here: for one payment, all debits add up to the same total as all credits. A worked example is in the ledger deep dive below.
- **Webhook event**: PSP event id (unique), type, payload, time processed.

Store money as an integer of cents plus a currency code. A float cannot hold 0.10 exactly, and errors add up over millions of payments.

## API

| Call | Purpose |
|---|---|
| `POST /v1/payments` | Amount, currency, merchant. Header `Idempotency-Key`. Returns 201 with status pending. |
| `GET /v1/payments/{id}` | Current status. |
| `POST /v1/webhooks/psp` | The PSP calls this with results. |

## High-level design

The order of steps inside the payment API matters more than the boxes.

1. Check the idempotency store. If this key was seen, return the saved response.
2. Write the payment row with status `pending` and commit it.
3. Call the PSP, passing the same idempotency key.
4. On the answer, or on a webhook, move the row forward and write the ledger entries in one transaction.

Write the row before you call the PSP. That single rule turns a crash from "money vanished" into "a pending row to resolve".

## Deep dive: idempotency keys

An **idempotency key** is a unique id the caller attaches to a request. The server stores the result under that key. A repeat with the same key returns the stored result and does not run the action again. Lesson [3.4](/learn/03-api-design/idempotency/) built this.

It is needed on two hops. The merchant sends a key to us, so the merchant's retries are safe. We send our own key to the PSP, so our retries are safe. Stripe's documentation says its idempotency layer saves the result of the first request for a key. It compares the parameters of later requests to the original. It also says that for API v1 keys may be removed after at least 24 hours. Plan for that: do not rely on a PSP key for retries that can come days later. Your own payment row is the long-term record.

Create the key once, when you create the payment row, and store it on the row. Never create a new key on a retry. A new key is a new payment.

## Deep dive: a crash after the PSP call

The worst moment is between "the PSP charged the card" and "we saved that". Compare two orders of work.

<PayCrash client:visible />

The better design is the pending-first rule plus a reused key. A **recovery job** scans for rows that are still `pending` after, say, one minute. For each one it repeats the PSP call with the stored key. Or instead, it asks the PSP for the payment by its reference. Then it moves the row to its final state.

### The state machine

A payment moves in one direction. Allow only these moves, and reject the rest:

| From | To | When |
|---|---|---|
| pending | succeeded | PSP says the card was charged |
| pending | failed | PSP says the card was declined |
| succeeded | refunded | A refund is made (below the line) |

A **state machine** is a fixed set of states and allowed moves. Writing the moves down means a late or repeated message cannot send a payment backward.

### Saga, not two-phase commit

A payment touches our database and the PSP. Two-phase commit (lesson [4.4](/learn/04-data/transactions/)) would need the PSP to take part in our transaction. It does not, and it would block while it waits. Use a **saga** instead (lesson [9.5](/learn/09-patterns/multi-step/)): a list of local steps, each with an undo.

| Step | Undo if a later step fails for good |
|---|---|
| Write pending row | Mark failed |
| Charge the card at the PSP | Void or refund at the PSP |
| Post ledger entries, mark succeeded | Post reversing entries |
| Tell the merchant | Retry. Nothing to undo |

An undo is a new action, not a rollback. A refund is a new money movement and gets its own ledger entries. A workflow engine such as Temporal (lesson [8.9](/learn/08-technologies/temporal/)) can run this list and remember where it stopped.

## Deep dive: the double-entry ledger

Do not keep one `balance` column and add to it. A bug or a crash leaves a number nobody can explain, and an update erases history.

**Double-entry bookkeeping** records each movement as two or more entries across accounts. The debits and credits of one movement add up to the same amount. Each account is one named place where money sits, such as "Merchant balance". An entry puts an amount on the debit side or the credit side of one account. Nobody has to trust one number. Anyone can add the two columns and see that they match. Entries are append-only. A balance is the sum of the entries of an account.

Example. A customer pays 2,000 cents (20.00 in the currency). Assume we keep 59 cents as a fee. The fee is invented for the example.

| Account | Debit | Credit |
|---|---|---|
| Cash held at PSP | 2,000 | |
| Merchant balance | | 1,941 |
| Fee revenue | | 59 |
| **Total** | **2,000** | **2,000** |

If the totals differ, something is wrong, and a check can find it. A refund adds the reverse entries. Nothing is deleted. The payment row and its entries commit in one local transaction (lesson [4.4](/learn/04-data/transactions/)). To keep that transaction on one machine, shard by payment id. So a payment and its entries share a shard (lesson [4.7](/learn/04-data/sharding/)).

## Deep dive: webhooks and reconciliation

A **webhook** is an HTTP call from the PSP to us when something changes. It can arrive late, twice, or in a different order. Stripe's documentation says it retries delivery for up to three days with exponential backoff in live mode. So the handler must be safe against all three.

- Verify the signature, so a stranger cannot fake a "paid" event.
- Store the PSP event id in a table with a unique constraint. A repeat finds the id and does nothing.
- Apply only forward moves of the state machine.
- Answer 200 quickly. Put heavy work on a queue (lesson [6.1](/learn/06-async/queues/)). A slow or failing handler makes the PSP retry.

**Reconciliation** is a job that compares two sources of truth. Each day it takes the PSP settlement report (the PSP's own daily list of the charges it made and the money it owes us) and our ledger and matches them by PSP reference. It flags three kinds of problem: money at the PSP with no ledger entry, a ledger entry with no PSP charge, and an amount that differs. Webhooks can be lost and code has bugs, so this job is the last net.

## Numbers

Assume 100M payments a day, 4 ledger rows per payment, and 400 bytes of rows per payment.

| Quantity | Math | Result |
|---|---|---|
| Average rate | 100M / 100,000 s | ~1,000 per second |
| Peak rate | given | 10,000 per second |
| Ledger inserts at peak | 10,000 x 4 | 40,000 rows per second |
| Storage per day | 100M x 400 B | 40 GB |
| Storage per year | 40 GB x 365 | ~14.6 TB |

Plan to shard by payment id, and size each shard from a limit you measure for your database. I give no per-node figure, because it depends on hardware and row size.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Write pending row first | A crash leaves a record to resolve | One extra write before the call | Always |
| Saga with undo steps | Works across the PSP | You write and test each undo | A step lives outside your database |
| Append-only double-entry ledger | Audit trail, checkable totals | More rows, balances need a sum or cache | Money is involved |
| One balance column | Simple, one write | No history, hard to audit | Never for real money |
| Sync response only | Simple flow | Misses late and lost outcomes | Never. Use webhooks and recovery too |
| Daily reconciliation | Finds drift that tests miss | Needs PSP reports, and people to fix mismatches | Always |

<Callout type="tip">
Say the crash story as a sequence: "I write pending first, call the PSP with the same key on every retry, and a recovery job resolves old pending rows." Then add: "The ledger is append-only double entry, and a daily reconciliation checks it against the PSP." That covers four ideas in two sentences.
</Callout>

<Callout type="mistake">
Do not say "two-phase commit with the PSP". The PSP is outside your transaction. Also do not treat the synchronous reply as final. A reply can time out while the charge still goes through. Do not use floats for money.
</Callout>
