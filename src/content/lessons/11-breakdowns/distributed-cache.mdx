Here the cache is the product, not a helper. You are asked to design the cache itself: a service that other teams use to store key-value pairs in memory. This case study follows the six steps of [the A Method for Any Design lesson](/learn/backend/00-orientation/design-method/). It adds little that is new in mechanism. It asks you to **combine** three earlier lessons and to find the one problem they do not solve: the hot key.

## Requirements

**Functional.**

1. Set, get, and delete a key.
2. Give each key an expiry time (TTL, time to live).
3. When memory is full, evict by LRU (least recently used first).

**Below the line.** Choosing the cache size, durability across restarts, strong consistency, complex queries, and transactions. Say these are out of scope. A cache is a copy. The source of truth is somewhere else.

**Non-functional.** These are interview **assumptions**.

- Highly available. Eventual consistency is fine.
- Under 10 ms per get or set.
- 1 TB of data and 100,000 requests per second.

### Scale, derived

- Nodes for the data. A node holds a slice of the data in RAM, so capacity is set by memory: a terabyte needs a few dozen nodes.
- Replicas. One extra copy of each range roughly doubles the node count.
- Load per node. If keys spread evenly, each node sees a small share of the request rate. Capacity is set by memory here, not by request rate.
- LRU overhead. A linked list is a chain of entries in which each one points to the one before and the one after. Those two pointers cost a small, fixed amount per entry. On large values that is nothing. On tiny values it is a big share. Small values make exact LRU costly.
- Latency. A round trip inside one data center is well under a millisecond (the [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson). One round trip from the client to the owning node leaves most of the 10 ms budget unused. A proxy in the middle adds a second hop. A client library that knows the ring avoids it.

## Core entities

- **Entry**: key, value, expiry time, last-access time.
- **Node**: one cache server with a set of positions on the hash ring.
- **Replica**: a copy of a node's key range, held on another node.

## API

```
GET    /cache/{key}                -> value | 404
PUT    /cache/{key}   { value, ttl }
DELETE /cache/{key}
```

In practice the client library speaks a compact binary format instead of text over HTTP, to save bytes and time. The HTTP shape above is only to show the contract.

### One node first

Start with the hot path of one machine. A hash map gives constant-time access: it finds a value from its key in one step, however many entries there are. A doubly linked list orders entries by last use, like a stack of papers where the one you touched last goes on top. A get moves the entry to the front. When memory is full, the node removes the entry at the back. The [Eviction](/learn/backend/05-caching/eviction/) lesson walks through it.

Exact LRU must update the list on every read, which means a lock on a shared structure. Real caches avoid that cost. Redis samples a few keys and evicts the least recently used of them. The default sample size is 5, and its docs report almost no loss on skewed access. Say you would take the approximation.

**TTL** is two mechanisms. A **lazy** check on read: if the entry is past its expiry, delete it and answer "miss". A **background sweep** samples entries and removes expired ones. This keeps memory from filling with dead data that nobody reads.

## Deep dives

### Placing keys: the ring

With 20 nodes, `hash(key) % 20` sends each key to a node. Going to 21 nodes changes `hash % N` for nearly everyone. Nearly all the keys move. Each moved key is a miss, so the database behind the cache takes almost all the traffic at once. The ring of the [Consistent Hashing](/learn/backend/04-data/consistent-hashing/) lesson moves only a small share, about one node's worth. The ring is a circle of positions. Each node sits at a point on the circle, and a key belongs to the first node you meet walking around from the key's own point. A new node takes over only the stretch just before it, so only the keys in that stretch move.

Use **virtual nodes**: each physical node owns many points on the ring, such as 128 (assumption). Many points per node smooth out the load, so no node gets a much larger arc than the rest. They also spread the load of a failed node over many survivors, not just its single neighbor. A binary search over the sorted points finds the owner quickly.

Where does the ring live? In the **client library**, loaded from a small config service that all nodes agree on (the [ZooKeeper / etcd](/learn/backend/08-technologies/zookeeper/) lesson). Clients refresh it when membership changes. A stale ring only sends a request to a node that no longer owns the key. That is a miss, not an error, which a cache can tolerate. Redis Cluster takes a related approach: 16,384 fixed numbered buckets, called hash slots, each key going to slot `hash(key) % 16,384` and each slot assigned to a node (the [Redis](/learn/backend/08-technologies/redis/) lesson).

### Replication for availability

If a node dies, its range is gone and its keys miss. Misses are survivable, but a whole range missing at once sends a spike to the database. Keep a copy: each key range is also stored on the next distinct node around the ring (the [Replication](/learn/backend/04-data/replication/) lesson). Skip virtual nodes that belong to the same machine.

Copy **asynchronously**. A write is acknowledged by the primary, and the copy follows. If the primary dies before the copy arrives, you lose a recent write. For a cache that costs a stale value or a miss, never the only copy of the data. This is the trade that eventual consistency gives you: lower write latency and higher availability, in return for stale reads.

When a node joins, it takes ranges from its neighbors, and those keys miss until they are filled. Warm it slowly, or accept a brief rise in database load.

### The hot key

Now the problem the ring cannot solve. A single key gets enormous traffic. A celebrity post, a flash-sale price, a global counter. All requests for one key hash to one node.

<DistributedCacheCompare client:visible />

**Adding nodes does not help**, because one key still lives on one node. Three tools:

1. **Near cache.** Each app server keeps the hot value in its own memory for a second or two (the [Cache Placement](/learn/backend/05-caching/cache-placement/) lesson). With a few hundred app servers, the owner then sees at most one read per app server per second for that key. The owner does not see every user read. The price is a value that is up to two seconds old.
2. **Read copies under suffixed names.** Store `hot#0` to `hot#3`. Names hash to different nodes. Readers pick one at random. A write updates every copy.
3. **Split a write-hot key.** A counter becomes sub-counters that are summed on read.

Detect hot keys by counting requests per key on each node over a short window. Treat only the top few as hot. A cache that treats every key this way pays the copy cost for no gain.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Modulo hashing | Trivial | Nearly all keys move on resize | Fixed-size cluster |
| Ring with virtual nodes | Only a small share of keys move; even load | Ring state in every client | Default |
| Smart client | No extra hop | Every language needs the library | Latency target is tight |
| Proxy tier | Thin clients, one place to change | Extra hop and extra machines | Many client languages |
| Async replicas | Fast writes, available reads | Stale reads, possible lost write | A cache |
| Exact LRU | Textbook behavior | Lock and 16 bytes per entry | Small caches |
| Sampled LRU | Cheap, nearly as good | Approximate | Large caches |
| Near cache for hot keys | Absorbs huge read load | Values a few seconds old | Read-hot keys |

## Interview lens

<Callout type="tip">
Name the combination: "Consistent hashing with virtual nodes places keys. Replicas on the next ring nodes give availability. Each node runs a hash map with an LRU list." Then raise the hot key yourself. "More nodes will not fix one hot key, so I would add a near cache and split write-hot keys." That shows you saw the limit of the ring.
</Callout>

<Callout type="mistake">
Do not say "shard with modulo". Do not claim strong consistency across replicas and low latency at once. Do not say a cache is durable. And do not say "add more nodes" for a hot key.
</Callout>

<Callout type="deep" title="Why a cache can be sloppy">
A cache holds copies. If a copy is lost or stale, the system falls back to the source of truth. That is why we can pick asynchronous replication, approximate LRU, and a stale ring. The same choices would be wrong for a database. Always say what lives behind your cache.
</Callout>
