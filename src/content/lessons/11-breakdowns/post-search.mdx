A social site has billions of posts. A user types two words and expects the best matches in half a second. This case study follows the six steps of [lesson 0.3](/learn/00-orientation/design-method/). The new idea is to treat search as a **derived copy** of the posts. A change stream feeds that copy. The idea also keeps the fast-changing signal (likes) out of that copy.

## Requirements

**Functional.**

1. Users create posts and like posts.
2. Users search posts by keyword.
3. Users sort the results by recency or by like count.

**Below the line.** Fuzzy matching and typo correction, personalization, privacy filters, images and video, and a smart ranking model. Say so, then keep the ranking to two sort orders.

**Non-functional.** These are interview **assumptions**.

- The median search finishes in under 500 ms.
- A new post is searchable within about a minute.
- High request volume, high availability.
- Load: 10,000 new posts per second, 100,000 likes per second, 10,000 searches per second.

### Scale, derived

Lesson [1.4](/learn/01-one-machine/estimation/) gives the method. Show the math, because the answer shapes the design.

- Posts per day: 10,000 x 86,400 s = 864 million.
- Posts in ten years: 864,000,000 x 365 x 10 = about 3.15 trillion.
- Raw text: assume 500 bytes per post with its metadata. Then 3.15 x 10^12 x 500 B = about 1.6 PB.
- Index size: assume 20 distinct terms per post. Assume each entry in a posting list takes 8 bytes (a 64-bit post id). That is 160 bytes per post, so 3.15 x 10^12 x 160 B = about 500 TB.
- Shards: lesson [8.5](/learn/08-technologies/elasticsearch/) gives 10 GB to 50 GB per shard. At the very best, 500 TB / 50 GB = 10,000 shards. That is the full ten-year index, and it already says something: we cannot ask every shard on every search.
- Likes: 100,000 per second is 10 times the post rate. Likes will be the main write load, not posts.

## Core entities

- **Post**: id, author, text, created time. The id grows with time (lesson [10.5](/learn/10-advanced/ids-and-time/)).
- **Like**: post id, user id. We mostly need the count.
- **Index entry**: term, list of post ids (the posting list).

## API

```
POST /posts                       -> { postId }
POST /posts/{id}/like
GET  /search?q=&sort=recency|likes&cursor=   -> { posts[], nextCursor }
```

Results use cursor pagination, as in lesson [3.3](/learn/03-api-design/pagination/).

## Data flow

Two chains. The write chain turns a post into an index entry. The read chain turns a query into a ranked page of post ids. They meet only at the index.

## High-level design

Step through the build. Each step names its requirement.

<PostSearchBuild client:visible />

**Why not `LIKE '%word%'` in the posts table?** That reads every row. At trillions of rows it never finishes. A B-tree cannot help with a match in the middle of text (lesson [4.3](/learn/04-data/indexing/)). The **inverted index** flips the question: for each term, keep the list of posts that contain it. A two-word search then finds the posts in both lists. See the build-up in lesson 4.3.

**Why a change feed and not a second write?** If the application writes to the database and then to the index, one of the writes can fail. The two copies then differ for good. [Lesson 6.5](/learn/06-async/cdc/) shows this race. With **change data capture**, the database log is the single record of what happened. The index is rebuilt from it, and it can be replayed.

**Freshness budget.** The requirement is one minute. Add up the stages, with assumed worst cases: change capture 5 s, indexer batching 5 s, search engine refresh 1 s (the default of lesson 8.5), result cache 30 s. That is 41 s, under 60 s. If you raise the cache time to 60 s, you break the requirement.

## Deep dives

### Sharding the index

Lesson 8.5 showed the engine's default: documents are spread over shards by id. A search asks every shard (scatter-gather, lesson [4.7](/learn/04-data/sharding/)). That is simple and spreads load evenly. With 10,000 shards it is too much work for every query.

**Split by time first.** Put posts into time slices, such as one slice per week, and shard each slice by post id. The default sort is recency, so a search asks the newest slice first. It stops as soon as it has a full page. Most searches touch a few slices.

**The likes sort is harder.** The best post by likes may be in any slice. Two honest choices are available. You can limit the likes sort to a recent window (a product decision, so ask). Or you can keep a second, smaller index that holds only posts above a like threshold.

An alternative is to split by **term** instead of by post: each shard owns some terms. A one-word query then asks one shard. But a multi-word query needs lists from several shards, which must be shipped to one place to intersect. And a very common term makes its shard hot. Most engines choose split-by-post for these reasons.

### Ranking by likes without flooding the index

Look at the likes path with one viral post.

<PostSearchCompare client:visible />

The Likes store holds the exact count. The index holds a rough count, updated only when the exact count passes a power of 2. A post with 1,000,000 likes crosses 20 milestones, so it causes 20 index writes. At query time the query service takes the top candidates and re-reads their exact counts, then sorts. This is a **two-stage ranking**: a cheap, approximate first stage over many posts, and an exact second stage over few.

The honest cost: the first stage orders posts only up to a factor of 2. A post at 1,000 likes and one at 1,023 share a bucket. Take enough candidates that the re-rank sees every post in the top bucket. If a bucket is too crowded, use finer milestones near the top.

### Hot terms and the result cache

Search terms follow a skewed pattern. A few queries ("world cup final") arrive again and again. Without help, each repeat does a full scatter-gather. Put a result cache in front of the query service. The key is the normalized query plus the sort order and the page. Use a short TTL, chosen from the freshness budget above. Lesson [5.2](/learn/05-caching/cache-placement/) covers placement, and lesson [5.5](/learn/05-caching/invalidation-stampede/) covers a popular key expiring. In that case, use one refresher per key, not one per user.

Posting lists also have a hot-term problem. A common word has a huge list. When intersecting, start with the shortest list. Test those ids against the longer ones, so the cost follows the rare term.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Split index by post | Even load, simple | Every query asks every shard | Default, with time slices to cut fan-out |
| Split index by term | One-term query asks one shard | Hot terms, cross-shard intersect | Mostly single-term lookups |
| Index every like | Always-fresh sort | Index overwhelmed by writes | Small sites |
| Milestone likes plus re-rank | Few index writes, near-exact top | Approximate first stage | Heavy like traffic |
| Result cache | Cheap repeats | Results up to TTL old | Skewed query traffic |
| Change feed to index | Index follows the database exactly | Seconds of lag | Always, over dual writes |

## Interview lens

<Callout type="tip">
Lead with the split: "The database is the truth. The index is derived and rebuildable. A change feed connects them." Then spend your time on the part that is specific to this problem: likes. "A like changes a count, not the words, so I keep the exact count outside the index and index only milestones."
</Callout>

<Callout type="mistake">
Do not write to the database and the index from the application and call it done. Do not run `LIKE` over the posts table. Do not forget the cache TTL when you check the one-minute freshness limit.
</Callout>

<Callout type="deep" title="Phrase queries">
A search for "new york" as an exact phrase needs word positions in the posting lists. Or the search needs an index of word pairs. Both make the index bigger. If the interviewer asks, say you would store positions and accept the larger index. That is a stated cost, not a free feature.
</Callout>
