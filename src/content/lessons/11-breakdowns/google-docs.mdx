## The problem

Two people open the same document. Alice types a word at the start. Bob deletes a sentence at the end. Both press keys at the same moment, from two continents.

Both must see both changes within a fraction of a second. The two screens must end with identical text. Nobody's edit may vanish.

Real-time delivery is solved (lesson [9.3](/learn/09-patterns/real-time-updates/)). The new problem is **merging**: edits made at the same time, on copies that have not yet seen each other. This case study covers two ways to merge, **operational transform** (OT) and **CRDTs** (conflict-free replicated data types, explained below), and the server design around them. We keep to plain text. Rich formatting and permissions are below the line.

## Requirements

**Functional.**

1. Create a document.
2. Several users edit the same document at once.
3. Each user sees the others' edits in real time.
4. Each user sees the others' cursors and who is present.

**Below the line.** Rich text, comments, sharing and permissions. Version history is an add-on question. We cover it in the storage deep dive.

**Non-functional.** The numbers are assumptions. No company source gave us scale figures, so we state ours.

- An edit shows on other screens within about 100 ms.
- All copies end with the same text. No confirmed edit is lost.
- Storage for a long document stays bounded.
- At peak, 10M open connections (our assumption).

## Core entities

- **Document**: id, title, latest snapshot, head sequence number.
- **Operation**: document, sequence number, client, payload, the version it was based on.
- **Snapshot**: document, version, full text, time.
- **Presence**: document, user, cursor, last seen. This lives in memory and is never stored.

## API

| Call | Purpose |
|---|---|
| `POST /v1/docs` | Create. Returns the document id. |
| `GET /v1/docs/{id}` | Latest snapshot and head version. |
| `WS /v1/docs/{id}/session` | Operations up, operations down, presence both ways. |
| `GET /v1/docs/{id}/versions` | List of snapshots, for history. |

Opening a document is two steps. Fetch the snapshot over HTTP, then open the WebSocket (lesson [2.5](/learn/02-networking/real-time-transport/)) and ask for everything after the snapshot's version.

## High-level design

Step through the build.

<DocsBuild client:visible />

Two choices carry the design.

- **One collaboration server owns each active document.** All its editors connect to that server. It gives every operation a **sequence number**, so there is one agreed order. How a document finds its server is routing by a hash of the document id (lesson [4.8](/learn/04-data/consistent-hashing/)).
- **Edits are operations, not whole documents.** An operation is a small change: "insert X at position 1", "delete the character at position 2". Small changes can be merged. Whole texts cannot.
- **Every accepted operation goes into an operation log.** The log is an ordered list, only ever added to at the end, like the line items on a bank statement. The current text is whatever you get by replaying the log from the start. If the server crashes, the log is what it recovers from. A **snapshot** is a saved copy of the full text at one version, so you do not have to replay from the very start.

## Numbers

Assume millions of open connections at peak, a few tens of thousands of connections per collaboration server, and a small share of users typing at any moment. The batched client sends a few operations per second per typing user.

That gives a few hundred collaboration servers, millions of operations per second across the fleet, and a modest load on each server. One editor's log for an hour of typing is small, a few hundred kilobytes at most. These figures are assumptions. Measure them for your own stack.

The point is the shape. The load splits cleanly by document, because one document never needs two servers. So you scale by adding servers.

## Deep dive: merging concurrent edits

Look at the failure first. The naive design has each editor send its whole text and keeps the last arrival. Switch to the second design to see the fix, and step through both.

### Operational transform, by hand

**Operational transform** (OT) changes an incoming operation so that it still means the same thing after other operations have been applied. The server holds the order. Each operation is transformed against the operations that came before it and that its author had not seen.

Work the example. The text is `ABC`. Positions count from 0: A is 0, B is 1, C is 2.

| Step | Alice | Bob | Server |
|---|---|---|---|
| Start | ABC | ABC | ABC |
| Each edits | `insert(1, "X")` gives AXBC | `delete(2)` gives AB | ABC |
| Server takes Alice first | | | AXBC |
| Transform Bob against Alice | | `delete(2)` becomes `delete(3)` | |
| Server applies Bob | | | AXB |
| Alice receives `delete(3)` | AXBC becomes AXB | | |
| Bob receives `insert(1, "X")` | | AB becomes AXB | |

Why did `delete(2)` become `delete(3)`? Alice's insert went in at position 1, before position 2. Everything at position 1 or after moved one place right. Bob's C moved from 2 to 3. The transform rule for this pair is as follows. If the insert position is at or before the delete position, add 1 to the delete position.

Why does Bob's side keep `insert(1, "X")` unchanged? Bob's delete was at position 2, after position 1, so it does not move the insert.

Try the wrong way to see the point. If the server applied `delete(2)` to `AXBC` without the transform, it would delete B and give `AXC`. Alice's screen and the server would disagree with Bob's.

Two inserts at the same position are a tie. The rule is to break it the same way everywhere. For example, break it by client id, so every copy picks the same order.

### CRDT, the other way

A **CRDT** (conflict-free replicated data type) builds the merge into the data. For text, every character gets a unique id, for example a pair of client id and a counter. An insert says "put this new character after the character with id *(A, 4)*", not "at position 1". A delete marks the character as deleted, with a **tombstone**, and does not remove it. Since each operation names its neighbor by id, the operations can be applied in any order. This means every copy ends the same. This property is called **commutative**.

The cost is metadata. Each character carries an id, and tombstones stay until a cleanup. The gain is that no central server needs to order the edits, so replicas can merge while offline.

| | OT | CRDT |
|---|---|---|
| How edits are placed | By position, then transformed | By unique ids of neighbors |
| Needs a server to order | Yes, in the classic design | No. Any order works |
| Extra data | Small | An id per character, tombstones |
| Hard part | Transform rules for every pair of operation types | Memory growth and cleanup |
| Offline editing | Harder | Natural |

Neither one removes the need for a server. You still need storage, authentication, permissions, and fan-out, which means sending each edit to every other editor of the document. Do not say "CRDTs need no server". Figma's engineers wrote that they chose not to use OT. They called OT the standard multiplayer algorithm popularized by apps like Google Docs. That is their claim and their reasons for their own problem. We cover their approach in the In the Wild module. In an interview, pick one, say why, and state its price.

## Deep dive: one owner per document

If two servers both accept operations for the same document, each makes its own order. The copies diverge. So one server must own a document at a time.

Route by hash of document id (lesson [4.8](/learn/04-data/consistent-hashing/)). Record the owner with a lease, a claim that runs out unless the owner keeps renewing it, in a coordination service such as ZooKeeper or etcd (lesson [8.8](/learn/08-technologies/zookeeper/)). When the owner dies, the lease expires and another server takes over. The new owner loads the latest snapshot, replays the log after it, and clients reconnect. A client reports the last sequence number it saw and resends operations that were never acknowledged. The server drops repeats by client id and operation number.

The operation log is written before the server confirms. A server that confirms first and writes later loses confirmed edits when it crashes. The Diagnose below shows this.

## Deep dive: cursors and presence

Cursors change many times a second and nobody needs them after a restart. So:

- Keep them in memory on the owning server. Do not write them to a database.
- Throttle (limit the rate): a client sends a cursor update at most every 50 to 100 ms (our assumption).
- Send them only to other sessions on that document.
- Expire them. If no heartbeat, a small "still here" message, arrives for about 30 seconds (assumption), drop the user.

A cursor is a position, so it has the same problem as an edit. If Alice's cursor is at position 5 and Bob inserts 2 characters at position 1, Alice's cursor moves to 7. Transform cursors with the same rule as operations.

## Deep dive: storage stays bounded

An operation log grows forever. Replaying a year of edits to open a document would be slow. So a **snapshot job** saves the full text every N operations. Pick N so that replay is short.

To open a document or recover, load the latest snapshot and replay only a bounded number of operations, which is small. To read an old version, take the nearest snapshot before it and replay up to that point. Old log entries before a kept snapshot can be trimmed or moved to cold storage (lesson [8.11](/learn/08-technologies/blob-storage/)). This depends on how much history you promise.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| OT with a central server | Compact operations, simple ordering | Transform rules are hard to get right | You already run a central server |
| CRDT | Any-order merge, offline editing | Metadata and tombstones | Offline or peer-to-peer matters |
| One owner per document | One order, simple merge | Failover and routing work | Always |
| Cursors in memory | No database load | Lost on restart, which is fine | Always |
| Snapshot every N operations | Bounded replay and storage | A background job | Long documents |
| Whole-document last write wins | Trivial | Edits are lost | Never for co-editing |

Give the merge as a tiny example: "Alice inserts at 1, Bob deletes at 2, so Bob's delete becomes position 3." One worked example shows more understanding than a page of definitions. Then name the price of your pick: OT needs a central order, a CRDT carries an id per character.
</Callout>

<Callout type="mistake">
Do not say "lock the paragraph" or "last write wins". The first blocks people from editing. The second drops edits. Also do not write every cursor move to the database.
</Callout>
