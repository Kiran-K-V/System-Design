## The problem

A product has many services that need to reach users. The order service says "your parcel shipped". The auth service says "your OTP is 481516". Marketing says "festive sale: 50% off today".

Each service could call Apple, Google, an SMS vendor, and an email vendor by itself. Apple and Google each run a delivery service for the phones they make. Apple's is called **APNs** (Apple Push Notification service). Google's is called **FCM** (Firebase Cloud Messaging). An app cannot reach a phone directly. It hands the message to APNs or FCM, and they carry it to the phone, like a post office that knows every address. We call such a message a **push** notification, and APNs and FCM are the **push providers**. Each provider limits how fast you may send. Then every team writes its own retry code, its own opt-out check, and its own rate limits. One bad deploy sends a user 40 copies of one message.

A **notification system** is one shared service. Services send it a request. It decides whether to send, picks the channel, calls the outside **provider** (the vendor that really delivers the message), and records what happened.

This case study follows the six steps of the [design method](/learn/00-orientation/design-method/). It adds three new ideas: fan-out over several channels, priority lanes, and safe retries against unreliable vendors. It does not re-teach queues, retries, or rate limiting. It links to the lessons that do.

## Requirements

**Functional.**

1. A service sends one notification to one user over push, SMS, or email, now or at a set time.
2. A service sends a campaign: one message to a segment of users.
3. A user sets preferences: which channels are on, and quiet hours.

**Below the line.** Message templates, delivery analytics, an in-app inbox, and "no more than N per week" frequency caps across campaigns. Say so aloud and move on.

**Non-functional.** These numbers are our assumptions. Interview prompts give similar ones. We state them so the design has a target.

- 10M notifications per day on average. We design for bursts of 5,000 per second.
- An accepted notification is never silently dropped.
- An OTP reaches the SMS vendor within about 5 seconds, even during a campaign.
- A user never receives the same notification twice, even though the pipeline can redeliver (lesson [6.3](/learn/06-async/delivery-semantics/)).
- One user gets at most a set number of messages per hour.

The average rate is about 100 per second. The burst is about 50 times the average. The design is about the burst, not the average.

## Core entities

- **Notification**: id, user id, channel, priority, status, idempotency key, send time.
- **Campaign**: id, segment, template, send time.
- **Preference**: user id, channels that are off, quiet hours.
- **Delivery attempt**: notification id, provider, attempt number, result.

## API

| Call | Purpose |
|---|---|
| `POST /v1/notifications` | Body: user, channels, priority, send time, and an `idempotency_key`. Returns 202, the HTTP status for "accepted, not yet sent". |
| `POST /v1/campaigns` | Body: segment, template, send time. Returns 202. |
| `PUT /v1/users/{id}/preferences` | Set opt-outs and quiet hours. |
| `GET /v1/notifications/{id}` | Status per channel. |

The idempotency key comes from the caller (lesson [3.4](/learn/03-api-design/idempotency/)). A caller that retries after a timeout gets the same notification, not a second one.

Data flow is a simple chain here, so we skip a separate data-flow step.

## High-level design

Step through the build. Each step adds boxes for one requirement.

<NotifBuild client:visible />

Read the finished picture from left to right.

- The **intake API** answers fast. It validates, writes to a log, checks preferences, and enqueues. It never calls a vendor itself, so a slow vendor cannot slow the callers.
- Each **channel** has its own queue and worker pool (lesson [6.1](/learn/06-async/queues/)). The pools differ because the vendors differ. They have different latency, different limits, and different failure patterns.
- **Preferences** are checked before the enqueue. Dropping an unwanted message early is cheaper than dropping it after the work.
- **Campaigns** are expanded in the background. A 3M-user campaign becomes 3M small messages in the bulk lane. The API call itself finishes in milliseconds.
- A **key-value store** such as Redis (lesson [8.2](/learn/08-technologies/redis/)) keeps per-user token buckets and dedupe keys.
- **Failures** go to a retry queue, and after N tries to a dead-letter queue (lesson [6.4](/learn/06-async/backpressure-dlq/)).

## Deep dive: a campaign must not starve an OTP

The simplest queue design puts every message in one queue. It fails the first time marketing sends a big campaign. Compare the two designs.

<NotifLanes client:visible />

Picture a campaign that adds millions of SMS messages. The vendor limit caps how fast they leave. An OTP sent after the campaign waits about ten minutes (~600 seconds in our assumptions).

The fix has two parts.

1. **Lanes.** Each channel has an urgent lane and a bulk lane. Campaigns only write to bulk.
2. **Capped pools.** Bulk workers may use most of the vendor limit. Urgent workers keep a small slice in reserve. Without a cap, bulk workers would use the whole vendor quota. And an urgent message would hit the vendor limit and fail.

The cost is small. The campaign finishes a little later, and nobody is waiting on a campaign to the second.

How many workers do we need? Use the throughput rule from lesson [1.3](/learn/01-one-machine/throughput-vs-latency/): a worker's speed depends on how many calls it keeps in flight and how long each call takes. Size the bulk pool to fill its share of the vendor limit. Size the urgent pool to cover its small reserve.

Link to the sibling case: the [rate limiter](/learn/11-breakdowns/rate-limiter/) shows how a token bucket is built. Here we use one in two places: per user, and per vendor.

## Deep dive: retries without a storm

Vendors fail. They time out, answer 429 ("slow down") or 503. A worker must not give up after one try. It also must not retry at once. The reason is that a thousand workers retrying together can keep a struggling vendor down (lesson [7.2](/learn/07-reliability/timeouts-retries/)).

The rules we apply:

- **Backoff with jitter.** Wait 1 second, then about 2, then about 4, with random spread. Failed messages go to a retry queue with a delay, so a worker is never blocked while it waits.
- **Retry only what can work.** Retry timeouts, 429, and 5xx. Do not retry "invalid phone number". Send that to the dead-letter queue at once.
- **A circuit breaker per vendor** (lesson [7.3](/learn/07-reliability/circuit-breaker/)). When most calls fail, stop calling for a while. Messages wait in the queue, and the vendor gets room to recover. A second SMS vendor can take over for urgent traffic.
- **A limit on tries.** After N tries the message goes to the dead-letter queue. A person or a job can replay it when the vendor is back.

Vendors also publish quotas, and exceeding them gets you throttled. For example, FCM documents its throttling and quotas. Read the quota of the vendor you name in the interview and size the pool from it.

## Deep dive: no duplicates

Queues deliver at least once. A worker can send an SMS, get the vendor "ok", and crash before it acknowledges the queue message. The queue then gives the message to another worker, which sends it again.

You cannot get exactly-once from the queue. You make the send idempotent instead (lesson [3.4](/learn/03-api-design/idempotency/)).

- If the vendor supports an idempotency key, send the notification id as the key. The vendor drops the repeat.
- If it does not, keep a dedupe record. Before the send, check the key `notification_id + channel`. Then set it after a successful send.

Both leave a small window. A crash between "vendor accepted" and "record written" can still send twice. For a promo that is acceptable. For an OTP, a repeat is harmless because the code is the same. State this trade-off. Do not promise zero duplicates.

## Numbers

Treat the figures in this lesson as assumptions. Three facts matter. The burst is far above the average. A campaign is large enough to block a single shared queue for minutes. And the intake log is small enough for one database with a retention job (lesson [4.7](/learn/04-data/sharding/) covers sharding if rows grow). Lesson [1.5](/learn/01-one-machine/numbers-to-know/) lists the numbers worth knowing.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| One queue per channel and priority | No starvation, tuned pools | More queues and workers to run | Message classes differ in urgency |
| One shared queue | Simplest to run | A campaign blocks urgent messages | Very low volume only |
| Retry queue with backoff | Vendor gets room to recover | Delivery is later | Vendor errors are temporary |
| Dedupe store check | Fewer repeat sends | Extra lookup, a small gap remains | Repeats annoy users |
| Check preferences before enqueue | Cheap drops | Stale cache can send to an opt-out | Always, with a short cache TTL |

<Callout type="tip">
Name the threat and the fix in one breath: "A campaign can starve OTPs, so each channel has an urgent lane and a capped bulk lane." Then give one number: a 3M campaign behind a 5,000-per-second limit blocks a shared queue for about 10 minutes. Interviewers remember a fact they can check.
</Callout>

<Callout type="mistake">
Do not claim exactly-once delivery. Say "at-least-once from the queue, plus an idempotent send". Also do not call the vendor from the API request path. A slow vendor then stalls every caller.
</Callout>
