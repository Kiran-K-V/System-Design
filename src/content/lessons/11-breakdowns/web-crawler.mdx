## The problem

A search or AI team wants the text of a large part of the web. The job is simple to say: start from some pages, follow every link, and save the text.

Three things make it hard at scale.

- **Size.** Ten billion pages must be fetched in days, not years.
- **Other people's servers.** Every fetch uses a site's bandwidth and CPU. A crawler that fetches too fast looks like an attack, and sites block it. Sites also publish a small text file called `robots.txt` at a fixed address, such as `example.com/robots.txt`. It lists which paths a crawler may not visit. Think of a "staff only" sign on a door. Good crawlers read it before the first fetch and obey it.
- **Messy input.** Pages fail, time out, repeat, link in circles, and sometimes generate endless links on purpose.

This case adds four ideas. One is a **URL frontier** [mid] (the list of URLs still to fetch) with a queue per host. Others are politeness rules including `robots.txt`, dedupe by URL and by content hash, and DNS caching. It builds on queues (the [Queues](/learn/backend/06-async/queues/) lesson), retries and dead-letter queues (the [Backpressure and Dead-letter Queues](/learn/backend/06-async/backpressure-dlq/) lesson), and the Bloom filter (a small structure that answers "seen this before?" using little memory) from the [Big-data Structures](/learn/backend/10-advanced/big-data-structures/) lesson.

## Requirements

**Functional.**

1. Crawl the web starting from a set of seed URLs.
2. Extract the text of each page and store it for later processing.

**Below the line.** What happens to the text later (for example training a model or building an index), images and video, pages that need JavaScript to render, pages behind a login, and re-crawling for freshness. Name them and move on.

**Non-functional.** Numbers are interview assumptions.

- **Fault tolerance.** A failed fetch or a crashed worker must not lose work.
- **Politeness.** Obey `robots.txt` and never overload a site.
- **Efficiency.** Finish the crawl in under 5 days.

### Derive the load

Assume 10 billion pages. Assume the average page costs 2 MB of transfer with its inline resources. Of that, the HTML is about 30 KB (assumptions).

The page count and the deadline fix the shape of the system. The crawl must sustain tens of thousands of pages per second (~23,000 for 10 billion pages in 5 days). That is petabytes of transfer, far more than one network card can carry. So the fetchers must be spread over a fleet of machines, and a handful is enough for raw bandwidth. Storing only the HTML is far smaller than the transfer, because pages carry images and scripts that we do not keep.

The limit that matters in practice is not bandwidth. It is politeness, as the deep dive shows.

## Core entities

- **URL**: address, depth, status, and a pointer to its stored page.
- **Host**: a site name with its cached `robots.txt` rules and its last fetch time.
- **Page**: raw HTML and extracted text, kept in blob storage (the [Blob Storage and CDN](/learn/backend/08-technologies/blob-storage/) lesson).
- **Content hash**: a fingerprint of a page's text.

## Interface

This system has no user-facing API. The input is a list of seed URLs. The output is the extracted text in blob storage, with one metadata row per URL.

## Data flow

1. Take a URL from the frontier.
2. Check the host rules, then fetch the page.
3. Save the raw HTML to blob storage.
4. Parse it into text and a list of links.
5. Save the text. Check each link against what is already seen.
6. Put new links in the frontier. Repeat.

## Deep dives

### Politeness: one queue per host

<CrawlerQueues client:visible />

The naive frontier is one first-in-first-out queue. Pages link to pages on the same site, so the queue fills with runs of URLs from one host. Several workers then hit that host at once.

The Stanford information retrieval book describes a common design. Front queues order URLs by priority. Back queues each hold URLs from a **single host**. A table maps hosts to back queues. A heap (a structure that always gives you the smallest item first) holds, for each back queue, the earliest time that host may be contacted again. A worker takes the queue with the earliest ready time. The worker fetches one URL, then puts the host back with a new ready time. The book notes a rule of thumb: wait about ten times as long as the last fetch took.

A simple version fits in Redis (the [Redis](/learn/backend/08-technologies/redis/) lesson). One key per host holds a rate limit or lock, set with an expiry of one second. Compare with the rate limiters of the [Rate Limiting Algorithms](/learn/backend/07-reliability/rate-limiting/) lesson. A fetcher that cannot take the key picks another host.

Politeness has a cost. At 1 request per second per host, a crawler that wants tens of thousands of pages per second must keep tens of thousands of different hosts in flight. A huge host cannot be finished fast. A host with 10 million pages would take months at that pace. So set a page budget per host, or crawl its pages at a lower priority.

**`robots.txt`.** Before the first fetch from a host, download `/robots.txt` and cache the rules. The robots.txt rules say a crawler should not use a cached copy for more than 24 hours. They also say a parser must read at least 500 KB of the file. If the file is unreachable because of server or network errors, the crawler must assume **complete disallow**. These errors are status 500 to 599. If the file is simply unavailable (a client error such as 404), the crawler may access any resource. Mix these up and you either crawl a site that said no, or skip a site that said yes. Note the order: a failing server blocks you, a missing file frees you.

**DNS.** Each fetch needs the host's IP address (the [DNS](/learn/backend/02-networking/dns/) lesson). At tens of thousands of fetches per second, lookups would pile up and the resolver would become a bottleneck. Cache the answer per host and honor its TTL. One lookup then serves thousands of pages on the same host. Run a local resolver cache so workers share the result.

### Fault tolerance: stages, queues, retries

The naive crawler fetches, parses, and stores in one process. A crash in parsing throws away a download that took time and used someone else's bandwidth.

Split it into stages. The fetcher writes raw HTML to blob storage and hands over an id. The parser reads that id. Each stage reads from a queue with a visibility timeout (the [Queues](/learn/backend/06-async/queues/) lesson). If a worker dies, the message becomes visible again and another worker takes it. Delivery is at least once (the [Delivery Semantics](/learn/backend/06-async/delivery-semantics/) lesson), so the stages must be **idempotent**. Processing the same URL twice must give the same result, and not two copies.

Retry a failed fetch with backoff (wait longer after each failure) and jitter (add a random delay so retries do not arrive together) (the [Timeouts, Retries, Backoff](/learn/backend/07-reliability/timeouts-retries/) lesson). After 5 tries (assumption) move the URL to a dead-letter queue (the [Backpressure and Dead-letter Queues](/learn/backend/06-async/backpressure-dlq/) lesson). Retry some errors and not others. A timeout is worth another try. A 404 is not.

### Dedupe: by URL and by content

There are two different duplicates.

**The same URL, seen twice.** Many pages link to the same page. Without a check, the crawl loops forever. First **normalize** the URL. Lower-case the host, drop the fragment (the part after `#`), sort query parameters, and remove tracking parameters. Then check whether it has been seen.

An in-memory set of 10 billion URLs does not fit on one machine. Even if you hash each URL to 8 bytes, the hashes alone take tens of GB. Two ways to hold that:

- A sharded key-value store, split by hash (the [Sharding](/learn/backend/04-data/sharding/) lesson). Exact, but each check is a network call.
- A **Bloom filter** (the [Big-data Structures](/learn/backend/10-advanced/big-data-structures/) lesson). With a 1% false positive rate, the filter needs only about 10 bits per item, several times less memory than the hashes. A Bloom filter never says "unseen" about a URL it has seen, so it never causes a repeat fetch. But 1% of new URLs are wrongly called "seen". That is about 100 million pages never crawled at this scale. For a crawl of the web that loss is often acceptable. State it as a choice.

**Different URLs, the same page.** Mirrors, tracking links, and print versions have different URLs and the same content. Store a **content hash** [mid]: a fixed-size fingerprint of the page text, such as a 32-byte SHA-256. Index it, and skip pages whose hash is already known. This index is also large at this scale. This finds exact copies only. Pages that differ slightly need other near-duplicate methods; the Stanford book has a chapter on it.

**Crawler traps.** Some sites build endless links, such as a calendar with a "next month" link forever. Limit link depth (15 to 20 hops is a common assumption) and the number of pages per host. Normalizing URLs removes many accidental traps.

## Numbers

| Quantity | Value | Where it comes from |
|---|---|---|
| Total transfer | 20 PB | 10B x 2 MB (assumed) |
| Pages per second needed | ~23,000 | 10B / (5 x 86,400 s) |
| Bandwidth needed | ~370 Gbit/s | 23,148 x 2 MB x 8 |
| Pages per machine | 3,750 per second | 200 Gbit/s x 30% / 2 MB (assumed) |
| Machines | 7 minimum, 8 used | 23,148 / 3,750 |
| Raw HTML | 300 TB | 10B x 30 KB (assumed) |
| URL hashes | 80 GB | 10B x 8 B |
| Bloom filter, 1% false positives | ~12 GB | 10B x 9.6 bits |
| Content hashes | 320 GB | 10B x 32 B |
| 10M pages from one host | ~116 days | 10M / 86,400 at 1 per second |
| `robots.txt` cache | 24 hours at most | The robots.txt rules |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| One global queue | Simple | Bursts on one host | Never at scale |
| Queue per host with timers | Politeness, spread load | A scheduler, hot big hosts | Any real crawler |
| Staged workers and blob storage | No lost downloads | More moving parts | Fetches are costly |
| Sharded store for seen URLs | Exact | A network call per check | Exactness matters |
| Bloom filter for seen URLs | 12 GB instead of 80 GB | About 1% of new URLs skipped | A crawl may miss some pages |
| Content hash | Skips copies | An extra index | Many mirrors |

## Interview lens

<Callout type="tip">
Do the arithmetic early: "10 billion pages in 5 days is tens of thousands of pages per second, so many fetchers". Then say the real limit: "per-site politeness, so I keep one queue per host and a timer for each". Name the `robots.txt` rule for 5xx versus 4xx. Mention the Bloom filter trade-off with its false positive rate.
</Callout>

<Callout type="mistake">
Do not use one global queue and breadth-first search. Do not keep all seen URLs in a language set. Do not say a Bloom filter is exact. Do not pass whole pages through queues. Do not forget a limit on depth and pages per host.
</Callout>
