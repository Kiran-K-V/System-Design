Advertisers pay per click. So a click count is money. This case study follows the six steps of [lesson 0.3](/learn/00-orientation/design-method/). It adds one idea to what you know: counting a stream **exactly once in effect**, and proving the count with a second, slower path.

## Requirements

**Functional.**

1. A user clicks an ad and is redirected to the advertiser's site.
2. An advertiser asks for the clicks on an ad over a time range, with one-minute granularity.

**Below the line.** Ad targeting and serving, fraud and spam detection, conversion tracking, and cross-device identity. Say these are out of scope and move on.

**Non-functional.** The numbers below are interview **assumptions**, not measurements from a company.

- Peak load of 10,000 clicks per second, and 10 million active ads.
- Analytics queries answer in under one second.
- Counts appear within a minute or so (near real time).
- No click is lost.
- A click is never counted twice.

### Scale, derived

Assume 100 million clicks a day. Lesson [1.4](/learn/01-one-machine/estimation/) gives the method.

- Average rate: 100,000,000 / 86,400 s = about 1,160 clicks per second.
- Peak is 10,000 per second, about 8.6 times the average. The design must handle the peak, so size for 10,000.
- Raw volume: at 100 bytes per event (assumption), 100,000,000 x 100 B = 10 GB per day. That is about 3.65 TB per year. The stream carries 10,000 x 100 B = 1 MB per second at peak. That is small for Kafka.
- Aggregated volume: a row is (ad id, minute, count). A day has 1,440 minutes. A single ad has at most 1,440 rows a day. In total there are at most 100 million non-empty rows a day, because each click lands in one row. Real counts are far smaller, because many clicks share a row.

## Core entities

- **Click event**: click id, ad id, user id, event time.
- **Minute count**: ad id, minute, number of unique clicks.

## API

```
GET  /click?token=<signed token>            -> 302 to the advertiser
GET  /ads/{adId}/metrics?from=&to=&granularity=1m
                                            -> [{ minute, clicks }]
```

The ad server builds the click link. The **token** holds a unique click id, the ad id, an expiry time, and a signature (an HMAC, a keyed hash: a short code that changes if anyone edits the token). The signature is a short code made with a secret key, so only our ad server can make a valid one. The click service checks it, so a forged id is rejected. The token expiry also bounds how long we must remember an id. We use that below.

## Data flow

The problem is a chain: click, log, window count, stored row, query. A second chain runs beside it: raw log, batch recount, corrected row.

## High-level design

Step through the build. Each step names the requirement it answers.

One word in the diagram needs a plain meaning first. An **upsert** is a write keyed by a name, here (ad id, minute). If a row with that key exists, the write replaces its value. If not, the write creates the row. Think of writing a score on a whiteboard line labelled "ad 7, 12:01": you wipe the old number and write the new one. Doing it twice leaves the same number. Plain "add 40" would not. The **lake** in the diagram is cheap storage that keeps every raw click as files, for good.

<AdClickBuild client:visible />

Three choices need a reason.

**Log first, count later.** The click service writes to Kafka and redirects. It does not count. Counting is slow and can fail. A user must not wait for it. The log keeps every click while the counter is down. Delivery rules for this link are in lesson [6.3](/learn/06-async/delivery-semantics/).

**Key by ad id.** All clicks for one ad go to one partition, and so to one Flink task. That task can keep a running count per ad per window in its own state. See lesson [4.7](/learn/04-data/sharding/) for why the key decides everything.

**Pre-aggregate.** At query time we read at most 1,440 small rows, not a day of raw clicks. That is how the sub-second target is met.

## Deep dives

### Count once in effect

Lesson [8.7](/learn/08-technologies/flink/) said that Flink's exactly-once is about its **state**. After a crash, Flink restores the last checkpoint and replays the log. Some events are processed twice. The state counts them once. What leaves Flink to the outside world can still repeat, unless the sink is transactional or idempotent.

Run one crash through two sinks.

<AdClickCompare client:visible />

A **sink** is the place Flink writes its results to. The additive sink turns replay into double counting. The upsert sink turns replay into a no-op, a write that changes nothing. Two rules make the upsert safe:

1. The key is (ad id, minute). The value is the **full** count of the window, never a delta.
2. Replay must produce the same count. Event-time windows give this, because the window is defined by the event timestamps, not by when the job ran.

If the sink cannot upsert, use a transactional sink that commits with the checkpoint. That is heavier, so prefer the upsert here.

### Deduplicate by click id

Duplicates come from three places. The sources are a browser that retries, a user who double-clicks, and a bad actor who replays a link.

**Naive:** dedupe by user id. That throws away real clicks. A user can click two different ads, or the same ad on two days, and both are valid.

**Better:** dedupe by **click id**. The id is unique per ad impression, and it is signed. Because a token binds one click id to one ad id, a repeat always lands on the same Flink task. That task keeps a set of recent click ids in its checkpointed state and drops a repeat. The state restarts with the job, so the set survives a crash.

How long must it remember? Only as long as a token is valid. Assume a one-hour expiry. At peak that is 10,000 x 3,600 = 36 million ids. At 16 bytes each (assumption), that is 36,000,000 x 16 B = 576 MB across the whole job. Per task, that is a few MB. Without the token expiry we would have to remember ids forever.

Do not dedupe in the click service with "check a cache, then write to Kafka". If you mark the id first and the write fails, the retry is dropped and the click is lost. If you write first and the mark fails, the retry duplicates. Both orders have a gap. State inside the stream has no such gap. The reason is that the id set and the log offsets are saved by the same checkpoint. Lesson [3.4](/learn/03-api-design/idempotency/) covers the key idea.

### Reconcile with a batch recount

A stream result can be wrong in ways the stream cannot see. These include an event that arrives after its window was finalized, a bug in the job, or a bad deploy. The cure is a second path.

Every raw event is copied to the lake. After an hour is finished, a batch job recounts that hour from the raw events. The job drops duplicate click ids and compares the result to the rows from the stream. Where they differ, it overwrites the row. This is the **Lambda** style: a fast path with a small error, and a slow path that is correct. You pay for two code paths. You buy a number you can defend.

A small window of "allowed lateness" in Flink handles late events cheaply (lesson 8.7 explains watermarks). The batch job handles the rest.

### One hot ad

Keying by ad id has a cost. One ad that gets most of the traffic sends most clicks to one partition. This is the hot key of lesson [4.7](/learn/04-data/sharding/). Add a small random suffix to the key, such as `adId#0` to `adId#7`, so one ad spreads over eight tasks. Each task emits a partial count. A second step adds the partials into the final row. Dedupe still works if the suffix is derived from the click id, not chosen at random per event.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Stream only | One code path, low delay | Late events and bugs stay wrong | Small money at stake, or counts that are only a rough guide |
| Stream plus batch recount | Defensible numbers, fixes for late data | Two code paths, storage for raw events | Billing and reporting to advertisers |
| Query raw clicks at read time | Always exact | Seconds to minutes per query | Rare, ad hoc questions |
| Upsert sink | Replay is harmless | Needs deterministic windows | Default here |
| Transactional sink | Works for any sink that supports it | Output waits for checkpoint commit | Sink cannot upsert |

## Interview lens

<Callout type="tip">
Say where each guarantee lives. "Kafka keeps the click. Flink checkpoints keep the state. The upsert keeps the output safe to repeat. The batch recount keeps the whole system honest." Then name what you do not claim: "I do not promise the stream is always right, only that the batch corrects it within the hour."
</Callout>

<Callout type="mistake">
Do not say "Flink gives exactly-once, so we are done". That holds for Flink's state, not for the sink. Do not dedupe by user id. And do not read raw clicks at query time to avoid building a pipeline.
</Callout>

<Callout type="deep" title="Is batch reconciliation worth it?">
Some teams skip it and trust checkpoints. That is fine when the cost of a wrong count is low. When the count is a bill, the second path is cheap insurance. A wrong number shows up in an advertiser's invoice, not in your dashboard.
</Callout>
