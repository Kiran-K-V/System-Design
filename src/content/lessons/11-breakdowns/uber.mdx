## The problem

A rider taps "Book ride". Within a minute the system must find a free driver who is close, offer the ride, and confirm one match. Meanwhile every driver phone reports its position again and again.

Two things make this hard.

- **Location writes are huge.** Positions change all the time, and the system needs the latest one.
- **Matching is a race.** Many riders want the same few nearby drivers. One driver must never get two rides.

This case adds three ideas: high-rate location updates, proximity search for nearby drivers, and matching under contention. The proximity mechanism is in the [Proximity Search](/learn/backend/10-advanced/proximity-search/) lesson. The contention patterns are in the [Dealing with Contention](/learn/backend/09-patterns/contention/) lesson. Redis is the [Redis](/learn/backend/08-technologies/redis/) lesson.

All company-scale claims about Uber are left out here. They are unverified. Every number below is an interview assumption we derive.

## Requirements

**Functional.**

1. A rider enters pickup and destination and gets a fare estimate.
2. A rider requests a ride from that estimate.
3. The system matches the rider with a nearby, available driver.
4. The driver accepts or declines, then goes to pickup and drop-off.

**Below the line.** Ratings, scheduled rides, ride categories, payments, and abuse checks. Name them and move on.

**Non-functional.**

- Match within 1 minute, or tell the rider it failed.
- Strong consistency for assignment: one driver, at most one ride at a time.
- Handle a burst, such as many requests from one place after an IPL match or a big concert ends.
- Location data may be a few seconds stale. A driver moves 50 meters in a few seconds, so slightly old data is fine.

### Derive the load

Assume millions of drivers are online at peak (assumption, ~10 million). Each sends a position every few seconds.

- Writes: that is a stream of **millions of location writes per second** (~2 million).
- Memory: the latest position of every driver is a small record, so all of them together fit in RAM on one machine (~1 GB).

A database that stores history for every ping would need millions of durable writes a second. We do not need history to match a rider. We need only the latest position. That one fact shapes the design.

## Core entities

- **Rider**: asks for rides.
- **Driver**: has a vehicle and a status (available or busy).
- **Fare**: an estimate with pickup, destination, price, and arrival time.
- **Ride**: a trip from request to completion, with a state and timestamps.
- **Location**: a driver's latest latitude, longitude, and time.

## API

```
POST  /fare               { pickup, destination }        -> Fare
POST  /rides              { fareId }                     -> Ride
POST  /drivers/location   { lat, long }                  -> ok
PATCH /rides/:rideId      { action: "accept" | "decline" } -> Ride
```

The driver's id comes from the session token (the [Auth Basics](/learn/backend/03-api-design/auth/) lesson), not from the body. A caller must not be able to move another driver. Make `POST /rides` safe to retry with an idempotency key (the [Idempotency](/learn/backend/03-api-design/idempotency/) lesson). Otherwise a double tap books two cars.

## Deep dives

### Location writes

The naive design runs `UPDATE drivers SET lat=?, long=? WHERE id=?` on a relational database for each ping. At millions of writes per second it fails. Each write also leaves a new row version and a log record that nobody needs.

The better design keeps only the latest position in memory. Redis `GEOADD` stores a position under a member name (the driver id). The docs give its cost as O(log N) per item. A second `GEOADD` on the same member **replaces** the old position. So the store never grows past one entry per driver.

One Redis instance is not enough for millions of writes per second. The [Redis](/learn/backend/08-technologies/redis/) lesson shows that a single instance does tens of thousands of commands per second without pipelining. A single instance does more with pipelining, which sends many commands in one network trip. So we split the index. **Shard by place, not by driver id.** A search needs the neighbors of one point. If neighbors sit on different shards, every search becomes a scatter-gather over all shards (send the question to every shard, then merge the answers) (the [Sharding](/learn/backend/04-data/sharding/) lesson). With a shard per city or region, one search touches one shard.

Drivers near a region border are a corner case. Query the neighbor region too when the search circle crosses the border. That is a known cost of space-based sharding.

You can also cut the write rate. A parked driver can ping less often than a moving one. Say it as an option, with the trade-off: stale positions for slow drivers.

<Callout type="deep" title="Redis GEO has no per-driver expiry">
`GEOADD` keeps its data in a **sorted set**. This is a Redis structure that holds unique members, each with a number called a score, and keeps them ordered by score. A sorted set member has no time-to-live (an expiry timer) of its own. A driver who closes the app stays in the index forever. Fix it with a second sorted set that maps driver id to last-seen time. A sweeper removes drivers older than, say, 15 seconds from both sets. Without this, riders get matched to drivers who left minutes ago.
</Callout>

### Proximity search

The [Proximity Search](/learn/backend/10-advanced/proximity-search/) lesson explained **geohash** [mid]. The geohash is a code that turns a latitude and longitude into a short string. This way, nearby points share a prefix. Redis GEO stores each point as a geohash score in a sorted set. So a range scan on the score finds points in one area. A B-tree on two plain columns cannot do this well. The reason is that a range on latitude and a range on longitude do not combine into one scan.

The matching service runs `GEOSEARCH` with `FROMLONLAT`, `BYRADIUS`, and `ASC`. Redis added `GEOSEARCH` in version 6.2.0. The docs give its complexity as O(N + log M). N is the number of items in the grid cells that cover the circle. M is the number of items inside the shape. It is fast when the radius is small. Use a radius of about 2 km in a city and widen it in steps if nothing is found.

The search returns nearby drivers in distance order. Distance in a straight line is not the same as drive time. A driver 300 m away across a railway line or flyover may be 20 minutes away. Real systems re-rank the top few candidates with a routing source. Say this as an extension.

### Matching and double assignment

<UberLock client:visible />

Reach for the contention toolbox from the [Dealing with Contention](/learn/backend/09-patterns/contention/) lesson. The naive "read status, then write" fails because the check and the write are separate steps. An in-process lock does not help, because two matchers run on two servers.

A lock with a time limit works. Create `driver:17` only if it does not exist, with an expiry of 10 seconds. One matcher wins. If the winner crashes, the key expires and the driver is free again. A lock that ends by itself is a **lease** [senior].

Be honest about the limit. The [Redis](/learn/backend/08-technologies/redis/) lesson warns that a Redis lock is safe for efficiency but not proof against pauses and clock jumps. If a matcher pauses past the expiry, a second matcher may take the lock. Meanwhile, the first matcher still thinks it holds the lock. The final write to the driver or ride record should therefore carry a **fencing token**. This token is a number that grows with each lock grant. The record rejects a write if the token is too old (the [Consensus](/learn/backend/04-data/consensus/) lesson). A conditional update on the ride row gives the same protection with no extra system. An example is "set driver only if the ride is still unassigned".

**Unresponsive drivers.** The offer waits about 10 seconds. If the matching service holds that timer in memory, a restart loses it and the rider waits forever. A durable timer (Temporal, the [Temporal](/learn/backend/08-technologies/temporal/) lesson) survives restarts. With a 1 minute budget and 10 seconds per offer, one rider can try only a handful of drivers. The rider tries them one after another. That is why offers to the nearest few drivers are sometimes sent at once. The extra offers are cancelled when one driver says yes. It trades driver annoyance for speed.

**Bursts.** If 100,000 requests arrive from one place, put requests on a queue (the [Kafka](/learn/backend/08-technologies/kafka/) lesson) and match them in order. Commit the offset only after a match, so a crashed matcher does not lose the request. Say the policy aloud: first come, first served, or nearest driver first.

## Numbers

Treat every figure as an assumption. The shape matters. The write rate is huge, so the index is sharded. The memory for the latest positions is small, so it fits in RAM. The one-minute budget allows only a handful of sequential offers. `GEOADD` costs O(log N) per item and `GEOSEARCH` costs O(N + log M) (Redis docs; `GEOSEARCH` was added in 6.2.0).

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Latest position in memory | 2M writes per second is possible | A crash loses recent positions | History is not needed to match |
| Shard the index by place | One search hits one shard | Border queries, uneven load | Search needs neighbors |
| Shard the index by driver id | Even load | Every search scatters | Rarely right for proximity |
| Lock with expiry | No double assignment, no stuck lock | Needs fencing for full safety | Short, hot critical section |
| Offer to one driver at a time | Simple, fair to drivers | Up to 10 s per attempt | Normal demand |
| Offer to several at once | Faster match | Cancel extra offers | Tight latency budget |

## Interview lens

<Callout type="tip">
Say the key fact first: "I only need each driver's latest position, so the index lives in memory and each ping replaces the last". Say the load shape out loud. Then name the contention risk before the interviewer asks: "two matchers can pick one driver, so I lock the driver with an expiry and make the final ride write conditional".
</Callout>

<Callout type="mistake">
Do not put latitude and longitude in two SQL columns and call it proximity search. Do not shard the geo index by driver id. Do not say a lock is "safe" and skip the crash case. Do not keep the offer timer only in process memory.
</Callout>
