## The problem

You edit a 2 GB video project on your laptop and save. Your phone and your teammate's computer must show the new version soon. The naive plan is to upload the whole file after each save and let every device download the whole file. That sends 2 GB for a change that may touch a few megabytes.

A file sync service has to move large files, over weak links, to many devices, without sending bytes it already has. Lesson [8.11](/learn/08-technologies/blob-storage/) taught the storage parts: pre-signed URLs, multipart upload, and a CDN. Lesson [9.6](/learn/09-patterns/large-blobs/) turned them into a pattern. This lesson puts them together and adds three ideas: chunking by hash, content-based dedupe, and cursor-based sync.

## Requirements

**Functional.**

1. Upload a file from any device.
2. Download a file on any device.
3. Share a file with another user, and list files shared with you.
4. Sync changes to a user's other devices automatically.

**Below the line.** Editing in place, previews, storage quotas, version history, and virus scanning.

**Non-functional.** Files up to 50 GB. Highly available, and availability matters more than consistency. Secure: only people with access can read a file. Durable: recover from loss or corruption. Low latency for upload, download, and sync.

**Scale numbers, as assumptions.** Take 50 GB to mean 50 GiB so the arithmetic is clean. Use 8 MiB chunks, since S3 multipart parts must be at least 5 MiB. Assume a 100 Mbit/s home upload link.

- Chunks in a 50 GiB file: 50 × 1,024 MiB ÷ 8 MiB = **6,400 chunks**. That is under the 10,000-part limit of one S3 multipart upload, so one multipart upload can carry the file.
- Upload time at 100 Mbit/s: 50 GB is 400 gigabits. 400 ÷ 0.1 = 4,000 seconds, about **67 minutes**. A link failure in that hour is likely. So uploads must resume, which is why chunks matter.
- Chunk list size: each SHA-256 hash is 32 bytes. 6,400 × 32 B = 204,800 B, about **200 KB** of metadata for a 50 GiB file. Tiny next to the file.

One company claim as context: Dropbox's engineering blog says every file is split into 4 MB blocks, each identified by a SHA-256 hash, and a file is the ordered list of those hashes. This is a claim from their article on streaming file synchronization, not our measurement. Our 8 MiB chunks are our own choice. The idea is the same.

## Core entities

- **File:** `file_id`, `owner_id`, `name`, `size`, and an ordered list of chunk hashes.
- **Chunk:** a block of bytes named by its SHA-256 hash. It lives in object storage. A metadata row records that the chunk exists. Several files can point to one chunk.
- **Share:** `file_id`, `grantee_id`, `permission`.
- **Device cursor:** the last change a device has seen.

Metadata is rows in a database. Chunk bytes are objects in blob storage. Never put file bytes in the database.

## API

| Call | Purpose |
|---|---|
| `POST /uploads` with name, size, and chunk hashes | Returns an upload id and pre-signed URLs only for chunks the server lacks |
| `PUT <pre-signed URL>` | Client sends one chunk straight to object storage |
| `POST /uploads/{id}/complete` | Server checks the chunks exist, then publishes the file |
| `GET /files/{id}/download` | Returns signed URLs for the file's chunks, after an access check |
| `POST /files/{id}/share` with grantee and permission | Creates a share row |
| `GET /changes?cursor=...` | Returns files changed since the cursor, and a new cursor |

The user comes from the auth token ([lesson 3.5](/learn/03-api-design/auth/)), not from the request body.

## High-level design

Step through it. Note that the app servers never touch file bytes.

<DropboxBuild client:visible />

**Why direct upload.** Suppose file bytes went through the API servers. Each would hold a long connection for an hour, and an API gateway often caps a request at about 10 MB ([lesson 8.10](/learn/08-technologies/api-gateway/)). A pre-signed URL lets the client write to object storage directly. The service only signs the URL, and the signature expires quickly. Use a short expiry, such as minutes, so a leaked URL stops working soon.

**Two writes can disagree.** The file row and the chunk objects are in two systems. Mark a file `pending` until `complete` succeeds and every chunk is confirmed present. A cleanup job aborts stale uploads so unused parts stop costing money. Lesson [8.11](/learn/08-technologies/blob-storage/) covers this.

**Sharing.** A share row says who may open which file. The metadata service checks it before it signs any download URL. Never expose public object URLs. A download URL should name one object and expire.

## Deep dive 1: big files and resume

One `POST` of a whole 50 GiB file fails at once: it exceeds any gateway limit, and a drop at minute 66 restarts from zero. The fix is the multipart pattern from lesson [9.6](/learn/09-patterns/large-blobs/). The client cuts the file into chunks. Each chunk is its own request. Parts go in parallel. After a failure, the client asks which parts exist (S3 offers `ListParts`) and sends only the missing ones. Finally one `complete` call joins them.

Resume is why 8 MiB beats 5 GB: a failed chunk costs a few seconds, not an hour. Too small is also bad. At 8 KiB there would be 6.5 million chunks for 50 GiB, a metadata row for each, and a request for each. Chunk size trades retry cost against bookkeeping cost.

## Deep dive 2: dedupe and delta sync

Every chunk is named by its content hash. That gives two savings for free.

1. **Skip chunks the server already has.** The client sends its hash list first. The server answers with the hashes it lacks. The client uploads only those. A file that was already uploaded, even by another user, costs a hash list and no bytes. This is **content-based dedupe**.
2. **Upload only what changed.** Edit a file and chunk it again. Unchanged chunks have unchanged hashes, so they are skipped.

Point 2 hides a trap. Switch between the two chunking methods below.

<DropboxChunks client:visible />

With **fixed-size chunks**, a chunk boundary is a byte offset. Insert one byte near the start and every later byte shifts by one. Every chunk after the edit now has different bytes, so every hash changes. Dedupe finds nothing to skip.

With **content-defined chunking**, a chunk boundary depends on the bytes near it. A rolling hash slides over the data and cuts where the hash matches a chosen pattern. After an insert, the cut points beyond the edit fall on the same bytes as before. Only the chunk around the edit changes. The cost is more compute on the client and chunks of uneven size, so bound the size above and below.

Hashing needs a strong function. SHA-256 makes an accidental match practically impossible, so equal hash can mean equal bytes.

**A privacy probe.** If one user's upload is skipped because the hash exists, then upload speed tells that user the content is stored. Someone holding a file's hash could learn whether another account has the file. Interviewers like this question. Answers: dedupe only inside one account or organization, or require the client to prove it holds the bytes before the server skips the upload.

## Deep dive 3: sync

A device must learn about changes made elsewhere. Polling `GET /files` every second for every user is wasteful: most polls find nothing. Instead each device keeps a **cursor**, a number that grows with every change in that user's account. The device asks `GET /changes?cursor=1840` and receives only entries after 1840, plus a new cursor. If the device was offline for a week, the same call catches it up.

To avoid a poll loop, add a push channel. When the sync service sees a change, it sends a small nudge ("something changed") over a long-lived connection ([lesson 2.5](/learn/02-networking/real-time-transport/)), and the device then calls `/changes`. The nudge carries no data, so a missed nudge costs only delay: the device still polls now and then as a safety net. After `/changes`, the device compares chunk hashes and downloads only chunks it lacks.

If two devices change the same file while offline, you have a conflict. A simple rule is to keep both: save the second version under a new name, such as "report (conflicted copy)". Do not discard a user's edit silently.

## Trade-offs

| Decision | Choice here | You gain | You pay |
|---|---|---|---|
| Upload path | Pre-signed URL, direct to storage | App servers carry no bytes | A two-step flow and a pending state |
| Chunk size | 8 MiB (assumed) | Cheap retries. Few rows | A small edit to a big chunk re-uploads the chunk |
| Chunking | Content-defined | Small edits upload little | More client CPU. Uneven chunk sizes |
| Dedupe | By content hash | Less storage and upload | The existence leak across users |
| Sync | Cursor plus push nudge | Little polling. Offline catch-up | A change log per account |
| Conflicts | Keep both copies | No lost edits | Users must merge by hand |

<Callout type="tip">
Say the split first: "Metadata in a database, bytes in blob storage. The client chunks the file, hashes each chunk, and the server tells it which hashes are missing. Uploads go straight to storage with pre-signed URLs, so the API tier never carries bytes. Sync is a per-device cursor with a push nudge." Then raise dedupe and the fixed versus content-defined chunking issue yourself.
</Callout>

<Callout type="mistake">
Do not store files in the database. Do not push the bytes through your API servers. Do not name chunks by file name, since renaming a file would look like new content. Do not use a long-lived or public download URL. And do not say "fixed-size chunks give delta sync" without noting that one inserted byte shifts every later chunk.
</Callout>

<Callout type="deep" title="A hash as an address">
When a chunk is named by its hash, the name is also a checksum. After a download the client re-hashes the bytes. If the result differs from the name, the chunk is corrupt, and the client can fetch it again. This gives an integrity check for free. It also makes chunks immutable: the same name always means the same bytes, so chunks are easy to cache and safe to share.
</Callout>
