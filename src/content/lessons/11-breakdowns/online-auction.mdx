## The problem

A seller lists a camera. Ten minutes before the end, 300 people want it. Many bids arrive in the same second.

Two rules must hold. First, the highest bid wins, and no accepted bid may be silently lost. Second, everyone watching must see the new price quickly, or they bid against a price that is already gone.

Most of the system is easy. One part is hard: many writers race to update **one value**, the highest bid of one auction. That is **contention**: many requests fighting for the same piece of data. Lesson [9.4](/learn/09-patterns/contention/) taught the general patterns. This case study applies them and adds two more problems: broadcasting the new price, and ending the auction on time.

## Requirements

**Functional.**

1. A seller posts an item with a start price and an end time.
2. A buyer places a bid. It is accepted only if it is higher than the current highest bid.
3. Anyone can view an auction and its current highest bid.

**Below the line.** Search, category filters, sort by price, and a history of past auctions.

**Non-functional.** These are our assumptions. No public company figure gives bids per second for one auction.

- Strong consistency for the highest bid. Two bids must never both "win" the same step.
- A bid gets an answer quickly. Agree on the number with the interviewer.
- Viewers see a new highest bid within about 1 second.
- No accepted bid is lost.
- The server clock decides when the auction ends.

## Core entities

- **Item**: id, seller, title.
- **Auction**: id, item, start price, end time, status, highest bid, highest bidder, version.
- **Bid**: id, auction, bidder, amount, time, idempotency key.

## API

| Call | Purpose |
|---|---|
| `POST /v1/auctions` | Item, start price, end time. Returns 201 (the HTTP status code for "created"). |
| `POST /v1/auctions/{id}/bids` | Amount and an idempotency key. Returns 201, or 409 (the status code for "conflict") if outbid. |
| `GET /v1/auctions/{id}` | Status and current highest bid. |
| `WS /v1/auctions/{id}/stream` | A WebSocket: one connection that stays open, so the server can push each new highest bid. |

The bid call needs an idempotency key (lesson [3.4](/learn/03-api-design/idempotency/)). That is a unique token the client attaches to one bid, so the server can spot a repeat of the same request and ignore it. A phone that retries after a timeout must not place two bids.

## High-level design

Step through the build.

<AuctionBuild client:visible />

Three details are worth saying aloud.

- The **auction row** holds the current highest bid. It is the only value that bids compete for. The **bid log** is append-only: rows are only added, never changed, so all bids are kept.
- A **pub/sub channel** (a named mailbox that many listeners can subscribe to) will carry each new price to viewers, and a **delay queue** (a queue that releases an item only at a set time) will end each auction. Both are explained in the deep dives below.
- **Reads** and **writes** have different shapes. A viewer reads again and again. A bidder writes once in a while. Keep the two paths apart so viewers cannot slow bids down.
- **Sharding** (lesson [4.7](/learn/04-data/sharding/)) is by auction id. All bids for one auction go to one shard. Different auctions spread over many shards.

## Numbers

Assume about a million new auctions a day, with a handful of bids each. The total write load is modest in this model: a few hundred bids a second at peak (~1,000). A single database handles that, and the bid log stays small.

Two things are large. The first is **per-auction contention**: the last minute of one popular auction has many bids on one row. The second is **fan-out**: each bid must reach every viewer of that auction. One bid becomes thousands of pushes. Notice that the fan-out is the bigger load. Sizing is about one hot auction, not the total.

## Deep dive: the highest-bid race

The naive handler does three steps in code: read the row, compare, write. The problem is that the three steps are not one step. Another bid can run between them.

<AuctionRace client:visible />

The failure is called a **lost update**. B was told "accepted", then A overwrote B. This is the same anomaly lesson [4.4](/learn/04-data/transactions/) showed.

The fix puts the check and the write in one statement. It is a **conditional write**, also called **compare-and-set**: change the value only if it still has the value you expect.

```sql
UPDATE auctions
SET highest_bid = :amount, highest_bidder = :user, version = version + 1
WHERE id = :id AND highest_bid < :amount AND status = 'open' AND end_at > now();
```

The database locks the row for the length of the statement. So two bids on one auction run one after the other. In PostgreSQL at the default isolation level (READ COMMITTED, which means each statement sees only data that other transactions have already committed), the second one re-checks the row after the first commits. If it affects 0 rows, the bid was too low, the auction was closed, or time ran out. The service returns 409 with the current high bid. The bid log insert goes in the same transaction.

This is **optimistic concurrency**: assume no conflict, and detect one at write time. It holds no lock while the client thinks. It works well when conflicts are rare for most auctions and bounded for one auction. The `version` column is for cases where the rule is more than "higher than". If a bid must be at least 5 above the current high, the service reads the row. The service then computes and writes with `WHERE version = :seen`. A 0-row result means "retry with fresh data".

What are the other options?

| Option | How | Cost |
|---|---|---|
| Row lock first | `SELECT ... FOR UPDATE`, then update | Holds a lock across two statements. Bids queue behind each other |
| Single writer per auction | Route all bids of one auction to one partition and one thread | Needs routing, and failover for the owner. No lock fights at all |
| Redis script | A Lua script (a small program that Redis runs as one uninterrupted step) does the compare and set in memory (lesson [8.2](/learn/08-technologies/redis/)) | Fast, but a failover can lose the latest bids. Say this out loud |

Do not lock the whole table. That makes every auction wait for every other auction.

## Deep dive: telling everyone

Each viewer wants the new price. The first idea is to poll. With thousands of viewers polling once a second, one auction row takes thousands of reads a second. A viewer sees a new price up to a second late.

Push is better. After a bid commits, the service publishes it to a **channel** for that auction, using pub/sub (lesson [6.2](/learn/06-async/pubsub-logs/)). **Gateway** servers hold the viewers' WebSocket connections (lesson [9.3](/learn/09-patterns/real-time-updates/)). Each gateway subscribes to the channels of the auctions its viewers watch, and pushes each message to those viewers.

Two details matter. A gateway that restarts loses its connections. Clients reconnect and fetch the current state with a plain `GET`, so a missed push is repaired. Second, send the highest bid and its version, not "a bid happened". A viewer drops any message older than what it already shows, so out-of-order delivery is harmless.

## Deep dive: when the auction ends

A cron job (a task that runs on a fixed schedule) that scans all auctions every minute is late by up to a minute. It scans millions of rows. Use a timer per auction instead. When an auction is created, schedule a close event at its end time in a delay queue or scheduler. One example is in lesson [11.15](/learn/11-breakdowns/job-scheduler/).

Two rules protect the end.

1. **The server clock decides.** A bid is valid only if `end_at > now()` on the database. A phone clock can be wrong or changed. A bid that left the phone at 17:59:59.9 but arrives at 18:00:00.1 is late. Say so in the rules. Clocks across servers also differ slightly (lesson [10.5](/learn/10-advanced/ids-and-time/)), so judge time in one place, the shard that owns the auction.
2. **Closing is conditional too.** Many auctions use **anti-sniping**: a bid in the last two minutes pushes the end time out by two minutes. Then the timer that fires at the old time is stale. The close statement is `UPDATE ... SET status = 'closed' WHERE id = :id AND status = 'open' AND end_at <= now()`. If it affects 0 rows, the auction was extended, so reschedule the timer for the new `end_at`.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Conditional update in a SQL database | Simple, correct, durable | One row is the throughput limit per auction | Default answer |
| Single writer per auction | No retries, clear order | Routing and owner failover | Very hot auctions |
| Redis compare-and-set | Very low latency | A failover can lose acknowledged bids | Speed matters more than strict durability |
| Push over WebSocket | Prices are fresh, no polling load | Many connections to manage | Many viewers per auction |
| Polling every few seconds | Easy | Stale prices, read load | Few viewers, relaxed freshness |
| Anti-sniping extension | Fairer end | Auctions can run long | Late bidding is common |

<Callout type="tip">
Draw the race first. "Two bids read 100, both pass the check, the lower one writes last." Then give the fix in one line: "one conditional update, so the database decides." Then say what the second bidder sees: a 409 with the current high bid.
</Callout>

<Callout type="mistake">
Do not say "use a distributed lock" before you have tried a conditional write. A lock adds a second system that can fail, and the database already locks the row. Also do not let the client send the bid time. The server picks the time.
</Callout>
