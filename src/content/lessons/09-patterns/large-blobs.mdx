## The problem

Users upload videos, photos, and documents. A file can be gigabytes. The obvious design is `POST /videos` with the file as the request body. The API server receives it, then writes it to storage.

Count what that costs. Take a 2 GB video and a user on a 20 Mbit/s home uplink. The transfer takes 2 × 8 × 1,000 Mbit ÷ 20 Mbit/s = 800 seconds, about 13 minutes. The API server holds that connection open for the whole 13 minutes. If 1,000 users upload at once, that is 1,000 open connections and 1,000 × 20 Mbit/s = 20 Gbit/s of inbound traffic. The server does nothing useful with the bytes. It only relays them.

Three more problems follow.

- **Gateways cap the body.** Amazon API Gateway rejects a body over 10 MB ([lesson 8.10](/learn/08-technologies/api-gateway/)).
- **A failure restarts everything.** If the connection drops at 99%, the user starts at byte zero.
- **The app tier scales with bytes.** You add servers because of file size, not because of logic.

## The mechanism: the server only signs

The rule is simple. **Bytes never pass through your app servers.** The server decides who may upload and what. The client sends the bytes straight to the blob store.

The store does not know your users, so the server hands the client a **pre-signed URL**: a URL that carries a signature made with the server's credentials. It allows one action on one key for a short time. The client needs no credentials of its own.

<LargeBlobsDirect client:visible />

The flow, in order:

1. The client asks the API to upload a file and states its name, size, and checksum.
2. The API checks auth and quota, and inserts a **metadata row** with status `PENDING`.
3. The API returns signed URLs. For a big file it starts a multipart upload and signs one URL per part.
4. The client sends the parts directly to the store, in parallel.
5. The API completes the multipart upload.
6. The store emits an event. A handler flips the row to `READY`.

### Why a metadata database and a blob store

Keep facts in the database and bytes in the store. The row holds the owner, name, size, checksum, status, and the object key. A query finds rows ("all of Ana's videos"). The key finds bytes. Blob storage cannot answer "where owner is Ana". A database should not hold a 2 GB value. Each system does the job it is good at.

### Large files: multipart and resume

A single PUT to S3 can carry at most 5 GB, per the S3 documentation. Beyond that you must use multipart upload, and AWS suggests it from about 100 MB. Lesson 8.11 gives the part limits. What matters for this pattern is what multipart buys you: parts go in parallel, and a failed part is sent again alone.

**Resume** follows from that. The store knows which parts it holds. After a crash or an app restart, the client asks for the list of uploaded parts, then sends only the missing ones. The client does not need to keep perfect memory, because the store is the record. Abandoned multipart uploads keep costing money until you complete or abort them, so add a lifecycle rule that aborts old ones.

### Checksums: trust but verify

Networks and disks can corrupt bytes. A **checksum** is a short fingerprint computed from the bytes. The client computes it, and the store computes it again on arrival. S3 supports this: if the values do not match, it fails the request with a `BadDigest` error. Check the whole file too. A file that arrives intact is the only file worth marking `READY`. Store the expected checksum in the metadata row so a later audit can compare.

### Done means "the store says so"

How does the API learn the upload finished? There are two choices.

- **The client says so.** The client calls `POST /videos/7/done`. This is easy, but a buggy or hostile client can claim success, or it can crash before it sends the call.
- **The store says so.** Store event notifications go to a queue, a function, or an event bus. This is the proof that the bytes exist.

Prefer the event, with the client call as a hint. S3 notifications are designed to be delivered at least once, typically within seconds but sometimes a minute or longer. So the handler must be idempotent: `UPDATE ... SET status='READY' WHERE id=7 AND status='PENDING'` does nothing the second time ([lesson 3.4](/learn/03-api-design/idempotency/)). Also add a cleanup job. A row that stays `PENDING` past a deadline means the user never finished. Delete the row and abort the upload.

### Downloads: signed URLs and a CDN

Reads need the same care. Do not stream a video through the API. There are two options.

- **A signed GET URL** straight from the store. Good for private files and small read volume.
- **A CDN with signed URLs** ([lesson 2.7](/learn/02-networking/cdn-proxies/)). CloudFront signs a URL with an expiry, using a canned policy for expiry only or a custom policy for more rules. Edge caches then serve the bytes close to the user. If anyone changes the query string after signing, the CDN returns 403.

The pattern is the same as for uploads. The API makes the decision, a signature carries it, and the data path skips the API.

## Numbers

Use the lesson 8.11 table for S3 limits. Derived numbers for this flow, from the 2 GB example above:

| Quantity | Calculation | Result |
|---|---|---|
| Parts at 64 MiB | 2 GiB = 2,048 MiB; 2,048 ÷ 64 | 32 parts |
| Calls to store, in all | 1 create + 32 parts + 1 complete | 34 |
| API calls for this upload | start, sign URLs, complete | about 3, whatever the file size |
| Retry cost of one bad part | 64 MiB ÷ 2,048 MiB | about 3% of the file |
| Single PUT, bad connection at 99% | the whole file again | 2 GB resent |

The server work stays about constant as the file grows. That is the gain.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Upload through the API | One simple endpoint. Full inspection of bytes | Connections held for minutes. Body caps. Bandwidth on the app tier | Small files only |
| Direct upload, one signed PUT | App tier off the data path | Two round trips. A leaked URL works until expiry | Files up to a few tens of MB |
| Direct multipart with resume | Parallel parts. Cheap retries | Client logic. Orphaned parts to clean up | Large files and mobile networks |
| Completion by storage event | Proof the bytes exist | At-least-once delivery. A short delay | Always, with the client call as a hint |
| CDN with signed URLs for reads | Fast far reads. Less origin load | Cache and invalidation rules | Public or private read-heavy media |

<Callout type="tip">
Say: "The API never touches the bytes. It checks auth, inserts a PENDING row, and returns signed multipart URLs. The client uploads parts straight to the blob store and can resume by listing parts. A storage event flips the row to READY through an idempotent handler. Downloads go through a CDN with signed URLs. Metadata is in a database, bytes are in the store." If asked about abuse, add short expiry, a size check on the finished object, and a malware scan before READY.
</Callout>

<Callout type="mistake">
Do not route large uploads through your servers "to validate them". You cannot hold that many connections. Do not mark a file ready because the client said so. And do not forget the stale states: rows stuck in PENDING and multipart uploads that were never finished.
</Callout>

<Callout type="deep" title="Two writes that cannot be one transaction">
The database row and the object live in two systems, so no transaction covers both. That is the same problem as in [lesson 9.5](/learn/09-patterns/multi-step/). The status column is the answer. It turns a two-system write into a small state machine: PENDING, then READY, with cleanup for the failure paths. The upload is a tiny saga where the compensation is "delete the row and abort the parts".
</Callout>
