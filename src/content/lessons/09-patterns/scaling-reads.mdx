## The problem

Most products read far more than they write. A feed is opened many times for each post. A product page is viewed far more often than it is edited. So the first scaling problem is usually reads.

Say the product has one PostgreSQL database. Lesson [1.5](/learn/01-one-machine/numbers-to-know/) gives about 10K to 50K simple indexed reads per second for one node. Traffic grows to 25,000 reads per second at peak. The database CPU sits at 100%, queries queue, and pages time out.

This is a pattern, not one trick. You will not need a new database. You combine four things you already know, in a fixed order, and you stop as soon as the numbers fit.

## Naive solution: a bigger machine

The first reflex is a larger database server. It works for a while and it is simple. It has three limits. The largest machine you can rent is a hard ceiling. The price climbs faster than the capacity. And a bigger machine is still one machine, so one failure takes reads and writes down together.

Before any new component, check the cheap things. Add the missing index (lesson [4.3](/learn/04-data/indexing/)). Fix the query that scans a million rows. A 1 ms read that you make 100 times faster is worth more than a new server. Scale out only when the work per read is already small.

## The mechanism: a ladder

Each rung takes a share of reads away from the rung behind it. Step through all of them. The first step shows the problem. The last step shows the full stack.

<ScalingReadsWalk client:visible />

**Rung 1: read replicas.** The primary keeps all writes. Followers copy its log (lesson [4.6](/learn/04-data/replication/)) and answer reads. Read capacity grows about linearly with the number of replicas. Writes do not grow at all. This is the simplest rung because the app still speaks SQL.

**Rung 2: a cache.** A cache holds the answers to the most common reads in memory (lessons [5.1](/learn/05-caching/why-cache/) to [5.3](/learn/05-caching/cache-strategies/)). The hit ratio is the share of reads the cache answers without help. Picture a librarian who keeps the 100 most asked books on the desk: each time someone asks for one of them, no trip to the shelves is needed. With a hit ratio `h`, only a share `1 - h` of reads reaches the database. At a high hit ratio, the database sees only a small share of reads. That is the largest single gain in the ladder, and it costs staleness (lesson [5.5](/learn/05-caching/invalidation-stampede/)).

**Rung 3: a CDN.** A CDN (content delivery network) is a set of servers spread around the world that keep copies of your public content. The "edge" is that outer ring of servers, close to users. Picture a local shop that stocks the popular items so people do not travel to the factory. A CDN answers requests for content that is the same for every user (lesson [2.7](/learn/02-networking/cdn-proxies/)). Those requests never reach your data center. If the CDN answers half of all reads, everything behind it sees half the demand. It only helps for shared, cacheable responses: images, scripts, public pages, and API responses that are identical for everyone.

Order matters. You add the rungs in this order because each one is cheaper to run per request than the one behind it, and each one hides load from it.

The chart shows how many reads per second each stage can serve. Move the sliders. Watch which tier becomes the limit.

<ScalingReadsMeter client:visible />

**The model.** Requests go from the edge inward. Each tier answers a share of what it receives and passes the rest on. A tier saturates when the share that reaches it is more than it can serve. The system limit is set by the first tier to saturate.

**Assumptions.** Reads only. One database node serves 10,000 reads per second. That figure is an assumption inside the 10K to 50K range of lesson 1.5, on the low side. One cache node serves 100,000 operations per second (lesson 5.1 gives 100K to 1M). Hit ratios do not change with load. The CDN has no limit. Replicas share load evenly and have no lag. These are round numbers for reasoning. Measure your own.

Try this. At the defaults, the database tier is the first limit. Now drop the cache hit ratio. The limit falls fast, because the replicas now see a much larger share of reads. The hit ratio decides how much the cache is worth.

## Read-your-writes after replica lag

Replicas are slightly behind the primary. A user posts a comment, the page reloads from a replica, and the comment is gone. Lesson [4.10](/learn/04-data/consistency-models/) names this: read-your-writes. Lesson [4.6](/learn/04-data/replication/) has a simulator for lag.

Three fixes, from simple to exact:

- **Read from the primary for a short window after a write.** Track the time of the user's last write. If it is recent, send that user's reads to the primary. Pick a window longer than normal lag.
- **A position token.** The write returns a log position. A replica may answer only once it has applied that position. Otherwise the read goes to the primary.
- **Pin by data, not by user.** Read the primary only for the rows this user just changed.

The cost is load on the primary, so keep the window short. Caches have the same problem. If a write only deletes the cached key, a read can refill the cache with the old value. The refill can happen when a read arrives before the replica has caught up. Facebook's memcache paper describes this for replicas in other regions (a region is a data center site in one part of the world). Its fix is a remote marker: a key that says "this data was just written, read it from the primary region". The paper says the marker trades extra latency on a miss for a lower chance of reading stale data. Your system may not need a marker. The idea still applies: after a write, remember that the replica is not trusted yet.

## Hot keys

A cache spreads keys over nodes by hash (a hash turns a key into a number that picks the node; lesson [4.8](/learn/04-data/consistent-hashing/)). One key still lives on one node. When a post goes viral, the node that holds it takes most of the traffic while the others idle. Adding nodes does not help, because the key does not move.

Options, cheapest first:

- **A small in-process cache** in every app server for the hottest keys, with a TTL (time to live: the number of seconds a copy is kept before it is thrown away) of a few seconds. "In-process" means the copy lives in the app server's own memory, so reading it costs no network trip. The cache node sees one read per app server per TTL, not one per user.
- **Copy the key to several cache nodes** and read from any copy. The memcache paper does this for keys that are fetched in large groups and fit on one or two servers. Its example: every request asks for the same group of items. If you split the group across two servers, every request still goes to both, so neither server gets any relief. If you copy the whole group to both servers, each request goes to just one of them, so the load is shared. The price is that every write must invalidate every copy.
- **Coalesce misses.** To coalesce is to merge many identical requests into one. When many requests miss on the same key at once, let one go to the database. The other requests wait (lesson [5.5](/learn/05-caching/invalidation-stampede/)). Memcache is the in-memory cache server that Facebook runs. The paper's lease does this: the server hands out one token per key. Each key gets at most one token every 10 seconds by default. The server tells other clients to wait briefly.

## Denormalize so a read is one read

A normalized schema stores each fact once and links rows by id, like a phone book that lists each person once. That is good for writes and awkward for reads. Denormalizing means copying a fact into the rows that need it, so a read does not have to join several tables. Say a feed page shows 20 posts, each with the author's name and a like count. Normalized, the page needs one query for the post ids, then one lookup per post for the author and another for the count. That is dozens of queries. Denormalized, each post row stores `author_name` and `like_count`, and the page is 1 query.

You pay on the write side. A like now updates two places. A rename updates every post by that author. And the copies can drift, so you need a way to repair them. Lesson [4.1](/learn/04-data/data-modeling/) gives the rule: copy a fact only when reads far outnumber writes and the copy is stable. Counters are the common case. Keep `like_count` as a column or in a cache instead of counting rows on every view.

## Trade-offs

| Rung | You gain | You pay | Choose when |
|---|---|---|---|
| Read replicas | Linear read capacity, same SQL | Lag, no write scaling, replica cost | Reads exceed one node and need fresh-ish data |
| Cache | Largest cut in database load, sub-millisecond reads | Staleness, invalidation, hot keys, cold start | A small set of keys takes most reads |
| CDN | Offloads shared content, lower latency worldwide | Only for shared responses, purge delay | Public, identical-for-all content |
| Denormalization | One read per view | Slower writes, copies that can drift | Read-heavy, stable fields |
| Bigger machine | No code change | Ceiling, price, one failure domain | Buying time |

## Interview lens

<Callout type="tip">
Say the order and the reason. "I would first check indexes, then add read replicas, then a cache with a short TTL in front, and a CDN for static and public content. Each step cuts load on the one behind it." Then say what it buys: "A high cache hit ratio leaves the database a small share of the peak, which a few replicas handle." End with the cost: "Users who just wrote read the primary, to avoid stale reads."
</Callout>

<Callout type="mistake">
Do not add a cache to cure a slow query. You hide the problem and add a staleness bug. Do not say "replicas scale writes". They do not. Do not forget the hot key. A cache hit ratio of 99% says nothing about one node taking 40% of the traffic. And do not cache personal data in a CDN without a cache key that includes the user.
</Callout>

<Callout type="deep" title="Why a cache can make an outage worse">
A cache that runs at 95% hit ratio protects a database that could not serve all reads on its own. If the cache is flushed, or a node dies, the database suddenly sees more reads. The read load can jump to many times its normal level. It fails, and the cache cannot refill because the database is down. Plan for this. Warm the cache (fill it with popular answers) before sending traffic, rate-limit misses, and keep replicas sized for some miss traffic, not for zero. Lesson 5.5 covers the stampede in detail.
</Callout>
