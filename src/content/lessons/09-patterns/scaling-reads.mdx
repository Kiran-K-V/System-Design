## The problem

Most products read far more than they write. A feed is opened many times for each post. A product page is viewed far more often than it is edited. So the first scaling problem is usually reads.

Say the product has one PostgreSQL database. Lesson [1.5](/learn/01-one-machine/numbers-to-know/) gives about 10K to 50K simple indexed reads per second for one node. Traffic grows to 25,000 reads per second at peak. The database CPU sits at 100%, queries queue, and pages time out.

This is a pattern, not one trick. You will not need a new database. You combine four things you already know, in a fixed order, and you stop as soon as the numbers fit.

## Naive solution: a bigger machine

The first reflex is a larger database server. It works for a while and it is simple. It has three limits. The largest machine you can rent is a hard ceiling. The price climbs faster than the capacity. And a bigger machine is still one machine, so one failure takes reads and writes down together.

Before any new component, check the cheap things. Add the missing index (lesson [4.3](/learn/04-data/indexing/)). Fix the query that scans a million rows. A 1 ms read that you make 100 times faster is worth more than a new server. Scale out only when the work per read is already small.

## The mechanism: a ladder

Each rung takes a share of reads away from the rung behind it. Step through all of them. The first step shows the problem. The last step shows the full stack.

<ScalingReadsWalk client:visible />

**Rung 1: read replicas.** The primary keeps all writes. Followers copy its log (lesson [4.6](/learn/04-data/replication/)) and answer reads. Read capacity grows about linearly with the number of replicas. Writes do not grow at all. This is the simplest rung because the app still speaks SQL.

**Rung 2: a cache.** A cache holds the answers to the most common reads in memory (lessons [5.1](/learn/05-caching/why-cache/) to [5.3](/learn/05-caching/cache-strategies/)). With a hit ratio `h`, only a share `1 - h` of reads reaches the database. At 90% the database sees one read in ten. That is the largest single gain in the ladder, and it costs staleness (lesson [5.5](/learn/05-caching/invalidation-stampede/)).

**Rung 3: a CDN.** A CDN answers requests for content that is the same for every user, at a server close to the user (lesson [2.7](/learn/02-networking/cdn-proxies/)). Those requests never reach your data center. It only helps for shared, cacheable responses: images, scripts, public pages, and API responses that are identical for everyone.

Order matters. You add the rungs in this order because each one is cheaper to run per request than the one behind it, and each one hides load from it.

## The meter: before and after

The chart shows how many reads per second each stage can serve. Move the sliders. Watch which tier becomes the limit.

<ScalingReadsMeter client:visible />

**The model.** Requests go from the edge inward. A tier answers a share of what it receives. The share that reaches a tier is the product of (1 - hit ratio) of every tier in front. A tier with capacity `C` that sees a share `r` saturates at a demand of `C / r`. The system limit is the smallest of those numbers.

**Assumptions.** Reads only. One database node serves 10,000 reads per second (an assumption inside the 10K to 50K range of lesson 1.5, on the low side). One cache node serves 100,000 operations per second (lesson 5.1 gives 100K to 1M). Hit ratios do not change with load. The CDN has no limit. Replicas share load evenly and have no lag. These are round numbers for reasoning. Measure your own.

Try this. At the defaults (3 replicas, 2 cache nodes, 90% hit, CDN 50%), the stages give 10K, 30K, 200K, and 400K reads per second. Now drop the cache hit ratio to 50%. The cache stage falls to 60K, because the three replicas now see half of all reads. The hit ratio decides how much the cache is worth.

## Read-your-writes after replica lag

Replicas are slightly behind the primary. A user posts a comment, the page reloads from a replica, and the comment is gone. Lesson [4.10](/learn/04-data/consistency-models/) names this: read-your-writes. Lesson [4.6](/learn/04-data/replication/) has a simulator for lag.

Three fixes, from simple to exact:

- **Read from the primary for a short window after a write.** Track the time of the user's last write. If it is recent, send that user's reads to the primary. Pick a window longer than normal lag.
- **A position token.** The write returns a log position. A replica may answer only once it has applied that position. Otherwise the read goes to the primary.
- **Pin by data, not by user.** Read the primary only for the rows this user just changed.

The cost is load on the primary, so keep the window short. Caches have the same problem. If a write only deletes the cached key, a read that arrives before the replica has caught up can refill the cache with the old value. Facebook's memcache paper describes this for replicas in other regions. Its fix is a remote marker: a key that says "this data was just written, read it from the primary region". The paper says the marker trades extra latency on a miss for a lower chance of reading stale data. Your system may not need a marker. The idea still applies: after a write, remember that the replica is not trusted yet.

## Hot keys

A cache spreads keys over nodes by hash (lesson [4.8](/learn/04-data/consistent-hashing/)). One key still lives on one node. When a post goes viral, the node that holds it takes most of the traffic while the others idle. Adding nodes does not help, because the key does not move.

Options, cheapest first:

- **A small in-process cache** in every app server for the hottest keys, with a TTL of a few seconds. The cache node sees one read per app server per TTL, not one per user.
- **Copy the key to several cache nodes** and read from any copy. The memcache paper does this for keys that are fetched in large groups and fit on one or two servers. Its example: a server holds 100 items and answers 500K requests per second, and each request asks for all 100. To serve 1M requests per second, splitting the items across two servers sends every request to both, so each still handles 1M. Replicating all 100 items on two servers lets each request go to either one, so each handles 500K. The price is that every write must invalidate every copy.
- **Coalesce misses.** When many requests miss on the same key at once, let one go to the database and make the others wait (lesson [5.5](/learn/05-caching/invalidation-stampede/)). The memcache paper's lease does this: the server hands out one token per key at most once every 10 seconds by default and tells other clients to wait briefly.

## Denormalize so a read is one read

A normalized schema is good for writes and awkward for reads. Say a feed page shows 20 posts, each with the author's name and a like count. Normalized, that is 1 query for the post ids, 20 for authors, and 20 for counts: 41 queries. Denormalized, each post row stores `author_name` and `like_count`, and the page is 1 query.

You pay on the write side. A like now updates two places. A rename updates every post by that author. And the copies can drift, so you need a way to repair them. Lesson [4.1](/learn/04-data/data-modeling/) gives the rule: copy a fact only when reads far outnumber writes and the copy is stable. Counters are the common case. Keep `like_count` as a column or in a cache instead of counting rows on every view.

## Trade-offs

| Rung | You gain | You pay | Choose when |
|---|---|---|---|
| Read replicas | Linear read capacity, same SQL | Lag, no write scaling, replica cost | Reads exceed one node and need fresh-ish data |
| Cache | Largest cut in database load, sub-millisecond reads | Staleness, invalidation, hot keys, cold start | A small set of keys takes most reads |
| CDN | Offloads shared content, lower latency worldwide | Only for shared responses, purge delay | Public, identical-for-all content |
| Denormalization | One read per view | Slower writes, copies that can drift | Read-heavy, stable fields |
| Bigger machine | No code change | Ceiling, price, one failure domain | Buying time |

## Interview lens

<Callout type="tip">
Say the order and the reason. "I would first check indexes, then add read replicas, then a cache with a short TTL in front, and a CDN for static and public content. Each step cuts load on the one behind it." Then use numbers: "25K reads per second at peak. A 90% cache hit leaves 2.5K for the database, which one replica handles." End with the cost: "Users who just wrote read the primary, to avoid stale reads."
</Callout>

<Callout type="mistake">
Do not add a cache to cure a slow query. You hide the problem and add a staleness bug. Do not say "replicas scale writes". They do not. Do not forget the hot key: a cache hit ratio of 99% says nothing about one node taking 40% of the traffic. And do not cache personal data in a CDN without a cache key that includes the user.
</Callout>

<Callout type="deep" title="Why a cache can make an outage worse">
A cache that runs at 95% hit ratio protects a database that could not serve all reads on its own. If the cache is flushed, or a node dies, the database suddenly sees up to 20 times its normal read load. It fails, and the cache cannot refill because the database is down. Plan for this. Warm the cache before sending traffic, rate-limit misses, and keep replicas sized for some miss traffic, not for zero. Lesson 5.5 covers the stampede in detail.
</Callout>
