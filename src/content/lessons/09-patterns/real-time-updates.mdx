## The problem

A user opens a chat, a live score page, or an order tracker. Something changes on the server. The user should see it in well under a second, without asking.

The [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson solved the client side of this: which transport carries the update. That lesson assumed one server. The hard part starts with two. The user is connected to server 1. The event is created by a request that landed on server 2. How does it get from one to the other?

Three questions follow, and this lesson answers each of them.

- **Fan-out.** One event must reach many sockets spread over many servers. How do you do it without sending a message to every server, or one message to every user?
- **Where is the user?** A socket is state held by one machine. Something must know which one.
- **What if the socket drops?** Deploys, crashes, and phone tunnels all cut connections. How does a user get what they missed?

## Transport recap, in one table

Do not re-learn this. The [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson has the detail.

| Method | How it works | Pick it for |
|---|---|---|
| Short polling | The client asks every few seconds | Slow updates |
| Long polling | The server holds the request until there is news | A fallback |
| SSE | One long HTTP response that the server keeps writing to | Server-to-client feeds |
| WebSocket | One two-way connection | Chat, games, collaboration |

Two SSE facts matter for the server side. MDN says the browser reconnects by default when the connection drops. And the event stream has an `id` field. The HTML standard says that on reconnect the browser sends the last id it saw in a `Last-Event-ID` header. That is a ready-made hook for catch-up. With WebSocket you build that part yourself.

## Naive solution: sockets and logic in one process

The simplest server keeps a map from user id to socket in memory. To notify user 7, it looks up the socket and writes. It works with one server.

With two servers it breaks in a quiet way. The write request for a message may land on server 2. The recipient is on server 1. Server 2 has no socket for them. The message is saved, and the user does not see it until they reload.

Two bad fixes appear next.

- **Each socket polls the database** every second. With a hundred thousand sockets that is a flood of queries to learn that usually nothing changed.
- **Every server asks every other server.** The number of connections grows with the square of the fleet.

## The mechanism

The pattern splits the work into four parts. Step through the walk: it follows one message, then one private message, then a crash.

<RealTimeUpdatesWalk client:visible />

**Connection servers** do only one job: hold sockets and write to them. They keep no business logic. The [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson calls this layer a gateway. Because they are stateful, deploys and load balancing need care.

**A durable log** is the source of truth. The API appends the event first and gets an order number for the channel: a sequence number. Only then does it announce it. If the live path loses the event, the log still has it. One writer per channel (or one log partition per channel, the [Pub/Sub and Logs](/learn/backend/06-async/pubsub-logs/) lesson; a partition is one slice of a log that keeps its events in strict order) gives all listeners the same order.

**Pub/sub** carries the announcement. Each connection server subscribes to the channels its own users watch, and unsubscribes when the last such user leaves. The bus then delivers one copy to each interested server. Each server writes it to its own sockets.

**A registry** answers "which server holds user 7?" for targeted messages. Each server writes `user -> server` entries with a short expiry and refreshes them while the socket lives. A crashed server's entries expire by themselves. A key with an expiry is a basic Redis feature (the [Redis](/learn/backend/08-technologies/redis/) lesson).

Use the right tool for the audience. **Broadcast to a channel** goes through pub/sub. **A message to one person** goes through the registry to one server. An entry that is missing, or that points to a dead server, means "not connected now". Send a push notification, or leave the message in the log for catch-up.

## The cost of fan-out

How many internal messages does one event cost? It depends on how many servers hold a member, not on how many members there are.

**The model.** If each member sits on a random server, then some members share a server. So the number of servers that hold a member is lower than the number of members. A global topic sends to every server. One message per member sends more messages than there are servers to reach, and many of them go to the same server.

**Assumptions.** Uniform random placement. Equal servers. Every server subscribes only to channels it has members in. Real placement is skewed, because friends often join around the same time and hit the same server. So real numbers are usually a little lower for small groups.

A small channel is cheap with per-channel subscriptions and wasteful with a global topic. A huge channel reaches nearly every server anyway. After that point the cost is on the last hop. A server with 1,000 members of a channel writes 1,000 small frames for each event. For very large audiences, one option is to batch the events. Each batch covers one short tick and sends a single frame per socket.

## Pub/sub is not a log

This trap catches many designs. Redis documents its Pub/Sub as **at-most-once**: "a message will be delivered once if at all". If a subscriber is not connected, or cannot keep up, the message is gone. The Redis docs point to Redis Streams for persisted messages.

So pub/sub gives a **fast** path and no **safe** path. That is why the log comes first. Treat the live message as a hint: "something new is in channel 9, sequence 43". The log is where the truth is. The [Pub/Sub and Logs](/learn/backend/06-async/pubsub-logs/) lesson covers logs that keep records.

## Reconnect and catch-up

A connection drops. The reconnect itself needs jitter, or 100,000 clients return in the same second (lessons [Real-time Transport](/learn/backend/02-networking/real-time-transport/) and [Timeouts, Retries, Backoff](/learn/backend/07-reliability/timeouts-retries/)). Jitter means each client waits a different random time before it retries. Picture a theatre exit: if everyone leaves through the door at the same instant, it jams. If people leave a little at a time, it flows. Reconnecting only restores the pipe. The client still has a gap.

The fix has three parts:

1. **Every event carries a sequence number** per channel, from the log.
2. **The client remembers the last number it processed** and sends it on reconnect. SSE does this with `Last-Event-ID`. With a WebSocket, send it in the first message.
3. **The server replays from the log**: every event after that number, in order. Then it switches the client to the live path.

The switch is the tricky moment. While the server replays events 43 to 50, event 51 may arrive live. If the server sends 51 first, the client sees a gap. If it sends 51 twice, the client sees a duplicate. The safe way is to buffer live events during the replay. Next, send the replay. Then send only buffered events whose sequence number is above the last one sent. The client also ignores any number it has already seen. Sequence numbers make the whole thing safe to repeat.

If the gap is very large, such as a phone off for a week, replaying every event is slower. In that case, sending the current state is faster. Pick a limit and send a fresh snapshot beyond it.

Slow clients need a rule as well. A client that cannot read as fast as events arrive makes the server buffer without limit. Give each socket a bounded send buffer. When it fills, drop the client. It reconnects and catches up from the log, which is correct because the log holds everything.

## Numbers

| Fact | Value | Source |
|---|---|---|
| Redis Pub/Sub delivery | at-most-once | Redis docs |
| SSE connections per browser and domain on HTTP/1.1 | 6 (the limit is per browser and domain, across tabs) | MDN |
| SSE streams on HTTP/2 | negotiated, default 100 | MDN |
| Servers reached for a small channel | Fewer than the member count, as some share a server | Derived above |
| Sockets per server | measure it: depends on runtime and kernel settings | The [Real-time Transport](/learn/backend/02-networking/real-time-transport/) lesson |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| One global topic | Simple, no subscription bookkeeping | Every server handles every event | Few servers or tiny fleets |
| Per-channel topics | Servers see only their channels | Subscribe and unsubscribe churn | Many channels, uneven size |
| Registry and direct send | Exact targets for private messages | A registry to keep fresh, stale entries | Direct messages, notifications |
| Log plus resume | Nothing is lost, replay is safe | A log to run and a sequence per channel | Any feature where a missed event matters |
| Pub/sub only | Lowest latency, least to run | Lost events on any drop | Ephemeral signals such as typing |

## Interview lens

<Callout type="tip">
Name the four parts in order. "Sockets live on connection servers. The API writes the event to a log, then publishes to pub/sub. Each server subscribes to the channels its users watch. A registry maps users to servers for direct messages. On reconnect the client sends its last sequence number and gets a replay." Then state the weak point: "Pub/sub is at-most-once, so the log is the safety net."
</Callout>

<Callout type="mistake">
Do not say "use Redis pub/sub" as if it never loses a message. Do not skip reconnect: a design with no catch-up loses events on every deploy. Do not let every server subscribe to everything when channels are many. And do not send the replay and the live stream as two unordered streams. Say how you avoid gaps and duplicates.
</Callout>

<Callout type="deep" title="Why a deploy is a reconnect storm">
A rolling deploy restarts connection servers one at a time. Each restart drops all of its sockets at once. Those clients reconnect to the survivors, which are then busy with their own load. If the fleet has 10 servers and you restart one, the other 9 absorb 1/9 more clients each. The extra clients arrive in a burst. Drain first: stop accepting new sockets, tell clients to reconnect after a random delay, and restart in small batches. Jitter plus a replay from the log makes it invisible to users.
</Callout>
