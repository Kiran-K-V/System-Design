## The problem

Reads are easy to copy. Writes are not. Every write must reach the one place that owns the data. Read replicas do not help: each replica has to apply every write too (the [Replication](/learn/backend/04-data/replication/) lesson). So a cache and replicas lift the read ceiling and leave the write ceiling where it was.

The [Numbers to Know](/learn/backend/01-one-machine/numbers-to-know/) lesson puts one database node at about 5K to 20K simple writes per second. Now picture a ticket sale, a flash sale, or a game event. Writes jump to 30,000 per second for a minute. One primary cannot take that. Its queue grows, latency climbs, and clients time out.

Writes have two different problems, and they need different fixes:

- **Too much total volume** for one node. The fix is to do less work per write, or to spread the writes.
- **Too much volume on one key.** The fix is to split that key.

This lesson puts four earlier ideas in the right order.

## Naive solutions

**A bigger primary.** It buys time, and then it hits the same wall as for reads.

**More replicas.** They do nothing for write volume. Each one replays the same stream of writes.

**Write to two databases from the app.** The [Replication](/learn/backend/04-data/replication/) lesson showed how this goes wrong: the two copies disagree after a crash.

**Retry harder.** When a database is saturated, retries add load. The [Timeouts, Retries, Backoff](/learn/backend/07-reliability/timeouts-retries/) lesson explains why that makes it worse.

## The mechanism

There are four moves, in the order you should try them. Read each one. After the fourth, a step-through walk follows one burst through all of them.

### Move 1: less work per write

**Batch.** A commit is the moment the database promises that a change is saved for good. Every commit has a fixed part, the flush of the log to disk, and a per-row part. Picture a delivery van: the trip costs the same for 1 parcel or 100, so you wait and send them together. If a worker commits 100 rows together in one transaction (a group of changes that succeed or fail as one unit), it pays the fixed part once. The PostgreSQL manual says this directly for bulk loads: do one commit at the end. The reason is that letting each row commit separately makes the database do much work per row. It also says `COPY` is optimized for loading many rows with much less overhead than separate `INSERT` statements.

Batching has a cost. A batch is acknowledged together, so each row waits for the batch to fill. A bad row can fail the whole transaction. And a bigger batch gives smaller gains each time, because the fixed part shrinks next to the per-row part.

**Use a store built for writes.** A B-tree updates pages in place (the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson). A **log-structured merge tree** (LSM tree) appends. Cassandra's write path is the standard example (the [Cassandra](/learn/backend/08-technologies/cassandra/) lesson). A write goes to the commit log, a sequential append, and to the memtable, a sorted structure in memory. When the memtable is full it is flushed to an immutable SSTable file (a sorted file on disk that is never changed after it is written). A write is never an in-place edit. The cost moves to reads, which may check several files, and to compaction, which merges those files in the background, like tidying a pile of sorted notes into one pile. Pick this kind of store when writes dominate and reads are by key or by a known range.

### Move 2: absorb bursts with a queue

Put a durable queue (the [Queues](/learn/backend/06-async/queues/) lesson) between the API and the database. The API appends the write and answers with an ack (an acknowledgement: "I got it"). A worker drains the queue at the speed the database allows. A burst becomes a backlog. The database sees a steady load.

This is **write-behind**: the write is acknowledged before it lands in its final home. Know what you gave up:

- The ack means "accepted", not "readable". A reader who checks at once may see nothing. That is the read-your-writes problem again (the [Consistency Models](/learn/backend/04-data/consistency-models/) lesson). Return the new value from the write path, or read through the queue's state.
- The queue must be durable, such as a replicated log. A write-behind cache in volatile memory loses acknowledged writes on a crash.
- Delivery is at-least-once (the [Delivery Semantics](/learn/backend/06-async/delivery-semantics/) lesson), so the worker may apply a write twice. Make writes idempotent (the [Idempotency](/learn/backend/03-api-design/idempotency/) lesson): applying the same write twice must give the same result as applying it once.
- The queue must drain. If the average write rate is above the drain rate, the backlog grows without end. In that case, you need backpressure (the [Backpressure and Dead-letter Queues](/learn/backend/06-async/backpressure-dlq/) lesson).

### Move 3: shard

When the sustained rate is above one node's ceiling, split the data (the [Sharding](/learn/backend/04-data/sharding/) lesson). A hash of the shard key picks the node. With an even spread, N shards take about N times the writes. That is the only way to raise the write ceiling for good.

The shard key decides everything. It sets how well writes spread, and which queries stay on one shard. Choose a key with many different values (high cardinality) and even traffic, such as a user id. Do not choose a key such as the date, because all of today's writes share one value.

### Move 4: break up hot keys

Sharding spreads keys, not one key. If a single key takes a large share of writes, the shard that holds it saturates while the others idle. DynamoDB documents each partition (one slice of a table, held on its own machines) as designed for 1,000 write units per second (one write unit is one write per second of an item up to 1 KB) (the [DynamoDB](/learn/backend/08-technologies/dynamodb/) lesson). A hot key hits that limit no matter how many partitions the table has.

The fix is **key salting**. Add a suffix to the key: `hot#0`, `hot#1`, up to `hot#k`. The writes for one logical key now go to `k` physical keys, which usually live on different shards. DynamoDB's guide describes two ways to pick the suffix:

- **Random suffix.** Choose a random number for each write. Writes spread evenly. The guide's example adds a number from 1 to 200 to a date key. To read the day back, you must query every suffix and merge.
- **Calculated suffix.** Derive the suffix from another field, such as a hash of the order id. Writes still spread, and you can find one item because you can recompute its suffix. Reading the whole day still needs every suffix.

So salting trades a cheap write for an expensive read: `k` lookups. For counters, keep `k` partial counters and add them when you read.

## The model behind the numbers

**The model.** Each commit has a fixed cost plus a small cost per row. With one row per commit, the fixed cost dominates. A big batch shares that fixed cost over many rows, so throughput rises toward a ceiling set by the per-row cost. For sharding, a hot key lands on one shard, and that shard gets more than its fair share. Salting splits the hot key over several shards and cuts the hottest shard's share. The cluster limit is set by the hottest shard, not by the total.

**Assumptions.** The two costs are illustrative round numbers, not measurements of any database. Other keys spread evenly. Shards are equal. Salts land on different shards. There are no cross-shard transactions and no network cost. The burst uses a steady level of normal traffic.

With no salts, the hot key's shard saturates first, and the cluster takes far less than the sum of its shards. With more salts, the hot share falls toward an even spread, so the cluster limit climbs back close to the sum of its shards.

## Trade-offs

| Technique | You gain | You pay | Choose when |
|---|---|---|---|
| Batching | Several times more rows per second per node, no new parts | Added latency, all-or-nothing batches | Bulk or stream ingestion |
| LSM store | Cheap sequential writes | Costlier reads, compaction work | Write-heavy, key-based reads |
| Queue (write-behind) | Bursts flatten into a backlog | Ack is not "readable", duplicates, a queue to run | Spiky load, work that can wait |
| Sharding | Write ceiling grows with node count | Resharding, no cross-shard joins or transactions | Sustained load above one node |
| Key salting | Hot key spreads across shards | Reads need `k` lookups and a merge | A few keys take a large share |

## Interview lens

<Callout type="tip">
Say which problem you have before you pick a fix. "Is it total volume or one hot key?" Then give the order: "Batch first, since it is free. A queue to absorb the sale spike. Shard by user id for the sustained rate. If one key is hot, salt it and sum the partial counts on read." Size it from the load: "The peak is several times one node, so I need more shards, with headroom."
</Callout>

<Callout type="mistake">
Do not say "add replicas" for a write problem. Do not shard by a low-cardinality key such as country or date. Do not put a queue in front and call it done. Say what the ack means, and what happens when the backlog does not drain. And do not forget that salting breaks the simple read.
</Callout>

<Callout type="deep" title="Sharded counters">
A like counter for a viral post is a hot key by design. One row updated thousands of times a second is also slow on its own. The reason is that every update makes a new row version in PostgreSQL (the [PostgreSQL](/learn/backend/08-technologies/postgresql/) lesson). Split the counter into `k` rows. A like increments a random one. A read adds them all, or a background job adds them into one cached total. The count is a little late and never lost.
</Callout>
