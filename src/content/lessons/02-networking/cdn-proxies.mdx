## The problem

Your servers are in New York. A user in London opens your site. Lesson 1.2 gave the physics: light in fiber moves at about 200,000 km per second, and New York to London is about 5,600 km. One round trip takes at least 56 ms, before any routing or queueing.

Lesson 2.3 counted how many round trips a cold HTTPS request needs: 3 with TLS 1.3 over TCP. That is at least 3 x 56 = 168 ms before the first byte (derived), for every new visitor, for every file.

A second pain sits at your end. Say a launch image is requested 1 million times in an hour. Without help, your origin serves it 1 million times. It uses CPU, bandwidth and connections to send the same bytes.

Faster servers fix neither one. Distance is physics, and a copy of the same file is the same file.

## Naive solution: more servers, in one place

Add more servers behind a load balancer (lesson 2.4). Your capacity grows. The London user still waits 168 ms. You can buy servers in London, but now you must run a full copy of your application, and its data, in every region. Module 4 shows how hard replicating data is. Most of what a page loads is not data that changes per user. It is the same logo, script and stylesheet for everyone.

So separate the two. Keep the one authoritative **origin** where it is. Put cheap copies of the shared bytes near users.

## The mechanism

### Proxies: who is the proxy working for?

A **proxy** is a server that makes requests on behalf of someone else. Which side it stands on gives it a name (MDN uses the same split).

<ProxyKinds />

A **forward proxy** acts for the clients. An office uses one to filter and log web access, to cache for a group, or to hide client addresses. Clients are set up to use it. A **reverse proxy** acts for the servers. Clients think it is the real server. It can end TLS, balance load, cache, authenticate and compress.

You already met a reverse proxy: the layer 7 load balancer in lesson 2.4. A CDN edge, an API gateway (Module 8) and nginx in front of an app are all reverse proxies with different jobs. One side effect to know: the server now sees the proxy's address. The `X-Forwarded-For` header, and the standard `Forwarded` header, carry the original client address, so you must read those for logs and rate limits (and only trust them from your own proxies).

### A CDN: reverse proxy caches near users

A **CDN** (content delivery network) runs reverse proxy caches in many cities. Each cache site is an **edge**. Your **origin** is the server that holds the truth. The edge stores responses and answers repeat requests itself.

Two questions come first. How does a user reach the nearest edge, and what happens on a request?

**Reaching the edge.** There are two common tools. With **DNS routing**, the CDN's name servers answer with the IP of a nearby edge (lesson 2.2). With **anycast**, every site announces the same IP range over BGP, the internet's routing protocol, and routers send a packet along the shortest path, so the nearest site wins. Cloudflare describes this design. It works well for stateless protocols like UDP. TCP needed extra engineering to run over anycast without routes flapping.

**The request.** The edge builds a **cache key** from the URL, plus the request headers that the response's `Vary` header names. If a fresh copy exists, that is a **hit**. The edge answers, and the origin never hears of it. If not, it is a **miss**. The edge fetches from the origin, stores the response if its headers allow, and returns it.

Many edges mean many misses for the same file. A popular file can be fetched by each edge once per expiry period. A **shield** fixes this. It is one more cache layer between the edges and the origin. All edges ask the shield, and the shield asks the origin. AWS says CloudFront Origin Shield consolidates requests for the same object, "resulting in as few as one request going to your origin". ### Cache headers: the origin controls the rules

The edge does not guess how long to keep a file. The origin says so in `Cache-Control` (RFC 9111). The directives that matter:

- `max-age=N`: the response is fresh for N seconds after it was made.
- `s-maxage=N`: the same, for **shared caches** only (caches that serve many users, such as a CDN). It overrides `max-age` there. A **private cache** is one user's cache, such as the browser. It ignores `s-maxage`.
- `public` and `private`: `private` means only a private cache may store it.
- `no-store`: do not store it anywhere. `no-cache`: store it, but ask the origin before each reuse. Despite the name, `no-cache` does not mean "do not cache".
- `stale-while-revalidate=N` (RFC 5861): after expiry, serve the stale copy for N more seconds while refreshing in the background. Users do not wait.
- `stale-if-error=N` (RFC 5861): if the origin fails with 500, 502, 503 or 504, serve the stale copy for N seconds.

### What gets cached, and what does not

Not every response is safe to share. Cloudflare's default is to cache by file extension (scripts, styles, images, fonts and so on) and not HTML or JSON. It also skips responses that carry `Set-Cookie` or `Cache-Control: private`, `no-store`, `no-cache` or `max-age=0`, and any method but GET. MDN notes that a request with an `Authorization` header is not stored in a shared cache unless the response says `public`.

The danger is a personalized page cached under one URL. If `/account` is stored by the CDN, the next visitor sees the first user's data. Mark personal responses `private` or `no-store`. When a response varies by header (language, for example), use `Vary` so each variant gets its own key. Do not `Vary` on something with endless values like `Cookie`, or the hit ratio falls to zero.

Public JSON can be cached, with an explicit rule. A "trending posts" endpoint with `s-maxage=10` turns 10,000 requests per second into about 1 origin request per 10 seconds per edge (derived).

### Changing a file that is already cached

Two ways. **Invalidation** tells the CDN to drop the file, so the next request goes to the origin. It costs money past a free allowance, takes time to spread, and does not reach copies in browsers. **Versioned file names** avoid the problem: `app.3f9c2a.js` never changes, and a new build is `app.8b1d07.js`. Set `max-age=31536000, immutable` on the versioned file. The HTML that points to it uses `no-cache`, so it is always fresh. AWS recommends versioning as the primary method for files you change often.

## Numbers

| Item | Value | How we know |
|---|---|---|
| NY to London, best-case round trip | at least 56 ms | lesson 1.2: 5,600 km at 200,000 km/s, there and back |
| Cold HTTPS, TLS 1.3 over TCP | 3 round trips = at least 168 ms | lesson 2.3 times 56 ms |
| Warm connection to a nearby edge | 1 short round trip | the edge is in your metro area, far below the 56 ms floor |
| Origin load | requests x (1 - hit ratio) | definition |
| Example: 10,000 requests/s, 95% hit ratio (assumed) | 500 requests/s reach the origin | derived |
| Origin requests per object per TTL, E edges | up to E without a shield, 1 with | derived upper bound for popular objects |

Hit ratio is not a constant. It depends on how many different objects you serve and how long they live. Do not quote a typical CDN hit ratio. Say "I would measure it, and tune TTLs and cache keys to raise it".

## Trade-offs

| Choice | You gain | You pay | Pick it when |
|---|---|---|---|
| CDN for static files | Low latency, tiny origin load | Stale copies, cost per request or byte | Always, for public static assets |
| Long TTL with versioned URLs | Highest hit ratio, instant rollback | A build step that renames files | Scripts, styles, images |
| Short TTL on dynamic data | Small staleness window, big offload on hot URLs | Some staleness | Public, popular, non-personal data |
| Origin shield | One origin fetch per object, not one per edge | Extra hop on a miss, extra charge | Many edges, expensive origin work |
| Invalidation | Fast removal | Cost, spread time, browsers keep copies | Emergencies, such as a wrong file |

## Interview lens

<Callout type="tip">
For a global read-heavy system, say it at the edge: "Static files and public pages go through a CDN. Hashed asset names get a one-year max-age. The shield cuts origin fetches. Personalized responses are private and bypass the cache." Then add the numbers: a London user's round trip is at least 56 ms to New York and a few ms to a nearby edge.
</Callout>

<Callout type="mistake">
Do not say "put the API behind a CDN" without saying what is cacheable. Cloudflare does not cache JSON by default. A per-user response cached under a shared key leaks data. Also do not answer "how do we ship a new version?" with "invalidate on every deploy". Version the file names. And do not claim a shield makes users faster. It protects the origin.
</Callout>

<Callout type="deep" title="Why a hit can still be slow">
A hit saves the long haul, but the user still opens a connection to the edge: TCP and TLS handshakes (lesson 2.3). The edge is near, so each round trip is cheap, but the count is the same. A CDN can also reuse warm connections from edge to origin, so a miss need not pay a cold handshake across the ocean.
</Callout>
