## The problem

Your servers are in New York. A user in London opens your site.

The [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson gave the physics. Light in fiber moves at about 200,000 km per second. New York to London is about 5,600 km. A round trip is there and back: 11,200 km. That takes at least 56 ms, before any routing or queueing.

The [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson counted the round trips for a first HTTPS request: 3 with TLS 1.3 over TCP. That is three of those long round trips before the first byte of the page arrives. A new visitor pays this. A repeat visitor on a new connection pays it too.

There is a second pain, and it sits at your end. Say a launch image is requested 1 million times in one hour. Your server sends the same bytes 1 million times. It spends CPU, network bandwidth, and open connections on a file that never changes.

Faster servers fix neither pain. Distance is physics. And a copy of a file is the same file.

This lesson follows one idea from start to end. Keep copies of shared files close to users. Then deal with the problems that copies bring: who hands them out, how users find them, when they go out of date, and how you replace them.

## The naive way: more servers, all in one place

The first idea is to add more servers behind a load balancer (the [Load Balancing](/learn/backend/02-networking/load-balancing/) lesson). Your capacity grows. The London user still waits 168 ms, because the servers are still in New York.

The second idea is to run a full copy of your application in London. Now you must also keep your data in London, and keep it in step with New York. Module 4 shows how hard that is.

Look at what a page loads. Most of it is the same logo, script, and stylesheet for every visitor. Call these **static files**: files that are the same for everyone and change rarely. They need no database and no logic. Only the delivery is slow.

So split the job in two.

- Keep one **origin**. The origin is the server that owns the real, authoritative copy of everything. Think of a factory that makes the product.
- Put cheap copies of the static files close to users. A saved copy of an answer, kept so it need not be fetched again, is a **cache**. Think of a corner shop that stocks the popular items. You do not drive to the factory for milk.

Why does this work? The factory makes each item once. The shops hand it out a million times. Number to remember: one origin request can serve a million user requests, if the copy stays valid.

Two problems remain. Someone must run the corner shop. And the shop must know when its stock is old. The next sections solve both.

## The mechanism

### Proxies: a server that speaks for someone else

A **proxy** is a server that makes requests on behalf of someone else. Think of a receptionist. You do not walk into the manager's office. You talk to the desk, and the desk talks to the manager. The receptionist can screen visitors, take messages, and answer easy questions without bothering the manager.

A middle point is a good place to do shared work once, for many people. Number: one office with 500 laptops can send all its web traffic through one proxy, and the proxy can log and filter all 500.

The name of a proxy depends on whose side it stands on.

A **forward proxy** stands for the clients. The clients are set up to use it. A company office uses one to filter and log web access, or to hide the laptops' addresses. The website sees the proxy's address, not the laptop's.

A **reverse proxy** stands for the servers. The client does not know it is there. It thinks it is talking to the real server. The proxy takes the request and passes it to a real server behind it. Think of a shop front: you talk to the counter, and never see the stockroom.

<ProxyKinds />

A reverse proxy does shared work for the servers behind it:

- It can end the encryption. **TLS termination** means the proxy does the TLS work (the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson) and passes plain requests to the servers behind it. Think of a mailroom that opens sealed envelopes in the lobby, so the staff upstairs get plain letters. The benefit: the proxy sits near the user, so the TLS handshake round trips are short ones.
- It can spread load across servers. You already met this: the layer 7 load balancer in the [Load Balancing](/learn/backend/02-networking/load-balancing/) lesson is a reverse proxy.
- It can keep a cache, check logins, and compress responses.

Real examples: **nginx** (said "engine-x") is a popular free program that people run as a reverse proxy. An **API gateway** is a reverse proxy in front of an API. It checks logins and limits traffic. A CDN, which comes next, is also a reverse proxy.

One side effect to know. The server now sees the proxy's address as the sender. Say your server rate-limits by address, and 10,000 users arrive through one proxy at `10.0.0.5`. The server counts 10,000 requests from one address and blocks them all. So the proxy adds a header, `X-Forwarded-For`, that holds the real client address. Your code reads that header for logs and rate limits. Trust it only when it comes from your own proxies, because any client can send a fake one.

### CDN: a chain of corner shops

A **CDN** (content delivery network) is a company-run fleet of reverse proxies with caches, placed in many cities. Think of a chain of corner shops across the world, all stocked from your factory. Cloudflare, Amazon CloudFront, and Akamai are well-known CDNs.

Each shop is a site in one city. People call this site an **edge** or a **PoP** (point of presence). "Edge" means it sits at the edge of the network, close to users. The edge stores responses. When a user asks for a file the edge already holds, the edge answers itself.

The reason is simple: you cannot beat distance with faster hardware. You can only move the data closer. Number: the round trip to an edge in your own city is a few ms (assumed), against 56 ms to New York.

### Reaching the nearest edge

The user types `example.com`. Something must send that user to the London edge, not the Tokyo edge. Two tools do this.

**DNS routing.** The [DNS](/learn/backend/02-networking/dns/) lesson showed that DNS turns a name into an IP address. A CDN's DNS servers can look at where the question came from, and answer with the address of a nearby edge. Two users asking for the same name get two different addresses.

**Anycast.** Normally one IP address belongs to one machine. With anycast, many edges all announce the same IP address. Think of a national helpline number. You dial one number, and the phone network connects you to the nearest call center. How does the internet do it? Networks tell each other which addresses they can reach, using a system called **BGP** (Border Gateway Protocol). Each edge announces the shared address, and routers send your packet along the best path they know. That is usually the closest edge. It is closest by network path, which is not always the closest on a map.

Each tool has a weak side. DNS routing is easy but depends on DNS answers, which get cached (the TTL from the [DNS](/learn/backend/02-networking/dns/) lesson). Anycast needs no DNS trick, and a failed edge simply drops its announcement and traffic moves on. The catch: a TCP connection must keep reaching the same edge. If routes change halfway, packets land at an edge that never saw the handshake. Cloudflare describes how it engineered around this.

### How one request is served

Before it can serve a copy, the edge needs a way to look one up. It builds a **cache key**: a label that names one stored response. Usually the key is the URL, such as `/logo.png`. Think of the index card in a library that tells the librarian which shelf to check. Same card, same book.

Then one of two things happens.

- A **cache hit**: the edge has a fresh copy under that key. It answers at once. The origin never hears about this request.
- A **cache miss**: the edge has no copy, or the copy is out of date. It asks the origin, stores the answer if the answer's headers allow, and returns it. This request pays the long trip.

The **hit ratio** is the share of requests that are hits. Number: with 10,000 requests per second and a 95% hit ratio, 9,500 are hits. Only 500 per second reach your origin. The origin load is requests x (1 - hit ratio). Moving from 95% to 99% cuts origin load from 500 to 100 per second. Every point of hit ratio matters.

There is one more problem. You have many edges, and each starts empty. A popular file is a miss once on every edge. With 40 edges, your origin can get 40 requests for one file per expiry period. Fix this with a **shield**: one more cache layer between the edges and the origin. Think of a regional warehouse between the shops and the factory. The shops order from the warehouse. The warehouse orders from the factory, once. AWS says its Origin Shield can send "as few as one request" to your origin for the same file.

Step through it below. In the picture, `GET` means "please send me this file", and `200` means "OK, here it is" (the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson). A packet is the little box moving along a line.

The shield makes the origin quiet. It does not make users faster. A miss now has an extra hop. The shield protects the origin, and the edge makes the user fast.

### Cache-Control: how long a copy may be kept

The edge does not guess. The origin says how long in a response header called **Cache-Control**. Think of the "best before" date on a food package. The shop reads the date. It does not decide.

The origin sends a list of directives. Each directive is one rule. Here are the ones you need.

| Directive | What it says | Everyday picture | Example |
|---|---|---|---|
| `max-age=N` | The copy is **fresh** for N seconds after the origin made it. Fresh means the cache may serve it without asking anyone. After N seconds the copy is **stale**: old enough that it needs a check before the next use. | Best-before date | `max-age=60`: up to 60 s of fresh service |
| `s-maxage=N` | Like `max-age`, but for shared caches only. A shared cache uses it instead of `max-age`. A private cache ignores it. | A bulk-buyer date on the crate, and a shorter date on the single item | `max-age=60, s-maxage=3600`: CDN keeps it 1 hour, browser 1 minute |
| `public`, `private` | `public`: any cache may keep it. `private`: only one user's own cache may keep it. | A shop shelf against your own bag | `private` on a page with your name on it |
| `no-store` | Do not keep it anywhere. | A note you read and burn | Private data |
| `no-cache` | Keep it, but ask the origin before each reuse. Despite the name, it does not mean "do not cache". | Phone the factory before every sale | The HTML page that names your files |
| `immutable` | This file will not change while it is fresh, so do not even check it. | A printed book edition | A file whose name changes when its content changes |

Two words need care. A **private cache** is one user's own cache, such as a browser. A **shared cache** serves many users, such as a CDN edge. Why have `s-maxage` at all? You often want the CDN to keep a file for an hour, while browsers check back every minute.

What does "ask the origin" cost? Less than a full fetch, if the cache uses **revalidation**. The cache sends the origin a fingerprint of its stale copy. This fingerprint is called an **ETag** (entity tag). It is a short string the origin gave out with the file, such as `"v7a3"`. The cache asks: "I hold version `v7a3`. Is it still current?" If yes, the origin answers `304 Not Modified`, which has no body. The 1 MB file is not sent again. The cache marks its copy fresh once more. If no, the origin sends the new file.

Two more directives remove waiting and errors.

- `stale-while-revalidate=N`: after the copy goes stale, the cache may serve the stale copy for N more seconds and refresh it in the background. Think of a shop that hands you the last loaf now and phones the bakery while you walk out. The user does not wait. Number: with `max-age=60, stale-while-revalidate=30`, requests in seconds 60 to 90 get an instant answer.
- `stale-if-error=N`: if the origin fails (it answers 500, 502, 503, or 504, which all mean "the server broke"), the cache may serve the stale copy for N more seconds. Think of a shop that sells yesterday's bread when the bakery is closed. Users see an old page, not an error.

Now try it. Slide the age. Watch the CDN and the browser disagree about the same copy. Then tick the box to take the origin down.

### What is safe to cache

Not every response is safe to share. A shared cache that stores the wrong response shows one user's data to another.

Picture a shop that keeps a pile of "my order" slips on the counter, and hands the top slip to whoever walks in. That is what happens if the CDN stores `/account`, the page with your name on it. The next visitor with the same URL gets the first visitor's page. That is a leak.

So CDNs follow rules. Cloudflare's default is to cache by file extension: scripts, styles, images, fonts. It does not cache HTML or JSON by default. It also skips these:

- Any method but GET. A GET only reads. A POST changes something, so the CDN does not store its answer.
- A response with `Set-Cookie`. A **cookie** is a small value the server asks the browser to send back on every later request, often to identify one user. A response that sets one is probably personal.
- A response marked `private`, `no-store`, `no-cache`, or `max-age=0`.

MDN notes one more case. A request that carries an `Authorization` header (a login credential) is not served from a shared cache, unless the response explicitly allows it, for example with `public`.

Mark every personal response `private` or `no-store`. That is the safe default.

Sometimes one URL has several valid versions, for example a page in English and in French. The response header `Vary` names the request header that decides the version, such as `Vary: Accept-Language`. The edge then adds that header's value to the cache key. English and French get separate copies. Number: with 2 languages you store 2 copies of the page.

Be careful. Never `Vary` on something with endless values, like `Cookie`. If every user has a different cookie, every request gets its own key, and the hit ratio falls close to zero. The Diagnose below shows this.

Public JSON can be cached, if you say so in the headers. A "trending posts" endpoint with `s-maxage=10` turns 10,000 requests per second into about 1 origin request per 10 seconds per edge (derived). The data is at most 10 seconds old. For trending posts, nobody minds.

### Replacing a file that is already cached

You fixed a typo in `app.js`. Thousands of copies of the old file sit in edges and in browsers. There are two ways to deal with it.

**Invalidation** (also called **purge**) tells the CDN: drop your copy of this URL. The next request is a miss and fetches the new file. Think of a product recall notice that goes to every shop. It works, but it has limits. It costs money after a free allowance. It takes time to reach all edges. And it does not reach copies in browsers, because the CDN cannot call your users' laptops.

**Versioned file names** avoid the problem. Put a **content hash** in the file name. A hash is a short fingerprint computed from the file's bytes. The same bytes always give the same fingerprint, and any change gives a different one. So `app.3f9c2a.js` never changes. When you ship a new build, its name is `app.8b1d07.js`. A new name is a new cache key, so no cache can hold a stale copy of it. Think of a new product with a new barcode: the old stock cannot be confused with it.

Then set `max-age=31536000, immutable` on the versioned file. That is 365 days. The file never needs a check. The page that mentions the file, the HTML, is the one thing that must stay current. Give the HTML `no-cache`, so every visit asks the origin and sees the newest file names. AWS recommends versioning as the main method for files that change often. Keep invalidation for emergencies, such as a wrong file that went out.

## Numbers

| Item | Value | How we know |
|---|---|---|
| New York to London, best-case round trip | at least 56 ms | the [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson: 5,600 km each way at 200,000 km/s |
| First HTTPS request, TLS 1.3 over TCP | 3 round trips, each at least 56 ms | the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson times the floor |
| Warm connection to a nearby edge | 1 short round trip | the edge is in your city, far below the 56 ms floor |
| Origin load | requests x (1 - hit ratio) | definition |
| Origin requests per file per freshness period, E edges | up to E without a shield, 1 with | derived upper bound for popular files |

The hit ratio is not a constant. It depends on how many different files you serve and how long each stays fresh. Do not quote a "typical" CDN hit ratio. Say: "I would measure it, then tune freshness times and cache keys to raise it."

## Trade-offs

| Choice | You gain | You pay | Pick it when |
|---|---|---|---|
| CDN for static files | Low latency, tiny origin load | Stale copies, cost per request or byte | Always, for public static files |
| Long freshness with versioned file names | Highest hit ratio, instant rollback | A build step that renames files | Scripts, styles, images |
| Short freshness on dynamic data | Small staleness window, big offload on hot URLs | Some staleness | Public, popular, non-personal data |
| Origin shield | One origin fetch per file, not one per edge | An extra hop on a miss, an extra charge | Many edges, expensive origin work |
| Invalidation | Fast removal | Cost, spread time, browsers keep copies | Emergencies, such as a wrong file |

## In practice

<Callout type="tip">
For a global read-heavy system, say it at the edge: "Static files and public pages go through a CDN. Versioned file names get a one-year max-age. A shield cuts origin fetches. Personal responses are private and skip the cache." Then add the numbers. A London user's round trip to New York is at least 56 ms. The round trip to a nearby edge takes a few ms.
</Callout>

<Callout type="mistake">
Do not say "put the API behind a CDN" without saying what is cacheable. Cloudflare does not cache JSON by default. A per-user response stored under a shared key leaks data. Do not answer "how do we ship a new version?" with "invalidate on every deploy". Version the file names. And do not claim a shield makes users faster. It protects the origin.
</Callout>

<Callout type="deep" title="Why a hit can still be slow">
A hit saves the long haul to the origin. But the user still opens a connection to the edge. That connection needs the TCP and TLS handshakes (the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson). The edge is near, so each round trip is cheap, but the count is the same. Say the edge round trip is 10 ms (assumed). A first HTTPS request then costs 3 x 10 = 30 ms, against 168 ms to New York.

A CDN can also keep warm connections open from edge to origin and reuse them. A miss then skips the cold handshakes across the ocean.
</Callout>
