## The problem

One server has a ceiling. In lesson 1.1 a pool of 200 threads, each waiting 50 ms, served at most 4,000 requests per second. Past that, requests queue (lesson 1.3). You can buy a bigger machine for a while. Then you hit the largest one.

Also, one server is one point of failure. When it crashes, the site is down.

So you run several identical servers. This creates new questions. Which address does the client call? Who decides which server gets this request? What happens when one server dies?

## Naive solution: DNS round robin

Publish several A records for one name, one per server. Resolvers rotate the list. Clients spread over servers. No new component.

It fails in three ways (lesson 2.2):

- **No health awareness.** DNS keeps returning the dead server's IP until the record changes and every cache expires.
- **No load awareness.** Rotation ignores that one server is full and another is idle.
- **Caching.** A resolver that cached one IP sends all of its users to that one server for a full TTL.

DNS is fine for choosing a region. It is too slow and too blind to balance requests.

## The mechanism: a load balancer in front

A **load balancer** (LB) is a server that sits in front of the pool. Clients connect to the LB's address. The LB picks a pool member and forwards the request. It has four parts:

1. A **listener**: the port and protocol it accepts.
2. A **pool** of backend servers, also called targets.
3. A **routing algorithm** that picks a server.
4. **Health checks** that decide which servers are in the pool.

<LbFailover client:visible />

The LB answers the failure question with a **health check**: a probe it sends to each server on a timer. A server that fails several probes in a row leaves the pool. It re-enters after several successes. This is an *active* check. A *passive* check watches real traffic instead: nginx marks a server failed after real requests to it fail (default `max_fails` of 1). Most setups use both.

### Layer 4 or layer 7

Network protocols stack in layers (lesson 2.1). **Layer 4** is the transport layer: TCP and UDP connections. **Layer 7** is the application layer: HTTP. A load balancer can work at either.

<LayerFourSeven />

A layer 4 LB sees only addresses, ports and flags. It picks a server when a connection opens, and every packet of that connection goes to that server. It is fast and protocol-agnostic. AWS Network Load Balancer works this way. It tracks a TCP flow and, by default, drops its state after 350 seconds of idle time.

A layer 7 LB reads each HTTP request. It can send `/api` to one pool and `/images` to another, add headers, retry a failed request on another server, and terminate TLS so backends skip the handshake work. AWS Application Load Balancer works this way. The price is CPU, since it parses every request.

With HTTP/2 or gRPC, one connection carries many requests. A layer 4 LB then pins all of them to one server. A layer 7 LB can spread them per request. Lesson 2.6 returns to this.

### Algorithms

| Algorithm | How it picks | Strength | Weakness |
|---|---|---|---|
| **Round robin** | Next server in order | Simple, even request count | Ignores request cost and server speed |
| **Weighted round robin** | Order, with more turns for big servers | Handles mixed hardware | Weights are set by hand |
| **Least connections** | Fewest active requests now | Adapts to slow requests | Needs live counts; new server gets a burst |
| **Hash (client IP or key)** | Hash of a key, modulo pool size | Same client, same server (sticky) | Skewed if one key is hot; reshuffles when the pool changes |

Try them on identical traffic. One request in five is heavy, and one client is noisy. Switch algorithms, then kill a server.

<LoadBalancerSim client:visible />

Look at what happens with hash when a server dies: the pool size changes, so `hash % N` changes, and most clients move to a different server. With 3 servers going to 4, only 1 in 4 keys stays where it was. Module 4 fixes this with consistent hashing.

<Callout type="deep" title="Health checks can cause the outage">
A deep health check that calls the database seems careful. But if the database slows down for 10 seconds, every server fails its check at once. The LB removes all of them. Many LBs avoid this by failing open: AWS ALB sends traffic to all targets when every target is unhealthy. Keep checks shallow (is this process able to serve?) unless you have a reason. Also set the thresholds on purpose. Slow detection means errors. Fast detection means a brief hiccup flaps servers in and out.
</Callout>

### Sticky sessions

Sometimes a user's state lives in one server's memory. The LB can pin the user with a cookie so later requests return to the same server. ALB supports this with a load-balancer cookie or an app cookie (1 day by default). It works, but it hurts: load becomes uneven, and if the pinned server dies the user loses their session. The better design is **stateless servers** with sessions in a shared store, so any server can serve any request.

### The LB is itself a single point of failure

Do not forget this. Run more than one LB node. Managed LBs do it for you: an AWS Network Load Balancer has one IP address per Availability Zone, and its DNS name returns them all. So DNS picks the LB node, and the LB node picks the server. The two techniques work together.

## Numbers

| Setting | Typical value (AWS ALB defaults) |
|---|---|
| Health check interval | 30 s |
| Probe timeout | 5 s |
| Failed probes to remove a server | 2 |
| Passed probes to restore a server | 5 |
| Time a dead server keeps receiving traffic | about 2 x 30 s = 60 s |
| NLB idle timeout for a TCP flow | 350 s |

Capacity math: with N servers sharing load evenly, losing one raises the load on each survivor by N / (N - 1). Three servers at 70% each carry 2.1 units. Two survivors would need 105%. So they overload. This is why you plan for N+1 and keep normal load below about (N - 1) / N.

## Trade-offs

| Choice | You gain | You pay | Pick it when |
|---|---|---|---|
| Layer 4 LB | Speed, any TCP/UDP protocol, TLS passes through | No view of requests, per-connection balancing only | Databases, game servers, very high throughput |
| Layer 7 LB | Path routing, retries, TLS offload, per-request balancing | CPU per request, one more hop | Web and API traffic, HTTP/2 and gRPC |
| Round robin | Simplicity | Blind to load | Similar requests, similar servers |
| Least connections | Handles uneven request cost | State and a cold-start burst | Long or variable requests |
| Sticky sessions | Quick fix for in-memory state | Uneven load, lost sessions on failure | Short-term bridge only |

## Interview lens

<Callout type="tip">
Place the LB explicitly: "Clients resolve DNS to the LB. A layer 7 LB terminates TLS, routes by path, and checks health every few seconds. Servers are stateless, so any server can take any request. We keep N+1 capacity." Naming health checks and N+1 shows you have run production systems.
</Callout>

<Callout type="mistake">
Do not draw one box labeled "Load Balancer" and move on. Say what happens when it fails, and what happens when a backend fails. Also do not use sticky sessions to avoid fixing server state. It trades a design problem for an outage.
</Callout>
