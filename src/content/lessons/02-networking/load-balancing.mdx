## The problem

Your service runs on one server. The [What a Computer Does With a Request](/learn/backend/01-one-machine/request-journey/) lesson showed what limits that server. It had a pool of 200 threads. Each request kept one thread busy for 50 ms while the thread waited for a database.

One thread finishes 20 requests per second (1 second divided by 50 ms). 200 threads finish 4,000 requests per second. The 4,001st request in that second waits in a queue, as the [Throughput vs Latency](/learn/backend/01-one-machine/throughput-vs-latency/) lesson showed.

You have two ways to raise that ceiling.

- Buy a bigger machine. This is **scaling up**. Picture one cashier in a shop who gets a faster till. It helps for a while. Then you own the biggest machine that exists, and the ceiling is still there.
- Add more machines. This is **scaling out**. Picture the shop opening three tills instead of one. Three identical servers (same code, same settings) carry about three times the load of one.

There is a second problem. One server is a **single point of failure**. That term means one part that, when it breaks, stops the whole system. Picture a one-lane bridge. One stalled car blocks every driver behind it.

The risk is real. Even a server that works 99.9% of the time is still down for hours each year. With three servers, any two can carry on while the third is down.

Running several servers raises three new problems.

1. The client knows one name. Which server does it call?
2. Something must decide which server gets each request.
3. Something must handle a server that dies.

The rest of this lesson solves them. We start with the simplest idea and watch it fail.

## The naive way: DNS round robin

The [DNS](/learn/backend/02-networking/dns/) lesson showed that DNS turns a domain name into an IP address. A name can have several addresses. So here is a first plan: list the addresses of all three servers under one name.

The DNS server hands the addresses out in turns. The first asker gets server 1. The second gets server 2. The third gets server 3. The fourth gets server 1 again. Taking turns in a fixed order is called **round robin**. Picture a dealer who gives one card to each player in turn.

This plan is cheap. It needs no new machine. With 3 servers, each one gets about a third of the new lookups.

It fails in three ways.

**1. DNS cannot see health.** The DNS server never checks whether a server is alive. Picture a receptionist who reads room numbers from a printed list. She does not notice that one room is on fire. When server 2 dies, DNS still hands out its address. One user in three gets an error. Some clients try the next address after a wait. Not all do, and every try adds delay.

**2. DNS cannot see load.** Turn-taking counts users. It does not count work. A user who asks for a huge report and a user who asks for a tiny page both count as one turn.

**3. Answers are cached.** Each DNS answer has a **TTL**, the time a resolver may keep the answer (the [DNS](/learn/backend/02-networking/dns/) lesson). Picture a printed flyer that people keep in their pockets. You cannot call the flyers back. Say the TTL is 300 seconds. After you remove a dead server from DNS, its address lives on in caches for up to 5 minutes.

Caching also breaks the even split. A resolver that cached server 1 sends all its users there for the full TTL. If 5,000 office workers share one resolver, all 5,000 hit server 1.

So DNS is fine for slow choices, such as which country's data center a user reaches. It is too slow and too blind to balance single requests. We need a component that sees every request and every server.

## The fix: a load balancer in front

A **load balancer** is a machine (or a program) that stands in front of the servers. Clients talk only to it. It passes each request to one server and passes the answer back. We write **LB** for short.

Picture the host at a restaurant door. Every guest talks to the host. The host sends each guest to a table with a free waiter. Guests never see the kitchen.

This solves the first problem. Clients know one address: the LB. The servers sit behind it. You can add, remove, or replace servers, and no client notices.

Here are the four parts of every LB.

1. A **listener**: the port and protocol the LB accepts traffic on. It is a standing order with its kernel, like the web server in the [IP, TCP, UDP](/learn/backend/02-networking/ip-tcp-udp/) lesson. For web traffic, the listener is on port 443 (encrypted) or port 80 (not encrypted).
2. A **pool**: the set of servers behind the LB. People also call them **backends** or **targets**. Picture the group of waiters the host can choose from.
3. A **routing algorithm**: the rule that picks one server from the pool for each request. This solves the second problem. We cover the rules below.
4. A **health check**: the way the LB decides which servers are fit to stay in the pool. This solves the third problem.

The LB adds one extra hop. A request now goes client, LB, server, LB, client. Inside one data center, an extra hop adds about one round trip of 0.5 ms (the [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson). That small cost buys everything in this lesson.

### Health checks

An LB must learn when a server is dead. It finds out by asking. A **health check** is a small test the LB sends to every server on a timer. The test message is a **probe**. The probe is often a plain HTTP request, such as `GET /health`. `GET` is the HTTP request that reads something, and `/health` is a path where the server answers "OK" if it can work. For non-web traffic, a probe can be just a try to open a TCP connection.

Picture a nurse who walks the ward every 30 seconds and asks each patient, "Are you fine?" A patient who gives no answer is a worry.

One missed answer proves little. A server can be busy for a moment. So the LB counts. It marks a server **unhealthy** only after a set number of failed probes in a row. This number is the **unhealthy threshold**. A probe also has a **timeout**: the longest the LB waits for an answer before it counts the probe as failed. An unhealthy server leaves the pool, and the LB stops sending it requests. The LB keeps probing it. After a set number of passed probes in a row, the server returns to the pool.

Example with real defaults: a probe every 30 s, a timeout of 5 s, two failures to remove a server. A server that dies right after a good probe is removed after about two probe intervals, roughly a minute. For that whole time, the LB still sends it traffic.

This is an **active** check, because the LB sends its own probes. A **passive** check works differently. The LB watches real requests and notes which ones fail. Picture a host who sees that every guest sent to table 3 never gets food. Nginx works this way by default. (Nginx is a popular web server program that can also act as an LB.) It marks a server as failed when a real request to it fails once. Most setups use both kinds.

What you just watched has a name: **failover**. The work of a failed server moves, with no human step, to the servers that still work. Picture a shop where one till closes and its queue splits across the open tills. In the animation, each of two survivors goes from 33% to 50% of the traffic. So the survivors must have spare room. Detection is not free. Say three servers share 3,000 requests per second, and the LB needs 60 seconds to notice a dead one. One request in three goes to the dead server. That is 1,000 failed requests per second, or 60,000 errors in the minute. (This assumes no retries.) The detection time is the cost of the health check.

## Layer 4 and layer 7 load balancers

An LB can read different amounts of each request. In the [IP, TCP, UDP](/learn/backend/02-networking/ip-tcp-udp/) lesson a packet looked like an envelope inside an envelope. Your data is the letter. The transport header (ports) wraps it. The IP header (addresses) wraps that. The frame wraps the rest. Each layer reads only its own header.

An LB has the same choice. It can read only the outer envelopes, or it can open the letter.

Engineers number these layers from the bottom: the frame is layer 2, the IP header is layer 3, the transport header is layer 4, and the letter itself (the HTTP request, which is the **application** layer) is layer 7. The numbers come from an old seven-layer model. You only need 4 and 7.

**A layer 4 LB** reads the IP header and the transport header. It sees addresses and ports. It does not open the letter. Picture a mail clerk who sorts by the address on the outside and never opens an envelope.

It picks a server when a connection opens. Then every packet of that connection goes to that same server. If an encrypted connection (TLS, the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson) comes in, the LB passes the encrypted bytes through. It cannot read them, and it does not need to.

This is fast and works for any protocol. The price is that it is blind to requests. It keeps a small note for each open connection, a **flow table**, so it knows where each packet goes. AWS (Amazon Web Services, a company that rents servers by the hour) sells a layer 4 product called the Network Load Balancer. It forgets a connection after 350 seconds with no traffic. A client that waits longer than that and then sends finds a broken connection.

**A layer 7 LB** opens the letter. It reads each HTTP request (the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson). It sees the **path**, which is the part of the web address after the domain name, such as `/api/users`. It sees the headers. It sees **cookies**. A cookie is a small piece of text that a server gives to a browser. The browser sends it back with every later request. Picture the ticket from a coat check: it tells the clerk which coat is yours.

Because it reads requests, a layer 7 LB can do more.

- Route by path. Send `/api` to one pool and `/images` to another.
- Retry. If one server fails a request, send the same request to another server.
- **Terminate TLS**. The LB does the TLS handshake and the decryption itself, then talks to servers over a private network. Servers skip that work. The certificate (the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson) lives on the LB. Picture a guard at the gate who checks IDs, so the staff inside do not each check them.

The price is CPU, because the LB parses every request. AWS sells a layer 7 product called the Application Load Balancer, or ALB.

One more difference matters with HTTP/2. In HTTP/2, one connection carries many requests at once (multiplexing, the [HTTP and TLS](/learn/backend/02-networking/http-tls/) lesson). A layer 4 LB picks a server per connection. So one busy client with one connection sends all its requests to one server. A layer 7 LB picks per request, so those requests spread out. Example: a client sends 300 requests on one HTTP/2 connection. A layer 4 LB gives one server all 300. A layer 7 LB can give each of 3 servers about 100. The same issue appears with gRPC, a request style built on HTTP/2. The [RPC and gRPC](/learn/backend/02-networking/rpc-grpc/) lesson returns to it.

## Routing algorithms

The LB needs a rule to pick a server for each request. Here are four common rules. Each one has a picture, a use, and a flaw.

**Round robin.** You met it in the DNS section. The LB takes turns: A, B, C, A, B, C. It is simple. Nine requests give each of 3 servers exactly 3. It works well when all requests cost the same and all servers are alike.

The flaw is that it counts requests, not work. Say most requests take 5 ms and a few take 2 s. A server that got two slow ones is busy. Its next turn still comes.

**Weighted round robin.** Each server gets a **weight**, which is its number of turns per round. A server twice as big gets weight 2. The turns go A, A, B. Picture a bigger shop that gets two deliveries for each delivery to a small shop. It handles servers of different size. The flaw: a person sets the weights by hand and must keep them right.

**Least connections.** The LB counts how many requests each server is working on right now. It sends the next request to the server with the lowest count. Picture a shopper who walks to the shortest checkout line. Example: A has 5 active requests, B has 2, C has 4. The next request goes to B.

It adapts to slow requests. A server stuck on heavy work has a high count, so it gets less. There are two costs. The LB must track live counts. And a new server starts at 0, so for a moment it wins every comparison and gets a flood. Picture a new till that opens, and the whole queue runs to it.

**Hash.** A **hash** is a fixed recipe that turns any input, such as a client IP address, into a number. The same input always gives the same number. Different inputs give numbers that look random. Picture a locker office: it turns your name into a locker number by a fixed rule. You get the same locker every time.

The LB then needs a server number from 0 to N-1, where N is the pool size. It uses **modulo**: the remainder after division. Write it `hash % N`. Example: the hash of a client is 17 and N is 3. 17 divided by 3 is 5 with remainder 2. So the client goes to server 2 (counting from 0).

The same client always lands on the same server. We say the client is **sticky** to that server. This helps when a server keeps data for that client in memory. It has two flaws.

1. **Hot keys.** If one client sends 40% of all traffic, one server takes 40% of the load, whatever you do.
2. **The pool changes.** When N changes, `hash % N` changes for most keys. Take N from 3 to 4. Look at the hash values 0 to 11. A value keeps its server only if `hash % 3` equals `hash % 4`. That holds for 0, 1 and 2 only. That is 3 of 12 values, or 25%. About 75% of clients move to a new server. Every client that moves loses whatever that server remembered about it. A later lesson on consistent hashing (Module 4) fixes this.

Now try all of them. First, a note on how the lab works. Time moves in **ticks**. A tick is one step of simulated time. Two requests arrive on each tick. One request in five is heavy and takes 8 ticks. The others take 1 or 2 ticks. One noisy client sends 40% of all traffic. The LB probes each server once per tick. It removes a server after 2 failed probes and restores it after 3 passed probes.

<Callout type="deep" title="Health checks can cause the outage">
A **dependency** is another system your server calls, such as a database. A deep health check calls the dependency, and that seems careful. But think about what happens when the database slows for 10 seconds. Every server fails its check at the same moment. The LB removes all of them. Now nothing serves traffic, and the database was the only thing that was ill.

Some LBs guard against this by **failing open**: when every server looks unhealthy, they send traffic to all of them anyway. AWS ALB does this. Failing open is a safety net, not a design.

Keep checks shallow. Ask only "can this process serve?" Alert on dependencies in a separate place. Set the thresholds with care too. A slow check means long errors. A fast check can cause **flapping**: a server that has one slow second is removed, comes back, is removed again, and so on.
</Callout>

## Sticky sessions

A **session** is what a server remembers about one user between requests: who is logged in, what is in the cart. Picture a waiter who remembers your order. If you wave over a different waiter, he knows nothing.

A server that keeps this memory itself is **stateful**. Picture notes kept in one teller's head. Only that teller can serve you well. A server that keeps nothing between requests is **stateless**. Picture a bank where every teller reads your account from one shared ledger. Any teller can serve you.

If servers are stateful, the LB must send each user back to the same server. This is a **sticky session**. The LB gives the user a cookie that names a server. On the next request, the LB reads the cookie and sends the user there. The AWS ALB supports this. The cookie lasts 1 day by default.

It works, but it hurts.

- Load gets uneven. A server with a few heavy users stays hot.
- If the pinned server dies, its users lose their sessions. If one of three servers dies, about a third of users are logged out at once.

The better design is stateless servers. Keep sessions in a **shared store**, which is a database or a fast in-memory store that every server can reach. Then any server can take any request, and any server can die without a logout.

## The LB is itself a single point of failure

You solved the one-lane bridge for the servers. You built a new one-lane bridge at the front: if the LB dies, no client reaches any server. So run more than one LB.

Managed LBs do this for you. **Managed** means the cloud company runs and repairs it. An AWS Network Load Balancer gets one IP address in each **Availability Zone**. An Availability Zone is one separate data center building inside a region, with its own power and network. A fire in one does not reach the others.

The DNS name of that LB returns all of those addresses. So DNS picks the LB node, and the LB node picks the server. The two ideas work together. DNS is blind to health and load, but that is acceptable for choosing among a few LB nodes that the cloud company keeps healthy.

## Numbers

These are the AWS Application Load Balancer defaults. Other products use other values, but the shape is the same.

| Setting | Typical value |
|---|---|
| Time between health probes | 30 s |
| Probe timeout | 5 s |
| Failed probes to remove a server | 2 |
| Passed probes to restore a server | 5 |
| Time a dead server keeps getting traffic | about a minute |
| Network Load Balancer idle timeout for a TCP connection | 350 s |
| Cookie life for sticky sessions | 1 day |

**Capacity math.** Say N servers share load evenly. When one dies, each survivor must absorb a share of the dead server's work. Each survivor's load rises by a factor of N / (N - 1).

Example: three servers each run at 70% of capacity. When one dies, its work moves to two survivors. Each survivor now has more than it can carry. They are overloaded, so requests queue and they may fail too. The failure spreads.

So plan for **N+1**: enough servers to carry the whole load with one missing. The safe normal load is (N - 1) / N of capacity.

| Servers | Safe normal load |
|---|---|
| 3 | about 67% |
| 4 | 75% |
| 10 | 90% |

More servers means each one can run hotter, because one loss is a smaller share of the whole.

## Trade-offs

| Choice | You gain | You pay | Pick it when |
|---|---|---|---|
| Layer 4 LB | Speed, any TCP or UDP protocol, encrypted bytes pass through | No view of requests, balances per connection only | Databases, game servers, very high traffic |
| Layer 7 LB | Routing by path, retries, TLS handled at the LB, balancing per request | CPU for every request, one more place to parse and fail | Web and API traffic, HTTP/2 and gRPC |
| Round robin | Simplicity | Blind to load | Similar requests, similar servers |
| Least connections | Handles uneven request cost | Live counts, a flood onto a new server | Long or variable requests |
| Hash | Same client, same server | Hot keys, most clients move when the pool changes | A server keeps useful data per client |
| Sticky sessions | A quick fix for server memory | Uneven load, lost sessions when a server dies | A short bridge while you fix the state |

## In practice

<Callout type="tip">
Place the LB in your design on purpose. For example: "Clients resolve DNS to the LB. A layer 7 LB ends TLS, routes by path, and probes health every few seconds. Servers are stateless, so any server can take any request. We keep N+1 capacity." Naming the health check and N+1 shows that you have run a real service.
</Callout>

<Callout type="mistake">
Do not draw one box labeled "Load Balancer" and move on. Say what happens when a backend fails, and what happens when the LB itself fails. Also do not use sticky sessions to avoid fixing server state. That trades a design problem for an outage.
</Callout>
