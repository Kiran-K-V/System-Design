## The problem

One user request often touches many internal services. A page load might call a profile service, a feed service, an ads service and a billing service. Those calls happen inside your own data center, between code you control.

Three things hurt at this scale.

- **Bytes and parsing.** JSON is text. It repeats every field name in every message and the receiver must parse it. Small cost per call, large cost at thousands of calls per second.
- **No contract.** The caller reads documentation and hopes. When a team renames a field, the break shows up in production, not at compile time.
- **Connection waste.** Each call needs a connection, or a pool of them. HTTP/1.1 (lesson 2.3) allows one request at a time per connection.

You do not need browser-friendly, human-readable text between two of your own services. You need a contract, a small encoding, and cheap calls. That is **RPC**, a remote procedure call: a network call that looks like a function call, `GetUser(42)`.

## Naive solution: REST and JSON between services

REST with JSON is the default (lesson 3.1 covers it). It works. Debugging is easy because you can read the bytes. It fails in a specific way when it carries internal traffic.

Take one small message: a user with an id, a name and a flag. As compact JSON it is `{"id":150,"name":"Ada","active":true}`, which is **37 bytes** (count the characters, or use the widget below). The real data is 3 digits, 3 letters and the word `true`. Most of the 37 bytes are field names, quotes, colons and braces. They are sent again on every call.

The contract is also unwritten. Nothing stops a service from sending `"id"` as a string tomorrow. So the fix has two parts: a schema both sides share, and an encoding that does not repeat names.

## The mechanism

### Protocol Buffers: schema first, bytes second

**Protocol Buffers** (protobuf) is the schema language and encoding that gRPC uses. You write a `.proto` file. A compiler generates typed code for each language.

```proto
message User {
  int32  id     = 1;
  string name   = 2;
  bool   active = 3;
}
```

The numbers (`= 1`, `= 2`) are **field numbers**. They, not the names, go on the wire. Each field is written as a **tag** followed by a value. The tag packs the field number and a **wire type** (how to read the value): `(field_number << 3) | wire_type`. Wire type 0 means a variable-length integer. Wire type 2 means a length followed by bytes, used for strings.

An integer uses a **varint**: 7 bits of number per byte, and the top bit says "more bytes follow". Small numbers cost one byte. Step through how 150 becomes three bytes.

For our message, protobuf writes `08 96 01 12 03 41 64 61 18 01`. That is 3 + 5 + 2 = **10 bytes**, against 37 for JSON. The saving comes from dropping names. It shrinks when strings dominate: a 500 character text field costs about 500 bytes in both formats.

### A schema is a promise: evolve it with rules

Because only numbers are on the wire, the rules are about numbers. From the protobuf guide:

- Adding a field is safe. Old code ignores the field it does not know.
- A field number cannot change once the message is in use.
- Never reuse a number. If you delete a field, mark its number `reserved` so nobody picks it again.
- Numbers 1 to 15 take a one-byte tag. 16 to 2047 take two. Give the common fields small numbers.

Renaming a field is safe for the binary format, because the name is not on the wire. Changing its number or its type is not.

### gRPC: protobuf on HTTP/2

**gRPC** is an RPC framework. The service is declared in the same `.proto` file (`rpc GetUser (GetUserRequest) returns (User);`), and the compiler makes the client stub and the server skeleton. It sends calls over HTTP/2 (lesson 2.3): one TCP connection, many streams.

One call is a `POST` to a path like `/users.v1.Users/Get`. The body is **length-prefixed messages**: 1 byte that says whether the message is compressed, 4 bytes of length (big endian), then the protobuf bytes. That is 5 bytes of overhead per message. The result status travels in HTTP/2 **trailers**, headers sent after the body.

Because the status comes last, an HTTP status of 200 does not mean the call worked. Read `grpc-status`.

### Four kinds of call

A method can stream in either direction. Each message on a stream keeps its order within one call.

<GrpcModes />

Use streaming when the data is a sequence: a price feed, a large upload in chunks, or a long chat. Streams are a cheaper alternative to polling (lesson 2.5) between services. But a started stream is pinned to one backend. gRPC's performance guide says streams cannot be load balanced once they have started.

### Deadlines: every call needs a time limit

A gRPC call has **no deadline by default**. A client can wait "effectively forever". So always set one. If the deadline passes, the client fails the call with `DEADLINE_EXCEEDED`, and the server learns the call was cancelled.

A deadline travels downstream. Say a client gives a call 300 ms. Service A spends 100 ms and calls service B. A should pass the remaining time, 200 ms, not a fresh 300. gRPC sends the remaining time rather than a clock time, which avoids trouble from clocks that disagree. In Go and Java the deadline is propagated by default. Without this, the work of a call that already timed out keeps running deep in your system.

### The load balancing trap

Lesson 2.4 said a layer 4 balancer picks a server when a connection opens. gRPC opens one connection and keeps it. So one client lands on one backend for its whole life, and every call follows it.

<GrpcBalance client:visible />

The two fixes both balance **per call**. A layer 7 proxy reads the HTTP/2 streams and chooses a backend for each. The client-side option puts a picker in the client, which keeps a connection to every backend and uses a policy such as `round_robin`. The proxy costs a hop. Client-side balancing costs logic in every client.

One more limit. Each HTTP/2 connection has a cap on concurrent streams. When a channel reaches it, extra calls queue in the client. For heavy traffic, gRPC suggests a pool of channels.

### What about browsers?

A browser cannot speak gRPC directly. It does not give a page control of HTTP/2 frames and trailers. The usual answer is a translating layer (the gRPC-Web protocol, or a gateway) in front of your services. This is why public APIs stay REST or GraphQL, and gRPC stays inside.

## Numbers

| Item | Value | Source |
|---|---|---|
| Our example message in JSON | 37 bytes | counted from the text |
| Same message in protobuf | 10 bytes | computed from the encoding rules |
| Overhead per gRPC message | 5 bytes (1 flag + 4 length) | gRPC HTTP/2 spec |
| Tag size, field 1 to 15 / 16 to 2047 | 1 byte / 2 bytes | protobuf guide |
| Default deadline | none | gRPC guide |
| Varint size | 1 byte for 0 to 127, 2 bytes up to 16,383 | derived: 7 bits per byte |

At 50,000 calls per second, 37 bytes of payload is 1.85 MB per second, and 10 bytes is 0.5 MB per second (derived). The bytes matter less than you expect. The parse cost and the typed contract are the stronger argument. Measure your own services before you promise a speed-up.

## Trade-offs

| Choice | You gain | You pay | Pick it when |
|---|---|---|---|
| REST and JSON | Readable, any client, HTTP caches work | Bigger payloads, no enforced contract | Public APIs, browser clients |
| gRPC and protobuf | Typed contract, compact bytes, streaming, deadlines | Binary needs tooling, browsers need a gateway, needs L7 or client-side balancing | Internal service-to-service calls |
| Unary call | Simple, easy to retry and balance | One message each way | Most calls |
| Streaming call | No per-message request setup | Pinned to one backend, harder to retry and debug | Feeds, uploads, long sessions |

## Interview lens

<Callout type="tip">
Say where each style lives: "Public API is REST for caching and reach. Between our services we use gRPC: a typed contract in a shared proto repo, compact messages, and deadlines on every call. We put an L7 proxy or use client-side round robin, because L4 would pin each client to one pod." That one sentence covers the contract, the encoding and the trap.
</Callout>

<Callout type="mistake">
Do not say "gRPC is faster because it is binary". The honest claim is smaller messages and fewer connections, and you should measure. Do not forget the balancing problem: scaling out backends does nothing if the clients hold one connection to one backend. And never renumber or reuse a protobuf field number.
</Callout>

<Callout type="deep" title="Why the status is in the trailers">
A server can start a streaming response, send many messages, and only then find a problem. HTTP already sent status 200 with the first headers. Trailers let it add a final status after the body. This is also why gRPC needs a transport that supports trailers, and why some proxies must be configured to pass them.
</Callout>
