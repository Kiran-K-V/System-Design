## The problem

Your mobile team builds a profile screen. It shows the user's name and avatar, plus their last 3 posts. Each post shows its author's name and avatar.

With the REST design from lesson 3.1 the app needs five requests. It fetches the user, then the post list, then each author. The phone is on a mobile network with an ~80 ms round trip (assumption). Each step waits for the one before it.

The screen waits on several round trips in a row, and downloads far more data than it shows. The web team has a different screen that needs different fields. The iOS team wants a third shape.

One resource per URL cannot fit all three. What do you do?

## Naive fixes, and where they break

**Fix 1: fatter responses.** Add `?include=posts,posts.author` to `GET /users/7`. This works for one screen. Soon you have ten `include` options, nobody knows which are cheap, and each response still carries fields the client ignores.

**Fix 2: one endpoint per screen.** Build `GET /screens/profile`. It is fast, but now the backend team writes and ships an endpoint. The team does this every time a client team changes a layout. The API becomes a copy of the UI.

Both fixes show the real tension. Who decides the shape of the response: the server, or the client?

## Three answers

Watch the REST lane. Two words describe what went wrong.

- **Over-fetching**: the response has more data than the client needs.
- **Under-fetching**: one response does not hold enough, so the client must call again.

Together they cause the real cost: **sequential round trips**. Parallel calls help only when the client already knows what to ask for.

### GraphQL: the client picks the fields

**GraphQL** is a query language for APIs. The server publishes a **schema**: a typed description of every object and the fields it has. The client sends a **query** that names the fields it wants.

```graphql
query {
  user(id: 7) {
    name
    avatar
    posts(first: 3) {
      text
      author { name avatar }
    }
  }
}
```

The server returns JSON with exactly that shape. Key facts from graphql.org:

- **One endpoint**, usually `/graphql`. Queries go in a `POST` body (`GET` is allowed for queries only).
- **Three operation types**: `query` reads, `mutation` writes, `subscription` pushes live updates.
- **Strong types and introspection**: clients can ask the server what the schema is. That is called **introspection**. Tools can validate queries before they run.
- **Evolution without versions**: you add fields freely and mark old ones **deprecated**. Deprecated means "still works, but do not use it in new code". Old clients keep working while new clients move on.

The server works through each field with a **resolver**: a small function that loads the data for that field. Think of a waiter who fetches each dish on your order one at a time. That design hides a trap.

### The N+1 problem

Say the query asks for 20 posts with their authors. A naive resolver does this. ("Naive" means the first, simple version, written without thinking about cost.)

1. One query loads the 20 posts.
2. For each post, the `author` resolver runs its own query. That is 20 more.

That is **N+1 queries**: one for the list, N for the children. The server runs all those queries one after another. The fix is **batching**: gather many small lookups and send them as one. Think of one trip to the shop with a full list, not 20 trips for one item each. A tool such as DataLoader waits for a tiny moment (one "tick" of the program, well under a millisecond), collects all author ids requested in that time, and asks for them together. The database query for that is `WHERE id IN (...)`, which means "give me every row whose id is in this list". That is 2 queries in total, however long the list is.

GraphQL did not remove the fan-out. It moved it from the phone to your data center, where round trips cost microseconds instead of 80 ms. That is a good trade. It still needs care.

### RPC: call a procedure

**RPC** (remote procedure call) makes a network call look like a function call: `GetProfileScreen(7)`. The unit of design is the **action**, not the resource. In gRPC, which you met in lesson 2.6, services are defined in `.proto` files with Protocol Buffers. A **Protocol Buffer** (protobuf) is a compact binary message format with a fixed layout. Also, gRPC generates client and server code in many languages. It runs on HTTP/2.

RPC fits **service-to-service** calls. Both sides are your code. Types are generated, so mistakes show up at **compile time**: when you build the code, before it runs, not in production. Messages are binary and small, so calls are fast. The downsides are tight coupling (change a method and every caller must update) and weaker support in browsers.

## What GraphQL costs you

GraphQL is not free. Four costs come up again and again.

- **HTTP caching.** Every query goes to the same URL by `POST`. CDNs and browsers cannot cache by URL. You must cache at the field level, or use **persisted queries**. With those, the server keeps a list of approved queries. The client sends only a short id such as `q42`, so the request can be a `GET` with a cacheable URL.
- **Query cost.** A client can ask for a deeply nested query that loads millions of rows. For example: users, their posts, each post's comments, each comment's author, and so on. Limit query depth, give each field a cost score and reject queries over a budget, or allow only pre-approved queries.
- **Authorization per field.** In REST, you guard a route. In GraphQL, one query reaches many types. Each resolver must check access.
- **Errors.** A response can hold data and errors together. The GraphQL-over-HTTP rules say to answer `2xx` when `data` is present, because HTTP has no status for "partial success". Monitoring that counts only 4xx and 5xx will miss failures.

## Numbers

| Style | Round trips | Time at 80 ms RTT | Bytes (assumed) |
|---|---|---|---|
| REST, per-resource | 3 (5 requests) | ~240 ms | ~11 KB |
| GraphQL | 1 | ~85 ms | ~1.3 KB |
| RPC, per-screen method | 1 | ~85 ms | ~1.5 KB |

At high traffic, REST makes several times as many requests as GraphQL or RPC. Each request also pays for headers, auth checks and logging.

## Trade-offs

One row below needs a picture first. A **BFF** (backend for frontend) is a small server that sits between one kind of client, such as the iOS app, and your internal services. It calls them and shapes one response for that client. Each client team gets its own BFF, so no one waits on a shared API.

| Style | Gain | Pay | Choose it when |
|---|---|---|---|
| REST | Simple, cacheable by URL, works everywhere | Over-fetch, many round trips | Public APIs, simple resources, CDN-friendly reads |
| GraphQL | Client picks fields, one round trip, typed schema | N+1, hard HTTP caching, query cost, auth per field | Many clients with different data needs, nested data |
| RPC / gRPC | Fast, small, generated typed clients | Tight coupling, browser limits | Internal service-to-service calls |
| BFF (backend for frontend: a small server built for one client) | One tailored API per client, REST inside | Another service to build and run | A few clients, each needing very different shapes |

## In practice

<Callout type="tip">
Default to REST for the public API. Add "RPC between internal services" when you draw the service boxes. Bring up GraphQL only when you can name the reason. The reason is several client types with different data needs, or deeply nested reads. Then name its costs: N+1 and caching.
</Callout>

<Callout type="mistake">
Do not say "GraphQL is faster". One request is faster than five. But the query still runs. If the server does 21 database queries to answer it, the work moved. You pay for it in latency and load. State where the fan-out happens.
</Callout>

<Callout type="deep" title="Why not GraphQL everywhere?">
GraphQL puts a general query engine in front of your data. That gives clients power, and gives attackers power too. Most teams that adopt it also adopt a gateway (one front-door server that all calls pass through), query depth limits, persisted queries and per-field auth. If you have two clients and stable screens, REST plus a few purpose-built endpoints is simpler.
</Callout>
