## The problem

A customer taps "Pay $50". The app sends `POST /charges`. The server charges the card. Then the connection drops before the response arrives.

The app sees a timeout. Did the payment happen? It cannot know. The server did the work, and the network ate the answer.

The client has two bad choices.

- **Give up.** If the charge never ran, you lose the sale.
- **Retry.** If the charge did run, you charge the customer twice.

This is not rare. Say you process 1 million payments a day, and 0.1% end in an ambiguous timeout (assumption). That is ~1,000 uncertain payments a day. If clients retry blindly, up to ~1,000 customers per day get double charged: ~$50,000 of refunds and angry support tickets.

Retries also come from places you do not control. A mobile network that flaps (drops and returns again and again) can cause them. So can a gateway, which is a front-door server that passes calls on to your service. It may retry on `502`, the status code for "the server behind me failed". A message queue can cause them too. A queue is a waiting line that holds jobs between services, and it may deliver the same job again (the [Delivery Semantics](/learn/backend/06-async/delivery-semantics/) lesson). Your server must expect the same request twice.

## Naive solutions and where they fail

**"Check first."** Before retrying, the client does `GET /charges?customer=42&amount=50` to see if the charge exists. This fails. The client never got the charge id, so it must search by guess. (An id is the unique number the server gives to each new record.) A customer may really buy two $50 items in one minute. And between the check and the retry, the first request may still be running.

**"Make the server detect duplicates by content."** Reject a second $50 charge for the same customer within 5 minutes. This blocks real purchases and still lets slow retries through.

What is missing is a name for the operation. Both attempts must carry the same identifier, so the server can tell "retry" from "new purchase".

## What idempotent means

A quick recap from the [REST Resources](/learn/backend/03-api-design/rest/) lesson. An operation is **idempotent** if doing it many times has the same effect as doing it once. `PUT /users/42` with a full body is idempotent. `DELETE /tweets/981` is idempotent. `POST /charges` is not, because each call creates a new charge.

The goal of this lesson: make `POST` safe to retry, without changing what it means.

## The mechanism: an idempotency key

An **idempotency key** is a unique value the client makes for one logical operation. The client sends it with every attempt of that operation. The server uses it to remember the result.

Stripe's API works this way. The client sends an `Idempotency-Key` header. The server saves the status code and body of the first request for that key. It saves them "regardless of whether it succeeds or fails". Later requests with the same key get the same result back, even a `500`. Now the same failure with a key.

### The server side

The key store is where the guarantee lives. It is a table. Each row holds the key, the saved response, a status, and a **hash** of the request body. A hash is a short fingerprint made from data. The same body always gives the same hash, and a different body almost always gives a different one. The server compares hashes instead of whole bodies. Look at each case it must handle. The status codes `409` and `422` in the animation are explained in the rules below.

<KeyLifecycle client:visible />

The rules that make it correct:

1. **Claim atomically.** "If the key is absent, insert it" must be one **atomic** step: one step that no other request can interrupt, like a turnstile that lets one person through at a time. The step can be a unique constraint, which is a database rule that refuses a second row with the same value. Or it can be `SET key value NX` in Redis, a fast in-memory store used for small, quick lookups. NX means "only if not exists". A check followed by an insert has a **race**: two requests both see "absent" and both run, because each looks before the other has written.
2. **Store the fingerprint.** Save a hash of the request body. If the same key arrives with a different body, that is a client bug. Stripe's idempotency layer compares parameters and errors if they differ. The draft standard for an `Idempotency-Key` header (see Further reading) uses `422` for a mismatch. `422` is the HTTP status code that means "I understood the request, but I refuse its content".
3. **Handle in progress.** If the key exists but has no result yet, a second request must not run the work. Return `409 Conflict` (the draft's choice; `409` is the HTTP status code that means "this clashes with the current state") or wait for the first to finish.
4. **Save the response.** Replay the saved status and body. The client cannot tell it was a replay, which is the point.
5. **Expire keys.** Stripe may remove keys at least 24 hours old. A key store that grows forever is a leak.
6. **Scope keys.** Combine the key with the caller (customer or API key). Two customers must never collide on `abc123`.

### The client side

- Generate the key **once per operation**, before the first try. A random **UUID** works: a 128-bit random value written as 36 characters, such as `3f2b8c1e-...`. The chance that two clients pick the same one is tiny. Stripe suggests it and allows up to 255 characters.
- **Reuse** the same key for every retry of that operation. A new key per retry would break the whole scheme.
- Retry with **exponential backoff and jitter**. Backoff means each wait is longer than the last: 1 s, 2 s, 4 s and so on. Jitter means you add a random amount. Without jitter, thousands of clients that failed together would all retry in the same instant and hit the server together again (the [Timeouts, Retries, Backoff](/learn/backend/07-reliability/timeouts-retries/) lesson).

### Make the write and the key one transaction

There is a gap in the design. What if the server charges the card and crashes before it saves the result under the key? On retry the key says "in progress" forever.

Two ways to close it:

- **Same transaction.** Put the key row and the charge row in the same database, and write them in one **transaction**: a group of database changes that succeed or fail as one unit, like moving money between two accounts. They both commit (become permanent) or both roll back (are undone). Then "key done" and "charge exists" cannot disagree.
- **Pass the key downstream.** When your service calls an outside payment processor, forward an idempotency key to it too. Stripe's engineering post describes this style of safe retry with recovery points. If a request was rolled back, retrying it wholesale is safe. Otherwise, the server resumes from where it stopped.

A key stuck "in progress" also needs a **lease**: a timeout after which another worker may take it over. Think of a library book with a due date. If the first worker crashed, nobody would ever finish the job without a lease. A lease of, say, 30 seconds (assumption) lets a second worker take over once the first has clearly gone.

### Other ways to get idempotency

You do not always need a key store.

- **Client-chosen id with `PUT`.** `PUT /orders/{client_generated_id}`. The second `PUT` hits the same resource.
- **Unique business key.** A `UNIQUE (order_id)` constraint on the payments table makes the second insert fail. The server then returns the existing row.
- **Conditional writes.** Each record carries a version number. "Update where version = 7" fails on a replay, because the first run already moved the version to 8.

## Numbers

- **Storage.** Each key stores a hash and a saved response, so the store grows with the number of writes per lifetime. Expire old keys to keep it small.
- **Cost per request.** One extra read or write on the key store, a short hop inside the data center. It runs only on `POST`s, not on reads.
- **Retry window.** A typical client retries over seconds to minutes. The key lifetime (24 hours here) only needs to be longer than the longest retry plus any queue delay.

## Trade-offs

| Approach | Gain | Pay | Choose it when |
|---|---|---|---|
| Idempotency key + key store | Works for any `POST`, replays the exact response | An extra store, expiry, in-progress handling | Payments, orders, any create with side effects |
| Unique business key in the database | No extra store, strong guarantee | Only fits when a natural unique key exists | The operation has a real id, such as `order_id` |
| `PUT` with client-chosen id | Standard HTTP, no new header | The client must create ids | Creating resources the client names |
| No protection | Simple | Duplicates under retry | Pure reads, or operations where a duplicate is harmless |

## In practice

<Callout type="tip">
For any money or inventory write, say: "The client sends an idempotency key. The server does an atomic insert-if-absent on the key, runs the work, saves the response, and replays it for retries. Keys expire after 24 hours." Then name the two edge cases. They are: the same key with a different body, and a request that is still in progress.
</Callout>

<Callout type="mistake">
Do not say "the server checks if the charge already exists" with no key. There is nothing stable to check against. Also do not say idempotency keys give "exactly-once delivery". The network still delivers the request twice. The key makes the effect happen once.
</Callout>

<Callout type="deep" title="The same idea in queues">
A message queue that guarantees "at least once" delivery will deliver some messages twice. The consumer fixes this the same way: it records the message id in a dedupe table (a table of ids already handled, so a repeat is skipped). It does this inside the same transaction as its work. The [Delivery Semantics](/learn/backend/06-async/delivery-semantics/) lesson builds on this. Idempotency is the tool that turns at-least-once delivery into effectively-once processing.
</Callout>

## Further reading

- [Stripe API: Idempotent requests](https://docs.stripe.com/api/idempotent_requests): header, key length, saved results, 24-hour pruning and parameter checks.
- [Stripe blog: Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency): recovery points and backoff with jitter.
- [IETF draft: The Idempotency-Key HTTP Header Field](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/): a proposed standard header. The draft has expired, so treat it as a reference design.
- [RFC 9110, section 9.2.2: Idempotent Methods](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods): the HTTP definition.

You do not need to read these sources or the RFC number to follow the lesson. They are here for people who want the formal rules.
