## The problem

Your tweets table has 10 million rows. A client calls `GET /tweets`. If the server answers with everything, that is 10 million x ~300 bytes = ~3 GB in one response. The server runs out of memory and the phone never finishes the download.

So every list endpoint must return a bounded slice, and let the client ask for the next slice. This is **pagination**. The default page is small: 20 tweets is ~6 KB, one fast round trip.

The design question is how the client says "the next slice".

## Naive solution: offset and limit

The first idea is the one SQL gives you.

```sql
SELECT * FROM tweets ORDER BY created_at DESC LIMIT 20 OFFSET 40;
```

The API shape is `GET /tweets?offset=40&limit=20`. The client asks for page 3 by skipping 40 rows. It is simple, and it lets the user jump straight to page 7. GitHub's REST API uses this style (`page` and `per_page`, default 30, max 100 on most endpoints).

It has two flaws.

### Flaw 1: it is wrong when the list changes

A feed changes all the time. Offset is a **position**: "the 5th row from the top". Positions move when rows are added or removed. Watch what that does.

An insert above the reader pushes items down, so the next page repeats one. A delete above the reader pulls items up, so the next page skips one. The reader sees a duplicate or a gap, and the server returns `200` both times. Nothing signals the error.

### Flaw 2: it gets slower the deeper you go

The database cannot jump to row 1,000,000. PostgreSQL's documentation says it plainly: "The rows skipped by an OFFSET clause still have to be computed inside the server; therefore a large OFFSET might be inefficient."

So `OFFSET 1000000 LIMIT 20` reads and drops 1,000,000 rows to return 20. The cost grows in a straight line with the offset. If skipping a row costs ~1 µs (an assumption), page 1 costs ~20 µs and offset 1,000,000 costs ~1 s. A crawler that walks every page makes the total quadratic.

One more rule from the same docs: always use `ORDER BY` with a unique ordering. Without it, the database may return rows in a different order for each query.

## The mechanism: a cursor

A **cursor** marks where the last page ended. Instead of "skip 40", the client says "give me items after this one".

```sql
SELECT * FROM tweets
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

This is also called **keyset pagination**: you page by the values of the sort key.

Why it fixes both flaws:

- **Correct under writes.** The cursor is a value, not a position. Rows inserted above it or deleted above it do not change what "older than this item" means.
- **Fast at any depth.** With an index on `(created_at, id)`, the database seeks directly to the cursor in about log(n) steps, then reads 20 rows. An **index** is a sorted copy of some columns that the database uses to find rows without scanning (lesson 4.3). Page 1 and page 50,000 cost the same.

The response carries the next cursor:

```json
{
  "data": [ { "id": 981, "text": "..." } ],
  "next_cursor": "eyJ0IjoxNzAwMDAwMDAwLCJpZCI6OTgxfQ",
  "has_more": true
}
```

Rules for a good cursor:

1. **Make it opaque.** Encode the sort key (for example in base64) and tell clients not to parse it. Then you can change the internals later without breaking anyone. The GraphQL documentation recommends the same.
2. **Break ties.** Many tweets share one `created_at`. Sort by `(created_at, id)`. A non-unique key makes items vanish or repeat at page borders.
3. **Say when it ends.** Return `has_more` or an empty `next_cursor`. Slack warns against guessing the end by comparing the result size with the limit: the last full page would look like "more".
4. **Cap the limit.** Stripe takes 1 to 100 items per page, default 10. Slack recommends 100 to 200 and allows up to 1,000.

Try it. Change the list between pages and compare.

### What real APIs do

| API | Style | How the client continues |
|---|---|---|
| Stripe | Cursor on object ids | `starting_after=<id>` or `ending_before=<id>`, plus `has_more` |
| Slack | Opaque cursor | `cursor=<next_cursor>`; an empty `next_cursor` ends the list; cursors expire |
| GitHub REST | Page number | `page` and `per_page`, and a `Link` header with `next`, `prev`, `first`, `last` |
| GraphQL (Relay style) | Cursor connection | `first: 10, after: $cursor`; `pageInfo { endCursor hasNextPage }` |

## What a cursor cannot do

Cursors give up two things.

- **Jumping to page N.** A cursor only moves forward or back from a known item. A UI with page numbers ("1 2 3 ... 40") needs offset.
- **A cheap total count.** `COUNT(*)` on a big table is itself a scan. Return `has_more` instead of "page 3 of 500,000". If you need a number, an approximate count is usually enough.

Cursors also do not freeze the list. New rows above the cursor never show up in the current walk. That is usually what you want. If you need a consistent snapshot, such as for an export, fix a maximum id or timestamp at the start and add it to every query.

## Numbers

- **Response size.** 20 items x ~300 B = ~6 KB. 100 items = ~30 KB. Choose the page size to fit one fast round trip.
- **Offset cost.** Reads `offset + limit` rows. Page 50,000 at 20 per page is offset 1,000,000: ~1,000,020 rows read for 20 returned.
- **Cursor cost.** About log(n) index steps plus `limit` rows. For 10 million rows, a balanced tree with a few hundred keys per node is only 3 to 4 levels deep (assumption, see lesson 4.3).
- **Total cost of a full walk.** Offset sums to roughly n^2 / (2 x limit) row reads. Cursor reads n rows. For n = 1,000,000 and limit 20, that is ~25 billion against 1 million (derived).

## Trade-offs

| Choice | Gain | Pay | Choose it when |
|---|---|---|---|
| Offset | Simple, can jump to any page, easy total count | Duplicates and gaps under writes, slow when deep | Small, mostly static data; admin tables; search with page numbers |
| Cursor (keyset) | Stable, constant cost, scales | No page jump, needs a unique sort key and an index | Feeds, infinite scroll, exports, anything large or live |
| Cursor over many shards | Same client contract | Server must merge streams from each shard | Sharded stores (lesson 4.7) |

## In practice

<Callout type="tip">
Say it in one breath: "A list endpoint takes a `limit` and a `cursor`, and returns `next_cursor`. I use cursors because the feed changes while users read it, and offset would repeat or skip posts." Then add the tie-breaker: sort by `(created_at, id)`.
</Callout>

<Callout type="mistake">
Do not offer offset pagination for a large, live feed and then move on. Someone will ask "what happens if a new post arrives between page 1 and page 2?" Also do not forget the unique tie-breaker in the sort key.
</Callout>

<Callout type="deep" title="Offset over many shards is worse">
Say the data lives on S shards, and a client asks for offset 10,000 and limit 20 in the global order. No shard knows how many rows to skip. Each shard must return its top 10,020 rows. The coordinator merges S x 10,020 rows and throws almost all of them away. Cursors avoid this: each shard returns only the next 20 rows after the cursor, and the coordinator merges S x 20.
</Callout>
