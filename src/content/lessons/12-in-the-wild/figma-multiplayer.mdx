Two Figma posts matter here. "How Figma's multiplayer technology works" (2019) explains how edits sync. "Making multiplayer more reliable" (2022) explains how a file survives a server crash. We mark **what Figma says** and **our reading** apart.

## The problem

Many people edit one design file at once. Everyone must see the same result. Edits must feel instant. And a server crash must not eat work.

Those are two separate problems. The first is **convergence**: after the same set of edits, every client shows the same file. The second is **durability**: an edit the user saw on screen should still exist after a failure.

## Before: sync is solved, durability has a gap

**What Figma says (2019).** Clients are web pages that "talk with a cluster of servers over WebSockets" (lesson [2.5](/learn/02-networking/real-time-transport/)). The servers "spin up a separate process for each multiplayer document". The server is "the ultimate authority on what the document looks like", so clients never need timestamps to order events.

For conflicts Figma uses the simplest rule that works. If two clients change the same property of the same object, "the document will just end up with the last value that was sent to the server". Different properties never conflict. Figma says OT, operational transformation, was "unnecessarily complex for our problem space", and adds "Figma isn't using true CRDTs though". The server is a central point, which a true CRDT does not need.

**What Figma says (2022).** The live file sits in server memory. About "every 30 to 60 seconds" the server writes a checkpoint. The post says "we could lose up to 60 seconds of work on the server-side if multiplayer crashes." A redeploy had a second cost. When multiplayer is redeployed, all files held in memory are closed. Each needs a checkpoint, so "a checkpoint-centric system causes large spikes in checkpoint load". For the worst 5% of files, the post says a checkpoint can take about 4 seconds or more.

## After: add a journal

<FigmaCompare client:visible />

**What Figma says.** Each change gets a sequence number, "an incrementing integer associated with the file". Changes go to a journal, "a durable datastore that is asynchronously written to" in batches. The post contrasts the cadence: "every 0.5 seconds vs. every 60 seconds". Recovery loads the latest checkpoint, then queries for all entries newer than it and replays them.

To keep two servers from writing one file's journal, multiplayer writes a (lock UUID, file key) entry to take ownership of the file. On a deploy, connections close and the server waits for any unsaved changes to reach the journal. The post says the p99 of that wait is under 1 second.

Figma's stated goal was less than one second of data loss. It reports that 95% of edits get saved within 600 ms. Before rollout it ran about 400 thousand consecutive successful validations. The journal and checkpoints are "dual solutions": the journal holds small increments, and a checkpoint holds the whole file.

One cost the post names: cross-region copying of data. Figma wanted file data replicated across regions within 30 minutes. It estimated that DynamoDB global tables for this would raise the cost of the feature 6x. It did not pick that route.

<Callout type="deep" title="Our reading">
The journal is a write-ahead log (lesson [4.2](/learn/04-data/storage-engines/)) applied to a live document. The checkpoint bounds replay time, like a database snapshot.

Last writer wins is cheap because one server orders all edits. The price is that a simultaneous edit to one property silently loses one value. That is fine for a position. It would be a bad fit for merging two people's typing into one text value.

The post does not say whether a client waits for the journal write before showing an edit. We therefore cannot say that no acknowledged edit is ever lost. The post claims a goal of under one second, not zero.
</Callout>

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| One authoritative server per file | One order, no timestamps, simple rules | A central point per document |
| Property-level last writer wins | Few conflicts, easy to reason about | Same-property edits overwrite each other |
| Checkpoints only | Simple | Loss window as long as the checkpoint gap |
| Journal plus checkpoints | Loss window near the journal gap | Extra durable writes, a lock per file, more to operate |

## Interview takeaways

<Callout type="tip">
For a collaborative editor, say: "One authoritative server per document orders edits. Conflicts resolve per property. I add a write-ahead journal with per-file sequence numbers, so a crash replays from the last checkpoint." Then name the cost: same-property overwrites and a single owner per file.
</Callout>

<Callout type="mistake">
Do not say "Figma uses CRDTs" or "Figma uses OT". The post says it is not using true CRDTs and rejects OT. Do not say checkpoints alone make data safe. They leave a gap as wide as the gap between them.
</Callout>
