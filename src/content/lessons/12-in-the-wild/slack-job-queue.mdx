The source is Slack Engineering's "Scaling Slack's Job Queue". The page is dated December 6, 2017 and shows an update on June 25, 2020. The system it describes is from 2017. We keep **what Slack says** apart from **our reading**.

## The problem

Slack runs slow work off the web request. Examples are posting a message, sending push notifications, and billing. The post says that on its busiest days the system "processes over 1.4 billion jobs at a peak rate of 33,000 per second". Jobs run "from a few milliseconds to (in some cases) several minutes".

This is a queue (lesson [6.1](/learn/06-async/queues/)). A queue only protects you while the machine that holds it has room.

## Before: jobs in Redis memory

**What Slack says.** The web app picks one of the configured Redis hosts "based on a hash" of the job identifier and the logical queue. Workers poll Redis. A worker moves a job from the pending queue to an in-flight list and starts a task. Failed jobs go to a retry queue a set number of times. Jobs that never succeed go to a list of permanently failed jobs, which people inspect by hand (lesson [6.4](/learn/06-async/backpressure-dlq/)).

The outage began with database contention. Jobs ran slowly, so they piled up, "which caused Redis to reach its maximum configured memory limit". New jobs could not be enqueued. Then came the nasty part: "our system actually required a bit of free Redis memory in order to dequeue a job". The queue stayed locked after the database recovered.

The post lists more limits. Redis had little operational headroom, "particularly with respect to memory". Connections formed "a complete bipartite graph", since every client talks to every Redis host. Workers "couldn't scale independently of Redis". And "dequeuing a job requires work proportional to the length of the queue".

## After: Kafka in front of Redis

<SlackCompare client:visible />

**What Slack says.** Kafka sits ahead of Redis. Replacing Redis outright would have meant changes to scheduling, execution, and deduplication logic. So the team put Kafka in front, "leaving the existing application enqueue and dequeue interfaces in place".

Two stateless Go services connect the pieces.

- **Kafkagate** takes an HTTP POST with a topic, partition, and content, and writes to Kafka with the Sarama driver. It waits only for the partition leader: "we only wait for the leader to acknowledge the request, and not for replication". The post says this carries a small risk of losing a job if a broker dies first.
- **JQRelay** moves jobs from Kafka to Redis. At startup it tries to take a Consul lock on a key for the topic. The winner relays all partitions of that topic. It "only advances the offset if the job is successfully written to Redis". For a Redis outage it retries without end. For a job-specific error it re-enqueues the job to Kafka. Rate limits live in Consul.

When enqueues outpace dequeues, Kafka holds the backlog. Operators can lower JQRelay's rate limit or pause writes to Redis.

The cluster, per the post, runs Kafka 0.10.1.2 on 16 brokers on i3.2xlarge machines. Every topic has 32 partitions, replication factor 3, and 2 days of retention. The rollout canaries covered 50 Redis clusters and 1600 Kafka partitions (50 topics times 32 partitions).

<Callout type="deep" title="Our reading">
The core change is where a spike waits. In RAM it breaks the store. On disk in Kafka it is just a backlog (lesson [8.6](/learn/08-technologies/kafka/)).

Offsets move after the Redis write. A crash between the two replays a job. So delivery is at-least-once (lesson [6.3](/learn/06-async/delivery-semantics/)), and workers should tolerate a repeat (lesson [3.4](/learn/03-api-design/idempotency/)). The post does not say this. It is our inference from how offsets advance.

Waiting for only the leader favors enqueue availability over durability. The post makes that choice openly. We do not read it as a mistake.
</Callout>

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Kafka in front of Redis | Spikes land on disk, interfaces unchanged | Two more services and a Kafka cluster to run |
| Leader-only ack | Enqueue stays available | A small chance to lose a job if a broker dies first |
| One relay per topic via a lock | No duplicate relaying in normal operation | A failover gap, and a replayed job after a crash |
| Offset after the Redis write | No job skipped | A possible repeat |

## Interview takeaways

<Callout type="tip">
Say: "I would put a durable log in front of the memory-bound store so a spike becomes a backlog on disk. A relay drains it at a tunable rate and commits the offset only after the write succeeds. Workers are idempotent." Then state your ack choice and why.
</Callout>

<Callout type="mistake">
Do not say "Slack replaced Redis with Kafka". The post kept Redis. Do not say "always use acks=all". Slack chose leader-only acks on purpose, and said what it risks.
</Callout>
