## The problem

Your app shows a profile page. Each view reads one user row from a PostgreSQL database. PostgreSQL is a popular database that stores data in tables. Traffic grows to 30,000 reads per second.

One database node does about 10K–50K simple indexed reads per second (the [Numbers to Know](/learn/backend/01-one-machine/numbers-to-know/) lesson). An indexed read finds a row through a sorted lookup structure, so it does not scan the whole table. Each read takes 1–5 ms. At 30,000 reads per second you sit at the edge. The next marketing email pushes you over. Queries queue, latency climbs, and the page times out.

Look at what the database is doing. It reads the same few thousand popular rows again and again. It reads them from disk or its own memory, over the network, for every request. The data did not change between reads. The work is repeated for nothing.

## Naive solution: buy more database

You can add read replicas or shard the data. A **read replica** (the [Replication](/learn/backend/04-data/replication/) lesson) is a second database machine that keeps a copy of the data and answers reads. A **shard** (the [Sharding](/learn/backend/04-data/sharding/) lesson) is one machine that holds only a slice of the data, such as users A to M. Both work. Both cost money and add operational work. **Replication lag** is the delay before a replica sees a new write. A **routing layer** is the code that decides which machine gets each request. **Rebalancing** is moving data between machines when you add or remove one.

Worse, they scale the wrong thing. You pay for more capacity to answer the same question over and over. The question is not "how do I read more rows per second?" The question is "why am I reading the same row again?"

## The mechanism: keep a copy close

A **cache** is a small, fast store that keeps copies of data from a bigger, slower store. Think of a notepad on your desk where you jot the phone numbers you look up often, so you do not walk to the archive room each time. A cache usually lives in memory (RAM), which is far faster than disk. Redis and Memcached are two popular programs that act as a cache server. The big store is the **source of truth**. The cache can lose any entry at any time without losing data, because the truth lives elsewhere.

Four words you will use for the rest of this module:

- A **hit** is a read the cache answers.
- A **miss** is a read the cache cannot answer. The request goes to the source of truth.
- The **hit ratio** is hits divided by all reads.
- The **working set** is the data your traffic touches in a window of time. A cache works when the working set fits in it.

A **key** is the name you use to look up a value, such as `user:7`. The animation uses three commands. `GET` asks the cache for a key. `SET` writes a value into the cache. `SELECT` is the database command that reads rows. Step through one key. Watch the first read pay extra, and the second read pay almost nothing.

A miss costs more than having no cache. You asked the cache, then the database, then wrote back. The cache only pays off if later reads hit. So the real question is: will they?

## Why reads repeat: locality and skew

Two properties of real traffic make hits likely.

**Temporal locality.** Data used now is likely to be used again soon. A user who opens a page refreshes it. A viral post is read a million times in an hour.

**Skewed popularity.** A few keys get most of the reads. Think of products, celebrities, trending hashtags, or the config row every request reads. Statisticians model this with a **Zipf law**: the key at popularity rank *r* gets traffic proportional to 1/*r*^s. Rank 1 is the most popular key. The number *s* sets how steep the skew is: a bigger *s* means a few keys take even more of the traffic. For example, with *s* = 1 the 10th key gets one tenth of the traffic of the top key. Redis's own docs say the same in plain words. Access patterns usually follow a **power law** (a few huge values, a long tail of tiny ones), so an **LRU** cache is a good default. LRU means "least recently used": when the cache is full, it throws out the entry that nobody has read for the longest time (the [Eviction](/learn/backend/05-caching/eviction/) lesson covers this).

Skew is the reason a small cache works. Move the slider and watch how little memory buys a high hit ratio.

<ZipfCache client:visible />

The model uses a clean law. Real traffic is messier. Some workloads are skewed more, some less. The lesson holds: before you size a cache, find out how skewed your reads are. Log key access counts for a day.

## What the hit ratio buys

A hit is fast. A miss is slower than having no cache, because the read pays for the failed cache lookup first and then for the database read. Many people forget that first cost. So the average read time sits close to the hit time when most reads hit, and it climbs toward the miss time as more reads miss.

The calculator shows **p99 latency**. Sort every read by how long it took. The p99 is the time that 99 out of 100 reads beat. It shows the slow tail that the average hides. Now try the calculator. Pay close attention to the database reads and the p99 outputs. You do not need to compute anything. Watch how the outputs move.

<HitRatioCalc client:visible />

Three things to learn from it:

1. **Think in miss ratio, not hit ratio.** Going from 90% to 99% hits looks like a small gain. It cuts database load about 10 times. Each extra nine of hit ratio cuts the load by another large factor.
2. **Average latency flattens early.** After 90%, the average improves slowly. The database load keeps falling fast.
3. **The tail stays slow.** If more than 1% of reads miss, p99 latency is the miss latency. Caches fix the average and the load. They do not fix the tail unless the hit ratio is very high.

<Callout type="deep" title="The cold cache trap">
Say the cache absorbs almost all reads, so your database sees only a small fraction of the traffic. A small database handles that. Then the cache restarts. Its memory is empty. For the first minutes, every read misses, and the database sees the full traffic: many times its normal load. It falls over. When it falls over, the cache can never refill, and the outage does not end by itself. If the system cannot survive without the cache, the cache is not an optimization any more. It is a required component. You must treat it like one. Replicate it (run a second copy), warm it (fill it with popular keys before you send traffic), and limit how much load can reach the database. The [Invalidation and Stampede](/learn/backend/05-caching/invalidation-stampede/) lesson covers this.
</Callout>

## When a cache does not help

- **Uniform reads.** If every key is equally likely and the data set is bigger than the cache, the hit ratio is about the share of the data that fits in the cache. A cache that holds a tiny slice of uniform data gives a tiny hit ratio.
- **Write-heavy data.** If a value changes between every two reads, each cached copy is wrong before its second use.
- **Data that must be exactly fresh.** An account balance during a transfer, or inventory at checkout. A copy can be stale (out of date). The [Invalidation and Stampede](/learn/backend/05-caching/invalidation-stampede/) lesson shows how stale it can get.
- **Data that already fits in the database's memory.** The database already caches. PostgreSQL keeps recently used pages (fixed-size blocks of table data) in its **shared buffers**, a memory area of 128 MB by default. It also relies on the operating system's **page cache**, which is free memory the OS uses to hold recently read file data. Adding a Redis in front helps only if you avoid the query work or the network trip, not the disk read.

## The numbers

| Item | Value |
|---|---|
| Read from RAM | ~100 ns |
| Redis or Memcached GET, same data center | ~0.5 ms (the network trip dominates) |
| Cache node throughput | ~100K–1M simple ops/s. Redis's FAQ cites ~1M requests/s with **pipelining**, which means sending many commands at once without waiting for each reply. |
| Indexed database read | ~1–5 ms (the [Numbers to Know](/learn/backend/01-one-machine/numbers-to-know/) lesson) |
| Memory for 1M small string keys in Redis | ~85 MB (Redis FAQ) |
| 1 KB objects | 1M objects ≈ 1 GB. 1B objects ≈ 1 TB (the [Numbers to Know](/learn/backend/01-one-machine/numbers-to-know/) lesson) |

A cache hit is not "100 ns fast". The memory read is fast. The network trip to reach it is not. That is why caching *inside* the app process (the [Cache Placement](/learn/backend/05-caching/cache-placement/) lesson) is another 1000 times faster than Redis.

## Trade-offs

| Gain | You pay | Choose it when |
|---|---|---|
| Lower read latency (average) | Extra latency on every miss | Reads are skewed and repeat |
| Database load drops by the miss ratio | A new component to run, size, and monitor | The database is the bottleneck or the cost driver |
| Absorbs traffic spikes on hot data | Stale reads, because the copy can lag the truth | Slightly old data is acceptable |
| Cheaper than scaling the database | Cold-start risk: a lost cache returns full load to the database | You can warm the cache or shed load |

## In practice

<Callout type="tip">
Do not say "add a cache" and stop. Say what you cache, why it is cacheable, and how big it is. For example: "Reads are 100:1 over writes and the top 1% of products get most views. The hot set is ~10 GB, so it fits in one Redis node. I expect a very high hit ratio, which cuts database reads many times over." Then name the cost: staleness.
</Callout>

<Callout type="mistake">
Do not treat the cache as free speed. Every cache adds a second copy that can disagree with the first. Also do not size the database for the hit case only. State what happens on a cold start.
</Callout>
