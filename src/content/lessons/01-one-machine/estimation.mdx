## The problem

The interviewer says: "Design Twitter. 100 million daily users."

Is that a lot? Does it fit on one server? Do you need a cache? Shards? You cannot answer from the number of users. You must convert users into the units machines care about: **requests per second, bytes stored, and bytes per second.**

That conversion is back-of-envelope estimation.

## Why estimate at all

Estimation has one job: **decide the design.** Each number should answer a question:

| Number | Design question it answers |
|---|---|
| Peak write QPS | Can one database take the writes? Do we shard? |
| Peak read QPS | Do we need replicas, a cache, a CDN? |
| Read : write ratio | Optimize the read path or the write path? |
| Total storage | One machine, many machines, or object storage? |
| Bandwidth | Does this need a CDN? Will the NIC saturate? |

If a number does not change a decision, skip it. Many interviewers prefer that you estimate **when a decision needs it**, not all at the start.

## The shortcuts

Make the math easy. Precision does not matter. The order of magnitude does.

- **1 day ≈ 100,000 seconds** (really 86,400). So **1M per day ≈ 10 per second**.
- **1 year ≈ 400 days** for storage (really 365; rounding up is safe).
- **Powers of 1,000:** KB → MB → GB → TB → PB.
- **Peak factor:** 2–3x average for normal consumer apps. 10x+ for events (ticket sales, live sports).

| Per day | Per second (avg) |
|---|---|
| 1M | ~10 |
| 10M | ~100 |
| 100M | ~1,000 |
| 1B | ~10,000 |

## Capacity from Little's Law

You can turn throughput into machines with lesson 1.3:

```
servers ≈ peak QPS ÷ QPS per server at safe utilization
```

Example: 600K reads per second. One cache node does ~100K per second. At 60% target utilization, one node gives 60K. So you need about **10 cache nodes**, plus spares.

<Callout type="deep" title="Storage: count what you store, not what users send">
Add indexes (often 20–50% more), replication (usually ×3), and metadata. A 1 KB tweet becomes ~4–5 KB on disk across all copies and indexes. For media, store the file in object storage (Module 8) and keep only a URL in the database.
</Callout>

## Trade-offs

| Approach | Good | Bad |
|---|---|---|
| Estimate everything at the start | Shows rigor | Burns 5–10 minutes; some numbers never matter |
| Estimate when a decision needs it | Each number has a purpose | You must notice when a decision needs one |
| Skip estimation | Saves time | You cannot justify scale choices |

## Interview lens

<Callout type="tip">
Say the assumption, then the result, then the decision. "200M writes a day is about 2K per second, 6K at peak. One Postgres primary can take that. Reads are 100x, so the read path needs a cache." Three sentences, one design decision.
</Callout>

<Callout type="mistake">
Do not do long arithmetic out loud. Round hard. 86,400 becomes 100,000. 365 becomes 400. The interviewer is checking judgment, not multiplication.
</Callout>
