## The problem

In lesson 1.1 you saw one request. The network took 75% of the time. The RAM read was too small to see.

That was not luck. Latency is the time one operation takes. Across a computer system it spans from 1 nanosecond to hundreds of milliseconds. That is a factor of 100 million.

Humans cannot feel a factor of 100 million. So we make bad guesses. We optimize a loop that costs 2 µs and ignore a database call that costs 2 ms.

## Units first

| Unit | Symbol | In seconds | Example |
|---|---|---|---|
| nanosecond | ns | 0.000 000 001 | CPU cache read |
| microsecond | µs | 0.000 001 | SSD read |
| millisecond | ms | 0.001 | network round trip |

Each unit is 1,000 times the one before it.

## Climb the ladder

The trick: pretend 1 ns is 1 second. Then step up the ladder and watch how long you wait.

<LatencyLadder client:visible />

## Read the ladder in three groups

**Group 1: on the CPU (1–10 ns).** Caches on the chip. You never design around these in a system design interview.

**Group 2: on the machine (100 ns – 100 µs).** RAM, CPU work, SSD. RAM is 1,000x faster than SSD. This gap is the reason caches exist (Module 5).

**Group 3: between machines (500 µs – 150 ms).** Network round trips. Even inside one data center a round trip costs 5x an SSD read. Across an ocean it costs 1,500x.

<Callout type="deep" title="Why the ocean round trip cannot get faster">
Light in optical fiber moves at about 200,000 km per second. New York to London is about 5,600 km. One way takes at least 28 ms. A round trip takes at least 56 ms, before any routing or queues. Real numbers are 70–150 ms. No faster CPU or better code changes physics. Only moving the data closer to the user does.
</Callout>

## Three rules that come from the ladder

1. **Count network hops first.** Each service call or database query adds at least ~0.5 ms. Ten calls in a row add 5 ms before any work. Make calls in parallel, or remove them.
2. **Keep hot data in RAM.** A cache hit (in RAM) instead of a database read (disk plus network) is often 10–100x faster.
3. **Put data near users.** For global users, the speed of light is your largest cost. Use CDNs and regional copies.

## Bandwidth is a different number

Latency is how long one thing takes. **Bandwidth** is how many bytes per second a link moves. They are not the same.

| Path | Bandwidth (approx.) |
|---|---|
| RAM, sequential read | 10–50 GB/s |
| NVMe SSD, sequential read | 3–7 GB/s |
| 10 Gbps network card | 1.25 GB/s |
| HDD, sequential read | 100–200 MB/s |

A truck full of hard drives has huge bandwidth and terrible latency. A phone call has low latency and low bandwidth. In design questions, check both. Video streaming is a bandwidth problem. Chat is a latency problem.

## Trade-offs

| Where data lives | Read latency | Cost per GB | Survives crash |
|---|---|---|---|
| CPU cache | ~1 ns | Not for sale | No |
| RAM | ~100 ns | High | No |
| SSD | ~100 µs | Medium | Yes |
| HDD | ~10 ms | Low | Yes |
| Another region | ~100 ms | Depends | Yes |

## Interview lens

<Callout type="tip">
Use orders of magnitude, not exact numbers. "A cache hit is about 1 ms end to end. A database read is about 5–10 ms. So the cache cuts p50 latency by 5x." This shows judgment. Nobody checks the third digit.
</Callout>

<Callout type="mistake">
Do not say "RAM is fast, disk is slow" and stop. Say how much: **1,000x**. The size of the gap decides whether a cache is worth its cost and complexity.
</Callout>
