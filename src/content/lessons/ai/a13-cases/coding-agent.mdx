## The problem

The Claude Code docs say that across enterprise deployments the average cost is "around $13 per developer per active day and $150-250 per developer per month", and below $30 per active day for 90% of users ([Claude Code costs](https://code.claude.com/docs/en/costs)). The page gives no as-of date. People run coding agents all day, so the bill is a budget line.

The work looks like this. The SWE-bench benchmark takes 2,294 problems from real GitHub issues in 12 Python repositories. The model gets the issue text and the codebase, and must edit the code. A run counts as resolved only if the patch applies and the tests pass ([SWE-bench paper](https://arxiv.org/abs/2310.06770), 2024).

Three facts make this case different from the agents in earlier lessons.

1. **It writes to a real filesystem.** A wrong step does not return a bad answer. It changes files, runs code, and can touch things outside the project.
2. **It runs long.** Thirty or more model calls is normal. Every call re-sends the history, so cost and delay grow with each step.
3. **Tests grade it.** A test is cheap and fast, which makes it a strong reward. It is also a weak spot. A flaky test sends the agent the wrong way. A weak test lets a bad fix through.

The questions on the way: what is the bar, how do we keep the damage small, how does the agent find code with a small history, why are tests the reward and what goes wrong, how do we stop a loop that cannot succeed, and what does one task cost. Three short drills at the end reuse the ideas for code completion, a review bot, and a browser agent.

The loop is taught in lesson [The Agent Loop](/learn/ai/a6-agents/agent-loop/), and the box in lesson [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/). We build on them and do not repeat them.

## Requirements and the quality bar

The product is a background coding agent. A developer files an issue or a prompt. The agent works in its own copy of the repo and opens a pull request. All numbers in this section are **illustrative bars we chose**, unless a source is named.

**Functional**

- FR1: take a task and run it with nobody watching.
- FR2: search and read the repo.
- FR3: edit files.
- FR4: run tests and linters, and read the results.
- FR5: open a pull request with a summary.

**Out of scope.** Inline completion, review of other people's PRs, and browser tasks (all three are drills below). Also deploys to production and model training.

**Non-functional, and the bar.**

- **Task pass rate.** The share of tasks where the agent's patch passes the held-out tests in a clean checkout. Bar: at least 60% on one run, and at least 45% when 3 runs of the same task must all pass.
- **Containment.** Zero writes outside the repo clone. Zero secrets in traces. These are counted, not sampled.
- **Cost per task.** Median at most $1, p95 at most $5, and a hard stop at $10.
- **Wall-clock.** p50 at most 10 minutes, p95 at most 30, hard stop at 60.
- **Cap-ended runs.** At most 5% of runs end because a cap fired and not because the agent finished. This is a health metric. A rising share means a loop problem.

Why two pass numbers? One run per task hides the tasks that work only half the time. The support case, lesson [Customer Support Agent](/learn/ai/a13-cases/support-agent/), used pass^k for refunds. Here a miss costs less, so the bar is looser.

## Eval plan

Per the [AI Design Method](/learn/ai/a0-orientation/ai-design-method/) lesson, the eval comes before the design.

**Build the offline set from your own repo.** SWE-bench shows the recipe. Take merged pull requests that resolve an issue and change test files. Apply the PR's tests to the old code, and keep a task only if at least one test goes from fail to pass (the paper calls it a fail-to-pass test). The paper adds that a median of 51 other tests run to check that old behavior still works. So each task has two test sets: the new tests the fix must pass, and the old tests it must not break.

Each task is a commit, an issue text, and those hidden tests. Aim for 200 tasks, stratified by repo area and by files touched.

**Grade the end state in a clean checkout.** Take the agent's patch, drop any edits to test files, apply it to a fresh clone, and run the held-out tests. Why drop test edits? The agent can turn a red test green by changing the test. Counting that as a pass rewards cheating. Also record **forbidden actions**: any write outside the clone, any call to a host not on the allow list. One of them fails the run, whatever the tests say.

**Repeat each task, and use the right k.** Run every task 5 times. Two measures come from the same runs, as lesson [Agent Trajectory Evals](/learn/ai/a8-evals/trajectory-evals/) taught. **pass^k** is the chance that all k runs pass. **pass@k** is the chance that at least one passes. A coding agent has a twist. A harness can run k attempts and keep one that passes the visible tests. Then pass@k, measured with hidden tests, is the number that matters, at k times the cost.

Here is a worked example with an **illustrative** mix of 100 tasks: 60 easy ones that pass 95% of runs, 25 flaky ones at 50%, and 15 hard ones at 5%.

| Measure | How it is computed | Result |
|---|---|---|
| pass^1 | (60 x 0.95 + 25 x 0.5 + 15 x 0.05) / 100 | 70.3% |
| pass^5 | (60 x 0.95^5 + 25 x 0.5^5 + 15 x 0.05^5) / 100 | 47.2% |
| pass@5 | (60 x (1 - 0.05^5) + 25 x (1 - 0.5^5) + 15 x (1 - 0.95^5)) / 100 | 87.6% |
| Naive guess for pass^5 | 0.703^5, as if every task were alike | 17.1% |

One agent, three honest numbers: 70% on one try, 47% if all 5 tries must pass, and 88% if any of 5 will do. The 25 flaky tasks are where reading traces pays most.

**Online signals.** PR merge rate, revert rate within 14 days, human edits before merge, cost per merged PR, and the share of runs ended by a cap. The slice that matters: tasks that touch more than 3 files, and repos with flaky suites.

**Regression gate.** Every change to the prompt, a tool description, a tool output limit, or the model runs the suite 3 times first. The incident drill shows why the output limit is on that list. Lessons [Golden Sets](/learn/ai/a8-evals/golden-sets/) and [Shadow, Canary, and Rollback](/learn/ai/a8-evals/rollout/) cover the set and the rollout.

## Budgets

**Wall-clock per task.** Our assumptions, for a task with 30 model calls and 4 test runs:

| Stage | Time (assumed) |
|---|---|
| Start the sandbox and clone the repo | 30 s |
| 30 model calls at 10 s each | 300 s |
| 30 tool actions (search, edit, install) at 1 s | 30 s |
| 4 test runs at 90 s each | 360 s |
| **Total** | **720 s, 12 minutes** |

Test runs take as long as the model does. So run only the affected tests inside the loop, cache dependencies, and run the full suite once, at the end.

**Dollars per task.** Prices are Anthropic list prices in USD per million tokens, as of 2026-10-20, from the [pricing page](https://platform.claude.com/docs/en/about-claude/pricing). The page shows no date of its own, so 2026-10-20 is the day I read it.

| Model | Input | 5 minute cache write | Cache read | Output |
|---|---|---|---|---|
| Claude Sonnet 5.5 | $2 | $2.50 | $0.10 | $10 |
| Claude Opus 5.5 | $4 | $5 | $0.20 | $20 |
| Claude Haiku 5.5 (prompt up to 100,000 tokens) | $0.10 | $0.125 | $0.01 | $0.50 |

Now the worked example. Assumptions (illustrative): the first call sends 20,000 tokens (system prompt, tool list, repo notes, task). Each later call adds 2,500 tokens (the last answer plus a tool result) and writes 600. There are 30 calls. Every call lands inside the 5 minute cache lifetime, so the cache stays warm. The Claude Code docs say that on an API key the lifetime is five minutes by default.

On call k the history is C(k) tokens, with C(1) = 20,000 and C(k) = C(k-1) + 2,500. Each call reads the old history from the cache, writes the new tokens, and writes the answer:

<Math block tex="\text{cost}_k = C_{k-1} \, p_{\text{read}} + \Delta_k \, p_{\text{write}} + 600 \, p_{\text{out}}" />

Add it up. The sum of C(k) over 30 calls is 30 x 20,000 + 2,500 x (0 + 1 + ... + 29) = 600,000 + 1,087,500 = 1,687,500 tokens. That is the input the model processes in total.

- Cache reads: 1,595,000 tokens x $0.10 / 1,000,000 = $0.160.
- Cache writes: 92,500 tokens x $2.50 / 1,000,000 = $0.231.
- Output: 18,000 tokens x $10 / 1,000,000 = $0.180.
- **Total on Sonnet 5.5, warm cache: $0.57.**

With no cache, all 1,687,500 tokens cost $2 each per million, which is $3.38, plus $0.18 output: **$3.56**. The cache cuts the bill 6 times. On Opus 5.5 every line doubles, so the warm-cache task costs **$1.14**. On Haiku 5.5, the history never passes 100,000 tokens, so the low tier applies, and the task costs **$0.04**.

At a 60% pass rate, the cost per resolved task is $0.57 / 0.6 = $0.95. A check against the docs: $13 a day divided by $0.57 is about 23 tasks of this small size. The docs average covers bigger contexts, Opus, and interactive sessions, so use it only as an order-of-magnitude check.

## Core entities and API

**Entities.** `Task` (repo, base commit, prompt, budget), `Run` (model, prompt version, state, stop reason), `Step` (tool call, result size, tokens, cost), `Sandbox` (policy version), `Artifact` (branch, PR URL).

**API.** `POST /tasks` returns a run id at once. `GET /runs/{id}/events` streams steps. `POST /runs/{id}/cancel` is the kill switch for one run. `POST /runs/{id}/approve` lets a person approve a held action. Lesson [Background Agents and Queues](/learn/ai/a7-agents-prod/background-agents-queues/) covers the submit, queue, run, notify shape. The new part is what runs inside.

## A naive design and where it breaks

The first build is a script. It runs the model in a loop on a developer machine or a CI runner, with the developer's shell, the developer's keys, and no limits. Here is where it breaks. Numbers are illustrative unless a source is named.

| Break | What happens | Number |
|---|---|---|
| Ambient access | The agent can read `~/.aws` and write `~/.bashrc`, because it runs as the developer. | Replit, July 2025 (secondary): an agent reportedly ignored an instruction not to change things and deleted a live production database. |
| No loop limit | A test can never pass, and the agent keeps trying. | 300 calls cost $15.45 on a warm cache, $238 on a cold one. A fixable run costs $0.24. |
| Whole repo in the prompt | The code does not fit, and every call re-sends it. | 100,000 lines at about 10 tokens a line is 1 million tokens, per call. |
| Flaky red | A test fails for no reason, and the agent edits good code. | 300 tests, each 0.2% flaky: 45% of full runs show a false red. |
| Long chain | Each step is 98% reliable. | 0.98^30 = 54.5% of 30-step tasks end with no error. |
| Secrets in the environment | A command such as `env` prints keys into the history and the trace store. | One log line can sit in the trace store for its whole retention period. |

The common cause is the same as in the support case. The model is the only guard. The rest of the lesson moves each control out of the model and into code.

Four rules sit behind the picture.

1. **The model proposes. The tool runner decides.** Every file and shell action passes one runner that checks it against the sandbox policy.
2. **The sandbox is one box per run.** One clone, one set of limits, thrown away after the run. State from one run cannot leak into the next.
3. **The guard is outside the loop.** Counting calls, dollars, and repeats is not a job for the model that is looping.
4. **The output is a pull request.** The agent never pushes to the main branch. A person merges.

## Deep dive 1: three boundaries for a box that runs code

**What it is.** The box from lesson [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) is the container. Its **policy** says what is allowed inside. For a coding agent the policy has three parts: files, network, and secrets. Anthropic's sandboxing post says "effective sandboxing requires both" file and network isolation ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Without network isolation, a compromised agent could leak files such as SSH keys. Without file isolation, it could escape and reach the network.

**Picture.** A contractor in a client's building. The contractor may work in one room (files), may call only numbers on an approved list (network), and is never handed the master key (secrets).

| Boundary | Policy | Enforced by | What the agent sees on a violation |
|---|---|---|---|
| Files | Read and write only in the clone and a temp folder. Deny reads of `~/.ssh` and `~/.aws`. Writes to `.git/hooks` and CI config need review. | The sandbox mounts, not the prompt. | An error result that names the rule. |
| Network | No direct route out. A proxy outside the sandbox checks each host against an allow list: the package mirror and the git proxy. | A proxy and firewall rules. | An error result: host not allowed. |
| Secrets | No cloud keys or SSH keys inside. Git pushes go through a proxy that adds the real token. Test databases hold fake data. | Credentials never enter the box. | Nothing to see. The key does not exist. |

Anthropic describes the third row for Claude Code on the web. The design is meant "to ensure that sensitive credentials (such as git credentials or signing keys) are never inside the sandbox". The sandboxed git client holds a scoped credential. The proxy checks the request (for example, that a push targets the configured branch), then adds the real token.

**Why a block is an error result and not a person.** Anthropic reports that in its own internal use, sandboxing "safely reduces permission prompts by 84%". This is a **company claim**, with no sample size or baseline. The idea is sound: in a small box, most actions need no question. If a developer saw 25 prompts a day, 84% fewer is 4 (illustrative arithmetic). Our reading: a blocked call should return a normal tool error, so the agent can adapt in the same loop. Watch it happen.

The run is **illustrative**: two blocks, no damage, no person woken.

**Two extra rules.**

- **A leaked secret in a log.** Plant a **canary**: a fake secret with a unique string in the sandbox environment. Scan every tool output and trace for the string. If it appears, something printed the environment. Kill the run and alert. Also run a redaction pass for key-shaped strings before any output enters the history, because the history goes to the model provider and to your trace store.
- **Task text is untrusted when it comes from an issue.** An attacker can file an issue. Lesson [Tool Permissions and Least Privilege](/learn/ai/a10-safety/tool-permissions/) covers the check-in-code idea. The review drill below has a real case.

**The prompt is not the control.** In July 2025, press and the OECD incident monitor reported that an agent used by the founder of SaaStr ignored an instruction not to change things and deleted a live production database ([OECD summary](https://oecd.ai/en/incidents/2025-07-19-1eb1), secondary). Accounts differ on details, and I could not load a primary post, so I give no counts. Our reading: an instruction in a prompt is a request. A credential that cannot reach production is a rule.

## Deep dive 2: context economics

**How does the agent find code?** Two ways. In **agentic search** the model runs the search itself, with `grep`, `glob`, and file reads, the way a developer would. An **index** is built ahead of time: files are cut into chunks, each chunk becomes an embedding, and a query returns the nearest chunks (lessons in the RAG module cover this).

Anthropic's agent SDK post says: "Semantic search is usually faster than agentic search, but less accurate, more difficult to maintain, and less transparent." It suggests starting with agentic search and adding an index only if you need speed or more query variety ([Anthropic](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)).

Our reading of why this fits a coding agent: the agent is changing the repo while it searches. An index built an hour ago is stale after the first edit. `grep` reads the live disk.

**What the Cursor numbers measure.** Cursor builds an index and syncs it with a **Merkle tree**, a hash tree. Each file gets a hash, and each folder hash comes from its children. Only entries whose hashes differ are synced. Lesson [Freshness and Updates](/learn/ai/a5-rag/freshness-updates/) taught the idea. Take a worked example (illustrative): 10,000 files, 10 children per folder, 4 levels. To find one changed file, compare the root (1 hash), then the 10 children on the path at each of 4 levels: 1 + 10 x 4 = 41 comparisons, not 10,000. Cursor's post gives two numbers ([Cursor](https://cursor.com/blog/secure-codebase-indexing)), both **company claims**:

- Semantic search "improved response accuracy by 12.5% on average" in Cursor's own evaluation, linked from the post. The post does not say how the evaluation works.
- "For the median repo, time-to-first-query drops from 7.87 seconds to 525 milliseconds." This compares building an index from scratch with reusing a teammate's index. It is a start-up time. It is not search latency, and it is not for every repo.

Neither number says an index beats grep for every query. The post gives no sync interval.

**Why history size matters.** Each call re-reads the history, so one call costs more as the history grows. With our Sonnet 5.5 warm-cache numbers, a call that adds 2,500 tokens and writes 600 costs $0.0123 plus the read of the history at $0.10 per million:

| History size | Cost of one call |
|---|---|
| 40,000 tokens | $0.016 |
| 200,000 tokens | $0.032 |
| 500,000 tokens | $0.062 |

Delay grows too. Lesson [Compaction](/learn/ai/a4-context/compaction/) covers the quality side.

**Compaction thresholds.** To **compact** is to replace old history with a summary. By our growth numbers a 200,000-token window fills at call 73: (200,000 - 20,000) / 2,500 + 1. The Claude Code docs say that by default it compacts when the conversation reaches the model's limit. For models with a native 1 million token window that is "about 967K tokens". You can set the window anywhere from 100K to 1M ([Claude Code model config](https://code.claude.com/docs/en/model-config#set-the-auto-compact-window)). The docs also warn that compacting a large context is itself a large request.

Here is the arithmetic (illustrative). Compact at 200,000 tokens. Read 200,000 tokens from the cache: $0.020. Write a 3,000 token summary: $0.030. Re-write a 23,000 token new prefix (20,000 fixed plus the summary): $0.0575. Total $0.1075. After that, each call costs $0.0146, not $0.0323: a saving of $0.0177 a call. The compaction pays for itself in 0.1075 / 0.0177 = 6 calls. Our reading: for a cost-bound agent, compact well below the maximum window.

**Subagents isolate. They do not save.** Lesson [Subagents](/learn/ai/a6-agents/subagents/) taught the mechanics. A search that reads 60,000 tokens in the main window rides along for the next 40 calls: a cache write of $0.15 plus reads of 60,000 x $0.10 / 1,000,000 x 40 = $0.24, about $0.39, and 60,000 tokens of window. A subagent returns perhaps 1,500 tokens, but its own calls still cost money: the Claude Code docs say "the subagent's own requests still draw on your usage". The gain is a clean window and better answers.

**Coupled coding tasks and many agents.** Anthropic's multi-agent write-up says "most coding tasks involve fewer truly parallelizable tasks than research" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). It calls domains where agents "share the same context or involve many dependencies between agents" a poor fit, and says multi-agent systems use about 15 times more tokens than chats, against 4 times for one agent. The Claude Code docs put agent teams at "approximately 7x more tokens than standard sessions" in plan mode. Our reading: use subagents for read-only fan-out, such as searching or summarizing a test run. Never run two agents that edit the same files.

## Deep dive 3: tests as the reward, and loops that must stop

**Why tests?** Anthropic's agent SDK post says "The best form of feedback is providing clearly defined rules for an output, then explaining which rules failed and why." It names linting as one example. A test is the same shape: a rule, a pass or fail, and a message. Lesson [Loop Patterns](/learn/ai/a6-agents/loop-patterns/) showed that a code check beats the model's opinion of its own work. SWE-bench grades the same way: apply the patch, run the tests.

**Weak spot 1: tests can be flaky.** A **flaky test** passes and fails on the same code. Google's testing blog gives numbers ([Flaky Tests at Google](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html), 2016): about 1.5% of all test runs report a flaky result, almost 16% of tests have some flakiness, and about 84% of the pass-to-fail transitions in post-submit testing involve a flaky test. A project averages about 1,000 tests, so at 1.5% about 15 tests fail on a full run. Google mitigates with re-runs of failing tests, a flaky mark that fails a test only when it fails 3 times in a row, and quarantine of tests that are too flaky.

For an agent the damage is direct. A red result means "your change is wrong", so the model edits good code. Our arithmetic: 300 tests, each failing by chance on 0.2% of runs. The chance of at least one false red in a full run is 1 - 0.998^300 = 45%. The fix belongs in the harness, not the model loop. Re-run a failing test twice, in the sandbox, at no token cost. Report "flaky, passed on re-run" if any re-run passes. Only a test that fails 3 times of 3 reaches the model. A real flake at 0.2% fails 3 times in a row with chance 0.002^3, about 8 in a billion. Keep a quarantine list, and log every flake.

**Weak spot 2: tests can be weak.** An agent can pass visible tests by editing them or by special-casing the input. Our rules: the held-out grader drops test-file edits, and the PR flags any edit to an existing test for the reviewer.

**Runaway loops.** A stuck loop spends money on every turn. Lesson [Loop Control](/learn/ai/a7-agents-prod/loop-control/) gave the stop conditions and the stuck detector. Here are the coding versions.

- **Retry cap.** Stop after N fix attempts for one task. Choose N from real traces. It must be above the attempts that healthy runs need.
- **No-progress detector.** Hash a failure signature: the failing test names, the normalized assertion text, and a hash of the diff. If the same signature repeats 3 times in a row, stop. A healthy retry changes the signature. A stuck loop does not.
- **Kill switch.** Three layers. A cancel flag the loop checks between tool calls. A hard stop that destroys the sandbox and revokes its tokens. A global switch that stops new runs. The model cannot reach any of the three.

A dollar cap alone is late: it is checked after a response arrives, so spend can pass it by one response.

**The infinite fix loop, in numbers.** The task is stuck: a test that cannot pass. The model is Sonnet 5.5 with a warm cache, and the history starts at 20,000 tokens and grows 2,500 per call.

Results from the same model:

| Controls | Calls | Cost, warm cache | Cost, cold cache |
|---|---|---|---|
| A fixable run, for comparison | 13 | $0.24 | $0.99 |
| Turn cap 300 only | 300 | $15.45 | $238 |
| Retry cap 10 | 26 | $0.49 | $2.82 |
| Same failure 3 times | 12 | $0.23 | $0.88 |

A stuck run is about 63 times the cost of a healthy one ($15.45 / $0.24). The cost is not linear. Starting after call 12, the next 50 calls cost $1.16, and the next 200 cost $8.38. Four times the calls is 7.2 times the cost, because every call re-reads a longer history. This estimate ignores compaction, so a real tool costs less on very long runs. The cheapest stop is still the early one.

## Failure modes and an incident drill

| Failure | What happens | Detect | Do |
|---|---|---|---|
| Write outside the repo | The agent edits a global file or a sibling project. | Boundary denial log, by path | Deny, return an error, stop the run after 10 denials |
| Infinite fix loop | Calls and spend rise with no new signature. | Same-failure counter, calls per run | Retry cap, no-progress stop, dollar cap |
| Leaked secret | A command prints the environment into the history. | Canary string in output or traces | Kill the run, rotate the secret, redact before the model sees it |
| Flaky test misleads | The agent edits correct code. | Disagreement between re-runs | Re-run in the harness, quarantine, report "flaky" |
| Truncated tool output | The failing line is cut off, and the agent guesses. | Tool-result size and cut rate | Keep the head and the tail, and put failures first |
| Injected issue or README | Text from outside steers the agent. | Forbidden-action rate on an attack suite | No secrets, allow-listed network, a person merges |

The saving was an illusion. Cost per run rose 9% even though each tool result got smaller, because runs were longer. Cost per resolved task is cost divided by pass rate, so it rose from 1.61 to 2.14 in relative units, about 33% worse, with 11 points of pass rate lost. A tool output limit is a model input, so it goes through the same gate as a prompt.

## Drill: Code completion

**The task.** Show gray "ghost text" as a developer types, and accept it with Tab (Copilot, Cursor Tab). Take 15 minutes.

**Bar.** Acceptance rate (accepted divided by shown) and retention (the share of accepted characters still in the file a few minutes later, our definition). Both must rise. An accepted and then deleted completion is noise. The latency bar comes from typing speed. At 60 words a minute and 5 characters a word (the usual convention), a key arrives every 200 ms. At 100 words a minute it is 120 ms, at 40 it is 300 ms. Ghost text is stale once the next key disagrees with it. Our bar: p50 under 300 ms from keystroke to ghost text, p95 under 600 ms.

**Design.** GitHub's post on Copilot ([GitHub, 2023](https://github.blog/ai-and-ml/github-copilot/how-github-copilot-is-getting-better-at-understanding-your-code/)) gives the shape.

- The prompt holds the code before the cursor (the **prefix**) and after it (the **suffix**). **Fill-in-the-middle** lets the model see the suffix. In an A/B test it gave "a 10% relative boost in performance, meaning developers accepted 10% more of the completions that were shown to them". Relative means 10% of the old rate, not 10 points.
- **Neighboring tabs** add snippets from other open files. The post says they "relatively increase user acceptance" by 5%.
- "Transformers that are fast enough to power GitHub Copilot can process about 6,000 characters at a time." That is the context budget. Packing means ranking what fits: code near the cursor, the suffix, the path and imports, then neighbor snippets by similarity.
- The prompt passes "through a contextual filter model and a GPT model" (the post's diagram caption). The post gives no filter detail and no latency number. It says the two features add no latency.

**Latency budget.** Our assumptions:

| Stage | Time (assumed) |
|---|---|
| Wait for a typing pause (debounce) | 40 ms |
| Build the prompt from cached context | 20 ms |
| Network round trip | 40 ms |
| Gateway, auth, routing | 10 ms |
| Model: queue and first token | 120 ms |
| Model: 12 tokens at 8 ms each | 96 ms |
| Filter and draw the text | 20 ms |
| **Total** | **346 ms** |

That is 46 ms over the p50 bar. Two fixes follow.

1. **Cancel, debounce, cache.** To **debounce** is to wait for a short pause before sending. When the next key arrives, cancel the old request. If the key matches the next character of the ghost text, trim the text on the client and send nothing. Cache by prefix.
2. **Cut decode time.** Show a short first chunk and stream the rest. Speculative decoding helps (elective [Speculative Decoding](/learn/ai/e3-inference-deep/speculative-decoding/) teaches it): a cheap guess at the next tokens, checked by the big model in one pass. Cursor uses the idea to apply an edit, with the old file as the guess. Their post claims "~1000 tokens (around 3500 char/s) on our 70b model", and speculative edits "up to 9x faster" than their previous GPT-4 speculative edits deployment ([Cursor](https://cursor.com/blog/instant-apply), company claim). That is applying an edit to a file, not tab completion.

**Failure: acceptance drops after a model upgrade.** Offline tests say the new model is better. Illustrative cause: it raises p95 latency from 350 ms to 600 ms, so more completions land after the next key and are cancelled. Shown rate falls from 40% of triggers to 28%, and accepted-per-shown stays at 25%. Accepted per trigger falls from 10% to 7%. Split the metric into shown rate, accept rate when shown, retention, and latency percentiles. Canary the model and gate on accepted per trigger, not on offline pass rate.

**Variant: Smart Compose and search autocomplete.** Every user types for hours a day and triggers many suggestions a minute, and many type at the same time. Request volume is orders of magnitude above chat. That calls for a small model, prefix caches, and heavy debounce.

## Drill: Code review bot

**The task.** A pull request opens. The bot posts comments on likely bugs. Take 10 minutes.

**Bar.** Two numbers. **Precision**: the share of posted comments that a maintainer marks valid. **Recall on seeded bugs**: the share of planted bugs the bot finds, on a set where you inserted known bugs into real PRs (lesson [Golden Sets](/learn/ai/a8-evals/golden-sets/) covers synthetic cases). Also a cap on comments per PR, 5 in our design, because a noisy bot gets muted. Acceptance rate is the online signal.

**Design.**

1. A PR webhook starts a background job (lesson [Background Agents and Queues](/learn/ai/a7-agents-prod/background-agents-queues/)).
2. The reviewer reads the diff and gathers context by agentic search: who calls this function, what the tests expect. Linters and tests run as tool results.
3. The model proposes **findings**. Each has a file, a line, a claim, and evidence quoted from the code.
4. A **verifier pass** checks each finding on its own: does the quoted evidence exist, and does the claim follow? A cheap model can do it.
5. Dedupe, rank by severity and confidence, keep the top 5, and post one review.

**Permissions.** Read-only on code. The only write is a comment. Repo content is untrusted. In May 2025 Invariant Labs showed an attack on an agent that used the GitHub MCP server. An attacker files a malicious issue in a public repo. When the user asks the agent about that repo, it follows the issue text and writes private repo data into a pull request on the public repo ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). The authors say "this is not a flaw in the GitHub MCP server code itself", and suggest least privilege, such as one repository per session. Our reading: PR text, code comments, and README files are attacker input, mainly on forks. Scope the token to one repo and give the bot no tool that sends data out. Lesson [Prompt Injection](/learn/ai/a10-safety/prompt-injection/) covers the pattern.

**Why the verifier exists.** Say the reviewer proposes 10 findings and only a few are real bugs, so precision is low. The verifier keeps most real findings and drops most false ones. Precision rises a lot and recall barely falls. Each check is a small call, so it costs little.

**Failure: acceptance halves after a prompt change.** A prompt that asks for "thorough" review raises the comment count, and the share marked valid falls. Detect it with the seeded set on every prompt change and a weekly valid-comment rate. Start in shadow mode, as in lesson [Shadow, Canary, and Rollback](/learn/ai/a8-evals/rollout/).

Cost per review is small. The reviewer makes a few calls, and each call re-reads the growing history, mostly from a warm cache. The verifier runs on a cheaper model, one short call per finding, so it adds only a small share to the bill. The main lever is how many calls the reviewer makes.

## Drill: Browser and computer-use agent

**The task.** Finish a task in a web app that has no API, for example filing a request in a vendor portal. Take 10 minutes.

**Bar.** Task success on a suite, checked by the **end state** (is the request in the portal?), not by what the agent says. Each task repeats k times, and we report pass^k. Zero unapproved irreversible actions, such as a purchase or a submit. Cost and time within a cap, for example 40 steps, $2, and 10 minutes (illustrative).

**Design.** Lesson [Computer and Browser Use](/learn/ai/a7-agents-prod/computer-browser-use/) taught the loop. The pieces here:

1. **Observe, decide, act, verify.** Send a screenshot, which the docs estimate at "roughly 1,000–1,800 input tokens" each, plus the page structure when you can. The model picks an action. Then verify. The docs warn that "Claude sometimes assumes outcomes of its actions without explicitly checking their results", and suggest a screenshot after each step.
2. **A sandbox per run.** A dedicated VM or container with minimal privileges, a clean browser profile, and no logged-in sessions ([Anthropic computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)).
3. **A domain allow list, enforced at the network layer**, not in a flag the page can route around.
4. **Credentials from a scoped vault.** The harness types them into the field. They never enter the prompt or the history.
5. **Approval before irreversible clicks.** The docs say to ask a human to confirm "financial transactions" and "agreeing to terms of service". The approval prompt shows the item, the price, and the address read from the page, not the agent's description of them.

**Why 30 steps is hard.** Small per-step errors compound. A step that works 98% of the time sounds reliable, but over 30 steps the task fails about half the time. Add a check after each step that catches most wrong actions, with a retry that fixes them, and most of that loss goes away. The price is one more screenshot per step. Short tasks and API shortcuts help the same way. For scale: the OSWorld paper (2024) built 369 computer tasks on real web and desktop apps. Humans did "over 72.36%" of them, and the best model then did "only 12.24%". That is a 2024 figure, not today's. Read a live leaderboard before you decide.

**Failure: the page redesign.** A portal changes its layout. The "Order" button moves, and the agent clicks "Order again" on a different item. A hidden line on a page may also say to do something else. The docs say "Claude will follow commands found in content even when they conflict with your instructions". Controls: the approval gate above, an end-state check, and a hostile-page suite in the eval set (lesson [Prompt Injection](/learn/ai/a10-safety/prompt-injection/)). Also expect CAPTCHAs and endless scroll. The step cap is the stop.

## Staff answer vs senior answer

| Topic | Senior answer | Staff answer |
|---|---|---|
| Loop | "Search, edit, run tests, repeat." | A guard outside the loop: retry cap, failure signature, dollar cap, kill switch |
| Sandbox | "Run it in a container." | Three boundaries: files, network allow list, no secrets inside, with a canary and a denial log |
| Quality bar | "It passes the tests." | Held-out tests in a clean checkout, pass^k and pass@k, forbidden actions fail the run |
| Flaky tests | "Re-run CI." | Re-run in the harness, report "flaky", quarantine list, so the model never sees noise |
| Context | "Use a bigger window." | Agentic search first, compaction well below the window, subagents for read-only fan-out |
| Cost | "Use a cheaper model." | Cost per resolved task from tokens and live prices, cache assumptions stated, p95 cap |
| Changes | "We tuned the prompt." | Every change, including tool output limits, passes the suite before release |

## What experienced teams know

1. **A test is only as good as its determinism.** About 84% of Google's pass-to-fail transitions involved a flaky test ([Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)). Our reading: an agent reads flakiness as "my change is wrong", so filter it in the harness.
2. **Start with agentic search.** Anthropic says to add an index only if needed ([SDK post](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)). Cursor's numbers are start-up time and an average accuracy gain, both company claims ([Cursor](https://cursor.com/blog/secure-codebase-indexing)). Our reading: the agent edits files, so a live search stays fresh.
3. **A small box means fewer questions.** Anthropic reports 84% fewer permission prompts in internal use (company claim, [post](https://www.anthropic.com/engineering/claude-code-sandboxing)). Our reading: count your own prompts before you promise a number.
4. **Many agents suit coupled code poorly.** Anthropic says most coding tasks have fewer parallel parts than research ([post](https://www.anthropic.com/engineering/multi-agent-research-system)). Our reading: fan out for reading, not for editing.
5. **Budget the p90, not the mean.** The $13 a day average hides a tail: 90% of users stay under $30 ([docs](https://code.claude.com/docs/en/costs)). Our reading: set per-run caps from your own traces.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Agentic search only | No index to build, always fresh | More tool calls on big repos | Small and mid repos, changing files |
| Add an index | Faster start and broad queries | Sync, staleness, extra cost | Huge repos, vague questions |
| Compact early | Cheaper, sharper calls | A summary can drop a detail | Long runs, cost-bound |
| Subagents | Clean main window | More total tokens | Wide read-only work |
| Harness re-runs for flakes | The model never chases noise | Extra test time | Any suite with flaky tests |
| Tight retry cap | Small worst case | Some fixable tasks stop early | Cost-bound, many parallel runs |
| Strict sandbox | Small blast radius | Some tools need a proxy | Always, for code you did not write |

## Interview lens

<Callout type="tip">
Say: "My bar is held-out tests in a clean checkout, reported as pass^k and pass@k, with zero writes outside the repo and a cost cap per task. The loop is gather, act, verify. The sandbox has three boundaries: files, an allow-listed network, and no secrets inside. A guard outside the loop caps retries, spots a repeated failure signature, and has a kill switch. I search with grep first and compact early, because every call re-reads the history. I re-run flaky tests in the harness so the model never sees noise. Every change, even a tool output limit, runs the suite before it ships." That covers the bar, the box, the loop, the context, and the gate.
</Callout>

<Callout type="mistake">
Do not grade on the agent's own tests. Do not trust a prompt line to keep it in the repo. Do not rely on a dollar cap alone, since it fires late. Do not use many agents to edit the same files. And do not quote a benchmark score without the date, the scaffold, and the test set.
</Callout>
