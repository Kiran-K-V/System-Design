## The problem

In June 2025 Anthropic described how it built the Research feature of Claude ([engineering post](https://www.anthropic.com/engineering/multi-agent-research-system)). Two of its numbers frame this lesson. The post says "multi-agent systems use about 15× more tokens than chats". It also says that running subagents in parallel "cut research time by up to 90% for complex queries". Both are **company claims**. Read them together. The product is fast because it spends a lot, in parallel, all at once.

So the main design object is the **budget**: tokens, tool calls, dollars, and seconds. A chat answer costs a fraction of a cent. A research run can cost several dollars and run for minutes. Every part of the design makes that spend safe and worth it. Effort rules limit it. Checkpoints keep a crash from doubling it. A citation gate keeps it from buying a report that looks right and is not.

This lesson answers six questions:

1. How many agents and tool calls should a query get, and what does each setting cost at live prices?
2. What do tokens buy, and when does one more subagent stop paying?
3. Why does a restart from zero double the bill, and how does a deploy avoid killing runs?
4. How do you check a citation claim by claim, and what does a good check still miss?
5. Why must a fetched web page be treated as hostile?
6. How do you budget the latency of many parallel fetches (the answer-engine drill)?

## Requirements and the quality bar

The product takes a question and returns a cited report in a few minutes. Traffic numbers are **illustrative**: 4,000 runs a day, of which 60% are simple, 30% are comparisons, and 10% are complex.

**Functional**

- FR1: accept a question and return a run id at once. The report arrives later.
- FR2: plan the work and pick the effort from the question.
- FR3: search and read the web in parallel, with several subagents.
- FR4: return a report in which every claim cites the page that supports it.

**Out of scope.** Private company documents (the [Enterprise RAG over Company Docs with Permissions](/learn/ai/a13-cases/enterprise-rag/) lesson, enterprise RAG), code execution, scheduled reports, and editing the report by chat.

**Non-functional, and the bar.** These are our bars, not a standard. Each says how it is measured.

| Metric | Bar | How measured |
|---|---|---|
| Claim-level citation recall | At least 95% of shipped claims supported by their cited text | An entailment check per claim, plus a weekly human audit |
| Claim-level citation precision | At least 90% of citations relevant | The same check |
| Rubric pass rate | At least 85% on a 100-query golden set | An LLM judge, plus human spot checks |
| Cost per run | Mean at most $3, hard cap $20 per run | The budget meter, summed per run |
| Wall-clock per run | P95 at most 10 minutes | Run store timestamps |

Deep dive 3 defines the citation metrics. The cost bar has two parts on purpose: the mean says if the business works, and the cap bounds the worst bill one query can create.

## Eval plan

Per the [AI Design Method](/learn/ai/a0-orientation/ai-design-method/) lesson, the eval comes before the design.

**Offline set.** Anthropic says it began with "about 20 queries representing real usage patterns". We use 100, stratified by effort class: 60 simple, 30 comparisons, 10 complex. The simple ones have a known short answer, so a code check grades them with no judge. Each query runs 3 times, since an agent that passes once may fail next time (lesson [Agent Trajectory Evals](/learn/ai/a8-evals/trajectory-evals/)).

**The rubric judge.** Reports are free text with no single right answer, so we use an LLM judge, as in lesson [Judges](/learn/ai/a8-evals/judges/). Anthropic grades with five criteria: "factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness (are all requested aspects covered?), source quality (did it use primary sources over lower-quality secondary sources?), and tool efficiency (did it use the right tools a reasonable number of times?)". It says a single call with a single prompt, scoring 0.0 to 1.0 and giving a pass or fail, "was the most consistent and aligned with human judgements". We copy the five criteria, but compute citation recall and precision in code, so the judge cannot be generous about them.

**Human spot checks.** The same post reports what automation missed: "human testers noticed that our early agents consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources". A content-farm page reads well and agrees with the report, so a judge can pass it. A person who knows the field sees the weak source. So people read a sample every week: runs the judge scored just above the pass line, and niche topics, where farms rank high. With the rule of three (zero failures in n checks bounds the true rate near 3 / n at 95% confidence), 100 reviewed reports with no source-quality failure support "at most 3%".

**Online.** Cost per run by effort class, subagents and tool calls per run, wall-clock, resume count, and citation recall of shipped reports. The slice that matters is the complex class: 10% of runs and most of the money.

## Budgets

**Prices, live.** As of 2026-10-20, from the [Anthropic pricing page](https://platform.claude.com/docs/en/about-claude/pricing), per million tokens, input then output.

| Model | Input | Output | Cache hit |
|---|---|---|---|
| Claude Opus 5.5 | $4 | $20 | $0.20 |
| Claude Sonnet 5.5 | $2 | $10 | $0.10 |
| Claude Haiku 5.5 (prompts up to 100,000 tokens) | $0.10 | $0.50 | $0.01 |

On the same page, web search costs "$10 per 1,000 searches, plus standard token costs for search-generated content", so one search is $0.01. Web fetch has "no additional charges beyond standard token costs". The page shows no date, so the date is the day I fetched it. For a search API outside the model, [Exa](https://exa.ai/docs/reference/pricing) lists search at $7 per 1,000 requests (auto and fast types), deep search at $12 to $15 per 1,000, and page contents at $1 per 1,000 pages.

**Dollars per run, in words.** Take the simplest case: one agent with 6 tool calls on Sonnet 5.5. The agent starts with a system prompt and a brief. Each tool call adds a long result to the context. Every model call re-sends the whole context, so the input the agent pays for grows with each step. Most of the bill is input tokens, not the words the agent writes. Add the search fees and a citation pass that reads the report and its sources. Under our illustrative sizes, the whole run costs a few tens of cents. A plain chat answer on the same model costs a couple of cents. So even this tiny run is many chats. Deep dive 1 prices all three effort classes.

**Time per run.** A model call plus its tool takes several seconds (illustrative). A simple run is one agent calling tools in a row, so it takes about a minute. A complex run takes only a few minutes, because the subagents run in parallel. One by one, the same calls would take about 20 times as long. The P95 bar is 10 minutes, so the typical run leaves slack for retries and slow pages.

## Core entities and API

**Entities.** `Run` (query, effort class, state, caps, spent), `Plan`, `Step` (a checkpoint), `Finding` (subagent id, claim, exact quote, url), `Source` (url, text hash, trust tier), `Report` (claims, each with its citations).

**API.** `POST /runs` with `{query, max_usd}` returns `{run_id}` at once. `GET /runs/{id}` returns state and progress, and `GET /runs/{id}/report` the report. `POST /runs/{id}/cancel` stops a run and keeps what it found. Lesson [Background Agents and Queues](/learn/ai/a7-agents-prod/background-agents-queues/) explains why a long run is submitted, queued, and polled. We use that pattern as given.

## A naive design and where it breaks

The first build in most teams is one agent loop with a long prompt: "Research this thoroughly and cite your sources". It has a search tool and a fetch tool, and no caps. It runs inside the web request. It reads each page straight into its context, and it cites the URLs it saw. Here is where it breaks. Numbers come from our cost model unless a source is named.

| Break | What happens | Number |
|---|---|---|
| Overspend on an easy query | The lead fans out. Anthropic reports that early versions made "errors like spawning 50 subagents for simple queries". | Many times the cost of one agent, for the same answer |
| One agent does it all in a row | A complex query needs about 180 calls. One by one they take tens of minutes, and the context overflows. | Far past the 10-minute bar |
| Crash at 80% | The run restarts from zero. | Most of the bill is paid twice |
| Deploy during runs | In-flight runs die when the workers restart. | Every run in flight, at once |
| Plausible source, wrong claim | The cited page is on topic and does not say it. | A link check passes it. An entailment check fails it |
| Page tells the agent what to do | A fetched page hides orders in its text. | One bad page among about 180 per complex run |

The cause is the same each time: the model is the only control, and a prompt is a request, not a rule. The rest of the lesson moves each control into code.

## Deep dive 1: effort scaling and the cost of a run

**What it is.** An **effort rule** maps the kind of query to the number of subagents and the number of tool calls each may use. Anthropic wrote its rules into the lead's prompt: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities."

**Picture.** An editor who sends one reporter to check a fact, a small team to compare two products, and a whole desk to investigate a company. The editor does not send the desk to check a fact.

**Why it exists.** Anthropic gives the reason: "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts." Without the rules, "overinvestment in simple queries" was "a common failure mode". The model does not feel the bill, so someone must tell it.

**The cost model.** A worker pays for every tool result again on every later call, because each call re-reads the whole context. So input cost grows much faster than the number of calls: double the calls and the input more than doubles. Lesson [Long-Running Agents and Context](/learn/ai/a6-agents/long-running-context/) shows the same growth.
With an Opus 5.5 lead and Sonnet 5.5 workers and no caching, the three effort classes differ a lot in cost. A simple run costs tens of cents. A complex run costs on the order of ten dollars. Wall-clock time grows far less than cost. The 15 calls for complex research are our assumption, since the post says only "more than 10 subagents".

Three things stand out. First, the classes differ by more than an order of magnitude, so the mix sets the bill. The complex 10% of runs is most of the money. Second, search fees are a fixed charge per call that caching cannot touch. In the complex row they are a large share of what remains. With caching on every call, worker tokens fall by a large factor, but the run still costs real money. Third, wall-clock time barely changes between 3 and 12 subagents, because they run in parallel. Cost grows with subagents. Time does not.

**Where the 15x goes.** Our three effort classes use from tens to over a thousand times the tokens of a chat. None is close to 15. Anthropic's 15x is an average over its own traffic, and we cannot see its mix, result sizes, or truncation. Do not plan from 15x. Measure tokens per run by effort class on your own traffic.

**What tokens buy.** Anthropic reports: "three factors explained 95% of the performance variance in the BrowseComp evaluation... token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." BrowseComp is a benchmark of hard web-search questions. Our reading: spend and success rise together across their runs. That does not show where the curve flattens on your queries. The product question is the **marginal value**: what does the next subagent add, against what it costs?

Think of the usual shape (illustrative). The first few subagents lift the pass rate a lot for little money. Each later step adds less quality and costs more, because cost grows with each subagent and the gain shrinks. At some point, a doubling of subagents adds almost no quality and doubles the bill.

The rule: add a subagent while the quality gain, times the value of a good report, exceeds the added cost. If a good report is worth little, stop early. If it is worth a lot, go further, but still stop before the flat part of the curve. The right effort depends on the value of the answer, so the effort table is a product decision.

**Enforce the rule in code.** A prompt rule lowers the odds of overspend. A cap removes it. Keep maximum subagents, maximum calls, and a dollar cap per class, and check them before each spawn. A run can pass a cap by one call, since caps are checked after a response arrives (lesson [Loop Control](/learn/ai/a7-agents-prod/loop-control/)). The other risk is a wrong class: a complex query called "simple" under-delivers. Let the lead ask once to move up a class, and count the raise against the dollar cap.

## Deep dive 2: durable execution and rainbow deploys

**What it is.** **Durable execution** saves the state of a run after each step, so a crash resumes the run and does not restart it. Lesson [Durable Execution and Graph Runtimes](/learn/ai/a7-agents-prod/durable-graph-runtime/) taught the mechanism. Here is the cost view.

**Picture.** A video game with a save point after every room. When the game crashes, you lose one room. With no saves, you lose the whole game.

**Why it exists.** Anthropic: "When errors occur, we can't just restart from the beginning: restarts are expensive and frustrating for users. Instead, we built systems that can resume from where the agent was when the errors occurred." Temporal's service hands a crashed worker's job to another worker, "which replays the Event History and resumes at the line where execution stopped". LangGraph warns that in-memory checkpoints do not survive: "When the process restarts, all checkpoints are lost".

**Why restart doubles the bill.** A complex run has about 190 steps (12 subagents with about 16 model calls each). Each step can fail: a crash, a timeout, or a rate-limit error that exhausts its retries. Even a small failure chance per step (our assumption, since I found no published figure) adds up over that many steps. Most runs will see at least one failure.

With no checkpoint, any failure sends the run back to step 1. Every failed attempt is billed in full, so the expected bill is well above one run, and it grows fast as runs get longer or failures more common. If the checkpoint is per subagent, a failure redoes only one subagent, and the extra bill is small. If it is per step, a failure redoes one step, and the extra bill is close to zero.
**What resume must handle.**

- Findings are stored under (run id, subagent id), so a resumed lead does not start finished subagents again.
- Searches are reads, so repeating one costs $0.01. Tools that write need idempotency keys, as in the durable runtime lesson.
- The plan is saved to the run store. Anthropic notes that past 200,000 tokens the lead's context "will be truncated".

**Rainbow deploys.** A deploy changes code while runs are in flight, and a new version can break an old run's checkpoint. Anthropic: "We can't update every agent to the new version at the same time. Instead, we use rainbow deployments to avoid disrupting running agents, by gradually shifting traffic from old to new versions while keeping both running simultaneously."

How many runs does a deploy touch? By Little's law, runs in flight equal the arrival rate times the run duration. At high traffic and a few minutes per run, hundreds of runs are in flight at any moment. A deploy that kills the workers loses all of them, and the money already spent on them. Do that several times a day and the waste is large. With a rainbow deploy, new runs go to the new version and the old fleet drains, staying up for at most the run time cap. You pay for two small fleets for a short time and lose no runs.

## Deep dive 3: the citation gate and source trust

### Counting a citation claim by claim

**What it is.** A **claim** is one statement in the report that can be true or false. The **citation gate** checks each claim against the exact text it cites.

**Why a link check is not enough.** A report can cite a real, relevant page that does not say what the claim says: a plausible source for a wrong claim. Counting "claims with a citation" cannot see it. The ALCE benchmark paper gives two definitions that can. They use an **entailment** check (also called NLI, natural language inference): a model that answers yes if the cited text, taken as true, implies the claim.

- **Citation recall** is per claim. "We calculate the citation recall of each statement (0 or 1) and average over all statements in the model response." A claim scores 1 only if it has at least one citation and the entailment check says the concatenated citations imply it.
- **Citation precision** is per citation. A citation is "irrelevant" if (a) it cannot support the claim on its own and (b) removing it does not hurt the other citations' support. A citation scores 1 if its claim has recall 1 and it is not irrelevant. The paper says its precision "does not require citing a minimal set". Redundant citations are not penalized.

Work an **illustrative** report: 8 claims, 10 citations.

| Claim | Citations | Cited text implies the claim? | Recall | Citation precision |
|---|---|---|---|---|
| c1 | A | Yes | 1 | A: 1 |
| c2 | B, C | Yes; B alone does, C alone does too | 1 | B: 1, C: 1 (redundant, not irrelevant) |
| c3 | D | No: on topic, but it never gives the number | 0 | D: 0 |
| c4 | E, F | Yes, from E; F says nothing relevant | 1 | E: 1, F: 0 |
| c5 | none | No citation | 0 | no citation to score |
| c6 | G, H | Yes, only the two together | 1 | G: 1, H: 1 |
| c7 | I | Yes | 1 | I: 1 |
| c8 | J | Yes | 1 | J: 1 |

Six of the 8 claims are supported by their cited text, so recall is 75%. Most citations are correct, so precision is a little higher. A check that asks "does the claim have a citation?" would report a higher recall and miss c3. Below our recall bar, the gate repairs the claim (look for a better span) or strikes it. A struck claim lowers completeness. That is the trade.

**What the gate costs.** The gate reads each claim with its cited text. On a small model that is almost free. On a strong model it is still a tiny share of a complex run. Use the stronger model: a wrong verdict here is expensive.

Anthropic's system uses a separate citation agent: the lead "passes all findings to a CitationAgent, which processes the documents and research report to identify specific locations for citations". The [Anthropic Citations API](https://platform.claude.com/docs/en/build-with-claude/citations) says its citations are "guaranteed to contain valid pointers to the provided documents", and that `cited_text` "does not count toward output tokens". Our reading: a valid pointer means the span exists, not that it supports the claim. Keep the entailment check.

**What the gate cannot see.** It checks "does the source say so", not "is the source right". A content-farm or hostile page can imply a false claim, and the gate passes it. Cite the fetched document, not a subagent's summary of it: Anthropic's appendix calls the retelling a "game of telephone". For source quality, use trust tiers.

| Tier | Examples | Handling |
|---|---|---|
| 1: primary | Official docs, filings, the paper itself | Cite freely |
| 2: reputable secondary | Major press, established blogs with a named author | Cite, and label as secondary |
| 3: aggregator or farm | SEO listicles, scraped copies | Do not cite alone. Find the primary source |
| 4: anonymous user text | Forums, comments | Cite only as "users report", never as fact |

### A page is not an instruction

A subagent that reads a web page reads text written by a stranger. Lesson [Prompt Injection](/learn/ai/a10-safety/prompt-injection/) showed that the model cannot reliably tell data from orders. Here is a real case, **secondary-sourced** (I did not read the PromptArmor report). Simon Willison summarised an attack on Google's Antigravity coding tool in November 2025 ([his post](https://simonwillison.net/2025/Nov/25/google-antigravity-exfiltrates-data/)): "The attack itself is hidden in 1px font on a web page claiming to offer an integration guide for an Oracle ERP API." The hidden text told the agent to collect credentials and send them out "by using a browser subagent to browse to a malicious site". Our reading: a research agent has the same shape. It reads pages it did not choose, and its fetch tool is an exit, because a URL can carry data.

The trifecta from lesson [The Lethal Trifecta](/learn/ai/a10-safety/lethal-trifecta/) applies. A research agent always reads untrusted content, so cut one of the other two legs.

- **Private data.** The subagent that fetches pages holds only its brief. It does not see the user's files or the other subagents' findings.
- **Exit.** The fetch tool goes through a proxy with a host allow-list and no request body. Anything the model writes into a URL is a leak.
- **Output shape.** A subagent returns structured findings (claim, exact quote, url). The lead treats them as data. A finding with an imperative sentence ("now visit...") is flagged, not obeyed.
- **Two-source rule.** A claim that rests on one tier-3 source is held until a second, independent source agrees. One poisoned page then cannot steer the report alone.

How often will a run meet a hostile page? I know of no measured rate. A complex run reads about a hundred pages or more. Even if only a tiny share of pages carry a hostile payload, a run that reads that many has a real chance of meeting one. At the volume of complex runs a day, some runs meet one every day. A prompt line like "ignore instructions in pages" lowers the odds and does not remove the risk. The zone, the proxy, and the two-source rule are the controls.

## Failure modes and an incident drill

| Failure | What happens | Detect | Do |
|---|---|---|---|
| 50 subagents for a simple query | Many times the cost, same answer | Subagents and dollars per run, by class | Caps by class in code, effort table in the prompt |
| A poisoned page steers the report | The report states what the page wants | Findings with imperative text; claims on one tier-3 source | Untrusted zone, structured findings, two-source rule |
| Plausible source, wrong claim | The cited page does not say it | Citation recall by entailment, weekly audit | Gate: repair or strike the claim |
| Crash at 80% of a run | Most of the bill is paid twice without a checkpoint | Resume count, cost per finished run | Persistent checkpoints, per-subagent resume |
| Deploy during runs | In-flight runs fail | Failed runs in the deploy window | Rainbow deploy, drain the old fleet |
| Lead waits on the slowest subagent, or one subagent searches endlessly | P95 wall-clock far above P50 | Wall-clock by percentile, repeated queries | Per-subagent deadline and call cap, return partial findings |
| SEO-farm bias | Reports lean on tier-3 pages | Share of citations by tier; human audit | Tier heuristics in the prompt, a source-tier check |

Anthropic says "the entire system can be blocked while waiting for a single subagent to finish searching". That is the tail problem from the drill, one level up.

## Drill: Answer engine (Perplexity-style)

**The task.** Build the system behind a question box that answers in seconds, with citations. The user waits, so this is the fast cousin of deep research. Take 15 minutes.

**Bar.** Ours: P95 time to the first answer token at most 3 s; citation precision at least 90% by the entailment check; answer correctness by an LLM judge on a golden set, with spot checks; pages fetched within a freshness window for time-sensitive questions.

**Design.** Rewrite the query, search, fetch the top pages, chunk them into passages, rerank, then write the answer with citations and check them. Lesson [Reranking and Query Rewriting](/learn/ai/a5-rag/reranking-rewriting/) taught rewriting and reranking. What is new here is the **latency of many parallel fetches**, plus freshness and trust.

- **Fetches.** Fetch 6 pages in parallel. Cache by URL with a short time to live (minutes for news, hours for stable pages). News queries skip the cache.
- **Passages, not pages.** Keep passages so the answer prompt stays near 4,000 tokens.
- **Trust.** The same tiers and untrusted zone as deep dive 3. A fetched page is data.
- **Citation check.** Run the entailment check on each sentence, or mark unchecked sentences as such. A fast path may stream first, verify after, and retract.

**Budget.** The time for each stage is **assumed**. The stages add up to a few seconds.

| Stage | Note |
|---|---|
| Rewrite (small model) | Short, a small model is fast |
| Search API call | One network round trip |
| 6 parallel fetches, wait for all | The slowest fetch sets the time. Explained below |
| Chunk and rerank | Local work, short |
| Answer, first token | The user sees this moment |

**Why the slowest of six matters.** Say one fetch is slow (past its own p95) with a small chance. The stage waits for all six, so it is as slow as the slowest. With six fetches, the chance that at least one is slow is several times higher than for one fetch, and it keeps rising with every fetch you add. Roughly, more than one run in four has a slow fetch at six pages.

<CrossTrackLink id="01-one-machine/throughput-vs-latency">
Tail latency multiplies with fan-out. A request that waits for 100 services is slow most of the time, even when each service is slow only 1% of the time. The 6-fetch case follows the same idea on a smaller scale.
</CrossTrackLink>

What does it do to the stage percentiles? The stage median is not the median of one fetch. It lands near the 89th percentile of a single fetch. The stage p95 lands near the 99th percentile of one fetch, far past the 95th we were given. So six parallel fetches more than double the median wait of one fetch, and the tail is worse. Step through a made-up draw of six fetches.

A **hedged request** sends a copy when a fetch passes a deadline, and the first reply wins. This cuts the tail a lot. The median does not change, because most stages finish before the deadline. The cost is the copies: only a few percent of fetches pass the deadline, so hedging adds only a few percent more requests. Stopping at the deadline and answering from five pages is the other choice, and it trades coverage for time.

**Perplexity on Vespa (vendor case study).** The Vespa page about Perplexity is vendor marketing, so every figure is a **company claim**. It says Perplexity handles "780m+" queries a month, growing "20%+" a month, and that Vespa "brought these capabilities together in a single distributed serving engine, with support for continuous indexing and machine learning inference". It names hybrid retrieval with structured filtering, passage-level retrieval, and multi-stage ranking ("lightweight ranking, then... richer neural models"). It also says Perplexity "has moved its web index to a purpose-built internal search system and continues to use Vespa for other use cases". It gives no latency in milliseconds. Our reading: at that volume, renting a search API for every query would cost millions of dollars a month, a reason to own retrieval (the page says in-house search "meant owning retrieval instead of renting it"). That cost is our inference, not Perplexity's.

**The failure: one slow source stalls every answer.** With several fetches, many answers wait on a tail fetch. Fix it with a deadline and a hedge. Watch the stage p95 on its own, since the end-to-end figure hides it.

## Teardown: Anthropic's multi-agent research system

This section reads one company post against what we built. Every figure is a **company claim** from the [engineering post](https://www.anthropic.com/engineering/multi-agent-research-system) (published 2025-06-13). The post gives no raw data, so none can be checked from outside.

| Claim, in their words | What it does not say (our reading) |
|---|---|
| "the lead agent spins up 3-5 subagents in parallel rather than serially", and a Claude Opus 4 lead with Claude Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" | 90.2% is a relative gain on an eval we cannot run, with models from 2025. It is not accuracy. The post says the system excels at "breadth-first queries" |
| Parallel calls "cut research time by up to 90% for complex queries" | "Up to" is the best case, for complex queries. Our model gives a cut of the same order |
| "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats" | An average over their traffic. Our three effort classes run from tens to over a thousand times a chat. Measure your own mix |
| "token usage by itself explains 80% of the variance" on BrowseComp | Spend and score rise together in their runs. It is not a law, and it is silent about where returns fall |
| A tool-testing agent "resulted in a 40% decrease in task completion time for future agents using the new description" | A speedup for later agents from better tool text, measured by them. Cheap to try, not a general constant |
| "we built systems that can resume from where the agent was"; "rainbow deployments" | Matches deep dive 2. The post gives no failure rate or checkpoint size |
| "human testers noticed that our early agents consistently chose SEO-optimized content farms" | A failure the automatic evals missed. Keep people in the loop |

Take-away: the design is not exotic. The hard parts are the budget rules, the saved state, and the checks around the loop.

## Staff answer vs senior answer

| Topic | Senior answer | Staff answer |
|---|---|---|
| Design | A lead and 3 to 5 subagents | The lead plus an effort table by class, enforced by caps in code |
| Cost | "It costs about 15 times a chat" | Cost per run by effort class from live prices, with the search fee shown apart, and the marginal value of the next subagent |
| Failure | "Retry on error" | Checkpoint per step, resume by run id, bill multiplier from the failure rate |
| Quality | "An LLM judge scores reports" | Claim-level recall and precision by entailment, a gate that repairs or strikes, humans on the farm-bias slice |
| Pages | "Sanitize the HTML" | An untrusted zone: no private data, no free exit, structured findings, a two-source rule |
| Latency | "Parallel fetches are fast" | Stage p50 is a high percentile of one fetch, and stage p95 is higher still. Deadline, hedge, and a partial-answer path |

## What experienced teams know

1. **The model cannot feel the bill, so write the rule.** Anthropic put scaling rules in the prompt because agents "struggle to judge appropriate effort" (company claim). Our reading: the prompt is layer one and a cap in code is layer two.
2. **Tokens buy quality, with falling returns.** Token use "by itself explains 80% of the variance" on BrowseComp (company claim). Our reading: price the next subagent against the value of a good report, not against zero.
3. **Restarts are the expensive path.** LangGraph's docs warn that in-memory checkpoints are lost when the process restarts ([durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)). Our reading: a long run with many steps almost always sees a failure, so without checkpoints the bill climbs.
4. **A citation can be real and still not support the claim.** ALCE scores recall by entailment, not by presence ([paper](https://arxiv.org/abs/2305.14627)). Our reading: the gate is a tiny share of a run's cost, so there is little reason to skip it.
5. **A fetched page can carry orders.** PromptArmor's Antigravity attack hid them in 1px text (secondary, via [Willison](https://simonwillison.net/2025/Nov/25/google-antigravity-exfiltrates-data/)). Our reading: the page leg cannot be cut, so cut private data and the exit.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Many subagents, higher effort | Wall-clock cut, wide coverage | Token use far above a chat, merge errors | Broad, high-value questions |
| Prompt caching | Large cut in worker tokens | Needs warm, stable prefixes. Real hit rates are below 100% | Long worker contexts with many calls |
| Checkpoint every step | Resume costs one step | A write per step, state size | Runs are long or expensive |
| Strict citation gate | Fewer unsupported claims | Struck claims lower completeness | A wrong claim costs more than a gap |
| Rainbow deploys | No dropped runs | Two fleets for a short time | Runs last minutes |

## Interview lens

<Callout type="tip">
Say: "The budget is the design. Each query gets an effort class from a rule table, with caps on subagents, calls, and dollars enforced in code. I price a run bottom-up at live prices, since 15x is an average. I checkpoint every step and use rainbow deploys, so a crash or release costs one step. Every claim passes a citation gate by entailment, with recall and precision defined. Pages are hostile: a zone with no private data and no free exit. A judge scores a sample and people read the farm-prone slice. I watch cost per run by class."
</Callout>

<Callout type="mistake">
Do not plan from "15x a chat". Do not trust a prompt to cap spend. Do not restart a failed run from zero. Do not count "claims with a link" as citation quality. Do not let a page-reading subagent hold private data or an open exit. And say a crash rate or injection rate is an assumption unless you have a source.
</Callout>
