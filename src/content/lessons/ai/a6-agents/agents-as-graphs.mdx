## The problem

The loop in the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson is 25 lines and it works. Then the questions start. The run crashed at step 7. Can it resume from step 7, not step 1? The tool step failed. Can you retry only that step? A reviewer must approve a refund before the agent sends it. Where does the run wait? A test must check the routing logic. How do you test one decision without running the whole loop?

In a plain `while` loop, the steps are not visible to anything but your code. State is local variables. The next step is an `if` buried in the body. You cannot pause the loop, save it, or test one part of it. This lesson shows a different shape for the same agent: a graph with explicit state, explicit steps, and explicit edges.

## The idea: state, nodes, edges

A **graph** here has four parts.

- **State.** One typed object that holds everything the run knows: the message list, a plan, scratch data, counters. Nodes pass data to each other only through state.
- **Nodes.** Each node is a function. It reads the state and returns an update. One node calls the model. Another runs tools. Another checks a result.
- **Edges.** An edge says which node runs next. A fixed edge always goes to the same node.
- **Conditional edges.** A routing function reads the state and returns the next node. "Tool calls in the last message? Go to `tools`. Otherwise go to `END`."

Now the two shapes from the [Workflows vs Agents](/learn/ai/a6-agents/workflows-vs-agents/) lesson. A workflow with fixed steps is a **DAG**, a directed graph with no cycle. It has one path and it always ends. An agent loop is a **cycle**: the `tools` node has an edge back to the `agent` node. The graph can run any number of times round the cycle, so it needs an exit.

## Why a graph, not a loop

Explicit steps give you things a bare loop cannot:

- **Checkpoints.** The runtime can save the state after each node. If the process dies, a new process loads the last saved state and goes on. The [Durable Execution and the Graph Runtime](/learn/ai/a7-agents-prod/durable-graph-runtime/) lesson covers the runtime and persistence. Here, remember only that it needs explicit state and explicit steps.
- **Retries.** You retry one node, not the whole run.
- **Tracing.** Each node run is one span, with its input state and its output update.
- **Tests.** A node is a function. Give it a state, check the update. A routing function is a pure function of state, so a unit test covers every branch.
- **Human steps.** A node can pause the run and wait for a decision.

## The same graph in LangGraph

LangGraph is one library that implements this model. Its `StateGraph` is built from a state schema. The docs say the schema can be a `TypedDict`, a dataclass, or a Pydantic model. Each state key has a **reducer**, a function that merges a node's update into the old value. With no reducer, an update replaces the value. With `operator.add` on a list, the update is appended. The `add_messages` reducer merges message lists by ID.

```python title="graph.py"
from operator import add
from typing import Annotated, TypedDict
from langgraph.graph import END, START, StateGraph

MAX_STEPS = 6

class State(TypedDict):
    messages: Annotated[list, add]   # reducer: append
    steps: int                       # default reducer: replace

def agent(state: State):             # node: reads state, returns an update
    reply = call_model(state["messages"])
    return {"messages": [reply], "steps": state["steps"] + 1}

def run_tools(state: State):
    return {"messages": run_requested_tools(state["messages"][-1])}

def route(state: State):             # conditional edge: reads state only
    if state["steps"] >= MAX_STEPS:  # exit guard
        return END
    return "tools" if state["messages"][-1].get("tool_calls") else END

g = StateGraph(State)
g.add_node("agent", agent)
g.add_node("tools", run_tools)
g.add_edge(START, "agent")
g.add_conditional_edges("agent", route, ["tools", END])
g.add_edge("tools", "agent")         # the cycle
app = g.compile()
app.invoke({"messages": [first_message], "steps": 0}, {"recursion_limit": 25})
```

`call_model` and `run_requested_tools` stand for your model call and tool dispatch from the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson. This code was run with stub model and tool functions to check the API names. `invoke` stopped when the stub model stopped asking for tools.

Four details from the LangGraph docs matter for design:

- A node returns a **partial** update. It does not need to return the whole state.
- `START` and `END` mark the entry and the exit. You must call `compile()` before you can run the graph. Compile also does basic structure checks, such as finding orphaned nodes.
- Execution runs in **super-steps**. A super-step is one round of node runs. Nodes that run in parallel share one super-step. The docs advise that for each node you choose one routing mechanism: fixed edges or conditional edges, not both. A node with two outgoing fixed edges runs both targets in the next super-step.
- The `recursion_limit` caps super-steps. The docs say that starting in version 1.0.6 the default is 1000. When it is reached, LangGraph raises `GraphRecursionError`. A limit of 1000 is a weak budget for an agent that calls a model each time round. Treat it as a last resort, and set your own guard in the router.

## Every cycle needs an exit

The conditional edge in the animation has two ways out. One exit is that the model sends no tool calls. The other is that the step counter reaches its budget. The first is the model's choice. The second is yours. Without the second, a model that keeps asking for tools keeps the graph running until the framework's limit fires.

Run a small graph by hand. You choose what each node produces. The router is real: it reads the state and picks the edge. Turn the guard off, make the model always ask for a tool, and see what stops the run.

Notice two things. With the guard on, the run ends with a clean status, and your code decides what to return. With the guard off, the run ends in an error from the framework. Any work in the state is held only if you saved it.

## State, resume, and side effects

When a graph runs with a checkpointer, LangGraph saves state at super-step boundaries. It does not save state in the middle of a node function. The docs say that if a run stops and resumes, for example after an interrupt or a retry, the affected node runs again from the start of its function. Code before the pause runs again too. So a node that sends an email must be safe to run twice. The [Rate Limits, Retries, and Idempotency](/learn/ai/a3-llm-apis/limits-retries-idempotency/) lesson gave you idempotency keys for this. The graph does not remove the need for them.

## The backend view: a state machine

You have built this before. A graph is a **state machine**. The state is the row in your database. Each node is a transition handler. A conditional edge is the guard on a transition. The cycle is a transition from a state back to itself or to an earlier state. The only new part is that the model decides which guard condition is true.

<CrossTrackLink id="08-technologies/temporal">
Temporal runs a multi-step process as ordinary code. It records each step in an event history, and a new worker replays that history to continue after a crash. Workflow code must be deterministic, and activities hold the side effects, such as API calls. An agent graph has the same split. The routing is orchestration. The model and tool calls are the steps that touch the outside world. LangGraph and Temporal both let a run continue after a crash, by different means.
</CrossTrackLink>

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Plain loop | Least code, easy to read | No checkpoints, hard to test in parts | A short run you can simply restart |
| Explicit graph | Checkpoints, retries, tracing, per-node tests | More structure, a framework to learn | Runs that are long, need review, or must resume |
| Rely on the framework recursion limit | Nothing to write | A weak, late stop with a generic error | Never, as the only guard |
| Guard in the router | Clean stop and your own return value | A counter in state | Every cycle |
| Fixed edges (DAG) | Predictable path, simple tests | No flexibility | Steps are known (the [Workflows vs Agents](/learn/ai/a6-agents/workflows-vs-agents/) lesson) |

## Interview lens

<Callout type="tip">
Say it in backend terms: "The agent is a state machine. State is a typed object. Nodes are functions from state to update. Edges are transitions, and a conditional edge routes on state. A fixed workflow is a DAG. The agent is a cycle, so I add an exit edge. The exit edge is guarded by a step budget in the router, not only the framework limit. Explicit state gives me checkpoints, retries, and a test per node."
</Callout>

<Callout type="mistake">
Do not draw an agent graph with a cycle and no exit that you control. Also do not put side effects in a node and assume it runs once. A resumed node runs again from its first line.
</Callout>
