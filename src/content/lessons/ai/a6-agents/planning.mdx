## The problem

You ask an agent to add a coupon field to a checkout page. That job touches the API, the UI, the tests, and a pull request. The agent works for 40 turns. Somewhere in the middle it forgets that tests were part of the job. It opens the pull request without them, and says "done".

Nothing crashed. The agent had no durable idea of what "finished" meant. Each turn it saw a long history and chose the next action by feel. On long tasks, feel drifts. A plan fixes that by writing "finished" down before the work starts.

## Two ways to run a long task

There are two styles. In the **interleaved** style, the agent has no written plan. It looks at the history, picks one action, sees the result, and picks the next. This is the loop from the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson and the ReAct pattern from the [Loop Patterns](/learn/ai/a6-agents/loop-patterns/) lesson. Anthropic's guide says what makes it work. In its words, "it's crucial for the agents to gain 'ground truth' from the environment at each step". Each new observation can change the next move.

In the **plan-then-act** style, a planner writes the steps first. Executors then run the steps. LangChain's write-up of plan-and-execute agents describes three parts. One part is a planner that "prompts an LLM to generate a multi-step plan". Another part is executors. They "accept the user query and a step in the plan and invoke 1 or more tools". The last part is a re-planning step. After the steps run, "the agent is called again with a re-planning prompt". The agent then decides "whether to finish with a response or whether to generate a follow-up plan."

Neither style wins everywhere. Interleaving adapts at every step but pays for it in tokens and can wander. Planning gives structure and cheaper steps, but a rigid plan breaks when the world surprises it. Most real agents mix them: a short plan, an interleaved loop inside each step, and a replan on failure. In the [Workflows vs Agents](/learn/ai/a6-agents/workflows-vs-agents/) lesson terms, plan-then-act moves the agent toward a workflow: the path is written down before it runs.

## The plan lives in state

A plan that exists only in the model's output scrolls away as the history grows. Keep it in **state**, a typed object your code owns (the [Agents as Graphs](/learn/ai/a6-agents/agents-as-graphs/) lesson). The plan is a list of steps, each with a status: pending, running, verified, or failed. Your code shows the current plan to the model on every turn. The model reads the plan instead of remembering it.

You have seen this in products. The context engineering guide gives "Claude Code creating a to-do list" as an example. That example is an agent that writes notes outside the context window. The list is the plan, kept as external state. Because your code holds the plan, you can also read it. Show the plan in the UI, log it, and test against it.

## Replan on failure

When a step fails, you have three options. Retry the same step. Replan the rest. Or stop and ask a human. A retry is right for a flaky tool. A replan is right when the failure shows that the plan was wrong, as with the missing import above. A stop is right when the agent has no safe next move.

Replanning has a cost. It needs a strong model call with the plan and the results so far. Set a cap on replans, as you cap loop steps (the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson). An agent that replans forever is the same endless loop in a new place. A good rule: replan on a tool failure or a failed check. After the cap, hand the task to a human.

## Plan verification: check before "done"

The plan is also your test for "finished". Anthropic's work on long-running agents shows the failure and the fix.

The failure first. They list two behaviors. One is "Claude declares victory on the entire project too early". The other is that the agent marks "features as done prematurely". An agent judges its own work, and a model is eager to report success.

The fix: keep a feature list as a file, and give the agent a narrow right to change it. In their setup, the initializer wrote the requirements. Coding agents could "edit this file only by changing the status of a passes field." Removing or editing the tests was not allowed. The list in their claude.ai clone example grew to "over 200 features". The team chose JSON for the file because models are less likely to overwrite it than Markdown. They also found agents were more reliable once prompted to verify features end to end. That verification used browser automation, as a human user would.

Turn this into a rule for your own agent. Before the system accepts "done", code checks the plan: is every step verified by a passed check? If not, the loop continues and the model sees the open steps. The check is code, not another opinion from the model. The same idea appears in the memory tool docs. They say to mark a feature complete "only after end-to-end verification confirms it works, not when the code is written."

## Plans and cost

A plan can lower the cost of a run, and the LangChain post says so. It claims plan-and-execute agents are faster, cheaper than ReAct agents, and can perform better. Their reasons are specific. The main agent is not called after each action. Sub-tasks can use smaller models. The large model is reserved for planning and the final response. These are the post's claims, not measured results, so test them on your own tasks.

The post also names two limits. Execution is "restricted by serial tool calling". And the design "doesn't support variable assignment". So each task still needs an LLM call. Also, later steps cannot reuse earlier outputs directly. There is a quiet risk too. An executor that sees only its step has less context, so it may fail more. A cheap executor needs a clear step and the facts it needs.

A toy model compares one interleaved loop with a plan-and-execute run. Every size in it is an assumption, and it counts input tokens only.

In the toy model, the plan run uses fewer input tokens than the no-plan loop, because the history does not grow on every call. If the executors run on a cheaper model, the saving grows. Most of that extra saving is the cheaper model, and only part is the plan. With few steps, the plan stops helping, because the planner call is overhead.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| No plan, interleaved | Adapts at every step, simple | Drift on long tasks, history grows each call | Short or exploratory tasks |
| Plan, then execute | Structure, progress you can see, cheaper executors | Planner call, brittle if the world changes | Long tasks with known parts |
| Replan on failure | Recovers from surprises | Extra strong-model calls, risk of loops | Tools fail, or plans can be wrong |
| Static plan, no replan | Predictable cost | Breaks on the first surprise | Stable tools, simple jobs |
| Plan-state check before done | Stops early victory | Extra checks and tests to write | Any task with several parts |

## Interview lens

<Callout type="tip">
Say: "For a long task I have the model write a short plan and keep it in state with a status per step. Each turn the model sees the plan. A failed step triggers a capped replan. A strong model plans and replans, cheaper models execute. Before the agent can say done, code checks that every step passed its own test. The check exists because models declare victory early." That covers structure, cost, and control.
</Callout>

<Callout type="mistake">
Do not treat the plan as a promise. A plan the model wrote is a guess, and tools fail. Do not let the model mark its own steps verified: a check outside the model sets that status. And do not claim a plan always saves money. It can, with small steps and cheap executors, but the planner call and the lost context also cost something.
</Callout>
