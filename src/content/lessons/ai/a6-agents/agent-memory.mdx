## The problem

On Monday your coding agent learns that the project deploys with `make ship`. On Tuesday it starts a new session and tries `npm run deploy`. It fails, the user explains again, and the agent fixes it. On Wednesday the same thing happens.

The model did not get worse. A model call is stateless (the [Anatomy of an LLM API Call](/learn/ai/a3-llm-apis/api-anatomy/) lesson). The only thing it knows is what is in the context window for this call. When the session ends, the window is gone. Anything the agent should keep must live somewhere else. That place is **memory**.

## What "memory" means

The word covers different things. The CoALA paper (a framework for language agents, linked below) gives clean names. It defines **working memory** as information that is "active and readily available" for "the current decision cycle". For a language model agent, that is the context window. It also defines three long-term kinds:

- **Episodic memory** "stores experience from earlier decision cycles". Example: a log of past runs, what the agent tried, and how it ended.
- **Semantic memory** "stores an agent's knowledge about the world and itself". Example: "this project deploys with `make ship`".
- **Procedural memory** is knowledge about how to act. The paper says it has two forms: implicit knowledge in the model weights, and the agent's own code.

The paper adds that "learning occurs by writing information to long-term memory". That is the whole job in one line. An agent that learns must write. An agent that benefits must read.

Most product work sits in the first two long-term kinds. You cannot change the weights from a chat session. So in practice, memory is a store of notes: facts (semantic) and experience (episodic). A rules file that the agent reads at the start of every session is procedural in spirit. However, that mapping is our reading, not the paper's.

The [Compaction of Long Conversations](/learn/ai/a4-context/compaction/) lesson covers what to do inside one session when the window fills: compaction. Memory is for what must survive the session, or survive a compaction.

## A memory store you can build today

Anthropic's memory tool shows the minimal design. It is **client-side**: "Claude requests file operations, and your application executes them." The model asks for a command. Your code runs it against storage you control and returns a `tool_result`. You turn it on with one entry in `tools`:

```json title="tools-entry.json"
{ "type": "memory_20250818", "name": "memory" }
```

The commands are `view`, `create`, `str_replace`, `insert`, `delete`, and `rename`. All paths sit under `/memories`. Your handler maps this prefix onto real storage, such as a per-user folder or keys in a database. When the tool is in your request, the API adds an instruction to the system prompt. In short, it says: view your memory directory before anything else, record progress as you go, and assume your context may be reset at any time.

Your handler is a security boundary. The docs warn that a path such as `/memories/../../secrets.env` can reach files outside the memory folder. The docs also warn that you must validate every path in every command. One safe pattern resolves the path to its canonical form and checks that it stays inside the root:

```python title="memory_paths.py"
from pathlib import Path

ROOT = Path("/srv/agent-memory/user-42").resolve()

def safe_path(p: str) -> Path:
    if not p.startswith("/memories"):
        raise ValueError("path must start with /memories")
    full = (ROOT / p.removeprefix("/memories").lstrip("/")).resolve()
    full.relative_to(ROOT)  # raises ValueError if full escapes ROOT
    return full
```

Catch the `ValueError` and return it as an error result, so the model sees what went wrong. The docs also list URL-encoded sequences such as `%2e%2e%2f`, so decode the path before you check it.

## Write, read, forget

A store without a policy fills with noise. Decide three things.

**What to write.** Write what is durable and useful in a later session: decisions, commands that work, user preferences, and lessons from failures. Do not write the whole transcript, and do not write guesses as facts. Keep notes short, one topic per file.

**When to read.** The simplest rule is to read at session start. The memory tool's own system prompt says so. The docs describe memory as supporting "just-in-time context retrieval". The agent keeps notes outside the window and reads them back on demand. So the active context stays focused. The context engineering guide puts it this way. An agent can write a to-do list or a `NOTES.md` file, and pull it back later. That guide also names the trade-off of loading data at run time. It is slower than retrieving precomputed data and needs good tool guidance, or the agent wastes context.

**When to forget.** The docs advise tracking file sizes and capping how large a file can grow. The docs also advise deleting files that "haven't been accessed in a long time". A stale note is worse than none. The agent trusts it, acts on it, and the result is wrong with full confidence. Date your notes, and let the agent replace a note when a fact changes.

**Sensitive data.** The docs say Claude "usually refuses to write sensitive information to memory files". The docs also say to add validation that strips sensitive information before the handler writes. Do not rely on the model alone. Passwords, tokens, and personal data do not belong in notes.

## Retrieval-based memory

A file folder works while the store is small. What if the agent has written 10,000 notes? Listing them is too much. Then you add search. Embed each note, store it in an index, and fetch the few that match the current task. This is the same retrieval used for documents, and module A5 covers it. The difference is that here the agent writes the corpus itself.

Retrieval changes the failure from "too many tokens" to "wrong notes". A search can miss the one note that matters. This is a toy, not a benchmark.

Loading every note puts a large block of tokens in front of the model, though only a few notes matter. Retrieval loads only the few that match. Expiry is a cost control as well as a hygiene rule. A longer expiry means a bigger store, so more to load or search.

## Risks: stale and poisoned memory

Memory makes an agent's past part of its input. That has two risks.

**Staleness.** A note says the API base URL is X. The team moved it last week. The agent now fails, or worse, writes to the old place. Fix it with dates, expiry, and a rule. The rule says the agent checks a note against the live system when it can.

**Poisoning.** The [Tool-calling Protocol](/learn/ai/a3-llm-apis/tool-calling-protocol/) lesson showed that tool results can carry instructions from outside, which is called indirect prompt injection. Memory extends the reach of that risk. Suppose the agent reads a web page that hides an instruction, and then saves a "useful tip" from that page. The instruction now sits in the store, and every later session reads it as if the agent had learned it. We derive this risk from prompt injection. It is not a measured rate, and we give no number. The defenses follow from the same ideas. Keep the source of each note. Treat notes from untrusted content as lower trust. Review what gets written for sensitive or action-like text. Let the user see and delete memories. Module A10 covers prompt injection in full.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Only the context window | Simple, nothing to secure | Forgets at session end | One-shot tasks |
| File notes (memory tool) | Easy to read and audit, small code | Agent must read and write well | Small stores, coding agents |
| Vector index of notes | Scales to many notes | Misses, another system to run | Thousands of notes |
| Load all notes | Never misses a note | Tokens and cost grow with the store | Very small stores |
| Expiry | Smaller store, fewer stale notes | A useful note may vanish | Most stores |
| Write policy and review | Cleaner, safer notes | Missed lessons, extra work | Anything that acts for a user |

## Interview lens

<Callout type="tip">
Say: "The window is working memory. For long-term memory, I keep notes outside the context window. The notes hold facts and past experience, written by the agent through a tool I control. At session start it views the store, and I load only what the task needs. I cap size, expire unused notes, strip sensitive data, and record where each note came from. The reason is that memory can carry a prompt injection into later sessions." The answer shows the types, the cost, and the risk.
</Callout>

<Callout type="mistake">
Do not say "just give the agent a vector database" without a write policy. Do not load all memories into every call: cost and noise grow with the store. And do not trust the model to keep secrets out of notes. The docs say Claude usually refuses, and still tell you to strip them in code.
</Callout>
