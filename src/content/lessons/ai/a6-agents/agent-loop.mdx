## The problem

Some tasks have no fixed number of steps. "Fix the failing test" may need one file read or twenty. You cannot write the sequence in advance, because the right next step depends on what the last step returned.

A single model call cannot do this. It answers once and stops. To let a model work toward a goal, you wrap it in a loop and give it tools. That loop is what people mean by an **agent**. This lesson shows the loop, how it stops, and what each turn costs. The lesson also shows why long loops fail more often than short ones.

## The idea: a while loop around the tool round trip

The [Tool-calling Protocol](/learn/ai/a3-llm-apis/tool-calling-protocol/) lesson covered one round trip. In it, the model writes a `tool_use` request, your code runs it, and you send back a `tool_result`. An agent repeats that trip. Four things make the loop:

1. A **history**: the list of messages so far, including every tool result.
2. A **model call** that reads the whole history.
3. **Tools** that your code runs when the model asks.
4. A **stop rule**: what ends the loop.

Anthropic's guide on agents describes the same thing. The guide says agents are "typically just LLMs using tools based on environmental feedback in a loop". The model gets real results from the environment at each step. Such results include tool output or code execution. The model uses them to judge its own progress.

Here is the loop in about 25 lines. The model name is Sonnet 5.5 and the limits are example values.

```python title="agent.py"
import time
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"
MAX_TURNS = 8          # step budget
MAX_TOKENS = 50_000    # token budget
DEADLINE_S = 120       # time budget

def run(goal, tools, handlers):
    messages = [{"role": "user", "content": goal}]
    spent, start = 0, time.monotonic()
    for turn in range(MAX_TURNS):
        resp = client.messages.create(
            model=MODEL, max_tokens=1024, tools=tools, messages=messages)
        spent += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":      # model chose to stop
            return "done", messages
        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                out, failed = handlers[block.name](**block.input), False
            except Exception as e:              # errors are results
                out, failed = f"{type(e).__name__}: {e}", True
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": str(out), "is_error": failed})
        messages.append({"role": "user", "content": results})
        if spent > MAX_TOKENS or time.monotonic() - start > DEADLINE_S:
            return "budget", messages
    return "max_turns", messages
```

Read it as a state machine with one exit chosen by the model and three exits chosen by you. The `for` loop, not `while True`, is deliberate. The step budget is part of the loop header, so it cannot be forgotten.

## The naive version: let it run

The first draft of most agents is `while True`. The only way out is the model deciding to stop. That is a bet that the model will always find the end. It will not. A tool can fail the same way every time, and a model can retry the same call. A vague goal such as "improve this codebase" has no natural end at all. The Claude Agent SDK docs say that without limits the loop "can run long on open-ended prompts". The docs also say that setting a budget "is a good default for production agents".

Each wasted turn costs money and time. And a loop that never ends is an outage for the one user waiting on it.

## Stop conditions

A stop rule has two sources.

**The model stops.** The reply has no `tool_use` block. The stop reason on that last turn is usually `end_turn`. The SDK docs list two other common values. `max_tokens` means the output limit was hit, so the reply may be cut off. `refusal` means the model declined. Your loop must handle all three. A `max_tokens` stop with no tool call is not a finished answer.

**Your code stops.** You set three budgets, and the loop ends when any one is spent:

- **Steps.** A turn counter. Anthropic's guide says to include stopping conditions "such as a maximum number of iterations". In the Claude Agent SDK, `max_turns` counts tool-use turns only.
- **Tokens or dollars.** A running sum of usage from each response. The SDK has `max_budget_usd`.
- **Time.** A wall-clock deadline, because a user is waiting.

Two details matter. First, a budget check runs after a response arrives. The reason is that the cost is known only from the usage in that response. The SDK docs say the response that reaches the cap still completes. So spend can pass the cap by one response. Set the cap below the real limit. Second, a retry is a turn. A tool that fails three times uses three turns and makes no progress. When you choose a step budget, count the retries.

When a budget ends the run, do not throw the work away. Return what the agent has, with a reason such as `max_turns`, so the caller can show partial results or resume with a higher limit.

## Why each turn costs more than the last

The API is stateless (the [Anatomy of an LLM API Call](/learn/ai/a3-llm-apis/api-anatomy/) lesson). Every model call resends the full history. Turn 5 pays for the tokens from turns 1 to 4 again. So input tokens grow faster than the number of turns.

Anthropic measured the effect at the system level. In their multi-agent research write-up, agents "typically use about 4× more tokens than chat interactions". Their number is an average for their own workloads, not a law, but the direction is general.

Picture a run of a dozen calls. The first call sends the system prompt, tools and goal. Every later call sends all of that plus everything added since. Most of the total input is old history sent again, not new work. Cost grows much faster than the number of turns. Prompt caching (the [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson) makes the repeated prefix cheap, but only if the prefix stays stable. A loop that appends is a good fit for it.

## Why long loops fail more often

Every turn is a chance to go wrong. The model may pick the wrong tool, pass a bad argument, or misread a result. If each step is right with probability p, and a run needs n correct steps in a row, the run succeeds with probability:

<Math block tex="P(\text{run succeeds}) = p^{n}" />

The [Probabilistic Components](/learn/ai/a0-orientation/probabilistic-components/) lesson built this formula. A step that is right 95% of the time sounds safe. Chain thirty of them, and the run fails more often than it succeeds. Real agents recover from some errors, so the formula is a worst case. It still shows why a loop needs checks inside it.

The second measure is about repeats. A **tau-bench** task puts an agent in a customer-service role with tools and a policy. A model plays the customer. The score compares the final database state with the goal state. The authors define **pass^k** as the chance that all k independent trials of a task succeed, averaged over tasks. For their best function-calling agent, gpt-4o, they report a pass^1 of 61.2% on the retail domain. They also report that pass^8 is below 25% in retail. The same agent solves a task about six times in ten. Yet it rarely solves the same task eight times in a row. The models are from 2024, so read the shape, not the numbers.

Why is pass^8 not just the one-run rate multiplied by itself eight times? Because tasks differ. Some are easy and the agent nearly always gets them. Some are hard. A mix of easy and hard tasks keeps pass^k above the all-equal curve. One illustrative fit uses a 61% average and a 30-point spread. It is not the paper's data.

The lesson for design: do not judge an agent by one run. Run each task several times. If users expect the same request to work every time, pass^k is the number that matches their experience. Pass^k falls fast as k grows.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Low step cap (for example 8) | Bounded cost and time | Hard tasks end early | Tasks are short and well scoped |
| High step cap (for example 50) | Room for long tasks | More cost on stuck runs, more compounding | Open-ended work with a token budget too |
| Token or dollar budget | Direct cost control | Can pass the cap by one response | Any production agent |
| Time deadline | A bounded wait for the user | Cuts good runs short | Interactive use |
| Return partial work on a cap | The user keeps progress | The caller must handle partial results | Almost always |

## Interview lens

<Callout type="tip">
Describe the loop and its exits in one breath: "It is a loop of model call, tool run, append result. The model can stop it, and I stop it with a step cap, a token budget, and a deadline. Each turn resends the history, so cost grows faster than the turn count. Reliability falls as p to the n, so I measure pass^k over repeated runs, not one run." That names the loop, the exits, the cost, and the metric.
</Callout>

<Callout type="mistake">
Do not say "the agent decides when it is done" and leave it there. Say what happens when it never decides. Also do not report one run's success as the agent's reliability. One success tells you almost nothing about the next run.
</Callout>
