## The problem

A chat adds a few hundred tokens per turn. An agent adds far more. The reason is that every step ends with a tool result. The result can be a file, a search page, or a test log. The model reads the whole history on every call, so each step is more expensive than the one before.

Anthropic's multi-agent write-up says agents "typically use about 4× more tokens than chat interactions" ([source](https://www.anthropic.com/engineering/multi-agent-research-system)). Picture a coding agent that reads files and runs tests for two hours. Its window is 200,000 tokens. If it adds 4,500 tokens a step, it hits the wall near step 44, in the middle of the job.

The [Context Window Budgeting](/learn/ai/a4-context/context-budgeting/) lesson taught how to budget a window and why quality drops as it fills (context rot). The [Compaction of Long Conversations](/learn/ai/a4-context/compaction/) lesson taught the three general levers: clear stale tool results, compact, and keep facts in files. This lesson does not repeat them. It covers what is different for an agent that runs a loop for a long time. It also shows how to combine the levers into one design.

## What grows in an agent loop

Each step adds three things: the model's output (reasoning and a tool call), the tool result, and sometimes a note. In the loop from the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson, the whole list is sent again on the next call.

Which part is the largest? No source I could find ranks the parts of an agent's context. So do not assume. Measure it for your agent, by logging tokens per message type. In the examples here I set tool results to 4,000 of 4,500 tokens added per step. That is our assumption, and it fits an agent that reads files. A chatty agent with small tool results will look different.

What the source does say: Anthropic describes context as an "attention budget". The source says "every new token introduced depletes this budget by some amount". Anthropic ties this budget to attention cost: "n² pairwise relationships for n tokens" ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). So the cost of a long run is not only money. A fuller window can also make the model worse at finding the fact it needs.

## Tactic 1: cap what comes in

The cheapest token is the one that never enters. Cap and paginate tool output, and return only the fields the model needs. Claude Code limits tool responses to 25,000 tokens by default, per Anthropic's tool-writing guide. The [Tool-calling Protocol](/learn/ai/a3-llm-apis/tool-calling-protocol/) lesson covers this, and the [Tool Design for Agents](/learn/ai/a6-agents/tool-design/) lesson covers tool design for agents.

## Tactic 2: clear old tool results

Once the agent has used a result, the raw text rarely matters again. Anthropic calls tool result clearing "one of the safest lightest touch forms of compaction". It is safe. The reason is that the data is usually not lost. A file can be read again, and a search can be run again. [Compaction of Long Conversations](/learn/ai/a4-context/compaction/) explained the API feature and its defaults. The design question for an agent is when to clear.

Clear in batches, not on every step. Say your trigger is 100,000 tokens. The agent runs freely up to it, then drops all but the newest few results in one move. This is our reasoning, not a quoted rule: a prompt cache (the [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson) matches an unchanged prefix. Clearing a little on each step would change the prefix on each step. One big clear changes it once and then leaves it stable until the next trigger. Keep the system prompt and tool definitions in front so they stay cached, as in the [Cache-friendly Prompt Layout](/learn/ai/a4-context/cache-friendly-layout/) lesson.

## Tactic 3: notes outside the window

Clearing removes the data. It does not remove the decision you made from the data. If the agent read a 4,000-token config file at step 8, it reached a decision. The decision was "use the adapter pattern". That decision must live somewhere that survives.

Anthropic names the pattern: "Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file". Agents write notes to a file outside the window and pull them back later. In its long-running harness post, Anthropic uses a `claude-progress.txt` file that "keeps a log of what agents have done", plus git history. A new session is told to "read the git logs and progress files to get up to speed". The reason is that "each new session begins with no memory of what came before".

For a backend engineer, this is a write-ahead log and a checkpoint. The window is volatile memory. The notes file is the durable store you replay from. The [Memory](/learn/ai/a6-agents/agent-memory/) lesson covers memory in general. Here the point is narrow: notes are cheap, and they decide what clearing and compaction can safely drop.

## Tactic 4: just-in-time retrieval

You can load everything up front, or keep light identifiers and load on demand. Anthropic calls the second approach just-in-time. The agent keeps "file paths, stored queries, web links". Tools such as glob and grep "allow it to navigate its environment and retrieve files just-in-time". It also uses Bash commands such as `head` and `tail` to look at big data without loading all of it.

The trade-off is speed against tokens. Preloading is one fast step but fills the window with data you may not use. Just-in-time costs extra tool calls, and each call is a model round trip. A path costs a few tokens. The file it points to may cost thousands.

## Tactic 5: send the wide work to a subagent

If a task needs a wide search, do not run it in the main window. A subagent explores in its own window and returns a short summary. Anthropic says the exploration "might use tens of thousands of tokens or more". Anthropic also says the sub-agent "returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". The [Subagents](/learn/ai/a6-agents/subagents/) lesson covers this in full.

## The cost of a long run

Cost is the sum of the context size at every call, not the final size. In the walk above, the plain run resends a bigger and bigger history on each call. It spends most of its input on old results, and it still fails before the task is done. The managed run clears stale results when the context gets large, and keeps the newest few in full. It uses about a third less input, and it finishes. The model is ours: cleared results shrink to a small placeholder, no cache, notes add a little text every few steps. Prices change, so check the current price list.

Notice two things. First, with large tool results the plain run dies early, and clearing is the difference between finishing and failing. Second, with small tool results (size 500) clearing never fires, and it does nothing. Clearing is for the runs that grow.

## Numbers

Think of the window as a bucket. Each turn pours tool results in. With no action, the bucket fills after a modest number of turns. Clearing removes most of each result, so the bucket fills much more slowly. Real agents also carry a system prompt and a reserve for the answer. Clearing is not instant, so the window peaks higher between clears. Treat the gain as an upper bound.

## Trade-offs

| Tactic | You gain | You pay | Choose it when |
|---|---|---|---|
| Cap tool output | Fewer tokens, no later work | The model may need another call | Always; set a cap |
| Clear old results | Large, cheap token cut | Raw data is gone, cache prefix changes | Results are re-fetchable |
| Notes file | Decisions survive clearing | A few tokens, write discipline | Any run with more than one clear |
| Just-in-time loading | Small window, fresh data | More tool calls, more latency | Large or changing data |
| Subagent | Main window stays small | Extra tokens in total (the [Subagents](/learn/ai/a6-agents/subagents/) lesson) | Wide search, clear summary |
| Compaction ([Compaction of Long Conversations](/learn/ai/a4-context/compaction/)) | Frees the most space | Lossy summary, extra model call | Last resort, near the limit |

## Interview lens

<Callout type="tip">
Say it as a budget: "Cost is the sum of context over steps, so I attack growth at four points. I cap tool output, clear stale results at a trigger so the cache prefix stays stable, write decisions to a notes file so clearing is safe, and load files just in time by path. For wide searches I use a subagent. I measure tokens per message type before I decide which one matters."
</Callout>

<Callout type="mistake">
Do not say "tool output is the biggest part of the context" as a fact. It is common in file-reading agents, but you must measure it. Also do not clear results without saving the decisions made from them. And do not pick 200,000 as your working limit: quality can fall well before the window is full.
</Callout>
