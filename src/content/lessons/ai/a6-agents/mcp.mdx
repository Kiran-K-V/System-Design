## The problem

You build an agent app. A customer wants it to read their files, query their database, and file tickets in their tracker. Each of these needs glue code. Each integration needs a tool definition, a way to call the system, and a way to carry its credentials. Now count the pairs. With 5 apps and 8 systems, that is up to 40 custom integrations. Someone writes each one and keeps it up to date.

This is the old N times M problem. The fix is also old. Put a standard between the two sides, so each app speaks the standard once and each system speaks it once. That is what the **Model Context Protocol** (MCP) is. It is an open protocol that connects a model application to tools and data. This lesson uses the spec revision 2025-06-18. A newer revision, 2025-11-25, exists, so check the current spec before you build.

## Messages, not magic

MCP is built on **JSON-RPC**, a request and response format encoded as JSON. The spec calls it "a stateful session protocol focused on context exchange and sampling coordination". If you know gRPC, the shape is familiar. The shape has a method name, parameters, and an id that pairs the answer to the request. It also has notifications that need no answer.

<CrossTrackLink id="02-networking/rpc-grpc">
A remote procedure call hides a network hop behind a function call. The caller names a method and sends arguments. The server runs it and returns a result or an error. Ids pair answers to requests, and timeouts and retries are your job. MCP uses the same idea with JSON-RPC messages.
</CrossTrackLink>

The difference is who the caller is. In MCP, the end of the call chain is a model that writes tool requests as text. So the protocol puts a host between the model and the server, and the host holds the controls.

## Host, client, server

There are three roles, from the architecture page of the spec.

- The **host** is the application the user runs. It "creates and manages multiple client instances", enforces security policy and consent, and coordinates the model.
- A **client** lives inside the host. It "establishes one stateful session per server". Each client has a 1:1 relationship with one server.
- A **server** is a program that offers capabilities. It can be a local process or a remote service.

The spec lists a design principle that matters for safety. Servers "should not be able to read the whole conversation, nor 'see into' other servers." The full conversation stays with the host. Each server gets only what it needs. The host is the gatekeeper between servers.

A server can offer three kinds of things, called primitives. **Tools** are functions the model can call. **Resources** are readable data, such as a file or a record, with URIs. **Prompts** are reusable prompt templates. A client can also offer features back to the server. The capability table in the lifecycle page lists three. One is `roots` (file system roots). Another is `sampling` (the server asks the host for a model completion). The third is `elicitation` (the server asks the user for input). Try the widget. Turn servers on and off, and turn client features on and off.

Notice the last line of the widget. The more servers you connect, the more tool definitions go into every model request. That is the cost from lesson [A6.5](/learn/ai/a6-agents/tool-design/). MCP makes it easy to pay by accident, because connecting a server is one config line.

## Start up, then work

A session has three phases: initialization, operation, and shutdown. The first message must be an `initialize` request from the client. It carries the protocol version, the client's capabilities, and its name. The server replies with its own capabilities. Then the client sends an `initialized` notification. This is **capability negotiation**: both sides state what they support, and "both parties MUST only use capabilities that were successfully negotiated."

<Ai6McpSeq client:visible />

Here is the server's answer to `tools/list`. It is the spec's own example. A tool has a `name`, a `description`, and an `inputSchema` in JSON Schema. It can also carry an optional `title`, an `outputSchema`, and `annotations`.

```json title="tools-list-response.json"
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_weather",
        "title": "Weather Information Provider",
        "description": "Get current weather information for a location",
        "inputSchema": {
          "type": "object",
          "properties": { "location": { "type": "string", "description": "City name or zip code" } },
          "required": ["location"]
        }
      }
    ]
  }
}
```

Compare it to the tool definition in lesson [A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/). It is the same idea with a different key name (`inputSchema`, not `input_schema`). The host converts it to whatever its model API expects. A call and its result look like this:

```json title="tools-call.json"
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } } }

{ "jsonrpc": "2.0", "id": 2,
  "result": { "content": [ { "type": "text", "text": "72°F, partly cloudy" } ], "isError": false } }
```

There are two kinds of error. An unknown tool or bad arguments return a JSON-RPC error, such as code `-32602`. A tool that ran and failed, for example because of an API rate limit, returns a normal result. The result has `isError: true`. The second kind goes back to the model, so write it as lesson [A6.5](/learn/ai/a6-agents/tool-design/) says: with a next step.

## Transports

How do the bytes move? The spec defines two standard transports.

**stdio.** The client starts the server as a subprocess. Messages go over standard input and output, one per line. The server "MUST NOT write anything to its stdout that is not a valid MCP message". Logs go to stderr. The spec says clients "SHOULD support stdio whenever possible." Use it for local tools. The pipe limits access to the one client that started the process.

**Streamable HTTP.** The server runs as its own process with one endpoint that takes POST and GET. It can answer with a single JSON body or open an SSE stream. SSE means Server-Sent Events, a one-way stream from server to client over HTTP. It can assign a session id in an `Mcp-Session-Id` header. This replaced the older HTTP+SSE transport from the 2024-11-05 revision. The spec adds three safety rules for it. Servers MUST validate the `Origin` header, to block DNS rebinding (a trick where a web page reaches a local server). Local servers SHOULD bind to 127.0.0.1, not 0.0.0.0. And servers SHOULD implement authentication.

## Authorization

Authorization is OPTIONAL in MCP. For HTTP transports, the spec bases it on OAuth 2.1 (a token-based authorization standard). The MCP server acts as an OAuth resource server. A client without a token gets HTTP 401. The client MUST use PKCE (a check that stops a stolen authorization code from being used). The client also MUST send the `resource` parameter, so the token is tied to that server. The server MUST accept only tokens issued for itself and MUST NOT pass tokens through to other APIs. For stdio, the spec says not to follow this flow and to take credentials from the environment. Lesson [A7.8](/learn/ai/a7-agents-prod/agent-identity-oauth/) covers agent identity and OAuth in depth.

## Trust: the protocol is not the safety layer

MCP moves tool calls. It does not decide whether a call is wise. The tools page says tools are "model-controlled", so the model can find and call them on its own. Then comes the rule that carries the weight. It says: "there SHOULD always be a human in the loop with the ability to deny tool invocations." Applications SHOULD show which tools are exposed, show when they are called, and ask for confirmation. Clients SHOULD also "show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration".

On tool metadata, the spec is exact. It says: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers." Annotations are optional properties that describe tool behavior. So a hint that says "this tool is read-only" is a claim from the server, not a fact. The servers have duties too: they MUST validate inputs, check access, rate limit, and sanitize outputs.

Local servers carry a different risk. The security best practices page says a local server runs code on the user's machine. Because of that, a bad "startup command" in a config can run anything with the client's rights. Clients that offer one-click setup MUST show the exact command and ask for approval. It also advises sandboxing. Treat a server like a dependency you install: know who wrote it.

The security page lists confused deputy, token passthrough, SSRF, session hijacking, local server compromise, and scope minimization. It does not give hostile tool descriptions a separate name. So this lesson makes no claim about them beyond the rules above.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| MCP server for a system | One integration works in many hosts | Another process to run and secure | Several apps need the same tools |
| Direct tool in your app | Full control, fewer parts | Rewrite for each app | One app, one team |
| stdio transport | Simple, tied to one client | Local only, one process per client | Desktop and developer tools |
| Streamable HTTP | Remote, many clients | Auth, Origin checks, session handling | Shared or hosted servers |
| Many servers in one host | Wide reach | Many tool definitions per request, more risk | Only what the task needs |

## Interview lens

<Callout type="tip">
Say: "MCP standardizes the host-to-tool link. The host runs one client per server. The client and server negotiate capabilities at start. Then the client lists and calls tools over JSON-RPC. I pick stdio for local and Streamable HTTP for remote. Safety stays in the host: confirm risky calls, show inputs, treat annotations and third-party servers as untrusted, and limit which servers connect." That shows protocol knowledge and judgment.
</Callout>

<Callout type="mistake">
Do not say "MCP makes tools safe" or "tool descriptions are trusted". The spec asks for a human in the loop and calls annotations untrusted unless the server is trusted. Also do not connect every server you can find. Each one adds tool definitions to every request, and each one is code that someone else wrote.
</Callout>
