## The problem

Lesson [A6.1](/learn/ai/a6-agents/agent-loop/) gave you the agent loop. The loop is flexible, and that is the trap. Once you can write it, every task looks like an agent task.

But a loop has a cost. Each turn resends the history. Each turn can pick the wrong tool. The path can differ on every run, so you cannot test it with a fixed list of cases. If the path is the same every time, you pay for flexibility you never use.

This lesson separates two designs, gives the five workflow patterns, and gives a rule for choosing.

## Workflows and agents

Anthropic draws one line. **Workflows** are "systems where LLMs and tools are orchestrated through predefined code paths". **Agents** are "systems where LLMs dynamically direct their own processes and tool usage". In a workflow, your code owns the control flow. The model fills in the steps. In an agent, the model owns the control flow.

A backend engineer knows this split. A workflow is a pipeline with a fixed topology, like a job DAG. An agent is closer to a worker that reads a queue and decides what to do next. You can read a pipeline and know what it will do. You can only observe an agent.

The naive design is to make everything an agent. A support bot, a report writer, and a code reviewer all become one loop. The one loop has a long prompt and a tool list. It demos well. Then you cannot say why run 41 took 19 steps and run 42 took 4. You also cannot cap cost with confidence, because the number of model calls is not set by your code.

## Five workflow patterns

The five patterns below come from Anthropic's guide "Building effective agents". Each is a way to arrange model calls so that your code, not the model, decides what runs next. Step through them, then read what each is for.

<Ai6FlowPatterns client:visible />

**Prompt chaining.** Split the task into fixed steps. Each call takes the output of the last. You can add a programmatic **gate** between steps. A gate is code that checks the output and stops early if it is off track. Anthropic says the main goal is to trade latency for higher accuracy, because each call has an easier task. Their examples: write marketing copy and then translate it, or write an outline, check it, and then write the document.

**Routing.** One call classifies the input, and code sends it down one path. Use it when inputs fall into distinct categories that need different handling, and when classification is accurate. Examples from the guide: sort customer queries into general questions, refunds, and technical support. Each category gets its own prompt and tools. Or send easy questions to a small, cheap model and hard ones to a larger one.

**Parallelization.** Independent calls run at the same time and code merges the results. It has two forms. In **sectioning**, each call handles a different subtask. For example, one call answers the user, and another screens the request for policy problems. In **voting**, the same task runs several times. You combine the outputs for higher confidence. For example, several reviewers each check code for a vulnerability.

**Orchestrator-workers.** A central model splits the task at run time and hands the pieces to worker calls, then merges the results. It looks like parallelization, but the key difference is that the subtasks are not predefined. The orchestrator picks them from the input. A coding change that touches a different set of files each time is the standard example.

**Evaluator-optimizer.** One call generates. Another evaluates and gives feedback. The first call revises, and the loop repeats. The guide names two signs of a good fit. One sign is that feedback from a human measurably improves the output. The other is that a model can give similar feedback. Always cap the rounds. Lesson [A6.4](/learn/ai/a6-agents/loop-patterns/) covers this loop in depth.

All five share one property. Your code, or a planning call whose output your code checks, sets the structure. You can draw the graph before the run. Anthropic stresses that these are building blocks, not rules. You can shape and combine them, for example routing into a chain.

## When the path cannot be written

Some tasks do not fit. Anthropic says agents suit open-ended problems where "it's difficult or impossible to predict the required number of steps". Agents also suit problems where you cannot hardcode a fixed path. A coding agent that must resolve an issue in an unfamiliar repository is an example. The agent runs for many turns and you must trust its decisions to some degree. The guide is direct about the price: higher cost and the potential for compounding errors. It recommends extensive testing in a sandbox and guardrails. Lesson [A6.1](/learn/ai/a6-agents/agent-loop/) gave the budgets.

Orchestrator-workers sits between the two. The orchestrator makes one planning decision and the workers run. That is far more bounded than a loop where every turn is a decision.

## How to choose

Three questions decide it.

1. **Predictability.** Can you write the steps down? If yes, write them. A workflow gives you a fixed set of paths to test. A failure points at one box in a diagram.
2. **Cost.** A chain costs the sum of its calls. Parallel voting costs the number of votes. An agent costs a number of turns you do not set, and each turn resends the growing history. Anthropic's guide gives no cost or latency numbers for the patterns, so use your own arithmetic. The chooser below does that under stated assumptions.
3. **Latency.** A chain adds the latency of every step. Parallel calls take about as long as the slowest one. An evaluator loop adds a round trip for each round.

Anthropic's rule is to find "the simplest solution possible, and only increasing complexity when needed". That may mean no agentic system at all. One well-prompted call, with retrieval or examples, often meets the bar. Prove that it does not before you add a loop. Use your evals (lesson [A0.2](/learn/ai/a0-orientation/ai-design-method/)) to decide.

Try the chooser. Set the task traits and see which pattern to try first. Then change the sliders to see the calls and latency of each pattern.

One more warning from the guide. Frameworks make these patterns easy to start. But they "can obscure the underlying prompts and responses, making them harder to debug". Anthropic suggests calling the model API directly first, since many patterns take a few lines of code. If you use a framework, read its code.

## Trade-offs

| Pattern | You gain | You pay | Choose it when |
|---|---|---|---|
| One call | Lowest cost and latency, nothing to debug | May miss the quality bar | Always try first |
| Prompt chaining | Easier steps, gates between them | Latency adds up across steps | Steps are fixed and known |
| Routing | Specialist prompts, cheaper models for easy inputs | A wrong route sends the input to the wrong path | Inputs fall into clear categories |
| Parallelization | Speed, or higher confidence from votes | Cost grows with each branch | Subtasks are independent |
| Orchestrator-workers | Handles subtasks that vary per input | An extra planning call, harder to test | You cannot list subtasks in advance |
| Evaluator-optimizer | Better output when feedback helps | Extra rounds of cost and latency | Clear criteria and measurable gain |
| Agent | Handles open-ended work | Unbounded turns, compounding errors, hard to test | The path cannot be written down |

## Interview lens

<Callout type="tip">
Show the decision, not only the options: "Can I write the steps down? Then it is a workflow. I pick the pattern from the shape. Fixed steps chain, distinct input types route, and independent parts run in parallel. Subtasks that vary per input use orchestrator-workers. I only use an agent when the path cannot be predicted. Then I add a step cap, a token budget, and evals over repeated runs." Name the cost of the agent in the same breath.
</Callout>

<Callout type="mistake">
Do not call a fixed pipeline an agent because a model sits inside it. Also do not reach for a framework before you have written the loop by hand once. And do not answer "agent" to every open question. Interviewers listen for whether you tried the simpler design first.
</Callout>
