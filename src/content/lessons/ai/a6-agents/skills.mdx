## The problem

Your team has an agent that must follow 30 procedures: how to fill a PDF form, how to write a release note, how to run the data-quality checks, and so on. Each procedure is 1,000 to 2,000 tokens of instructions. Where do they live?

The first answer is the system prompt. Paste all 30 in. It works, and it fails in three ways. The prompt is now about 40,000 tokens (30 x 1,300 is our illustrative average). Every request pays for it, though most requests use one procedure or none. The window is crowded, so the instructions that matter compete with 29 that do not. And one team now owns one giant prompt that everyone edits.

You want the agent to hold many procedures and read only the one it needs. A backend engineer knows this shape: an index in memory, the data on disk, a read on a hit.

## What a skill is

A skill is a folder. Per the Agent Skills specification ([agentskills.io](https://agentskills.io/specification), fetched 2026-10-16), a skill contains at minimum a `SKILL.md` file. It may contain `scripts/` (executable code), `references/` (documentation), and `assets/` (templates and data). Anthropic's own description is "At its simplest, a skill is a directory that contains a SKILL.md file".

The `SKILL.md` file starts with YAML frontmatter. Two fields are required:

- `name`: 1 to 64 characters, lowercase letters, digits, and hyphens only. It must not start or end with a hyphen. The name must not have two hyphens in a row. The name must also match the folder name.
- `description`: 1 to 1,024 characters. It should say what the skill does and when to use it.

An optional `compatibility` field takes up to 500 characters, and `allowed-tools` is marked experimental. The Markdown body after the frontmatter holds the instructions. Here is a small one:

```markdown title="pdf-forms/SKILL.md"
---
name: pdf-forms
description: Fills in PDF forms and extracts form fields. Use when the user mentions a PDF form, fields, or signing a PDF.
---

# PDF forms

1. List the fields: run `scripts/list_fields.py input.pdf`.
2. Fill them from the user's data: run `scripts/fill_form.py input.pdf data.json`.
3. For checkbox and date rules, read `references/forms.md`.
```

The `description` is the whole routing signal. The spec's own poor example is `Helps with PDFs.` Its good example names the actions and the trigger words. The model decides whether to use a skill from this text alone. So write the text like an API contract, not a slogan.

## Progressive disclosure

This is the core idea. Skills load in three levels. The spec says metadata is about 100 tokens per skill and is loaded at startup for all skills. The `SKILL.md` body is loaded when the skill is activated. The spec recommends under 5,000 tokens and under 500 lines. Files in `scripts/`, `references/`, and `assets/` load only when required. Anthropic says: "At startup, the agent pre-loads the name and description of every installed skill into its system prompt." The full `SKILL.md` is read only if Claude judges the skill relevant.

Scripts are special. They run, and their code is not read. Anthropic: Claude "can run this script without loading either the script or the PDF into context". A 400-line script costs nothing in tokens. Only what it prints does. It is also deterministic, so the result is repeatable.

## The arithmetic

With 30 skills the startup cost is 30 x 100 = 3,000 tokens. Against a 40,000-token prompt, that is 7.5% of the size. A request that uses one 1,300-token skill adds that body: 4,300 tokens in all. A request that uses none adds nothing.

Now prices. Claude Sonnet 5.5 input costs $2 per million tokens, and a cache read costs 0.05 times that. These prices are as of 2026-10-16 ([claude.com/pricing](https://claude.com/pricing)). Without a cache, 1,000 requests with the 39,000-token prompt cost 39,000 x 1,000 x $2 / 1,000,000 = $78. With skills they cost 4,300 x 1,000 x $2 / 1,000,000 = $8.60. With the big prefix cached, the big prompt costs 39,000 x 0.05 = 1,950 token-equivalents per request. In dollars, that is $3.90 per 1,000. Skills with a cached 3,000-token prefix plus 1,300 uncached cost (150 + 1,300) x 1,000 x $2 / 1,000,000. The result is $2.90.

So caching (lesson [A2.5](/learn/ai/a2-inference-cost/prompt-caching/)) closes most of the dollar gap. Skills still win on the other two problems: window space and attention. A 39,000-token prompt of mixed procedures is a context-rot risk (lesson [A4.3](/learn/ai/a4-context/context-budgeting/)), and it takes room from the work. Try the numbers.

## Skills, tools, MCP, system prompt

These four are often mixed up. They answer different questions.

| Mechanism | What it is | In context | Use it for |
|---|---|---|---|
| System prompt | Text always sent | All of it, every call | Rules that apply to every task |
| Tool | A callable action with a schema (lesson [A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/)) | Its definition, always | One action: search, send, read |
| MCP server | A protocol that serves tools and data from another system (lesson [A6.6](/learn/ai/a6-agents/mcp/)) | Tool definitions, unless loaded later | Connecting a system |
| Skill | A folder of instructions and code | A short description, then the body on demand | A procedure: how to do a job well |

A short way to say it: tools do actions, MCP connects systems, and skills teach a procedure. A skill can use tools and MCP, and Anthropic says it plans to explore how skills "can complement Model Context Protocol (MCP) servers by teaching agents more complex workflows". Its post does not compare skills with subagents. The SDK does show how they meet: an `AgentDefinition` has a `skills` list that preloads skill content into a subagent. The docs say a non-fork subagent does not receive preloaded skill content unless it is listed there. Even so, unlisted skills stay invocable through the Skill tool.

## Using skills in the SDK

In the Agent SDK, skills are files on disk. The SDK has no API to register one in code. It finds them through the `user` and `project` setting sources, for example `.claude/skills/<name>/SKILL.md`. It reads the metadata at startup and loads the full content when Claude invokes the skill. The `skills` option narrows what Claude may invoke: a list of names, `"all"`, or `[]` for none. An unlisted skill returns `Skill <name> is not in this session's skills allowlist`.

Read the next part carefully. The allowlist is not a security boundary. The docs say unlisted skills' files "remain on disk and stay reachable through Read and Bash". If a skill must not be reachable, do not install it in that environment.

## A skill is code: review it

A skill contains instructions and may contain scripts. That is a supply chain. Anthropic's advice: "We recommend installing skills only from trusted sources". The advice also says to audit the bundled code and resources of anything less trusted. The reason is that a malicious skill could introduce vulnerabilities or direct the agent to exfiltrate data. Treat a skill like a dependency: pin it, read it, and review changes. Lesson [A10.4](/learn/ai/a10-safety/tool-permissions/) covers this in the security module.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Everything in the prompt | Always present, no routing step | Tokens on every call, crowded window | Few, short rules that always apply |
| Skills | Small startup cost, shared know-how | A routing step that can miss, files to maintain | Many procedures, few used per task |
| A tool for each procedure | Typed inputs, code runs the logic | Definitions always in context | A single action with a clear schema |
| Script in a skill | Deterministic, code not in context | Needs an environment that runs code | Repeatable steps like parsing and fills |

## Interview lens

<Callout type="tip">
Say it as lazy loading: "A skill is a folder with a SKILL.md. Only the name and description, about 100 tokens each, sit in the system prompt. The body loads when the task matches, and references and scripts load only if needed. Scripts run without their code entering context. I would move rarely used procedures out of the prompt into skills, keep the description specific so routing works, and review skills like dependencies."
</Callout>

<Callout type="mistake">
Do not write a vague description: a skill the model never matches is dead weight. Do not call the allowlist a sandbox. And do not say skills save money in every case. With a prompt cache, the dollar gap is small. The main gain is window space and attention.
</Callout>
