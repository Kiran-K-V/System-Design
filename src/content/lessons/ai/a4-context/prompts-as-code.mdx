## The problem

A support team ships a bot that turns customer emails into a JSON refund ticket. One Friday a user writes in French, and the bot answers in English prose, not JSON. The parser crashes. An engineer opens the prompt, which is now a wall of 900 words, and adds one line: "Always answer in the user's language, keep it short." The French case works.

On Monday, three other kinds of email fail. Long emails come back cut off. Sarcastic ones are tagged as praise. Emails with two requests lose the second. Nobody changed any code. Nobody can say which of the 900 words caused which failure. The fix for one case broke three others. The numbers in this story are an illustration, not data from a real team. The pattern is real, and every prompt that grows by patches meets it.

The cause is that a **prompt** [junior], the text you send to the model, is the contract between your code and a callee that is probabilistic. The callee does not throw an error when you break the contract. It returns a different answer. So you cannot see a break by running the code. You see it only by running cases.

## Naive solution: one long prompt that grows

The first prompt is short and works. Each bug adds a sentence. After 30 patches the prompt holds rules that contradict each other, rules for cases that no longer occur, and a tone nobody chose. Anthropic's context engineering guide gives the target the other way round: aim for "the minimal set of information that fully outlines your expected behavior". It also warns that hard-coding complex, brittle logic into prompts makes them fragile. A patched prompt is the opposite of minimal. (The guide adds that minimal does not mean short: you still give the model enough information up front.)

There is a second trap. A prompt is tuned for one model. Anthropic's prompting guide notes that on Claude Opus 5, verification instructions carried over from prompts for earlier models can cause over-verification, adding tokens and latency, and says to remove them. It also warns that a line such as "If in doubt, use [tool]" causes a tool to be called too often on newer models. So a prompt that was right last year can be wrong after a model change, and you will not know unless you measure.

## The mechanism: split it, version it, test it

**Split the prompt into parts.** Most production prompts have five:

| Part | What it holds | Changes how often |
|---|---|---|
| Role | Who the model is, in one or two lines | Rarely |
| Task | What to do, and what not to do | Per feature |
| Context | Facts for this call: retrieved text, user data | Every call |
| Format | The shape of the reply, such as a JSON schema | Rarely, and with the parser |
| Examples | A few input and output pairs (lesson A4.2) | Per quality fix |

Each part is a small file or a function. The final text is built from a **template** [junior]: a string with named slots, such as `{{ticket_text}}`, that code fills with **variables** at call time. Small parts can be tested one at a time. A change to the format part should not touch the role part.

Put untrusted text, such as the customer email, in a clearly marked slot, for example inside `<email>` tags. Tell the model that this slot holds data, not instructions. This is the basic form of defensive prompting. It does not stop all attacks. The full threat model is in module A10.

**Version the prompt like code.** Store each prompt as a file in git, or in a **prompt registry** [mid]: a service that stores named prompts, keeps every saved version, and lets code fetch a version by name or by a label such as `production`. Langfuse, which offers one, describes its prompt management as covering versioning and labels, caches prompts client-side in its SDK so a lookup is as fast as reading memory, and lets you link prompts to traces to compare performance by prompt version. The rules are the same as for a library:

- Every change is a new version. Never edit a version in place.
- Each deploy **pins** one version. Production runs "v9", not "latest". A rollback is moving the pin back.
- Every request logs the prompt version. When quality drops, the log shows which version served the bad answers.

<CrossTrackLink id="07-reliability/observability">
Logs, metrics, and traces tell you what a running system is doing. For a prompt, add one field to every trace: the prompt version. Without it you cannot tie a bad answer to a change.
</CrossTrackLink>

A registry label is a deploy switch. Moving `production` from v7 to v9 changes live behavior with no code review and no build (this risk is our reading, not a claim from the registry docs). So gate label changes the way you gate a release.

**Review the diff.** A prompt change goes through a pull request. The reviewer reads a text diff, which is small and clear. Then the reviewer reads the **eval diff**: which test cases changed from pass to fail, and the reverse.

**Run a regression eval on every change.** A **regression eval** [mid] is a fixed set of inputs with automatic checks, run on each new prompt version, to catch a change that makes old cases fail. Anthropic's guidance on tests is to favor volume: more cases with slightly noisier automatic grading beat fewer cases graded by hand. It also asks that the set match your real task mix, including edge cases such as overly long input. Its sample code uses a different model to grade than the one that generates, and calls that best practice. Lesson A8.1 covers eval design. Here, treat the eval as the unit test for the prompt.

The gate rule matters. "Total score must not fall" would let a version through that fixes one case and breaks another, as long as the totals are even. "No case that passed may now fail" blocks that, but it can also block a good change that trades away an unimportant case. Pick a rule on purpose, and let a human override it with a written reason. Pick v4, which is the Friday patch from the story. Against v3 it fixes 1 case and breaks 3, and the score falls from 6 to 4. Both gate rules block it. Now pick v5. It fixes the three broken cases by splitting the patch into two rules and adding one example. The score is 7 of 8, and nothing that passed before fails. The eval did the work that nobody could do by reading 900 words.

## Numbers

An eval has a price. Take 200 cases of 2,000 input tokens each: 200 × 2,000 = 400,000 input tokens. At Claude Sonnet 5.5's input price of $2 per million tokens (as of 2026-10-16, [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)), that is 400,000 / 1,000,000 × $2 = $0.80 of input per run, before output tokens and before any grader calls. That is cheap next to one bad release. It is not free, so run the full set on a pull request, and a small smoke set on every commit.

Because outputs vary from run to run, a one-case difference on 8 cases is noise. On 200 cases, a drop of 6 points is more likely to be a real change. A later lesson on evals shows how to size the set and repeat runs.

## Trade-offs

| Option | You gain | You pay | Choose it when |
|---|---|---|---|
| Prompt in app code, no eval | Fastest to start | Silent regressions, no rollback | A prototype only |
| Prompt files in git plus CI eval | Review, history, rollback with the code | A deploy to change a prompt | Engineers own the prompts |
| Prompt registry with labels | Hot swap, non-engineers can edit, version in traces | One more service, and a label change is a deploy | Many prompts, or fast iteration |
| Fine-tune instead of prompting | Shorter prompts, fixed style | Training runs, and the same need to eval | Prompting fails a stable task |

## Interview lens

<Callout type="tip">
Say how a prompt change ships: "Prompts live in git with a version id. Each PR runs a 200-case regression eval. The gate blocks any case that passed and now fails. Production pins one version, and every trace logs it. Rollback is a pin change." Then name the metric: pass rate on the set, and the number of cases that flipped.
</Callout>

<Callout type="mistake">
Do not say "we tested it by trying a few examples". A prompt edit has no compiler. Also do not say "we will tune the prompt until it works" without a fixed test set. You will fix one case, break another, and not know. And do not forget the model: a model upgrade is a prompt change, so run the eval again.
</Callout>
