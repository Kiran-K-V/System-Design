## The problem

A team ships a document assistant. Each request carries tool definitions, system rules, and a 148,000-token contract, followed by one short question. The [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson ([prompt caching](/learn/ai/a2-inference-cost/prompt-caching/)) explained why this is a good fit for a prompt cache. The long part repeats, so the provider can store its work and charge a small read price. The team turns caching on. The bill does not move.

Nothing is broken. The cache is on. Every request still misses. Someone added the current time to the first line of the system rules. This lesson is not about prices or break-even. [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) covers those. It is about **layout**: the order of the parts of a prompt, and which edits kill a cached prefix.

<CrossTrackLink id="05-caching/cache-strategies">
A cache is only useful when a key repeats. In a key-value cache you control the key. In a prompt cache, the key is the exact beginning of your prompt. So you control it only through how you build the prompt. A small change to the key is a miss.
</CrossTrackLink>

## Why only a prefix counts

A **prefix** is the start of a prompt, from the first token up to some point. A provider's cache matches whole prefixes. It cannot reuse a block from the middle of a prompt. The reason is that the model's stored work for a token depends on every token before it. The OpenAI guide puts it this way: "Cache reuse requires the entire rendered prefix to match." If one early token changes, all later stored work is useless.

So the layout rule is plain. Put the parts that never change first. Put the parts that change last. The order in a stable prompt, most stable first, looks like this:

1. Tool definitions.
2. System rules.
3. Few-shot examples and reference documents.
4. Conversation history, which grows only at the end.
5. Per-user data, the current time, and the new question.

Anthropic builds the prefix in a fixed order: `tools`, then `system`, then `messages`. A cache entry covers everything "up to and including the block designated with `cache_control`". A **breakpoint** is that `cache_control` marker. You can set up to 4 breakpoints per request. Automatic caching, a single top-level `cache_control` field, uses one of those 4 slots. If 4 explicit breakpoints already exist, the API returns a 400 error.

## What kills a cache

Anthropic's docs state a general rule: "Changes at each level invalidate that level and all subsequent levels." Read the order again: tools, system, messages. A change in tools breaks all three. A change in the system block breaks system and messages. A change in a message breaks only the messages from that point on. The docs list these causes:

| Edit | What it breaks | Why |
|---|---|---|
| Change a tool name, description, or parameter | Everything | Tools come first |
| Toggle web search or citations | System and messages | Each toggle changes the system prompt text |
| Change the effort or thinking setting | Message blocks | The setting is part of the rendered prompt |
| Add or remove an image anywhere | Message blocks | Images are part of messages |
| Change `tool_choice` | Message blocks only | Tools and system stay valid |
| Timestamp or per-user text early in the system prompt | System and messages | The text differs on each request |
| Reorder blocks | Everything from the first moved block | The prefix no longer matches |

Two more rules bite in real systems. First, the lookback: on each breakpoint the system checks at most 20 positions back for an earlier entry. A long conversation that adds many blocks between requests can walk past its own last write. Put a breakpoint in the right place, not only at the end. Second, a prompt shorter than the minimum is not cached, and no error tells you. On Sonnet 5.5 the minimum is 512 tokens (as of 2026-10-16, [prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Other models use 1,024, 2,048, or 4,096. Check the response fields `cache_creation_input_tokens` and `cache_read_input_tokens`. They are the only honest signal.

<Ai4CacheLinter client:visible />

What to notice:

1. **Start state.** The cached prefix is only tools and system rules, because the time block is third. The big document sits after it, so it pays full price on every request. The cache is on, and it saves almost nothing.
2. **"Sort: stable first".** The prefix now covers the document too. Only the small volatile blocks pay full price. The cost per request falls by a large factor.
3. **Order inside the stable group does not matter.** Drag the document to the top of the start state. The prefix grows to cover the document, tools, and system rules. Only the position of the first volatile block counts. (On the real Anthropic API the order tools, system, messages is fixed by the request format. The toy ignores that.)
4. **Between volatile blocks.** Order among the time, the profile, and the question changes nothing. They all pay full price.

## Worked example: 20 questions on one document

A user asks 20 questions about one long document, a few minutes apart. Without a cache, each question sends the whole document at the full input price. With a cache, the first question writes the prefix at a small premium. Every later question reads it at a deep discount. Prices are on the [Anthropic pricing page](https://platform.claude.com/docs/en/about-claude/pricing), and they change. The [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson covers the economics and break-even.

The write premium is paid back by the first read. After that, each question is far cheaper than the uncached version. The saving holds only if each next question arrives within the cache lifetime, which is 5 minutes by default. Each use refreshes it at no cost, so steady traffic keeps the entry alive. After a quiet gap, the next question pays the write again.

## OpenAI: the same idea, with fewer knobs

OpenAI caches automatically for supported models. The [prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) (as of 2026-10-16) says the minimum cacheable prompt is 1,024 tokens for GPT-5.6 and later. The default retention is 30 minutes. Cache reads cost 0.1 times the uncached input price on most of these models. On GPT-6.1 Sol, the cache read costs 0.05 times the uncached input price. Writes cost 1.25 times. In the default implicit mode the system places the breakpoints, at the end of the latest eligible message. Explicit mode, where you mark them, exists on GPT-5.6 and later only. For earlier models, the minimum length varies with request settings, so read the guide for your model.

The layout advice matches Anthropic's. The guide says to put stable developer instructions and shared reference material first. It says to put dynamic content last: timestamps, user details, and the current question. Append new messages. Do not rewrite earlier turns. The usage field `usage.input_tokens_details.cached_tokens` reports how many tokens hit. On earlier models, a `prompt_cache_key` helps route related requests to one cache. But the guide says keys "do not pin requests to a machine or guarantee a cache hit". Treat a hit as likely, not certain.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Static first, dynamic last | High hit rate, stable cost | Dynamic data sits far from the top of the prompt | Always, for any prompt over the minimum length |
| One breakpoint after the shared prefix | Simple, one write | A change in the prefix rewrites all of it | A single document or fixed instructions |
| Several breakpoints (up to 4) | A change late in the prompt keeps earlier parts | More writes, a slot budget | Tools, system, document, and history change at different rates |
| Frozen tool list | A stable first block | You cannot tune tool text freely | Production traffic with a stable tool set |
| Time or user data in the last block | Full prefix reuse | The model sees that data late | The data does not need to shape the early instructions |

Layout rules also help with correctness. A cached prefix is the same bytes on every request. So a prompt change is a deploy. Version it (the [Prompts as Versioned Code](/learn/ai/a4-context/prompts-as-code/) lesson), and watch the hit rate after you ship.

## Interview lens

<Callout type="tip">
Say it as a rule and a metric: "I keep the prompt in stable-to-volatile order. So tools, system rules, and documents come first, and the time, user data, and the question come last. I log cache read tokens divided by total input tokens per route, and I alert when it drops." Naming the metric shows you know a cache can fail silently.
</Callout>

<Callout type="mistake">
Do not say "we turned on caching, so it is cheaper". Caching is a property of the layout, not a switch. Also do not put a timestamp, request ID, or user name at the top of the system prompt. Even when you add them "for context", keep them out. If the model must know the time, say so in the last block.
</Callout>
