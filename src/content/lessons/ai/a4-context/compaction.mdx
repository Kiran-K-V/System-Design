## The problem

A coding agent has worked for two hours on a refactor. It has read 40 files and run the tests 15 times. The context holds 150,000 tokens and the window is 200,000. At 6,000 tokens a turn it has about 8 turns left. The refactor needs 30 more.

Lesson A4.3 listed the choices: append forever, drop old turns, or shrink the history. This lesson is about shrinking it well. The goal is to keep what the task needs and drop what it does not, at a cost you can state.

## Naive solutions

**Cut the oldest turns.** This is a sliding window. It is simple and predictable. It also deletes the early turns that hold the task goal, the user's rules, and the decisions made so far. The agent then repeats work or contradicts a past decision.

**Stop and start over.** Clear the chat and begin a new session. The agent loses all state and must rediscover it. For a two-hour task that is a large loss.

Both treat all tokens as equal. They are not. A decision ("we use the adapter pattern, not inheritance") is worth far more per token than the 4,000-token output of a test run that passed 20 turns ago.

## The mechanism: three levers

There are three tools. They go from cheap and safe to costly and lossy, and from client-side to server-side. Use them in that order.

**Lever 1: clear stale tool results.** Old tool output is the safest thing to remove. Anthropic's context engineering guide calls tool result clearing the "safest lightest touch" form of compaction. Anthropic's **context editing** [mid] feature does this by rule: once the prompt passes a trigger, the API removes the oldest tool results and keeps the most recent ones. The strategy `clear_tool_uses_20250919` (a beta feature, as of 2026-10-16) has these defaults in the docs: a trigger of 100,000 input tokens, and the 3 most recent tool uses kept. A cleared result is replaced by placeholder text that tells the model it was removed. You can exclude tools whose output must stay, and set a minimum amount to clear. The tool inputs, meaning the calls themselves, stay unless you turn on clearing for them. Source: [context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing).

**Lever 2: compaction.** **Compaction** [mid] replaces the older turns of a conversation with a summary that the model writes. Anthropic's compaction docs say the summary is written on the server, so you need no summarizer code. With the token-threshold form, the API watches the input size. Per the docs (as of 2026-10-16), the default trigger is 150,000 input tokens, the value must be at least 50,000, and `input_tokens` is the only trigger type. When the trigger fires, "the API automatically drops all content blocks prior to the `compaction` block, continuing the conversation from the summary". The docs also describe an on-demand form where your application decides when to compact. Both are beta features, so check the page before you build on them: [compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), [at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold).

Two details change the design.

- **Recent turns.** The threshold form does not keep recent turns by itself. The docs show a `pause_after_compaction` option: the API stops after it writes the summary, and your code adds the last few messages back after the compaction block. Recent turns stay word for word, and old turns become prose.
- **Cost.** Compaction is an extra model call. The docs say the top-level `usage` numbers do not include it, and you must add up the `usage.iterations` entries to see the true bill.

Claude Code and the Agent SDK compact for you when the window nears its limit. The Agent SDK docs say it keeps recent exchanges and key decisions, and emits a `compact_boundary` message when it happens. They also say that "specific instructions from early in the conversation may not be preserved", and that persistent rules belong in CLAUDE.md, which is re-injected on every request.

**Lever 3: files outside the window.** Write durable facts to a file, and read them back when needed. The memory tool does this: the docs describe a directory of memory files that your application stores, and say that memory "preserves the information that must survive summarization". A progress log, a decisions list, and a checklist are typical. Also keep the raw transcript in your own storage. If the summary loses a fact, you can find it.

## What is kept, and what is lost

Anthropic describes what Claude Code keeps: "architectural decisions, unresolved bugs, and implementation details". It drops "redundant tool outputs or messages", and after compaction it continues with "the five most recently accessed files". The guide's tuning advice is "Start by maximizing recall", meaning capture everything that might matter, and only then raise precision by removing noise. An aggressive summary can drop a detail whose value shows only later.

That is the quality risk. A summary is lossy compression. Typical losses are an exact error string, a file path read at turn 4, a number from a table, and a rule the user stated once. You cannot see the loss in the summary, because you do not know what the later task will need. Three defenses help.

- Put rules and facts that must survive into a file that is re-read, such as CLAUDE.md or a memory file. Do not leave them only in the chat.
- Give the summarizer instructions on what to keep. The compaction API has an `instructions` parameter, and Claude Code reads a "summary instructions" section in CLAUDE.md.
- Test it. After a compaction, ask a question that needs an early fact. Count how often the agent gets it right on your task set. A fact that is lost 1 time in 10 is a real bug in a task with 10 compactions.

## Compaction and the prompt cache

A cached prefix works only if the start of the prompt is unchanged. Compaction rewrites the history, so the prefix changes. OpenAI's caching guide says compaction "can prevent reuse from the first changed token onward", and notes that the first request after compaction may reuse less of the cache. It also advises comparing total input cost before and after, because "fewer input tokens can still save money even when the cache-hit rate falls". Keep the system prompt and tool definitions stable and in front. Then only the history part of the cache restarts. Lesson A2.5 has the cache mechanics.

## Numbers

The window is 200K and compaction fires at 150K. The history of 150K tokens becomes an 8K summary. How many turns fit before the window fills again, at 6K per turn?

<Math block tex="\text{turns} = \left\lfloor \frac{200{,}000 - 8{,}000}{6{,}000} \right\rfloor = \left\lfloor 32.0 \right\rfloor = 32" />

In words: the room left after the summary, divided by tokens per turn. But the trigger fires at 150K, not at 200K, so the next compaction comes sooner: (150,000 - 8,000) / 6,000 = 23.7, after about 24 turns. A long task is a saw-tooth: climb, drop, climb. Over 24 turns you also pay the summary call once.

What does that call cost? It reads about 150,000 input tokens and writes 8,000 output tokens. At Claude Sonnet 5.5 prices of $2 per million input and $10 per million output (as of 2026-10-16, [pricing](https://platform.claude.com/docs/en/about-claude/pricing)), that is 150,000 / 1,000,000 × $2 = $0.30 plus 8,000 / 1,000,000 × $10 = $0.08, so about $0.38, ignoring cache. In return, every later turn reads 142K fewer tokens.

The simulator below uses these round numbers. Its model is ours: each turn adds a fixed number of tokens, a share of them is tool results, clearing removes tool results from all but the last 3 turns, and compaction replaces everything with the summary. A cleared result counts as zero tokens, while the real placeholder costs a few. Turn clearing on, and watch the compaction events become rarer.

## Trade-offs

| Lever | You gain | You pay | Choose it when |
|---|---|---|---|
| Clear old tool results | Large saving, little risk | The agent cannot re-read the cleared output | Tool output is bulky and old |
| Compaction | Unbounded chat length | A model call, lost detail, a cache restart | Long tasks with many turns |
| Memory files | Facts survive any summary | File reads, storage to manage | Facts must last across summaries or sessions |
| Sliding window | No extra call | Early goals and rules vanish | Short, shallow chats |

## Interview lens

<Callout type="tip">
Describe the order: "At 100K I clear old tool results, keeping the last 3. At 150K I compact into an 8K summary and keep the last few turns verbatim. Rules and decisions live in a memory file that is re-read, and the raw log goes to storage." Then say how you test it: a question per early fact after each compaction.
</Callout>

<Callout type="mistake">
Do not say "we summarize when the window is full". At the limit there is no room to run the summarizer, and the summary call itself must fit. Trigger early. Also do not rely on the summary to carry a hard rule. Put hard rules in a file that is re-injected on every request.
</Callout>
