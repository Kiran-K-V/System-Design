## The problem

Your product sends each user question to a **model provider**: a company that runs large language models and lets you call them over an API. Your code looks like `answer = provider.generate(prompt)`. You do not run the model. You rent it.

Renting has a cost. When the provider is down, your product is down.

This happens to the biggest providers. On 11 December 2024, OpenAI's API, ChatGPT, and Sora all failed. OpenAI's own incident report puts the outage between 3:16 PM and 7:38 PM Pacific time. That is 4 hours and 22 minutes in which every one of those products was broken.

Your gateway from [lesson A3.8](/learn/ai/a3-llm-apis/multi-provider-gateway/) can send a failed call to a second provider. That lesson showed the mechanism. This lesson asks harder questions about it:

1. Which failures are worth switching for, and which are not?
2. What does a backup have to be, before the day you need it?
3. Will the backup give answers your product can still use?
4. What does the switch cost?
5. What if the switch itself breaks?

## Question 1: when a call fails, should I retry or switch?

Every HTTP response carries a **status code**, a number that says how the call went. 200 means success. A code from 400 to 499 means the caller did something wrong. A code from 500 to 599 means the server did.

Three LLM-specific cases need names.

- A **rate limit** is a cap on how much you may use per minute. The provider counts requests and tokens. Go over, and you get status **429**. A token is a small piece of text, roughly three quarters of a word. It is the unit that LLM providers count and bill.
- **Overload** means the provider as a whole has too much traffic. Anthropic's error page says its **529** `overloaded_error` "can occur when the API experiences high traffic across all users". The problem is theirs, not yours.
- A **spend cap** is a monthly limit on money. Anthropic gives each usage tier a cap: $500 on the Start tier, $1,000 on Build, and $200,000 on Scale. When you reach it, calls stop until the first day of the next month.

Now the trap. The spend-cap failure also arrives as a **429**. It looks like a rate limit. But a rate limit clears in seconds, and a spend cap does not. A rate-limit 429 usually carries a `retry-after` header: a number of seconds to wait. Anthropic's rate-limits page says the spend-cap 429 has no `retry-after` header, and "retrying, including the SDK's automatic retries, fails until access resumes." The official SDK retries twice by default. For a spend cap, both retries are wasted. The error body also carries the code `enforced_spend_limit_reached`, so your router can tell the two cases apart.

A different cap works another way. If you set your own spend limit below the tier cap, Anthropic returns status 400, not 429. Failing over on that error would defeat the limit you set on purpose. It needs a human, not a switch.

One more trap: a failure can come after the success code. With **streaming**, the provider sends the answer in pieces as the model writes it. It sends the 200 first. A failure in the middle arrives as an error event inside the stream. Anthropic's streaming docs show an `overloaded_error` arriving this way. So "I got a 200" does not mean "the answer is complete".

Here is the decision table that follows from these facts.

| What you see | What it means | Retry the same provider? | Switch to a backup? |
|---|---|---|---|
| 429 with `retry-after` | Rate limit. It clears in seconds | Yes, after the wait | Only if the wait is longer than your time budget |
| 429 with no `retry-after`, and a spend-cap code | Monthly cap reached. It does not clear | No | Yes, and page a human to raise the cap |
| 400, message "reached your specified API usage limits" | Your own spend limit | No | No. A human decides |
| 529 | Provider overloaded | A short backoff, once or twice | Yes |
| 500, 504, connection drop | Provider fault or timeout | Backoff, then yes | Yes |
| Other 400 | Your request is wrong | No | No, a backup rejects it too |
| Error event inside a 200 stream | Failed mid-answer | Restart, do not append | Yes, and discard the partial text |

The last row has a rule: never glue the backup's answer onto half of the primary's. Start the answer over.

## Question 2: what does "switch" mean, and what must the backup be?

Think of a building with a backup generator. When the power goes out, the generator takes over. Nobody notices, if the generator was tested.

In software, this is **failover**: moving traffic to a backup when the primary fails. You met it in the [replication lesson](/learn/backend/04-data/replication/), where a database promotes a follower to leader.

<CrossTrackLink id="04-data/replication">
When a database leader dies, a follower is promoted. The hard parts are detecting the failure (a dead leader looks like a slow network), choosing the best replacement, and stopping the old leader from coming back and acting as if nothing changed. A provider failover has the same three parts, with different names: detect, choose, and stop the old path from being used too early.
</CrossTrackLink>

There are two ways to keep a backup.

- **Warm standby.** The backup takes no normal traffic. It waits. Like the generator, it costs little. It is also untested in daily life, and its caches are empty.
- **Active-active.** Both providers take live traffic all the time, for example 95% and 5%. Both are always exercised, so you learn quickly if one breaks. You pay a bit more complexity.

Why does this choice exist? You want two things that pull against each other: low cost in normal days, and a backup you can trust on a bad day. A standby is cheap and unproven. A shared load is proven and a little more work.

How do you measure the result? With an **RTO**, a recovery time objective. It is the longest time you accept between "the primary failed" and "users get answers again". For a support bot, that might be 30 seconds. For a nightly batch job, it might be hours. The RTO decides how much you spend, because a short RTO needs a backup that is always ready.

Numbers make the RTO concrete. Say each attempt waits up to 30 seconds before it times out. The SDK retries twice. That is 3 attempts, so 3 x 30 = 90 seconds of waiting before you even start the backup. An RTO of 30 seconds cannot work with those settings. You need a shorter timeout on the first piece of the answer. This is the **time to first token (TTFT)**: how long until the first words arrive. With streaming you can say "if no first token in 5 seconds, give up on this attempt". Lesson A9.7 teaches TTFT in depth.

## Question 3: will the backup give answers my product can use?

The backup is a different model, from a different company. It was trained differently. Your prompt was tuned for the primary. So the backup may answer in a different length, tone, or format.

Four things can change. Treat each as a test you run before the outage.

**Quality.** The same question may get a worse answer. You measure this with a **golden set**: a fixed list of test questions, each with a known good answer or a check. [Lesson A8.3](/learn/ai/a8-evals/golden-sets/) builds one. Run the golden set on the backup, and write down the score next to the primary's. Say the primary scores 0.90 and the backup scores 0.84 (illustrative). Now you know the cost of switching: 6 points. You can decide if that is acceptable, or if the backup should only serve some tasks.

**Format.** Your code probably parses the answer as JSON with fixed field names. A backup might wrap the JSON in a markdown code fence, rename `amount_cents` to `amountCents`, or return the number `1250` as the string `"1250"`. The HTTP code is still 200. Your parser fails, and the failure shows up far from the cause. A gateway vendor's blog post lists exactly these drifts, but gives no measurements. Treat it as a sensible warning, not a statistic. The fix is a **schema check** in the router: validate every answer against the expected shape, and count the failures per provider. [Lesson A3.3](/learn/ai/a3-llm-apis/structured-output/) covers structured output.

**Request settings.** Providers differ in what they accept, and so do models from one provider. Anthropic's error docs show that Claude Opus 5.5 and Sonnet 5.5 reject a forced tool choice with a 400. Models from version 4.6 up reject a prefilled assistant message. So a request that works on the primary can fail on a backup, and the other way round. Keep one request builder per target, and test each one.

**Side effects.** Suppose your agent calls a `refund` tool, and then the provider fails before the answer is written. A naive router retries the whole request on the backup. The backup sees no refund in its context and calls `refund` again. The customer is refunded twice. The defence is an **idempotency key**: a unique id sent with each action, so the system does the action once even if it is asked twice. [Lesson A3.6](/learn/ai/a3-llm-apis/limits-retries-idempotency/) covers it.

## Question 4: what does the switch cost?

You pay twice: in tokens and in speed.

The cost comes from the **prompt cache**. Most prompts start with the same long block: instructions, tool definitions, documents. A provider can store the processed form of that block, so the next call that begins with the same block costs much less. [Lesson A2.5](/learn/ai/a2-inference-cost/prompt-caching/) explains how. The saving is large. On Anthropic's pricing page, a cache hit on Sonnet 5.5 costs $0.10 per million tokens, against $2 for normal input. That is 20 times cheaper.

The cache lives inside one provider. Anthropic's docs say caches are isolated between organizations and, on its own API, between workspaces. So after a failover, the backup starts with an empty cache. The first requests pay full price for the long block. They also pay the cache-write premium: 1.25 times the input price, to store it.

Now the surprise. Each model also has a **minimum**: the shortest block it will cache. A block below the minimum is processed at full price, and Anthropic's docs say "no error is returned". The minimums differ by model: 512 tokens for Sonnet 5.5 and Haiku 5.5, 1,024 for Sonnet 4.6, and 4,096 for Haiku 4.5. Take a prompt with an 800-token repeated block. On Sonnet 5.5 it caches. On Sonnet 4.6 it never does. The bill nearly doubles, and no log line says why.

Try it. Change the repeated block and watch which backup stops caching.

At 800 tokens, the primary Sonnet 5.5 costs $0.00468 per request. The backup Sonnet 4.6 costs $0.0093: 1.99 times as much. Part of that is the higher price per token ($3 against $2). The rest is the cache that never starts. Move the slider to 1,100 tokens, and the backup caches. Then the gap shrinks to about 1.5 times.

## The naive way: retry harder, or switch blindly

Two designs are common, and both fail.

The first is **retry harder on one provider**. It treats every error as temporary. During a real outage, retries pile on top of an overloaded service. During a spend cap, every retry is certain to fail. Users wait through the full timeout on every attempt.

The second is **switch on any error, and trust the result**. It sends every failure to the backup. It never asks if the backup is any good. A bad request gets rejected twice. A format change breaks downstream code. A tool call repeats an action. And the bill grows with no error to explain it.

Both designs have the same flaw: they decide from the status code alone. The real fix decides from the kind of error, a time budget, and tests run in advance.

## The real fix: five ideas

### Idea 1: decide by error kind and by clock

The table in Question 1 is the rule. Put it in code, not in a person's head. Each attempt has a short limit on TTFT, and the router keeps a running clock for the whole request. When the clock says "there is no time for another retry", it goes to the backup. This turns the RTO from a hope into a number you can compute.

### Idea 2: open the switch, probe, then ramp back

Retrying a provider that is down only makes the queue longer. A **circuit breaker** is a switch that stops calls to something that keeps failing, then tests it with one call later. The [circuit breaker lesson](/learn/backend/07-reliability/circuit-breaker/) teaches it. The same logic fits here: after N failures in a row, open the switch. Send everything to the backup. After a pause, send one test request to the primary. If it works, bring traffic back in small steps.

Notice the last step. The router does not return all traffic at once. The reason is in Anthropic's docs: a sharp rise in usage can trigger a 429 from "acceleration limits". The docs say to "ramp up your traffic gradually". That rule applies to your backup as well. If you move 100% of traffic to a provider that has seen 0%, you may hit its acceleration limits.

### Idea 3: prove the backup before the outage

A backup you have never run is a hope. Run these checks on a schedule, not on the day:

- the golden set, on every backup, with a minimum score you wrote down;
- one real request per target per day, using the exact request builder, to catch rejected settings;
- the schema check on every answer, with a counter for failures.

Cost check, derived: a 500-case golden set with 3,000 input tokens and 500 output tokens per case, run on Sonnet 4.6 at $3 and $15 per million tokens, costs 500 x (3,000 x 3 + 500 x 15) / 1,000,000 = $8.25 per run. A weekly run is about $33 per month. That is small next to a 4-hour outage.

### Idea 4: keep a trickle on the backup

A warm standby has empty caches and no real traffic. Send it a small steady share, such as 5%. Four things happen. The backup's prompt cache stays warm. Its rate limits are exercised. Its quality shows up in your real traffic. And when you do switch, the jump is from 5% to 100%, not from 0% to 100%.

There is a catch. The cache lifetime is 5 minutes by default, and each use refreshes it. If a prefix is used less than once in 5 minutes, it expires every time. Then every request pays the write price of 1.25 times, and none gets the 0.1 times read price. A trickle must be steady enough to keep the cache alive, or it costs more than it saves.

### Idea 5: keep the switch independent of what failed

The OpenAI report is a lesson in this. A new telemetry service put heavy load on the **control plane** of their Kubernetes clusters. The control plane is the part that manages and configures the system. The **data plane** is the part that serves requests. The report says the fix required removing the bad service, and removing it needed the control plane, which was overloaded. Engineers could not reach what they needed to repair.

Your equivalent: the place where you flip the failover switch must not depend on the provider that is failing. If your feature flags, your config store, or your dashboards live on the same provider, you may be unable to change the route in an outage. Keep a local config file the router can read, and a manual override that works from a laptop. OpenAI's own listed fixes include "break-glass access", a way in that works when everything else does not.

One more point on regions. You might think moving to another region adds capacity. Anthropic's rate-limits page says limits are shared across `inference_geo` values, so switching geography on the same account does not add headroom. It also may break a data residency promise. Check both before you rely on a region switch.

Your design should name its three bars. **Quality bar:** the backup scores at least a stated number on the golden set. **Latency budget:** first token within 5 seconds, and total time to a working answer within your RTO. **Cost:** compute the per-request cost on the backup, cold and warm, as the widget does.

## Trade-offs

| Design | You gain | You pay | Choose it when |
|---|---|---|---|
| One provider, retries only | Simplest. One prompt to tune | A provider outage is yours. Spend caps stop everything | Internal tools where hours of downtime are fine |
| Warm standby, tested weekly | Low cost. A backup exists | Cold cache on the switch, a quality gap, a 0 to 100% jump | A support bot with an RTO of minutes |
| Active-active, 95 / 5 | Warm cache, real quality data, a smaller jump | Two sets of prompts and tests. Cache is thin at low traffic | Revenue-critical paths |
| Self-hosted model as backup | Independent of any provider's capacity | You run GPUs. Usually lower quality | Strict data rules, or when no second provider is allowed |

## What experienced teams know

1. **A spend-cap 429 never clears, and your own limit is a 400.** The Anthropic docs say the cap has no `retry-after` and "keeps failing until access resumes". Route it as "fail over and page a human", never as "retry". And do not fail over on your own spend limit: it would defeat the limit. ([Anthropic rate limits](https://platform.claude.com/docs/en/api/rate-limits))
2. **A 200 is not a success.** Streams can fail after the 200, so handle the error event and restart the answer. Then validate the shape of every answer. Count schema failures per provider, because a quiet format drift is the common way a failover "works" and breaks the app. ([Anthropic streaming docs](https://platform.claude.com/docs/en/build-with-claude/streaming), and a [vendor post on format drift](https://dev.to/kuldeep_paul/every-way-llm-provider-failover-breaks-in-production-3lao) that has no measurements)
3. **Each model accepts different settings.** A forced tool choice is rejected on Opus 5.5 and Sonnet 5.5. A prefilled reply is rejected from 4.6 up. Use one request builder per target, and send one real request to each target every day. ([Anthropic error docs](https://platform.claude.com/docs/en/api/errors))
4. **Check cache minimums before you pick a backup.** Below the minimum, nothing is cached and no error appears. The same 800-token prefix caches on Sonnet 5.5 and not on Sonnet 4.6, and the cost per request nearly doubles. ([Anthropic caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))
5. **Never cut over 0% to 100%.** A sharp usage increase can trigger a 429 on the backup too. Keep a steady trickle, and ramp in steps. ([Anthropic errors page, acceleration limits](https://platform.claude.com/docs/en/api/errors))
6. **Keep the switch off the failing path.** In OpenAI's December 2024 outage, the fix needed the control plane that was down. Put the failover switch somewhere that survives your primary's failure. ([OpenAI incident report](https://status.openai.com/incidents/01JMYB483C404VMPCW726E8MET))

## Interview lens

<Callout type="tip">
Say: "I sort errors by kind. Rate limits wait, overload and 5xx switch, a spend cap pages a human. The backup has its own golden set score, a schema check, and a daily request test. It gets about 5% of traffic so its cache and limits are warm. A circuit breaker opens after N failures, and traffic ramps back in steps." That covers detection, quality, cost, and recovery in four sentences.
</Callout>

<Callout type="mistake">
Do not say "we have a fallback model, so we are covered". A backup that was never evaluated is a second way to fail. And do not quote an uptime number for the backup that you did not measure. Say how you test it, and how often.
</Callout>
