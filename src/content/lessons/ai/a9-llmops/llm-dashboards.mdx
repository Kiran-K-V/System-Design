## The problem

It is Friday afternoon. Your LLM dashboard shows uptime at 100%. The error rate is 0%. GPU utilization is 95%. Tokens per second just set a record.

The support channel says: "The assistant is so slow today."

Every number on the dashboard is true. The dashboard is still wrong, because it measures how busy the machines are. Users care about something else: how long they wait, whether the answer is good, and what it costs you.

A dashboard for an LLM system must answer questions a normal web dashboard never asked. Here are the five this lesson works through:

1. What does "slow" mean for a model call?
2. When does a request count as "good"?
3. Why does GPU utilization mislead?
4. How can cost double while nothing errors?
5. When should a number wake someone up?

## Question 1: what does "slow" mean for a model call?

A normal web request has one clock: start to finish. A model call has two. Think of a restaurant. You wait for the first dish to arrive. Then you wait between courses. A restaurant can be fast at the first and slow at the second, or the other way round.

The model writes its answer one **token** at a time. A token is a small piece of text, about three quarters of a word. The server can send each token as soon as it is ready. That is called streaming, from [the Streaming Responses lesson](/learn/ai/a3-llm-apis/streaming/). So you can time two things.

- **TTFT** is the *time to first token*: how long until the first words reach the user. It decides whether the product feels responsive. Databricks, which publishes detailed measurements of LLM serving, says TTFT is "how quickly users start seeing the model's output after entering their query".
- **TPOT** is the *time per output token*: the pause between tokens after the first. It decides how fast the answer feels as it appears. Databricks defines it as the "time to generate an output token for each user".

Why two clocks and not one? Because the model does two different jobs. First it reads your whole prompt in one big pass. Then it writes the answer one token at a time. [The Prefill vs Decode: TTFT and TPOT lesson](/learn/ai/a2-inference-cost/prefill-decode/) explains why the first job is limited by compute and the second by memory speed. Each job breaks in its own way.

The two clocks combine into one idea, from the same Databricks post: the whole request takes TTFT, plus TPOT for every output token. For a long answer, the start is a small part of the total. Most of the time is the writing.

That points to a surprising fact. Databricks tested MPT models and reports: "The addition of 512 input tokens increases latency less than the production of 8 additional output tokens." Output tokens are the expensive ones for time. So an answer that grows from 200 to 400 tokens costs you more time than a prompt that grows by a few hundred tokens. Watch the length of answers.

You also need to read these numbers as **percentiles**. Sort 100 request times from fastest to slowest. The **p95** is the 95th one: 95 of 100 requests are faster than it. It shows how bad the slow tail is. An average hides the tail. If most requests are fast and a few are very slow, the average still looks fine. The p95 shows the slow ones. Users in the slow tail are very unhappy, and the average does not show it.

## Question 2: when does a request count as "good"?

A factory counts the items that pass inspection, not the items that leave the line. A line that makes 100 items an hour and ships 60 broken ones is worse than a line that makes 50 good ones.

LLM serving has the same idea. **Throughput** is how many requests the system finishes per second. **Goodput** is how many requests per second finish *and meet your latency targets*. The DistServe paper (OSDI 2024) defines it per GPU: "the maximum request rate that can be served adhering to the SLO attainment goal (say, 90%) for each GPU provisioned". A **target** (an SLO, from the [backend observability lesson](/learn/backend/07-reliability/observability/)) is a promise like "TTFT p95 under 1 s". Here, a request counts only if it meets *both* its TTFT target and its TPOT target.

Why does this exist? Because you can raise throughput in a way that hurts every user. The server can group requests into a **batch**: several requests processed in one pass of the GPU. A bigger batch uses the GPU better, but each request waits longer.

Databricks measured this on one A100 GPU with a 7B-parameter model. They state: "if we maximize throughput with a batch size of 64, latency increases by 4x while throughput increases by 14x."

If your target is strict, then at that batch size almost every request misses it. Throughput looks great. Goodput approaches zero. This is simplified: real requests vary, so the fall is less sharp. The direction holds.

## Question 3: why does GPU utilization mislead?

If you run the model yourself, the GPU is the expensive part. It seems natural to watch "GPU utilization", the number shown by the `nvidia-smi` tool.

Here is what that number means. NVIDIA's own documentation defines it as the "percent of time over the past sample period during which one or more kernels was executing on the GPU". A **kernel** is one program running on the GPU. The sample period is between 1 second and 1/6 of a second. So the number answers: "in the last second, was *anything* running?" It does not answer: "how much of the GPU was working?"

An everyday picture: a factory with 100 machines. One machine runs all day. The lights are on all day. The "is anything running?" meter reads 100%. The factory is 99% idle.

The mismatch is real. One engineering write-up reports that a single kernel on one streaming multiprocessor, a tiny part of the GPU, can make `nvidia-smi` report 100%. It recommends metrics from DCGM, NVIDIA's data center monitoring tool, such as tensor core activity and memory bandwidth.

For model serving, the better number is **MBU**, model bandwidth utilization. Start with the problem. To write each token, the GPU must read the model's whole set of weights from its memory, plus the saved context. Reading memory is the bottleneck, not arithmetic. **Memory bandwidth** is how many bytes per second the memory can deliver. MBU asks: of the bytes per second the memory could deliver, how many did we use? Databricks gives the formula: achieved bandwidth is (model size + saved context size) divided by TPOT. MBU is that divided by the peak bandwidth.

MBU tells you how close the decode phase is to its real limit. `nvidia-smi` could say "100%" while MBU is only about half. This is also covered in [the Prefill vs Decode: TTFT and TPOT lesson](/learn/ai/a2-inference-cost/prefill-decode/). If you rent the model from an API provider, you do not see any of this. Skip this question, and watch the first two.

## Question 4: how can cost double while nothing errors?

Your bill depends on tokens, and tokens are cheap or expensive depending on the **prompt cache**. Many prompts start with the same long block, so the provider stores that block's processed form and charges much less for the next call that begins with it ([the Prompt Caching: Mechanics and Economics lesson](/learn/ai/a2-inference-cost/prompt-caching/)). On Anthropic, a cache hit on Sonnet 5.5 costs $0.10 per million tokens against $2 for normal input.

Each API reply says how many tokens were read from the cache. Anthropic's usage fields are `cache_read_input_tokens`, `cache_creation_input_tokens`, and `input_tokens`. Total input is their sum. The **cache hit rate** is cache reads divided by that total.

Why does the hit rate matter on a dashboard? It can fall to zero without any error. Anthropic's docs say a block shorter than the model's minimum is not cached and "no error is returned". The minimum differs by model: 512 tokens for Sonnet 5.5, 1,024 for Sonnet 4.6, 4,096 for Haiku 4.5. A model switch, a failover, or a slightly shorter prompt can drop you below it.

Example: a prompt with an 800-token repeated block is cached on a model with a low minimum. On a model with a higher minimum, the same block is not cached. The cost per request about doubles. The error rate stays at 0%. Only the hit rate and the cost per request show it.

## The naive way: the dashboard everyone builds first

Most teams start from the web playbook. They chart uptime, error rate, average latency, GPU utilization, and tokens per second. All of these are real. Each one misses a way that LLM systems fail.

Two tiles need a word. The **queue** is the number of requests waiting for the server. The **backup share** is the share of traffic sent to a backup provider. Step through three failures. In each, a tile you would normally watch stays calm.

## The real fix: one dashboard, five rows of metrics

### Idea 1: user-facing metrics first

**What it is.** The top row is what users feel: TTFT p95, TPOT p95, whole-request time, and good requests per second. Add a quality signal from sampled live traffic, such as the online eval pass rate from [the Online Evals and A/B for LLM Features lesson](/learn/ai/a8-evals/online-evals-ab/) and the complaint rate from [the Incident Response for Model Regressions lesson](/learn/ai/a9-llmops/incident-response/).

**Everyday picture.** The customer's face at the table, not the kitchen's gas bill.

**Why it exists.** These are the numbers you promise. If they are green, the product is working, whatever the machines say. If they are red, you act.

**Example.** The OpenTelemetry project, which defines standard names for telemetry, has names for these in its generative AI conventions: `gen_ai.server.time_to_first_token` and `gen_ai.server.time_per_output_token`, both in seconds. The page marks them "Development", so names may change. Use the standard names to avoid a rename later, and pin the version.

### Idea 2: money metrics

**What it is.** Show token spend split into four kinds: uncached input, cache writes, cache reads, and output. Show cache hit rate per model. Show cost per request and, better, cost per *successful* task, from [the Cost Engineering lesson](/learn/ai/a9-llmops/cost-engineering/).

**Everyday picture.** A phone bill that shows minutes and data separately, so a spike has a name.

**Why it exists.** Cost is a first-class output of an LLM system, and it moves without errors. The split tells you where it moved.

**Example.** Cache writes cost a little more than normal input, and reads cost far less. A prefix that is written and never read costs more than one that is never cached.

### Idea 3: provider and agent health

**What it is.** Count errors by kind, not as one total: rate-limit 429s, spend-cap 429s, 529 overloads, 5xx, and errors inside a stream. Add the share of traffic on the backup provider. For agents, add steps per run, tool error rate, and the share of runs that get stuck, from [the Loop Control and Stopping lesson](/learn/ai/a7-agents-prod/loop-control/).

**Everyday picture.** A car dashboard has separate lights for oil, temperature, and brakes, not one light that says "problem".

**Why it exists.** The causes need different fixes. The Anthropic error docs say a 529 means high traffic across all users, and a spend-cap 429 "keeps failing until access resumes". One total cannot tell you which.

**Example.** Even a step that works nearly every time can fail a long run, because small risks add up over many steps. So the steps-per-run chart is a quality chart in disguise.

### Idea 4: saturation, if you host the model

**What it is.** Queue depth (requests waiting), batch size, KV cache use, MBU, and goodput. The **KV cache** is the server memory that holds the model's notes on the prompt so far ([the KV Cache lesson](/learn/ai/a2-inference-cost/kv-cache/)). When it is full, new requests wait. A deeper treatment is in elective E3.7.

**Everyday picture.** The queue outside a shop is a better sign of trouble than the light inside it.

**Why it exists.** These show a server heading toward trouble *before* TTFT breaks. A queue grows first. Then TTFT rises.

**Example.** MBU shows how close decode is to the memory limit, which a busy-light cannot.

### Idea 5: alert on burn, not on level

**What it is.** An alert on "TTFT above 1 s for one minute" fires on noise and sleeps through slow leaks. The better rule alerts on the **burn rate**: how fast you spend your error budget, relative to your target. The Google SRE workbook defines it as "how fast, relative to the SLO, the service consumes the error budget". The [backend observability lesson](/learn/backend/07-reliability/observability/) teaches it.

<CrossTrackLink id="07-reliability/observability">
Metrics, logs, and traces answer different questions. A target says what "good enough" means. A burn-rate alert pages you only when the error budget is truly at risk. It uses a long window to show the problem matters, and a short window to stop the alert soon after the problem ends.
</CrossTrackLink>

Apply the same idea to money. A monthly token budget is a budget like any other. A burn rate of 1 means the budget lasts exactly the month. A higher burn rate means it runs out sooner. The SRE workbook pairs a fast, high burn rate with a short window, and a slow, low burn rate with a long window. Using this on dollars is our own extension, not something the workbook says.

For example, a loop with a bug can spend a big share of the month's budget in one hour. That is a very high burn rate, and it should page you. Try different spend levels.

<Ai9DashBurn client:visible />

**Everyday picture.** A fuel gauge that warns you by how fast the tank is falling, not only by how empty it is.

**Why it exists.** A fixed threshold either pages all night or misses the slow leak. A burn rate scales with your target.

**The rule.** The SRE workbook says the short window should be much shorter than the long one, about a twelfth. After errors stop, the short window recovers fast, so the alert clears quickly.

## Numbers

| Item | Takeaway | Source |
|---|---|---|
| Output tokens vs input tokens | A few output tokens add more time than hundreds of input tokens | Databricks, MPT models |
| Batch size up | Throughput rises a lot, and latency rises too | Databricks |
| GPU utilization | Only says a kernel ran in the sample period | NVIDIA NVML docs |
| Cache minimums | Differ by model, and a block below the minimum is not cached | Anthropic caching docs |
| Burn-rate pages | A fast burn with a short window, a slow burn with a long window | Google SRE workbook |

Name your targets. These are examples to adapt, not rules: TTFT p95 under 1 s, TPOT p95 under 50 ms, and 99% of requests meeting both. The cost line: report cost per successful task each day, and alert on burn.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Metrics only | Cheap to store. Fast to chart | Single bad requests stay invisible | Always, as the base layer |
| Metrics plus traces | You can open one slow request and see why | Storage and privacy cost | You need to explain tail latency |
| TTFT-only target | Easy to measure | Misses slow writing and long answers | A first version |
| TTFT, TPOT, and goodput targets | Matches what users feel | More instrumentation | Streaming products at scale |
| Burn-rate alerts | Few false pages. Catches slow leaks | Harder to set up than a threshold | Production systems with a target |

## What experienced teams know

1. **GPU utilization is a time measure, not a work measure.** It says a kernel was running during the sample, not how much of the GPU was used. Put MBU and DCGM activity next to it. ([NVIDIA NVML docs](https://docs.nvidia.com/deploy/nvml-api/api/structnvmlUtilization__t.html), and an [engineering write-up on utilization vs saturation](https://arthurchiao.art/blog/understanding-gpu-performance/))
2. **Output tokens drive latency.** In Databricks' tests, 8 more output tokens cost more time than 512 more input tokens. Alert on answer length drift, not only on prompt length. ([Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices))
3. **Throughput can rise while users suffer.** Batch 64 gave 14 times the throughput and 4 times the latency. Always chart TTFT and TPOT at the same batch size as throughput. ([Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices))
4. **Headline speedups depend on the baseline.** The DistServe paper says 7.4 times more requests, but that is against one baseline (DeepSpeed-MII) on a chatbot workload. Against vLLM on the same workload, the paper reports 2.0 to 4.6 times. The 12.6 times "tighter SLO" is a different case, against vLLM, on summarization. Ask which baseline and which workload before you quote a number. ([DistServe paper, OSDI 2024](https://arxiv.org/html/2401.09670))
5. **Watch cache hit rate per model.** A block below the minimum is not cached and no error is returned, and minimums differ by model. A hit rate that falls to zero is the first sign of a silent cost jump. ([Anthropic caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))
6. **Split provider errors by kind.** 529 means overload for everyone, and a spend-cap 429 has no `retry-after` and does not clear. Lump them together and you will retry the wrong ones. ([Anthropic error docs](https://platform.claude.com/docs/en/api/errors))

## Interview lens

<Callout type="tip">
Say: "I would chart what users feel: TTFT and TPOT at p95, and good requests per second against a target. Then cost per task and cache hit rate, errors split by kind, steps per run for agents, and queue depth and MBU if we host. Alerts use burn rate over two windows, on latency and on dollars." Then add: "GPU utilization alone misleads, because it only says a kernel was running."
</Callout>

<Callout type="mistake">
Do not say "I would alert when GPU utilization passes 90%". It is a busy light, not a health measure. Do not quote a throughput gain without the latency that came with it. And do not average latency: the p95 is the number users feel.
</Callout>
