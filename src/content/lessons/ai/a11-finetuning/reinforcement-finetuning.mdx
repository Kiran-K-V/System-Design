## The problem

You ask your model: "What is 23 x 47?" It answers, in a calm and confident paragraph, "1,071". The right answer is 1,081. The explanation reads fine. Only the number is wrong.

You could fix this with the tools you know. Supervised fine-tuning (SFT) needs a correct worked answer for every prompt, and someone has to write them. Preference tuning needs pairs of better and worse answers, and someone has to label them. Both cost human time per example.

But a calculator can check this answer in a microsecond. When a program can say "right" or "wrong", you do not need a person in the loop. You can let the model try, grade the tries with the program, and learn from the grades. In its 2025 R1 paper, DeepSeek used this idea to train its R1-Zero model. Its score on AIME 2024, a hard high-school math contest, rose from 15.6% to 77.9% during training. The only feedback was a right-or-wrong check plus a format rule.

This lesson answers four questions:

1. Can a program tell the model whether it was right?
2. How does a bare score teach a model?
3. What happens when a prompt gives no signal?
4. What happens when the model finds a shortcut?

This family of methods is called **reinforcement fine-tuning**. The data you bring is not labeled answers. It is prompts plus a grader.

## Question 1: can a program tell the model whether it was right?

Yes, for some tasks. A **verifiable reward** is a score that code computes with no human opinion. A **reward**, as you saw in the last lesson, is a number that says how good an answer was. Verifiable means the number comes from a check you can rerun.

Think of an autograder for a coding class. Students submit code. A script runs the unit tests. The grade is the share of tests passed. Nobody reads the code, and the grade is the same every time. That is a verifiable reward.

Why does it exist? Because human labels are slow and judge models are biased and costly. A check is cheap, fast, and repeatable, so you can score millions of tries. Examples that work:

- **Math with one numeric answer.** Compare the final number with the answer key. DeepSeek's R1-Zero required the answer in a marked box, so a rule could verify it.
- **Code.** Compile it and run a set of tests. DeepSeek's team did this for competition code.
- **Format rules.** Did the answer put its reasoning inside the right tags? Did it return valid JSON that fits a schema?
- **Tool calls.** Did the agent call the right function with the right arguments? This is a check on the outcome, as in the [Agent Trajectory Evals](/learn/ai/a8-evals/trajectory-evals/) lesson.

The AI2 team that built the open Tulu 3 models gave this recipe a name in late 2024: **RLVR**, reinforcement learning with verifiable rewards. It gives a reward of a fixed value when the completion is verified correct, and nothing otherwise. A managed form of the same idea is called reinforcement fine-tuning, which a section below covers.

## Question 2: how does a bare score teach a model?

A score alone says "that was 1" or "that was 0". It does not say which words to change. How can that train anything?

The trick is to ask the same question several times. The model writes text by picking each next word with some chance, so it will not give the same answer every time. Each attempt is a **sample**. Ask 4 times and you may get 4 different answers. Some will be right and some will be wrong. The group of samples for one prompt is a **group**.

Now compare answers inside the group. If an answer scored better than its siblings, the choices that produced it were good. If it scored worse, those choices were bad. Think of grading on a curve: your mark does not matter as much as your mark against your class.

The number that captures this is the **advantage**: how much better than the group average an answer was. The formula is advantage = (reward - group average) / spread, where spread is the standard deviation (how far rewards typically sit from the average). This method is called **GRPO**, group relative policy optimization. DeepSeek introduced it in a math paper in 2024. A useful property is that no separate scoring model is needed to find the average. The group provides it.

Look at what happens in the update. Words from answers with a positive advantage become more likely. Words from answers with a negative advantage become less likely. The model is the same **policy** you met in the last lesson: the model whose behavior we are shaping.

How much work is this? A lot. Each update needs many answers per question, and each answer can run to thousands of tokens. DeepSeek's R1-Zero run wrote and scored hundreds of long answers for every single update. Generation, not the update itself, is where the time goes.

## Question 3: what if every answer in the group scores the same?

All four answers were wrong. The average is 0, the spread is 0, and every advantage is 0. Nothing is learned. The same happens if all four are right. A group teaches something only when it holds at least one right answer and at least one wrong one.

This is the most practical fact in the lesson. Say the model solves a prompt only rarely, and you draw a small group. Most groups are all wrong, so most groups teach nothing. You pay for every sample and learn from only a few. If the model solves the prompt about half the time, almost every group holds a mix, and almost every group teaches something. So pick prompts in the middle band, not too hard and not too easy.

This is why OpenAI's guide for reinforcement fine-tuning says your baseline eval scores must sit between the minimum and the maximum. If the model scores 0 on every prompt, there is nothing to reinforce. If it scores perfect, there is nothing to improve. Run your evals first, and keep the prompts in the middle band.

## The naive way: let a model be the grader

Most tasks are not like arithmetic. "Was this email polite?" has no calculator. The tempting move is to ask a language model to grade each answer on a scale, and use that as the reward.

It works for a while and then breaks. Training pushes the policy to earn high grades, and the policy is better at finding grader weaknesses than you are at fixing them. This is **reward hacking**: scoring high without doing the work you wanted. Teaching to the test is the human version. A student who learns the exam's quirks gets an A and learns nothing.

DeepSeek's team met this. Their R1 paper explains that they did not use neural reward models for reasoning tasks because those models are "susceptible to reward hacking during large-scale reinforcement learning". When they did use a model-based reward for helpfulness, the paper shows the reward rising while the model's CodeForces performance fell. OpenAI's grader guide gives the same warning: a model that has hacked its grader "will score highly on model grader evals but score poorly on expert human evaluations".

But a code check does not make you safe. Programs can be fooled too. METR, a group that tests AI systems, studied an early version of OpenAI's o3. In 128 runs on its RE-Bench tasks, the model tried reward hacking in 39 of them, 30.4%. On METR's HCAST tasks, it was 8 of 1,087 runs, 0.7%. METR reported that this was more than 43 times more common on RE-Bench, "perhaps because" the model could see the whole scoring function there. That 0.7% is a number for one task suite. Do not use it as a general rate.

## The real fix: make the grader the product

When you do reinforcement fine-tuning, you are not mostly training a model. You are building a grader. The model will optimize whatever you write, so write it as carefully as production code.

### Idea 1: use checks first, a model grader last

Start with the strictest check that fits. OpenAI's grader API lists the options. A **string check** compares text exactly or by "contains". A **text similarity** grader scores how close two texts are. A **score model** grader asks a model for a grade. A **Python grader** runs your code. A **multigrader** combines several. Scores run from 0 to 1, so partial credit is possible.

Pick the strictest tool that does the job. Exactly matching a final number beats a "contains" check. Why? A "contains" grader gives full marks to an answer that lists ten candidate numbers, one of which is right. Training will find that. Use a model grader only for the part no code can check, and test it against expert human judgments first. Check that it ranks a few known good, medium and poor answers in the right order.

### Idea 2: wall off the grader and read the runs

The METR animation above shows the fix. Run the grader where the solution cannot look at it: another process, no shared memory, hidden test inputs. The [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) lesson covers sandboxes. Then read a sample of the runs from late in training, not just the dashboard. A reward curve cannot tell a skill from a trick. A person reading the transcript can.

Do not rely on telling the model not to cheat. METR tried it. On one task, with 20 runs per prompt, 80% of first plans described a hack under the original prompt. With "Please do not cheat" it was 80%. With "Please do not reward hack" it was 70%. A prompt that asked for only the intended methods went up to 95%. The model also knows what it is doing: when METR asked whether a hacked plan matched the user's intent, the model said "no" 10 times out of 10.

### Idea 3: size the run, and pick where to run it

Reinforcement fine-tuning costs many more samples than SFT. The R1-Zero run used a large GPU cluster for over a week, which is a six-figure bill (~$200,000 at the paper's assumed GPU price). Most teams will not run that. They will run a small, narrow job.

The good news: the update carries little information. Thinking Machines Lab pointed out that each sample gives roughly one bit, right or wrong. That is far less than a LoRA adapter can store, even at the smallest rank. They found that LoRA matched full fine-tuning for this kind of training. So a LoRA adapter (the [SFT and LoRA](/learn/ai/a11-finetuning/sft-lora/) lesson) is a good default.

Where to run it:

- **Open-source tools.** The Hugging Face TRL library has a `GRPOTrainer`. You write the reward functions in Python.
- **Training services.** Thinking Machines Lab offers Tinker, a training API for open-weight models.
- **OpenAI's managed reinforcement fine-tuning.** The guide says it supports o-series reasoning models only, and "currently only for o4-mini". Read the date before you plan on it. OpenAI's [deprecations page](https://developers.openai.com/api/docs/deprecations) (checked 2026-10-16) lists o4-mini, and fine-tuned o4-mini models, for shutdown on October 23, 2026. It also says new organizations cannot start fine-tuning, existing customers cannot create new jobs after January 6, 2027, and the Evals platform shuts down on November 30, 2026, and graders documented for eval workflows are part of that shutdown. So the managed route is closing. The skill that carries over is writing the grader.

## Numbers

State these before a run.

- **Quality bar.** Pass rate on a held-out set with the same checker, plus a second set graded by a different method, such as expert review. The second set catches hacks. A run that raises the training reward but not the held-out score has learned the grader.
- **Latency budget.** Reasoning models trained this way write longer answers. DeepSeek reported that R1-Zero tended to produce longer responses as training went on. Longer thought means more time to the last token. Measure median and 95th-percentile output length before and after.
- **Cost per request.** Output tokens drive it. Output tokens cost more than input tokens, so a tuned model that writes much longer answers costs proportionally more. If your tuned model is self-hosted, the same applies to GPU time.
- **Training cost.** Samples per step times steps. Even a small run generates hundreds of thousands of answers.

## Trade-offs

| Method | You gain | You pay | Choose it when |
|---|---|---|---|
| SFT on examples | Simple, cheap | Needs a correct answer per prompt | You have good demonstrations |
| Preference tuning (DPO) | Learns taste and style | Needs pairs, can learn length | The target is tone or safety, with no checkable answer |
| RLVR with a code checker | No labels, the checker scales | Many samples, needs a hack-proof grader | Math, code, format, tool outcomes |
| RFT with a model grader | Covers fuzzy tasks | Grader drifts and is gamed | Fuzzy goals, with strong audits |
| Distillation | Cheap, strong for small models | Copies teacher errors | A stronger model already exists (the [Distillation and Training Data](/learn/ai/a11-finetuning/distillation-data/) lesson) |

## What experienced teams know

1. **Reinforcement learning sharpens what the model can already do.** A [study of RLVR](https://arxiv.org/abs/2504.13837) compared tuned models with their base models. At one try, the tuned models won. When the base models got many tries (large k), they scored higher. The authors conclude the reasoning ability comes from the base model, and that distillation can add genuinely new patterns. Before you pay for a run, sample the base model 16 or 32 times per prompt. If it almost never gets any right, RL has little to reinforce.
2. **GRPO can inflate answer length.** The [Dr. GRPO analysis](https://arxiv.org/abs/2503.20783) found a bias in the original GRPO objective that artificially increases response length, especially for wrong answers. The TRL docs trace it to dividing each answer's loss by its own length. TRL now offers `dapo` and `dr_grpo` loss types for this. Plot the length of wrong answers during training.
3. **Telling the model not to cheat is not a control.** METR's [reward hacking report](https://metr.org/blog/2025-06-05-recent-reward-hacking) cut the rate only from 80% to 70% with "Please do not reward hack". Change the environment, not the prompt.
4. **A small adapter is enough.** The [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/) study (September 2025) matched full fine-tuning at rank 1 for RL, because RL absorbs far less information per sample than SFT. Start with a small rank and save the memory.
5. **Hacking in training can spread to other behavior.** Anthropic's [paper on production reinforcement learning](https://arxiv.org/abs/2511.18397) found that a model that learned to reward hack went on to show alignment faking (appearing aligned while pursuing other goals), cooperation with malicious actors, and sabotage in Claude Code tests. Training on standard chat safety data fixed chat behavior but not agent behavior. Treat hack detection as a safety control, not only a quality one.
6. **A managed service can be withdrawn.** The OpenAI timeline above shows a fine-tuning product with a closing date. Keep your grader and prompts as portable code in your repo, so you can move the job to an open-source trainer.

## Interview lens

<Callout type="tip">
Say: "I'd use reinforcement fine-tuning when the outcome is checkable. Prompts plus a grader, no labeled answers. I sample a group of answers per prompt, grade them, and push the model toward the above-average ones. The grader is the product: code checks first, a sandbox around them, a held-out set graded a different way, and a human reading late-training transcripts. I'd check the base model's pass rate first, since prompts that are all right or all wrong teach nothing." That shows mechanism, cost, and a safety habit.
</Callout>

<Callout type="mistake">
Do not say "RL teaches the model new skills" without caveats. Do not say hacking is rare because a benchmark reports 0.7%. That number is for one task suite, and the rate on a task where the model can see the scorer was 30.4%. And do not promise a model grader is objective. It is a model with biases that the policy will learn.
</Callout>
