## The problem

Your first model call works in five minutes. Your first production incident comes a week later. A user sees an answer that stops in the middle of a sentence. A JSON parser crashes on a reply that is empty. A chat feature costs five times what the spreadsheet said.

All three come from the same gap. The API call looks like a function call, and it is not one. It has a request shape you must know field by field. It returns a reason why it stopped. It returns a meter. Code that ignores the reason and the meter works in a demo and fails at scale.

This lesson walks one call from the first byte to the bill. The design method from [lesson A0.2](/learn/ai/a0-orientation/ai-design-method/) asked for a cost per request. The `usage` field here is where that number comes from.

<CrossTrackLink id="03-api-design/rest">
An LLM API is a plain REST-style endpoint: an HTTP POST with a JSON body and a JSON reply, plus status codes for errors. Everything you know about resources, status codes, and versioning applies. The new parts are that the reply is probabilistic, that it can stop for several reasons while the HTTP status is still 200, and that you pay per token.
</CrossTrackLink>

## The shape of a request

A request has five parts: which model, what the model sees, what limits apply, which tools exist, and how to sample. Here is the smallest useful request to the Anthropic Messages API. The field names come from the API reference, fetched 2026-10-16.

```json title="anthropic-request.json"
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "system": "Be brief.",
  "messages": [
    { "role": "user", "content": "Hi" }
  ]
}
```

- `model` picks the model. Model ids change, so keep the id in config, not in code.
- `max_tokens` is required. It is the most tokens the model may write. The docs say the model may stop before the maximum, so it is a ceiling and not a target. A value of 0 fills the prompt cache without generating output.
- `system` holds standing instructions. It is a top-level field. The reference says there is no `"system"` role for input messages in this API.
- `messages` is the conversation. Each item has a `role` of `user` or `assistant`, and `content`.
- Optional fields add `tools` (lesson A3.4), sampling settings such as temperature ([lesson A1.5](/learn/ai/a1-model-function/sampling-decoding/)), `stop_sequences`, and `stream` (lesson A3.2).

OpenAI's Responses API has the same parts under other names. This is the same call, as the OpenAI docs show it:

```json title="openai-request.json"
{
  "model": "gpt-5.5",
  "instructions": "Be brief.",
  "input": "Hi",
  "max_output_tokens": 1024
}
```

| Part | Anthropic Messages | OpenAI Responses |
|---|---|---|
| Standing instructions | `system` | `instructions` |
| The conversation | `messages` | `input` |
| Output cap | `max_tokens` (required) | `max_output_tokens` |
| The reply | `content` blocks | `output` items |
| Why it ended | `stop_reason` | `status`, `incomplete_details.reason` |
| The meter | `usage.input_tokens`, `usage.output_tokens` | `usage.input_tokens`, `usage.output_tokens`, `usage.total_tokens` |

The two shapes are close, but not the same. A gateway that swaps providers must translate both ways (lesson A3.8). Provider docs change, so check the page date before you copy a field name. Here the Anthropic fields are from the Messages and stop-reasons pages, and the OpenAI fields are from the Responses reference, all read on 2026-10-16.

## The shape of a response

```json title="anthropic-response.json"
{
  "id": "msg_01234",
  "type": "message",
  "role": "assistant",
  "content": [
    { "type": "text", "text": "Hello!" }
  ],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "stop_details": null,
  "usage": { "input_tokens": 12, "output_tokens": 5 }
}
```

The docs example uses `input_tokens: 100` and `output_tokens: 50`. The numbers here are smaller, for the walk below. `content` is a list of blocks, because one reply can mix text and tool calls. The OpenAI reply has the same idea: an `output` list of items, a `status` of `completed` or `incomplete`, and a `usage` object.

```json title="openai-response.json"
{
  "id": "resp_...",
  "status": "completed",
  "output": [
    {
      "type": "message",
      "role": "assistant",
      "content": [{ "type": "output_text", "text": "Hello!" }]
    }
  ],
  "usage": { "input_tokens": 12, "output_tokens": 5, "total_tokens": 17 }
}
```

## The API remembers nothing

Look at turn 2 in the walk. The second request holds the whole first exchange again. This is the single most important fact about the API: it is **stateless**. A stateless service keeps no memory of earlier calls. Each call sees only what you send in it.

A backend engineer knows this pattern. It is the same reason a REST server does not remember the last request, and a client carries the session token. Here the client carries the whole conversation. The cost is real. Input grows with every turn.

Take a chat with a 500-token system prompt, a 150-token user message each turn, and a 300-token reply each turn (these are assumed numbers). At turn n, the input is 500 + 150n + 300(n - 1) tokens. At turn 10 that is 500 + 1,500 + 2,700 = 4,700 tokens. Add up turns 1 to 10 and you send 26,750 input tokens, though the conversation only holds 5,000 tokens of new text (500 + 10 x 150 + 10 x 300 = 5,000). That is 5.35 times more input than new text.

Prices apply per token. At Opus 5.5 rates of $4 per million input tokens and $20 per million output tokens (Anthropic pricing, https://claude.com/pricing, as of 2026-10-16), the 10-turn chat costs 26,750 x $4 / 1M = $0.107 for input and 3,000 x $20 / 1M = $0.060 for output. The total is about $0.167. Input is 64% of the cost, though the model wrote the output. Try the numbers yourself.

Two things lower this cost. A **prompt cache** lets the provider reuse work for a repeated prefix at a lower price (lesson A2.5). A **summary** of old turns replaces them with fewer tokens (module A4). Both start from the same fact: the history is yours to manage.

<Callout type="deep" title="Chaining by id">
OpenAI's Responses API can chain turns with `previous_response_id` and stores responses by default. That saves you resending the history over the wire. The migration guide notes that earlier input tokens in the chain are still billed as input tokens. So the wire gets lighter, and the bill does not. Also, `instructions` are not carried over by `previous_response_id`, so resend them each time.
</Callout>

## Stop reasons

The reply ends for a reason, and the API tells you which. In the Anthropic API the field is `stop_reason`. The "Handling stop reasons" page lists seven values:

| Value | Meaning (from the page) | What your code does |
|---|---|---|
| `end_turn` | Claude finished its response naturally. | Show it. |
| `max_tokens` | The response reached your `max_tokens` limit. | Raise the cap or continue. |
| `stop_sequence` | Claude emitted one of your `stop_sequences`. | Expected. |
| `tool_use` | Claude is calling a tool. | Run it (lesson A3.4). |
| `pause_turn` | A server-tool loop reached its iteration limit. | Send the content back to continue. |
| `refusal` | Claude declined to respond. | Read `stop_details`, retry on a fallback model. |
| `model_context_window_exceeded` | The response filled the model's context window. | Treat it as truncated. |

Now the trap. Every row above comes back with HTTP 200. The page says a refusal is "a normal HTTP 200 response, not an error". A `max_tokens` stop is also a success at the HTTP level. A handler that only checks the status code sends a half-sentence to a user, or feeds an empty string to a JSON parser. Use the explorer to see what each handler does with each value.

<Ai3ApiStop client:visible />

This is a failure you can measure. Count the share of calls per `stop_reason` in your logs. A rising `max_tokens` share means your cap is too low for your prompts. A rising `refusal` share means a prompt change or an input pattern is tripping the safety filter. Both are alerts you can set from one field.

OpenAI reports the same facts in different fields. A reply cut by the cap has `status: "incomplete"` and `incomplete_details.reason: "max_output_tokens"`, per the structured-outputs guide. A refusal shows up as a content part of type `refusal`. Your gateway must map both shapes to one internal enum.

## Usage: where cost comes from

The `usage` object is your meter. With prompt caching on, Anthropic splits the input into three counters. The prompt caching page gives the rule:

<Math block tex="\text{total input} = \text{cache\_read\_input\_tokens} + \text{cache\_creation\_input\_tokens} + \text{input\_tokens}" />

In words: `input_tokens` counts only the tokens after the last cache breakpoint, and the total is the three counters added up. The docs example is 1,800 read from cache, 248 written, and 2,048 plain, for 4,096 in all. If you bill only on `input_tokens`, you miss the other two. Lesson A3.9 builds the full metering. For now, store all counters from every response, together with the model id and a request id.

Bill from `usage`, not from your own token estimates. A tokenizer can differ between model versions, and the usage field is what the provider charges against. See [lesson A1.1](/learn/ai/a1-model-function/tokens/) for why the same text gives different counts.

## Limits worth knowing

- The Messages request body has a 32 MB limit. A larger one fails with HTTP 413, error type `request_too_large`.
- Non-streaming requests that could run longer than 10 minutes are rejected by the SDKs. Use streaming for long output (lesson A3.2).
- On Claude 4.6 and later, a request that ends with an assistant message (a "prefill") returns 400.

These come from the Anthropic errors page, read on 2026-10-16. Limits change, so check the live page before you rely on one in a design.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Resend the full history | Total control of context | Input grows each turn | Short chats, or you trim history |
| Chain by id (`previous_response_id`) | Smaller requests | Same input bill, provider holds state | You want less glue code |
| High `max_tokens` | Fewer cut replies | Slower worst case, higher cost cap | Long answers are normal |
| Low `max_tokens` | Hard cost and time cap | More `max_tokens` stops | Short labels and tags |
| Log every `usage` | Exact cost per call | Storage, a schema | Always |

## Interview lens

<Callout type="tip">
Say the call has three outputs, not one: the content, the stop reason, and the usage. "I branch on stop reason, I log usage with tenant and feature tags, and I alert when the max_tokens share rises." That sentence shows you have run this in production.
</Callout>

<Callout type="mistake">
Do not say "the model remembers the conversation". The API is stateless. Your code (or the provider's chain feature) resends the history, and you pay for it each time. Also do not treat HTTP 200 as success: a refusal and a truncated reply both arrive as 200.
</Callout>
