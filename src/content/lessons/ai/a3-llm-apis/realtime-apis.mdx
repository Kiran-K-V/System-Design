## The problem

A user talks to a voice assistant. With the tools you know so far, the app would record the whole sentence. The app would send it as a request, wait for the full answer, and play it. Two things go wrong.

- **It feels slow.** The user waits for the end of the request, for the model, and for the audio.
- **The user cannot interrupt.** A person who hears a wrong answer says "no, I meant Tuesday" at once. A request and response call has no way to hear that while the answer plays.

Voice needs a connection that stays open and carries audio **both ways at the same time**. Events flow up (microphone chunks) and down (transcripts, model audio, signals about who is speaking). That is a different API shape from lesson [A3.2](/learn/ai/a3-llm-apis/streaming/), where the server streams one answer to one request.

Module A12 covers voice in depth, including the latency numbers. This lesson covers the API side: the connection, the events, and the cancel.

## Two ways to build a voice agent

A **cascaded** pipeline chains three components: speech to text (STT), a text LLM, and text to speech (TTS). A **speech-to-speech** model takes audio in and gives audio out in one model.

| | Cascaded (STT, LLM, TTS) | Speech to speech |
|---|---|---|
| Parts | Three services you can swap one by one | One model and one session |
| Text in the middle | Yes: log it, filter it, run guardrails and tools on it | The API gives transcripts, but the model works on audio |
| Delay | Each stage adds time before the next can start | One model, so fewer hops to first audio |
| Debugging | You can inspect each stage | You see events and transcripts only |

The table is design reasoning, not a benchmark. Which one wins depends on your eval and your latency budget. OpenAI's Realtime guide describes its speech-to-speech session. It is one where "the agent handles audio turns, tools, interruptions, and handoffs inside that session". Gemini's Live API is also a speech-to-speech style API on a persistent connection. A cascade stays useful when you need full control of each stage. It also stays useful when you must run a text-only guardrail on every sentence.

## The connection: WebRTC or WebSocket

<CrossTrackLink id="02-networking/real-time-transport">
HTTP only answers questions. SSE, WebSocket, and WebRTC let the server speak first. WebSocket is one long two-way connection through your servers. WebRTC sends media straight between peers, with NAT traversal and a relay as fallback.
</CrossTrackLink>

For model APIs, the choice follows from who holds the API key. As of 2026-10-16:

| API | Browser or phone | Your own server |
|---|---|---|
| OpenAI Realtime | WebRTC, with an ephemeral client secret that your server requests (`/v1/realtime/client_secrets`) | WebSocket |
| Gemini Live | A stateful WebSocket (WSS) straight from the client is allowed. The page recommends ephemeral tokens over standard API keys in production | Server to server over the same WebSocket |

The rule is the same for both. **Never ship a long-lived API key to a browser.** Your server mints a short-lived token, and the client uses it. A second difference matters for interruption. On WebRTC and SIP, OpenAI says "the server manages a buffer of output audio". On a WebSocket, the client controls playback. That decides who must act at barge-in, as the next section shows.

## Events, turns, and barge-in

### Turn detection

Who decides that the user has finished? **Voice activity detection** (VAD) listens to the audio and detects speech start and stop. OpenAI's VAD guide says it is on by default in speech-to-speech sessions, emits `input_audio_buffer.speech_started` and `input_audio_buffer.speech_stopped`, and is set with `session.update` at `session.audio.input.turn_detection`. It has two modes:

- `server_vad` splits turns on silence. `silence_duration_ms` is the silence needed to end a turn, and "shorter values end turns faster". `threshold` and `prefix_padding_ms` tune loudness and the audio kept from before speech.
- `semantic_vad` uses a classifier that judges from the words whether the user is done. `eagerness` is `low`, `medium`, `high`, or `auto`. Trailing-off speech gets a longer wait than a complete sentence.

This is a trade-off you set. A short silence limit makes replies come sooner, and it cuts off people who pause to think. A long limit does the opposite. The silence wait is also the first slice of your latency budget, as the widget below shows.

Three rules come out of this.

1. **Playback is separate from generation.** The model may have produced 10 seconds of speech while the user heard 3. At barge-in the app must stop the speaker at once, not wait for the queue to drain.
2. **Truncate the transcript to what was heard.** OpenAI's conversations guide says that on WebSocket the client must stop audio itself and send a truncation request, and that on WebRTC the server truncates unplayed audio. If you skip it, the model's memory says it spoke words the user never heard.
3. **Mute is not cancel.** OpenAI's WebSocket page for its newer GPT-Live endpoint says "Muting input does not cancel backend work or stop generated speech". Use the cancel and truncate path to stop an answer.

OpenAI's current pages show two event vocabularies. The Realtime guide uses names such as `input_audio_buffer.append`, `response.output_audio.delta`, `response.cancel`, and `conversation.item.truncate`. The GPT-Live page uses `session.input_audio.append`, `session.output_audio.delta`, `session.input_transcript.delta`, and `response.create`. Pick one endpoint and read its own event reference. Do not mix names.

### Sessions and state

A realtime session holds state: its instructions, the conversation items so far, and the turn settings. A dropped connection can lose that state unless your server rebuilds it. The pages I read do not state session time limits. Check the current docs for the limit on your model, and design the reconnect path first.

## Numbers

**Audio on the wire.** Raw audio is cheap next to video, but it adds up. OpenAI's GPT-Live page lists `audio/pcm` at 24,000 Hz (the default) or 16,000 Hz, and `audio/pcmu` or `audio/pcma` at 8,000 Hz. Gemini Live takes 16-bit PCM at 16 kHz in and gives 16-bit PCM at 24 kHz out. Raw PCM is a steady stream of bytes, before any codec. On a WebSocket the audio is also base64 text inside JSON, which makes the stream about a third larger.

**Price.** OpenAI's pricing page lists realtime prices per million tokens, as of 2026-10-16:

| Model | Modality | Input | Cached input | Output |
|---|---|---|---|---|
| gpt-realtime-2.1 | Audio | $32.00 | $0.40 | $64.00 |
| gpt-realtime-2.1 | Text | $4.00 | $0.40 | $24.00 |
| gpt-realtime-2.1-mini | Audio | $10.00 | $0.30 | $20.00 |
| gpt-realtime-2.1-mini | Text | $0.60 | $0.06 | $2.40 |

Source: [developers.openai.com/api/docs/pricing](https://developers.openai.com/api/docs/pricing). Audio output costs much more than text output on the same model. The pages I read do not say how many tokens one second of audio is. So I cannot turn these prices into dollars per minute. Measure it: run a one-minute call and read the usage the session reports (lesson [A3.9](/learn/ai/a3-llm-apis/cost-metering/)).

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Cascaded pipeline | Control of every stage, text guardrails | More hops, more services | Regulated flows, custom voices |
| Speech to speech | One session, fewer hops | Less insight, audio token prices | Natural conversation |
| WebRTC to browser | Media path built for audio, short-lived token | Signaling and NAT work | Browser and mobile clients |
| WebSocket from server | Simple, you control playback | You must stop audio at barge-in | Phone bridges, server agents |
| Short VAD silence | Faster replies | Cuts off pausing users | Short commands |
| Semantic VAD | Fewer cut-offs | Classifier cost and delay | Open conversation |

## Interview lens

<Callout type="tip">
Say: "Voice needs a persistent duplex connection. I would use WebRTC for browsers with a server-minted ephemeral token, and a WebSocket from my server otherwise. VAD marks turns. On barge-in the client stops playback, truncates the item to what was heard, and the response is cancelled." Then give the latency budget as a sum of stages. And say which numbers you measured.
</Callout>

<Callout type="mistake">
Do not treat the end of audio generation as the end of audio playback. Do not use mute to stop a reply. Do not put a long-lived API key in a client. And do not quote a latency target without saying where each slice of it goes.
</Callout>
