## The problem

Your product calls one model provider. One afternoon the provider is overloaded. Anthropic's error page says a 529 `overloaded_error` "can occur when the API experiences high traffic across all users". Your users see errors. Your retries make the load worse (lesson [A3.6](/learn/ai/a3-llm-apis/limits-retries-idempotency/)).

Three other pains come from the same root. Each team in the company keeps its own provider key, so you cannot say who spent what. A model upgrade means a code change in ten services. And a tenant with a loop bug can burn the whole account's rate limit.

A provider outage is your outage, unless a layer between your code and the providers can absorb it. That layer is a gateway.

## What you already know

<CrossTrackLink id="08-technologies/api-gateway">
An API gateway is the one front door for client traffic. It ends TLS, checks identity, limits rates, and routes each request to a service. It runs a fixed chain of cheap checks first, so bad traffic never reaches expensive work.
</CrossTrackLink>

An LLM gateway is the same idea turned around. It sits on the **outbound** side: between your services and the model providers. It still authenticates, limits, routes, caches, and logs. What changes is that the backends are not copies of one service. They are different vendors with different request formats, prices, and behavior. That is the new part of this lesson.

## The mechanism

### One internal API and model aliases

The gateway exposes one request shape to your code. Inside, an adapter per provider translates to that provider's format and translates the answer back. Your code asks for an **alias** such as `chat-main` or `summarize-cheap`. The gateway config says which provider and model each alias means today.

This is a lookup table you already know from service discovery. It buys two things. A model change is a config edit, not a deploy. And the alias is the unit you evaluate, budget, and report on.

### Fallback on provider errors

Step through one request where the primary provider fails.

<Ai3GwWalk client:visible />

A fallback should fire on errors that another target can fix: 429 (rate limited), 529 (overloaded), 5xx, and timeouts. It should not fire on a 400, because a malformed request fails everywhere. Check the default of your product. Portkey's docs say that without `on_status_codes` "fallback triggers on any non-2xx status code". Cloudflare AI Gateway triggers a fallback "if a model request returns an error", and can also trigger on timeouts. Set the list on purpose.

Two cases need care.

- **Spend-cap 429.** Anthropic's errors page says a tier spend-cap 429 has no `retry-after` header and "keeps failing until access resumes". Retrying the same provider cannot work. A second provider can.
- **Retry multiplication.** The Anthropic SDK retries twice by default. If your gateway also retries, and your app retries, one user request can become many provider calls. Decide which layer owns retries.

### The fallback model needs its own eval

Here is the trap. The gateway makes the swap invisible to the app. It does not make the *answers* equal. A prompt tuned on model A runs on model B with different wording, different length, and sometimes a different format.

Tool calls show it clearly. Anthropic returns `tool_use` blocks, OpenAI returns `function_call` items, and Gemini returns `function_call` steps (lesson [A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/)). The gateway can translate shapes. But if it translates one parameter badly, a request that worked on A fails on B. Prompt caches also stay with one provider, so the first calls after a failover pay full input price.

So a fallback target is not ready until you run your golden set against it (lesson [A0.2](/learn/ai/a0-orientation/ai-design-method/)). Then check that it clears your quality bar. Otherwise the gateway turns a loud outage into a quiet quality drop. Log which model answered, so that drop is visible.

### Routing by cost, latency, or capability

Routing picks the target for each request. Three common rules:

- **Cheapest capable.** Send easy requests to a small model and hard ones to a strong model. A cascade tries the cheap model first and escalates when a check fails.
- **Fastest.** Prefer the target with the lowest recent latency.
- **Strongest.** Prefer the best model, and fall back down the list.

A strong model can cost many times more per request than a small one. So the blended cost depends mostly on the share of traffic that can go to the cheap model. Even a modest share cuts the bill a lot. That share is only safe if an eval shows the cheap model clears the bar on those requests. Routing without an eval is a guess.

### Tenant keys, quotas, cache, and logs

- **Keys and quotas.** Give each tenant (or team or feature) its own gateway key. The gateway holds the real provider keys. A tenant over its quota gets a 429 from the gateway, before any provider cost. This is the token bucket of lesson 7.4, applied per tenant and per tokens, not only per request.
- **Cache.** An exact-match cache hashes the whole request and returns the stored answer on a repeat. Cloudflare's docs say its cache is "based on exact match of the entire request", with a TTL from 60 seconds to one month, and that semantic caching is planned, not shipped. Put the tenant id in the cache key. If you leave it out, one tenant can be served another tenant's answer.
- **Logs.** Log tenant, alias, the model that really answered, token counts, latency, status, and a `fell_back` flag. Prompts hold user data, so decide retention and redaction first. These records are the input to cost metering (lesson [A3.9](/learn/ai/a3-llm-apis/cost-metering/)).

## Products

All facts below come from each product's docs on 2026-10-16.

| Product | Routing and fallback | Notes |
|---|---|---|
| LiteLLM | Strategies named `simple-shuffle` (default), `latency-based-routing`, `least-busy`, `cost-based-routing`, `usage-based-routing`. Priority `order` levels escalate on connection errors, 404, and 429. | Library or proxy you run. Its docs disagree on cooldown and retry defaults, so set your own and test them. |
| OpenRouter | Hosted. By default spreads load across providers, weighted by the inverse square of price. `sort` or `order` turns that off. `allow_fallbacks` is `true` by default. | `require_parameters` is `false` by default, so a provider can ignore a parameter without an error. Set it to `true` if you rely on tools or a response format. |
| Portkey | `strategy.mode` set to `fallback` with a target list. Optional `on_status_codes`. | Default is any non-2xx, so list the codes yourself. |
| Cloudflare AI Gateway | Fallback is an array of request objects. The `cf-aig-step` header says which step answered, 0 for the primary. | Exact-match cache with `cf-aig-cache-status` of `HIT` or `MISS`. |
| Envoy AI Gateway | Named here only. | I could not confirm its fallback or quota features from its docs. Check before you rely on it. |

## Build or buy

Buy (or adopt open source) first. Aliases, fallback, and key management are solved problems, and a product gives them in a day. Build when one of these holds. Data may not leave your network, and no product fits that rule. You need routing logic tied to your own eval results. Or the gateway must sit inside an existing platform team's proxy. Even then, a thin layer over an open library often beats a from-scratch build. Two cautions apply to both paths. The gateway is a shared hop and a single point of failure, so run it as several stateless copies. And keep business logic out of it, as in the backend lesson.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| One provider, no gateway | Fewest moving parts | Outage is your outage, no per-tenant view | Prototype or internal tool |
| Gateway with fallback | Survives 429, 529, 5xx | Eval per target, extra hop, format drift | Customer-facing product |
| Cost routing | Blended cost falls | Quality risk, needs an eval per route | Large share of easy traffic |
| Exact-match cache | Repeat calls cost nothing | Low hit rate on free text, tenant leak if key is wrong | FAQ-like or batch traffic |
| Self-hosted fallback | Works when all vendors fail | Ops, weaker model, GPU cost | Strict uptime or privacy rules |

## Interview lens

<Callout type="tip">
Say: "I would put an LLM gateway in front of the providers, with aliases so code never names a model. It falls back on 429, 529, and 5xx. But I would only list a fallback model after it passes the same eval. I would log which model answered and meter tokens per tenant." Then say that the cheap share of traffic must be backed by an eval.
</Callout>

<Callout type="mistake">
Do not say "we have a fallback provider, so we are safe" without saying that the fallback was evaluated. Do not retry in the app, the SDK, and the gateway at once. Do not cache without the tenant in the key. And do not fall back on a 400.
</Callout>
