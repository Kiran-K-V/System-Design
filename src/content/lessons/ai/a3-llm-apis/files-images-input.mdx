## The problem

A model reads tokens. An image is not text, so the provider turns it into tokens before the model sees it. You pay for those tokens, and they take up context.

A team builds an invoice reader. A test with ten invoices costs a few cents. In production they send 200,000 scanned pages a month. The bill is five times higher than the estimate, and nobody knows why. The estimate counted words. The pages were sent as images, and images have their own price rule.

This lesson gives that rule and the limits around it. The lesson also gives the choices you control: what format to send, how large, and how often.

Facts about Anthropic's API come from its vision, PDF, and Files pages, fetched on 2026-10-16. Other providers use other formulas. Check their pages before you copy any number here.

## Naive solution: send the raw scan every time

The simple design sends each page exactly as the scanner produced it, as base64 text in the request body. It has three faults.

1. **Cost.** A big image can cost thousands of tokens. A clean text page often costs fewer.
2. **Payload size.** Base64 inflates the bytes. In a chat, each turn resends the full history, so the same images ride along on every call. Anthropic's vision page says this grows request size and latency as the conversation grows.
3. **No check.** Nothing stops a 40 MB scan, a Word file, or an image with a hidden instruction in it.

## The mechanism: patches, caps, and file ids

### Images are counted in patches

Claude's vision page says it views images in patches, not pixels. Each patch is 28 by 28 pixels, and each patch is one visual token. The cost of an image is:

<Math block tex="\text{tokens} = \lceil w / 28 \rceil \times \lceil h / 28 \rceil" />

In words: round the width up to whole patches, round the height up to whole patches, and multiply. A 1000 x 1000 image is 36 x 36 patches, so 1,296 tokens. The page's own example says the same.

Older material, and some provider pages, use a pixel-area rule such as "width times height divided by 750". Anthropic's current page does not. It states the patch rule above. If you find the older rule in a blog post or a code sample, check the date before you trust it.

### The downscale cap depends on the model

Large images are resized first, then counted. The page gives two tiers:

| Tier | Models | Max long edge | Max visual tokens |
|---|---|---|---|
| High-resolution | Claude 4.7 and later | 2576 px | 4784 |
| Standard | All other models | 1568 px | 1568 |

An image is resized when it breaks either limit. The token limit often bites first. A 1920 x 1080 screenshot is not cut to 1568 px wide. The standard tier shrinks it to 1456 x 819 so it fits 1,568 tokens, and the cost is 1,560. The high-resolution tier does not resize it, and the cost is 2,691. The same image costs 1.7 times more on the newer models, because they keep more detail. The page says high-resolution images can use about three times more tokens than on a standard-tier model.

After resizing, Claude pads the image up to the next multiple of 28 on the bottom and right. The padding holds no content.

What to notice. Doubling both sides of an image roughly quadruples its patches, until the cap stops the growth. Past the cap, extra pixels cost nothing but also add no detail. So send images at or below the cap. A smaller image can read worse, so test text legibility on your own pages.

### A PDF is text plus an image

A PDF page has two sources of information: a text layer, if the file has one, and the page graphics. The PDF page of Anthropic's docs says each page is processed as both text and image. Many Claude models accept PDFs directly. The limits are 32 MB per request and 600 pages, or 100 pages when the context window is under 1M tokens. Dense pages can fill the context before the page limit.

<Ai3FilePdfWalk client:visible />

The page does not give a token count per page for the direct API. It does give one data point for Amazon Bedrock. A 3-page PDF takes about 1,000 tokens as text only. With page images, the same PDF takes about 7,000 tokens. Do not budget from that figure for another setup. Measure your own files with the token counting endpoint, which accepts base64 images and PDFs. It does not accept `url` or `file` sources.

### Which format, by content

| Content | Best input | Why |
|---|---|---|
| Clean text, no layout needed | Extract text yourself, send text | Cheapest. Exact characters. |
| Tables, forms, stamps, charts | Page image or PDF | Layout carries meaning |
| Scan with no text layer | OCR first when you need exact values; image when you need layout | The model reads pixels. It can misread digits. |
| Word, Excel files | Convert to text or PDF | A `docx` is not a supported document block type |

Here is the invoice example with illustrative numbers. Suppose one invoice page is 1240 x 1754 px. The page is an A4 scan at about 150 DPI. The page holds about 600 tokens of text. As text, it costs about 600 tokens. As an image on a high-resolution model, it costs 45 x 63 = 2,835 tokens. As a PDF, it costs the text plus a page image, so more than either. At $2 per 1M tokens (Sonnet 5.5 input), that is about $0.0012, $0.0057, and up to about $0.0069 per page. The text figure is an assumption. The image figure follows the formula.

### Upload once, refer by id

The Files API stores a file and returns a `file_id`. An image or document block can then point at the id with `"type": "file"`. This keeps the request small. Facts from the Files page:

- Up to 500 MB per file and 1 TB per organization.
- Upload, list, get, and delete calls are free. File content used in a Messages request is billed as input tokens, every time.
- Files persist until you delete them. `expires_in_seconds` can set an expiry from 1 hour to 90 days.
- About 500 file calls per minute.

Upload does not make an image cheaper. The tokens are the same. It removes the bytes from the request, not the tokens from the bill.

The Files page warns that uploaded files are open to the whole workspace, not to one end user. Never accept a `file_id` from a user. Keep your own map of user to file, and use one workspace per tenant when tenants must be separate.

### Check before you send

Run these checks in your own code. A rejected request wastes a round trip.

- Image count: 100 per request for models with a 200K context window, 600 for others. Max 8000 x 8000 px per image.
- Over 20 images in one request, a stricter per-image dimension limit applies. It counts images from earlier turns and images inside tool results. Keep each side at or below 2000 px.
- Image size: 10 MB base64 on the direct API. 5 MB on Bedrock and Google Cloud.
- Formats: JPEG, PNG, GIF, WebP. An animated GIF uses its first frame only.
- Request size: 32 MB on the Messages API.
- Heavy JPEG compression can make small text unreadable. Look at the image you actually send.

Pre-processing is the best saving. Crop to the region that holds the answer. Downscale to the cap. Run OCR for plain text. A crop of a totals box can cost a tenth of the full page and read better. Vision internals are in lesson A12.1.

<Callout type="deep" title="Files can carry instructions">
An image or PDF can hold text that tells the model what to do, in white-on-white print or tiny type. The model reads it like any other input. Treat file content as untrusted data. Lesson [A10.2](/learn/ai/a10-safety/prompt-injection/) covers defenses. For now, keep tools that have side effects out of any call that reads files from unknown senders.
</Callout>

## Numbers

Here is the chain for a batch of scans. All figures are derived with the formula above. Prices are input prices, as of 2026-10-16.

| Case | Tokens per image | Cost per 1,000 images |
|---|---|---|
| 1000 x 1000 on Haiku 4.5 ($1) | 1,296 | $1.30 |
| 1000 x 1000 on Opus 5.5 ($4) | 1,296 | $5.18 |
| 4K (3840 x 2160) on Opus 5.5 ($4) | 4,784 | $19.14 |
| 1240 x 1754 on Sonnet 5.5 ($2) | 2,835 | $5.67 |
| Same page at 50% (620 x 877) on Sonnet 5.5 | 736 | $1.47 |

The first three rows match the vision page's own cost examples. The last two are derived. These costs are input only. Output tokens and any text you send add to them.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Send extracted text | Cheapest, exact characters | Loses layout | Clean digital text |
| Send full-size image | Maximum detail | Tokens up to the cap | Dense charts, small print |
| Downscale or crop first | Fewer tokens, faster calls | May lose small text | Most pipelines |
| Send PDF directly | No rasterizing code | Text plus image per page, page limits | Mixed pages, quick start |
| Files API `file_id` | Small requests, reuse | Workspace-wide access, storage to manage | Many turns on the same file |

## Interview lens

<Callout type="tip">
Say the formula and the cap: "An image is patches of 28 by 28. So tokens are the width and height in patches multiplied, capped by the model's tier. I would crop and downscale first, then upload once by file id. I would run a token count on a sample to set the budget." Then give one number, such as 2,835 tokens. That figure is for an A4 scan at 150 DPI on a high-resolution model.
</Callout>

<Callout type="mistake">
Do not budget images with an old pixel-area rule. Do not assume one number for all models, because the tier changes the cap. Do not accept a `file_id` from a user. And do not forget that a PDF page costs text and image, not one or the other.
</Callout>
