## The problem

A model knows what it learned in training. It does not know today's weather, your customer's order status, or the result of a SQL query. It also cannot send an email or refund a payment. Text in, text out.

To be useful in a product, a model must reach your systems. The question is how, without handing it the keys. This lesson covers the call protocol. Lesson [A6.5](/learn/ai/a6-agents/tool-design/) covers how to design tools for agents. Module A6 covers the agent loop built on top of this protocol.

## The idea: the model asks, your code acts

Here is the whole idea in one sentence. The model never executes anything. It writes a structured request, such as "call `get_weather` with city Paris". Your code reads the request and decides whether to run it. Your code runs it and sends the result back as input for the next model call.

A backend engineer knows this shape. It is a **remote procedure call** where the caller is a probabilistic text generator, and the server is your code. The model is the client, your code is the dispatcher, and the real work happens in your process. You hold every check: who is allowed, which arguments are valid, what the timeout is.

There are four steps, and they repeat:

1. You call the model with the user's message and a list of tool definitions.
2. The model replies with a request for one or more tools.
3. Your code runs them and collects the results.
4. You call the model again with the results added to the history. The model either answers or asks for more tools.

## Defining a tool

A tool definition has a `name`, a `description`, and an `input_schema` in JSON Schema. The Anthropic docs say the name must match `^[a-zA-Z0-9_-]{1,128}$`. Each tool description should say what the tool does, when to use it, and when not to. The description should also explain what each parameter means. They advise at least 3 to 4 sentences per tool.

```json title="tool-definition.json"
{
  "name": "get_weather",
  "description": "Get the current weather in a given location",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "The city and state, e.g. San Francisco, CA" },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["location"]
  }
}
```

This is the docs' own example. Its description is short, so treat it as a shape, not as a model to copy. The model sees your definitions as text. The API builds a special system prompt from them. So a vague description is the first cause of wrong calls. Each `input_examples` entry adds about 20 to 50 tokens for a simple example. A nested example adds 100 to 200 tokens. These figures come from the docs.

## The round trip on the wire

When the model wants a tool, the response has `stop_reason: "tool_use"` and one or more `tool_use` blocks. Each has an `id`, a `name`, and an `input` object:

```json title="response.json"
{
  "stop_reason": "tool_use",
  "role": "assistant",
  "content": [
    { "type": "text", "text": "I'll check the current weather in San Francisco for you." },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_weather",
      "input": { "location": "San Francisco, CA", "unit": "celsius" }
    }
  ]
}
```

Your reply is a new `user` message. It holds a `tool_result` block that points to the call by `tool_use_id`:

```json title="next-request-message.json"
{
  "role": "user",
  "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A09q90qw90lq917835lq9", "content": "15 degrees" }
  ]
}
```

Two format rules from the docs cause most 400 errors. First, the `tool_result` message must come directly after the assistant message with the `tool_use`. No other message can sit in between. Second, in the user message, `tool_result` blocks must come first. Text goes after them. A text block before a result returns a 400. The Claude API has no separate `tool` role. Tool use and results live inside the `assistant` and `user` messages.

OpenAI's Responses API does the same with other names. The model's request is an output item of type `function_call` with a `call_id`, a `name`, and `arguments` (a JSON string). You answer with an input item of type `function_call_output` that carries the same `call_id` and an `output` string. The idea, the link by id, and the loop are the same, so a thin adapter can hide the difference.

## Parallel calls

A reply can hold several `tool_use` blocks. By default Claude may call multiple tools in one response. The docs say the API does not prescribe an execution order. You can run them at the same time, one after another, or in a mix. Independent read-only calls are usually safe to run in parallel. Calls with side effects or order needs may be better run one by one.

The rule you cannot bend: return one `tool_result` for each `tool_use` block, all together in the next user message. If you skip a call (say you ran them in order and an early one failed), still send a result for it with `is_error: true` and a short reason, for example "Not executed: the preceding write_file call failed." Skip it entirely and the API returns a 400.

To stop parallel calls, set `disable_parallel_tool_use: true` inside `tool_choice`. With `auto`, that means at most one tool per response. OpenAI's switch is `parallel_tool_calls: false`, which gives exactly zero or one call.

## Choosing when the model calls

`tool_choice` controls whether the model may, must, or must not call a tool. The Anthropic docs list four options. `auto` (the default) lets the model decide. `any` makes it use one of the tools. `tool` forces one named tool. `none` blocks tool use. There is a catch. The define-tools page says that `any` and `tool` return a 400 error. The error happens on Claude Opus 5.5, Sonnet 5.5, Fable 5.1, and Mythos 5.1. On those models, use `auto` with strict tool use (`strict: true`) so the tool input matches your schema. Or use structured output (lesson [A3.3](/learn/ai/a3-llm-apis/structured-output/)) when you need a fixed reply shape. Forcing a tool also skips the thinking block on models that accept it.

OpenAI's `tool_choice` takes `"auto"`, `"required"`, or a named function. The parameter also takes `allowed_tools` with a mode and a list. The value `"none"` imitates passing no functions. With `strict: true`, OpenAI needs `additionalProperties: false` on each object. OpenAI also needs every property listed in `required`. Write optional fields as a type that also allows `null`.

## Errors are results

A tool will fail. The network drops, a record is missing, a rate limit hits. What should your code do? Not throw. Return the error to the model as a result:

```json title="error-result.json"
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "content": "ConnectionError: the weather service API is not available (HTTP 500)",
  "is_error": true
}
```

The docs say the model will then use the error in its reply. They also say to write instructive errors. Instead of `"failed"`, give what went wrong and what to try next, like "Rate limit exceeded. Retry after 60 seconds." For invalid calls, such as a missing required parameter, the docs say Claude usually retries 2 to 3 times with corrections before it apologizes. Strict tool use avoids this class of failure by making inputs match the schema.

Notice the vague-error case. If the tool says only "failed", a model may call it again. The docs I read set no iteration cap, so you must set one. A loop cap is a plain counter in your code: after N tool rounds, stop and return what you have. Choose it from the longest real task you expect, plus a margin.

## Why the model never runs anything

This design is a security boundary. Your code sits between the model and your systems, and it can:

- **Check the call.** Is this tool allowed for this user? Do the arguments make sense? A model that was fed text from a web page may ask for something the user never wanted.
- **Limit the power.** Give a read-only tool read-only credentials. Put a human approval step in front of a refund.
- **Treat results as untrusted input.** The docs warn that tool results often carry content from outside your control. Examples include web pages, inbound email, uploads, and third-party APIs. An attacker can embed instructions in that content to redirect the model. This is **indirect prompt injection**. The docs advise keeping untrusted content inside `tool_result` blocks, not in the system prompt. Module A10 covers it fully.
- **Make side effects safe to repeat.** A retry can run a tool twice. Lesson [A3.6](/learn/ai/a3-llm-apis/limits-retries-idempotency/) gives each tool call an idempotency key.

The mistake to avoid is trusting the arguments. The model's `input` is data from a probabilistic text generator, shaped by whatever it read. Validate it like any request from the outside world.

## Cost of a loop

Every round is a full model call, and the API is stateless (lesson [A3.1](/learn/ai/a3-llm-apis/api-anatomy/)). So each call resends the history, including every earlier tool result. A tool that returns a big JSON blob pays for it again on every later call. Say a search tool returns 20,000 tokens in round 1. The task runs 6 more model calls in the same conversation. At $4 per million input tokens (Opus 5.5, claude.com/pricing, 2026-10-16) with no caching, those 20,000 tokens cost 20,000 x 6 x $4 / 1M = $0.48 extra. Prompt caching (lesson [A2.5](/learn/ai/a2-inference-cost/prompt-caching/)) cuts it, and trimming the tool result cuts it more.

This is why tool output must be small and useful. Anthropic's tool-writing guide gives two examples of good practice. A tool that can answer in a concise mode used about one third of the tokens of the detailed mode (72 against 206 tokens in their example). And Claude Code restricts tool responses to 25,000 tokens by default. The guide also suggests pagination, range selection, filtering, or truncation, with helpful instructions to the agent if you truncate. The define-tools docs add these tips. Return only high-signal fields, and use stable identifiers. Group related actions into fewer tools. Prefix names with the service, such as `github_list_prs`.

## From one tool call to an agent

An **agent** is this loop with the exit decided by the model. The steps are: call the model, run the tools it asks for, and send the results. Repeat until `stop_reason` is `end_turn` or your cap fires. This lesson stops at the protocol. Module A6 covers planning, state, and when a loop is the wrong shape. Keep the loop short and the cap explicit until then.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Parallel tool calls | Lower latency for independent reads | Harder error handling, ordering bugs | Independent, read-only tools |
| Sequential execution | Simple, safe order | Slower | Writes, or calls that depend on each other |
| `auto` with strict tools | Valid inputs, model decides when | No forced call on some models | Most designs on current Claude models |
| Forced tool (`any` or `tool`) | A tool call every time | Returns 400 on some models, skips thinking | Older models that accept it |
| Detailed tool results | More facts for the model | More tokens, resent every round | The model needs the detail |
| Concise tool results | Fewer tokens, cheaper loops | The model may need another call | Most results |

## Interview lens

<Callout type="tip">
Say the boundary out loud: "The model proposes, my code disposes. It emits a tool_use, I validate the arguments and check permissions, run it with a timeout, and return a tool_result. Errors go back as is_error results with a next step. The loop has a cap, and tool output is size-limited because every result is resent on later calls." That covers protocol, safety, and cost in four sentences.
</Callout>

<Callout type="mistake">
Do not say "the model calls the API". It does not. It writes text that your code parses and acts on. Also do not trust tool inputs or tool outputs: both can carry attacker-shaped text. And do not leave the loop without a cap.
</Callout>
