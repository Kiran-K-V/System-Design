## The problem

A team must tag 2 million product descriptions with categories. The job is a one-time backfill. Nobody is waiting for any single answer. They write a loop that calls the model once per item.

The loop has three costs. It pays the full price. It competes with the live product for the same rate limits. So a long backfill can push real users into 429 errors. And it needs retry, pacing, and resume code that the team must write and run for days.

Many LLM jobs do not need an answer now. For those, providers offer a batch API: submit a file of requests, come back later, and pay about half. Facts about Anthropic come from its batch, rate limits, and prompt caching pages, fetched on 2026-10-16. Prices are USD per 1M tokens.

## Naive solution: loop over sync calls

```
for item in items: save(call_model(item))
```

It works for 100 items. At scale it breaks. A crash at item 1,400,000 means a restart from a checkpoint you must have built. Rate-limit retries ([the Rate Limits, Retries, and Idempotency lesson](/learn/ai/a3-llm-apis/limits-retries-idempotency/)) slow it down and make it fragile. A big `max_tokens` and a long call can hit network timeouts. Anthropic's errors page suggests the Batches API for long requests, because you poll for results instead of holding a connection.

## The mechanism: submit, poll, collect, retry

<CrossTrackLink id="06-async/queues">
A queue decouples the producer from the consumer. The producer adds work and moves on. Workers take work at their own pace. A batch API is a managed queue. You are the producer, and the provider runs the workers and holds the results.
</CrossTrackLink>

### The lifecycle on Anthropic

1. **Build the list.** Each request has a `custom_id` and a `params` object, which is a normal Messages request. The `custom_id` is 1 to 64 characters: letters, digits, hyphen, underscore.
2. **Submit.** One call creates the batch. A batch is limited to 100,000 requests or 256 MB, whichever comes first. `processing_status` starts as `in_progress`.
3. **Poll.** Check the status until it is `ended`. The page describes polling. It does not describe a webhook, so check before you design around one. A scheduled job that polls every few minutes is enough.
4. **Collect.** Stream the results file from `results_url`. It is `.jsonl`, one result per request. Results may come back in any order, so you must join on `custom_id`.
5. **Handle failures.** Each result is `succeeded`, `errored`, `canceled`, or `expired`. Resubmit the rest.

Time and retention, from the page: most batches finish in under 1 hour. Results are readable when every request has finished or after 24 hours, whichever comes first. A batch expires if it is not complete in 24 hours. Results stay downloadable for 29 days after creation, so copy them into your own store.

Rules that cause surprises:

- Params are validated asynchronously. A bad request is reported only when the batch ends. Run one request through the normal API first.
- `max_tokens: 0` is not allowed in a batch. `stream: true` and fast mode (`speed`) are not supported.
- Errored, canceled, and expired requests are not billed.
- A batch can go slightly over your workspace spend limit, because of concurrent processing.
- Processing can slow down with demand. The page warns that more requests may expire after 24 hours in that case.

### Separate limits

The Message Batches API has its own limits, shared across models. One is a requests-per-minute limit. Another is a cap on batch requests waiting in the queue. The cap is 200,000 on the Start tier, 300,000 on Build, and 500,000 on Scale. The last limit is the 100,000 per batch. These are separate from the RPM, ITPM, and OTPM that your live traffic uses. A backfill in a batch does not drain the live bucket. This is a larger reason to use batch than the discount. The reason applies when you share an organization with a product that has users.

### Price

Anthropic charges 50% of the standard price on all usage in a batch. Prices as of 2026-10-16, from the [batch page](https://platform.claude.com/docs/en/build-with-claude/batch-processing) and [claude.com/pricing](https://claude.com/pricing):

| Model | Sync in / out | Batch in / out |
|---|---|---|
| Opus 5.5 | $4 / $20 | $2 / $10 |
| Sonnet 5.5 | $2 / $10 | $1 / $5 |
| Haiku 5.5 (prompt up to 100K tokens) | $0.10 / $0.50 | $0.05 / $0.25 |

The discount stacks with prompt caching. Cache reads cost 0.05 times the base input price on Opus 5.5 and Sonnet 5.5. On Haiku 5.5, they cost 0.1 times the base price. So a cached batch input token on Sonnet 5.5 costs $0.05 per 1M, down from $2. A batch runs requests concurrently, so cache hits are best effort. The page says hit rates typically run from 30% to 98%. To raise them, put identical `cache_control` blocks in every request. Keep a steady stream, and share as much content as you can. Also consider the 1-hour cache duration. The reason is that a batch can take longer than the 5-minute default lifetime. The [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson covers caching.

### Other providers

The idea is the same. The numbers differ, so keep them in config, not in code. As of 2026-10-16:

| Provider | Discount | Window | Limits | Results kept |
|---|---|---|---|---|
| Anthropic ([page](https://platform.claude.com/docs/en/build-with-claude/batch-processing)) | 50% | 24 h, then expire | 100,000 requests or 256 MB per batch | 29 days |
| OpenAI ([page](https://developers.openai.com/api/docs/guides/batch)) | 50% | 24 h (the only option now) | 50,000 requests, 200 MB file, 2,000 batches per hour | Output file deleted 30 days after completion |
| Google Gemini ([page](https://ai.google.dev/gemini-api/docs/batch-api)) | 50% | Target 24 h, expires after 48 h pending or running | Inline total under 20 MB, file up to 2 GB | 6 weeks |

OpenAI says you are charged for tokens consumed by the completed requests of an expired batch. Failed requests go to an error file, and expired ones carry the code `batch_expired`. Output order may not match input order there either. Use `custom_id`.

### Run it safely

A batch job is a distributed job, so give it the properties from [the Rate Limits, Retries, and Idempotency lesson](/learn/ai/a3-llm-apis/limits-retries-idempotency/).

- **Make submit idempotent.** Creating a batch twice costs twice. Save your own job row with a unique `job_id` before you submit. Then store the returned batch id on that row. After a crash, look up the row. Do not submit again if it holds a batch id.
- **Design the `custom_id`.** Use a stable key such as `job_id:item_id`, within 64 characters. A retry batch then reuses the same ids. A write to your store keyed by `custom_id` overwrites instead of duplicating.
- **Chunk by limits.** A job bigger than one batch must be split into several. Respect the queue cap, and submit in waves.
- **Validate first.** Send a handful of requests to the sync API with the same params.
- **Check completeness.** After download, compare the set of `custom_id` values with your input set. Anything missing or not `succeeded` goes to the retry list.

### When batch fits

| Fits | Does not fit |
|---|---|
| Evals and regression runs over a golden set | A chat or a form where a user waits |
| Backfills, re-tagging, re-embedding a corpus | A step in an agent loop that needs the last result |
| Nightly summaries and enrichment | Anything with a latency target under a few minutes |
| Bulk classification and extraction | Work that must finish by a fixed time without slack |

An agent run is a chain: each step needs the previous answer. Running one step per batch adds up to a day per step. You can batch many independent runs, one step at a time, but the wait per step stays.

<Callout type="deep" title="Batch is a spot-like tier">
Cheaper capacity that can be late is a common cloud pattern. Spot instances work this way. You get a lower price in return for giving up a promise about when. Treat the 24-hour window as a ceiling, not an estimate, and give your pipeline slack for it.
</Callout>

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Sync loop | Instant results, simple | Full price, shares live limits, resume code | Small jobs, user waiting |
| Batch | Half price, own limits, managed queue | Up to 24 h wait, late validation, partial failures | Evals, backfills, enrichment |
| Batch with caching | Stacked savings | Prompt layout work, best-effort hits | Many requests share a big prefix |
| Own queue and paced sync | Control over timing | You build and run it | Jobs with a deadline shorter than the window |

## Interview lens

<Callout type="tip">
Say: "This job has no user waiting, so I would run it as a batch. It costs 50% less and uses separate limits, so it does not hurt live traffic. I would key each request with a stable custom_id, poll for the status, join results by id, and resubmit failures. I would keep a job row so a restart does not submit twice." Then name the cost: the same job is half price as a batch.
</Callout>

<Callout type="mistake">
Do not use batch for anything a user is waiting on. Do not assume the results are in input order. Do not skip a sync test of the params, because errors come late. And do not forget to copy results out before the retention period ends.
</Callout>
