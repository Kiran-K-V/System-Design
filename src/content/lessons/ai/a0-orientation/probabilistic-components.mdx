## The problem

A backend function has one contract: same input, same output. Your tests rely on it. Your retries rely on it. Your cache relies on it.

A model call breaks that contract. Send one prompt twice and you may get two different answers. Set the temperature to 0, and you may still get two.

This is not a bug you can fix once. It is a property of the component. You must design around it, the way you design around a network that drops packets. This lesson gives the four consequences, the math that shows how fast they add up, and the design rules that follow.

## Naive solution: set temperature to 0

The common fix is "set the temperature to 0 and it will be deterministic". Temperature controls how random the choice of the next token is. At 0 the model picks the most likely token every time.

It does not work, and there is a measurement. Thinking Machines sampled 1,000 completions of the prompt "Tell me about Richard Feynman" from Qwen3-235B-A22B-Instruct-2507 at temperature 0, 1,000 tokens each.

| Result | Value |
|---|---|
| Unique completions | 80 |
| Most common completion | appeared 78 times |
| First tokens that were identical | 102 |
| Split at token 103 | "Queens, New York" in 992 runs, "New York City" in 8 |

The cause they found is that GPU kernels are not batch invariant. A kernel is the low-level routine that does the math. Batch invariant means it returns the same numbers whatever the batch size. Batch size changes with server load, so your output depends on how many other users are on the machine. With batch-invariant kernels all 1,000 completions matched. The price: for Qwen3-8B on one GPU, 1,000 requests took 26 s with the default vLLM setup, 55 s with an unoptimized deterministic setup, and 42 s with an improved kernel. That is about 1.6 times the default time (derived: 42 / 26).

So even "deterministic" settings give you a distribution unless the serving stack is built for it. Treat every output as a draw from a distribution.

## Four consequences

**1. Outputs need a pass rate.** You cannot say "this prompt works". You say "this prompt passes 92% of 200 cases". Lesson [A0.2](/learn/ai/a0-orientation/ai-design-method/) called this the quality bar.

**2. Retries can change results.** A retry of a failed function call gives the same failure. A retry of a model call may give a better answer, or a different wrong one. That makes retries a tool for quality, not just for transient errors. It also means a retry may not reproduce a bug.

<CrossTrackLink id="07-reliability/timeouts-retries">
The backend track covers timeouts, retries, and backoff for calls that fail from network trouble. Those rules still hold for model calls. The AI-specific change is that a retry of a model call can also change the content of the answer.
</CrossTrackLink>

**3. Errors compound across steps.** An agent or pipeline calls a model several times. If each step must be right, the chances multiply.

**4. Tests become statistics.** A test passes or fails once. An eval runs many trials and reports a rate with a margin of error. Anthropic's guide on agent evals gives two ways to summarize several tries. **pass@k** is the chance at least one of k tries succeeds. **pass^k** is the chance that all k tries succeed. At a 75% rate per try and k = 3, pass^3 is 0.75 to the power 3, about 42%. The same tries give pass@3 of 1 minus 0.25 cubed, about 98% (derived). The first number matters when the user sees each try. The second matters when you can pick a good one.

## The math of compounding

If each of n steps succeeds with probability p, and all must succeed, the chance of a clean run is:

<Math block tex="P(\text{success}) = p^{n}" />

In words: multiply p by itself n times. The steps are assumed independent.

| Per-step p | Steps n | End to end |
|---|---|---|
| 95% | 10 | 59.9% |
| 90% | 10 | 34.9% |
| 95% | 20 | 35.8% |
| 99% | 20 | 81.8% |

All four rows are derived from the formula, not measured. Read the first row: a component that is "95% good" gives a pipeline that fails four runs in ten. Anthropic's guide on building agents says agents "cost more and risk compounding errors". The table puts a number on that.

The model behind the simulator is simple. A verifier checks each step output. It catches a bad one with some probability. On a catch, the step retries, up to the retry limit. A bad answer that the verifier misses passes on and counts as a failure. The simulator ignores the cost of the extra calls, and it assumes attempts are independent. Real failures are often correlated: a prompt that confuses the model once will confuse it again. So treat the verified numbers as an upper bound.

## Design rules

Three rules follow from the math.

1. **Shorten the chain.** Every step you remove multiplies the success rate by 1 / p. Merge two steps into one call when the model can do both.
2. **Add checks where errors are cheap to catch.** A schema check on JSON output costs almost nothing and catches many failures. A model as judge costs a model call. A retest against a small set of rules costs milliseconds.
3. **Keep a human path.** When the check fails twice, hand off. Say what share of requests reach the human, because that share is a staffing cost.

Real failures show the human path is not optional. In 2024 an Air Canada chatbot gave a passenger wrong bereavement-fare advice. The tribunal held that the airline "did not take reasonable care to ensure its chatbot was accurate". In 2023 a New York court fined two lawyers $5,000 for a brief with cases ChatGPT had invented. In both, an automated step had no check and no human gate.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Fewer, larger steps | Higher end-to-end rate | Harder prompts. Harder to debug which part failed. | When one call can do both parts |
| Verifier plus retry | Large gain in rate | More latency and cost per step | When a bad answer is costly |
| Deterministic serving | Repeatable outputs for debugging | About 1.6x time in the Thinking Machines test | When you must reproduce a result |
| Human review | Highest trust | Staff cost, slow | High-risk actions |

## Interview lens

<Callout type="tip">
When someone proposes a ten-step agent, say: "If each step is 95% reliable, ten steps give about 60% (0.95 to the power 10). I would cut steps, add a check after the risky ones, and route low-confidence cases to a person." One line of arithmetic shows you think in rates.
</Callout>

<Callout type="mistake">
Do not say "temperature 0 makes it deterministic". The Thinking Machines test found 80 different outputs in 1,000 runs at temperature 0. Do not say "pass rate is 95%, so the agent is 95% reliable". That is the per-step rate. Do not add a model-as-judge check and call the step perfect: the judge has its own error rate.
</Callout>
