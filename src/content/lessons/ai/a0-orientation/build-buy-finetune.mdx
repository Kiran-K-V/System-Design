## The problem

You have a quality bar, an eval, and a budget (the [AI Design Method](/learn/ai/a0-orientation/ai-design-method/) lesson). Now step 4: where does the model come from? There are four options. Each costs more effort than the one before.

1. Use no model. Rules or a heuristic.
2. Buy: call a hosted model through an API, with a prompt.
3. Adapt: add retrieval so the model sees your facts, or fine-tune it on your examples.
4. Build and run: host a model on your own GPUs.

A common mistake is to jump to the last two because they feel serious. The right order is the reverse. Take the cheapest option that clears the bar, and move down only when the eval shows a gap.

## Naive solution: fine-tune to teach the model our facts

A team has a product with thousands of policy documents. They think: the model does not know our policies, so we will train it on them. It feels natural. It fails in two ways.

First, facts change. Weights are fixed at training time. A policy that changes on Tuesday stays old in the model until the next training run. Second, fine-tuning is poor at storing exact facts. OpenAI's guide on model optimization splits the problem this way: prompting fixes missing knowledge, unclear goals, and output format. Fine-tuning fits when you need consistent behavior or format, or need shorter prompts at scale. Facts belong in the context, not in the weights.

## The mechanism: a decision tree

The tree has five questions, from cheapest to most expensive. A "yes" stops the walk. A "no" moves down.

<Ai0DecisionTree client:visible />

**Row 1: rules first.** Google's Rules of Machine Learning, Rule 1, reads "Don't be afraid to launch a product without machine learning." If a simple heuristic gets you part of the way, launch with it. It gives you data, a baseline, and a metric. Rule 4 adds a point about a simple first model. That model "provides you with baseline metrics and a baseline behavior" to test fancier ones against.

**Row 2: hosted API and a prompt.** Start here for most GenAI work. You pay per token, you run nothing, and you can change model by changing a string. Anthropic's agent guide gives the stance: find the simplest solution, and add complexity only when needed.

**Row 3: retrieval.** If answers fail because the model lacks facts, put the facts in the prompt. Retrieval fetches the relevant text at request time. Updates take effect when the document changes. This track covers retrieval later.

**Row 4: fine-tuning.** Fine-tuning means more training on your own examples. Use it when prompts cannot fix the behavior or format, when you need shorter prompts, or when a small tuned model can replace a big one. OpenAI's guide lists these reasons. One reason is that there are more examples than fit in a context window. Others are shorter prompts, proprietary data kept out of requests, and a smaller cheaper model for a narrow task. Hamel Husain says 99% of the labor in fine-tuning is assembling high-quality data. Budget for that, not for the training run. One more risk: the same OpenAI guide says its fine-tuning is no longer accessible to new users. A fine-tune can sit on a platform that changes its terms.

**Row 5: self-hosting.** Run an open model on GPUs you rent or own. Three things can force it: **privacy** (data may not leave your network), **unit cost at volume**, and **latency** (a model close to the user, or a small model for a tight budget). Next: the cost question.

## Numbers: API against a GPU

Prices are USD, as of 2026-10-15.

API output prices, per 1M tokens, standard tier:

| Provider and model | Output price | Source |
|---|---|---|
| Anthropic Haiku 5.5 (prompt up to 100K tokens) | $0.50 | claude.com/pricing |
| Anthropic Sonnet 5.5 | $10.00 | claude.com/pricing |
| Anthropic Opus 5.5 | $20.00 | claude.com/pricing |
| OpenAI gpt-6-luna | $0.50 | developers.openai.com/api/docs/pricing |
| OpenAI gpt-5.4-mini | $4.50 | developers.openai.com/api/docs/pricing |
| Google Gemini 2.5 Flash | $2.50 | ai.google.dev/gemini-api/docs/pricing |

GPU rental: Lambda lists H100 SXM at $3.99 per GPU-hour on demand for its largest configuration (lambda.ai/pricing). Smaller configurations are $4.09 to $4.29. RunPod's page (updated 2026-10-08) shows $3.49 secure and $2.69 community in its structured data, but its visible table shows $3.99. The two sources disagree, so this lesson uses Lambda and you should confirm on the console.

A rented GPU is billed by the hour. It costs the same whether it is busy or idle. An API is billed by the token, so an idle hour costs nothing.

So the cost per token on your own GPU depends on how busy you keep it. A fully busy GPU can make tokens cheaper than a small API model. A GPU that serves a spiky workload sits idle most of the day, and idle time is billed. At low use, the same GPU costs several times more per token (~4x at a quarter busy).

This gives a break-even. Below some level of steady use, the API is cheaper. Above it, the rented GPU is cheaper, if utilization holds. The level depends on the API price you compare with. One benchmark served Llama 3.1 8B on one H100 with vLLM. It is an 8B model on one setup. Your model, prompt size, and server will differ, so measure your own.

The estimate counts output tokens only and ignores input processing, batching limits, and quality differences.

Against a cheap API model the break-even needs high volume and high utilization. Against a $10-per-million model the GPU wins at a far lower volume. But the 8B model is not equal to Sonnet 5.5 in quality. Compare on your eval, not on price alone.

## Hidden costs

The estimate misses four terms.

- **Eval cost.** Every model you try needs the eval run on it. A judge model for grading is a second bill.
- **Lock-in.** Prompts tuned to one model drift when you change it. Fine-tunes tie you to the platform that hosts them.
- **Privacy.** A hosted API sends data to a third party. For regulated data this may rule the option out, and the cost comparison does not matter.
- **Operations.** Self-hosting means you handle GPU failures, scaling, upgrades, and on-call. Budget for two GPUs if you need failover, as the checkbox shows.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| Rules | Free, fast, auditable | Weak on free text | When a heuristic clears the bar |
| API plus prompt | No ops, quick start, best models | Per-token bill, data leaves your network | Default start |
| Retrieval | Fresh facts, citations | Pipeline to build and evaluate | When failures are missing facts |
| Fine-tune | Format and behavior, shorter prompts | Data labor, platform risk, stale facts | When prompts cannot fix behavior |
| Self-host | Privacy, low unit cost at high load | Ops, idle GPU cost, weaker models | Volume and utilization are high, or data cannot leave |

## Interview lens

<Callout type="tip">
Say the order out loud: "I would start with a hosted model and a prompt, measure it against the eval, add retrieval if the failures are missing facts, fine-tune only if behavior or format still fails, and self-host if privacy or volume forces it." Then name the break-even idea: self-hosting pays only when the GPU stays busy, so say how you expect to keep it busy.
</Callout>

<Callout type="mistake">
Do not fine-tune to add facts. Do not compare an API price with a GPU price at 100% utilization and call it done. Do not leave out the quality gap between an 8B open model and a frontier model. And do not quote a price without a date: these numbers change often.
</Callout>
