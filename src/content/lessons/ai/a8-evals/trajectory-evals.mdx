## The problem

You build a support agent that can look up orders, read the refund policy, and issue refunds. In the demo it handles ten requests well. You ship it. A week later finance finds 40 refunds on orders that were past the return window. The agent told each customer "your refund is on its way", and the customer was happy. Your eval, which checked only the final reply, was green.

An agent is not one model call. It is a loop ([lesson A6.1](/learn/ai/a6-agents/agent-loop/)): the model picks a tool, your code runs it, the model reads the result, and it picks again. Many steps happen between the question and the reply. A grade on the last message cannot see them.

This lesson answers five questions:

1. What exactly do we grade?
2. Can we trust what the agent says it did?
3. What should we grade besides the end state?
4. Does the agent pass every time, or only on average?
5. How do we run the repeats fairly?

The quality bar for the design is a number you can measure: the share of tasks where all repeat runs end in the right state. We will name it soon.

## Question 1: what exactly do we grade?

Four words, taught once, used all lesson.

A **task** is one job with a known right result, such as "refund order 1042 if the policy allows". A **trial** is one attempt at a task. Anthropic's guide on agent evals says it plainly: "Each attempt at a task is a trial." A **transcript** is the full record of a trial: every model output, every tool call, every tool result. It is the same idea as a log of one request through your backend.

A **trajectory** is the ordered list of steps in that transcript: call, result, call, result, reply. Picture a dashcam. The recording is the trajectory. Where the car ended up is the **outcome**. Anthropic defines the outcome as "the final state in the environment at the end of the trial".

Why do we need both words? Two cars can end at the same address, and one of them ran three red lights. The outcome tells you where you landed. The trajectory tells you how, and where it went wrong.

## Question 2: can we trust what the agent says it did?

No. The agent writes text, and text can say anything.

Anthropic's guide gives a flight example. A booking agent might end its transcript with "Your flight has been booked". Whether it was booked is a different fact: does a reservation exist in the database? A delivery driver who says "delivered" is not proof. The package on the doorstep is.

So there are two kinds of check on a run, and the difference matters.

### The naive way: a text check

A **text check** looks at what the agent wrote. It is the naive way, and it is what failed in our opening story. The reply said "refund", the check looked for the word "refund", and it passed.

### The real fix: a state check

A **state check** looks at the world the agent changed. It reads the database after the run and compares it with the single correct end state. The tau-bench benchmark does exactly this. Sierra, a company that builds customer-service agents, published tau-bench in 2024. It puts an agent in a simulated shop or airline, with a database and written rules, and talks to it through a simulated customer. Its reward is 1 only when "the final database is identical to the unique ground truth outcome database". The tasks are written so that only one end state is correct.

Why does this exist? A state check is a code check ([lesson A8.4](/learn/ai/a8-evals/judges/)), so it is exact, free, and the same every run. It also does not care how the agent got there. Anthropic's guide notes it is "often better to grade what the agent produced, not the path it took", because agents find valid paths you did not think of. In one case, a strong model "failed" a flight-booking task as written because it found a better solution than the one the task author expected. The guide calls it "a loophole in the policy".

One number: the tau-bench paper tested gpt-4o, a leading model of 2024, as a function-calling agent. It passed 61.2% of the retail tasks and 35.2% of the airline tasks on a single run. Those are scores from a state check, not from a friendly reply.

## Question 3: what else is worth a grade?

The outcome comes first. But three more things are worth a grade. Each gets its own idea.

### Idea 1: the outcome (a state check)

**What it is.** After the run, query the world and compare it with the expected end state: the refund table, the ticket status, the file on disk.

**Everyday picture.** A building inspector. The contractor says the wiring is done. The inspector opens the wall.

**Why it exists.** It is the only grade that cannot be fooled by fluent text.

**One number.** Our refund agent: expected state is "no refund on #1042, store credit of $80". Actual state: an $80 refund row. The check fails, whatever the reply said.

### Idea 2: the steps

**What it is.** Did the agent call the right tool, with valid arguments, without pointless repeats? For each step, a code check can test the tool name, the argument types, and whether the same call ran twice.

**Everyday picture.** A flight recorder. You read it after a crash to find the first wrong move.

**Why it exists.** The outcome says "fail". It does not say why. The first bad step is where you fix the prompt, the tool description, or the tool itself ([lesson A6.5](/learn/ai/a6-agents/tool-design/)). Step grades also catch a lucky pass: the right end state reached by a wrong route.

**One number.** In our run, 4 of 5 steps were fine. The one bad step, the refund call, is where the fix goes. Use a model judge on steps only for questions code cannot answer, such as "was this search query sensible?". Anthropic's guide says model graders are "non-deterministic" and need calibration against human graders, as [lesson A8.4](/learn/ai/a8-evals/judges/) shows.

### Idea 3: the efficiency

**What it is.** How many steps, tokens, dollars, and seconds the run used. Anthropic's guide lists "latency, token usage, cost per task, and error rates" as numbers you can track on a fixed set of tasks.

**Everyday picture.** Fuel use on the drive. Two cars arrive at the same place. One burned three times as much fuel.

**Why it exists.** An agent that reaches the right state in 40 calls instead of 5 costs eight times as much and takes eight times as long. Cost per task belongs on the same chart as pass rate. A change that raises the pass rate by two points and triples the cost is a decision, not a free win.

**One number.** [Lesson A7.2](/learn/ai/a7-agents-prod/loop-control/) works an illustration: 200 steps that each carry 30,000 tokens of context send 6 million input tokens. At Sonnet 5.5's $2 per million input tokens, that is $12 for one run, with no caching.

### Idea 4: the safety

**What it is.** A list of actions the agent must never take, checked on every run: refunding outside policy, deleting a record, calling a tool it was not given for this task.

**Everyday picture.** The red lights in the dashcam recording. Reaching the address is not enough if you ran three of them.

**Why it exists.** The outcome check can pass while a rule is broken on the way. The tau-bench authors point this out themselves: a correct final database is necessary but not sufficient, because an agent can write to the database without the customer's confirmation. So safety gets its own grade, usually as code checks on the transcript.

**One number.** A refund over the policy limit is a zero-tolerance failure. Count it separately and show it on the dashboard as its own line. It does not average away.

## Question 4: does the agent pass every time, or only on average?

Run the same task five times. A language model samples its words by chance, so the five trajectories differ. Maybe the agent gets it right three times and wrong twice. One run per task tells you nothing about that.

Two measures answer two different questions. Both come from the same set of trials.

**pass@k** is the chance that at least one of k attempts succeeds. Picture a basketball player taking k shots at the hoop and counting a point if any goes in. It fits cases where a person picks the best of several tries, such as code suggestions. **pass^k** (said "pass hat k") is the chance that all k attempts succeed. Picture a pilot who must land safely on all k flights. It fits cases where every user gets one run and every run must be right, such as a refund agent.

Why does it exist? Customers do not get the best of eight tries. Each gets one. If the agent works 75% of the time per attempt, the chance that it works on three attempts in a row is 0.75 x 0.75 x 0.75 = 0.42. Anthropic's guide gives this exact example: "(0.75)³ ≈ 42%". A 75% agent is wrong in more than half of three-visit customer histories.

Real numbers from tau-bench. The paper reports that gpt-4o passed 61.2% of retail tasks on one run, and that the all-eight-runs rate (pass^8) for the same agent falls below 25%. Sierra's own write-up from March 2025 says early agents passed fewer than 50% of tasks, and about 25% when the same task was repeated eight times. The agent did not get worse. The measurement got stricter.

Is it just 0.612 to the power 8? Work it out: 0.612^8 = 0.0197, about 2%. The real value, under 25%, is far higher. Why? Because tasks differ. Some tasks pass nearly every run. Some never pass. The 61% is an average over very different tasks. In math terms, the average of p^k is not the same as the average of p, taken to the power k, and it is always at least as large. The widget below shows both cases with the same 61.2% average.

How do you compute it from real runs? Run n trials of each task. Say a task passed c times. The tau-bench paper gives an unbiased estimate of the chance that k fresh trials all pass:

<Math block tex="\widehat{\text{pass}^k} = \frac{\binom{c}{k}}{\binom{n}{k}}" />

Here <Math tex="\binom{n}{k}" /> means "the number of ways to choose k items from n". Example: n = 8 trials, c = 6 passes, k = 4. Then C(6,4) = 15 and C(8,4) = 70, so the estimate is 15 / 70 = 21%. The single-run rate for that task is 6/8 = 75%. You average the estimate over all tasks. You need n of at least k.

Read the "Mixed" case at k = 8. Half the tasks are solid, 30% are flaky, and 20% never pass. The mean pass rate is 61.2%, but the all-eight-pass rate is 21.7%. The 30% of flaky tasks are where an engineer should read transcripts, since a flaky task has both passing and failing runs to compare.

## Question 5: how do we run the repeats fairly?

Repeats only mean something if each trial starts from the same place.

**What it is.** Each trial runs in its own clean environment: a fresh copy of the database, no leftover files, no cached results from the last trial.

**Everyday picture.** A driving test where every candidate starts from the same car park spot. If the previous candidate left the car in a different gear, the second result is not comparable.

**Why it exists.** Shared state makes trials depend on each other. Failures arrive in bunches, and your pass^k looks worse than it is. Worse, it can look better. Anthropic reports seeing an agent gain "an unfair advantage on some tasks by examining the git history from previous trials".

**One number.** Cost. A run of 100 tasks with 8 trials each is 800 runs. At an illustrative $0.30 a run that is $240, and it takes real minutes per run. Start smaller. Anthropic's advice: "20-50 simple tasks drawn from real failures is a great start".

## Numbers

| Quantity | Value | Source |
|---|---|---|
| Per-run success, gpt-4o, retail tasks (2024) | 61.2% | tau-bench paper |
| All 8 runs pass, same agent, retail | under 25% | tau-bench paper |
| 75% per run, 3 runs in a row | 42% | Anthropic's guide |
| Same 61.2%, if every task were identical, k = 8 | 2.0% | derived: 0.612^8 |
| Eval cost, 100 tasks x 8 trials x $0.30 per run | $240 | illustrative |
| Starter set | 20 to 50 tasks from real failures | Anthropic's guide |

Latency budget: trials are independent, so run them in parallel. Wall time then equals the slowest run, not the sum. Cost per request of the eval itself is just the agent's cost per run, times k, times tasks. The design below names its bar: "pass^4 of at least 90% on the refund tasks, with zero safety failures", measured by state checks on a fresh environment per trial. The 90% is a product choice, not a law.

## Trade-offs

| Grader | You gain | You pay | Choose it when |
|---|---|---|---|
| State check on the outcome | Exact, cheap, cannot be fooled by text | Needs a seeded environment and a known end state | Always, first |
| Code checks on steps | Pinpoints the first bad step | Brittle to valid alternative paths | Debugging and safety rules |
| Model judge on the trajectory | Handles "was this reasonable?" | Noisy, needs human calibration | Only for what code cannot test |
| More trials per task (larger k) | Exposes flaky tasks, a stricter reliability number | Cost grows as tasks x k x cost per run | Customer-facing agents |

## What experienced teams know

1. **One pass rate hides an unreliable agent.** A model that passes most tasks on one run can still fail most tasks when you demand all runs. Sierra's data shows the fall from over 60% to about a quarter at eight runs, and says "the pass^k curves remain far from ideal". Report pass^k next to the single-run rate. Source: [Sierra on tau-bench](https://sierra.ai/blog/tau-bench-shaping-development-evaluation-agents).

2. **Read the per-task pass counts, not just the average.** pass^k is not the single-run rate raised to k. Uneven tasks give a far higher value. The tasks with some passes and some fails are your best debugging material. Source: [the tau-bench paper](https://arxiv.org/abs/2406.12045) and the derivation above.

3. **Text lies and rigid graders lie the other way.** An agent can say "booked" without booking. A grader can also fail a correct answer. Anthropic reports a score of 42% that became 95% after fixing grading bugs, one of which rejected "96.12" for expecting "96.124991...". Read transcripts from both passes and fails, or you will not know if the grader works. Source: [Anthropic on demystifying agent evals, 2026-01-09](https://anthropic.com/engineering/demystifying-evals-for-ai-agents).

4. **Isolate every trial.** Shared state creates correlated failures and unfair wins. Anthropic saw an agent read git history left by an earlier trial. Start each trial from a clean copy. Source: same Anthropic guide.

5. **A correct end state is necessary, not sufficient.** The tau-bench authors note an agent can reach the right database state without the customer's confirmation. Add explicit safety checks on the transcript: forbidden tools, missing confirmations, actions outside scope. Source: the tau-bench paper.

6. **Start with 20 to 50 tasks taken from real failures.** A small set drawn from [your own error analysis](/learn/ai/a8-evals/error-analysis/) beats a large generic one. Add a task each time production fails in a new way. Source: the Anthropic guide.

## Interview lens

<Callout type="tip">
Say: "I grade the outcome with a state check against a seeded environment, then steps, cost, and forbidden actions. I run each task several times in clean environments and report pass^k, since each user gets one run. I read the flaky tasks first." Add one number: a 75% agent is 42% over three runs.
</Callout>

<Callout type="mistake">
Do not say "I check that the reply says the task is done". Do not report only the average single-run pass rate. Do not use a model judge as the first grader of a trajectory: start with code checks on state, then calibrate any judge against human labels.
</Callout>
