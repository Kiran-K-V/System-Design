## The problem

A user asks an agent to fix a failing test and open a pull request. The run takes 6 minutes. It reads files, runs the test suite, edits code, and runs the suite again. The user closes the laptop after 30 seconds.

If the agent runs inside the HTTP request, this fails in three ways. Load balancers and browsers cut idle connections long before 6 minutes. A dropped connection loses the work, and the user pays for tokens that produced nothing. And 500 users at once need 500 open connections, each tied to a worker, so a burst becomes an outage.

Backend engineers solved this shape years ago. The agent version adds a few new parts: a sandbox for every run, a durable state store, cost caps, and a human who may need to answer in the middle.

<CrossTrackLink id="09-patterns/long-running-tasks">
Work that takes minutes cannot hold a request open. Accept the task and return a job id with HTTP 202. Run it on a worker. Let the client poll or subscribe. Leases and heartbeats let another worker take over a job if one dies. Every pattern in this lesson sits on that base.
</CrossTrackLink>

<CrossTrackLink id="06-async/queues">
A queue lets a producer hand work to workers and move on. It absorbs bursts and survives worker crashes, but it adds no capacity and delivers at least once. The visibility timeout hides a claimed message and then returns it if the worker is silent. That timeout is the part that matters most for runs that last minutes.
</CrossTrackLink>

## The mechanism: submit, queue, run, notify

The flow has five parts.

1. **Submit.** The API validates the request, stores a run record, enqueues it, and returns a run id at once.
2. **Queue.** The run waits, usually in a queue per tenant. It moves on when a worker is free and the tenant is under its limit.
3. **Worker and sandbox.** A worker claims the run and boots an isolated sandbox for it. The agent loop runs there (the [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) lesson covers the sandbox).
4. **Progress.** The agent writes each step to a trace. Clients poll the run id or subscribe to events.
5. **Finish.** The result is stored with the trace, and a notification goes out.

Step through one run, including the case where the agent needs a human.

<Ai7BgLife client:visible />

```python title="submit_run.py"
@app.post("/runs", status_code=202)
def submit(req: RunRequest, tenant: Tenant = Depends(auth)):
    run, created = db.get_or_create_run(
        tenant_id=tenant.id,
        idempotency_key=req.idempotency_key,       # a webhook retry must not start a second run
        task=req.task,
        budget_usd=min(req.budget_usd, tenant.max_run_usd),
    )
    if created:
        queue.enqueue(f"tenant:{tenant.id}", run.id)
    return {"run_id": run.id, "status_url": f"/runs/{run.id}"}
```

Two details in that handler matter. The idempotency key stops a retried webhook from starting two runs ([the Rate Limits, Retries, and Idempotency lesson](/learn/ai/a3-llm-apis/limits-retries-idempotency/) covers keys for model calls; the [backend idempotency lesson](/learn/backend/03-api-design/idempotency/) covers the general case). The budget is clamped to the tenant's maximum, so a caller cannot ask for an unlimited run.

### Triggers

A run need not start from a user click. Common triggers are a schedule, a webhook, and a new email or ticket. Claude Code's GitHub Action shows all three in one product. It runs on GitHub-hosted runners and starts from an `@claude` mention, from pull request events, or from a cron schedule. Its docs add rules that apply to any trigger design:

- Issue and pull request events need a user with write access. A schedule has no user, so that check is skipped.
- A bot actor is rejected unless you list it in `allowed_bots`. This keeps bots from triggering the agent in a loop.
- GitHub runs scheduled workflows only from the default branch. In public repositories, GitHub disables the schedule after 60 days without repository activity.
- Commits pushed with the default `GITHUB_TOKEN` do not trigger other workflows. If you expect CI to run on the agent's commits, authenticate differently.

### When the worker dies

A worker can crash 5 minutes into a 6-minute run. Two recovery styles exist. With a durable runtime (the [Durable Execution and the Graph Runtime](/learn/ai/a7-agents-prod/durable-graph-runtime/) lesson), state is checkpointed, and another worker resumes from the last checkpoint. With a plain queue, the message becomes visible again after the visibility timeout, and another worker runs the whole task. That second style needs idempotent steps, or the retry sends the email twice.

The timeout must fit the job. If a run takes 6 minutes and the timeout is 30 seconds, the queue hands it to another worker. This happens while the first worker is still working. The fix is a heartbeat or lease. The heartbeat or lease extends the timeout while the worker is alive. The long-running tasks lesson explains it.

### The output is a pull request

The agent should not push to the main branch. Every cloud agent product we checked ends in a reviewable artifact. Claude Code in the cloud works on a branch and lets you create a pull request. Codex cloud lets you review changed files and test results, then commit or open a pull request. Cursor's cloud agents push to a separate branch and "produce merge-ready PRs with artifacts". A human merges. That human step is the approval gate from the [Human-in-the-Loop](/learn/ai/a7-agents-prod/human-in-the-loop/) lesson, moved to the end of the run.

## What real products do

The primary docs agree on the main design, and differ in the details. All of what follows is from each vendor's own pages, as of 2026-10-16.

| Product | Where it runs | Notes from the docs |
|---|---|---|
| Claude Code GitHub Actions | GitHub-hosted runners | Consumes GitHub Actions minutes and API tokens. Docs advise `--max-turns`, workflow timeouts, and concurrency controls |
| Claude Code in the cloud | An isolated, Anthropic-managed VM per session | Keeps running after you close the laptop. Git credentials stay outside the VM, behind a proxy. Sessions run in parallel and share your plan limits |
| Codex cloud | A cloud environment with its own workspace per task | Tasks can keep running while your computer sleeps. Internet access is set per environment |
| Cursor cloud agents | Isolated VMs in the cloud | Environments come from a snapshot, a Dockerfile, or agent-led setup. Cursor manages capacity |

One detail from the Claude Code docs shows why state must be durable. A cloud session's VM is reclaimed after a period of inactivity. Reopening the session provisions a new VM. The conversation is restored, but background work that was still running, such as subagents and shell commands, is not. A run that waits for a human therefore cannot count on its VM surviving. Save state, and treat the sandbox as disposable.

## Many tenants, one pool

A shared worker pool has a weak spot. If tenant A submits 400 runs and tenant B submits 5, a single first-in, first-out queue serves A's 400 first. B waits behind a burst it did not cause.

The standard fixes are a queue per tenant, a concurrency limit per tenant, priorities, and fair share. Fair share means the scheduler takes one run from each tenant in turn. Priorities let a paid interactive run jump ahead of a nightly batch. Set a cost limit per queue as well, because a looping agent spends money even while it waits on nothing.

<Ai7BgFair client:visible />

Try a large burst from tenant A on a few workers. First in, first out makes B wait behind almost all of A's runs. With fair share, B's few runs start in the first rounds. The last run in either mode finishes at about the same time. Fair share adds no capacity. It decides who waits.

## Capacity and cost

Sizing a pool is Little's law: runs in flight equals arrival rate times time per run. Slower runs or more arrivals mean more workers busy at the same time. At exactly 100% busy, queue wait grows without bound, so you add headroom. Plan for a pool about twice the average need, to absorb bursts and boot time.

Cost has two lines. Model spend is bounded by the per-run cap, such as the `max_budget_usd` option in the Claude Agent SDK. The docs warn the last response can pass the cap by its own cost plus any running subagent spend. For that reason, leave margin. Sandbox spend is busy time times the sandbox price, plus idle capacity you keep warm. Boot time counts as busy time with no useful work in it.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Hold the request open | Simplest code | Timeouts, lost work, no scale | Runs under a few seconds |
| Queue and workers | Burst absorption, retries, no open connections | A status API and an event channel | Any run over about 30 seconds |
| Durable runtime resume | Continue from the last checkpoint | A runtime to operate | Long, costly, or human-gated runs |
| Visibility timeout and retry | Simple, uses the queue you have | Whole run repeats, needs idempotent steps | Short, safe-to-repeat runs |
| Sandbox per run | Isolation, disposable state | Boot time and cost per run | Agents that run code or tools |
| Per-tenant queues and fair share | A noisy tenant cannot starve others | More scheduler logic | Any shared multi-tenant pool |

## Interview lens

<Callout type="tip">
Describe it as a pipeline: "Submit returns a run id with 202 and an idempotency key. A queue per tenant feeds a worker pool with fair share and concurrency limits. Each run gets its own sandbox. State is checkpointed, so a worker crash resumes instead of restarting. The output is a PR plus a notification. Capacity follows Little's law, with headroom on top. Each run has a budget cap, and each queue has a cost limit."
</Callout>

<Callout type="mistake">
Do not leave out the visibility timeout. A 6-minute run with a 30-second timeout runs twice. And do not let the agent push to the main branch. A background agent works unwatched, so its output needs a review gate.
</Callout>
