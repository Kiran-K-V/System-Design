## The problem

Your company builds a support agent. The travel team builds a booking agent. A vendor sells a fraud-check agent. You want your agent to ask theirs for help. Each team has its own code, its own tools, and its own release schedule. Each team also has its own idea of what a "request" is.

You could write a custom integration for each pair. With 5 agents, that is up to 10 pairs. Each pair needs its own auth, its own retries, and its own way to report progress on slow work. A wire protocol removes that. It says how to find an agent and how to hand it a job. It also says how to follow the job and how to get the result.

## Two protocols, two directions

The tool-calling lesson ([lesson A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/)) showed how a model asks your code to run a tool. The Model Context Protocol ([lesson A6.6](/learn/ai/a6-agents/mcp/)) standardizes how an agent connects to tool servers. The Agent2Agent protocol, A2A, standardizes how an agent connects to another agent.

The A2A docs draw the line this way: "MCP is vertical. It deepens a single agent." and "A2A is horizontal." In their words, "A2A is about agents partnering on tasks; MCP is more about agents using capabilities." MCP tools are "typically primitives with well-defined, structured inputs and outputs". An agent, by contrast, is a more autonomous system. It may take minutes, ask you a question halfway, and use tools you never see.

The docs give an example. A customer talks to a shop-manager agent over A2A. A mechanic agent calls diagnostic scanners through MCP. The page sums it up: "A2A connects the agents to each other; MCP connects each agent to its own tools." Step through the layers. The last step marks the trust boundary.

## The parts of A2A

I read the A2A specification, version 1.0.0 (the latest version listed on 2026-10-16), at a2a-protocol.org. The parts below are the ones you design around.

**Agent Card.** A JSON document that describes an agent's "identity, capabilities, endpoint, skills, and authentication requirements". The spec's discovery section gives the path `https://{server_domain}/.well-known/agent-card.json`. This is the same idea as a service's OpenAPI file or an OAuth metadata document, written for an agent. Here is the shape, with illustrative values. The field names are from the spec's AgentCard, AgentSkill, and AgentInterface tables.

```json title="agent-card.json"
{
  "name": "Fraud Check Agent",
  "description": "Scores a payment for fraud risk and explains the score",
  "version": "1.0.0",
  "supportedInterfaces": [
    { "url": "https://fraud.example.com/a2a", "protocolBinding": "HTTP+JSON", "protocolVersion": "1.0" }
  ],
  "capabilities": { "streaming": true, "pushNotifications": false },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    { "id": "score-payment", "name": "Score a payment", "description": "Returns a risk score", "tags": ["fraud", "payments"] }
  ]
}
```

The card also carries `securitySchemes`, which tell a client how to authenticate. The spec lists API key, HTTP auth, OAuth 2.0, OpenID Connect, and mutual TLS. Identity for A2A uses the same ideas as [lesson A7.8](/learn/ai/a7-agents-prod/agent-identity-oauth/). Those ideas are a token bound to the caller, a narrow scope, and a short life. The spec says A2A "treats agents as standard enterprise applications, relying on established web security practices".

**Operations.** The abstract operations include Send Message, Send Streaming Message, Get Task, List Tasks, Cancel Task, and Subscribe to Task. Each protocol binding names them its own way. In the JSON-RPC binding they are `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, and `SubscribeToTask`.

**Message or Task.** `SendMessage` returns at once with one of two things. For a simple exchange the agent may return a direct Message. For real work, the agent may create a Task. A Task is "a stateful unit of work initiated by an agent, with a unique ID and defined lifecycle". A Task has an `id`, a `status` (state plus a message), optional `artifacts`, and optional `history`. An **artifact** is the output: a document, an image, or structured data.

**Context.** A `contextId` "groups multiple Task objects and independent Message objects". Use one context for one conversation. Follow-up tasks join it.

**Streaming.** With `SendStreamingMessage` the stream "MUST begin with the Task object" when the agent returns a task. After that come `TaskStatusUpdateEvent` messages for state changes and `TaskArtifactUpdateEvent` messages for output. For a slow job, the spec also lists push notifications: the agent posts updates to a webhook the client supplies. Streaming works as in [lesson A3.2](/learn/ai/a3-llm-apis/streaming/): events arrive in order while the work goes on. The trade is the usual one: a held connection for short jobs, a callback for long ones.

## Task states

The spec defines the TaskState values. In version 1.0.0 the names carry a prefix. The old short names such as "input needed" or "done" do not appear.

- Active: `TASK_STATE_SUBMITTED`, `TASK_STATE_WORKING`.
- Interrupted: `TASK_STATE_INPUT_REQUIRED` ("the agent requires additional user input to proceed") and `TASK_STATE_AUTH_REQUIRED` ("authentication is required to proceed").
- Terminal: `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, and `TASK_STATE_REJECTED` ("the agent has decided to not perform the task").

There is also a `TASK_STATE_UNSPECIFIED` placeholder. Two rules matter for design. A terminal task takes no more messages. The life-of-a-task page says that once a task is terminal "it cannot restart". It also says a follow-up "must initiate a new task within the same contextId". And on `TASK_STATE_AUTH_REQUIRED` the spec says agents "MUST NOT treat the TASK_STATE_AUTH_REQUIRED state transition, by itself, as authorization" for any operation. Click through the machine below. The state machine looks like a job queue state machine, and that is the mapping to hold. SUBMITTED is queued, and WORKING is running. An interrupted state is waiting on a human or a credential. Terminal states are done, failed, or cancelled. If you built the background runs of [lesson A7.7](/learn/ai/a7-agents-prod/background-agents-queues/), you have built the client side already.

## When a protocol is worth it

A wire protocol has a cost: a network hop, a second set of failure modes, and a trust boundary. Use the cheapest thing that works.

- **An in-process subagent** ([lesson A7.6](/learn/ai/a7-agents-prod/multi-agent-orchestration/)) when the same team owns both sides. No wire, no discovery, shared logs. Do not run a network protocol between two functions.
- **A plain HTTP API** when the other side is a deterministic service. A fraud score that is a function of fixed inputs is a tool, not an agent. Wrap it as an MCP tool or a normal API call.
- **A2A** when the other side is an autonomous agent owned by someone else, the work takes long enough to need states and streaming, the agent may need to ask questions mid-task, and you want discovery by card instead of a hand-written integration.

Other agent protocols exist, for example one that connects code editors to coding agents. I did not load a primary specification for them, so this lesson does not teach them.

## The trust boundary

A remote agent is someone else's code running someone else's model on someone else's inputs. What it returns is data from an outside party. Treat it the way lesson [A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/) treats a tool result: it can carry text that tries to steer your agent. Our rule, which module A10 develops: remote output is data, not instructions. Your agent may read it, quote it, and show it. A tool call still needs your own policy and your own user's approval. A remote agent cannot grant itself that approval by asking nicely.

Authenticate both ways. Scope the token you give the remote agent to the one job. Keep your user's credentials out of the task text. Log the task id with the user and run id, so an incident can be traced across the boundary.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| In-process subagent | No wire, shared tracing, simple | Same deploy and owner | One team owns both agents |
| Plain HTTP or MCP tool | Predictable, cheap, easy to test | No task lifecycle or questions mid-call | The other side is deterministic |
| A2A | Discovery, task states, streaming, cross-vendor | Network hops, auth, a trust boundary | Another owner runs an autonomous agent |
| Custom integration | Fits exactly | Pairwise work, no shared tooling | Only one pair will ever talk |

## Interview lens

<Callout type="tip">
Say it in two lines: "MCP is vertical, an agent to its tools. A2A is horizontal, an agent to another agent. I would use A2A only across an ownership boundary for long, autonomous work, with the agent card for discovery and tasks with states for progress. Inside one team I use a subagent, and for a deterministic service I use a normal API." Then name the trust rule. Remote output is data.
</Callout>

<Callout type="mistake">
Do not say A2A replaces MCP. The A2A docs call them complementary: MCP gives each agent depth, and A2A gives the system reach. Also do not retry a failed task by resending to the same task id. A terminal task cannot restart, so start a new task in the same context.
</Callout>
