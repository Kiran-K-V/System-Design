## The problem

Many useful agents run code. A data agent runs a Python script. A coding agent runs tests and shell commands. A research agent runs a parser on a downloaded file. The model writes the code, and the model reads untrusted text, such as a web page or an issue comment. A hidden instruction in that text can steer the code it writes. The the [Tool-calling Protocol](/learn/ai/a3-llm-apis/tool-calling-protocol/) lesson introduced this as prompt injection. Module A10 covers prompt injection.

Now ask where that code runs. If it runs as your service, on your host, with your environment variables, it has your reach. It can read `~/.ssh`. It can open a connection to any address. It can delete files. The model does not need to be malicious. One confused step is enough.

Anthropic's Claude Code sandboxing post makes the point in two sentences. Without network isolation, "a compromised agent could exfiltrate sensitive files like SSH keys". Without filesystem isolation, "a compromised agent could easily escape the sandbox and gain network access". It says "effective sandboxing requires both". You need to close both doors, because each one alone leaves the other open.

## The naive design: run it next to the app

The first version calls `subprocess.run` in the service, or runs a container that mounts the host's cloud credentials "so tools just work". Both have the same fault. The code inherits whatever the process can reach, which is called **ambient authority**. The agent got no permission on purpose. It got every permission that was lying around.

## The mechanism: a box, plus a policy

Two separate choices decide the damage.

1. **The box** is the isolation technology. It sets how hard it is for code to reach the host.
2. **The policy** is what the code is allowed to see and do inside the box.

A strong box with a weak policy still leaks. A weak box with a strict policy is only as good as its kernel.

### The box: four layers

<Ai7BoxWalk client:visible />

- **Process.** Same user, same kernel, same files. No box at all.
- **Container.** Namespaces and resource limits restrict what a process sees and uses. All containers on a host still share one host kernel. A kernel bug can break out of the box.
- **gVisor.** A **user-space kernel** written in Go. Its Sentry answers the container's system calls. The gVisor docs say "the Sentry does not pass system calls through to the host kernel". A Gofer process mediates file access. The docs state the cost: "reduced application compatibility and higher per-system call overhead". The docs also state that gVisor "may provide poor performance for system call heavy workloads". It avoids large fixed overheads, so it starts light. It does not implement every system call, so some programs fail.
- **MicroVM.** A small virtual machine with its own guest kernel behind a hardware boundary. Firecracker uses the Linux Kernel-based Virtual Machine (KVM). Firecracker also adds a jailer, "a second line of defense in case the virtualization barrier is ever compromised". Its site states boot in under 125 ms and under 5 MiB overhead per VM. The site also states up to 150 microVMs created per second per host. These are the vendor's own figures, and the page gives no test conditions. Measure on your hardware.

Derived from the vendor number: 1,000 idle microVMs at no more than 5 MiB each add no more than 5,000 MiB, about 4.9 GiB, of monitor overhead. The guest's own memory is extra.

Hosted services package these choices. Modal Sandboxes offer two runtimes. gVisor "provides strong isolation and is suitable for most workloads". VMs "run the Sandbox in a virtual machine with its own Linux kernel". VMs suit work such as running Docker, mounting FUSE filesystems, or nested cgroups. Its GPU sandboxes work only on gVisor. A sandbox has a default maximum lifetime of 5 minutes. The `timeout` can raise that lifetime to 24 hours. E2B is another hosted option. Its docs page that I read gives no isolation technology, start time, or timeout, so I will not quote any.

### The policy: five controls

Pick a box, then apply these. None depends on the box.

1. **No ambient credentials.** The box starts with no cloud keys, no SSH keys, no token in the environment. Give it only what this run needs, as a scoped, short-lived secret (see [auth basics](/learn/backend/03-api-design/auth/) and the [Agent Identity and OAuth for Tools](/learn/ai/a7-agents-prod/agent-identity-oauth/) lesson for token design). Delete it when the run ends.
2. **Network egress allow list.** Deny all outbound traffic by default. Allow the few hosts the task needs. This is the control that stops data from leaving even after a read.
3. **A limited file view.** Writes go to one working directory. Reads cover only what the task needs.
4. **Time and memory caps.** A run ends on a timeout and a memory limit, as the loop caps in the [Loop Control and Stopping](/learn/ai/a7-agents-prod/loop-control/) lesson do.
5. **Disposable.** Make a new box for each run, or at least each tenant, and throw it away. State from one run cannot leak into the next.

Treat everything that comes out of the box as untrusted input. A file the code wrote can hold text aimed at the next model call.

## A real default to learn from

The Claude Code docs describe the defaults of its Bash sandbox. They are worth reading because they are not what most people assume:

- **Writes:** the working directory, a per-user temp directory, and directories you added. Protected paths stay write-denied.
- **Reads:** "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`." You must add `denyRead` rules to close that read access.
- **Network:** no direct route out. Connections go through a proxy on the machine that checks each host against your allowed domains, which start empty.
- **Environment variables:** inherited from Claude Code, including any secrets in its environment.
- **Not covered:** the file tools (Read, Edit, Write), MCP servers, and hooks run outside the sandbox. The sandbox is also off by default.

It builds on Linux bubblewrap and macOS seatbelt. Anthropic reports that, in its internal use, sandboxing "safely reduces permission prompts by 84%". That is the point of a good box: a person approves less (the [Human-in-the-Loop](/learn/ai/a7-agents-prod/human-in-the-loop/) lesson), because the blast radius is small. It is an internal figure from one team. Do not assume your number.

Notice the lesson inside the defaults. A write-only box still lets code read `~/.ssh`, and the network rule is what stops the key from leaving. Closing one door was not enough. You must set read rules, not only write rules.

## Trade-offs

| Box | You gain | You pay | Choose it when |
|---|---|---|---|
| Process plus OS sandbox | Cheapest, fast, no new service | Shared host kernel | Your own code on a dev machine |
| Container | Easy tooling | Shared host kernel | Trusted code, low risk |
| gVisor | A user-space kernel with no large fixed overhead | Per-call cost, some programs fail | Model-written code, light on system calls |
| MicroVM | Own kernel, hardware boundary | Image to build, memory per VM | Untrusted tenants, or full Linux needed |
| Hosted sandbox service | No boxes to run yourself | Vendor limits (lifetime, egress options) | You want to ship fast |

## Interview lens

<Callout type="tip">
Say: "I separate the box from the policy. The box depends on who wrote the code: an OS sandbox for my own, gVisor or a microVM for model-written or tenant code. The policy is always the same: no ambient credentials, an egress allow list, and a limited file view. The policy also includes time and memory caps and a new box per run. I treat output as untrusted." That shows both layers.
</Callout>

<Callout type="mistake">
Do not say "we run it in Docker" as if that were a full answer. A container shares the host kernel and says nothing about credentials, egress, or file reads. Also do not set only write limits. Reads of `~/.ssh` and a free network path are how keys leave.
</Callout>
