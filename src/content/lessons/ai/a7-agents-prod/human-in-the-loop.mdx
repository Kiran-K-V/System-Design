## The problem

An agent can send money, delete data, and write to a customer. The model decides what to call, and the model is wrong some of the time (the [Probabilistic Components](/learn/ai/a0-orientation/probabilistic-components/) lesson says how often to plan for). Loop caps (the [Loop Control and Stopping](/learn/ai/a7-agents-prod/loop-control/) lesson) limit how long a wrong run lasts. They do not make a single wrong action safe.

The usual answer is to put a person in the loop: the agent asks, the person approves. The protocol for tools says so. The MCP tools spec gives a rule. It says there "SHOULD always be a human in the loop with the ability to deny tool invocations". Note the word: it is a SHOULD, not a MUST. Whether and where to ask is your design.

## The naive design: ask about everything

The first version asks before every tool call. It feels safe. It fails in a known way.

Anthropic reports that Claude Code users "approve 97% of permission prompts", and that the rejection rate is "only 3%". Anthropic reads this as evidence that "many users are clicking through reflexively rather than reviewing each command". Think about what that means. A prompt that is approved 97 times in 100 is, in practice, a delay. It is not a control. People who see the same prompt all day stop reading it.

An agent that makes a tool call every few seconds, with a prompt on each, interrupts a person all day. No one reads carefully at that rate. The dangerous call looks like all the safe ones around it.

Anthropic also reports a signal in the other direction. When Claude presents a plan for approval, "users reject 39% of them". The same people who wave through commands push back on a plan. An approval step that is rare and meaningful gets real attention.

## The mechanism: tiers, then a durable pause

The fix has two parts. First decide which actions need a person. Then build a pause that does not hold a worker.

### Where approvals go

Ask a person in three cases:

- **Before an irreversible action.** Sending an email, charging a card, deleting a record, deploying.
- **Above a spend or scale limit.** A refund over $100, a query that touches 10,000 rows.
- **On low confidence.** The model, a classifier, or a rule says the call is unusual. Use this one with care: model confidence is often not calibrated (the [Probabilistic Components](/learn/ai/a0-orientation/probabilistic-components/) lesson).

Sort every tool into a tier. The tiers below are an example design, not a standard:

| Tier | What the action is | Gate | Example |
|---|---|---|---|
| 0 | Read, no side effect | None | `read_file`, `search_docs` |
| 1 | Write that can be undone | Run, log, review once at the end | Edit in the working directory under a checkpoint |
| 2 | Irreversible, or above a limit | Stop and ask | `refund`, `send_email`, `deploy` |

The Claude Agent SDK offers the same shape as modes. In `default` mode, a call that needs approval goes to your `canUseTool` callback, and with no callback it is denied. `acceptEdits` auto-approves file edits and common filesystem commands. `plan` lets Claude explore without editing source files. `dontAsk` never prompts and denies anything that would. `bypassPermissions` runs all allowed tools, and the SDK page says to use it only in isolated environments. Pick the mode, then add rules for your own tools.

### Show the exact action

The prompt must show what will happen: tool name, arguments, and for a write, the diff. "Allow the agent to update the order?" is a summary. "refund(order 8841, $480.00) to card ending 4417" is the action. The MCP spec sets a rule for clients. It says to "show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration". A summary hides the one field that matters, and a model can write a harmless summary of a harmful call.

### A pause that waits for free

An approval may take hours. A person is at lunch. You do not want a worker, a connection, or a thread blocked that long. This is where durable state (the [Durable Execution and the Graph Runtime](/learn/ai/a7-agents-prod/durable-graph-runtime/) lesson) pays off.

In LangGraph a node calls `interrupt()`. The docs say this pauses execution, saves state through the checkpointer, and waits until you resume. A checkpointer is required. The caller resumes with `Command(resume=...)` on the same thread id, and that value becomes the return value of `interrupt()`:

```python title="approve.py"
from langgraph.types import Command, interrupt

def approve_refund(state):
    ok = interrupt({"action": "refund", "order": state["order"], "amount_usd": state["amount"]})
    return Command(goto="issue_refund" if ok else "cancel")

# later, from the approval endpoint
graph.invoke(Command(resume=True), {"configurable": {"thread_id": "run-8841"}})
```

The payload given to `interrupt()` must be JSON-serializable, because the checkpointer stores it.

## The rules that cause bugs

The LangGraph interrupts page lists several traps. All of them follow from one fact: on resume, "the runtime restarts the entire node from the beginning".

1. **Code before `interrupt()` runs again.** If a node creates a record, then calls `interrupt()`, it creates a second record on resume. The docs say side effects before an interrupt "should (ideally) be idempotent". Put the side effect after the interrupt or in its own node.
2. **Do not wrap `interrupt()` in a broad `try/except`.** The pause works by raising a special exception. The page says a broad handler would catch it and "the interrupt will not be passed back to the graph".
3. **Do not loop on `interrupt()` inside one node.** The page warns against `while True` plus `interrupt()`. A resume re-runs earlier iterations. Call it once and loop back with a conditional edge.
4. **Resume values match by position.** With several interrupts in a node, "matching is strictly index-based". Do not skip one conditionally.

Temporal has the same need and a different mechanism. It is a durable workflow that waits for a message from outside. See the lesson [Temporal](/learn/backend/08-technologies/temporal/). The rule is the same too. The paused work must live in storage, not in a process.

With "ask on everything", most prompts land above what a person can review carefully, so most are approved unseen, and some risky actions slip through. With "ask on tier 2 only", the prompts are few enough to fit within capacity, so each gets a real look and the risky actions are caught. The second policy has fewer prompts and catches more. That is the point of tiers.

## Make the approval useful

- **Log each decision**: who, which action, the exact payload, the time. This is your audit trail, and your data on whether the gate works.
- **Let the person edit**, not only accept or reject. A refund of $480 may become $48.
- **Return a rejection as a tool result**, so the model can pick another plan.
- **Set a timeout policy.** A request that nobody answers for 24 hours should expire and notify, not wait forever. Decide what the agent does on expiry.
- **Ask where a person has context.** Do not route a refund approval to someone who cannot judge a refund.

## Trade-offs

| Policy | You gain | You pay | Choose it when |
|---|---|---|---|
| Ask on every call | Feels safe, simple | Fatigue, little real review | A short pilot with few calls |
| Tiered gates | Attention goes to risky calls | You must classify every tool | Most production agents |
| Plan approval | One review covers many steps | Plans drift from execution | Long, multi-step work |
| Auto mode (a classifier decides) | Fewer interrupts | Classifier errors, needs monitoring | Trusted, well-scoped tasks |
| Sandbox plus few prompts | Safe default, fewer prompts | A box to build (the [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) lesson) | Code and shell agents |

## Interview lens

<Callout type="tip">
Say: "I tier tools by risk. Reads run. Reversible writes run under a checkpoint and get one review at the end. Irreversible or high-spend actions stop at an interrupt that shows the exact call. The pause is durable, so no worker waits. I watch the approval rate: 97% means the prompt is not a control." That covers design, mechanism, and a metric.
</Callout>

<Callout type="mistake">
Do not answer "add a human approval" and stop. Say where, for which tier, what the screen shows, and how it pauses. Also do not put a side effect before `interrupt()`. It runs again on every resume.
</Callout>
