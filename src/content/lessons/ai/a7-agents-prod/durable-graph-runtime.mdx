## The problem

A chat reply takes seconds. An agent run is different. It may call the model 30 times, run a dozen tools, and take twenty minutes. Anthropic's write-up of its multi-agent research system describes agents. They "can run for long periods of time, maintaining state across many tool calls".

Machines fail during that time. A deploy replaces the worker. The kernel kills the process for memory. A spot instance is reclaimed. At minute 17 of a 20-minute run the worker is gone. What should happen next?

"Start over" has two costs. You pay for the model calls again. Worse, the tools fire again. If the first attempt already sent an email, a second attempt may send it twice. Or the second attempt may decide something different and send another one. This lesson is about how to avoid both.

## The naive fix: retry the whole job

The backend track already has the usual answer for slow work. Accept the request, put a job on a queue, and let a worker run it. See [long-running tasks](/learn/backend/09-patterns/long-running-tasks/). If the worker dies, the message becomes visible again and another worker runs the job from the top.

For a short, idempotent job that is fine. For an agent it is weak, for two reasons.

1. **Cost.** The job restarts at step 1. Every earlier model call is paid for again.
2. **Different path.** The model is not deterministic (sampling is covered in module A1). The second run may choose other tools in another order. The first run's side effects are already in the world, and the second run does not know about them.

What you want is to resume from where the run stopped, with the state it had.

## Durable execution, in brief

<CrossTrackLink id="08-technologies/temporal">
Temporal runs a multi-step process as ordinary code and saves each step in an event history. If the worker dies, a new worker replays the history and continues from the same point. Your code (the workflow) must be deterministic. Every call to the outside world goes in an activity whose result is recorded. Activities retry by policy, so a flaky call does not end the run.
</CrossTrackLink>

That is the full idea of **durable execution**: run state and history survive a crash, and another worker continues. Read the Temporal lesson for the mechanism. Here we add what is new for agents.

## What changes when the step is an LLM call

Temporal checks replay by comparing commands with the history. Its docs say the workflow must make "the same Workflow API calls in the same sequence, given the same input". It must do this each time it runs. An LLM call breaks that rule. Ask twice and you may get two different answers.

So the model call does not go in the workflow code. The Temporal docs say to put non-deterministic work such as "API calls, LLM/AI invocations, database queries" in Activities. They "execute outside the replay path and are automatically retried". The activity's result is saved in the history. On replay, the workflow reads the saved answer. It does not call the model again, so the replay is the same as the first run.

Two practical results follow:

- One model call is one activity. Its result is saved once it finishes.
- A call that is in flight when the worker dies is lost. The activity retries and you pay for it again. That is the unit of loss.

## The graph-runtime way: checkpoints

Agent frameworks built on graphs (the [Agents as Graphs](/learn/ai/a6-agents/agents-as-graphs/) lesson) take a different route. Instead of replaying code against a history, they save the **state** of the graph and restore it. In LangGraph the saver is called a checkpointer. The LangGraph checkpointers guide says: "LangGraph creates a checkpoint at each super-step boundary." A **super-step** is "a single iteration over the graph nodes". Nodes that run in parallel are part of the same super-step. Nodes that run one after another fall into separate ones.

So the right sentence is "a checkpoint per super-step", not "a checkpoint per node". In a plain chain the two are the same thing. With a fan-out, one checkpoint covers the whole parallel group. The same guide adds that as each node in a super-step finishes, its outputs are written to the checkpointer's `checkpoint_writes` table, so a node that finished is not lost when its sibling fails.

<Ai7DurWalk client:visible />

The code is short. You pick a saver, compile the graph with it, and give every run a `thread_id`:

```python title="graph.py"
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DB_URI) as saver:
    saver.setup()
    graph = builder.compile(checkpointer=saver)
    config = {"configurable": {"thread_id": "run-8841"}}
    graph.invoke({"task": task}, config)   # worker dies somewhere in here
    graph.invoke(None, config)             # new worker: continue this thread
```

Facts from the LangGraph persistence page that matter in production:

- `MemorySaver` and `InMemorySaver` store checkpoints in RAM and lose them when the process restarts. `SqliteSaver` is for development. Use a persistent checkpointer such as `PostgresSaver` in production.
- A thread is the unit of resume. With `PostgresSaver`, keep `thread_id` values under 255 characters.
- The checkpointers guide lists three durability modes. `exit` saves only when the graph exits. `async` saves while the next step runs. `sync` saves before the next step starts. In `exit` mode a crash may lose all progress. In `async` mode a crash during the next step may lose the save for the step before it. Check which one you run.
- Checkpoints pile up. Set a retention policy. The page gives no number of days.

## Where work runs twice

A restored run does not continue exactly where it stopped. It continues from the last saved point, and some code runs again. Three cases matter.

**The node that was in flight.** Its output was never saved, so it runs again from its first line. If it makes an LLM call, you pay again. If it already sent an email before the crash, the email goes again.

**Interrupts.** When a node waits for a person (the [Human-in-the-Loop](/learn/ai/a7-agents-prod/human-in-the-loop/) lesson), the LangGraph docs say "the runtime restarts the entire node from the beginning" on resume. Code before `interrupt()` runs again. The docs say side effects before it "should (ideally) be idempotent".

**Replay for debugging.** You can re-run a thread from an old checkpoint to see what went wrong. Or you can fork it with `update_state`, which "creates a new checkpoint that branches from the specified point". The time-travel page is blunt: "Replay re-executes nodes — it doesn't just read from cache." It adds that "LLM calls, API requests, and interrupts fire again and may return different results." This is the opposite of Temporal replay. In Temporal, a replay reads recorded activity results. In a graph runtime, replay runs the nodes. Play with the numbers:

## Idempotent tools

A tool is **idempotent** when calling it twice has the same effect as calling it once. Backend lesson [idempotency](/learn/backend/03-api-design/idempotency/) covers the pattern: the caller sends a unique key and the server remembers it. For an agent, derive the key from something stable. The key can be the run id plus the node name, or the id of the tool call. Do not derive it from the time or from model text, which changes on retry.

Two other fixes work without server support. Put the side effect in its own node, so a checkpoint is saved right before it. Or write "intent saved" and "done" markers and check them first. A durable runtime makes retries safe only if the tools tolerate them.

## Fan-out, join, and subgraphs

Graph runtimes also give you parallel work. A node with several outgoing edges starts all its targets in the next super-step. The `Send` API handles the case where the number of branches is not known ahead. One node produces a list. A later node runs once per item with its own input.

Join needs a merge rule. Each state key has a reducer. The LangGraph graph docs say the default reducer "ignores the left argument and replaces the state value with the right argument". If three parallel nodes write one key, one write replaces the others unless you define a reducer. For example, a reducer can append to a list. The docs page I read does not say which write wins. Do not depend on it.

A **subgraph** is "a graph that is used as a node in another graph". By default it inherits the parent's checkpointer for a single call and has no memory of earlier calls. With `checkpointer=True` it keeps its own history on the thread. Interrupts in a nested subgraph still reach the top-level graph.

## Deploys while agents run

A deploy is the other cause of dead workers. Temporal replay requires the same calls in the same sequence. So changing workflow code under an open run can break it. Graph checkpoints hold state. So a change to node names or state shape can also leave old checkpoints that do not fit. Anthropic's approach: "we use rainbow deployments to avoid disrupting running agents". In a **rainbow deployment**, old and new versions run side by side. Traffic shifts gradually, so a run that started on the old version finishes there.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Retry whole job | No new system | Repeat cost, repeat side effects | Short, idempotent runs |
| Graph checkpoints | State restored at a step, built into the graph | Node re-runs, replay fires LLM calls again, state-shape changes | The agent is already a graph |
| Temporal-style history | Recorded results, timers, retry policy | Determinism rules, code versioning | Long runs with many external calls |
| Idempotency keys | Safe retries for any recovery | Work on every tool | Always, for side effects |
| Rainbow deploys | Running agents finish on their version | Two versions live, more capacity | Runs last longer than a deploy |

## Interview lens

<Callout type="tip">
Say: "An agent run is a long workflow. I checkpoint state at each super-step, resume by thread id, and keep model calls out of deterministic replay. A node in flight runs again, so every tool takes an idempotency key. I deploy with rainbow rollouts so running agents are not cut off." That names the mechanism, the loss unit, and the safety rule.
</Callout>

<Callout type="mistake">
Do not say "checkpoint per node" as if it were a law, and do not say replay is free. In a graph runtime, replay re-runs nodes and calls the model again. Also do not assume resume means exactly-once. It means at-least-once, and your tools make it safe.
</Callout>
