## The problem

An agent loop asks the model what to do, runs a tool, and asks again. Who decides when to stop? In the happy case the model does: it replies with no tool call. But a loop that depends on the model alone has no hard end. The model can repeat a failing call, flip between two approaches, or chase a goal that cannot be met.

Two things go wrong, and they feed each other. Quality falls as steps are added. Cost rises with every step, and rises faster than you expect. This lesson covers both: the math, the stop conditions, the caps, and the detector. That detector catches a loop that is going nowhere.

## Errors compound

[Lesson A0.3](/learn/ai/a0-orientation/probabilistic-components/) shows the rule. If each step succeeds with probability p and steps are independent, a chain of n steps succeeds with probability p to the power n. The chance of success shrinks with every step you add.

A step that is "95% good" sounds fine. A 20-step run built from such steps fails most of the time. Independent errors are a simplification. In real runs, one bad step often makes the next one worse. So p^n is a gentle estimate.

Four levers move that probability: fewer steps, a verifier after risky steps, retries, and checkpoints. Retries suit steps that are safe to repeat (idempotent, see lesson [A7.1](/learn/ai/a7-agents-prod/durable-graph-runtime/)). Checkpoints limit a failure to one step, not the whole run. Judge a run by its path, not only its final answer. Lesson [A8.5](/learn/ai/a8-evals/trajectory-evals/) returns to that.

## Naive solution: trust the model to stop

Leave the loop with no limit. The Claude Agent SDK documents this case. Its `max_turns` and `max_budget_usd` options both default to "No limit". Without limits, the loop "runs until Claude finishes on its own, which is fine for well-scoped tasks but can run long on open-ended prompts". The same page says setting a budget "is a good default for production agents".

What does a run with no limit cost? Each step resends the growing context, so cost is steps times context times price. Prompt caching (lesson [A2.5](/learn/ai/a2-inference-cost/prompt-caching/)) cuts the repeated prefix, but the shape stays. A run that loops for hundreds of steps can cost far more than the task is worth.

LangGraph has a built-in ceiling. Its graph docs say "Starting in version 1.0.6, the default recursion limit is set to 1000 steps". The graph docs also say "once the limit is reached, LangGraph will raise `GraphRecursionError`". A step here is a super-step. At 1,000 steps, a loop can still burn a large budget. A default that protects the process does not protect the budget.

## Stop conditions

Build a stack of independent reasons to stop, and make each one report why it fired:

1. **The model is done.** A reply with no tool calls. The SDK reports a `stop_reason` such as `end_turn`, `max_tokens`, or `refusal`.
2. **A goal check passes.** Your code tests the result: tests pass, a field is filled, a verifier agrees.
3. **Turn cap.** Max steps.
4. **Budget cap.** Max tokens or dollars.
5. **Wall-clock timeout.** A run that waits on a slow tool must also end.
6. **User cancel.**
7. **Stuck detector.** The loop is going nowhere.

Each SDK defines "turn" its own way, and the difference matters:

- Claude Agent SDK: `max_turns` "counts tool-use turns only". It caps tool-use round trips. A final text-only reply is not counted. When it fires, the result has subtype `error_max_turns`, and there is no `result` text.
- OpenAI Agents SDK: the limit applies to "agent-loop turns (LLM calls)". It raises `MaxTurnsExceeded`. The page states no default, and says `max_turns=None` disables the limit.
- LangGraph: `recursion_limit` counts super-steps, 1000 by default.

The same number means different amounts of work. A limit of 10 in one SDK is not a limit of 10 in another.

## Budget caps and overshoot

A budget cap in dollars is the most direct control. The Claude Agent SDK has `max_budget_usd`. When it fires, the result subtype is `error_max_budget_usd`. The cap includes subagents: their spend counts toward the total. Once spend reaches the cap, spawning another subagent fails with "Budget limit reached".

Know one detail: the cap is a check after the fact. The SDK docs say Claude Code compares spend with the cap "after model responses arrive". The response that reaches the cap "still completes and counts". Spend can pass the cap by the cost of that one response. Subagents still running add whatever they spend before they stop. Set the cap below the real limit you can afford. A cap is a fence, not a wall.

A budget cap alone also has a gap. It fires only when money is gone. A loop that repeats one useless call for 40 turns is wasteful long before it hits $5. For that you need a detector.

## Stuck and oscillation detection

A loop that makes no progress leaves signs. Three cheap ones:

- **Same call, same arguments.** Count calls by (tool name, normalized arguments). Stop when one pair appears n times, say 3.
- **Same state.** Hash the state after each step. If a hash repeats, the loop has come back to where it was. This also catches A, B, A, B swings, where no two neighbors match.
- **Flat progress.** Track a number that should move: tests passing, items done, files changed. Stop when it is flat for k steps.

Pick thresholds from real traces. A threshold of 2 will flag a legitimate retry. A threshold of 10 pays for 9 wasted turns.

When a detector fires, you have four choices. **Stop** and report. **Summarize** what was tried, then stop. **Ask a human** with that summary (lesson [A7.3](/learn/ai/a7-agents-prod/human-in-the-loop/)). **Fall back** to a simpler path, such as a fixed workflow or a stronger model for one step. Pick one per cause. Never loop again with the same prompt and hope.

Notice three things. A stuck run with the detector on stops after n turns, at a small cost. With it off, the budget cap ends the run, and spend lands past the cap. A healthy run is never stopped by a detector set at 3 or more, because its calls differ. And a large turn cap with a small budget means the budget is your only real limit.

## A hook as a stop point

If you use Claude Code hooks, a `PreToolUse` hook can block a call. The hooks page says to "exit with code 2 to block the action". One caution from that page: a timed-out command hook does not block the tool call. The default command timeout is 600 seconds. The hooks page says to set `onFailure: "block"` if the call must be blocked when the hook times out. A guard that can fail open is not a guard. The Claude Code GitHub Actions page lists three cost controls for CI. Set `--max-turns` in `claude_args`. Set workflow-level timeouts to avoid runaway jobs. Use GitHub concurrency controls to limit parallel runs.

## Trade-offs

| Control | Catches | Misses | Choose it when |
|---|---|---|---|
| Model says done | Normal finish | Any loop where the model never decides | Always on, never alone |
| Turn cap | Long loops | Costly turns, and different meanings per SDK | Always, as a backstop |
| Budget cap | Cost growth | Waste under the cap; overshoot by one response | Production runs |
| Timeout | Slow tools, hangs | Fast useless loops | Always |
| Stuck detector | Repeats, A-B swings | Loops with changing arguments | Agents that call tools |
| Verifier per step | Wrong results early | Cost and latency of the check | High-risk steps |

## Interview lens

<Callout type="tip">
Say: "Success compounds down with every step, so I cut steps and verify risky ones. The loop has layered stops: done, goal check, turn cap, dollar cap, timeout, and a stuck detector on repeated calls. The caps are checked after a response, so I keep headroom. On a trigger I summarize and hand to a human." That shows the compounding idea, the layers, and the overshoot detail.
</Callout>

<Callout type="mistake">
Do not offer "max steps" as the only answer. A step cap says nothing about cost per step, and one SDK's turn is not another's. Do not quote a dollar horror story as evidence either. Explain the cost from steps, context size, and price.
</Callout>
