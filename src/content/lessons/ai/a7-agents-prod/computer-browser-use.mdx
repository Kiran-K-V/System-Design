## The problem

Your agent must file an expense in a vendor portal. The portal has no API, no export, and no MCP server. A person does it with a mouse. The only interface the agent has is the one a human has: pixels in, clicks out.

Two older answers exist. A script with fixed selectors (Selenium, Playwright code) breaks when the page changes a class name. A person doing the work by hand does not scale. A model that reads the screen and decides the next click sits between them. It adapts to a layout change, but it is slower, costs more per step, and gets things wrong more often than an API call. This lesson shows the loop, the cost, and the controls that make it safe enough to run.

## The mechanism: a screenshot and action loop

You already know the shape from the tool-calling protocol ([lesson A3.4](/learn/ai/a3-llm-apis/tool-calling-protocol/)). Computer use is one tool whose results are pictures. Anthropic's docs describe four steps:

1. You give the model the computer tool and a task.
2. The model replies with `tool_use` blocks: take a screenshot, click here, type this.
3. Your app runs them in order and returns one `tool_result` for each, usually with a fresh screenshot.
4. The loop ends when the model replies with text and no tool calls.

The model never touches the machine. Your app owns a virtual display and executes every action, which is why you can put checks in front of it. Step through one task and watch the image tokens add up.

### Coordinates and scale

The model returns coordinates in the pixel space of the screenshots you sent, origin at the top left. Two traps follow. If you shrink a screenshot before sending it, you must scale the model's coordinates back up before you click. If a click lands consistently off to one side, the docs say unscaled coordinates are the usual cause. On a Retina screen, either downscale the capture by 2x or halve the returned coordinates.

Image limits matter too (images as input are covered in [lesson A3.5](/learn/ai/a3-llm-apis/files-images-input/)). The docs say newer models accept up to 2,576 pixels on the long edge and 4,784 visual tokens, counted as `ceil(width / 28) x ceil(height / 28)`. Earlier models accept 1,568 pixels and about 1.15 megapixels. An oversized image is rejected, not resized for you. The docs recommend 1280x720 or 1024x768 for desktop and 1280x800 or 1366x768 for web apps, and advise against anything above 1920x1080.

By that formula, a 1280x800 screenshot is 46 x 29 = 1,334 visual tokens. The docs' own estimate is "roughly 1,000 to 1,800 input tokens" per screenshot, so 1,334 sits inside it.

### Batches

The model may return several actions in one turn. Your app runs them in order and stops at the first failure. Later actions get an error result such as "Not executed: an earlier computer action in this turn failed." A batch can end with a screenshot, which saves a round trip. Fewer round trips means fewer screenshots sent and less time.

```python title="cu_loop.py"
def run_task(task, max_turns=30):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_turns):                      # hard cap: see lesson A7.2
        reply = call_model(messages)                # sends the computer toolset
        messages.append({"role": "assistant", "content": reply.content})
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return reply                            # text only: the model says it is done
        results, failed = [], False
        for b in calls:
            if failed:
                results.append(error_result(b.id, "Not executed: an earlier action failed."))
                continue
            ok, shot = run_action(b.input)          # scale coordinates back up here
            failed = not ok
            results.append(tool_result(b.id, shot, is_error=not ok))
        messages.append({"role": "user", "content": results})
        messages = drop_old_screenshots(messages, keep=3)   # or server-side clearing, see docs
    raise RuntimeError("step cap reached")
```

This is a sketch. Check the computer-use docs for the exact request shape and tool version. As of 2026-10-16 the current toolset is `computer_toolset_20260801`, and the docs say Claude 5.5 and later models return an error for the older `computer_20251124` and `computer_20250124` versions.

## What it costs

Cost has three parts: tokens, time, and reliability.

**Tokens.** The API is stateless (lesson [A3.1](/learn/ai/a3-llm-apis/api-anatomy/)), so each call resends everything. If you keep every screenshot, call k carries k images. Over n steps you send 1 + 2 + ... + n = n(n+1)/2 images. For 30 steps that is 30 x 31 / 2 = 465 sends. The docs give one option for this: keep the last 3 screenshots and prune every 25 turns, so the prefix stays byte-identical between prunes. For Opus 5.5, Sonnet 5.5, and Haiku 5.5 they advise against pruning on the client, because removing an earlier screenshot invalidates the later thinking blocks. They suggest resizing to 2,000 pixels or less per side and using server-side tool result clearing instead. Either way the effect is the same, so the model here is "keep 3": call k carries min(k, 3) images, and the total is 1 + 2 + 28 x 3 = 87 sends. That is 5.3 times fewer than 465. Prompt caching ([lesson A2.5](/learn/ai/a2-inference-cost/prompt-caching/)) also lowers the price of the repeated part, but dropping old images cuts the tokens themselves.

**Time.** Each step is a model call plus a screen action plus a page load. The docs give no latency per step, and I found no primary figure, so treat any number as an assumption. The widgets use 5 seconds per step and label it illustrative. Measure your own. The point holds at any value: 30 steps of N seconds is a task measured in minutes, not milliseconds.

**Reliability.** A task is a chain of steps, and every step can fail. If each step goes right with probability p, an n-step task finishes with probability p^n (lesson [A7.2](/learn/ai/a7-agents-prod/loop-control/)). The per-step values below are illustrative:

| Per-step success | 10 steps | 30 steps |
|---|---|---|
| 99% | 90.4% | 74.0% |
| 98% | 81.7% | 54.5% |
| 95% | 59.9% | 21.5% |

Derivation: 0.98^30 = e^(30 x ln 0.98) = e^(-0.606) = 0.545. Errors are not always independent, so treat this as a shape, not a forecast. The lever is fewer steps: batch actions, use shortcuts, and give the model an API tool for any part that has one.

## Pixels or page structure

A browser is easier than a whole desktop, because a web page has structure. Microsoft's Playwright MCP server gives a model structured accessibility snapshots of the page, "bypassing the need for screenshots or visually-tuned models". Its snapshot tool is described as better than a screenshot, and the screenshot tool is view-only: "You can't perform actions based on the screenshot." The model acts on elements it names from the snapshot, not on coordinates.

| | Pixels (computer use) | Page structure (accessibility snapshot) |
|---|---|---|
| Works on | Any app, including canvas, games, and native desktop apps | Web pages that expose a usable accessibility tree |
| Model input | Screenshot, roughly 1,000 to 1,800 tokens | Text. Size follows the page, so measure it |
| Needs a vision model | Yes | No |
| Typical failure | Misjudged coordinates, small targets, scale errors | Missing or badly labelled elements, huge snapshots on dense pages |
| Choose it when | No DOM is available, or layout is the point | The target is a web app and you control or know the page |

Many agents use both: structure to act, pixels to check what the page looks like. The cheapest option is neither. If the vendor has an API, or an MCP server exists (lesson [A6.6](/learn/ai/a6-agents/mcp/)), call it. One API call replaces a whole chain of clicks.

## Controls

An agent that clicks through the web reads untrusted text all day. A page can contain instructions, and the docs warn that the model may follow instructions found in page content. This is prompt injection through the screen (module A10 covers it). Anthropic's precautions are a good baseline, and they match the sandbox rules from lesson [A7.4](/learn/ai/a7-agents-prod/sandboxes-code-execution/):

- Run it in a dedicated virtual machine or container with minimal privileges.
- Give it no sensitive data, such as login credentials. Start with a clean, isolated browser profile and no logged-in sessions.
- Limit internet access to an allow list of domains.
- Ask a human to confirm anything with real-world consequences: purchases, accepting terms, sending messages. That is the approval gate from lesson [A7.3](/learn/ai/a7-agents-prod/human-in-the-loop/).

One detail from Playwright MCP deserves attention. Its default profile is persistent, so cookies and logins survive between runs. The `--isolated` flag keeps the profile in memory and drops it when the browser closes. Its `--allowed-origins` option defaults to allowing all origins, and the docs say it "does not serve as a security boundary and does not affect redirects". They also say the server as a whole is "not a security boundary". Enforce the domain allow list outside the agent, at the network or VM level, not in a flag the page can route around.

## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| API or MCP tool | Fast, cheap, reliable | Needs one to exist | Always, first |
| Page structure | Text input, no vision model | Fails on poor accessibility data | Web apps you can inspect |
| Pixels | Works on any screen | Tokens and time per step, scale bugs | No DOM, legacy or desktop apps |
| Keep all screenshots | Full history | n squared token growth | Short tasks only |
| Drop old screenshots | About 5x fewer image tokens at 30 steps | Less visual history | Long tasks |
| Isolated profile | No leaked logins | Re-login for each run | Default for untrusted pages |

## Interview lens

<Callout type="tip">
Lead with the order of preference: "API first, then an MCP tool, then page structure, then pixels, because each step down costs more tokens, time, and reliability." Then give the numbers: one screenshot is about 1,000 to 1,800 tokens, a 30-step task at 98% per step finishes 55% of the time, and every page is untrusted input, so the browser runs in a disposable VM with an allow list and a human gate before any submit or payment.
</Callout>

<Callout type="mistake">
Do not offer computer use as the default way to integrate with a system that has an API. And do not say a domain allow list "is in the browser config" if the page can redirect around it. Enforce it where the agent cannot edit it.
</Callout>
