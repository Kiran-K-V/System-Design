## The problem

A chat reply takes seconds. An agent run can take minutes. In that time the agent reads files, calls tools, edits things, and sometimes goes the wrong way. The user is waiting and has only a spinner to look at.

That creates three problems. The user cannot tell if the run is working or stuck. The user cannot stop a wrong turn until it ends. And when it ends with a bad result, the user cannot easily undo it. Good agent UX answers three questions at every moment. The questions are what it is doing, can I change course, and can I take it back.

This lesson covers the interface. The reliability side lives elsewhere: the [Loop Control and Stopping](/learn/ai/a7-agents-prod/loop-control/) lesson stops runaway loops, and the [Human-in-the-Loop](/learn/ai/a7-agents-prod/human-in-the-loop/) lesson gates actions with a human. Here we ask what the human sees.

## Naive design: a spinner, then a result

The simplest agent UI shows "Thinking..." and, at the end, a final answer. It has two failures.

The first is **opacity**. [The Streaming Responses lesson](/learn/ai/a3-llm-apis/streaming/) showed that users feel the time to the first visible output, not the time to the last token. An agent run is that problem at a larger scale. A run with no visible progress looks frozen after a few seconds. Users then cancel or resubmit runs that were working fine.

The second is **a blind approval gate**. Many designs add a popup before each risky action: "Allow this tool call? Yes / No". It feels safe. Anthropic's data says it often is not. In its post on making auto mode the default in Claude Code (dated 2026-08-07), Anthropic writes: "Data suggests that manual review can become habitual: users approve 97% of permission prompts in Claude Code." The same post reports that "when Claude presents a plan for approval, users reject 39% of them". The numbers are for Claude Code users. They show the shape of the problem, not a law for your product. But a prompt that is approved 97 times in 100 is a rubber stamp. The 3 that matter hide among the 97.

## Show progress: the plan, then the steps

Anthropic's agent-design guide says: "Prioritize transparency by explicitly showing the agent's planning steps." Two kinds of signals do most of the work.

A **plan** says where the run is going before it starts. It is short, and the user can reject it cheaply. The 39% plan rejection rate in the Anthropic post suggests users do act on a plan when they see one. That suggests a wrong plan is cheaper to catch than a wrong edit.

A **step stream** says where the run is now. Each tool call or file edit becomes one row: "Reading config.py", "Running tests". The rows come from the same events you already stream (the [Streaming Responses](/learn/ai/a3-llm-apis/streaming/) lesson). Group them: show the current step in full and fold the older ones into one line. Show what the agent found, not only what it did, and link sources so the user can check them.

Add **time and cost so far**. A run with a budget cap (the [Loop Control and Stopping](/learn/ai/a7-agents-prod/loop-control/) lesson) can show spend against the cap. Show it in plain units, such as elapsed time and dollars. Do not show a number you did not measure. A cost meter also answers the question "is it stuck". If elapsed time grows and no new step appears, say so.

A small handler turns raw events into rows. The event shape here is made up for illustration. Real SDKs name their events differently.

```typescript title="progress.ts"
type AgentEvent =
  | { type: 'plan'; steps: string[] }
  | { type: 'step_start'; id: string; label: string }
  | { type: 'step_end'; id: string; ok: boolean }
  | { type: 'error'; message: string };

function reduce(rows: Row[], e: AgentEvent): Row[] {
  switch (e.type) {
    case 'plan':
      return [...rows, { kind: 'plan', lines: e.steps }];
    case 'step_start':
      return [...rows, { kind: 'step', id: e.id, label: e.label, state: 'running' }];
    case 'step_end':
      return rows.map((r) => (r.kind === 'step' && r.id === e.id ? { ...r, state: e.ok ? 'done' : 'failed' } : r));
    case 'error':
      return [...rows, { kind: 'error', message: e.message }];
  }
}
```

## Interrupt, steer, and rewind

A user who sees a wrong turn should be able to say so now. **Interrupting** stops the run. **Steering** adds a message that changes it mid-run. In Claude Code, a user can type while the agent works. The docs call this queueing messages while Claude works.

The undo side is **checkpoints**. The Claude Code checkpointing docs say it "automatically captures the state of your code before each prompt you send that starts a turn". Every such prompt creates a new checkpoint. Run `/rewind`, or press Esc twice when the prompt box is empty, to open the rewind menu. The menu lists these actions: restore code and conversation, restore conversation only, and restore code only. It also lists summarize from here and summarize up to here. The docs list the limits too. Rewind does not track files changed by Bash commands. A subagent's edits are usually not restored. Edits made outside the session are normally not captured. The docs say plainly that checkpoints are not a replacement for version control.

Follow one run. It has a steer and a rewind. Notice that the steer message gets no checkpoint of its own. The docs say a message typed mid-turn "has none of its own". Edits made after that message count toward the prompt that started the turn.

The design lesson: an **undo** is only as good as what it covers. If the agent can change things the checkpoint does not track, the UI must say so. Say so before the run, not after. Prefer reversible actions by default. Write a draft, not a send. Stage a change, not a deploy. Propose a diff, not an overwrite. Put the one-way actions behind a gate.

## Approvals that mean something

Approval fatigue is easy to see. If users approve almost every prompt, rejections are rare, and the few that matter hide among the many that do not. Anthropic reports that rate for Claude Code users, and I apply it here as an assumption to your product. The lesson is the shape: when almost every prompt is approved, a user stops reading them.

Four changes help.

- **Ask less.** Gate only the actions that are hard to undo or reach outside the sandbox (the [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) lesson). Let reversible ones run, and let rewind cover them.
- **Show the exact action.** Show the command or the diff, not "Allow this tool?". A reviewer can only judge what they can see.
- **Make the rare prompt stand out.** If 3 in 40 prompts are risky, style them differently and say why.
- **Gate the plan.** One plan review replaces many step reviews, and the 39% figure shows people reject bad plans.

Log each decision ([the Agent Identity and OAuth for Tools lesson](/learn/ai/a7-agents-prod/agent-identity-oauth/) audit trail). The log lets you measure your own approval rate and see if it drifts toward 100%.

## Failure states and correction

Design the failure screens as carefully as the happy path. A run can fail in at least four ways. The ways are: a tool errors, the model refuses, a limit stops it, or the user's network drops. For each one, the UI should say what happened and what was kept. It should also say what the user can do next: retry, edit the prompt, or rewind. "Something went wrong" tells the user nothing.

Make correction cheap. If the user can edit the prompt, regenerate, or mark a step as wrong in one click, they correct small errors early. Each correction is also a labeled signal: log it with the run id for your evals (module A8). Show confidence only if it is calibrated against real outcomes. An unearned "95% sure" teaches users to over-trust.

That is **trust calibration**. Over-trust means approving without looking. Under-trust means re-doing the agent's work by hand. The right amount of visible signal moves users between the two. Try it. ## Trade-offs

| Choice | You gain | You pay | Choose it when |
|---|---|---|---|
| Spinner only | Clean screen | No trust, cancelled runs | Runs under a few seconds |
| Plan up front | Cheap review of direction | One more step before work starts | Runs that edit or spend |
| Full step stream | Users see liveness and detail | Noise, more to read | Long runs, power users |
| Approve every action | Feels safe | Fatigue, rubber stamps | Almost never |
| Approve risky actions only | Prompts that get read | You must classify risk | Mixed reversible and one-way actions |
| Checkpoints and rewind | Cheap undo for tracked changes | Limits: untracked changes remain | Edits to files or state you can snapshot |

## Interview lens

<Callout type="tip">
Answer in three layers: "Show progress, so the run is not a black box: a plan, then streamed steps with elapsed time and cost. Allow control: interrupt, steer, and rewind to a checkpoint. Gate only the risky, one-way actions, with the exact command visible. The reason is that users approve 97% of generic prompts and stop reading them." Then say how you would measure it: approval rate, rewind rate, and correction rate.
</Callout>

<Callout type="mistake">
Do not say "add a confirmation dialog" as the whole safety plan. Do not claim undo covers everything: it covers what it tracks. And do not hide failure behind a generic error. Say what was kept and what to do next.
</Callout>
