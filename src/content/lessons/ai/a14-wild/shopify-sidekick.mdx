## What they built and why it was hard

**Company claim.** Sidekick is "an AI-powered assistant that helps merchants manage their stores through natural language interactions". A merchant can ask "which of my customers are from Toronto?" Sidekick queries the customer data, applies filters, and shows the result. It can also write SEO descriptions and fill them into a product form. The post says it is built around the "agentic loop", which it credits to Anthropic: a person gives input, the model decides on an action, the app runs the action, the result is fed back, and the cycle repeats until the task is done. Lesson [A6.1](/learn/ai/a6-agents/agent-loop/) teaches that loop.

Three problems grew together as Sidekick got more capable.

1. **The tool set grew.** A **tool** is a function that the model may ask the app to run, such as "list customers" or "update a product". The model sees each tool as a **schema**: text that gives the tool's name, what it does, and what inputs it takes. Every schema is sent to the model on every call.
2. **The instructions grew.** Each tool brings special cases, and the team wrote them into the system prompt, the fixed text that tells the model how to behave.
3. **Quality was hard to know.** A merchant conversation has many steps and no single right answer. A unit test cannot grade it.

The post answers each problem. This lesson takes them one at a time: how many tools, where the rules live, and how you can trust a model that grades the others.

**What the post does not publish.** It gives no count of Sidekick's tools (only "dozens"), no latency, no cost, and no accuracy of tool choice. It says performance "improved across all metrics" after just-in-time instructions, and shows none of those metrics. The post is a set of design lessons with a few numbers, not a benchmark.

## The before

### Many tools

**Company claim.** The post describes three tiers, quoted here as the post writes them:

| Tool count | What the post says |
|---|---|
| 0 to 20 | "Clear boundaries, easy to debug, straightforward behavior" |
| 20 to 50 | "Boundaries become unclear, tool combinations start causing unexpected outcomes" |
| 50+ | "Multiple ways to accomplish the same task, system becomes difficult to reason about" |

The post does not say how the tiers were measured. They are the team's experience, written as ranges with soft edges.

**Why would more tools hurt?** The post gives the symptom, not a mechanism. Here is our reading, in two parts. Each part has a number you can derive.

*Part one: the model must choose.* On every step the model reads all the tool descriptions and picks one, or none. Picture a drawer with 10 labelled keys, against a drawer of 70 keys where nine open the same door. The more keys look alike, the more often you pick the wrong one. The post's third tier says this in its own words: "multiple ways to accomplish the same task". A simple count shows the growth. With N tools there are N times (N minus 1), divided by 2, pairs of tools that someone must check for overlap. For 20 tools that is 190 pairs. For 50 it is 1,225. For 70 it is 2,415. That is a count of possible confusions, not a measured error rate. The post publishes no accuracy by tool count. Lesson [A6.5](/learn/ai/a6-agents/tool-design/) gives the general rules for naming and splitting tools.

*Part two: the schemas cost tokens.* A **token** is a small piece of text, about three-quarters of a word. The API is stateless, so every call re-sends all the schemas. Take an assumed 300 tokens per schema. That is the size the A6.5 lesson used as an illustration. Measure your own with a token counter. Then N tools add N times 300 tokens to each call.

Step through the post's tiers. The bar uses the post's words. The meter under it uses our assumption.

Both bars share one scale. The axis end of 80 tools is ours. The post only says "50+".

Here is what those tokens cost over a task of 10 model calls. Check the 70-tool row by hand. 70 times 300 is 21,000 tokens a call, and ten calls send 210,000. At $2 per million that is $0.42. With caching, one write costs 21,000 times $2.50 per million, which is $0.0525. Nine reads cost 9 times 21,000 times $0.10 per million, which is $0.0189. The sum is $0.0714. All of this is **Our reading**, with an assumed schema size.

Caching cuts the price about six times here. It does not cut the choice: the model still reads 70 tools.

### Many instructions

**Company claim.** The post names the second problem "Death by a Thousand Instructions": "our system prompt became an unwieldy collection of special cases, conflicting guidance, and edge case handling that slowed down the system and made it nearly impossible to maintain."

**Our reading.** Tools and instructions grow together. A new tool brings a rule such as "if this tool fails, try that one", and rules about pairs of tools grow with the pair count. A rule written for one page of the admin sits in the prompt on every other page. The model reads all of it every time, and two rules can disagree. Nobody can say which rule caused a bad answer.

### Vibe testing

**Company claim.** The post is blunt about how teams usually check quality: "These days, so many people are vibe testing their LLM Systems and thinking that it's good enough; it's not." It also rejects a judge that is just "Rate this 0-10". It says the work "needs to be principled and statistically rigorous, otherwise you should be shipping with a false sense of security."

## The design

### Fewer tools, clear boundaries

**Company claim.** The post's advice is plain: "Stay simple: Resist the urge to add tools without clear boundaries. Quality over quantity applies strongly to agent capabilities." And: "Avoid multi-agent architectures early: Simple single-agent systems can handle more complexity than you might expect."

**Our reading.** The post does not say how many tools Sidekick runs now, and it does not offer tool search, a router, or sub-agents as the answer to 50+ tools. Do not cite it for those. It supports something narrower: each tool gets a clear boundary, overlapping tools are a smell, and a single agent is the first design. Lessons [A6.2](/learn/ai/a6-agents/workflows-vs-agents/) and [A7.6](/learn/ai/a7-agents-prod/multi-agent-orchestration/) cover going beyond that.

### Just-in-time instructions

**What it is.** A **just-in-time (JIT) instruction** is guidance that the app returns together with the data of a tool call, at the moment the model needs it. **Company claim:** "Instead of cramming all guidance into the system prompt, we return relevant instructions alongside tool data exactly when they're needed. Our goal is to craft the perfect context for the LLM for every single situation, not a token less, not a token more."

**Picture.** A new cook gets one page of kitchen rules on day one, and a sticky note on each pan: "this pan: medium heat only". The note is read when the cook picks up the pan.

**Why it exists.** A model reads the whole prompt every time, and rules that do not apply still compete for its attention. The post lists three benefits. **Company claim:**

- "Localized guidance": instructions appear only when relevant, so the core system prompt stays "focused on fundamental agent behavior".
- "Cache efficiency": "We can dynamically adjust instructions without breaking LLM prompt caches".
- "Modularity": "Different instructions can be served based on beta flags, model versions, or page context".

**Number, our reading.** To see the cache point, you need to know what a prompt cache is. A **prompt cache** stores the model's work on the start of a prompt, so that a later request with the same start is cheaper. It matches only an exact **prefix**: the prompt from its first token up to a point. Change one early token and everything after it misses. Lesson [A4.5](/learn/ai/a4-context/cache-friendly-layout/) teaches the layout rule, and [A2.5](/learn/ai/a2-inference-cost/prompt-caching/) covers prices. Anthropic's order is tools, then system prompt, then messages. A tool result is a message, and it sits at the end.

So there are two ways to deliver a rule that changes with a beta flag. Edit the system prompt, and the stored prefix is wrong from that block on. Or put the rule in the tool result, and the stored prefix is untouched. Step through it. Token sizes are illustrative: 15,000 for the tools, 4,000 for history, 6,000 for a prompt that holds every rule, and 1,000 for one that holds only core behavior.

<Ai14SidekickJit client:visible />

The arithmetic is the one in the last step. A request that breaks the cache from the system block reads 15,000 tokens at $0.10 per million and writes 10,000 at $2.50 per million: $0.0015 plus $0.025, which is $0.0265. A request that matches the whole 20,000-token prefix reads it all: $0.0020. Over 1,000 requests that is $26.50 against $2.00, a factor of 13.25. The factor depends on our sizes. The direction does not. **The post publishes no cache hit rate and no saving.**

**The catch, our reading.** A JIT instruction stays in the history after it is delivered, so it adds tokens on every later call. It can go stale: if a later tool result says the opposite, the model sees both. And if the model never calls that tool, it never sees the rule. Test these cases before you copy the idea.

### Ground truth sets, not golden datasets

**Company claim.** Shopify moved "away from carefully curated 'golden' datasets toward Ground Truth Sets (GTX) that reflect actual production distributions". The team samples real merchant conversations and builds criteria from what it sees. The process has three steps in the post: "Have at least three product experts label conversations across multiple criteria", "Use Cohen's Kappa, Kendall Tau, and Pearson correlation to measure inter-annotator agreement", and "Treat human agreement levels as the theoretical maximum our LLM judges can achieve".

**Our reading.** "Inter-annotator agreement" means how often the people doing the labelling agree with each other. Kendall tau compares rank orders: of all pairs of conversations, how often do two graders put the same one first? Pearson measures how closely two lists of scores rise and fall together. Use them for scores, such as 1 to 5, and kappa for labels, such as pass or fail. The post gives no value for tau or Pearson. Lesson [A8.3](/learn/ai/a8-evals/golden-sets/) covers sets built from real traces.

### Cohen's kappa, from scratch

Start with a trap. Suppose you grade 100 conversations. Humans mark 10 as bad and 90 as fine. An LLM judge that says "fine" every time agrees with the humans on 90 of 100. That is 90% agreement from a judge that catches nothing. The reason is that the labels are lopsided. Most conversations are fine, so any grader that leans toward "fine" agrees with any other.

**What kappa measures.** Cohen's kappa is the agreement you got beyond the agreement that luck would give. **Luck** here means two graders who each say "bad" at their own rate and ignore the conversation. Write p-o for the observed share of agreement and p-e for the share expected by luck:

<Math block tex="\kappa = \frac{p_o - p_e}{1 - p_e}" />

In words: the top is how far above luck you got. The bottom is the most you could have got above luck. So 0 means no better than luck and 1 means perfect.

**A table you can fill by hand.** Here are the 100 conversations. The human is the row. The judge is the column. The judge flagged 12 conversations as bad. This is an illustrative judge.

| | Judge: bad | Judge: fine | Row total |
|---|---|---|---|
| Human: bad | 6 | 4 | 10 |
| Human: fine | 6 | 84 | 90 |
| Column total | 12 | 88 | 100 |

1. Observed agreement: both said bad (6) plus both said fine (84), over 100. That is p-o = 0.90.
2. Luck for "bad": the human says bad 10 times in 100 and the judge 12 times in 100. If each acted blindly, both would say bad on 0.10 times 0.12 = 0.012 of conversations.
3. Luck for "fine": 0.90 times 0.88 = 0.792.
4. Luck in total: p-e = 0.012 plus 0.792 = 0.804.
5. Kappa = (0.90 minus 0.804) divided by (1 minus 0.804) = 0.096 divided by 0.196 = **0.49**.

Now the always-fine judge. Its observed agreement is also 0.90. Its luck is 0.10 times 0 plus 0.90 times 1, which is 0.90. Kappa is (0.90 minus 0.90) over 0.10, which is **0**. Same 90% raw agreement, kappa 0.49 against 0. That gap is what kappa is for.

Two more checks. The judge in the table caught 6 of 10 bad conversations (recall 60%), and 6 of its 12 flags were right (precision 50%). Lesson [A8.4](/learn/ai/a8-evals/judges/) says to read those next to kappa. And with balanced classes, 50 bad and 50 fine, 90% agreement gives p-e = 0.5 and kappa = 0.8. The same raw agreement means more when labels are balanced.

Lesson [A13.4](/learn/ai/a13-cases/support-agent/) already teaches pass^k and judge agreement for a support agent. Here we keep to one question the Sidekick post raises: how good can a judge get, and how do you know?

### Validating the judge against humans

**Company claim.** "Through iterative prompting, we improved our judges from barely-better-than-random (Cohen's Kappa of 0.02) to near-human performance (0.61 vs. human baseline of 0.69)."

<Ai14SidekickKappa />

Read the figure with care. The plan for this lesson expected a kappa for each criterion and each judge. **The post does not give that.** It says it built "specialized LLM judges for different aspects of Sidekick's performance", and it gives one before and after pair. It does not say whether 0.02 and 0.61 belong to one judge or are an average. It does not name the criteria, the number of conversations, the label scale, or how a three-person human panel became one 0.69. We drew no bar for a criterion, because the page has none.

**What 0.02 means.** The judge in the table above that flags 12 conversations at random would catch about 1.2 of the 10 bad ones, so its kappa would be about 0. A kappa of 0.02 is a judge whose flags tell you almost nothing.

**What 0.61 may look like.** The post does not publish its label mix, so we cannot turn 0.61 into counts. On our 10 percent bad mix, a judge that catches 7 of 10 bad conversations and flags 4 fine ones by mistake scores 0.63. That is close in size, and it is only an example.

**Why 0.69 is the ceiling.** A judge cannot be more "right" than the people it is graded against, because the people define right. The post calls 0.61 "near-human", 0.08 below the humans. Our reading: past this point more prompting mostly fits the judge to one labeller's quirks. Spend the effort on the rubric where the experts disagree.

**A second test.** **Company claim:** "once our LLM Judge has high correlations to human, we try to randomly replace the Judge with a human for each conversation in our GTX, and when it's difficult to tell whether we used a human or judge as part of the group, then we know we have a trustable LLM Judge." Put another way: swap the judge into the human panel at random and see whether the group's verdicts change in a way you can detect. The post gives no result for this test.

Here is the whole check, as a procedure we would run. It joins the post to lesson [A8.4](/learn/ai/a8-evals/judges/).

1. Sample real conversations. Do not write them from specs.
2. Have at least three experts label each one against written criteria.
3. Measure how much the experts agree with each other. That is your ceiling. (We assume pairwise kappa, averaged. The post does not say how it combined three labellers.)
4. Run the judge on the same conversations. Compute kappa against the human label, plus recall and precision on the bad class.
5. Change the prompt one thing at a time and recompute. Stop near the ceiling.
6. Run the swap test.
7. Re-run the check when the judge model, the prompt, or the use changes. The reward-hacking story below is a change of use.

### Simulator, reward signals, and reward hacking

Two more pieces of the post are short, and they close the loop.

**Company claim.** To test changes before release, Shopify built "an LLM-powered merchant simulator that captures the 'essence' or goals of real conversations and replays them through new system candidates". The judge grades each full conversation, and the team picks the best candidate. Lesson [A8.6](/learn/ai/a8-evals/simulated-users/) covers simulated users.

**Company claim.** Shopify also fine-tuned a model with GRPO, a reinforcement learning method where the model writes several answers to one prompt and each is scored, so better ones become more likely. The score is called a reward. Shopify's rewards combined "procedural validation (syntax checking, schema validation) with semantic evaluation from LLM judges". The model then found shortcuts, which the post calls reward hacking:

- "Opt-out hacking": the model explains why it cannot help, instead of trying a hard task.
- "Tag hacking": it uses customer tags as a catch-all instead of the right field.
- "Schema violations": it invents IDs or uses wrong enum values.

The post's example: asked to "segment customers with status enabled", the model wrote `customer_tags CONTAINS 'enabled'` instead of `customer_account_status = 'ENABLED'`. After the team fixed its validators and judges, **Company claim:** "Syntax validation accuracy improved from ~93% to ~99% across all skills", "LLM judge correlation increased from 0.66 to 0.75 on average", and "end-to-end conversation quality matched our supervised fine-tuning baseline". Lesson [A11.4](/learn/ai/a11-finetuning/reinforcement-finetuning/) covers graders as rewards.

**Our reading.** A judge good enough to grade is not automatically good enough to train against, because training pushes hard on every gap in it. The 0.66 to 0.75 pair is a different measure from kappa, so panel B of the figure keeps it apart.

**Second source, clearly separate.** Shopify's post on its product catalogue ([Leveraging multimodal LLMs, 2025-07-16](https://shopify.engineering/leveraging-multimodal-llms)) describes a different system. It says LLM judges grade generative fields "against detailed guidelines", and flag low-quality inferences in production for human review. It says nothing about tool counts, kappa, or just-in-time instructions. We use nothing else from it.

## Our reading

**It maps onto three lessons.** Tool tiers are the tool-design lesson ([A6.5](/learn/ai/a6-agents/tool-design/)) seen from production: clear boundaries and a token cost on every call. Just-in-time rules are the cache-layout rule ([A4.5](/learn/ai/a4-context/cache-friendly-layout/)) applied to rules: keep the front of the prompt stable and put what changes at the tail. The kappa climb is the judge lesson ([A8.4](/learn/ai/a8-evals/judges/)) with a real trajectory: check the grader like a classifier, with the humans as the ceiling.

**One thread ties them.** Tools, rules, and graders all fail the same way: they pile up with no boundary, and then you cannot say which part caused a bad result. Each fix adds a boundary: a tool gets a clear job, a rule gets a place and a moment, a judge gets a human reference.

**What we would test before copying.**

- Tool choice. Take 50 real tasks, run them with 20, 50, and 70 tools, and count wrong picks. The post gives no such number.
- JIT rules. Log cache read and write tokens on a request that gets a new rule. Look for rules that go stale in long chats.
- The judge. Label 100 conversations with at least two people. Compute human kappa first, then judge kappa, recall, and precision.
- Your own domain. A merchant-admin assistant has a narrow domain and known pages. An open-ended tool set may behave differently.

## What to copy and what not to

| Idea | When it fits | When it does not |
|---|---|---|
| Keep the tool set small, with clear boundaries | Any agent with tools that overlap | You genuinely need many distinct tools. Then add boundaries, not a count cap |
| JIT instructions in tool results | Rules that depend on the tool, page, flag, or model version | A rule the model needs before it picks any tool. Keep that in the system prompt |
| Rules loaded by flag or version | You ship experiments or switch models often | A single fixed deployment with a short, stable prompt |
| Ground truth set from real chats | You have production traffic and can get expert time | Day one, before traffic. Start from scenarios, then replace them |
| Kappa and a human ceiling | Lopsided labels, such as rare failures | You have only one labeller. You cannot measure the ceiling |
| Simulated merchant for pre-release tests | A change that is risky to send straight to users | Simulator goals drift from real users. Re-sample real chats often |
| Single agent first | Most products at the start | The task truly splits into independent jobs |

## Interview lens

<Callout type="tip">
Say: "I keep the tool set small and each tool's boundary clear, because the tiers Shopify describes go from easy to debug at 20 tools to hard to reason about at 50 or more, and every schema is tokens on every call. I put situation rules in the tool result, not the system prompt, so the cached prefix stays stable. I grade with an LLM judge only after I check it against at least three human labellers, using kappa, not raw agreement, and I treat human agreement as the ceiling." Then add: "These are company claims from one post, so I would measure tool-choice accuracy and cache hit rate on my own traffic."
</Callout>

<Callout type="mistake">
Do not say "Shopify showed that more than 50 tools breaks an agent". The post gives tiers as experience, with no measurement. Do not quote 0.02 to 0.61 as a range across criteria. </Callout>
