## What they built and why it was hard

Character.AI lets people hold open-ended conversations with fictional characters. A user may chat for an hour. The service must answer each message in seconds, for millions of people at once.

**Inference** is the work a trained model does to produce a reply. A **query**, in the post's word, is one request to the model. The post does not define it further.

**Company claim** (summary post, 2024-06-20): "Character.AI serves around 20,000 queries per second – about 20% of the request volume served by Google Search, according to public sources." The technical post says "more than 20,000" and names its source for Google: about 105,000 queries per second, "according to third party estimates (Statista, 2024)". The summary post adds: "We manage to serve that volume at a cost of less than one cent per hour of conversation."

Why is chat hard to serve cheaply? Because a chat is long. **Company claim** (technical post): "the majority of chats are long dialogues; the average message has a dialogue history of 180 messages." Every new message must be read together with all 180 before it. A model has no memory of its own, as lesson [A13.2](/learn/ai/a13-cases/chatgpt-assistant/) showed. Compare a search query, which stands alone. A chat turn drags its whole past behind it. The cost of a turn depends on how well the system remembers that past.

## The before

Take a plain design. Each turn goes to any free GPU server. The server reads the full history, writes the reply, and forgets everything. Two problems follow.

**Problem 1: the work repeats.** The first pass over a prompt is called **prefill**, and the work is heavy (lesson [A2.2](/learn/ai/a2-inference-cost/prefill-decode/)). With a 180-message history, turn 181 repeats the prefill of messages 1 to 180, and so does turn 182. The post says "continuously refilling KV caches on each turn would be prohibitively expensive". The **KV cache** is the saved result of that first pass: a store of keys and values that the model computes for every token it has read (lesson [A2.3](/learn/ai/a2-inference-cost/kv-cache/)). With the cache, the model reads only what is new. Without it, it re-reads everything.

**Problem 2: the cache is too big to keep.** Suppose the server does keep the cache in GPU memory. The post says: "The key bottleneck of LLM inference throughput is the size of the cache of attention keys and values (KV). It not only determines the maximum batch size that can fit on a GPU, but also dominates the I/O cost on attention layers." A **batch** is the set of chats the GPU serves in one step. A bigger batch gives more tokens per second for the same weights (lesson [A2.4](/learn/ai/a2-inference-cost/batching-throughput/)). The cache decides how many chats fit. For scale, lesson [A13.2](/learn/ai/a13-cases/chatgpt-assistant/) worked an example: a 70-billion-parameter model needs over a gigabyte of KV for one 4,000-token chat, so one 8-card server holds only a few hundred chats. Character.AI's model size is not published. The example shows the size of the problem, not their number.

So there are two goals. Make each chat's cache smaller, so more chats fit. And keep the cache between turns, so a turn does not start from zero. The post attacks both, then makes the arithmetic cheaper with int8.

## The design

### Lever 1: make the KV cache smaller

**Company claim** (technical post): three techniques "reduce KV cache size by more than 20X without regressing quality. With these techniques, GPU memory is no longer a bottleneck for serving large batch sizes."

**Multi-Query Attention (MQA).** A model layer has many **attention heads**. Each head looks at the text in its own way. Each head has a **query**, the question it asks, and a **key** and **value**, the labels and contents of every earlier token. The cache stores keys and values. In plain multi-head attention, every head has its own key and value, so the cache is big. **Grouped-Query Attention (GQA)** lets a group of query heads share one key and value. **MQA** lets all query heads share one. Picture a class where each student keeps a private copy of the textbook, then groups of students share a copy, then the whole class shares one.

**Company claim**: "We adopt Multi-Query Attention (Shazeer, 2019) in all attention layers. This reduces KV cache size by 8X compared to the Grouped-Query Attention adopted in most open source models." **Our check**: the 70B model in lesson [A13.2](/learn/ai/a13-cases/chatgpt-assistant/) has 8 KV heads, so one shared head fits the 8x claim. The price is model capacity. One shared key and value holds less than eight, so the model must be trained with MQA from the start. The post does not give a quality number for this step alone.

**Hybrid attention horizons.** Normal attention lets every token look at all earlier tokens. This is **global attention**. **Local attention** lets a token look only at the last N tokens, a **sliding window**. A local layer never needs a cache longer than N. The post: "We interleave local attention (Beltagy et al., 2020) with global attention layers." It reports that "reducing attention horizon to 1024 on most attention layers does not have a significant impact on evaluation metrics, including the long context needle-in-haystack benchmark. In our production model, only 1 out of every 6 layers uses global attention." The needle test hides one fact in a long text and asks the model to find it. **Our reading**: take a long chat. One layer in six keeps all of it. Five in six keep at most 1,024 tokens. So the cache is a fraction of full size, and the longer the chat, the bigger the cut.

**Cross-layer KV sharing.** Neighbouring layers often learn similar keys and values. The post: "We tie the KV cache across neighboring attention layers, which further reduces KV cache size by a factor of 2-3x." Tied layers read one stored copy. For global layers, which dominate memory in long chats, the post ties "the KV cache of multiple global layers across blocks". It cites Brandon et al., 2024 and says "we find that sharing KV across layers does not regress quality."

These three are **model design**, set when the model is trained. An engineer who only calls or hosts a model cannot add them. Lesson [A1.4](/learn/ai/a1-model-function/attention-cost/) explains the cost of attention that they cut.

### Lever 2: keep the cache between turns

This is the part the post calls one of its key innovations: "One of our key innovations is an efficient system for caching attention KV on host memory between chat turns." **Host memory** is the ordinary RAM of the server, not the fast but small memory on the GPU. Think of a desk and a filing cabinet. The GPU's own memory is the desk: quick, small. Host memory is the cabinet: slower, much bigger. Between turns, a dialogue's KV goes into the cabinet. When the user writes again, it comes back to the desk.

The mechanism, step by step, in the post's words where we quote:

1. **Save.** "For every prefilled prefix and generated message, we cache the KV values on host memory and retrieve them for future queries." A **prefix** is the first part of a prompt.
2. **Organize.** "Similar to RadixAttention (Zheng et al., 2023), we organize cached KV tensors in a LRU cache with a tree structure." **LRU** means least recently used: when the cache is full, drop the entry that went longest without use. A **tree** lets dialogues that share an opening share its storage.
3. **Index.** "The cached KV values are indexed by a rolling hash of prefix tokens." A **hash** turns a run of tokens into one short number. A **rolling** hash can be extended one token at a time at low cost, so a hash for every prefix of a long prompt takes a single pass.
4. **Look up.** "For each new query, a rolling hash is calculated for each prefix of the context, and the cache is retrieved for the longest match. This allows reusing the cache even for partially matched messages." If a user edits a message in the middle, everything before the edit still matches.
5. **Route.** "At a fleet level, we use sticky sessions to route the queries from the same dialogue to the same server." A **sticky session** is a rule that keeps one user on one server. Lesson [A13.2](/learn/ai/a13-cases/chatgpt-assistant/) calls it session affinity and works through the hot-server trade-off, so we do not repeat it.
6. **Capacity.** "Since our KV cache size is small, each server can cache thousands of dialogues concurrently."

The size of the cache is what makes steps 1 to 6 work. This is why lever 1 comes first. A cache 20 times smaller means a server can hold 20 times more dialogues in the same RAM.

**Company claim**: "Our system achieves a 95% cache rate, further reducing inference cost." The post does not say how a cache rate is counted. It could mean the share of turns with a hit, or the share of prompt tokens read from cache. These two differ a lot, and the post does not say which it means.

### Lever 3: make each number smaller

**Company claim**: "We use int8 quantization on model weights, activations, and attention KV cache." **Int8** stores each number in 8 bits, half of the 16 bits in the usual format (lesson [A2.6](/learn/ai/a2-inference-cost/quantization-small-models/)). Less data means less memory and less to read per step. The post adds that it trains the model this way: "Different from commonly adopted 'post-training quantization' techniques, we natively train our models in int8 precision, eliminating the risk of training/serving mismatch." Post-training quantization shrinks a finished model. Here the model learns with int8 from the start, so what it learns is what it serves. The post does not state how much quality, cost or speed int8 added by itself.

### Later: speed, then a new stack

The first post was about memory. **Company claim** (Part Deux, 2024-11-21): "In this post, we turn our focus to speed." It describes a custom int8 attention kernel. A **kernel** is a small program that runs on the GPU. The post says two ideas make it fast. The first fuses the step that converts int8 back to higher precision into the attention kernel, which avoids extra memory traffic. The second packs several query heads into one block of work, which suits MQA decoding because all those heads read the same key and value. The result: "up to 10% in prefill and 30% in decoding over a prior baseline that used a handwritten Triton attention kernel". Prefill and decode are the two phases from lesson [A2.2](/learn/ai/a2-inference-cost/prefill-decode/). The benchmarks ran on one H100. Kernel internals are elective topics (E3), so we stop here.

**Company claim** (DigitalOcean and AMD write-up, hosted on Character.AI's blog, 2026-01-13): "Character.ai leverages multiple models like Qwen, Mistral and more", and the write-up tunes "the Qwen3-235B Instruct FP8 model". The company "runs models using vLLM", on AMD MI325X GPUs. The target workload is "5600 / 140 (ISL / OSL)", which we read as about 5,600 input tokens and 140 output tokens per request. The headline is "~2x QPS per 8x MI325x server compared to a generic setup on other providers". The vLLM flags include `--enable-prefix-caching`, which the write-up describes as useful "for multi-turn chats that share a common prompt prefix". It also says Character.AI has "a concept of persistent user session to ensure the consistency of the following requests from the same user, to maximize KV cache hit rate". A footnote says the results come from "internal testing conducted by DigitalOcean and AMD".

## Our reading

### What "less than one cent" implies

**Our reading.** The claim is a unit price, so convert it into GPU time. Prices as of 2026-10-20: a Lambda H100 SXM 80 GB on an 8-GPU on-demand instance costs about $4 per GPU-hour ([Lambda pricing](https://lambda.ai/pricing)). At one cent an hour, one conversation hour gets only a few GPU-seconds of one H100, for a full hour of chat. That is a very small slice.

Now the fleet. The number of GPUs the claim allows depends on how often a user sends a message, which the posts do not give. If users message often, the same traffic needs fewer conversation hours and the budget per turn is tiny. Whatever rate you assume, the fleet the claim allows is far smaller than the A13.2 drill, where a 70B model with a 90% hit rate needed several times more GPUs for the same 20,000 queries per second. So at least one of these must hold if the claim is right: the model is much smaller than 70B, the hit rate is higher, a turn is shorter, or Character.AI pays less per GPU-hour. The claim does not say which. Treat this as a check on an assumption, not as Character.AI's fleet.

A second check on the post's own example. The two cost figures in it (the yearly total at one cent an hour, and the commercial-API total) agree in order of magnitude with the "at least 13.5X" claim. Both say "at least", so they can agree.

### The 20x puzzle

**Our reading.** The three listed cuts multiply: MQA, the hybrid layers, and the sharing. Stacked on a long chat, they would give far more than "more than 20X". The post does not say if the baseline already has some of these, which chat length it counts, or whether the three cuts stack. Do not reuse "20x" as a rule. Work out the cut for your own model and your own chat length.

### Why the host-memory tier is believable

**Our reading.** Shrink the cache of a large model by 20x, and one long dialogue takes a small amount of memory. A server with a terabyte of RAM could then hold thousands of them. That agrees with "thousands of dialogues", under assumptions of our own: the model shape, the 20x, and the RAM size are all guesses. Copying one dialogue from host memory to the GPU takes a few milliseconds over a fast link, while a long prefill of a large model takes hundreds of milliseconds (lesson [A13.2](/learn/ai/a13-cases/chatgpt-assistant/), our model). So the copy is cheap beside the work it saves. We did not find a primary source for the link speed.

### Which cache rate is 95%?

Use the simulator. It models 8 servers with an LRU cache of whole dialogues, with randomly chosen turns. It compares the post's sticky sessions against sending each turn to a random server. All inputs are illustrative, and the logic is in a separate file with a node check.

<Ai14CharacterCacheSim client:visible />

Read three presets.

- **Roomy cache.** 8,000 open dialogues, 1,000 per server, and room for 1,500. With 99% of turns sticky and 3% rewinding, sticky sessions reach a 96.4% cache rate and prefill 340 tokens per turn. Random routing reaches 18.9% and prefills 7,750. Sticky does 3.6% of the no-cache work, random 81.1%.
- **Cache too small.** Drop the room to 600 dialogues per server, below the 1,000 each server must hold. Sticky falls to 57.9%. An LRU cache that is too small evicts a dialogue just before its next turn. Room well below the working set is a cliff, not a slope.
- **Leaky routing.** Only 70% of turns follow the rule (the rest model deploys, failures, rebalancing). Sticky falls to 63.6%. A leaked turn misses, and it also fills another server with a copy that pushes out useful dialogues.

The lesson: a 95% cache rate is reachable, and our model happens to reach 96.4%. That says nothing about their setup. The rate depends on three numbers: cache room per server against its dialogues, how well routing holds, and how many turns rewind. **Before you quote a cache rate, define it.** In our model the ceiling is 99%, because each new user message is never in the cache yet.

### The stack in 2026

**Our reading.** The 2024 design needs a model built for it: MQA in every layer, hybrid layers, tied KV, and int8 from training. None of that can be added to a model you did not train. The 2026 write-up describes Qwen3-235B and Mistral models served with vLLM, using its generic prefix cache and a "persistent user session". Those two facts fit together if some of the workload now runs on open-weight models. The posts do not say what share of traffic runs where, or whether the 2024 model is retired. We also cannot reconcile the write-up's own figures. It says two TP4 groups give "~2x QPS compared to DP1 / TP8 / EP8", and then "~45% better on throughput", and "~91% better compared to generic setup". TP and EP name how a model is split across GPUs. The text does not explain how 2x and 45% describe the same comparison. Read the 2x as somewhere between 1.45x and 2x.

What carries over to any stack is the cache idea: keep the prefix, route by dialogue, and spill to host memory. What does not is the model design.

### Business context

**Company claim** (2024-06-20): "these sorts of inference improvements unlock the ability to create a profitable B2C AI business at scale". **Company claim** (2026-10-12): Character.ai "has initiated a voluntary Chapter 11 bankruptcy process to facilitate a court-supervised sale of the company", after "significant legal, regulatory, and operational headwinds". The platform "remains up and running". **Our reading**: this lesson does not say what caused the filing. The posts publish no revenue or cost totals, and they name legal and regulatory pressure, not GPU cost. The one lesson we take: cost per hour is half of unit economics. A design review also needs revenue per hour.

## What to copy and what not to

| Idea | When it fits | When it does not |
|---|---|---|
| Keep the KV between turns | Long chats, where history dwarfs each new message | Short one-shot calls with nothing to reuse |
| Sticky sessions by dialogue | A cache that lives on one server | Skewed load with a few huge chats. Then add load-aware routing (A13.2) |
| A host-memory tier under the GPU | KV is small enough that thousands of dialogues fit | Large KV per token, where the cabinet fills fast |
| Match the longest prefix | Users edit or regenerate | Prompts that change early, so the prefix never matches |
| MQA, hybrid layers, tied KV | You train your own model | You call an API or host a model you did not train |
| Native int8 training | Same, and you can test quality loss | Teams without training budget. Use post-training methods and a golden set (lesson [A8.3](/learn/ai/a8-evals/golden-sets/)) |
| Define "cache rate" first | Always | Never skip |

For a team that hosts an open model, the practical copy is the first three rows: turn on prefix caching in the engine, route by dialogue, and watch your own hit rate by chat length. For a team that calls an API, the provider's prompt cache does this work (lesson [A2.5](/learn/ai/a2-inference-cost/prompt-caching/)).

## Interview lens

<Callout type="tip">
Say: "In long chats the history is the cost. I keep the KV between turns, in host memory under the GPU, indexed by a rolling hash of the prefix so an edit still matches its start. I route a dialogue to one server, and I check that the cache has room for the dialogues that server owns. The model shape sets how many fit, so MQA and tied layers, if I own the model. I would ask how 'cache rate' is counted before I trust 95%. And I turn any cost-per-hour claim into GPU time, then ask what model and hit rate make it possible."
</Callout>

<Callout type="mistake">
Do not repeat "20x smaller KV" or "95% cache rate" as facts. They are company claims with no stated baseline or definition. Do not say sticky sessions fix the cache without naming what happens when a server restarts or the cache is too small. Do not copy MQA or int8 training advice for a model you only host.
</Callout>
