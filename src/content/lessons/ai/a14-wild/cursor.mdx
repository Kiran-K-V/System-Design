## What they built and why it was hard

A coding agent answers questions about your code, so it must find the right code. One way is **semantic search**: the code is cut into chunks, each chunk becomes a vector, and a question is matched to the nearest vectors (lesson [Choosing Embedding Models](/learn/ai/a5-rag/embedding-models/)). Cursor says this matters a lot: "Semantic search is one of the biggest drivers of agent performance. In our recent evaluation, it improved response accuracy by 12.5% on average." That is a **company claim**. The indexing page does not say how the evaluation worked. The post it links to says a little more, which we cover in the numbers section.

The index has to be built first, and that is slow. The indexing post says: "large repositories with tens of thousands of files can take hours to process if indexed naively, and semantic search isn't available until at least 80% of that work is finished." So a new engineer who opens a big repo waits hours with a weaker agent.

The second problem is a different job. The agent has planned a change in chat. Now the change must be written into a file. Cursor's post calls this the apply step and says that "Frontier models such as GPT-4o struggle on large edits, with problems of laziness, inaccuracy, and high-latency." It adds: "Worst of all, existing models are slow at large edits, breaking the programmer out of flow." Both are waiting problems, and they share a cure: stop redoing known work. The index already exists for a teammate. The new file is mostly the old file.

## The before

**Indexing, the naive way.** When a project opens, the client uploads every file. The server cuts each file into chunks, embeds every chunk, and stores the vectors. When a second person opens a copy of the same repo, the work starts again from zero. Cursor's key observation is that "clones of the same codebase average 92% similarity across users within an organization." The page does not say how it measures similarity. Our reading: roughly nine files in ten are already indexed on the server, and the naive design ignores that.

A naive sync after an edit has the same shape. The client can send its whole file list and let the server compare. The page gives the size of that list: "In a workspace with fifty thousand files, just the filenames and SHA-256 hashes add up to roughly 3.2 MB." Our arithmetic: 3.2 MB over 50,000 files is 64 bytes per file. A **hash** [junior] is a short fixed-size fingerprint of some data. SHA-256 makes a 32-byte one. Moving 3.2 MB on every small save is a poor trade for a one-line change.

**Apply, the naive way.** Ask a frontier model to write the new file, or to write a diff. Cursor tried both. A full rewrite is simple but slow. On diffs, the post says "Most models fail to output accurate diffs, with the exception of Claude Opus." The post gives three reasons that models write diffs badly. They "think in fewer tokens", because a short diff gives fewer passes of thinking. Diffs are "out of distribution", because models have seen far more whole files than diffs. And a diff needs line numbers, and "models are notoriously bad at counting line numbers." So Cursor chose to rewrite the whole file and to make that rewrite fast.

## The design

### Step 1: find the change with a Merkle tree

A **Merkle tree** [mid] is a tree of hashes. Each file gets a hash of its content. Each folder gets a hash computed from the hashes of its children. The top folder's hash is the **root**. Cursor says the tree "features a cryptographic hash of every file, along with hashes of each folder that are based on the hashes of its children."

Picture a book where each chapter has a stamp that depends on its pages, and the book has a stamp that depends on its chapter stamps. To learn whether two copies are the same, compare one stamp. To find the changed page, walk down only where stamps differ.

Why it works: a good hash gives the same output for the same content, and a different output if even one byte changes. So two equal root hashes mean two equal trees (up to a collision, which a 256-bit hash makes negligible). Two different roots mean something below differs. Cursor describes the edit side: "Small client-side edits change only the hashes of the edited file itself and the hashes of the parent directories up to the root of the codebase." And the sync side: the client compares its hashes with the server's "to see exactly where the two Merkle trees diverge. Entries whose hashes differ get synced. Entries that match are skipped." Entries missing on the client are deleted from the server, and entries missing on the server are added. The page adds that "the sync process never modifies files on the client side."

Step through a small tree. It has 4 entries per folder and 3 levels, so 64 files. The hashes are made-up four-digit stand-ins.

<Ai14CursorMerkle client:visible />

Now the number. Let f be the entries per folder and d the depth. One changed file needs one comparison for the root, then f comparisons at each of d levels:

<Math block tex="\text{comparisons} = 1 + f \times d" />

For the toy tree: 1 + 4 x 3 = 13, against 64 files. The saving is small here. Scale it up. Take 16 entries per folder and 4 levels. That is 16^4 = 65,536 files, about the size of the page's 50,000-file example. One edit costs 1 + 16 x 4 = **65** comparisons. If each hash is 32 bytes, that is about 2 KB of hashes, against 3.2 MB for the full list. The ratio is about 1,500 to 1. This is **our arithmetic**. We assume raw 32-byte hashes and ignore message overhead and round trips. The page does not describe the protocol at that level. It also gives no sync interval.

The cost grows with the logarithm of the repo, not with its size. It is the diff step of the pipeline in lesson [Freshness and Index Updates](/learn/ai/a5-rag/freshness-updates/). There the change feed was a database log. Here the feed is a hash walk, because the client has no log to read.

### Step 2: cache embeddings by chunk content

Once a file is known to have changed, it must be re-indexed. The post says: "When a file changes, Cursor splits it into syntactic chunks. These chunks are converted into the embeddings that enable semantic search. Creating embeddings is the expensive step, which is why Cursor does it asynchronously in the background."

A **syntactic chunk** [mid] follows the shape of the code, such as one function or one class, and not a fixed count of characters. Lesson [Chunking and Contextual Retrieval](/learn/ai/a5-rag/chunking-contextual/) covers how to chunk.

Then the key idea: "Cursor caches embeddings by chunk content. Unchanged chunks hit the cache." A **content-addressed cache** [mid] uses a hash of the content as the key. The value is the embedding. If the same text shows up again, the same key shows up, and the cache answers without calling the model. Git works the same way: its book says Git "is a content-addressable filesystem", a key-value store where the key comes from the content.

Everyday picture: a translator keeps a notebook of sentences she has already translated. A new draft arrives. She looks up each sentence, and only the new ones cost her time.

Worked example (ours). A file has 12 syntactic chunks. You change one function. Eleven chunks hash to keys already in the cache. One chunk does not. You pay for 1 embedding, not 12. Now see why the chunk shape matters. Suppose chunks were fixed windows of 500 tokens. Insert 3 lines at the top. Every window after the insert shifts, so all of them get new content and new keys. A miss on 12 of 12. With syntactic chunks the insert leaves the other 11 functions intact. This is **our reasoning**. The page says the chunks are syntactic and the cache is keyed by content. It does not run this comparison.

The page does not say how large the cache is, what its hit rate is, or whether it is shared between users. That last point matters for the security section below.

### Step 3: reuse a teammate's index with a simhash

The Merkle tree makes small syncs cheap. It does not help the first sync, when the server knows nothing about this copy. Cursor's answer is to find a teammate's index that is almost the same, and start from it.

The first problem is finding it. You cannot compare 50,000 hashes against every index on the server. You need one short value per codebase, built so that similar codebases get similar values. A normal hash cannot do this. Change one file, and a normal hash of the file list flips about half its bits. The tool for this job is a **simhash** [senior], a "similarity hash". Here is how a textbook simhash works. The page does not give Cursor's exact scheme, so treat this as the idea, not as their code.

1. Give each item a fixed-size hash. Here an item is a file's content hash. Take 8 bits for the demo.
2. Keep one counter per bit position. For each item, add 1 to the counter if the bit is 1, and subtract 1 if it is 0.
3. The final fingerprint has a 1 where the counter is above zero, and a 0 elsewhere.

Each item votes on each bit. A few changed items change a few votes. Most counters keep their sign. Here is a worked example with five files (ours, run by script):

```
set A  10110010 10010110 11110011 00110010 10100110
counters   3  -3   3   3  -5  -1   5  -3   -> 10110010
set B  (last file replaced by 01001101; 4 of 5 files shared)
counters   1  -1   1   3  -3  -1   3  -1   -> 10110010
set C  (five unrelated hashes)
counters  -5   1  -1  -5  -1  -3   3  -1   -> 01000010
```

Sets A and B differ by 0 bits. Sets A and C differ by 4 of 8 bits, which is what random sets do on average. The number of bits that differ between two fingerprints is their **Hamming distance** [mid]. Small distance means similar sets. With 8 bits and 5 items this is a toy. A real scheme uses more bits and many more items.

The page says how the fingerprint is used. The client builds the Merkle tree of its copy, "derives a value called a similarity hash (simhash) from that tree", and uploads it. The server "uses it as a vector to search in a vector database composed of all the other current simhashes for all other indexes in Cursor in the same team (or from the same user)". That is nearest-neighbour search, as in lesson [ANN Indexes and Billion-Scale Search](/learn/ai/a5-rag/ann-indexes/). For each result, the server checks "whether it matches the client similarity hash above a threshold value". If it does, that index becomes the starting index for the new codebase. The page does not give the threshold, the bit width, or the search library.

The copy runs in the background. Meanwhile the client can already search. In the page's words: "the client is allowed to make new semantic searches against the original index being copied, resulting in a very quick time-to-first-query for the client."

Look at the scope. The search covers indexes "in the same team (or from the same user)". Reuse never crosses a team boundary. That is a first limit. The second is the proof.

### Step 4: prove you hold the file

Here is the catch. A 92% match means 8% of files differ. Say the teammate's copy has files you do not have: a private branch, a local notes file, a folder you have no access to. If the server hands you results from their index, you could read chunks of files that are not on your disk. The page states the two rules: "Results need to reflect the user's local codebase, even when it differs from the copied index. And the client can never see results for code it doesn't already have."

Cursor's fix reuses the tree. "Each node in the tree is a cryptographic hash of the content beneath it. You can only compute that hash if you have the file." When a workspace starts from a copied index, "the client uploads its full Merkle tree along with the similarity hash. This associates a hash with each encrypted path in the codebase." The server stores this tree "as a set of content proofs". Then, "during search, the server filters results by checking those hashes against the client's tree. If the client can't prove it has a file, the result is dropped."

Think of a library desk that gives you the notes on a book only if you can show you already hold that edition. The test is not "who are you". The test is "do you already have this".

When the client's tree and the server's tree reach the same root, the sync is complete. At that point, "the server deletes the content proofs and future queries run against the fully synced index."

Compare it with lesson [Permissions in Retrieval](/learn/ai/a5-rag/retrieval-permissions/). There, an access list says who may read each chunk. Here the filter asks what the caller already holds. The page says the server "filters results". It does not say whether the filter runs before or after the nearest-neighbour search. That lesson shows why it matters: a post-filter can leave too few results.

### Step 5: the apply step

Back to the second post. The planning stage is a chat with a strong model. The apply stage turns the plan into a file. Cursor's idea is to split the work: "Applying the change to the current file should be straightforward and instant." So it trained a model just for apply.

The training data is mostly synthetic. The page starts from a few real apply prompts and many "cmd-k" prompts (edit instructions on a selected region), has GPT-4 write a chat answer for each, then has a model "apply" it. It mixes this with the real data and fine-tunes Deepseek Coder Instruct and Llama 3 models. The page says: "We find that our best model (llama-3-70b-ft) almost matches claude-3-opus-diff and outperforms gpt-4-turbo and gpt-4o."

Quality check, with a warning. The evaluation set is "~450 full-file edits of files under 400 lines", graded with Claude-3 Opus. The page itself says: "These scores likely bias towards outputs of Claude models." The numeric scores sit in charts, and we quote none. Lesson [SFT and LoRA](/learn/ai/a11-finetuning/sft-lora/) covers fine-tuning in general.

### Step 6: speculative edits

Now the speed. Start with why a model is slow at writing a long file. As lesson [Prefill vs Decode: TTFT and TPOT](/learn/ai/a2-inference-cost/prefill-decode/) taught, decode makes one token per pass, and each pass reads all the model weights from memory. For a 70B model in BF16 that lesson derived a floor of about 48 tokens a second on 2 H100 GPUs and about 96 on 4, for one user. A 400-line file is about 4,000 tokens at 10 tokens a line (our assumption). At 96 tokens a second that is about 40 seconds.

**Speculative decoding** [senior] is a way around that, in plain words. Elective E3.4 teaches it in full. You do not need it here. The idea has three parts.

1. A cheap guess supplies the next several tokens.
2. The big model runs once over all the guessed positions together and says, for each position, which token it would have written.
3. Keep the guessed tokens up to the first one the model disagrees with. At that spot, use the model's own token. Throw away the rest of the guess.

Checking 30 positions in one pass costs only a little more than making 1 token, because the pass is limited by reading weights, not by arithmetic. So every accepted guess token is nearly free. The output is exactly what slow decoding would have written. The original paper (Leviathan and others) shows "a 2X-3X acceleration compared to the standard T5X implementation, with identical outputs" on a different model and task.

Normally a small draft model makes the guess. For an edit you already have a very good guess: the old file. Cursor's words: "With code edits, we have a strong prior on the draft tokens at any point in time, so we can speculate on future tokens using a deterministic algorithm rather than a draft model." They call it **speculative edits**. Cursor says it "is equivalent to a full-file-rewrite, while being up to 9x faster."

Step through a toy. A 10-line file, 10 tokens per line. The new file keeps lines 1 to 4 and 7 to 10, and writes 3 new lines in place of lines 5 and 6.

<Ai14CursorSpec client:visible />

The toy shows the shape. Copied text is cheap. New text costs one token per pass. A file that changes little speeds up a lot. A file that is rewritten from scratch speeds up not at all. The page does not say how the guess finds its place again after an edit. It says only "deterministic algorithm". Fireworks, Cursor's inference partner, "built out api support for our custom speculation logic".

## Our reading

**1. The index is a cache of derived data, and the Merkle tree is its invalidation rule.** Lesson [Freshness and Index Updates](/learn/ai/a5-rag/freshness-updates/) taught that every index goes stale and needs a change feed. A client-side repo has no log, so Cursor derives the feed by walking hashes. The cost per edit is about 1 + f x d comparisons, plus embedding the changed chunks. The cache by content removes most of the embedding cost.

**2. Index reuse is a permission problem in disguise.** The server holds derived data (vectors and chunk text) built from a person's code. Handing it to a second person is a read of that code. The usual answer is an access list. Cursor has no list to consult, because there is no central owner of "who may read this repo". So it asks the caller to prove possession. This fits when the set of files you may read equals the set of files you hold. It does not fit when a person may read a file they have not downloaded.

**3. The proof is a claim, not a challenge.** As the page describes it, the client uploads a tree of hashes and the server checks results against it. Our reading: the server cannot see whether the client computed those hashes from files or copied them from somewhere. A challenge-response step would close that gap, for example by asking for a hash of the file content joined with a random value. The page does not describe one. This is the first thing to ask about before copying the design. The risk is small if hashes are never shared. It grows if a hash list can leak.

**4. A shared embedding cache can answer "does this text exist somewhere?"** If the content-keyed cache is shared across users, a fast reply can tell a caller that someone already indexed that exact text. The page does not say how the cache is scoped. Scope it to the team, or add a per-team secret to the key.

**5. During the copy, some results are missing.** The client sees "results only for code it shares with the copied index". Its own different or new files (about 8% on average) are absent until the background sync ends. The agent loop must tolerate this. Falling back to `grep` on the live disk is a clean way, as the coding-agent case argued.

**6. The tail gained the most.** The p99 fell 690 times, the median 15 times. Our reading: the "before" time is uploading and embedding everything. The "after" time is hashing the repo, uploading the tree, and one search. The page does not break down the 525 ms or the 21 s.

**7. Apply needed control of the serving stack, and the post is old.** The post says "It is not possible to build speculative edits into any of anthropic's models, so we need to train and deploy a performant custom model." That is a 2024 statement about Llama 3 and GPT-4. Our reading: a team that only calls a closed API cannot add its own guess logic. We did not check any provider for a feature that accepts a predicted output. Check before you build, and do not read 1,000 tokens a second as a current figure.

## What to copy and what not to

| Idea | Copy it when | Do not copy it when |
|---|---|---|
| Merkle sync to find changes | Many files, small frequent edits, no change log to read | One huge file changes completely each time. The tree stops at the file, so you still need a chunk-level diff |
| Embedding cache keyed by chunk content | Edits leave most chunks unchanged and chunks follow code structure | Chunks are fixed windows that shift on every insert, or the cache is shared across trust boundaries without thought |
| Reuse a similar index by simhash | Many near-identical copies inside one team | Every user has unique content, or the sharing scope is wider than one trust boundary |
| Proof of possession before results | Access is defined by what you already hold | Access is defined by a role or a group. Use an access list (lesson [A5.9](/learn/ai/a5-rag/retrieval-permissions/)) |
| Speculation from the old text | The output is mostly a copy of the input | The output is new text, such as a first draft |
| Tuned small model for one narrow job | The job is narrow, latency matters, and you can host it | You cannot host it, or you cannot test it (no eval set) |

## Interview lens

<Callout type="tip">
Say: "Indexing a repo is slow, so I sync with a Merkle tree and compare hashes top-down, which costs about 1 plus entries-per-folder times depth, not the number of files. I cache embeddings by chunk content so unchanged chunks are free. A new teammate reuses a similar index found with a simhash. Because a similar index holds files they do not have, I filter results by a proof that the client holds each file, and I would ask how the proof resists a replayed hash list. For an edit I rewrite the whole file with speculative decoding, using the old file as the guess, and I say the gain depends on how much of the file is copied." That shows the cost model, the leak, and the limit.
</Callout>

<Callout type="mistake">
Do not say "similar index, so reuse it" and stop. A 92% match means 8% of the files differ, and those are the leak. Do not quote "9x" without the baseline. Do not present a vendor number as a measurement you made. And do not claim the proof is a full security guarantee: the page describes hash possession, not a challenge.
</Callout>
