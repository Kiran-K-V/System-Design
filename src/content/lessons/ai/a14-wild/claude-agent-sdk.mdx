Anthropic describes the Claude Agent SDK as "a collection of tools that helps developers build powerful agents on top of Claude Code". ## What they built and why it was hard

**Company claim.** Anthropic built Claude Code to help its own developers write code. Then the team found that "Claude Code has become far more than a coding tool". They use it "for deep research, video creation, and note-taking", and "it has begun to power almost all of our major agent loops". So they renamed the Claude Code SDK to the Claude Agent SDK. The idea behind it, in the post's words: "The key design principle behind the Claude Agent SDK is to give your agents a computer, allowing them to work like humans do." A computer here means a terminal, files, and tools to search, edit, and run them.

**Our reading.** What is hard about this? In code, the world answers back. A compiler complains and a test fails. A finance or email agent has no compiler. It must find its own context, pick from many tools, and decide for itself whether the work is right. The post's loop is an answer to those three problems, one stage each.

**What kind of source is this?** It matters, so I say it plainly. The post is a design philosophy with practical advice. It is not a description of how Claude Code works inside. Look at the verbs. The email agent that carries the whole post is imagined: "we might define", "we might give it", "our email agent might have". The post gives no code for the loop, no prompt, no limit values, and no measured result from a real deployment. It does not say how many turns a typical run takes or how a subagent is scheduled. For mechanics, read the SDK docs (the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson used them for turn limits and budgets).

So the question here is not "how is it built?" It is "what does the advice assume, and what does it cost to follow?" "Our reading" answers it.

## The before

**Company claim.** The post names the design it moves away from in one sentence: "When developing an agent, you want to give it more than just a prompt: it needs to be able to fetch and update its own context." A prompt is a fixed block of text. Everything the model knows must be put into it before the call.

**Our reading.** The implied before is a one-shot pipeline: gather everything first, call the model once, return the answer. It has two weak points, and the post's loop targets both.

The first is context. Load everything up front and you overfill the window, or you guess what the model will need. The post's fix: let the model fetch what it needs, when it needs it.

The second is success. A one-shot pipeline has no step that asks "did that work?" Picture a task of 5 steps in a row, where each step is right 90% of the time. The chance that all five are right is 0.9 to the power 5, which is 0.59049, about 59% (the [Probabilistic Components](/learn/ai/a0-orientation/probabilistic-components/) lesson built this rule). So 41 runs in 100 end wrong, and nobody is told. The 90% is an illustration, not a figure from the post. With no check, every step's error passes straight to the answer.
## The design

### The loop

**Company claim.** "In Claude Code, Claude often operates in a specific feedback loop: gather context -> take action -> verify work -> repeat." The post says this gives a useful way to think about other agents and the capabilities they need.

The [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson gave the code shape: model call, tool run, append the result. The post sorts what happens inside. Each turn is mostly one of three jobs: fetch information, change something, or check something. The next three sections take the stages in order.

### Gather context

**Agentic search** [mid] means the model searches by calling tools, such as `grep` (find lines in files that match a pattern) and `tail` (show the last lines of a file). It loads only what the search returns. A person debugging in a terminal works the same way.

**Company claim.** "When Claude encounters large files, like logs or user-uploaded files, it will decide which way to load these into its context by using bash scripts like grep and tail. In essence, the folder and file structure of an agent becomes a form of context engineering." The post's email agent keeps old conversations in a folder called "Conversations" so it can search them.

**Context engineering** [mid] is the work of choosing what goes into the model's window and when. The claim is that your folder layout is part of that work: name files so a search finds them, and split large data so one read does not flood the window. The [Context Management for Long-running Agents](/learn/ai/a6-agents/long-running-context/) lesson calls this just-in-time retrieval.

**Semantic search** [mid] is the other way. You cut documents into chunks, turn each chunk into a vector (a list of numbers that stands for its meaning), and search by similarity (lessons [Choosing Embedding Models](/learn/ai/a5-rag/embedding-models/) and [Chunking and Contextual Retrieval](/learn/ai/a5-rag/chunking-contextual/)). **Company claim.** The post says it is usually faster than agentic search, but less accurate, harder to maintain, and less transparent. It advises you to start with agentic search and add semantic search only if you need speed or more variety in queries. The [coding agent lesson](/learn/ai/a13-cases/coding-agent/) quotes the full sentence. The post gives no speed or accuracy figure for either method.

**Subagents.** **Company claim.** The SDK "supports subagents by default". The post gives two reasons. First, parallelism: "you can spin up multiple subagents to work on different tasks simultaneously". Second, context: subagents "use their own isolated context windows, and only send relevant information back to the orchestrator, rather than their full context". The **orchestrator** [mid] is the main agent that hands out the work. The email example: the agent starts several search subagents at once, each running a different query over the email history, and each returns "only the relevant excerpts rather than full email threads". The [Subagents](/learn/ai/a6-agents/subagents/) lesson teaches the mechanism, the brief, and the token cost. The post does not state that cost.

**Compaction.** **Company claim.** "The Claude Agent SDK's compact feature automatically summarizes previous messages when the context limit approaches, so your agent won't run out of context." The post says it is "built on Claude Code's compact slash command". The [Compaction of Long Conversations](/learn/ai/a4-context/compaction/) lesson teaches compaction and its two costs: a lossy summary and an extra model call. The post gives no trigger size.

### Take action

**Company claim.** "Tools are the primary building blocks of execution for your agent." The post adds that tools "are prominent in Claude's context window, making them the primary actions Claude will consider when deciding how to complete a task". So it says to design tools "to maximize context efficiency". Its examples for the email agent are `fetchInbox` and `searchEmails`, the agent's "primary, most frequent actions". The [Tool Design for Agents](/learn/ai/a6-agents/tool-design/) lesson covers tool design.

Three more ways to act:

- **Bash and scripts.** Bash is "a general-purpose tool" for flexible work. The agent could download a PDF attachment, convert it to text, and search the text.
- **Code generation.** "Code is precise, composable, and infinitely reusable." The post says file creation in Claude.ai "relies entirely on code generation": Claude writes Python scripts that build Excel, PowerPoint, and Word files. Running model-written code needs a safe box, which the post does not discuss (the [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) lesson).
- **MCP.** The Model Context Protocol "provides standardized integrations to external services, handling authentication and API calls automatically". The examples are Slack, GitHub, Google Drive, and Asana (the [MCP Servers and Clients](/learn/ai/a6-agents/mcp/) lesson).

### Verify work

**Company claim.** "Agents that can check and improve their own output are fundamentally more reliable—they catch mistakes before they compound, self-correct when they drift, and get better as they iterate." The post gives no measurement behind "fundamentally". It then names three approaches.

**Rules.** The post calls clear rules the best form of feedback, and says to explain which rule failed and why. **Linting** [junior] is a program that checks code against style and error rules. The post says "it is usually better to generate TypeScript and lint it than it is to generate pure JavaScript because it provides you with multiple additional layers of feedback". For the email agent it suggests two rules: throw an error if the address is invalid, and throw a warning if the user has sent mail to that address before. **Our reading:** note the two levels. An error should stop the send. A warning tells the model something to weigh.

**Visual feedback.** For visual tasks such as UI or HTML email, screenshot the result and give the image back to the model to check layout, styling, content hierarchy, and responsiveness. **Playwright** [junior] is a tool that drives a real browser from code, so an agent can open a page, resize it, and take screenshots. The post says a Playwright MCP server can automate this. It adds its own caution: "a single screenshot has limited viewport info".

**LLM as judge.** Another model grades the output "based on fuzzy rules". **Company claim**, exact words: "This is generally not a very robust method, and can have heavy latency tradeoffs, but for applications where any boost in performance is worth the cost, it can be helpful." The example is a subagent that judges whether a draft's tone fits the user's past messages. The post gives no accuracy or latency number. The [Code Checks and LLM Judges](/learn/ai/a8-evals/judges/) lesson teaches how to measure whether a judge can be trusted.

**Our reading:** each of the three brings a signal from outside the model's own answer. Rules are code. A screenshot shows what the output really looks like. A judge is the weakest, because it is another model call and shares some of the first model's blind spots. The [Loop Patterns](/learn/ai/a6-agents/loop-patterns/) lesson gives the same order: code checks first, a model as judge last.

## Our reading

The post gives no figures, so the useful work is to ask what the loop implies. Three things follow, each with a worked number.

### Verification is the reward

In the [AI Coding Agent](/learn/ai/a13-cases/coding-agent/) lesson a test run was called the reward: the signal that lets a loop end well. The post makes the same point for every agent. The loop can only be as good as the signal in its third stage.

Here is the model. A task needs many steps in a row. After each attempt a check runs. It flags a wrong attempt with some chance (the catch rate). It flags a right attempt by mistake with some chance (the false-alarm rate). A flagged attempt is retried, up to a limit. An unflagged attempt is accepted, right or wrong.

A step then ends in one of three ways. It is accepted and right. It is accepted and wrong. Or it is still flagged after the last retry, and the run stops and says it failed. I call that a **loud failure**. The second case is a **silent failure** [mid]: the agent says "done" and is wrong. Silent failures are the dangerous ones, because nobody looks.

Three things to notice, with illustrative values. First, with no check, small per-step errors compound over a chain, and every failure is silent. Second, a strong rules check with retries turns most of those into correct runs. A weak LLM judge still beats no check at all. That fits the post: "any boost in performance". Third, most of what a weak check leaves behind is silent. A weak verifier does not only lower the pass rate. It lets wrong answers pass as done.

Also check retries. A check with no retry only turns silent failures into loud ones, and false alarms stop good runs. A rules check with no retries can score worse than no check. The pass rate rises only when a flag leads to another attempt. The [Loop Patterns](/learn/ai/a6-agents/loop-patterns/) lesson has a one-step version of this idea. Here the check runs after every step of a chain, which is closer to the post's picture.

The post does not say how often rules, screenshots, or judges catch errors.

The cost side. A cheap rules check adds a little cost per attempt. An LLM judge can cost as much as a full attempt, so a run costs about twice as much. The post says the judge has "heavy latency tradeoffs" and gives no number, so this is only our model of the direction. Measure the check's real time before you choose it.

### Tool-result size sets the context budget

**Company claim:** tools sit "prominent" in the window, so design them for context efficiency. **Our reading:** the number that matters most is the size of a tool result, because every later call re-reads it (the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson).

Every call re-reads the whole history, and each tool result stays in it. So the history grows by the size of each result, and the total input over a run grows much faster than the number of calls. Whole files as results fill the window quickly. A few grep lines leave room for far more calls. That fits the post putting grep and tail before any index and asking for context-efficient tools. It does not say how large its own tool results are.

### Context budget per turn

**Company claim:** subagents return only what is relevant, and compaction runs near the limit. **Our reading:** these are two levers on one budget. Subagents lower how fast the history grows. Compaction resets it when it gets full.

A search that needs many calls in the main window adds every result to the history. As a subagent, the parent adds only a short brief and gets a short summary back, so the parent window grows far less. The cost is more total tokens across all windows, as the [Subagents](/learn/ai/a6-agents/subagents/) lesson shows. So the budget per turn is a design choice with three parts: how big each result is, how much of the work moves to a subagent, and when compaction fires.

### What we would test before copying

1. **Catch rate of your own check.** Collect 50 outputs you know are wrong. Run the check. The share it flags is your d. Collect 50 right outputs and measure f. The post gives you neither.
2. **Tool-result size.** Log tokens per tool result in real runs. Look at the 90th percentile, not the mean.
3. **Pass^k with and without verify.** Run each task several times in both setups (the [Agent Loop](/learn/ai/a6-agents/agent-loop/) lesson). Count silent failures separately from loud ones.
4. **Judge against people.** If you use a judge, measure its agreement with human labels before you trust it (the [Code Checks and LLM Judges](/learn/ai/a8-evals/judges/) lesson).

## What to copy and what not to

The post says nothing about safety. It tells you to give an agent bash and a file system, and it never mentions a sandbox, permissions, or approval. That is a gap in the post, not a design choice we can read from it. Lessons [Sandboxes and Code Execution](/learn/ai/a7-agents-prod/sandboxes-code-execution/) and [Tool Permissions and Least Privilege](/learn/ai/a10-safety/tool-permissions/) cover the missing part.

| Idea | Fits when | Does not fit when |
|---|---|---|
| Start with grep, not an index | Data is files you can search; content changes often | You need fast answers over a huge fixed corpus, or meaning-based matches |
| Subagents for wide searches | The work splits into independent pieces and most results are noise | Pieces depend on each other, or the total token cost matters more than the window |
| Compaction near the limit | Runs are long and history cannot be dropped | Runs are short; or a lost detail is costly (keep notes in files) |
| Rules first in verify | You can write the check as code | The output is subjective: tone, taste |
| Visual check | The output is something people look at | One screenshot hides the problem (mobile widths, interaction) |
| LLM judge | Nothing else exists and a gain is worth the cost | You need a reliable gate; use it as a hint, and measure it |
| "Give the agent a computer" | The agent runs in a sandbox with narrow rights | The agent touches real accounts with no limits |

## Interview lens

<Callout type="tip">
Say it as a loop with a signal: "I think of an agent as gather, act, verify. For gather I start with file search like grep and add an index only if I need it. I use subagents for wide searches, so the main window stays small, and I compact near the limit. For verify I put rules first, then a render or screenshot, and an LLM judge last, because it is the least robust. I measure the check's catch rate. With no check, five steps at 90% give 59%. With a good check and retries, a lot more." This shows the loop, the order of verify, and a number you can derive.
</Callout>

<Callout type="mistake">
Do not present this post as a description of how Claude Code is built, or quote numbers from it. It has none. Do not say "add an LLM judge and quality is fixed". The post itself calls that approach "not very robust", and a weak check lets wrong answers pass as done. Also do not skip the retry: a check with no second attempt only changes how the run fails.
</Callout>
