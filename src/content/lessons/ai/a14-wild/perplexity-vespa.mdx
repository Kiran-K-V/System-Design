The address redirects to `vespa.ai/case-studies/why-perplexity-chose-vespa-for-ai-search/`. **Vespa wrote the page, and Vespa sells the engine.** So it is a **vendor case study** [junior]: a story told by the seller of a product, about a customer. Every claim on it is labelled **Company claim (Vespa)** here. Every inference of ours is labelled **Our reading**.

We fetched the page on 2026-10-20. It shows no date on screen. Its page metadata says it was first published on 2025-04-14 and last modified on 2026-10-06. We also use two other Vespa sources. One is a blog post by Vespa's CEO, dated 2025-04-15. The other is Vespa's documentation, fetched 2026-10-20. The documentation tells you what the product does by default. It does not tell you what Perplexity set.

[Lesson A13.7](/learn/ai/a13-cases/deep-research/#drill-answer-engine-perplexity-style) already used this page for a rent-versus-own estimate. We do not repeat that. ## What they built and why it was hard

An **answer engine** [junior] takes a question, finds text on the web, and asks a language model to write a cited answer. The page puts the weight on the finding step. **Company claim (Vespa):** "What separates a trustworthy answer from a plausible-sounding one is the quality of the information retrieved before the model ever runs." The same paragraph says this "meant owning retrieval instead of renting it".

The page then says what the retrieval layer had to do. **Company claim (Vespa):** it "had to index a large, high-quality slice of the web, stay current as that web changed, and return results fast enough to feel instant, all while serving traffic at consumer scale". So the problem has four parts: **coverage**, **freshness**, **speed**, and **scale**.

Here are the three figures the page prints under "Perplexity at a Glance". Each is a **Company claim (Vespa)**.

- "780m+" queries a month.
- "20%+" monthly query growth.
- "170M+" monthly website visits.

**Our reading.** 780 million queries a month is a few hundred queries a second on average. Peak load is higher than the average, and the page gives no peak. Growth of 20% a month, if it held for a year, would multiply traffic several times. The page does not say how long the growth lasted. Do not divide 780m by 170M to get 4.6 queries per visit. The visits count website visits only. The page does not say how many queries come from the apps or an API.

One more point matters before the design. The page has a section called "An Evolving Search Architecture". **Company claim (Vespa):** "It has moved its web index to a purpose-built internal search system and continues to use Vespa for other use cases." The figures above are printed as current. The page does not say which part of that traffic Vespa serves today. We come back to this in "Our reading".

## The before: separate stores

**Company claim (Vespa):** "Rather than stitching together separate databases, vector stores, ranking services, and model-serving infrastructure, Perplexity looked for a single platform capable of performing retrieval and ranking as one integrated system." The page does not show the stitched design. It does not give a hop count or a diagram. So the design below is **our illustration**, built to count what such a stack costs.

The illustrated stack has six calls for one question. An embedding server turns the question into a vector. A vector database finds near vectors. A keyword index finds exact words. A metadata store holds fields such as date and language. A light ranker service cuts the list. A GPU service reranks the survivors. Three things go wrong in a stack like this. We take them one at a time.

### Why a filter is hard in a vector search

**Company claim (Vespa):** "Perplexity found that vector databases could not reliably support even simple boolean filters, while traditional search backends offered only primitive semantic ranking." Read the first half closely.

A **boolean filter** [junior] is a yes-or-no test on a stored field, such as `language = en` or `published after 2026-01-01`. An answer engine needs many of them. It needs fresh pages for news, one language for one user, and no blocked sites.

A vector search uses **ANN** [mid], approximate nearest neighbour search. It finds the vectors closest to the question vector without checking every vector. The index is a map of distances. It does not know which vectors pass your filter. Lesson [A5.3](/learn/ai/a5-rag/vector-db-filters/) shows the trap. If the index returns its 40 nearest candidates and then the filter drops the ones that fail, a filter that 10% of rows pass leaves 40 x 0.10 = **4 rows**. A filter that 1% pass leaves 0.4 rows. The query returns without an error. It just returns too few results. The share of rows a filter keeps is its **selectivity** [mid]. The lower it is, the worse the trap.

Vespa's own documentation describes how an engine can avoid the trap. **Company claim (Vespa docs, fetched 2026-10-20):** the query operator can be combined with other filters; there are "two high-level strategies", pre-filtering (the default) and post-filtering; and the nearest-neighbour search supports "both pre-and post-filtering, beam exploration, and filtering before distance calculation". The strategy is chosen with two settings, `approximate-threshold` and `post-filter-threshold`. Pre-filtering means: find the rows that pass the filter first, then search only those. The engine can do this because the filter fields and the vectors live in one index.

**Our reading.** The page's sentence has no product name, no test, no selectivity and no date. It says what Perplexity found with the tools it tried, at an unknown time. Products change. In lesson [A5.3](/learn/ai/a5-rag/vector-db-filters/), pgvector 0.8.0 added iterative scans for exactly this problem. So do not repeat the sentence as a rule about all vector databases. Do repeat the lesson under it. Ask any store: how does my filter meet your index, and what comes back at 0.1% selectivity?

### What a network hop costs

A **network hop** [junior] is one call from one service to another over the network. A **round trip** [junior] is the call and the reply together. Picture asking a colleague at the next desk compared with sending a courier across town. The question is the same. The wait is not.

<CrossTrackLink id="01-one-machine/latency-numbers">
A round trip inside one data centre takes about 500 microseconds, which is 0.5 ms. That is about 5 times an SSD read. Across an ocean it is 70 to 150 ms. That is the one sourced number we use for hops below.
</CrossTrackLink>

A hop costs four things, and only the first is a fixed price.

1. **The round trip.** About 0.5 ms each, and hops in a row add up.
2. **The bytes.** A candidate list must be sent and received. A thousand passages are megabytes, and a real link carries less than its label.
3. **The tail.** A call that is slow once in a while hurts more when you make more calls, because any one slow call slows the request. The same rule appeared in [A13.7](/learn/ai/a13-cases/deep-research/) for parallel fetches.
4. **The copies.** Each store holds its own copy of the data. A page that is updated in the vector database before the metadata store gives a candidate that the filter has not seen yet.

The fourth cost is the one the page leans on. It lists "real-time updates" as one of its capabilities, which we take up below.

## The design

**Company claim (Vespa):** the engine "brought these capabilities together in a single distributed serving engine, with support for continuous indexing and machine learning inference". The page then lists seven features under "One Engine for Retrieval, Ranking and Inference". We take five that matter for this lesson. Each gets the claim, the idea from scratch, and our reading.

### Hybrid retrieval with structured filtering

**Company claim (Vespa):** "Combine lexical, semantic, and structured signals within a unified retrieval and ranking pipeline, so results are both semantically relevant and exactly matched on names, terms, and filters."

**Lexical** [junior] search matches words. **Semantic** [junior] search matches meaning through vectors. **Structured** signals are the filter fields. The page says the AI ecosystem had "split into lexical systems and semantic systems, each strong on one side and weak on the other". Lesson [A5.5](/learn/ai/a5-rag/hybrid-rrf/) taught why you need both. A search for the error code `ERR_4012` needs the words. A search for "get my money back" needs the meaning. The page's claim is about where they run. It says they run in one engine and in one pipeline, with the filter applied inside the same search.

### Passage-level retrieval and ranking

**Company claim (Vespa):** "Rank and return the most relevant passages within documents, not just entire pages, giving the language model more focused, grounded context."

A **passage** [junior] is a short piece of a page, a few sentences long. Retrieval at page level returns the whole page. The model then reads thousands of tokens to use one paragraph. **Illustrative numbers:** if a page is 4,000 tokens and the answer sits in a 200-token passage, ten pages cost 40,000 input tokens and ten passages cost 2,000. That is 20 times fewer. Lesson [A5.4](/learn/ai/a5-rag/chunking-contextual/) taught how to cut pages into chunks. The page's claim is that the engine ranks the passages inside each document, so you do not need a separate chunk store.

### Real-time updates

**Company claim (Vespa):** the engine can update "content, vectors, metadata, and behavioral signals" "without interrupting live queries or rebuilding the index".

**Real-time indexing** [mid] means a new or changed page becomes searchable in seconds, with no batch rebuild. The page says Perplexity's index had to "stay current as that web changed". Lesson [A5.8](/learn/ai/a5-rag/freshness-updates/) covers update paths. The one-engine point is this: the vector, the words and the metadata are in one record. One write updates all of them. In a stitched stack, three stores take three writes, and a reader can see a half-updated page.

### Multi-stage ranking: the funnel

**Company claim (Vespa):** "Narrow large candidate sets efficiently with lightweight ranking, then apply richer neural models to the most promising results."

A **multi-stage ranker** [mid] is a funnel. A cheap scorer looks at many candidates and keeps a few. An expensive scorer looks at only the few. Picture a hiring process. A resume screen reads 1,000 resumes in an afternoon. Interviews take an hour each, so you run them for 20 people. The reason is cost. A **cross-encoder** [senior] reads the question and one passage together, so it is precise, and it must run once per pair. Lesson [A5.6](/learn/ai/a5-rag/reranking-rewriting/) taught this.

The page publishes no candidate counts. Vespa's documentation gives product defaults. **Company claim (Vespa docs, fetched 2026-10-20):** the first-phase expression is "computed for every document retrieved by the query" and must be cheap. The second phase is, by default, "evaluated for the 100 best hits from the first-phase ranking per content node". A **content node** [mid] holds a share of the data and its index. The **stateless container** [mid] takes the query, sends it to the content nodes, and merges what they return. A third phase, the **global phase**, will "run in the stateless container after gathering the best hits". The docs say: "By default, global-phase ranking runs on the 100 globally best hits for a schema." They say the phase "is optimized for inference with ONNX models" (**ONNX** [mid] is a file format that many runtimes can load, for a trained model). They add: "A typical use case is re-ranking using cross-encoders". The docs also let you run it on a GPU. These are product defaults. Do not read them as Perplexity's settings.

Now the idea. **Illustrative:** retrieve about a thousand candidates. A light ranker scores each one in microseconds and keeps about a hundred. A cross-encoder is slow per pair, so it scores only those hundred and keeps about ten. If the cross-encoder scored all thousand, it would take roughly ten times longer. The funnel avoids most of that neural cost for a tiny cost of light ranking. Move the sliders below. The per-pair time comes from the same example as lesson [A5.6](/learn/ai/a5-rag/reranking-rewriting/) and is also an assumption.

Look at the three bars at the bottom of the simulator. They show that the funnel is the big saving. The next section looks at the smaller one.

### Machine learning in the serving layer

**Company claim (Vespa):** "Execute ranking models and cross-encoders directly within the serving layer, eliminating external orchestration and its added latency." And: "Co-locating data, indexes, and computation on the same nodes avoids bandwidth bottlenecks and keeps infrastructure spend in check as traffic grows."

The **serving layer** [mid] is the part of the system that answers live queries. **Inference** [junior] is running a trained model to get a score. **Co-location** [mid] means the model runs on the same machines that hold the data. Picture a cook who works in the pantry compared with one who sends a runner to a warehouse for every ingredient. The idea is to bring the computation to the data.

Step through the three designs. The first is the stitched stack. The second is one engine with the model still outside. The third runs the model inside.

## Our reading

**The page describes a choice made at one time.** The headline reads like a current setup. The text says the web index has since moved to a "purpose-built internal search system". The phrase "purpose-built" does not tell you whether the new system keeps the one-engine idea. It does not give a reason or a date. A reasonable guess is that a company at this scale wants more control, but that is a guess. So the page is good evidence for the problem list: filters, hybrid retrieval, freshness, a funnel. It is weak evidence for "Vespa is how Perplexity searches today".

**The funnel is the big saving. The hop is the small one.** Take the default simulator inputs (1,000, 100 and 10 candidates, 0.5 ms a round trip).

| Design | Network | Total | Calls and round trips in a row |
|---|---|---|---|
| Separate stores | 6.0 ms (2.5 ms round trips, 3.5 ms for 4.4 MB) | 61.0 ms | 6 calls, 5 round trips |
| One engine, reranker outside | 1.8 ms | 56.8 ms | 3 calls, 3 round trips |
| One engine, inference inside | 1.0 ms | 56.0 ms | 2 calls, 2 round trips |
| No funnel (neural on all 1,000) | not counted | 410 ms | not counted |

All of these are **illustrative**. On them, going from separate stores to one engine with inference inside saves about 5 ms of 61, which is 8%. Dropping the funnel costs about 350 ms. The page says external orchestration adds latency. That is true in direction. At 0.5 ms a hop it is a small part of a request.

Three things make the hop matter more than that.

1. **Retrieval width.** Raise the retrieved candidates to 10,000. The stitched design now ships 40.4 MB, which takes 32 ms, and its network share rises to 26% of 135 ms. The one-engine design with inference inside ships 20 KB. This is the bandwidth claim in numbers. It bites when you rank many candidates.
2. **Round-trip time.** At 5 ms a hop (a busy network, or a call across zones), the stitched total is 83.5 ms against 65.0 ms. The Vespa CEO's blog says the whole path must fit in "about a hundred milliseconds", so that gap matters.
3. **The tail.** Six calls give a 5.9% chance that one is in its slowest 1%. Two calls give 2.0%. The median hides this.

**What does not change.** The embedding call stays unless the engine also makes the query vector, which the page does not claim. The funnel is a design of ours that you can build in any stack. A stitched stack with a funnel keeps most of the saving.

**What we would test before copying the design.**

- Filtered recall: run your real filters at 0.1% selectivity and count the rows that return.
- The p99 of the full path in both designs, under the same load. Not the average.
- Freshness lag: the time from a write to the page being searchable and filterable, in each store.
- GPU cost. A model inside the engine ties GPU capacity to the nodes that hold the index. If the two need to scale at different rates, you may pay for idle GPUs. The page does not discuss this.

## What to copy and what not to

| Idea | Copy it when | Do not copy it when |
|---|---|---|
| Filter inside the search, with a pre-filter | Filters are common and can be very selective (a tenant, a date, a language) | The filter keeps most rows, so a plain post-filter works |
| Two-stage funnel, cheap then neural | The neural model costs milliseconds per pair and you retrieve hundreds | You retrieve under 20 candidates, so a funnel saves nothing |
| Passage-level ranking | The answer is a few sentences inside long pages | The pages are already short, such as FAQ entries |
| One engine for retrieval and ranking | The index is large, updates are frequent, and the team can run it | A small corpus fits in one Postgres, or the team cannot run a cluster |
| Inference inside the serving layer | You score thousands of candidates, or you have a tight tail budget | The model must scale apart from the index, or it changes weekly |
| A vendor page as evidence | You want the problem list and the vocabulary | You want a number you can plan from. This page gives none for latency |
