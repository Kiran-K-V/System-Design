## The problem

Your design says "the user sends a 2,000-word document and gets a summary". Three questions follow. Does it fit in the model? How long will it take? What does it cost?

All three answers depend on one unit. It is not the word, the character, or the byte. It is the **token** [junior]: one piece of text that the model treats as a single symbol. The context limit counts tokens. Latency grows with tokens. The price list is in tokens. If you size a design in words, you will be wrong. The error is not the same for every user.

## Naive view: one word is one token

A beginner thinks a model reads words. That fails in two ways.

- A word list is closed. A new name, a typo, or a word in another language has no entry. The old fix was an "unknown" symbol, and the model lost the word.
- A word list is huge. Every form of every word (run, runs, running, runner) is its own row.

The other extreme is one token per character. That approach never fails on unknown words. But a 2,000-word document becomes about 12,000 symbols. And the model has to learn spelling for every word.

Tokenizers sit between the two. Common words are one token. Rare words are a few pieces. Unknown text falls back to bytes.

## The mechanism: byte-pair encoding

A **tokenizer** [junior] is the component that turns text into token ids and back. It is fixed before the model is trained. It is a lookup structure, close to a compression dictionary.

**Byte-pair encoding (BPE)** [mid] builds that dictionary from data. It was taken from data compression and applied to translation by Sennrich and colleagues (2015), who report gains of +1.1 and +1.3 BLEU over a back-off dictionary on two WMT15 tasks. The training loop is short:

1. Start with single symbols. For GPT-2 and Llama 3, the base is the 256 possible byte values. So any input can be encoded, and no unknown token is needed.
2. Count each pair of neighbors, weighted by how often the word occurs.
3. Merge the most frequent pair into a new symbol.
4. Repeat until the vocabulary reaches the target size.

Karpathy's `minbpe` states the id rule. Ids 0 to 255 are raw bytes. So the vocabulary size is 256 plus the number of merges. Step through three merges on a real string. The corpus here is the string itself. A real tokenizer reads terabytes of text, but the loop is the same.

Sizes: GPT-2 has 50,257 tokens. GPT-4-era `cl100k_base` has about 100K. Llama 3 has 128K: about 100K from the tiktoken tokenizer plus 28K added for non-English text. The Llama 3 paper reports 3.94 characters per token on English, up from 3.17 for Llama 2. A bigger vocabulary packs the same text into fewer tokens. The price is a larger embedding table (lesson [A1.2](/learn/ai/a1-model-function/embeddings/)).

To encode new text, apply the learned merges in the order they were learned. Decoding is a table lookup from id to bytes. Both are fast and run on a CPU, outside the model.

Before any request reaches a model, a parser turns bytes into structure. Tokenizing is the same kind of step. It runs on the CPU, before the GPU, and its output size sets the work for everything after it.
</CrossTrackLink>

## Where the rule of thumb breaks

You will hear "one token is about four characters" or "three quarters of a word". The first number is real for English prose on older tokenizers. Kaplan and colleagues measured 4.3 characters and 1.4 tokens per word on WebText2. They used the GPT-2 tokenizer. It is not a law. Anthropic's model overview says 1M tokens is about 555K words on the current Claude tokenizer (about 1.8 tokens per word), and 750K words on earlier models. The same page gives 200K tokens as about 150K words for the earlier ones. **The ratio belongs to the tokenizer.** Count with the tokenizer of the model you use.

Other languages are worse. A tokenizer trained mostly on English has few merges for Hindi or Burmese, so those texts stay in small pieces. Petrov and colleagues (2023) found that the same translated text can differ in token length. The difference can be up to 15x between languages. A TopBots test in 2023 on `cl100k_base` used 2,033 short texts per language. It found median token counts of about 5x English for Hindi and Bengali. For Armenian, the count was about 9x. For Burmese, the count was over 10x. Newer tokenizers show smaller gaps, but multilingual tokenizers still do not close them.

This is a cost and a quality issue. A Hindi user pays about five times more per message. The same user fills the context window five times faster. That user waits for five times more tokens on the way out.

Two more failures come from the same cause. First, the model sees tokens, not letters. One paper on letter counting reports that the GPT-4o tokenizer cuts "strawberry" into "st", "raw", "berry". So a question about the letter r asks the model to see inside a symbol. The paper lists three causes: tokenization, attention limits, and no character-level training data. We did not test current models. Second, numbers and code also split in ways that depend on the tokenizer. We have no sourced ratio for them, so measure them.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Bigger vocabulary | Fewer tokens per text, faster and cheaper | Larger embedding and output tables | Many languages, long contexts |
| Smaller vocabulary | Small tables | More tokens per text | Tiny models |
| Count by tokenizer | Exact limits and bills | You need the tokenizer library | Any production budget |
| Count by words times a ratio | Quick sizing | Off by 25% or more for some users | Interviews, first estimates |

## Interview lens

<Callout type="tip">
Size a design in tokens and name the tokenizer. Say: "A 3K-token prompt on a 128K-context model, priced per million input tokens." Then add: "For non-English users I would measure token counts per language, because they can be several times higher."
</Callout>

<Callout type="mistake">
Do not say "one word is one token" or give a fixed "4 characters per token" for every user. Say it is a ratio that depends on the tokenizer and the language. Do not forget that output tokens cost more than input tokens on the pricing page above.
</Callout>
