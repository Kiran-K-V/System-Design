## The problem

Your design says "the user sends a 2,000-word document and gets a summary". Three questions follow. Does it fit in the model? How long will it take? What does it cost?

A language model is a program that reads text and writes text. Engineers often call it an LLM, short for large language model. The model does not read letters the way you do. Inside, it works only with numbers. So something must turn your text into numbers first.

That step cuts the text into small pieces. Engineers call each piece a **token**. Think of a Lego set. The model does not see a finished castle. It sees a pile of bricks, and each brick is one token.

Three things count tokens, not words:

- The context limit is the most text the model can read at one time. It is measured in tokens.
- Latency is the time the user waits. It grows with the number of tokens.
- The price list charges per token.

If you size a design in words, you will be wrong. The error is not the same for every user.

## Naive view: one word is one token

A beginner thinks a model reads whole words. Imagine the model owns a big word list, and each word has a number. That fails in two ways.

- A word list is closed. A new name, a typo, or a word in another language has no entry. The old fix was one "unknown" symbol for every missing word. The model lost the word.
- A word list is huge. Every form of every word (run, runs, running, runner) needs its own row.

The other extreme is one token per character. Picture a library that files each book letter by letter. That approach never fails on an unknown word. But a 2,000-word document becomes about 12,000 symbols. And the model has to learn how to spell every word from scratch.

Real tokenizers sit between the two. Common words are one token. Rare words are a few pieces. Text the tokenizer has never seen falls back to bytes. A byte is the smallest unit a computer stores. It is a number from 0 to 255, and every letter or symbol is made of one or more bytes.

## The mechanism: byte-pair encoding

A **tokenizer** is the part that turns text into token ids and back. A token id is the number that names one token. Think of a school with student ID numbers. The name is the piece of text. The id is the number the model uses.

The tokenizer keeps a list of every piece it knows, with an id for each. Engineers call that list the **vocabulary**. The list is fixed before the model is trained. It works like a dictionary used for compressing files.

**Byte-pair encoding (BPE)** is the method that builds this vocabulary from real text. The name says what it does. It looks at pairs of neighbors and joins them. It started as a trick to make files smaller. Later, engineers found it also works well for cutting text into pieces. The training loop is short:

1. Start with single symbols. In GPT-2 and Llama 3, the starting symbols are the 256 possible byte values. (GPT-2 and Llama 3 are well-known language models. Llama 3 is an open model from Meta.) So any input can be encoded, and no "unknown" token is needed.
2. Count each pair of neighbors. Think of counting how often two letters sit side by side. A pair inside a common word counts more than a pair inside a rare word.
3. Merge the most frequent pair into one new symbol. Think of gluing two bricks into one bigger brick.
4. Repeat until the vocabulary reaches the target size.

The ids follow a simple rule. Ids 0 to 255 are the raw bytes. Each merge adds one new token with the next free id. So the vocabulary is the 256 bytes plus one token per merge.

Now step through three merges on a real string. The text we learn from is the string itself. A real tokenizer reads terabytes of text. The loop is the same.

Here are some real sizes. GPT-2 has 50,257 tokens. The GPT-4-era tokenizer has about 100K. (GPT-4 is a model from OpenAI. K means thousand.) Llama 3 has 128K. About 100K of them come from an existing tokenizer, and 28K were added for non-English text. Meta's report on Llama 3 gives 3.94 characters per token on English. For Llama 2, the older model, it was 3.17.

A bigger vocabulary packs the same text into fewer tokens. The price is a larger **embedding table**. That is a big table that gives each token a list of numbers the model can work with. The [Embeddings](/learn/ai/a1-model-function/embeddings/) lesson explains it.

To encode new text, apply the learned merges in the order they were learned. To decode, look up each id in the table and get its bytes back. Both steps are fast. They run on the CPU, outside the model. The CPU is the main chip of a computer. It does general work, one step after another.

<CrossTrackLink id="01-one-machine/request-journey">
Before any request reaches a model, a parser turns raw bytes into structure. A parser is a program that reads raw input and sorts it into labeled parts. Tokenizing is the same kind of step. It runs on the CPU. The GPU comes later. A GPU is a chip built to do huge amounts of simple math at once, and it runs the model. The number of tokens sets the work for everything after this step.
</CrossTrackLink>

## Where the rule of thumb breaks

You will hear "one token is about four characters" or "three quarters of a word". The first number is real for English prose on older tokenizers. One older study measured 4.3 characters per token and 1.4 tokens per word on English web text. It used the GPT-2 tokenizer. But this is not a law.

Anthropic, the company that makes Claude, gives its own numbers in its model overview. On the current Claude tokenizer, 1M tokens is about 555K words. Here M means million. That is about 1.8 tokens per word. On earlier models, 1M tokens is about 750K words. The same page gives 200K tokens as about 150K words for the earlier models. **The ratio belongs to the tokenizer.** Count with the tokenizer of the model you use.

Other languages are worse. Picture a tokenizer trained mostly on English. It has learned many merges for English letter pairs. It has few merges for Hindi or Burmese, so those texts stay in small pieces.

A research study in 2023 found that the same translated text can differ in token length. The difference can be up to 15x between languages. A blog test in 2023 used the GPT-4-era tokenizer on 2,033 short texts per language. The median Hindi or Bengali text had about 5x the tokens of English. For Armenian, it was about 9x. For Burmese, it was over 10x. Newer tokenizers show smaller gaps. But tokenizers built for many languages still do not close them.

This is a cost problem and a quality problem. A Hindi user pays about five times more per message. The same user fills the context limit five times faster. The same user also waits for five times more tokens on the way out.

An estimate from the ratios above is not a tokenizer's count.

Here are real prices. They are from 2026-10-15, taken from the [Anthropic pricing page](https://platform.claude.com/docs/en/about-claude/pricing). Claude Sonnet 5.5 and Claude Haiku 5.5 are two models from Anthropic.

- Input tokens are the text you send to the model. Output tokens are the text the model writes back.
- Claude Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens.
- Claude Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens. This holds for prompts up to 100,000 tokens. A prompt is the text you send in one request.

Check the live page before you quote these prices.

Two more failures come from the same cause. First, the model sees tokens, not letters. One research paper on letter counting reports that the GPT-4o tokenizer cuts "strawberry" into "st", "raw", "berry". GPT-4o is another model from OpenAI. Now think about the question "How many letter r are in strawberry?" The model must look inside a single symbol to answer. That is hard for it.

The paper lists three causes. The first is tokenization. The second is limits in attention, the step where the model weighs how the tokens relate to each other. The third is a lack of training data that works at the level of single characters. We did not test current models.

Second, numbers and code also split in ways that depend on the tokenizer. We have no sourced ratio for them, so measure them.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Bigger vocabulary | Fewer tokens per text, faster and cheaper | Larger embedding and output tables | Many languages, long contexts |
| Smaller vocabulary | Small tables | More tokens per text | Tiny models |
| Count by tokenizer | Exact limits and bills | You need the tokenizer library | Any production budget |
| Count by words times a ratio | Quick sizing | Off by 25% or more for some users | Interviews, first estimates |

## Interview lens

<Callout type="tip">
Size a design in tokens and name the tokenizer. Say: "A 3K-token prompt on a 128K-context model, priced per million input tokens." (A 128K-context model can read up to 128K tokens at one time.) Then add: "For non-English users I would measure token counts per language, because they can be several times higher."
</Callout>

<Callout type="mistake">
Do not say "one word is one token" or give a fixed "4 characters per token" for every user. Say it is a ratio that depends on the tokenizer and the language. Do not forget that output tokens cost more than input tokens on the pricing page above.
</Callout>
