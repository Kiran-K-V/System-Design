## The problem

Lesson [A1.3](/learn/ai/a1-model-function/forward-pass/) gave a clean rule: about 2N FLOPs per token. A 70B model costs 140 GFLOPs per token. By that rule, a 100,000-token prompt costs 100 times a 1,000-token prompt.

It does not. Measure it and the long prompt is slower than 100 times. The 2N rule counts the matrix weights. It leaves out one more cost: every token also **reads all earlier tokens**. That part does not grow in a straight line.

## Naive view: cost per token is constant

If each token costs the same, a prompt costs `n × 2N`. Latency grows in a straight line. You plan capacity on that. And for a short prompt it is nearly true.

It fails because of what attention does. **Attention** [mid] lets a token pull information from the other tokens. Each token makes a **query** [mid] (what am I looking for). Each earlier token offers a **key** [mid] (what do I hold) and a **value** [mid] (what I pass on). The model compares the query with every key. It turns the scores into weights with softmax. Then it takes a weighted sum of the values.

<Math block tex="\text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{Q K^{\top}}{\sqrt{d_k}}\right) V" />

The original Transformer paper states this formula. In words: score every query against every key, then mix the values by those scores. For a backend engineer it is a nested loop: for each token, loop over all earlier tokens. Two nested loops over n items give n² steps.

## The mechanism: the score matrix

Picture the scores as an n × n grid. Row i holds token i's scores against every token it may read. A **causal mask** [mid] blocks the cells above the diagonal, because a text generator may not read the future. About half the grid stays.

<Ai1AttnMatrix client:visible />

Per layer, the score step costs 2·n²·d FLOPs for QKᵀ and another 2·n²·d for the weighted sum with V. Here d is d_model, equal to heads times head dim. Over L layers:

<Math block tex="\text{attention FLOPs} \approx 4\,n^{2}\,d\,L" />

This is a standard estimate, and the same for grouped-query attention, because every query head still scores every key. Compare it with the linear part, 2·N·n. The ratio simplifies:

<Math block tex="\frac{4\,n^{2}\,d\,L}{2\,N\,n} = \frac{2\,n\,d\,L}{N}" />

Plug in Llama 3 70B: N = 70.5B, d = 8,192, L = 80. Then 2·d·L/N = 1,310,720 / 70.5e9 = 1.86 × 10⁻⁵ per token of prompt.

- **n = 8,192:** the ratio is 0.152. Linear work is 1.16 PFLOPs. Attention adds 0.18 PFLOPs, about **15%**.
- **n = 131,072 (128K):** the ratio is 2.43. Linear work is 18.5 PFLOPs. Attention is 45 PFLOPs, about **2.4x** the linear part.
- The ratio reaches 1 at n = N / (2dL), about **54,000 tokens**.

Going from 8K to 128K is 16 times more tokens. Linear work grows 16x. Attention work grows 16² = 256x. These numbers are for the full square. Kernels that skip the masked half do half the work. The results are 7.6% at 8K, 1.2x at 128K, and a break-even near 108,000 tokens. Drag the slider and switch the mask.

All of this is the **prefill** [mid] phase: the model reads the whole prompt at once. During generation, each new token adds just one row of n scores. As a result, its attention work grows linearly with the context. Lesson [A2.2](/learn/ai/a2-inference-cost/prefill-decode/) covers that phase.

## Memory: the n × n matrix

A naive implementation writes the whole score matrix to GPU memory. For 70B that is 64 heads × n² × 2 bytes (BF16) per layer. At 8K tokens that is 8.6 GB. At 128K it is 2.2 TB. No GPU has that, so the naive method does not work at long context, whatever the compute budget.

**FlashAttention** [senior] fixes the memory problem without changing the answer. Its authors call it "an IO-aware exact attention algorithm that uses tiling". It computes the result in small tiles that fit in fast on-chip memory. The method fuses the steps into one GPU kernel. It also keeps only a running maximum and sum per row. The paper reports that it uses less memory, linear in sequence length, and is up to 7.6x faster on GPT-2 (their Figure 1). Per layer, the extra storage is about one fp32 number per row per head. At 128K, 64 × 131,072 × 4 bytes = 34 MB. This is our estimate from the paper's O(n) result.

Note what did **not** change. FlashAttention computes every cell, so FLOPs stay quadratic. It saves memory reads and writes, which is where the time goes in practice. But a 128K prefill still does the n² work.

## The KV cache: what you must keep

When a model generates token n+1, it needs the keys and values of all n earlier tokens. They do not change, so the model computes them once and stores them. That store is the **KV cache** [mid]. It is a cache in the backend sense: compute once, read many times, memory in exchange for compute.

<CrossTrackLink id="05-caching/why-cache">
A cache trades memory for repeated work. The KV cache avoids repeated work for attention. It keeps each token's key and value. As a result, later tokens do not recompute them. As with any cache, size and eviction become design questions.
</CrossTrackLink>

The size per token is 2 (K and V) × layers × KV heads × head dim. Multiply that by 2 bytes (BF16). For 70B: 2 × 80 × 8 × 128 × 2 = 327,680 bytes, which is **320 KiB per token**. An 8K sequence takes 2.5 GiB. A 128K sequence takes 40 GiB. The cache grows in a straight line with n, but each user has their own.

Why 8 KV heads and not 64? **Multi-query attention (MQA)** [senior] has all query heads share one key and value head. The shared head cuts memory traffic when generating, at a small quality loss. **Grouped-query attention (GQA)** [senior] sits between full multi-head and MQA. Its authors report that a multi-head checkpoint can be converted with about 5% of the original pretraining compute. The converted model has quality close to multi-head and speed close to MQA. Llama 3 uses 8 KV heads with 64 query heads at 70B. With 64 KV heads the cache would be 8 times larger: 2.5 MiB per token, or 320 GiB at 128K. This is derived arithmetic.

Llama 3 supports up to 128K tokens. Its paper says the model was pretrained at 8K and then extended. Several vendors list windows of about 1M tokens as of 2026-10-15 (lesson [A1.6](/learn/ai/a1-model-function/hallucination-context/)). A big window is a ceiling, not a recommendation: each token costs compute, memory, and latency.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Long prompt | Whole document in view | Quadratic attention in prefill, KV cache per user | The task truly needs it |
| Retrieve a few chunks | Short prompt, low cost | Retrieval step and its misses | Large corpora |
| FlashAttention | Linear score memory, faster kernels | A fused kernel on supported GPUs | Always, at long context |
| GQA with few KV heads | Smaller KV cache, more users per GPU | Small quality risk | Serving many long sessions |
| Skip the masked half | Half the attention FLOPs | Kernel support | Prefill of long prompts |

## Interview lens

<Callout type="tip">
When someone proposes "just put the whole corpus in the prompt", answer with numbers. "At 128K tokens a 70B model spends about 2.4 times more on attention than on the weights. The KV cache is 40 GiB for one user. I would retrieve the 3K tokens that matter."
</Callout>

<Callout type="mistake">
Do not say "FlashAttention makes attention linear". It makes the **memory** linear. The FLOPs stay quadratic. Do not say "double the context, double the cost" for prefill. Do not confuse the KV cache (grows in a line with n, per user) with the score matrix. The score matrix grows with n², and a good kernel never stores it.
</Callout>
