## The problem

You need to answer three sizing questions about a model you did not build. How much GPU memory do the weights take? How much compute does one token cost? How does it change if you pick the 70B model instead of the 8B?

You do not need the math of training. You need to read a model config and see what it means for memory and compute. A **FLOP** [mid] is one floating-point operation, such as one multiply or one add. This lesson gives you that skill, using Llama 3 as the worked case.

## Naive view: a black box

If the model is a black box, you can only measure it: run it, time it, read the bill. That works for one model. It fails when you must compare models before you buy GPUs, or explain why a 70B model is about nine times more compute per token than an 8B one. The inside is simple enough to count.

## The mechanism: a stack of identical layers

A decoder-only transformer turns a list of token ids into a score for each possible next token. It does this in four parts.

1. **Embed.** Look up each id in the table (the [Embeddings](/learn/ai/a1-model-function/embeddings/) lesson). Each token becomes a vector of d_model numbers.
2. **N layers.** Every layer has two blocks with the same shape in every layer, but different weights.
   - **Attention** [mid]: each token reads information from earlier tokens (the [Attention and Its Cost](/learn/ai/a1-model-function/attention-cost/) lesson).
   - **MLP** [mid] (feed-forward block): two or three matrix multiplies that work on each token alone. The Illustrated Transformer states it plainly: the same network is applied to each position independently.
3. **Output head.** A final matrix maps the last vector to one **logit** [mid] (raw score) per vocabulary token.
4. **Softmax** [mid]. It turns the logits into probabilities that sum to 1 (the [Sampling and Decoding](/learn/ai/a1-model-function/sampling-decoding/) lesson covers sampling from them).

Between blocks, a vector per token flows along the **residual stream** [senior]. Each block computes a change and adds it to the stream. The stream keeps its width (d_model) from the first layer to the last. For a systems engineer, think of it as a shared buffer that every layer reads and appends to.

### The Llama 3 configs

These come from Table 3 of the Llama 3 paper.

| | 8B | 70B | 405B |
|---|---|---|---|
| Layers | 32 | 80 | 126 |
| d_model | 4,096 | 8,192 | 16,384 |
| FFN dim | 14,336 | 28,672 | 53,248 |
| Query heads | 32 | 64 | 128 |
| KV heads | 8 | 8 | 8 |
| Vocabulary | 128,000 | 128,000 | 128,000 |

For scale, the original Transformer paper's base model had 6 layers, d_model 512, FFN dim 2,048, and 8 heads. Llama 3 8B is wider by 8x and deeper by 5x.

### Counting the parameters

A **parameter** is one learned number. Every weight matrix is a rectangle of them, so counting is multiplication. Let d be d_model, h the number of query heads, and h_kv the KV heads. The head dim = d / h, which is 128 in all three models.

- **Attention per layer:** four matrices. The query and output matrices are d × d. The key and value matrices are d × (h_kv × head dim). They are smaller because the 8 KV heads are shared (grouped-query attention, the [Attention and Its Cost](/learn/ai/a1-model-function/attention-cost/) lesson).
- **MLP per layer:** three matrices of d × FFN (the SwiGLU design in Llama).
- **Embeddings:** vocabulary × d for the input table, and the same again for the output head.

<Math block tex="P \approx L\,\bigl(2d^2 + 2d\,d_{kv} + 3\,d\,d_{ff}\bigr) + 2\,V d" />

Add up the matrices in every layer, then add the two embedding tables. For Llama 3 8B the total lands at about ~8B, as the paper says. The same count for 70B and 405B also lands within 1% of the published sizes. We assume untied input and output tables, SwiGLU, and we skip the small normalization weights.

Two facts stand out. The MLP holds most of the parameters (about 70% in 8B). Attention holds only a small share (about 17% in 8B). Even so, the next lesson shows attention can dominate the cost at long context.

## Cost per token: about 2N

Each parameter in a matrix takes part in one multiply and one add per token. That is **2 FLOPs per parameter per token**. Kaplan and colleagues give the forward pass as about 2N FLOPs per token, with N the parameter count. So a bigger model costs more per token in direct proportion to its parameter count. The rule has one flaw: the input table is a lookup, not a multiply, so the true cost is a little lower, most visibly for small models. The attention score math adds more at long prompts (the [Attention and Its Cost](/learn/ai/a1-model-function/attention-cost/) lesson).

Memory is separate. The weights in BF16 take 2 bytes per parameter. The 8B model fits on one GPU (~16 GB). The 70B model needs about ~141 GB, which a single 80 GB GPU cannot hold. (The [GPU Memory Math](/learn/ai/a2-inference-cost/gpu-memory-math/) lesson does this properly.)

Training costs more. The backward pass takes about twice the forward pass. As a result, training costs about three times the forward pass for each token, and it repeats that over trillions of training tokens. That is why training a big model takes a large cluster for months, while one answer takes a fraction of a second.

## Numbers

| Fact | Takeaway | Source |
|---|---|---|
| Parameter counts, 8B / 70B / 405B | Match the published sizes within 1% | Derived from Table 3 |
| Forward FLOPs per token | About 2 per parameter | 2N, Kaplan |
| Weights in BF16 | About 2 bytes per parameter | Derived |
| Training cost per token | About three times the forward pass | Kaplan |
| KV cache | Fixed bytes per token, grows with prompt | Derived |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| More layers | More depth to compute | Cost grows in proportion | Reasoning-heavy tasks |
| Wider d_model | Bigger matrices | Parameters grow with d² | Quality has to scale |
| Fewer KV heads (GQA) | Smaller KV cache and fewer key and value weights | Slight quality risk | Long contexts, many users |
| Bigger vocabulary | Fewer tokens per text | Larger tables | Multilingual use |
| Bigger model | Higher quality | About 2N FLOPs per token and N × 2 bytes of memory | Hard tasks that a small model fails |

## Interview lens

<Callout type="tip">
Say the cost the way a systems person does: "A 70B model costs about 140 GFLOPs per token and needs about 140 GB for the weights in BF16, so it needs several GPUs." Then name the rule: 2 FLOPs per parameter, 2 bytes per parameter.
</Callout>

<Callout type="mistake">
Do not say a model "has billions of lines of logic". It has a few matrix shapes repeated per layer. Do not forget that FLOPs and memory are separate limits. Do not say "bigger model, slower by the same factor" without saying which limit you mean. The limits are compute for long prompts and memory for generating one token at a time (the [Prefill vs Decode: TTFT and TPOT](/learn/ai/a2-inference-cost/prefill-decode/) lesson).
</Callout>

<Callout type="deep" title="Why the 2N rule is an estimate">
The count skips the normalization weights, which are tiny. It treats embeddings as a lookup. It skips the attention-score math, which grows with context length and is the topic of the next lesson. For a first estimate, 2N is within a few percent at short context. State it as "about 2N".
</Callout>
