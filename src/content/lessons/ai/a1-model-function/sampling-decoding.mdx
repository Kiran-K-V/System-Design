## The problem

You send the same prompt twice. You get two different answers. Or you send a classification prompt 1,000 times and the label flips on a few of them. Your test suite is flaky and nobody changed the code.

The cause is in the last step of the model, not the first. The forward pass ([the Transformer Forward Pass lesson](/learn/ai/a1-model-function/forward-pass/)) ends with one score per token in the vocabulary. A vocabulary is the full list of tokens the model knows. GPT-2 has 50,257 of them. Llama 3 has 128K. The model has not chosen a word yet. It has produced a long list of scores.

**Decoding** is the loop that turns those scores into text. It picks one token, appends it to the input, runs the model again, and repeats. [The Probabilistic Components lesson](/learn/ai/a0-orientation/probabilistic-components/) said a model is not a function that always returns the same output. This lesson shows where the randomness comes from, how to control it, and where the control stops working.

## Naive solution: always take the top token

The simplest rule is **greedy decoding**: pick the token with the highest score each time. It is a lookup with no random number in it. It sounds safe, and it fails in two ways.

First, the text is poor. The nucleus sampling paper (Holtzman et al., 2020) found that text from likelihood-maximizing decoding is "bland and strangely repetitive". Beam search, a smarter search that keeps several candidate sentences, did no better. With beam size 32 the model got "stuck in a repetition loop it cannot escape".

Second, greedy is not as deterministic as it looks. Later in this lesson we show a real experiment where 1,000 greedy runs gave 80 different texts.

## From scores to a token

The scores the model outputs are called **logits**. A logit can be any real number. To get probabilities, apply the **softmax** function with a **temperature** T:

<Math block tex="p_i = \frac{e^{x_i / T}}{\sum_j e^{x_j / T}}" />

In words: divide every score by T. Raise e to that power. Then divide by the total, so everything sums to 1. At T = 1 this is the plain softmax. A small T makes the top token win by more. A large T flattens the list. As T goes to 0 the result is greedy decoding, and most APIs treat T = 0 as exactly that.

Two more tools cut the tail of the list. Long tails matter: with a 128K vocabulary, thousands of tokens are each unlikely, but together they hold real mass, and sampling from all of them sometimes picks nonsense.

- **Top-k** keeps only the k most likely tokens. Holtzman et al. note that a fixed k is "sub-optimal across varying contexts": 40 candidates is too many when one token is obvious and too few when many fit.
- **Top-p**, also called **nucleus sampling**, keeps the smallest set of tokens whose probabilities add up to at least p. The set grows and shrinks with the model's confidence. Their paper uses p = 0.95.

After each cut, the kept probabilities are scaled so they sum to 1 again. Then the sampler draws one token.

Here is an example with ten illustrative scores for the next token after "The capital of France is". At T = 1, softmax gives Paris most of the probability (about 3 in 4), "the" and "a" a few percent each, and a small tail. A top-k cut of 3 drops the tail, so Paris gains share. A top-p cut of 0.9 keeps the few tokens that together cover 90% of the mass.

1. **Temperature changes shape, not order.** The ranking of tokens never changes. Low T makes Paris almost certain. High T flattens the distribution and the tail wakes up.
2. **Steps run in order.** Temperature, then top-k, then top-p. Libraries differ in the exact order and in tie handling, so read the docs of the one you use.

Now watch decoding run. The sampler needs one random number per token. It lines up the probabilities as a strip from 0 to 1 and picks the token whose segment holds the number.

## Temperature 0 is not deterministic

Set T = 0 and you expect the same output every time. In production it often is not. Thinking Machines tested this ("Defeating Nondeterminism in LLM Inference"). They asked Qwen3-235B-A22B at temperature 0 the same question, "Tell me about Richard Feynman", 1,000 times, with 1,000 tokens each.

- They got **80 unique completions**. The most common one appeared 78 times.
- The first 102 tokens were identical in all runs. At token 103, 992 runs wrote "Queens, New York" and 8 wrote "New York City". After that the texts went apart.
- With batch-invariant kernels turned on, all 1,000 completions were identical.

Why does a fixed model with no random number give different text? The reason is in how computers add numbers. **Floating-point** addition is not associative: the order of the additions changes the result. Here is a case in 32-bit floats. Add 1 to 100,000,000 first, then subtract 100,000,000: the 1 is lost to rounding, and the answer is 0. Subtract first, then add 1: the answer is 1. Same three numbers, two answers.

A GPU adds up thousands of numbers inside every matrix multiply. How it splits that work depends on the shape of the input. The shape depends on the **batch**. A batch is the group of requests the server runs together to keep the GPU busy. Your request shares a batch with other users' requests (the [Batching and Throughput](/learn/ai/a2-inference-cost/batching-throughput/) lesson covers batching in detail). So the order of additions depends on how many other people are on the server right now. The last bits of every score depend on that too. As the paper puts it, "the load (and thus batch-size) nondeterministically varies".

Most of the time the last bits do not matter. But at some token the top two scores are almost tied. A change in the 7th digit flips which one wins. Once one token differs, every token after it can differ. This is a backend idea you know: a result that depends on the **hidden state of a shared system**, like a cache hit that changes a timing, but here it changes the output.

The fix exists. Batch-invariant kernels compute each request the same way regardless of batch size. It costs speed. The paper tested Qwen-3-8B on one GPU. The first deterministic version was about twice as slow as default vLLM. An improved attention kernel closed part of the gap, but it stayed slower.

<Callout type="deep" title="Seed, temperature 0, and what you can promise">
A seed fixes the random number u. It does not fix the scores that go into the strip. If the scores move by a tiny amount, the same u can land on a different token. So "temperature 0" and "seed = 42" are both **best effort** on a shared hosted model. The exception is when the provider documents a stronger guarantee. Check the provider's docs. Do not build a system that fails if two calls differ. Build one that checks the output (see below) and treats a rare difference as normal.
</Callout>

## Numbers

| Choice | What it does | Typical use |
|---|---|---|
| T = 0 (greedy) | Always the top token, up to the numeric noise above | Classification, extraction, tool calls |
| T around 0.7 to 1 | Draws from the full distribution | Chat, brainstorming |
| Top-p 0.95 | Cuts the unlikely tail (Holtzman's setting) | Open-ended text |
| Repetition penalty about 1.2 | Divides the score of tokens already used | Stops loops. The CTRL paper reports 1.2 as a good balance |
| Constrained decoding | Sets the probability of tokens that break a format to zero before the draw | JSON, a fixed label set |

Cost: sampling is cheap. The forward pass of a large model does billions of operations per token. Sampling over the vocabulary is several orders of magnitude smaller (our derived estimate). Nobody picks greedy to save compute.

## Trade-offs

| Setting | You gain | You pay | Choose it when |
|---|---|---|---|
| Greedy or T = 0 | Fewer different outputs, easier tests | Repetitive text, still not exact | One right answer exists |
| Higher T | Varied, natural text | More wrong or odd tokens, flaky tests | Variety is the product |
| Top-p / top-k | Fewer nonsense tokens | A little less variety | Any sampling with a long tail |
| Batch-invariant kernels | Bit-exact repeat runs | About 1.6x time in the paper's best case | Evals, debugging, audits |
| Output check and retry | Catches the rare flip | One extra call on failures | Any pipeline that needs a valid label |

## Interview lens

<Callout type="tip">
Say what you set, and why: "Temperature 0 and a fixed label set for the classifier, plus a validator that rejects anything outside the set and retries once. I measure the label flip rate on a golden set of 500 tickets. I expect the rate to be low, not zero." That answer names a setting, a check, and a rate.
</Callout>

<Callout type="mistake">
Do not say "temperature 0 makes it deterministic". It removes the deliberate randomness only. On a shared server, batch size can still change the numbers. Also do not use a high temperature to "make the model more creative" on a task with one right answer.
</Callout>
