## The problem

A support bot tells a customer: "You can return a laptop within 30 days." The real policy is 14 days. The customer reads the reply, trusts it, and files a complaint on day 20. Nothing crashed. No error was logged. The reply was well written and sounded sure.

This is a **hallucination**: a fluent answer that is not true, or not supported by the source. For a backend engineer, the closest picture is a cache. On a miss, it returns a plausible-looking value instead of a miss. There is no "not found" path in the model, unless you build one.

Two questions follow. Why does the model do this? And if the fix is to give it the facts, how many facts can you give it? Where do you put them? The first question is about training. The second is about the **context window**. It is the maximum number of tokens the model can read at once, counting the prompt and the reply.

## Why a model guesses

A language model is trained on one task. Given text so far, it produces a likely next token. The lesson [A1.5](/learn/ai/a1-model-function/sampling-decoding/) showed how the next token is drawn. The training text has facts in it, and the model stores some. A fact it saw once or twice is stored weakly. A fact it never saw is not stored at all.

When the model needs such a fact, it has no "I do not know" signal built in. It has a probability list, and it picks from it. The walk below uses made-up probabilities for a made-up shop. It shows what the list looks like when the fact is missing. The example also shows what happens when the fact is in the prompt.

OpenAI researchers explain the cause in "Why Language Models Hallucinate" (Kalai et al., 2025). Two parts matter to us.

1. **Pretraining makes some errors unavoidable.** The paper says hallucinations "originate simply as errors in binary classification". Telling a valid statement from an invalid one is hard. It gives a lower bound. If 20% of birthday facts appear exactly once in the training data, the model should hallucinate. This happens on at least about 20% of birthday questions after pretraining. A fact seen once cannot be told from a lucky guess.
2. **Tests reward guessing.** The paper says "language models are optimized to be good test-takers, and guessing when uncertain improves test performance". Most benchmarks give 1 point for a right answer and 0 for a wrong one. They also give 0 for "I do not know". So "IDK-type responses are maximally penalized while an overconfident 'best guess' is optimal". If a model is 30% sure of an answer, a guess scores 0.3 points on average. The phrase "I do not know" scores 0. A model trained and ranked on such tests learns to guess.

The paper gives a real example. A model (DeepSeek-V3) was asked for a person's birthday and told to answer only if it knew. In three attempts it gave three different dates: "03-07", "15-06", and "01-01". All were wrong.

The paper also notes that a model after pretraining can be well calibrated. Well calibrated means its confidence matches how often it is right. In its Figure 2 caption, "The pretrained model is well calibrated". Post-training changes that.

The practical lesson: you cannot count on the model to say "I do not know". You must design the "not found" path yourself. The standard way is to put the facts in the prompt and require the model to quote them. That is retrieval, which module A5 covers. For now, think of it as turning a memory test into an open-book test.

## What the window holds

An open-book test only works if the book fits. Context windows have grown fast. Here are the current flagship numbers, read from the providers' own model pages on 2026-10-15.

| Provider | Models (as shown on the page) | Context window | Max output |
|---|---|---|---|
| Anthropic | Claude Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5 | 1M tokens | 128K |
| OpenAI | GPT-6 Astra, GPT-6.1 Sol, GPT-6 Luna | 1.05M tokens | 128K |
| Google | Gemini 4 Argon | 1M tokens, shared by input, thinking, and output | up to 1M (long decode) |

Sources, as of 2026-10-15: [Anthropic models overview](https://platform.claude.com/docs/en/models/overview), [OpenAI models](https://developers.openai.com/api/docs/models), [Gemini models](https://ai.google.dev/gemini-api/docs/models) and [Gemini long context](https://ai.google.dev/gemini-api/docs/long-context). Model names and sizes change often, so check the page before you design around a number.

Anthropic's page says 1M tokens is roughly 555,000 words on the current tokenizer. That is several novels. So the window is no longer the limit for most documents. Cost is. A full 1M-token prompt to Claude Sonnet 5.5 costs $2.00 in input alone. That is 1 million tokens at $2 per million input tokens, from the same page, as of 2026-10-15. You pay it on every call unless you cache. The Gemini docs make the same point. They say "you have to pay the input token cost every time you send that query."

## Naive solution: put everything in the window

If 1M tokens fit, why not paste the whole wiki into every prompt? Because accuracy drops with more text, and it drops unevenly.

**Lost in the Middle** (Liu et al., 2023) tested multi-document question answering. The prompt held 10, 20, or 30 documents, and exactly one held the answer. The authors moved the answer document to different positions. Accuracy was highest at the start, lower at the end, and lowest in the middle: a U-shaped curve. The abstract says performance "significantly degrades when models must access relevant information in the middle of long contexts". The chart uses real numbers from the paper's Appendix G tables. The paper reports only some positions, so the chart shows only those.

<Ai1HallCurve client:visible />

Read the numbers for GPT-3.5-Turbo (16K) with 30 documents. Answer first: 73.4%. Answer at index 9: 50.5%. That is a drop of 22.9 points. And the closed-book score, with no documents at all, was 56.0%. So with the answer buried in the middle, the extra documents made the model worse than no documents. Switch to Claude-1.3: the dip is smaller (59.1% first, 54.8% at index 9), but it is there. These are 2023 models. Current models are better, but the shape of the problem is still documented.

Two newer results point the same way.

- **Needle in a haystack** hides one fact (the needle) at a chosen depth in a long text. The test then asks for that fact back. The Gemini docs report about 99% recall for a single needle. They also warn that with several needles "the model does not perform with the same accuracy".
- **Context rot** (Chroma, 2025-07-14) tested 18 LLMs and found their performance "grows increasingly unreliable as input length grows". The text gives no per-model numbers, only charts.

So there are two costs of a long prompt. They are dollars, and a quality loss that you must measure on your own task. The attention cost of long prompts (lesson [A1.4](/learn/ai/a1-model-function/attention-cost/)) adds latency on top.

## Design rules that follow

1. **Retrieve, do not dump.** Send the few passages that matter, not the whole corpus.
2. **Put the key facts first or last.** The U-curve says the ends are safest.
3. **Require quotes.** Ask the model to copy the sentence it relies on. A cheap string check then confirms that the quote appears in the source. If it does not, reject the answer.
4. **Make "I do not know" an allowed answer.** Say so in the prompt, and test that the bot uses it when the source is missing.
5. **Measure.** Build a test set of questions with known sources and some with none. Track how often the bot invents an answer.

| Option | You gain | You pay | Choose it when |
|---|---|---|---|
| Rely on model memory | No extra pipeline | Silent wrong answers on rare facts | Common knowledge only |
| Retrieval plus quote check | Grounded, checkable answers | A retrieval system to build and run | Facts that change or are private |
| Whole corpus in the window | Simple code | Input cost on every call, and the middle gets lost | Small corpus, low traffic |
| Fine-tuning on the facts | Style and format control | Slow to update, and facts are still stored weakly | A behavior fails, not a missing fact |

## Interview lens

<Callout type="tip">
Name the failure rate, not only the failure. "On my golden set of 300 questions, 60 have no answer in the docs. The bot should refuse on those. I track the fabrication rate on those 60 and the unsupported-quote rate on the other 240." Then name the fix: retrieval, a quote check, and a refusal path.
</Callout>

<Callout type="mistake">
Do not say "a bigger context window removes hallucination". The window removes the retrieval step, not the guessing. If the fact is not in the prompt, the model can still invent an answer. The model can do the same when the fact sits in the middle of 500K tokens. Also do not propose fine-tuning to teach a changing policy. A fact seen a few times is stored weakly, and you must retrain to update it.
</Callout>
