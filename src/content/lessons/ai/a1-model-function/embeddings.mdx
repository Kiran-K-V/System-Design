## The problem

Lesson [A1.1](/learn/ai/a1-model-function/tokens/) ended with integers. The word "cat" might be id 8415 and "kitten" id 52,017. Those numbers are arbitrary: the tokenizer assigned them in the order it learned merges. Id 8415 is not "close" to 8416 in meaning. A model that does arithmetic on ids learns nothing.

We need a representation where **meaning becomes distance**. Two tokens used in similar ways should be near each other, and arithmetic on them should make sense.

## Naive solution: one-hot vectors

The simplest vector for token 791 is 128,000 zeros with a 1 in position 791. This is a **one-hot** [junior] vector. It has two problems.

- It is huge and almost empty. 128,000 numbers to say one thing.
- Every pair of tokens is equally far apart. "Cat" is as far from "kitten" as from "invoice". Distance carries no meaning.

## The mechanism: a learned lookup table

An **embedding** [mid] is a dense vector of a few thousand numbers that stands for one token. The model keeps a table with one row per vocabulary token. Llama 3 8B has 128,000 rows and 4,096 columns (the model width, called d_model). The id is the row index.

A backend engineer already knows this structure: it is `table[id]`. The read is O(1). No matrix multiply happens. Step through the lookup and the size math.

<Ai1EmbedLookup client:visible />

The size is worth memorizing. 128,000 × 4,096 = 524,288,000 numbers. In BF16 (2 bytes each) that is about 1.05 GB. This table is part of the weights: it is loaded to the GPU like every other matrix.

The rows are **learned**. At the start of training they are random. Training adjusts every row that appears in a batch, so tokens that appear in similar contexts drift toward similar vectors. The model builds its own coordinate system for meaning. Word2vec showed this early: its paper reports that the vector for "King" minus "Man" plus "Woman" is closest to "Queen".

### Two different uses

The table inside a language model is one use. The other is an **embedding model**: a separate model that reads a whole text and returns one vector for it. You call it through an API to search, cluster, or deduplicate text. OpenAI documents two such models. `text-embedding-3-small` returns 1,536 numbers. `text-embedding-3-large` returns 3,072. Max input is 8,192 tokens. Their vectors are normalized to length 1, and a `dimensions` parameter shortens them. Shortening works because of an idea called Matryoshka representation learning. The first numbers carry the coarse meaning. As a result, a prefix still works. The authors of that paper report up to 14x smaller embeddings at the same accuracy on ImageNet-1K. Test the loss on your own data before you cut.

## Cosine similarity: distance as an angle

To compare two vectors you need a measure. The common one is **cosine similarity** [mid]: the cosine of the angle between the two vectors.

<Math block tex="\cos(a, b) = \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert}" />

In words: take the dot product, then divide by both lengths. The result is 1 when the vectors point the same way. It is 0 when they are at a right angle. It is −1 when they are opposite. Length drops out. If both vectors have length 1, the denominator is 1, so cosine equals the dot product. That is why OpenAI normalizes: the cheap dot product gives the cosine.

Try it in 2D. The real vectors have thousands of dimensions, but the angle works the same. The points are illustrative, placed by hand. Click two phrases. Stretch one vector and watch which numbers move.

<Ai1EmbedCosine client:visible />

Work one example. Take a = (3, 4) and b = (4, 3). The dot product is 12 + 12 = 24. Both lengths are 5. Cosine = 24 / 25 = 0.96, an angle of about 16°.

## Why a vector at all

Arithmetic works on it. You can add, average, and compare vectors. Sentence-BERT shows why this matters for systems. Finding the closest pair among 10,000 sentences with a cross-encoder needs about 50 million model runs. That work takes around 65 hours with BERT. With embeddings, each sentence is encoded once and then compared with cosine similarity: about 5 seconds. You trade some precision for a huge drop in work.

## Where closeness lies

Embedding distance measures how similar texts look to the model, not whether they agree. In the playground, "refund my order" and "do not refund me" sit at nearly the same angle. That placement is illustrative, but the failure is real. Opposite statements about the same topic often land close. Unrelated texts that share surface words also land close. We have no sourced rate for it. So never trust a similarity score alone. Set a threshold on your own data. Check retrieval quality with an eval (module A5). Let a second step (a reranker or the model itself) read the candidates.

## Numbers

Storage is bytes per number times dimensions times count.

| Dimensions | Bytes per vector (float32) | 10M vectors |
|---|---|---|
| 256 | 1,024 | 10.2 GB |
| 768 | 3,072 | 30.7 GB |
| 1,536 | 6,144 | 61.4 GB |
| 3,072 | 12,288 | 122.9 GB |

All values are derived: dims × 4 bytes, then × 10,000,000. An index such as HNSW adds overhead on top. Float16 halves each row. Shortening dimensions cuts it in proportion.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| More dimensions | Finer detail in meaning | Storage and search cost grow in proportion | Hard, nuanced retrieval |
| Fewer dimensions (Matryoshka) | Smaller index, faster search | Some quality loss, measured per task | Large corpora, tight memory |
| Normalized vectors | Cosine equals dot product, fast | Length information is gone | Almost all search |
| Embeddings only | One cheap step | Negation and facts slip through | First-stage candidate search |
| Embeddings plus rerank | Better top results | Extra latency and cost per query | Answer quality matters more than speed |

## Interview lens

<Callout type="tip">
Give the size with the idea. "Each chunk is a 1,536-dimension vector, 6 KB in float32. So 10M chunks is about 61 GB before the index. I would store float16 or shorten the vectors if memory is tight." Then say how you check retrieval quality.
</Callout>

<Callout type="mistake">
Do not say "embeddings understand meaning" and stop there. They place texts by learned similarity, which can put opposites close. Do not compare vectors from two different embedding models. Each model has its own coordinate system. So distances across models mean nothing.
</Callout>
