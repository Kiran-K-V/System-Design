## The problem

Your index does not store documents. It stores **chunks**: pieces of documents, each with one vector. A search returns chunks, and the model answers from the chunks it gets. The chunk is the unit of retrieval.

That makes chunking a quality decision, not a detail. Make chunks too big and each vector blurs many topics. So the search is noisy, and you pay to send extra text to the model. Make them too small and a chunk loses the facts around it. A chunk that says "revenue grew 3% over the previous quarter" has no company and no year. No embedding model can find that chunk for the question "how much did ACME grow in Q2 2023?". The reason is that the words that matter are not in the chunk.

The [Choosing Embedding Models](/learn/ai/a5-rag/embedding-models/) lesson chose the embedding model. This lesson decides what text you give it.

## Naive solution: cut every N tokens

The first version most teams ship is a fixed-size splitter. Cut every 800 tokens, maybe with 400 tokens of overlap, and move on. It is easy and it is predictable. It also ignores the text. A cut can fall in the middle of a sentence, a table row or a rule that needs two paragraphs.

Step through four ways to cut one document, and then the second problem: a good cut can still lose the subject.

## Three ways to cut

**Fixed-size** chunking cuts every N tokens. It is fast and gives chunks of equal size, which keeps the index easy to size. It breaks structure.

**Recursive** chunking tries a list of separators from the largest to the smallest. The order is paragraph break, line break, sentence end, then space. It splits on the first one that makes pieces small enough. Structure survives when it can. This is the usual default in the common RAG toolkits, and it needs no model call.

**Semantic** chunking cuts where meaning changes. One method embeds each sentence and cuts where the distance between neighbours jumps. Another asks an LLM to choose the cuts. It finds better boundaries and costs a model pass before indexing.

**Overlap** repeats the end of one chunk at the start of the next. It protects text that a cut would split. Its price is storage and embedding cost for the repeated text, and duplicate hits in the results.

Add structure on top of any of these. Split Markdown on headings. Keep a table or a code block in one piece. Carry the heading path ("Billing > Refunds") with each chunk.

## What the measurements say

Chroma tested chunkers on a retrieval benchmark. They used OpenAI's text-embedding-3-large, retrieved the top 5 chunks, and measured recall, precision and IoU. IoU (intersection over union) [mid] is the share of the retrieved tokens that are also in the answer text. It drops when a chunker returns redundant or extra text.

| Chunker | Overlap | Mean chunk | Recall | IoU |
|---|---|---|---|---|
| LLM chunker (GPT-4o) | 0 | ~240 tokens | 91.9% | 3.9% |
| ClusterSemantic, size 400 | 0 | ~182 tokens | 91.3% | 4.5% |
| Token splitter, size 400 | 0 | 400 | 89.2% | 2.7% |
| Token splitter, size 400 | 200 | 400 | 88.6% | 2.7% |
| Recursive, size 200 | 0 | ~137 tokens | 88.1% | 6.9% |
| Token splitter, size 800 (OpenAI default) | 400 | 800 | 87.9% | 1.4% |
| Recursive, size 800 | 400 | ~661 tokens | 85.4% | 1.5% |

Source: [Chroma, "Evaluating Chunking"](https://www.trychroma.com/research/evaluating-chunking), read 2026-10-16.

Three things stand out. The spread is about 6.5 points of recall (85.4% to 91.9%). So chunking matters, but chunking is not the biggest lever. The smart cutters (LLM and cluster) lead on recall. And the default setting, 800 tokens with 400 overlap, is near the bottom on both recall and IoU. Chroma writes that "reducing chunk overlap improves IoU scores, as this metric penalizes redundant information". Dropping the 200-token overlap from the 400-token splitter moved recall by 0.6 points (88.6% to 89.2%). The same change left IoU at 2.7%.

Read this carefully. It is one benchmark, one embedding model and top 5. It does not say recursive-200 beats everything. It says test your own data, with your own queries, before you accept the default.

## The lost-subject problem

A well-cut chunk can still fail. Chunks are embedded one at a time, and each loses the document around it. The company name is in the title. The year is in the header. The chunk holds only the sentence.

**Contextual retrieval**, described by Anthropic, fixes this at index time. For each chunk, an LLM reads the whole document and the chunk. The LLM writes a short context that places the chunk in the document. Anthropic says this text is "usually 50-100 tokens". It is put in front of the chunk before the chunk is embedded and before it is added to the BM25 index (the keyword index from the [Hybrid Search and Reciprocal Rank Fusion](/learn/ai/a5-rag/hybrid-rrf/) lesson). Only the index changes. The text sent to the answering model can still be the plain chunk.

Anthropic measured the effect with the top-20 failure rate, which is 1 minus recall@20. That rate is the share of questions where no right chunk is in the top 20.

| Setup | Top-20 failure | Cut vs. baseline |
|---|---|---|
| Embeddings only | 5.7% | none |
| + contextual embeddings | 3.7% | 35% |
| + contextual BM25 | 2.9% | 49% |
| + reranking (the [Reranking and Query Rewriting](/learn/ai/a5-rag/reranking-rewriting/) lesson) | 1.9% | 67% |

Source: [Anthropic, "Introducing Contextual Retrieval"](https://www.anthropic.com/news/contextual-retrieval), read 2026-10-16. The post does not name its corpus in the text we read. So treat the percentages as one test on one data set. Your numbers will differ.

Read the table as a stack of fixes. Each stage removes a different kind of miss. Context repairs the lost subject, BM25 repairs exact terms, and the reranker repairs ordering. The full stack misses far fewer questions than embeddings alone.

## What the context step costs

The context step is an LLM call per chunk. A naive version resends the whole document with each chunk. A 10-chunk document would pay for itself 10 times. Prompt caching ([the Prompt Caching: Mechanics and Economics lesson](/learn/ai/a2-inference-cost/prompt-caching/)) removes that. You write the document into the cache once. Then each chunk's call reads it at a small fraction of the input price.

Anthropic reports that the one-time cost to generate contextualized chunks is small per million document tokens. Their assumptions were 800-token chunks and 8k-token documents. The cache write is paid once per document. The cache reads for the other chunks cost a small fraction of the input price. So the cost scales with how many documents you index, not with how many chunks each one has. Check current prices on [claude.com/pricing](https://claude.com/pricing).

Two things to remember. It is a one-time index cost, not a per-query cost. And it repeats whenever documents change, so a fast-changing corpus pays it again (the [Freshness and Index Updates](/learn/ai/a5-rag/freshness-updates/) lesson). Contextual chunks are also longer by 50 to 100 tokens, so the embedding bill grows a little.

Chunk count, repeated tokens and cost all move with size and overlap.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Fixed-size cuts | Simple, even chunks | Cuts through rules | A first version, or uniform logs |
| Recursive split | Keeps paragraphs, no model | Sizes vary a little | The default for prose |
| Semantic or LLM cuts | Best boundaries in Chroma's test | A model pass at index time | Dense, mixed documents worth the cost |
| Overlap | Protects split text | Repeated storage, duplicate hits | Fixed cuts you cannot change |
| Context prefix | Fewer lost-subject misses | An LLM call per chunk, longer chunks | Chunks lose entity, date or section |
| Smaller chunks | Precise hits, less noise | More vectors, less context per hit | Short factual answers |

## Interview lens

<Callout type="tip">
Say what you measure. "I would build a small gold set of real questions with the chunk that answers each one, then compare chunkers on recall@k and on tokens sent to the model. Then I would add a context prefix if the misses are lost-subject cases." That is a measured plan, not a default.
</Callout>

<Callout type="mistake">
Do not say "800 tokens with 400 overlap is the standard setting" as if it were proven. In Chroma's test that setting was near the bottom for recall and IoU. Also do not forget the cost of contextual retrieval. Contextual retrieval is one LLM call per chunk, and the call repeats when documents change.
</Callout>

<Callout type="deep" title="Late chunking and other ideas">
Another family embeds the whole document first and then pools token vectors into chunk vectors. So each chunk vector sees its surroundings. We did not load a source for this family here. So treat this family as a pointer to search for, not a result. The common idea is the same as the context prefix: a chunk vector should know where it came from.
</Callout>
