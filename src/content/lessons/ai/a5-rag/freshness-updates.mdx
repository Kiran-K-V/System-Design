## The problem

A support bot answers from your policy pages. On Monday at 09:00 legal changes the refund window from 30 days to 14. At 09:05 a customer asks about refunds. The bot says 30 days. The page is correct. The index is not.

A search index is a copy of your data. Every copy can go stale. In RAG the copy has two extra problems. The text was cut into chunks, so one edit touches several index entries. The entries are vectors, and making a vector costs a model call. So "keep the index fresh" means a small pipeline, a delete path, and a number you promise to meet.

## Naive solution: rebuild the index every night

A nightly job reads all documents, chunks them, embeds them, and writes a new index. It is simple and it works. It fails in three ways.

1. Staleness is up to 24 hours. A refund rule that changed at 09:00 is wrong until the next run.
2. The cost scales with the corpus, not with the change. If 0.1% of pages change per day, you pay for 100% of the embeddings.
3. Deletes are easy to miss. A job that only adds new chunks never removes the old ones.

The fix is to move only the change. Step through one edit.

## The mechanism: an incremental pipeline

The pipeline has five stages. Each one can fail on its own.

1. **Change event.** Do not poll the source table. Read its commit log and publish an event per change. The backend track covers this.

<CrossTrackLink id="06-async/cdc">Change data capture reads the database log and publishes each committed change as an event. The outbox pattern writes the event in the same transaction as the data, so a crash cannot lose one. Events can arrive twice or out of order, so consumers must be idempotent. Here the event says "document 881 changed to version 12".</CrossTrackLink>

2. **Re-chunk and diff.** Cut the new version into chunks. Hash each chunk. Compare with the stored hashes. Only changed chunks continue. Cursor's indexer works this way: it hashes every file into a Merkle tree. Each folder hash comes from its children. The indexer "walks only the branches where hashes differ". It also "caches embeddings by chunk content", so an unchanged chunk is never embedded again ([Cursor](https://cursor.com/blog/secure-codebase-indexing)).
3. **Embed.** Send the changed chunks to the embedding model, in batches.
4. **Upsert.** Write each new vector under a stable chunk id. Upsert means insert, or replace if the id exists. Retries then do no harm.
5. **Delete.** Remove chunks that no longer exist. If version 12 has 7 chunks and version 11 had 8, chunk 8 must go. This is the stage that gets forgotten.

Store the document id and version as fields on every chunk. Then "delete all chunks of document 881 older than version 12" is one filter. You do not depend on remembering chunk ids.

### What a delete does inside the index

A graph index such as HNSW (the [ANN Indexes and Billion-Scale Search](/learn/ai/a5-rag/ann-indexes/) lesson) links each vector to its neighbours. Removing a node means repairing every link that pointed to it, while queries run. That is slow and hard to do safely. So stores mark the point as deleted and skip it in results. The Qdrant docs say deleted points are "marked as deleted to avoid slow disk operations during queries" and keep using memory until a vacuum optimizer removes them ([Qdrant optimizer](https://qdrant.tech/documentation/ops-optimization/optimizer/)). The hnswlib library has the same shape. `mark_deleted` "marks the element as deleted, so it will be omitted from search results". An option lets new items take the place of deleted ones ([hnswlib](https://github.com/nmslib/hnswlib)). Updating a vector under an existing label works, but the README says it is slower than inserting a new one.

What this means for you:

- A deleted chunk disappears from results at once. Disk and memory come back later.
- Heavy churn builds up tombstones. Memory grows and search does extra work until compaction runs.
- Vacuum starts by a rule. In its sample config Qdrant shows `deleted_threshold: 0.2` and `vacuum_min_vector_number: 1000`. The page does not call these defaults, so treat them as example values and check your version.
- Some stores put new writes in a log first. In turbopuffer, each namespace commits one log entry per second. Data not yet indexed is still searched exhaustively ([turbopuffer](https://turbopuffer.com/docs/architecture)). So a write can wait up to about a second before it is visible.

### Re-embedding when the model changes

Vectors from two models live in different spaces. You cannot compare them. A model change means a full re-embed, as in the [Choosing Embedding Models](/learn/ai/a5-rag/embedding-models/) lesson. Do it with a **versioned index**: build `docs_v2` beside `docs_v1`. Keep writing every change to both indexes. Check quality on your golden set. Then switch the alias that queries use from v1 to v2 (a blue/green swap). Keep v1 for a short time so you can switch back. The rebuild competes with live updates for embedding capacity, so give it its own quota.

## Numbers: a staleness SLO

A **freshness SLO** is a promise such as "99% of edits are searchable within 60 seconds." Measure it end to end. Put a timestamp on each change event at the source. When the chunk becomes searchable, record the difference. Report the 99th percentile, not the mean. A mean hides the burst that makes users complain.

The model is simple. A quiet change waits for the CDC delay, its own embedding time, and the commit delay. A burst waits for the queue to drain at the spare capacity. All inputs are your assumptions. In quiet times the delay is short. A burst of changes must drain through the spare capacity, which is the capacity minus the steady traffic, so it takes much longer. A full re-embed of a large corpus takes days at the same speed.

## Trade-offs

| Choice | Gain | Pay | Choose when |
|---|---|---|---|
| Nightly rebuild | Simple, no delete bugs | Hours of staleness, full cost | Content changes slowly |
| CDC pipeline with upsert | Seconds of staleness, pay per change | Queue, ordering, delete path | Content changes during the day |
| Write-through (embed in the request) | Fresh at once | Slow writes, failures reach the user | Small corpus, low write rate |
| Versioned index and swap | Safe model change, easy rollback | Double storage during the swap | Any model or chunking change |

<Callout type="tip">
In an interview, name the freshness SLO first. Then draw CDC, queue, embed, upsert, and say that delete is its own stage. Say that you tag chunks with document id and version, so deletes and re-embeds are filters.
</Callout>

<Callout type="mistake">
Do not say "we update the vector when the document changes" and stop. Say what happens to the old chunks. Do not forget that deletes are tombstones, so memory does not drop at once. Do not rebuild the full index in place when the embedding model changes.
</Callout>

<Callout type="deep" title="A stale index can also be a worse index">
Some index types learn from the data. An IVF index picks cluster centres from the vectors it saw at build time. After heavy changes, the new vectors may sit far from those centres. So recall can drop, even though every document is present. This is a reasoned effect, not a measured one here. If you use such an index, schedule a rebuild and watch recall on your golden set.
</Callout>
