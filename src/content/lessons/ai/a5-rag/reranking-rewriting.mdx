## The problem

Hybrid search (the [Hybrid Search and Reciprocal Rank Fusion](/learn/ai/a5-rag/hybrid-rrf/) lesson) returns a list in which the right chunk is somewhere. It is often not first. Suppose it is at position 31 of 50. If you send the top 5 chunks to the model, the model never sees it. If you send all 50, you pay for 10 times the input tokens. The model must find one useful chunk among 49 distractors. The [Why Models Hallucinate, and the Context Window](/learn/ai/a1-model-function/hallucination-context/) lesson showed how models lose facts in long inputs.

Two fixes exist, and they attack different ends. One improves the **order** of the candidates after retrieval. The other improves the **query** before retrieval.

## Why the first-stage search is only approximate

A **bi-encoder** [mid] embeds the query and each chunk separately. The chunk vectors are computed once, offline, and stored. At query time you embed only the query and compare. This is what makes search over millions of chunks fast.

It is also a limit. The chunk vector was fixed before the query existed. It must carry everything about the chunk that any future query could need, in one vector. The vector and the query never meet inside the model.

A **cross-encoder** [senior] reads the query and one chunk together as a single input. Its attention can compare every query word to every chunk word. It outputs one relevance score. It is more precise because it sees the pair. It cannot precompute anything. The reason is that the input includes the query. So each new query needs a fresh forward pass for every chunk you want to score. For a corpus of a million chunks that is a million passes per query. So it is used only on a short list.

**Late interaction** [senior], as in ColBERT, sits between them. It encodes the query and chunk separately, like a bi-encoder, but keeps one vector per token, not one per chunk. Scoring compares the query token vectors with the chunk token vectors. Chunk token vectors can still be computed offline. The ColBERT abstract reports that it stays competitive with BERT-based rerankers while running about a hundred times faster ([ColBERT](https://arxiv.org/abs/2004.12832)). The price is storage: one vector per token, not one per chunk. The ColBERTv2 abstract says it cuts the space of late-interaction models by 6 to 10 times. We cite these as the papers state them and do not give scores.

| | Bi-encoder | Late interaction | Cross-encoder |
|---|---|---|---|
| Query and chunk meet | Never, only by vector distance | At token level, after encoding | Inside the model, together |
| Precompute chunks | Yes, one vector | Yes, many vectors | No |
| Cost per query | Lowest | Middle | Highest, per pair |
| Best use | Stage 1 over the corpus | Stage 1 or 2 when you can store it | Stage 2 over a short list |

## The cascade

Put the cheap one first and the exact one second. Retrieve 50 chunks with dense plus BM25 plus RRF. Rerank those 50 with a cross-encoder. Send the top 5 to the LLM. Step through it, and the query-side fix first, because a bad query poisons both stages.

If you know recommender systems: this is the same two-stage shape, a cheap candidate generator and then a heavier ranker. The classic version is elective [Two-Tower Retrieval and the Ranking Cascade](/learn/ai/e1-classic-ml/retrieval-ranking/), so we do not teach it here. The sbert docs describe the same pattern for text. A retriever returns, for example, 100 hits. A re-ranker scores them and shows the top 5 ([sbert: retrieve and re-rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)).

Anthropic's contextual retrieval test (the [Chunking and Contextual Retrieval](/learn/ai/a5-rag/chunking-contextual/) lesson) put numbers on one stack. Adding a reranker took the top-20 failure rate from 2.9% to 1.9% ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). That is one test. It shows the direction, not a promise.

## What the reranker costs

Reranking adds a step to the latency path and a line to the bill.

**Latency.** You score N pairs. Time is about N times the time per pair, divided by how many pairs the hardware scores at once. We found no published per-pair latency, so this lesson uses an **illustrative** value. Measure your own reranker. Rerank time also grows with chunk length, since the model reads the query and the chunk together. Hosted rerankers cap the input: check the limit of the model you use.

**Cost.** A hosted reranker bills by tokens. Voyage lists rerank-3 at $0.05 per 1M tokens and rerank-3-lite at $0.02 (as of 2026-10-16, [docs.voyageai.com](https://docs.voyageai.com/docs/pricing)). We assume billing counts the document tokens of every candidate. At these prices, reranking 50 candidates costs a fraction of a cent per query.

Now the saving. If the LLM reads 5 chunks instead of 50, its input is ten times smaller. An LLM input token costs far more than a reranker token. So the reranker costs much less than the LLM input it removes. Reranking often pays for itself on the model bill alone, and it can improve the answer.

## Fixing the query

A reranker repairs order. It cannot repair a query that never retrieved the right chunk. These four tools work on the query.

**Query rewriting.** A small LLM rewrites the user's text into a better search query. The common case is a chat follow-up ("and for annual plans?") that needs the earlier turns to make sense. The Rewrite-Retrieve-Read paper adds a small rewriter tuned with feedback from a frozen LLM reader. Its abstract reports consistent improvements and gives no effect size in the part we read ([arXiv 2305.14283](https://arxiv.org/abs/2305.14283)). Cost: one short LLM call before every search.

**HyDE** (hypothetical document embeddings). An LLM writes a made-up answer to the query. You embed that answer and search with it. The idea is that an answer looks more like a chunk than a question does. The HyDE paper reports it beats the unsupervised Contriever retriever and comes close to fine-tuned retrievers, and it warns that the made-up document can hold false details ([arXiv 2212.10496](https://arxiv.org/abs/2212.10496)). The fake answer is only a search key, never shown to the user. But a false detail can pull the search toward the wrong chunks. We give no effect sizes: the abstracts do not give any.

**Multi-query.** The LLM writes 3 or 4 variants of the query. You search each and merge the lists with RRF, as in the [Hybrid Search and Reciprocal Rank Fusion](/learn/ai/a5-rag/hybrid-rrf/) lesson. It improves recall for vague questions and multiplies the number of searches.

**Query decomposition.** A question with parts ("Compare the refund rules for plan A and plan B") is split into sub-questions. Each is retrieved on its own, and the answers are combined. Without it, the top-k list fills with chunks about whichever part matches best, and the other part is missing.

| Tool | Fixes | Costs | Risk |
|---|---|---|---|
| Rewrite | Follow-ups, typos, missing topic | One small LLM call | A bad rewrite loses the user's intent |
| HyDE | Short or vague questions | One LLM call, one embed | False details steer the search |
| Multi-query | Vague, many-phrasing questions | N searches | More noise to filter |
| Decomposition | Questions with several parts | Several searches and calls | Latency, and a merge step |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| No reranker | Lowest latency and cost | Right chunk often out of top-k | Easy queries, tight latency |
| Cross-encoder rerank | Better order, shorter LLM prompt | Latency, a model, a bill | Answer quality limits the product |
| Larger N | More recall before the cut | Linear rerank time and cost | The right chunk is often deep |
| Late interaction | Between the two in cost | Heavy index storage | You can afford token vectors |
| Query rewriting | Fixes chat follow-ups | A call before search | Multi-turn products |

## Interview lens

<Callout type="tip">
Describe the funnel with budgets: "Stage 1 retrieves 50 with hybrid search. A cross-encoder reranks them and I send 5 to the LLM. The reranker adds N times the per-pair latency but cuts LLM input by 10 times." Then say how you would measure it: recall@50 for stage 1, recall@5 after the rerank.
</Callout>

<Callout type="mistake">
Do not put a cross-encoder over the whole corpus. Do not quote a latency or quality gain you did not measure. And do not add HyDE or rewriting by default: each adds an LLM call and a way to be wrong. Add them when you can show the failure they fix.
</Callout>
