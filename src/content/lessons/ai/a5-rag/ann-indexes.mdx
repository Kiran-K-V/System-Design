## The problem

Lesson [A5.1](/learn/ai/a5-rag/embedding-models/) priced one embedding: 6,144 bytes at 1,536 dimensions. Now scale it. A company that indexes every paragraph of its documents, tickets and code can reach a billion vectors. That is about 6 TB for a billion vectors. The FAISS guide says that "all Faiss indexes are stored in RAM." A machine with 6 TB of memory is not a normal machine. Every query would still read all of that memory.

So the question changes from "which vectors are close?" to "how do we find them without holding or scanning everything?"

<CrossTrackLink id="10-advanced/vector-databases">
Exact search compares the query with every stored vector, which costs N x d work. Approximate search (ANN) trades a little recall for a large cut in work. IVF groups vectors into clusters and scans only the nearest few. HNSW is a layered graph that a query walks greedily from the top. pgvector filters after the scan. This lesson does not repeat the walk-through. It adds the memory math, the knobs, and the billion-scale options.
</CrossTrackLink>

## Naive solution: one flat index

A **flat** index stores every vector as it is and compares the query to all of them. The FAISS wiki gives its memory as 4 x d bytes per vector. It has perfect recall. It also has no tuning, and it is the right answer up to a modest size (backend lesson 10.4 gives about 100,000 vectors as a rough line).

At a billion vectors, a flat index needs terabytes of RAM, and each query reads all of it. A full pass takes minutes. That is the cost to beat.

## The mechanism: four ways to cut

Each family cuts a different cost. The FAISS wiki lists bytes per vector for the first three.

| Index | Bytes per vector | What it cuts |
|---|---|---|
| Flat | 4 x d | Nothing. Exact. |
| IVFFlat | 4 x d + 8 | Work per query. The 8 bytes store the id. |
| PQ | ceil(M x nbits / 8) | Memory. Each vector becomes a short code. |
| HNSW | 4 x d + M x 2 x 4 | Work per query. Adds graph links to the vectors. |

**IVF** scans only a few clusters. It saves time but not memory: it still stores the full vectors. **PQ** (product quantization) [senior] cuts each vector into M pieces. Each piece gets replaced by the id of its nearest entry in a small learned table. PQ stores only those ids. With 96 pieces of 8 bits each, a vector becomes a code of about 100 bytes, a small fraction of the original. The FAISS wiki allows nbits of 8, 12 or 16. The price is lost precision: distances from codes are estimates. **HNSW** is fast and accurate, but it keeps full vectors and adds links on top.

### Worked example: a billion vectors

Flat, IVFFlat and HNSW all keep the full float vectors, so they sit near the same terabytes of memory. HNSW adds a little for its links. Only PQ changes the order of magnitude: its codes are many times smaller, and fit on one large server. But those codes are only part of the cost. You also keep the codebooks, and usually the full vectors on cheaper storage. That way you can re-score the best few hundred candidates. Try other values in the calculator.

### DiskANN: keep the graph on the SSD

HNSW needs the whole graph and all vectors in RAM. **DiskANN** [senior] (NeurIPS 2019) keeps most of the index on an SSD and a compressed copy in memory. The abstract reports one workstation with modest RAM and an inexpensive SSD. That workstation can index and search SIFT1B, a billion-point benchmark, with low latency and high recall. The paper says FAISS and a similar system with a like memory footprint plateau at much lower recall. It also claims many more points per node than HNSW or NSG at high recall.

Read this with care. It is one benchmark on one dataset, from the authors, in 2019. SIFT vectors are not 1,536-dimension text embeddings. Treat it as proof that the approach works, not as your latency.

## Tuning: the recall and latency knobs

**Recall** here has a second meaning. Recall means the share of the true top-k (found by an exact search) that the index returns. A recall of 0.95 means 19 of 20 true neighbors are returned. Every knob below moves recall against time.

| Knob | Index | Default (source) | Raise it and you get |
|---|---|---|---|
| `nprobe` | IVF | 8 in Milvus; 1 in pgvector | Better recall, slower query |
| `nlist` | IVF | 128 in Milvus, range 32 to 4,096 | Finer clusters, slower build |
| `efSearch` | HNSW | 40 in pgvector (`hnsw.ef_search`) | Better recall, slower query |
| `M` | HNSW | 16 in pgvector; hnswlib says 12 to 48 suits most cases | Better recall, more memory |
| `ef_construction` | HNSW | 64 in pgvector | Better graph, slower build |

Defaults are from the Milvus IVF_FLAT docs, the pgvector README and the hnswlib parameter guide, read on 2026-10-16. The HNSW paper has its own suggested values. But we could not read the paper body, so we cite the library defaults. The hnswlib guide adds that `ef` can be anything from k up to the dataset size. The guide also says that a recall below 0.9 on your test means there is room to improve.

Two rules from the docs. Milvus says to set `nprobe` in proportion to `nlist`. The FAISS guide says `nlist` should be 4 x sqrt(N) to 16 x sqrt(N). That applies to datasets under 1 million vectors. IVF needs 30 x nlist to 256 x nlist training vectors.

Raising a knob has no fixed payoff: it depends on your data. So the method is a sweep. Take your A5.1 query set, compute the exact top-k once, then run the index at several `efSearch` or `nprobe` values. Plot recall against latency, and pick the cheapest setting that meets your bar.

```python title="sweep_hnsw.py"
import faiss, numpy as np

d, M = 1536, 16
index = faiss.IndexHNSWFlat(d, M)       # 4*d + M*2*4 bytes per vector
index.hnsw.efConstruction = 64
index.add(vectors)                      # float32 array, shape (n, d)

for ef in (16, 40, 100, 200):
    index.hnsw.efSearch = ef
    _, found = index.search(queries, 10)
    recall = np.mean([len(set(f) & set(t)) / 10 for f, t in zip(found, exact_top10)])
    print(ef, recall)
```

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Flat | Exact results, no tuning | N x d work per query | Under about 100,000 vectors |
| IVFFlat | Fast build, tunable work | Full vectors in RAM; recall depends on nprobe | Data changes slowly |
| PQ | Far less memory | Estimated distances, lost recall | RAM is the limit |
| HNSW | Best speed for a given recall | Vectors plus links in RAM | Millions of vectors, live updates |
| DiskANN | A billion points on one box | SSD reads, a more complex build | Billions of vectors, RAM-limited |

## Interview lens

<Callout type="tip">
Lead with the memory math: "A billion 1,536-dimension float vectors is terabytes flat. PQ codes are many times smaller and fit on one big server. I would keep codes in RAM and full vectors on SSD to re-score the top few hundred." Then say how you tune: "I sweep efSearch against recall on a labelled query set and pick the cheapest setting that meets the bar."
</Callout>

<Callout type="mistake">
Do not say HNSW "scales to billions" without its memory. HNSW holds full vectors plus links, so a billion vectors is terabytes of RAM. Do not quote a recall without saying how you measured it. Do not copy a DiskANN number as your own latency: it is one benchmark on SIFT1B.
</Callout>

<Callout type="deep" title="Why codes lose recall">
PQ replaces each piece of a vector by its nearest table entry. Two different vectors can share a code. So their estimated distance to the query is identical when the true ones differ. That is why systems re-score a candidate list with the full vectors. The first pass is cheap and wide, and the second is exact and narrow.
</Callout>
