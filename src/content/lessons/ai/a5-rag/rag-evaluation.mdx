## The problem

Users say "the bot gives wrong answers." That sentence hides two different faults. Either the right text never reached the model, or it did and the model ignored or distorted it. The fixes are different. Retrieval faults call for chunking, hybrid search, reranking. Generation faults call for prompts, context order, a different model. If you guess, you spend a week on the wrong half.

A RAG system is two components in a row. Measure each on its own, then measure the whole. This lesson gives the metrics, a golden set to compute them on, and a rule for what to fix first. The full eval method is in the [Eval-Driven Design](/learn/ai/a8-evals/eval-driven-design/) lesson, and how to trust a judge is in the [Code Checks and LLM Judges](/learn/ai/a8-evals/judges/) lesson.

## Naive solution: read some answers and judge by feel

A developer asks 10 questions, reads the replies, and says "looks good". It fails because 10 samples are noisy, you remember the good ones, and a change that helps one question may hurt twenty. You cannot tell whether last week's chunking change helped. You also cannot tell which half broke.

## The mechanism: a golden set and two sets of metrics

### Build the golden set first

A **golden set** is a list of test cases. Each case holds a question, the ids of the chunks (or documents) that contain the answer, and a short reference answer. Build it in this order:

1. Sample real questions from logs or support tickets. Questions invented by the team sound like the documents. Real ones do not.
2. For each, find the gold chunks by hand or by a first pass with a model, then check by hand.
3. Write the reference answer in one or two sentences.
4. Cover easy and hard cases: exact terms, paraphrases, questions with no answer in the corpus, questions that need two chunks.

Start with 50 to 200 cases. Keep it versioned like code. Add every production failure to it. If the chunking changes, gold chunk ids change too, so store the source passage as well as the chunk id.

### Retrieval metrics

These need no LLM. They compare the ranked list to the gold labels. Take one query where the retriever returns 5 chunks and the 3 relevant chunks that exist are in the corpus. Ranks 1 and 3 are relevant, ranks 2, 4 and 5 are not.

- **Recall@k**: of all relevant chunks, what share is in the top k? Here 2 of the 3 that exist were found, so recall is about two thirds. Use it to ask "did the evidence reach the model?"
- **Precision@k**: of the k returned, what share is relevant? Here 2 of 5 are relevant, so precision is low. It measures noise in the prompt.
- **MRR** (mean reciprocal rank): the reciprocal rank is 1 divided by the rank of the first relevant chunk. Average that over all queries. A first hit at rank 1 scores the maximum. A first hit at rank 3 scores a third of that. It rewards putting a good chunk first.
- **nDCG@k** (normalized discounted cumulative gain): a hit at rank i earns 1 / log2(i + 1). So lower ranks count less. nDCG compares your list with the best possible list, where all relevant chunks come first. A score of 1 means your order is perfect. It rewards the whole order, and it needs graded labels if some chunks are better than others.

Recall@k is the one to watch for RAG, since the model needs the evidence somewhere in the context. Anthropic reports its contextual retrieval results as the failure rate "1 minus recall@20" ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). Try the list below. ### Generation metrics

These need an LLM as a judge, because the output is free text. RAGAS is an open-source library that defines several. The definitions below come from its docs, fetched 2026-10-16.

- **Faithfulness** "measures how factually consistent a response is with the retrieved context." The judge lists the claims in the response and checks each against the context. The score is "Number of claims in the response supported by the retrieved context". That count is divided by "Total number of claims in the response" ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)). A 5-claim answer with 4 supported claims scores 0.8. This is the groundedness check.
- **Response relevancy** (also called answer relevancy) "measures how relevant a response is to the user input". Response relevancy penalizes answers that are incomplete or include unnecessary details. RAGAS generates artificial questions from the answer (3 by default) and averages the cosine similarity to the real question ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/)).
- **Context precision** "evaluates the retriever's ability to rank relevant chunks higher than irrelevant ones". It is the mean of precision@k over the chunks. Precision@k is the number of relevant chunks at rank k over the chunks at rank k ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)).
- **Context recall** "measures how many of the relevant documents (or pieces of information) were successfully retrieved". The score is reference claims supported by the retrieved context over total reference claims ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)).
- **Noise sensitivity** "measures how often a system makes errors by providing incorrect responses" when given relevant or irrelevant documents. Lower is better ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/noise_sensitivity/)).

Note that RAGAS context recall counts claims in the reference answer, so it needs no chunk ids. The classic recall@k needs labeled chunks but no LLM. Pick by what labels you can afford.

The judge is a model, so it costs money and adds variance. The RAGAS docs say its LLM-based metrics may use one or more LLM calls. Two runs can give different numbers. Spot-check the judge against human labels before you trust it. The [Code Checks and LLM Judges](/learn/ai/a8-evals/judges/) lesson covers this in detail.

### Component and end-to-end

**Component evals** run one stage alone: the retriever on the golden set, the generator on fixed, correct context. They are cheap, fast and tell you where the fault is. **End-to-end evals** run the whole chain and score the final answer against the reference. They tell you what the user sees. Use component evals in development and each commit, end-to-end evals before release and on a sample of production traffic.

The decision rule: **fix retrieval first.** If the gold chunk is not in the context, no prompt can recover it. If recall@k is high and faithfulness is low, the model is the problem. If both are high and users still complain, check that the golden set looks like real questions.

## Numbers and trade-offs

| Metric | Needs | Cost | Tells you |
|---|---|---|---|
| Recall@k | Gold chunk labels | No LLM | Did the evidence arrive |
| Precision@k, MRR, nDCG | Gold chunk labels | No LLM | Noise and ordering |
| Faithfulness | Answer and context | LLM calls | Did the model stay grounded |
| Response relevancy | Question and answer | LLM and embeddings | Did it answer the question |
| Context recall | Reference answer | LLM calls | Did context cover the reference |

<Callout type="tip">
In an interview, say "I split retrieval from generation." Name recall@k for the first and faithfulness for the second. Say you build the golden set from real queries, and that you fix retrieval first.
</Callout>

<Callout type="mistake">
Do not report one blended "accuracy" for a RAG system. Do not tune prompts while recall@k is low. Do not trust a judge score you never checked against human labels. Do not build the golden set only from questions the team wrote.
</Callout>

- [RAGAS: Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/): reference claims covered by the context.
