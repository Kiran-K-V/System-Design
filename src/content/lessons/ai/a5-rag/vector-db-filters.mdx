## The problem

A customer opens your support assistant and asks a question. The search must return the 10 chunks nearest to the question, but only chunks that customer is allowed to see. That is a vector search with a **filter**. A filter is a condition on stored fields such as tenant, date, language or document type.

Lesson [A5.2](/learn/ai/a5-rag/ann-indexes/) tuned the index for speed and recall with no condition attached. A filter changes the problem. The index knows distances between vectors. It does not know which vectors belong to tenant A.

<CrossTrackLink id="10-advanced/vector-databases">
Backend lesson 10.4 already showed the trap. In pgvector, the scan uses the approximate index first, then applies the filter. So a condition that matches 10% of rows with `ef_search` 40 leaves about 4 rows. It listed three fixes: iterative index scans, a B-tree index on the filter column, and partial indexes or partitions. This lesson goes through the strategies in order, shows the failure in motion, and adds how to choose a database.
</CrossTrackLink>

## Naive solution: search, then filter

This is **post-filtering**. Ask the index for its nearest candidates, then drop those that fail the filter. The pgvector README states it plainly: "With approximate indexes, filtering is applied after the index is scanned." Its example: "If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average."

The idea is simple. The index returns a fixed number of candidates. Only the share that matches the filter survives. A tenant that owns 1% of the data would see almost nothing. The failure is silent. The query runs, returns fewer rows than asked, and no error appears. The model downstream answers from less context than you planned.

## The mechanism: three strategies

**Pre-filtering.** Find the rows that match the filter first, then search only those. If the match set is small, you can compare the query with every one of them. That is an exact search over a subset, so recall is perfect and the answer always has min(k, matches) rows. The cost is work in proportion to the number of matching rows. The pgvector README says exact indexes "work well for conditions that match a low percentage of rows". Otherwise, the README says approximate indexes "can work better." In Postgres, the start it gives is a B-tree index on the filter column.

**Post-filtering with iterative scans.** Keep the approximate index and let the scan continue when too few rows pass. Version 0.8.0 of pgvector added iterative index scans. You turn them on with `hnsw.iterative_scan`, set to `strict_order` or `relaxed_order`. Strict keeps results in exact order by distance. Relaxed allows them slightly out of order for better recall. The scan stops at `hnsw.max_scan_tuples`, 20,000 by default. At a 10% match it needs only a few hundred candidates for 10 rows. At a very rare match, it would need far more than the cap. The scan stops early, so you get only a couple of rows.

**Filterable HNSW.** Check the filter while walking the graph, and only keep matching points. This sounds ideal, but it has a trap. If most points are skipped, the walk can lose its path through the graph.

Qdrant's article on filterable HNSW shows this. Its author ran a 2019 experiment on his own modified Python HNSW, not on the Qdrant product. With m = 16, precision@10 was 0.85 at one setting of his test parameter and 0.05 at the next. His explanation is that once enough nodes are removed, the graph splits into islands. Then the search cannot cross between them. The fix he proposes is extra edges built within each category, so each category stays connected on its own. Qdrant's docs tell you to create payload indexes on fields you filter by. Ideally, create them before you load data, so the engine can plan around them. Without an index, filtering still returns correct results, but it is not accelerated.

### See the rows returned

Move the share of matching rows down from 100% and watch each strategy.

<Ai5FiltCalc client:visible />

At 10% with the defaults, the post-filter returns 4 of 10. The iterative scan returns 10, and the exact scan returns 10. At 0.01%, post-filter returns 0.004 rows (essentially none). The iterative scan returns about 2 of 10. The exact scan over 1,000,000 rows compares just 100 vectors and returns 10. At very low selectivity, pre-filtering plus exact scan is the only strategy that returns the full 10. The numbers assume matching rows are spread evenly in the index. A tenant whose data sits in one region of the vector space behaves differently, so measure on your own filters.

```sql title="filtered_search.sql"
-- pgvector 0.8.0 or later
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
CREATE INDEX ON items (tenant_id);          -- exact path for small tenants

SET hnsw.iterative_scan = relaxed_order;    -- keep scanning until enough rows pass
SET hnsw.max_scan_tuples = 20000;           -- the default cap

SELECT id, content
FROM items
WHERE tenant_id = 42
ORDER BY embedding <=> $1
LIMIT 10;
```

## Choosing where vectors live

Three families, and no single winner. These are decision points, not benchmarks.

**pgvector in your Postgres.** Vectors sit beside your rows, in the same transaction, backup and permission model. A tenant filter is an ordinary `WHERE`. You get the limits of one node, and the vector index must share memory with everything else. The pgvector README lists vector indexes up to 2,000 dimensions for the `vector` type.

**A dedicated vector database** such as Qdrant. It is built around filtered search, with payload indexes and a filterable graph, and it can shard vectors across machines. You pay for another system to run, and you must keep it in sync with your source of truth.

**An object-storage-based service** such as turbopuffer. Its docs say object storage is the durable store and a write is durable once it returns. The first query on a namespace reads object storage directly: on 1 million documents, p50 874 ms. After that the namespace is cached on NVMe and the p50 is 14 ms (turbopuffer architecture docs, as of 2026-10-16). Cold queries take 3 to 4 round trips of about 100 ms each. The trade is cost and scale against a slow first query. Both numbers are medians for 1 million documents, so do not read them as p90 or as your latency.

The docs of Pinecone and turbopuffer do not say whether their filters apply before or after the vector search. So ask: how does this system combine my filter with its index, and what happens at 0.1% selectivity? Then run your own filters at your own selectivity and count the rows that come back.

## Numbers

| Fact | Value | Source |
|---|---|---|
| Post-filter rows, 10% match, ef_search 40 | about 4 | pgvector README |
| Iterative scan | from pgvector 0.8.0; cap 20,000 tuples | pgvector README |
| Filterable-HNSW experiment | precision@10 0.85 to 0.05, m = 16 | Qdrant article, author's 2019 Python test |
| turbopuffer, 1M docs | p50 874 ms cold, 14 ms cached | turbopuffer docs |
| Cold query round trips | 3 to 4, about 100 ms each | turbopuffer docs |

## Trade-offs

| Strategy | You gain | You pay | Choose when |
|---|---|---|---|
| Post-filter | One simple index scan | Short results at low selectivity | The filter keeps most rows |
| Iterative scan | Full results at moderate selectivity | More scanning, a cap on work | Filter keeps 1% or more |
| Pre-filter and exact | Perfect recall on the subset | Work grows with matching rows | A tenant or partition is small |
| Filterable graph | Fast at many selectivities | Extra edges and index setup | A dedicated DB with payload indexes |
| Partition or partial index | An index per tenant | Many indexes to maintain | Few big tenants |

## Interview lens

<Callout type="tip">
Name the failure before you are asked: "A post-filter on an ANN index returns about ef_search x selectivity rows. At 10% that is 4 of 40. So I would use iterative scans or a B-tree index plus exact scan for small tenants. I would also test results at the smallest tenant size." Then say how you pick the store: scale, filter shape, and who runs it.
</Callout>

<Callout type="mistake">
Do not claim a filter "just works" on a vector index. Do not quote the 0.85 to 0.05 figure as a Qdrant benchmark: it was the author's own 2019 experiment. And do not use a tenant filter as your only permission check without testing for results that leak across tenants. Lesson [A5.9](/learn/ai/a5-rag/retrieval-permissions/) covers permissions.
</Callout>
