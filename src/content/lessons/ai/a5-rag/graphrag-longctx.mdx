## The problem

A legal team indexes 800 contracts. They ask two questions. First: "What penalty does Acme owe if it delivers late?" Second: "What are the top risks across all our contracts?"

The first question lives in one or two chunks. Vector search finds them. The second question lives in no chunk. It is a statement about the whole set. Top-k search returns the 5 chunks most similar to the words "top risks". Those chunks come from whichever contracts happen to use that phrase. The answer looks confident and covers 5 chunks of 800 contracts.

The GraphRAG paper (Edge et al., Microsoft) states this directly: "RAG fails on global questions directed at an entire text corpus", with "What are the main themes in the dataset?" as the example ([arXiv 2404.16130](https://arxiv.org/abs/2404.16130)).

This lesson covers two ways around it. One is to build a summary structure at index time (GraphRAG). The other is to skip retrieval and put everything in the prompt (long context). Then it compares both with plain RAG on cost.

## Naive solution: top-k and hope

Raise k. Send 50 chunks, or 200. This helps a little and does not fix the shape of the problem. A question about "all contracts" needs information from every contract. And no k that fits in a prompt covers a corpus of 800. Rerankers (the [Reranking and Query Rewriting](/learn/ai/a5-rag/reranking-rewriting/) lesson) reorder what was retrieved, so they cannot help either.

## The mechanism: GraphRAG

GraphRAG moves the work to index time. Step through it.

<Ai5GraphWalk client:visible />

The pipeline in four steps, following the paper and the [GraphRAG docs](https://microsoft.github.io/graphrag/):

1. **Extract.** An LLM reads each chunk and lists entities, relationships and key claims.
2. **Build the graph.** Entities become nodes and relationships become edges.
3. **Find communities.** A clustering step (the docs name the Leiden technique) groups densely linked nodes, hierarchically.
4. **Summarize.** An LLM writes a summary of each community, bottom-up. These summaries are stored.

At query time there are two modes. **Global search** is "for reasoning about holistic questions about the corpus" by using the community summaries. Each summary produces a partial answer, and the partial answers are combined. **Local search** is "for reasoning about specific entities". Local search fans out from an entity to its neighbors and their text.

The Microsoft Research blog reports results from pairwise LLM-grader tests. In these tests, the blog says GraphRAG beat a baseline RAG on comprehensiveness and diversity of answers. Faithfulness (measured with SelfCheckGPT) was similar. The test data was in the range of 1 million tokens. The blog gives no numeric win rates in the text we read, so we give none ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/graphrag-unlocking-llm-discovery-on-narrative-private-data/)). The grader was a model, and the results are from one team's data sets.

### The cost: heavy indexing

Look at the steps. Step 1 is an LLM call over every chunk of the corpus. Step 4 is more LLM calls over all the communities. The Microsoft blog says the LLM processes the entire private dataset to build the graph. Neither the blog nor the docs gave a token or dollar figure, so we give none. Plan to measure it on a sample, then scale. Also plan for rebuilds. If documents change, the entities and summaries that depend on them go stale (the [Freshness and Index Updates](/learn/ai/a5-rag/freshness-updates/) lesson covers update pipelines).

For a backend engineer: it is a **materialized view** of the corpus. You pay to precompute an answer shape, so that a query type that would otherwise scan everything becomes cheap. Like any materialized view, it must be refreshed when the base data changes.

## The alternative: put it all in the prompt

Models now accept very long prompts. Claude's pricing page lists a context window of up to 1M tokens for its current models. The page also says Sonnet 5.5 has no tiered long-context price (as of 2026-10-16, [claude.com/pricing](https://claude.com/pricing)). Why build an index at all? Put the corpus in the prompt and ask.

Three costs answer that. This lesson gives cost first, since it is the one you can derive.

**Cost per query.** Input tokens are billed on every query, so a prompt that carries the whole corpus pays for the whole corpus each time. RAG sends only a few retrieved chunks, so it is far cheaper per query, by about two orders of magnitude (~100x) at this size. Prices are on the [pricing page](https://claude.com/pricing).

A prompt cache changes this ([the Prompt Caching: Mechanics and Economics lesson](/learn/ai/a2-inference-cost/prompt-caching/)). After the first write, the corpus is read at a deep discount. Cached long context is still dearer per query than RAG, but it can be close enough for many queries on one fixed corpus. It only works when queries arrive inside the cache window (5 minutes by default) and the text before the question is identical every time.

**Quality.** A big window does not mean the model uses all of it well. Lost in the Middle (Liu et al.) found a pattern. Accuracy "is often highest when relevant information occurs at the beginning or end of the input context". For facts in the middle, accuracy is lower (the [Why Models Hallucinate, and the Context Window](/learn/ai/a1-model-function/hallucination-context/) lesson, [arXiv 2307.03172](https://arxiv.org/abs/2307.03172)). Databricks tested long-context RAG with several models, and the old models in the test degraded as context grew. Llama-3.1-405B averaged 0.623 at 16k, 0.594 at 32k and 0.587 at 64k. Claude-3-sonnet refused on copyright grounds in 3.7% of cases at 16k, 21% at 32k and 49.5% at 64k ([Databricks](https://www.databricks.com/blog/long-context-rag-performance-llms)). Those are 2024-era models. Newer models are better at long input, so test the model you will use. The direction is the warning.

On the other side, a 2025 study compared the two directly. It found "LC generally outperforms RAG in question-answering benchmarks, especially for Wikipedia-based questions", RAG did better on dialogue and general queries, and chunk-based retrieval lagged summarization-based retrieval, which came close to long context ([arXiv 2501.01880](https://arxiv.org/abs/2501.01880)). We read only the abstract, so we do not know the models. It says long context can win on quality. It does not say it wins on cost.

**Latency.** A long prompt must be prefilled before the first token, and prefill time grows with the prompt (the [Prefill vs Decode: TTFT and TPOT](/learn/ai/a2-inference-cost/prefill-decode/) lesson). We have no sourced time for 500K tokens. A cache read can cut the work, and a cache miss will not.

## When to pick which

| Situation | Pick | Why |
|---|---|---|
| One document or a small set that fits | Long context | No index, no retrieval misses. Cache it for many queries. |
| Large or growing corpus, many queries | RAG | Cost per query stays flat as the corpus grows. |
| Questions about specific facts | RAG, local search | Few chunks hold the answer. |
| Questions about the whole corpus | GraphRAG global, or map-reduce | No chunk holds the answer. |
| Corpus changes every hour | RAG | A graph and summaries are costly to rebuild. |
| Corpus beyond the window | RAG or GraphRAG | It does not fit. |

For whole-document questions on one text that fits, the [Long-document Strategies](/learn/ai/a4-context/long-documents/) lesson shows the map-reduce option. GraphRAG is that idea done at index time, over a corpus.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Vector RAG | Cheap per query, local answers | Fails on global questions | Most question-answering |
| GraphRAG | Global answers, themes | Heavy LLM indexing, rebuilds | Stable corpus, theme questions |
| Long context | No index, whole-text view | Cost per query, middle-loss risk | One document or a short list |
| Cached long context | Much lower input cost | Same-prefix rule, 5-minute window | Many queries on one fixed corpus |

## Interview lens

<Callout type="tip">
Classify the question first. "Is it local or global? A local question needs a few chunks, so I use RAG. A global question needs a whole-corpus view, so I use summaries built at index time or a map-reduce." Then say the cost shape out loud: a huge prompt pays for the whole corpus on every query.
</Callout>

<Callout type="mistake">
Do not say long context makes RAG obsolete. With a huge prompt, the cost per query is far higher unless you cache. A large window does not guarantee that the model uses all of it. Do not say GraphRAG is a better RAG for all questions. It targets global ones and costs far more to build.
</Callout>
