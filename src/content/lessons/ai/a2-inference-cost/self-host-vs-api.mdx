## The problem

Lesson [A0.4](/learn/ai/a0-orientation/build-buy-finetune/) gave you the break-even: an H100 at $3.99 an hour serving a small model at its measured speed beats a $0.50-per-million API only above about 49% utilization. That lesson stopped at one GPU and one utilization number. A real product has a traffic curve, a peak, a failure budget, and a team. This lesson turns the break-even into a plan. The lesson covers how many GPUs you need, what they cost over a month, and what you give up.

The question to answer is not "which is cheaper per token?" It is "what do I pay for a month of this traffic on each path, and what else changes?"

## Naive solution: divide the price by the speed

The naive plan takes the hourly price. The plan then divides that price by tokens per hour at full speed. Last, the plan compares the result to the API price. At 100% busy the H100 looks cheap. It is wrong in three ways.

First, no GPU is busy 100% of the time. You must leave room for bursts. Second, you must rent for the peak and pay for the quiet hours. Third, the speed figure came from one model on one setup. Change any of them and the number moves.

## The mechanism: size for the peak

Capacity planning is the estimation chain from the backend track, applied to tokens. Requests become tokens per second, and tokens per second become GPUs. Lesson [A2.4](/learn/ai/a2-inference-cost/batching-throughput/) gave the cost formula for one GPU. For a fleet:

<Math block tex="\text{GPUs} = \left\lceil \frac{\text{peak QPS} \times \text{output tokens per request}}{R \times u} \right\rceil" />

In words: take the tokens per second you must produce at peak. Divide that figure by what one GPU makes at your target utilization u. R is the tokens per second one GPU makes at full load. The target u is below 100% on purpose: it is your headroom for bursts and for latency (a busy server answers each user more slowly, lesson [A2.4](/learn/ai/a2-inference-cost/batching-throughput/)).

The cost per million tokens depends on the tokens you serve, not on the tokens you could serve:

<Math block tex="c = \frac{\text{GPUs} \times P_{\text{GPU}} \times 730}{\text{tokens served per month} / 10^{6}}" />

Here P is the GPU price per hour and 730 is the hours in a month. A 24-hour day makes the gap obvious.

**Throughput R.** The A0.4 benchmark is Llama 3.1 8B on one H100 with vLLM, from the [E2E Networks benchmark](https://docs.e2enetworks.com/docs/tir/benchmarks/inference_benchmarks/). Its short-chat row has 128 tokens in, 128 out, and request rate 64. That row lists 8,399 tokens per second. The row also lists 35.04 completed requests per second. The listed figure counts prompt and output tokens. For example, 35.04 x 256 = 8,970, which is near 8,399. The other rows fit the same way. A second row gives 8.95 x 2,152 = 19,260, against 19,127 listed. The output rate is 35.04 x 128 = 4,485 tokens per second (derived from the row). This lesson uses R = 4,485. The planner has a button for the listed figure too, so you can see how much it would flatter a plan. It is still one model on one setup: measure R yourself.

A second warning on R concerns a benchmark. The vLLM v0.6.0 release notes report 2.7x more throughput on Llama 3 8B on one H100 than v0.5.3. That figure comes from their own benchmark. Your serving software version can change R by a large factor.

### The planner

Enter your traffic. The default is 50 peak requests per second at 400 output tokens, with average load at 30% of peak.

<Ai2HostPlanner client:visible />

Hand check for the default: peak tokens per second = 50 x 400 = 20,000. At R = 4,485, that is 4.5 GPUs, so 5 before headroom. At a 70% target: 20,000 / (4,485 x 0.7) = 6.4, so 7 GPUs. Monthly cost = 7 x $3.99 x 730 = $20,389. Average load is 6,000 tokens per second, so average utilization is 6,000 / (7 x 4,485) = 19%. Tokens served per month = 6,000 x 3,600 x 730 = 15.8 billion. Cost per million tokens = $20,389 / 15,768 = $1.29. Against Haiku 5.5 at $0.50, that is $7,884 a month for the API. At this traffic shape, the API wins on price. Click the listed-figure button (8,399) and the plan drops to 4 GPUs. A plan built on that number would under-buy by 3 GPUs.

What to notice:

1. **Raise the average-to-peak share.** Flat traffic makes self-hosting far cheaper per token. Spiky traffic makes it expensive.
2. **Move the target utilization.** Higher targets need fewer GPUs and give users slower answers.
3. **Compare against Sonnet 5.5.** A $10 API price flips the answer, but an 8B model is not a Sonnet 5.5 substitute. Compare quality on your eval.

The planner counts output tokens only, one model size, and one GPU type. It counts no spare capacity unless you tick the box. It ignores input processing, the KV cache limit on batch size, and the cost of your team.

## What the planner leaves out

- **Operations.** You carry GPU failures, driver and server upgrades, autoscaling, and on-call. One spare GPU for failover is the minimum, and it is a fixed monthly cost.
- **Quality and eval cost.** Each model change needs the eval run again. An open model of 8B and a frontier API model are different products.
- **Lock-in.** Prompts tuned to one model drift when you switch. Self-hosting reduces dependence on a provider and adds dependence on your own stack.
- **Data privacy.** If data may not leave your network, the API is out, whatever the price. This is the most common forcing reason.
- **Latency control.** You choose the region, the batch size, and the model size. A small quantized model nearby (lesson [A2.6](/learn/ai/a2-inference-cost/quantization-small-models/)) can meet a tight budget that a remote API cannot. You also own the tail: a busy GPU slows every user.
- **Big models.** A 70B model in BF16 needs two H100s (lesson [A2.1](/learn/ai/a2-inference-cost/gpu-memory-math/)). They must talk fast. NVLink is 900 GB/s per H100 (NVIDIA's H100 page). Splitting a model across GPUs (tensor parallelism) stays inside one node. Elective E3.6 covers it.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| API | No fixed cost, no ops, best models, no idle bill | Per-token price, data leaves, provider limits | Variable or low volume, quality first |
| Self-host, fixed fleet | Predictable bill, data stays, full control | Pays for peak all day, ops load | Flat, high traffic or strict privacy |
| Self-host, autoscaled | Lower idle cost | Cold start lag, queueing on ramps, more moving parts | Strong daily pattern, tolerant latency |
| Hybrid: base load self-hosted, bursts to API | Fleet stays busy | Two paths to test and monitor | High base load with rare peaks |

## Interview lens

<Callout type="tip">
Say the chain: "Peak is 50 requests per second at 400 tokens, which is 20,000 tokens per second. At about 4,500 output tokens per second per GPU and a 70% target, that is 7 GPUs, about $20,400 a month at $3.99 an hour. Average load is 30% of peak, so real utilization is about 19%, and the API costs less. I would measure output tokens per second on our own model first, because benchmark columns often count input tokens too."
</Callout>

<Callout type="mistake">
Do not compare a GPU price at 100% utilization with an API price and stop. Do not size for the average and then say p99 is fine. Do not quote a throughput figure without saying which model, hardware, server, and request shape it came from. And do not forget the eval and on-call cost. A saving of a few hundred dollars a month does not pay for a person.
</Callout>
