## The problem

Lesson [A0.4](/learn/ai/a0-orientation/build-buy-finetune/) gave you the break-even: an H100 at $3.99 an hour serving a small model at its measured speed beats a $0.50-per-million API only above about 26% utilization. That lesson stopped at one GPU and one utilization number. A real product has a traffic curve, a peak, a failure budget, and a team. This lesson turns the break-even into a plan: how many GPUs, what they cost over a month, and what you give up.

The question to answer is not "which is cheaper per token?" It is "what do I pay for a month of this traffic on each path, and what else changes?"

## Naive solution: divide the price by the speed

The naive plan takes the hourly price, divides by tokens per hour at full speed, and compares the result to the API price. At 100% busy the H100 looks cheap. It is wrong in three ways.

First, no GPU is busy 100% of the time. You must leave room for bursts. Second, you must rent for the peak and pay for the quiet hours. Third, the speed figure came from one model on one setup. Change any of them and the number moves.

## The mechanism: size for the peak

Capacity planning is the estimation chain from the backend track applied to tokens: requests become tokens per second, and tokens per second become GPUs. Lesson [A2.4](/learn/ai/a2-inference-cost/batching-throughput/) gave the cost formula for one GPU. For a fleet:

<Math block tex="\text{GPUs} = \left\lceil \frac{\text{peak QPS} \times \text{output tokens per request}}{R \times u} \right\rceil" />

In words: the tokens per second you must produce at peak, divided by what one GPU makes at your target utilization u. R is the tokens per second one GPU makes at full load. The target u is below 100% on purpose: it is your headroom for bursts and for latency (a busy server answers each user more slowly, lesson A2.4).

The cost per million tokens depends on the tokens you serve, not on the tokens you could serve:

<Math block tex="c = \frac{\text{GPUs} \times P_{\text{GPU}} \times 730}{\text{tokens served per month} / 10^{6}}" />

Here P is the GPU price per hour and 730 is the hours in a month. A 24-hour day makes the gap obvious.

**API prices** are in lesson A0.4: Haiku 5.5 $0.50 per million output tokens, Sonnet 5.5 $10, Opus 5.5 $20 (the Anthropic pricing page lists the same figures as of 2026-10-16).

**Throughput R.** The A0.4 figure is 8,399 tokens per second for Llama 3.1 8B on one H100 with vLLM, from the [E2E Networks benchmark](https://docs.e2enetworks.com/docs/tir/benchmarks/inference_benchmarks/), at a request rate of 64 with 128 tokens in and 128 out. That page defines throughput as "the total number of tokens generated per second". We checked it against the same row, which also lists 35.04 completed requests per second. At 128 output tokens each, that is 35.04 x 128 = 4,485 output tokens per second (derived). The two numbers do not agree. The gap, 8,399 / 35.04 = 240 tokens per request, is nearer the 256 tokens of input plus output. So 8,399 may count prompt tokens too. We cannot tell from the page. For capacity planning, 4,485 is the safer output-only number, and it is a reason to measure R yourself. The planner has a button for each.

A second warning on R: the vLLM v0.6.0 release notes report 2.7x more throughput on Llama 3 8B on one H100 than v0.5.3, on their benchmark. Your serving software version can change R by a large factor.

### The planner

Enter your traffic. The default is 50 peak requests per second at 400 output tokens, with average load at 30% of peak.

<Ai2HostPlanner client:visible />

Hand check for the default: peak tokens per second = 50 x 400 = 20,000. At R = 8,399, that is 2.4 GPUs, so 3 before headroom. At a 70% target: 20,000 / (8,399 x 0.7) = 3.4, so 4 GPUs. Monthly cost = 4 x $3.99 x 730 = $11,651. Average load is 6,000 tokens per second, so average utilization is 6,000 / (4 x 8,399) = 18%. Tokens served per month = 6,000 x 3,600 x 730 = 15.8 billion. Cost per million tokens = $11,651 / 15,768 = $0.74. Against Haiku 5.5 at $0.50, that is $7,884 a month for the API. At this traffic shape, the API wins on price. Click "Output only" and 7 GPUs are needed (20,000 / (4,485 x 0.7) = 6.4).

What to notice:

1. **Raise the average-to-peak share.** Flat traffic makes self-hosting far cheaper per token. Spiky traffic makes it expensive.
2. **Move the target utilization.** Higher targets need fewer GPUs and give users slower answers.
3. **Compare against Sonnet 5.5.** A $10 API price flips the answer, but an 8B model is not a Sonnet 5.5 substitute. Compare quality on your eval.

The planner counts output tokens only, one model size, one GPU type, and no spare capacity unless you tick the box. It ignores input processing, the KV cache limit on batch size, and the cost of your team.

## What the planner leaves out

- **Operations.** You carry GPU failures, driver and server upgrades, autoscaling, and on-call. One spare GPU for failover is the minimum, and it is a fixed monthly cost.
- **Quality and eval cost.** Each model change needs the eval run again. An open model of 8B and a frontier API model are different products.
- **Lock-in.** Prompts tuned to one model drift when you switch. Self-hosting reduces dependence on a provider and adds dependence on your own stack.
- **Data privacy.** If data may not leave your network, the API is out, whatever the price. This is the most common forcing reason.
- **Latency control.** You choose the region, the batch size, and the model size. A small quantized model nearby (lesson [A2.6](/learn/ai/a2-inference-cost/quantization-small-models/)) can meet a tight budget that a remote API cannot. You also own the tail: a busy GPU slows every user.
- **Big models.** A 70B model in BF16 needs two H100s (lesson A2.1). They must talk fast. NVLink is 900 GB/s per H100 (NVIDIA's H100 page). Splitting a model across GPUs (tensor parallelism) stays inside one node. Elective E3.6 covers it.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| API | No fixed cost, no ops, best models, no idle bill | Per-token price, data leaves, provider limits | Variable or low volume, quality first |
| Self-host, fixed fleet | Predictable bill, data stays, full control | Pays for peak all day, ops load | Flat, high traffic or strict privacy |
| Self-host, autoscaled | Lower idle cost | Cold start lag, queueing on ramps, more moving parts | Strong daily pattern, tolerant latency |
| Hybrid: base load self-hosted, bursts to API | Fleet stays busy | Two paths to test and monitor | High base load with rare peaks |

## Interview lens

<Callout type="tip">
Say the chain: "Peak is 50 requests per second at 400 tokens, which is 20,000 tokens per second. At about 8,000 tokens per second per GPU and a 70% target, that is 4 GPUs, about $11,650 a month at $3.99 an hour. Average load is 30% of peak, so real utilization is about 18%, and the API costs less. I would measure tokens per second on our own model first, because the benchmark may count input tokens."
</Callout>

<Callout type="mistake">
Do not compare a GPU price at 100% utilization with an API price and stop. Do not size for the average and then say p99 is fine. Do not quote a throughput figure without saying which model, hardware, server, and request shape it came from. And do not forget the eval and on-call cost: a saving of a few hundred dollars a month does not pay for a person.
</Callout>
