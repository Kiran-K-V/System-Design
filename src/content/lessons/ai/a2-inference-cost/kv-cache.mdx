## The problem

[The Attention and Its Cost lesson](/learn/ai/a1-model-function/attention-cost/) introduced the KV cache and its size formula. This lesson asks the operations question. You have 4 H100s, the weights are loaded, and 148 GB of memory is left (the [GPU Memory Math](/learn/ai/a2-inference-cost/gpu-memory-math/) lesson). Users start sessions with different lengths and different answer lengths. You do not know in advance how long any of them will run. How do you hand out that memory without wasting most of it or running out?

## Naive solution: recompute, then reserve

Two naive moves, and both fail.

**Recompute.** Skip the cache. Each new token recomputes Keys and Values for the whole text so far. Work per token grows with length, and the whole answer costs about n²/2 K/V computations. For 1,000 tokens that is 500,500 against 1,000 with a cache.

**Reserve the maximum.** Keep the cache, but give each request one contiguous slab sized for its longest possible length. The reason is that GPU kernels usually want one contiguous tensor. The slab is booked for the request's whole life. Most requests stop earlier, so most of the slab is never used.

## The mechanism: the cache is a per-session cache

For a backend engineer the KV cache is a per-session cache. It holds work already done (Keys and Values for a session's tokens). The cache is keyed by session. It grows with the session.

<CrossTrackLink id="05-caching/eviction">
A cache has limited space, so you need a rule for what to drop. For the KV cache the rule is harsh: dropping part of a running request's cache means redoing that work. Servers instead make new requests wait. Or they throw away or swap out the cache of a whole sequence and rebuild it later.
</CrossTrackLink>

The vLLM paper uses an all-or-nothing rule: evict every block of a sequence or none. The reason is that a sequence needs all its blocks at each step.

### Size per token

<Math block tex="\text{KV bytes per token} = 2 \times L \times H_{kv} \times d_{head} \times \text{bytes}" />

The 2 is for K and V. L is layers, H_kv the number of KV heads, d_head the head width. For Llama 3 70B (80 layers, 8 KV heads, head width 128, BF16): 2 x 80 x 8 x 128 x 2 = 327,680 bytes, **320 KiB per token**. The layer and head counts come from the Llama 3.1 70B `config.json` (the same architecture; Meta's own file needs a login, so we read a public mirror).

| Model | Layers | KV heads | KV per token (BF16) | One 8K sequence |
|---|---|---|---|---|
| Llama 3 8B | 32 | 8 | 128 KiB | 1.0 GiB |
| Llama 3 70B | 80 | 8 | 320 KiB | 2.5 GiB |
| Llama 3 405B | 126 | 8 | 504 KiB | 3.9 GiB |
| Mixtral 8x7B | 32 | 8 | 128 KiB | 1.0 GiB |

Sources: Llama 3 paper Table 3, Mixtral paper Table 1. All use 8 KV heads and head width 128. Derived with the formula above.

The 8 KV heads matter. Llama 3 70B has 64 query heads. With **grouped-query attention** [mid] (GQA), several query heads share one K/V head. Without it the cache would be 64 / 8 = 8 times bigger. That is 2.5 MiB per token. The cache would be 20 GiB for an 8K sequence. The GQA paper reports that converting a model costs about 5% of its original pre-training compute. The converted model keeps quality close to full multi-head attention. Cache size drove that design.

Now scale it by users:

- One 128,000-token sequence on Llama 3 70B: 40 GiB. Half an 80 GB card.
- 32 sequences of 8K tokens: 32 x 2.5 = 80 GiB. On 4 x H100 (137.8 GiB of room, with the 10% reserve from the [GPU Memory Math](/learn/ai/a2-inference-cost/gpu-memory-math/) lesson) that fits. On 2 x H100, with 4 GB, it does not.

## Allocation: paging fixes waste

The vLLM paper profiled existing serving systems. It found that only **20.4% to 38.2%** of KV memory held real token data. The rest was reservation that was never used, plus gaps. The vLLM launch post says such systems waste 60% to 80% of memory. Three kinds of waste appear:

- **Reserved:** space booked for tokens that have not been generated yet.
- **Internal fragmentation** [mid]: space reserved that the request never uses.
- **External fragmentation** [mid]: free space split into holes too small for any new request.

The fix comes from operating systems. **PagedAttention** splits each sequence's cache into small fixed-size blocks. It keeps a **block table** per sequence that maps its logical blocks to physical ones. The blocks need not touch. The paper's own analogy: blocks are pages, tokens are bytes, and requests are processes. Blocks are taken on demand, one at a time as the sequence grows. All blocks are the same size, so there is no external fragmentation. Waste only happens in the last block of each sequence. vLLM reports under 4% waste. (The mechanics of the kernel are elective [PagedAttention](/learn/ai/e3-inference-deep/paged-attention/).)

The demo below is a toy: six requests share a 16,384-token pool, with illustrative sizes. Move the slider and watch the two allocators. Then tick the box to let B and D finish.

<Ai2KvPaged client:visible />

At 50% progress the contiguous pool holds 5,050 real tokens in 14,336 reserved: 65% wasted. The paged pool holds 5,072 tokens for the same data: 0.4% wasted. The newcomer G reserves 4,096 tokens. The contiguous pool says no, even though about 11,300 tokens of the pool hold no data. The paged pool says yes, since G only needs 19 blocks to start. Tick the box and the contiguous pool has 4,096 free tokens in three separate holes, and still says no.

Paging has a second gift: blocks can be shared. Many requests with the same prompt prefix can point to the same blocks. That is the idea behind prompt caching (the [Prompt Caching: Mechanics and Economics](/learn/ai/a2-inference-cost/prompt-caching/) lesson).

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Contiguous reservation | Simple kernels | 60% to 80% waste, fewer users | Almost never today |
| Paged blocks | Near-zero waste, sharing | Block-table lookup, a more complex kernel | A shared server |
| Shorter max context | More sessions per GPU | Less context per request | Most sessions are short |
| GQA model | 8x smaller cache | A small quality risk | Always choose when serving many users |
| Queue or preempt new requests | No out-of-memory crash | Waiting, or recompute work | The pool is full |

## Interview lens

<Callout type="tip">
Say the cache as a budget: "KV is 2 x layers x KV heads x head width x bytes. For 70B that is 320 KiB per token. After weights, I divide the leftover memory by tokens per session to get concurrent sessions." Then mention paging as the way to not waste that memory.
</Callout>

<Callout type="mistake">
Do not claim the KV cache is small because 320 KiB sounds small. Multiply by tokens and by users. Do not say "more GPUs fix it" without saying that weights and cache are both split over them. Do not size by prompt length only: the cache grows with the output too.
</Callout>

<Callout type="deep" title="Why the cache is read on every step">
The cache is not only stored, it is read. Each decode step reads the weights and every cached K and V of that request. At long contexts the cache read can rival the weight read. That is one reason the floor from the [Prefill vs Decode: TTFT and TPOT](/learn/ai/a2-inference-cost/prefill-decode/) lesson rises with context length, and why bigger batches stop being free.
</Callout>
