## The problem

You test one model two ways. A 20,000-token document with a one-line answer takes a second before anything appears, then it is done. A one-line question with a 1,000-word answer starts at once, then streams for half a minute. Same model, same GPUs. Why do the two feel so different?

Because a call is two jobs with different limits. If you tune one and measure the other, you waste money. This lesson separates them and gives you a number for each.

## Naive solution: "latency is cost per token times tokens"

[The Transformer Forward Pass lesson](/learn/ai/a1-model-function/forward-pass/) gave one cost per token: about 2N FLOPs. A single number per token predicts that a 20,000-token prompt and a 20,000-token answer cost the same. They do not. The prompt tokens go through the model **together**. The answer tokens go through **one at a time**. The reason is that each one depends on the one before it ([sampling and decoding](/learn/ai/a1-model-function/sampling-decoding/)).

## The mechanism: two phases, two ceilings

- **Prefill** [junior]: the model reads the whole prompt in one pass and produces the first output token. The time until you see that token is **TTFT** [junior] (time to first token).
- **Decode** [junior]: the model makes the rest of the tokens, one per pass. The average gap between tokens is **TPOT** [junior] (time per output token).

Databricks states the total: latency = TTFT + TPOT x number of output tokens. A TPOT of 100 ms is 10 tokens per second for that user. For a backend engineer, TTFT is time to first byte, and TPOT is the pace of a streamed response.

A GPU kernel can hit one of two ceilings. The **compute ceiling** is peak FLOP/s. The **memory ceiling** is how fast bytes arrive from HBM. Which one binds depends on **arithmetic intensity** [mid]: FLOPs of work per byte moved. The **ridge point** [mid] is the intensity where the two ceilings meet: peak FLOP/s divided by bandwidth.

For an H100 SXM in BF16, dense: 989 TFLOPS / 3.35 TB/s = **295 FLOPs per byte**. (A2.1 explained why 989 and not 1,979.)

Now the intensity of a transformer pass. Each weight is a 2-byte value. It is read from HBM once per pass. It does 2 FLOPs (a multiply and an add) for every token in that pass.

So intensity is about the number of tokens that share one read of the weights. In **decode** that is the batch size: one token from each request. At batch 1, intensity is about 1, far below the ridge. In **prefill** it is the prompt length. A prompt of a couple of thousand tokens sits far above the ridge. Watch the dot move.

The consequence: decode is **memory-bound**, prefill is **compute-bound**. A prompt shorter than the ridge (a few hundred tokens) is still on the slope. The attention term and the KV cache reads move the real ridge. So treat 295 as a first estimate. The roofline here is our model, in the style Databricks describes.

### The decode floor

Every decode step reads all the weights once. When several GPUs share the model (tensor parallel, A2.1), each reads its own slice in parallel. So the step time has a floor: the weight bytes divided by the total memory bandwidth of the GPUs that hold them.

This is a floor, not a forecast. The real step also reads the KV cache and talks over NVLink. For a 70B model in BF16 (~140 GB), the floor is a few tens of milliseconds per token on two H100s. Adding GPUs lowers the floor, because each one reads less. A GPU with faster memory lowers it too.

A common mistake is to divide the whole weight size by the bandwidth of one GPU. That assumes the model sits on one GPU, which a 70B BF16 model cannot do. Use the number of GPUs that actually holds it.

### The TTFT floor

Prefill does work for every prompt token, plus the attention score work from [the Attention and Its Cost lesson](/learn/ai/a1-model-function/attention-cost/), which grows with the square of the prompt. So TTFT grows with prompt length, and faster than a straight line for very long prompts. The floor for a 2,000-token prompt on a 70B model is on the order of ~0.1 s (our estimate). Real servers reach a fraction of peak, so TTFT is longer. Move the sliders to see both floors for a whole request.

Try a short prompt and a long answer. Decode takes almost all the time. This is why output length drives latency: the Databricks guide says so too. To speed up a slow answer, first ask for fewer output tokens.

## Measuring: MFU and MBU, not "utilization"

NVIDIA's own docs define the GPU percentage in nvidia-smi. It is the percent of time over the sample period during which one or more kernels was executing. It does not say how much of the math units or the memory bandwidth the kernel used. A decode loop keeps a kernel running all the time. So it reads near 100% while it wastes most of the chip.

Two better numbers:

- **MFU** [mid] (model FLOPs utilization): achieved FLOP/s over peak FLOP/s. Good for prefill and training. Llama 3 405B pre-training reached 38 to 43 percent on H100s (41% at 16K GPUs). That is training, not serving.
- **MBU** [mid] (model bandwidth utilization): achieved bytes/s over peak bytes/s. Here, bytes are weights plus KV cache per step, divided by TPOT. Databricks' example: a 7B BF16 model at 14 ms TPOT moves 14 GB in 14 ms. That is 1 TB/s, so 50% of a 2 TB/s GPU. Good for decode.

At batch 1, decode MFU is tiny by design. Judge decode by MBU.

## Trade-offs

| Lever | You gain | You pay | Choose when |
|---|---|---|---|
| Shorter prompt | Lower TTFT, cheaper prefill | Less context for the model | Long inputs dominate TTFT |
| Fewer output tokens | Lower total latency | Shorter answers | Answers are long (decode dominates) |
| More GPUs per replica | Lower TPOT floor, more KV room | Cost, link traffic | One user needs speed |
| Higher batch | More tokens/s per GPU | Higher TPOT per user (A2.4) | You serve many users |
| Lower precision | Fewer bytes per step, so lower TPOT | Quality risk (A2.6) | Decode is the limit |

## Interview lens

<Callout type="tip">
Split every latency answer into the two phases: "TTFT is prefill, compute-bound, grows with prompt length. TPOT is decode, memory-bound, set by weight bytes over bandwidth. For 70B on two H100s, that is a few tens of ms per token. So a long answer takes seconds, however short the prompt." Then say which phase you would shorten first.
</Callout>

<Callout type="mistake">
Do not quote GPU utilization as evidence that a deployment is efficient. Do not say "the GPU is the bottleneck" without naming compute or memory bandwidth. Do not divide the weight size by one GPU's bandwidth when the weights are split over several.
</Callout>

<Callout type="deep" title="Why a bigger batch does not slow the step much">
At batch 1, a step takes about the weight bytes over the total bandwidth, whatever the batch is. This holds as long as compute stays below the roof. Going from 1 to 16 tokens per step adds a little KV reading and some math. But the time does not grow 16 times. That is why batching raises throughput nearly for free, until the ridge or the KV cache stops it. The [Batching and Throughput](/learn/ai/a2-inference-cost/batching-throughput/) lesson builds on this.
</Callout>
