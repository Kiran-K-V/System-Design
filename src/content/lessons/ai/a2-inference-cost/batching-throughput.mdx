## The problem

[The Prefill vs Decode: TTFT and TPOT lesson](/learn/ai/a2-inference-cost/prefill-decode/) showed that one user at batch 1 uses about 0.3% of an H100's compute ceiling. You still pay for the whole GPU, by the hour. A 70B model on two H100s serves only a few dozen tokens per second to a single user. That makes each token very expensive.

The same two GPUs can serve many users at nearly the same step time. This lesson shows how much, what it costs each user, and how the scheduler decides who is in the batch.

## Naive solution: one request at a time

Serve requests in a queue, one after another. It is simple, and each user gets the fastest possible TPOT. But each decode step reads 140 GB of weights to produce one token, and the math units sit idle. Cost per token is at its worst. Tail latency also suffers: a request that arrives behind a long one waits for all of it.

The next idea is to group requests. That is **batching** [junior]: run several requests through the model in the same pass.

## The mechanism: share each read of the weights

Decode is memory-bound: its time is set by reading the weights, not by math. A step with 1 token and a step with 16 tokens read the same 140 GB. So the extra 15 tokens are nearly free until compute or the KV cache becomes the limit. The weights are read once, and every request in the batch uses them.

Databricks measured this on one A100 with MPT-7B, static batching, 512 input and 64 output tokens. Throughput in requests per second is 0.9 at batch 1, 3.2 at batch 4, and 5.3 at batch 8. It is 8.0 at batch 16, 10.5 at batch 32, and 12.5 at batch 64. That is about ~14x more throughput at batch 64.

Read three things off it.

1. **Throughput rises fast, then flattens.** Early doublings add a lot. Later doublings add little. Past the compute-bound point, Databricks says, every doubling of batch size increases latency without increasing throughput.
2. **Latency per user rises.** Databricks reports several times more latency at batch 64 than at batch 1. A full static batch finishes together, so every user waits for the whole batch.
3. **There is a knee.** A service picks a batch size that meets its latency target, not the biggest one.

Two more limits stop the batch from growing. The KV cache ([the KV Cache lesson](/learn/ai/a2-inference-cost/kv-cache/)) grows with every user. On 4 x H100 with 70B, the pool holds dozens of 8K-token sequences, but only a handful of 128K-token ones. And the ridge point (295 on an H100) caps how many tokens help.

<CrossTrackLink id="01-one-machine/throughput-vs-latency">
Throughput and latency are different numbers, and a queue links them. As load rises, a server does more total work, but each request waits longer. A batch size is the same trade: more work per second, more wait per user. Little's Law ties them together.
</CrossTrackLink>

## Which requests go in the batch

Requests do not all have the same length. That is where the scheduler matters. There are three common styles, as Databricks describes them.

- **Static batching:** the client packs a group and the response returns when every sequence in it is done. The batch is as slow as its longest member.
- **Dynamic batching** [mid]: the server collects requests on the fly for a short window. The server then runs them as a batch. It can be near-optimal for short or uniform responses. Typically it performs worse than static batching on uniform loads.
- **Continuous batching** [mid]: the scheduler decides at every decode step. A finished request leaves at once and a waiting one takes its place. Databricks reports 10x to 20x better throughput than dynamic batching.

The same tokens finish in fewer steps under continuous batching, and the slots stay fuller. For a backend engineer this is a worker pool. Static batching is a pool that waits for all its workers to finish before taking new jobs. Continuous batching hands a job to any worker that is free.

Reported gains depend on the baseline, so do not add them up. Anyscale measured 8x for continuous batching alone over static batching on OPT-13B on one A100 40GB, and up to 23x when paged memory is added (vLLM). The Orca paper reports 36.9x over FasterTransformer on GPT-3 175B at the same latency. Different models, hardware, and baselines. The common point: filling idle slots is worth a large factor.

One caution. At low load there is little to batch. Databricks notes that dynamic batching can beat continuous batching in low-QPS settings. Measure with your own traffic.

### Goodput

**Goodput** [mid] is the rate of requests that meet their latency targets (TTFT and TPOT), not the raw rate. A server that completes many requests per second but misses the TPOT target on a large share of them has a low goodput. Throughput can rise with batch size while goodput falls once users are too slow. Pick the batch size by goodput.

## From throughput to dollars

The GPU costs the same whether it is busy or idle. So cost per token falls when throughput rises, and rises when the GPU sits idle. Two factors set the cost: tokens per second, and the share of time the GPU has work (utilization).

Price anchor: Lambda lists an NVIDIA H100 SXM 80 GB at ~$3.99 per GPU per hour on its 8-GPU instance (on-demand; Lambda pricing page, [lambda.ai/pricing](https://lambda.ai/pricing), as of 2026-10-16). Prices change, so check the page.

- **Batch 1 on a 70B model:** the GPUs do almost no useful math per step, so each token carries a huge share of the hourly bill.
- **Many streams sharing each step:** the same hourly bill is spread over many more tokens, so cost per token falls a lot. This is an upper bound on the gain. The KV reads and the ridge point make real systems slower.
- **A busy GPU versus a mostly idle one:** the idle GPU costs the same per hour, so each useful token costs several times more.

Doubling throughput halves the cost per token. That is why the scheduler is a cost lever, not only a speed lever. ## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Bigger batch | Throughput, lower cost per token | Higher latency per user, more KV memory | Offline jobs, cost-sensitive traffic |
| Smaller batch | Low TPOT | High cost per token | Interactive, strict latency target |
| Continuous batching | Few idle slots, short requests leave early | A more complex scheduler | Shared servers with mixed lengths |
| Dynamic batching | Simple | Waits for a window, idle after short requests | Low QPS, uniform responses |
| Run the GPU busy | Lowest cost per token | No spare capacity for spikes | Steady, predictable load |

## Interview lens

<Callout type="tip">
Tie batching to the roofline: "Decode is memory-bound, so each weight read serves one token at batch 1. Batching shares the read across users, so throughput rises, up to the ridge or the KV cache limit. Each user's latency rises. Continuous batching keeps slots full when lengths differ." Then say that cost per token falls as throughput rises, and state what utilization you assume.
</Callout>

<Callout type="mistake">
Do not say "more users, same speed for everyone". Per-user TPOT rises with batch size. Do not quote a continuous-batching gain without its baseline. Do not quote a cost per token at full utilization and call it the bill.
</Callout>

<Callout type="deep" title="Why throughput eventually stops rising">
The step time is roughly max(time to read weights and KV, time to do the math). While memory dominates, more tokens in the step are almost free. Once the math dominates, each extra token adds its own time. So a doubled batch doubles the step, and throughput stays flat. KV reads grow with batch and context, so the real knee comes earlier than the ridge point suggests.
</Callout>
