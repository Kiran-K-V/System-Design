## The problem

An assistant sends the same 20,000 tokens at the start of every call. Those tokens are a system prompt, a tool list, and a few examples. The user's actual question is 300 tokens. You pay for the 20,000 on every call, and the model re-reads them on every call.

The money first. Input tokens are billed per token, so a 20,000-token prefix is most of the bill on every call, for text that never changes. The time next: the provider must run the prefill pass over all 20,000 tokens. This happens before the first output token (the [Prefill vs Decode: TTFT and TPOT](/learn/ai/a2-inference-cost/prefill-decode/) lesson). That is the wait you feel as time to first token.

## Naive solution: send it and pay again

Nothing is wrong with the naive call. It is simple, and it works. It wastes work, because the first 20,000 tokens produce the same Keys and Values every time. The [KV Cache](/learn/ai/a2-inference-cost/kv-cache/) lesson showed that the KV cache stores those per-token results so the model need not recompute them. Inside one request the server already reuses them. Between requests it throws them away. Prompt caching keeps them.

## The mechanism: store the prefix, match by prefix

The idea is one you know from the backend track.

<CrossTrackLink id="05-caching/cache-strategies">
A cache stores the result of expensive work under a key and serves repeats from memory. You choose a strategy for reads and writes and accept a risk of stale data. Prompt caching is the same pattern. The key is the exact prefix of the prompt, and the value is the model's KV entries for it.
</CrossTrackLink>

How a hit works:

1. A request arrives. The provider compares the start of the prompt with stored prefixes.
2. If a stored prefix matches token for token, the provider loads its KV entries. It then runs prefill only on the rest.
3. If nothing matches, it runs the full prefill and may store the prefix for next time.

The match is by **prefix**. One changed token in the middle ends the match at that point, and everything after it is a miss. Order matters: put what stays the same first, what changes last. The [Cache-friendly Prompt Layout](/learn/ai/a4-context/cache-friendly-layout/) lesson teaches how to lay out a prompt for hits. Here we only need the rule.

Self-hosted servers do this too. SGLang's paper names the technique RadixAttention: it keeps prompts' KV entries in a tree so shared prefixes are stored once.

### What each provider does

All numbers are USD per 1M input tokens, as of 2026-10-16, from each provider's page.

**Anthropic** ([prompt caching docs](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)):

- Prefix order is tools, then system, then messages. A change at one level invalidates that level and every level after it. Editing a tool invalidates all three.
- A write costs 1.25x the base price for the default 5-minute lifetime, or 2x for the 1-hour lifetime. A read costs 0.1x on most models. It costs 0.05x on Sonnet 5.5 and Opus 5.5, and 0.025x on Fable 5.1 and Mythos 5.1.
- Each use refreshes the timer at no cost. The lifetime counts from the start of the request, so a long streamed answer eats into it.
- Minimum cacheable prompt: 512 tokens on Sonnet 5.5, Opus 5.5, and Haiku 5.5. It is 1,024 to 4,096 on other models. A shorter prompt runs uncached and raises no error. Check `cache_creation_input_tokens` and `cache_read_input_tokens` in the response; both 0 means no caching happened.
- Cache hits are not deducted from your rate limit.

**OpenAI** ([prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)):

- Caching is automatic. On GPT-5.6 and later, the minimum is 1,024 tokens. A read costs 0.1x (0.05x for GPT-6.1 Sol). A write costs 1.25x. The default lifetime is 30 minutes and each reuse extends it.
- Earlier models have a model-dependent read price and no write fee. Retention is `in_memory` (about 5 to 10 minutes idle, up to 1 hour) or `24h`. Organizations without Zero Data Retention default to `24h`.
- Cached tokens still count toward the tokens-per-minute limit. This differs from Anthropic.
- Changing the model, the tools, `text.format`, or `reasoning.effort` breaks the match.

**Google Gemini** ([caching guide](https://ai.google.dev/gemini-api/docs/caching), [pricing](https://ai.google.dev/gemini-api/docs/pricing), last updated 2026-10-15):

- Implicit caching is on by default for Gemini 2.5 and newer. The minimum is 2,048 tokens on 2.5 Flash and 2.5 Pro, and 4,096 on newer models. Savings pass on automatically; the guide gives no percentage.
- Explicit caches take a lifetime as a duration string such as `"300s"`. The guide does not state a default. They also carry a storage fee: $1.00 per 1M tokens per hour on 2.5 Flash, $4.50 on 2.5 Pro. So you pay a small hourly fee just to keep the cache, even when nobody reads it.
- Cached input is $0.03 on 2.5 Flash (base $0.30). On 2.5 Pro it is $0.125 (base $1.25, prompts up to 200K).

## Numbers: the break-even

A write costs a premium over the base price. A read costs a small fraction of it. So caching pays an extra amount at the write, and each read then saves most of the base price. The number of reads needed to recover the premium is the premium divided by the saving per read.

- **5-minute write (1.25x), read at 0.1x:** the premium is small and each read saves a lot. One reuse is enough.
- **1-hour write (2x), read at 0.1x:** the premium is bigger. You need two reuses.
- **On Sonnet 5.5**, reads are cheaper still, so the whole-number answers stay at one and two.

What to notice:

1. **Zero reads loses money.** A write that is never read costs 25% extra on the prefix. This is the failure case for a prompt that changes every call.
2. **The 1-hour option needs more traffic to pay**, but it survives gaps that kill a 5-minute entry. Pick the lifetime from your request spacing, not by habit.
3. **The saving has a cap.** The calculator prices only the prefix. Output tokens and new input are the same either way, so a short shared prefix saves little in total.

Assumptions: every read lands inside the lifetime. The prefix is above the minimum length and identical each time.

### Latency

A hit skips the prefix prefill, so time to first token should drop. We do not quote a figure because it depends on model, prefix size, and load. Measure it: send the same prompt twice and compare. The first request of a session is slow because it writes.

## A different cache: semantic caching

Semantic caching stores whole answers and reuses one when a new question looks similar to an old one. It usually finds this match by comparing embeddings. It is a different tool. A provider cache never changes the answer: the model still runs on every request, only the prefill is cheaper. A semantic cache can skip the model call entirely, so it saves more. It can also return an answer meant for a different question or a different user. We have no sourced hit rate or error rate for it, so this lesson gives none. If you build one, measure the wrong-reuse rate on your own eval (the [AI Design Method](/learn/ai/a0-orientation/ai-design-method/) lesson) before shipping.

## Trade-offs

| Choice | Gain | Pay | When to choose |
|---|---|---|---|
| No caching | Simple, no lapse risk | Full price and full prefill each call | Short prompts, or every prompt is unique |
| 5-minute cache | 0.1x or lower reads, cheap 1.25x write | Lapses if requests are more than 5 minutes apart | Steady traffic, bursts inside a session |
| 1-hour cache | Survives gaps | 2x write, needs 2 reuses to pay | Sparse traffic with a big shared prefix |
| Automatic (OpenAI, Gemini implicit) | No code change | Less control, hits you cannot force | Default start |
| Semantic cache | Skips the model call | Wrong-reuse risk, extra system to run | Repeated near-identical questions, after you measure the risk |

## Interview lens

<Callout type="tip">
Say it with the mechanism: "Our 20K-token prefix is most of each call's input bill. A 5-minute write costs a small premium and a read costs a small fraction of base, so one reuse breaks even. I keep stable content first, check the cache-read field in the response, and alert when it drops to zero."
</Callout>

<Callout type="mistake">
Do not cache a prompt that changes every call: you pay the write premium and never get a read. Do not edit the tool list or the top of the prompt on each request. The reason is that the edit invalidates everything after it. Do not assume cached tokens are free of rate limits on every provider: OpenAI counts them toward tokens per minute.
</Callout>
