## The problem

A photo app resizes every upload into thumbnails. One resize takes about 200 ms of CPU. A **worker** is a program that takes one job and does it. A pool of 10 workers keeps up with normal traffic easily.

A marketing email goes out. For 10 seconds, uploads arrive several times faster than the workers can resize them. The upload endpoint now has two bad options.

- **Do the resize inside the request.** The user waits for the resize. Requests pile up on the 10 workers. By lesson 1.3, waiting time explodes once the arrival rate passes the service rate. Users see timeouts.
- **Buy for the peak.** You need many extra workers for 10 seconds, and few for the rest of the day. For a one-time spike, most of those machines sit idle.

Both fail for the same reason. The caller and the work are **tied together in time**. The caller must wait. The workers must be ready at the moment of the burst.

## The mechanism: put a buffer in between

A **queue** is a buffer that sits between a **producer**, which creates work, and **workers**. Workers, also called consumers, do the work. The producer adds a **message** that describes the job, for example the id of the uploaded photo. The producer returns at once. Workers take messages one by one at their own speed.

This breaks the tie in time. It gives you four things:

1. **The caller does not wait.** The upload returns after one fast write to the queue.
2. **Bursts are absorbed.** The queue is longer for a while. Nothing times out. **Amazon SQS** (Simple Queue Service) is a queue that Amazon Web Services runs for you. You send messages to it over the network, and you never run a queue server yourself. Its docs describe the buffer this way. A queue can process each buffered request on its own, "scaling transparently to handle any load increases or spikes."
3. **Producer and worker are decoupled, which means one does not depend on the other being up.** A worker can be down, slow, or deployed again. The messages wait.
4. **Workers scale on their own.** You add workers when the queue grows.

<Callout type="deep" title="A queue buffers. It does not add capacity">
If producers are faster than workers for long enough, the backlog grows without end. A queue only moves the wait from the caller to the queue. It does not remove the wait. Lesson 1.3 showed why: the closer the load gets to 100% of capacity, the longer the line. Lesson 6.4 covers what to do when the line grows.
</Callout>

## What a worker does with a message

A worker does three things, in order: **receive** the message, **process** it, then **acknowledge** it (an ack). The ack tells the queue the work is done. Only then does the queue delete the message.

Why not delete on receive? Suppose the worker crashes after receiving and before finishing. The queue already threw the message away. The job is lost, with no error anywhere. So queues keep the message until the worker says it is done.

That creates the next question. How does a queue know a worker died? It cannot. So SQS uses a **visibility timeout**. "Visible" means other workers can see and take the message. When a worker receives a message, the queue hides it from other workers for a set time. The default is 30 seconds. If the worker deletes the message in time, it is gone. If not, the timer ends and the message becomes visible for another worker. A worker with a long job can ask for more time with the SQS call `ChangeMessageVisibility`. **RabbitMQ** is a popular queue server that you run yourself. The server in the middle is called a **broker**. RabbitMQ does the same as SQS with a different tool. If a consumer's connection (its channel) closes without an ack, the broker puts the message back in the queue. The broker also marks it `redelivered`.

Notice what this buys and what it costs.

- **You get no lost messages.** A crashed worker only delays its message.
- **You pay with duplicates.** Worker 1 may have done part of the job. A slow job that outlives the timeout gets handed to a second worker while the first still runs. SQS has two kinds of queue. A **standard** queue is the fast kind, with no order promise. It says so directly: delivery is **at least once**, so design consumers to be idempotent. Idempotent means that running the same job twice has the same result as running it once.

The fix is lesson 3.4 again. Make the job safe to run twice. For a thumbnail, write the output to a key built from the photo id. A second run then overwrites the same file.

A timeout that is too short hands a slow job to a second worker, so you get duplicate work. A timeout that is too long makes a crashed worker's message wait before anyone retries it. Pick a value above your slowest normal job.

## Numbers

| Fact | Value | Source |
|---|---|---|
| SQS default visibility timeout | 30 s (range 0 s to 12 hours) | SQS docs |
| SQS default retention (how long an unread message is kept) | 4 days (range 60 s to 14 days) | SQS docs |
| SQS maximum message size | 1 MiB (1,048,576 bytes). Larger payloads go to S3 (Amazon's file storage service), with a pointer in the message. | SQS quotas page |
| SQS messages per batch request | 10 | SQS quotas page |
| SQS standard queue, in-flight messages (received but not yet deleted) | about 120,000 | SQS docs |
| SQS FIFO queue, per partition (one slice of the queue) | 300 API calls per second per action, or 3,000 messages per second with batching | SQS quotas page |
| RabbitMQ prefetch | 100 to 300 usually gives good throughput | RabbitMQ docs |

Prefetch is how many unacknowledged messages a RabbitMQ consumer may hold at once. A high value keeps workers busy. It can also leave one worker holding many messages while others sit idle.

Store the payload by reference when it is big. A message with an S3 key and a few ids is cheap. A 1 MiB message ties up the queue for every retry.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Queue between caller and work | Fast response. Bursts absorbed. Workers fail safely. | The result is not ready on return. You need a way to report status. Duplicates are possible. | Slow or spiky work the user does not need to wait for |
| Synchronous call | Simple. Result in hand. | Caller waits. Spikes hit the workers directly. | Fast work and light load |
| Standard queue (SQS) | Very high throughput | No order guarantee. Duplicates. | Independent jobs |
| FIFO queue (first in, first out) | Order within a group. 5 minute dedupe, meaning it drops a repeat of the same message (lesson 6.3). | Lower throughput | Jobs that must run in order |
| Short visibility timeout | Fast recovery | Duplicates for slow jobs | Short, idempotent jobs |
| Long visibility timeout | Few duplicates | Slow recovery after a crash | Long jobs. Or extend the timeout while working. |

## Interview lens

<Callout type="tip">
Say what the queue is for: "I put a queue between the API and the resize workers. The API returns right away. The queue absorbs the burst and workers drain it at a steady rate. I size workers for the average, and alert on queue age, not queue size." Then name the guarantee: "Delivery is at least once, so the job is idempotent."
</Callout>

<Callout type="mistake">
Do not say "the queue makes the system faster". It makes the **caller** faster. Total work is the same. Do not say "SQS delivers exactly once". Standard queues are at least once. Do not say "delete the message first so we never process twice". A crash after the delete loses the job. And do not forget the user. If the work finishes later, say how the user finds out (polling, a push, or an email).
</Callout>
