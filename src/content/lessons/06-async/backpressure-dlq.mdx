## The problem

Lesson 6.1 said a queue hides a spike. It did not say what happens when the spike never ends. During a sale, orders arrive a little faster than the workers can finish them. Nothing crashes. The queue just grows by a few messages every second. After an hour, the backlog is huge. A new order waits at the back of it, many minutes, before a worker sees it.

The difference between how fast messages arrive and how fast they are handled is called **lag**. Consumer lag is how far behind the newest message the consumer is. Lag shows up as a wait. Users see "my order is stuck". The queue itself looks healthy.

A second problem hides in the same system. One message is broken. Every attempt to process it fails. The worker retries it again and again, and the line behind it stops moving.

This lesson covers both topics. It covers what to do when the queue grows, and what to do with a message that never succeeds.

## When the line grows

You have five levers. Each moves the pain to a different place.

1. **Add consumers.** This works if you have spare partitions or workers, and the downstream system can take the load. It costs money and has a limit (lesson 6.2: a partition is one lane of a log, and only one worker in a group reads a lane, so the lane count caps the group).
2. **Slow the producers.** This is **backpressure**: the slow stage pushes the slowness back toward the source. Think of a sink with a slow drain. If you keep pouring, it overflows. If the sink could tell the tap to ease off, it would not. The queue plays the sink, and the producers are the tap. Without it, a slow stage fills every buffer behind it until something runs out of memory or the wait becomes huge. In practice, an API can return `429 Too Many Requests`, which is the standard HTTP answer for "too many calls, slow down". The caller then waits and tries later. Lesson 7.4 covers rate limiting.
3. **Bound the queue and block.** The queue has a size limit. When it is full, producers are held back or rejected. Nothing is lost, but callers wait or see errors.
4. **Bound the queue and drop.** When the queue is full, throw something away: the newest message or the oldest. Nothing blocks. Data is lost.
5. **Limit what a worker holds.** This is **prefetch**. RabbitMQ is a popular queue server. Its consumer may hold only a set number of unacknowledged messages. A message is unacknowledged while the worker has received it but has not yet told the queue that it finished. The docs say values of 100 to 300 "usually offer good throughput". A value of 1 is the most conservative. Zero means no limit. A high prefetch leaves one worker with many messages while another sits idle.

RabbitMQ offers both bounded modes. A queue with a length limit has an `overflow` setting. With `drop-head`, the default, it removes messages from the front. With `reject-publish`, it refuses new ones. When publisher confirms are on (a setting where the queue answers each publish with "got it" or "refused"), the publisher gets a `basic.nack`, which means "negative acknowledgement", for a refused message and can react.

Try the three policies on the same burst. The queue limit is 200 messages. Workers do 50 per second. Producers send 30 per second, then 300 per second for 20 seconds.

Compare the three runs:

| Policy | Peak queue | Worst wait | Lost messages | Who feels it |
|---|---|---|---|---|
| No limit | grows to thousands | long, and still growing | 0 | Every user waits |
| Block | stays at the limit | short and bounded | 0 | Producers wait. Their callers feel it. |
| Drop | stays at the limit | short and bounded | thousands | Dropped users lose data |

In the block run, the producers hold the extra messages while the queue stays at its limit. The work still gets done, just later. Choose by asking what the work is worth. Dropping a "like" event is fine. Dropping a payment is not. Blocking protects the data and moves the wait upstream. That only helps if the upstream can wait or can tell its own callers "try later".

Also watch the right signal. **Queue age** (how old the oldest message is) tells you the user wait. Queue size alone does not. SQS is Amazon's managed queue service. It reports `ApproximateAgeOfOldestMessage` for this. Autoscale workers and alert on age.

## The message that never succeeds

Most failures are **transient**: a timeout, a lock, a brief outage. A retry fixes them. Some failures are **permanent**: a malformed payload, a missing record, a bug on one input. A retry never fixes them. A message that always fails is a **poison message**.

The naive design retries forever. It fails in two ways. The poison message burns worker time on every attempt. And in an ordered queue, or in one partition of a log, it sits at the front. Nothing behind it moves, and lag climbs.

The standard fix is a **dead-letter queue** (DLQ): a second queue for messages that failed too many times. The main queue counts how often a message was received. At a limit, it moves the message to the DLQ. SQS calls the limit `maxReceiveCount`.

One more word helps for the diagram below: the **visibility timeout**. When a worker receives a message, the queue hides it from other workers for a set time. If the worker deletes the message in that time, the work is done. If not, the message becomes visible again and a worker receives it a second time. Each receive adds one to the count.

Rules from the SQS docs worth remembering:

- A DLQ must live in the same AWS account and the same Region (a Region is one geographic AWS location, such as Frankfurt) as the source queue. Create it first.
- **Set DLQ retention longer than source retention.** For a standard queue (the default SQS type, which does not promise strict order), the enqueue time (the moment the message first entered a queue) does not change when a message moves. A message that waited 1 day in the source queue, with a 4 day DLQ retention, is deleted from the DLQ after 3 more days, not 4.
- A low `maxReceiveCount` such as 1 means a single failure sends the message to the DLQ. Set it high enough to allow for real retries.
- With a standard queue and `maxReceiveCount` above 3, a message received 3 or more times without a delete moves to the back of the queue.
- Do not use a DLQ with a FIFO queue (a queue type that keeps strict first-in, first-out order) if you need exact order. The message leaves the sequence.
- **Redrive** moves messages from the DLQ back to a source queue, after you fix the cause.

RabbitMQ has the same idea. A `basic.nack` or `basic.reject` with `requeue=false` sends the message to a dead-letter exchange (RabbitMQ's name for the routing point that decides which queue gets the message), or discards it if none is set. Requeueing in a tight loop wastes resources. Quorum queues (a RabbitMQ queue type that copies its data to several servers) have a delivery limit, 20 by default since RabbitMQ 4.0, after which the message is dropped or dead-lettered.

A log does not count receives for you. RabbitMQ streams have no dead-letter exchange. In a log, your consumer code must set the bad record aside, for example by writing it to another topic, so the offset (the reader's bookmark position in the log) can move on.

A DLQ is **not** the fix. It keeps a bad message safe and out of the way. A person still has to read it, find the cause, and fix it. So put an **alarm** on the DLQ. A DLQ that fills in silence is a bug that nobody sees.

## Numbers

| Fact | Value | Source |
|---|---|---|
| SQS `maxReceiveCount` back-of-queue move | received 3 or more times, when the limit is above 3 | SQS DLQ docs |
| SQS in-flight messages, standard queue | about 120,000 | SQS docs |
| RabbitMQ prefetch for good throughput | 100 to 300 | RabbitMQ docs |
| RabbitMQ quorum queue prefetch cap | 2,000 | RabbitMQ docs |
| RabbitMQ quorum queue delivery limit, default | 20 (4.0 and later) | RabbitMQ docs |
| DLQ monitoring metric (SQS) | `ApproximateAgeOfOldestMessage` | SQS DLQ docs |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Unbounded queue | No loss, no producer blocking | Wait grows without limit. Storage grows. | Short bursts you can drain, with alerts |
| Block producers | No loss | Latency moves upstream | Data must not be lost |
| Drop messages | Fast, bounded | Data loss | Data that is cheap or replaceable |
| Low `maxReceiveCount` | Poison messages leave fast | Transient errors reach the DLQ | Failures are usually permanent |
| High `maxReceiveCount` | Rides out transient errors | Poison messages waste many attempts and are found later | Dependencies are flaky |
| High prefetch | Throughput | Uneven work across consumers | Short, equal jobs |
| Low prefetch | Even spread | More round trips | Long or very uneven jobs |

## Interview lens

<Callout type="tip">
Name the signal and the policy. "I alert on the age of the oldest message, not the depth. If the queue passes its limit, producers get a 429 and retry with backoff. Workers retry a message up to 5 times. After that it goes to a DLQ with an alarm, and we redrive after a fix." That one answer covers lag, backpressure, and poison messages.
</Callout>

<Callout type="mistake">
Do not say "the queue will absorb it" without saying what happens if the load stays high. Do not say "retry until it works". A poison message never works. Do not call the DLQ the fix: it only stores the problem. And do not set the DLQ retention shorter than the source queue. The old messages vanish from the DLQ almost at once.
</Callout>
