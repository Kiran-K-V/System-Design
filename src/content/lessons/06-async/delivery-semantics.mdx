## The problem

A payment system sends "credit $10" through a **broker**. A broker is the server in the middle that stores messages and hands them to programs (the **consumers**) that act on them (the [Queues](/learn/backend/06-async/queues/) lesson). Someone asks: "Is delivery exactly-once?" The honest answer is "it depends on which step you mean."

A message travels through three steps. Each can fail alone.

1. **Producer to broker.** The producer sends. The broker stores it and replies with an **ack**. An ack (short for acknowledgement) is a small reply that means "I got it". The ack can be lost.
2. **Broker to consumer.** The broker hands the message to a consumer. The consumer can crash.
3. **Consumer to its effect.** The consumer changes a database, sends an email, or calls an API.

In every step, one side acts and the other side cannot see whether it worked. That uncertainty is the whole topic.

## Three guarantees

**Kafka** is a broker that keeps messages in an append-only log (the [Pub/Sub and Logs](/learn/backend/06-async/pubsub-logs/) lesson). Its docs define the three guarantees in one line each.

| Guarantee | Meaning | Risk |
|---|---|---|
| **At-most-once** | Messages may be lost but are never redelivered | Loss |
| **At-least-once** | Messages are never lost but may be redelivered | Duplicates |
| **Exactly-once** | Each message is processed once and only once | Hard. See below. |

Kafka's default is at-least-once. SQS standard queues are at-least-once too. SQS is the Amazon queue service from the [Queues](/learn/backend/06-async/queues/) lesson.

Why can you not just have both? Because of one fact. When a sender gets no ack, it cannot tell **"the message was lost"** from the other case. The other case is **"the message arrived and the ack was lost"**. There are two choices. Send again, and risk a duplicate. Do not send again, and risk a loss. No third option exists inside one unreliable link.

Watch the second case happen. The consumer does everything right, and the money still moves twice.

## The producer hop: idempotent producers

A producer that resends after a lost ack creates a duplicate record in the log. Kafka fixes this inside the broker. The broker gives each producer an ID. The producer sends a **sequence number** with every message. The broker uses that number to drop a resend it has already stored.

This is on by default now: `enable.idempotence` defaults to `true`. "Idempotent" means a repeat has the same result as one run. The setting needs `acks=all`. The `acks` setting says how many broker copies must hold a message before the broker sends the ack. With `all`, every in-sync copy (a replica, the copies that keep the data safe if one machine dies) must have it. The setting also needs `retries` above 0 (the default is 2,147,483,647). Retries is how many times the producer resends after a failure. It also needs `max.in.flight.requests.per.connection` of at most 5, which caps how many sends can wait for an ack at once. The producer's `delivery.timeout.ms` bounds the retrying, with a default of 2 minutes.

The limit matters. The idempotent producer only removes duplicates from **its own internal retries**. The Kafka docs say an application that sends the same data again by hand cannot be de-duplicated. A new send has a new sequence number.

**RabbitMQ** is a broker that you run yourself. It has a similar step on the producer side: publisher confirms. A confirm is RabbitMQ's name for the ack to the producer. A persistent message (saved to disk) in a durable queue (one that survives a restart) is confirmed after it reaches disk. Without confirms, a crash before the disk write can lose the message. RabbitMQ also has transactions (a group of steps that all happen or none do), but the docs say they reduce throughput by a factor of 250.

## The consumer hop: when do you ack?

The consumer has two jobs after it receives a message: **process** it and **ack** it. The order matters. Pick a rule, pick a crash point, and read the result. "Dedupe" in the diagram is short for de-duplicate: the consumer spots a message it has already handled and skips it. The next sections show how.

<AsyncCrashMatrix client:visible />

Read the table in three lines.

- **Ack first** can lose work. If the consumer dies after the ack and before the work, the broker thinks it is done. That is at-most-once.
- **Work first** can repeat work. If the consumer dies after the work and before the ack, the broker sends it again. That is at-least-once.
- **Work first, plus dedupe**, is safe at both points.

For anything that must not be lost, pick work first and fix the duplicates.

## Exactly-once effects: dedupe at the consumer

True exactly-once delivery over a network is not on offer. What you can get is **exactly-once effect**: the message may arrive twice, but the change happens once. The recipe is an **idempotent consumer**, from the [Idempotency](/learn/backend/03-api-design/idempotency/) lesson.

Give every message a unique id. The consumer keeps a table of processed ids. Before it acts, it checks the table. The check and the effect must be in **one database transaction** (the [Transactions and Isolation](/learn/backend/04-data/transactions/) lesson). A transaction is a group of database changes that all succeed or all fail together, like a bank transfer that cannot take money out without putting it in. Then a crash can never leave one without the other.

<AsyncAckWalk mode="dedupe" client:visible />

If the id is saved in a different system from the effect, you rebuild the gap. Save the id first and crash, and the work is lost. Do the work first and crash, and the work repeats.

A dedupe table grows. Keep each id at least as long as the longest time a redelivery can arrive. Then expire it.

<Callout type="deep" title="What Kafka transactions give you">
Kafka can make "read, process, write" exactly-once **inside Kafka**. A transactional producer writes the output records and the consumer's offsets in one transaction. An offset is the consumer's bookmark: the position of the last message it has read. The consumer reads with `isolation.level=read_committed`, so it sees only transactions that finished, and it sets `enable.auto.commit=false`, so Kafka does not save its bookmark on its own. A transaction that stays open too long is cancelled by the coordinator (a Kafka server that tracks transactions): `transaction.timeout.ms` defaults to 1 minute. Kafka's own docs add the limit: for other destination systems, exactly-once "generally requires cooperation with such systems". If your consumer writes to a database such as Postgres or calls an API, Kafka transactions do not cover that write. Use a dedupe table or an idempotency key there.
</Callout>

## What the platforms offer

| System | What it gives | Limit |
|---|---|---|
| Kafka idempotent producer | No duplicates from producer retries | Not for resends by your own code |
| Kafka transactions | Atomic read-process-write inside Kafka | Kafka to Kafka only |
| SQS standard | At-least-once, high throughput | Duplicates, no order |
| SQS FIFO (first in, first out queue) | No duplicate sends inside a 5 minute deduplication interval. It uses a deduplication id, or a fingerprint (a SHA-256 hash) of the message body with content-based deduplication. | A repeat after 5 minutes is a new message |
| RabbitMQ | Publisher confirms. Quorum queues (queues copied across several servers) confirm after the copies accept. A delivery limit (20 by default since 4.0) stops endless redelivery. | Confirms add latency. Transactions are far slower. |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| At-most-once | Lowest latency. No duplicates. | Lost messages | Metrics, logs, anything where a gap is fine |
| At-least-once, no dedupe | Nothing is lost | Duplicates reach the effect | The effect is naturally idempotent, like "set price to 9" |
| At-least-once + idempotent consumer | Safe, correct effects | A dedupe table and a transaction per message | Payments, orders, ledgers |
| Kafka transactions | Atomic inside Kafka | Latency and throughput | Stream processing from topic to topic |
| `acks=all` (wait for every in-sync copy) | No loss from one broker failure | Slower writes | Almost always |
| `acks=1` (wait for the leader copy only) | Faster writes | A leader crash can lose data | Rarely. Only when loss is cheap. |

## Interview lens

<Callout type="tip">
Say: "The network gives at-least-once at best. I get exactly-once effects with an idempotent consumer. Every event has a unique id, and the consumer saves the id in the same transaction as the change." Then show you know the edge: "Kafka transactions cover Kafka to Kafka. Writes to an outside system need the dedupe table."
</Callout>

<Callout type="mistake">
Do not say "we use Kafka, so it is exactly-once". Say what is exactly-once and over which hops. Do not say "the idempotent producer removes all duplicates". It only covers its own retries. Do not ack before processing and then claim no loss. And do not put the dedupe check in a different store from the effect, with no transaction between them.
</Callout>
