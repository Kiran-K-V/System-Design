## What it is

Apache Cassandra is a wide-column, distributed, peer-to-peer database. It is built for a high write rate and horizontal scale. "Peer-to-peer" means no node is special. There is no leader and no single master. Any node can take any request.

It is the working example of ideas you have already seen. Its storage is the log-structured design from [lesson 4.2](/learn/04-data/storage-engines). Its placement is [consistent hashing](/learn/04-data/consistent-hashing). Its consistency is the quorum rule from [lesson 4.11](/learn/04-data/consensus), which you set per request ([lesson 4.10](/learn/04-data/consistency-models)).

## The internal model

### The ring: who owns which key

Cassandra hashes the **partition key** of each row into a token. The tokens form a ring. Each node owns ranges of the ring. A row belongs to the node that owns its token, and to the next nodes around the ring up to the replication factor. **Replication factor** (RF) is how many copies of each row exist. Cassandra's dynamo design page says nodes use **virtual nodes**, so each machine owns many small ranges and the load spreads evenly. Replication settings are set per keyspace, and the docs advise NetworkTopologyStrategy for production.

There is no central place that holds the ring map. Every node runs the **gossip** task by itself, on a timer. Gossip passes membership, token ownership, and schema versions between nodes. The docs show a gossip round about once per second. One detail worth knowing: whether a peer is UP or DOWN is a local decision of each node. It is not passed around by gossip.

### The data model: partition key and clustering columns

A table's primary key has two parts.

- The **partition key** picks the node and groups rows into a partition. The docs say only an equality is allowed on a partition key.
- The **clustering columns** order rows inside a partition. Range queries on them must ask for a contiguous set of rows.

```sql
CREATE TABLE readings_by_sensor (
  sensor_id  uuid,
  read_at    timestamp,
  value      double,
  PRIMARY KEY ((sensor_id), read_at)
) WITH CLUSTERING ORDER BY (read_at DESC);
```

Here `sensor_id` is the partition key and `read_at` is a clustering column. "Latest 100 readings for sensor X" reads one partition from its start. "All readings above 50 across all sensors" has no partition key, so it is not a query this table supports. DataStax's guide puts it this way: the partition key decides which node stores the data, and by default a query must use the whole partition key in its `WHERE` clause. So you model a table for each query you plan to run, and you copy data ([lesson 4.1](/learn/04-data/data-modeling)). This is the price of a ring with no coordinator that knows where everything is.

### The write path

A write needs only a sequential disk append and a memory insert. Step through one replica.

<CassWritePath client:visible />

The three parts, from the Cassandra storage docs:

1. The **commit log** gets every write first. It is only for crash recovery.
2. The **memtable** is an in-memory structure that "stores writes in sorted order until reaching a configurable limit".
3. A **flush** writes the memtable to an **SSTable**. "SSTables are immutable, and never written to again after the memtable is flushed."

Then **compaction**: "Cassandra triggers compactions which combine multiple SSTables into one." It costs I/O because it rewrites data. The reward is fewer files per read. A delete is also a write, a marker called a tombstone, since files cannot be edited.

Reads may touch the memtable and several SSTables. That is why reads are costlier than writes here, and why compaction matters.

### Tunable consistency

With RF = 3, each write goes to three replicas. How many must answer before the coordinator replies? The Cassandra docs list the consistency levels. Three of them:

| Level | Meaning |
|---|---|
| `ONE` | "Only a single replica must respond." |
| `QUORUM` | "A majority (n/2 + 1) of the replicas must respond." |
| `ALL` | "All of the replicas must respond." |

`LOCAL_QUORUM` is a majority of the replicas in the coordinator's own data center. The docs give the overlap rule as `W + R > RF`, where W and R are the write and read levels. That is the quorum rule of lesson 4.11. Watch what happens at `ONE`, then at `QUORUM`.

<CassConsistency client:visible />

At `ONE`/`ONE`, W + R = 2 is not more than 3, so a read can miss a write. At `QUORUM`/`QUORUM`, W + R = 4 is more than 3, so a read always meets a replica that took the latest completed write. Cassandra is, in the docs' words, an "eventually consistent storage system". You buy stronger reads with latency and with availability. Try the calculator. Pick the Cassandra presets.

Cassandra also has **lightweight transactions** for compare-and-set, built on Paxos. They need more round trips, so use them for rare cases such as "create this username only if it does not exist", not for every write.

## When to use it

- A very high write rate that you can spread over many partition keys: events, messages, sensor readings, feeds.
- Data you read by key, with known query shapes, plus a range inside one partition (latest N by time).
- You need no single leader and no single point of failure, including across data centers.
- You accept eventual consistency, or you pay for stronger levels per request.

## When not to

| Situation | Why | Look at |
|---|---|---|
| Ad-hoc queries, joins, or reports | You can query only by partition key and clustering order | [PostgreSQL](/learn/08-technologies/postgresql) or a warehouse |
| Multi-row transactions with strong isolation | Only per-partition and lightweight transactions | [PostgreSQL](/learn/08-technologies/postgresql) |
| Small data on one machine | A ring has operational weight you do not need | [PostgreSQL](/learn/08-technologies/postgresql) |
| Full-text relevance search | No inverted index with scoring | [Elasticsearch](/learn/08-technologies/elasticsearch) |
| You want a fully managed key-value store | You run and tune the cluster | [DynamoDB](/learn/08-technologies/dynamodb) |

## Limits and numbers

| Fact | Value | Source |
|---|---|---|
| Quorum size | n/2 + 1 replicas, rounded down | Cassandra docs, Dynamo page |
| Overlap rule | W + R > RF | Cassandra docs, Dynamo page |
| Gossip round | about once per second | Cassandra docs, Dynamo page |
| Partition key in a query | equality only | Cassandra docs, CQL DML |
| Partition size guidance | ideally under 100 MB | DataStax docs (vendor guidance, not a hard limit) |

Partition size has no hard limit in the Apache docs we could read. The 100 MB figure is DataStax's recommendation, and other guides repeat it with different ceilings. Treat it as a design target: bound a partition's growth in the schema, for example by adding a time bucket to the partition key. The docs we read give no default replication factor, so say "RF = 3 is the common choice" as your own design choice, not as a default.

## Interview lens

<Callout type="tip">
Lead with the access pattern: "Messages are read by conversation, newest first. Partition key is the conversation, clustering column is time, descending. Writes are commit log plus memtable, so they are fast." Then state the knob: "RF = 3 with QUORUM reads and writes, so W + R = 4 > 3, and I survive one replica failing."
</Callout>

<Callout type="mistake">
Do not say Cassandra is strongly consistent by default. It is eventually consistent unless you raise the level. Do not say a write goes straight to an SSTable. It goes to the commit log and memtable first. Do not say you can update an SSTable in place. And do not pick a partition key that makes one partition grow without bound, such as a constant or a very popular ID.
</Callout>

<Callout type="deep" title="Why QUORUM tolerates one down node but ALL does not">
With RF = 3, QUORUM needs 2 acks, so one replica can be down and writes still pass. ALL needs 3, so one dead replica blocks every request for the partitions it holds. You trade availability for the strongest single-request view. The same pattern appears in [CAP and PACELC](/learn/04-data/cap-pacelc): when a replica is unreachable, you pick between answering and being sure.
</Callout>
