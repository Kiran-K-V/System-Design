## What it is

PostgreSQL is an open-source relational database. You describe data as tables with typed columns, and you ask questions in SQL. It gives you transactions with ACID guarantees, joins, constraints, and many index types.

In an interview, PostgreSQL is the safe default. If the data is relational and one primary machine can carry the writes, say "PostgreSQL" and move on. This lesson shows why it is a good default and where the default stops. Everything here builds on three earlier lessons: [how a database stores data](/learn/04-data/storage-engines), [indexing](/learn/04-data/indexing), and [transactions and isolation](/learn/04-data/transactions).

## The internal model

### Rows live in pages, and an update makes a new row version

PostgreSQL stores a table in a **heap**: a set of 8 KB pages ([lesson 4.2](/learn/04-data/storage-engines)). A **row version**, also called a tuple, is one stored state of a row. Every `UPDATE` creates a new row version for the same logical row. The old version stays in the page for now.

Each row version carries two hidden columns. According to the PostgreSQL docs, `xmin` is the ID of the inserting transaction. `xmax` is the ID of the deleting transaction, or zero for a row version that nobody has deleted. A row version where `xmax` is not zero may still be visible. That usually means the deleting transaction has not committed yet, or it rolled back.

### MVCC: readers never wait for writers

This is **multi-version concurrency control** (MVCC): keep several versions of a row, and let each query see a consistent one. The PostgreSQL docs say each statement sees a snapshot of the data "as it was some time ago, regardless of the current state of the underlying data". They also say the locks for reading "do not conflict with locks acquired for writing data, and so reading never blocks writing and writing never blocks reading". MVCC removes read-write blocking only. Two writers on the same row still queue. A hot row is still a hot row.

The cost of MVCC is **dead row versions**. A version becomes dead when no transaction can see it any more. They take space until something removes them.

### VACUUM cleans up dead versions

The docs give four jobs for vacuuming: recover or reuse space used by updated or deleted rows, update planner statistics, update the visibility map (which speeds up index-only scans), and protect against transaction ID wraparound. The standard `VACUUM` "removes dead row versions in tables and indexes and marks the space available for future reuse". It does not return the space to the operating system, except when pages at the end of the table become completely free. `VACUUM FULL` compacts the table and does return space, but it takes an `ACCESS EXCLUSIVE` lock, so nobody can read or write the table meanwhile.

You rarely run VACUUM by hand. **Autovacuum** runs it in the background. Your job is to keep it able to finish. The usual blocker is a transaction that stays open for hours, because VACUUM cannot remove a version that an open snapshot may still read.

Transaction IDs are a fixed-size counter. The docs say every table must be vacuumed "at least once every two billion transactions" to avoid wraparound. The setting `autovacuum_freeze_max_age` defaults to 200 million.

### The write-ahead log

PostgreSQL follows the rule from lesson 4.2: write the log before the page. Changes go to the **write-ahead log** (WAL) first. The docs say that "only the WAL file needs to be flushed to disk to guarantee that a transaction is committed". Data pages can be written later. After a crash, PostgreSQL replays the WAL (REDO) to rebuild the pages. The same log supports point-in-time recovery and replication.

### Indexes

The default is B-tree: `CREATE INDEX` makes one unless you ask for another. The other built-in types fit special queries ([lesson 4.3](/learn/04-data/indexing)).

| Type | Good for |
|---|---|
| B-tree | Equality and range queries, sorting. The default. |
| Hash | Equality only |
| GIN | Values that hold many items, such as arrays |
| GiST, SP-GiST | Geometric and other custom search types |
| BRIN | Huge tables where values correlate with physical order. Stores a min and max per block range. |

### Replication

A **standby** is a second PostgreSQL server that replays the primary's WAL. This is streaming replication. It is asynchronous by default. With synchronous settings, a commit waits until the standby confirms. The docs say the minimum wait time is "the round-trip time between primary and standby". That is the trade-off from [lesson 4.6](/learn/04-data/replication), now with PostgreSQL labels. Step through it again and watch the crash.

### One process per connection

Each client connection is a server process. The default `max_connections` is typically 100. A process costs memory and scheduling time. So 5,000 mostly idle connections is a poor design, and raising the limit to 10,000 is not the fix.

The fix is a **connection pooler** such as PgBouncer. Many clients talk to the pooler, and the pooler shares a few server connections among them.

<PgPooler />

PgBouncer has three modes: session, transaction, and statement. In transaction mode a server connection is lent out only for the length of one transaction. That gives the best sharing. The cost: per the PgBouncer docs, transaction mode "breaks a few session-based features". Examples are `LISTEN`, `PREPARE`, and session-level advisory locks.

## When to use it

- You have relational data with relationships between entities, and you need joins, constraints, and multi-row transactions.
- One primary can carry the write rate. Add read replicas for read-heavy load ([lesson 4.6](/learn/04-data/replication)).
- You do not know all the queries up front. SQL and secondary indexes handle new questions without a redesign.
- You want strong guarantees by default. The default isolation level is Read Committed. Repeatable Read prevents phantoms in PostgreSQL. Serializable prevents all the listed anomalies. Read Uncommitted is accepted but behaves as Read Committed.

## When not to

| Situation | Why PostgreSQL strains | Look at |
|---|---|---|
| Write rate beyond one primary | All writes go to one leader. Sharding is your job ([lesson 4.7](/learn/04-data/sharding)). | [Cassandra](/learn/08-technologies/cassandra) or [DynamoDB](/learn/08-technologies/dynamodb) |
| Key-value access at huge scale with fixed query shapes | You pay for SQL features you do not use | [DynamoDB](/learn/08-technologies/dynamodb) |
| Ranked full-text search with filters over a large corpus | Search engines build and score inverted indexes for this | [Elasticsearch](/learn/08-technologies/elasticsearch) |
| Sub-millisecond lookups of hot data | Every query goes through a process, a parser, and disk-backed pages | [Redis](/learn/08-technologies/redis) as a cache |

## Limits that matter

| Limit | Value | Source |
|---|---|---|
| Default `max_connections` | typically 100 | PostgreSQL docs, connection settings |
| Maximum field size | 1 GB | PostgreSQL docs, limits |
| Maximum table size | 32 TB (with the default 8 KB block size) | PostgreSQL docs, limits |
| Maximum columns per table | 1,600 | PostgreSQL docs, limits |
| Database size | unlimited | PostgreSQL docs, limits |
| Vacuum every table at least once per | 2 billion transactions | PostgreSQL docs, routine vacuuming |
| `autovacuum_freeze_max_age` default | 200 million | PostgreSQL docs, routine vacuuming |

A row version must fit in one 8 KB heap page. Large values are moved out of the page and stored separately (TOAST). The docs do not give one single "maximum row size" number, so do not quote one.

## Interview lens

<Callout type="tip">
Name the reason, not just the product: "Orders and payments need multi-row transactions and constraints, so PostgreSQL. One primary plus read replicas covers the load at this scale. If writes outgrow one primary, I would shard by user ID." Then name the operational cost: "Connections are processes, so I will put PgBouncer in front, and I will watch long transactions because they block VACUUM."
</Callout>

<Callout type="mistake">
Do not say "readers take row locks, so reads block writes". Under MVCC they do not. Do not say the default isolation level is Serializable. It is Read Committed. Do not fix "too many connections" by raising `max_connections` to a large number. And do not say a standby is always up to date: replication is asynchronous unless you turn on synchronous commit, and then every commit pays a round trip.
</Callout>

<Callout type="deep" title="Why a hot UPDATE makes bloat">
A counter row updated 1,000 times leaves 1,000 dead versions behind the live one, until VACUUM can remove them. If the row is updated faster than VACUUM can clean up, or an old transaction holds the horizon back, the table and its indexes grow while the row count stays at one. A common fix is to avoid hot rows: append events and sum them, or keep the counter in Redis and write it back in batches.
</Callout>
