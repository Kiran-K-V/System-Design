## What it is

PostgreSQL is an open-source relational database. You describe data as tables with typed columns, and you ask questions in SQL. It gives you transactions with ACID guarantees, joins, constraints, and many index types. A **transaction** is a group of changes that succeed or fail together. **ACID** is the name for the safety promises a transaction makes: all of it happens or none of it, the data stays valid, transactions do not trip over each other, and a committed change survives a crash. A **join** combines rows from two tables. A **constraint** is a rule the database enforces, such as "this column is never empty".

In an interview, PostgreSQL is the safe default. If the data is relational and one primary machine can carry the writes, say "PostgreSQL" and move on. This lesson shows why it is a good default and where the default stops. Everything here builds on three earlier lessons: [how a database stores data](/learn/backend/04-data/storage-engines), [indexing](/learn/backend/04-data/indexing), and [transactions and isolation](/learn/backend/04-data/transactions).

One of PostgreSQL's limits is easy to miss until it stops you. In 2015 it stopped Sentry for most of a working day. [The story](#incident) is in the VACUUM section.

## The internal model

### Rows live in pages, and an update makes a new row version

PostgreSQL stores a table in a **heap**: a pile of fixed-size 8 KB blocks called pages, with rows in no special order ([the How a Database Stores Data lesson](/learn/backend/04-data/storage-engines/)). A **row version**, also called a tuple, is one stored state of a row. Every `UPDATE` creates a new row version for the same logical row. The old version stays in the page for now.

Each row version carries two hidden columns. According to the PostgreSQL docs, `xmin` is the ID of the inserting transaction. `xmax` is the ID of the deleting transaction, or zero for a row version that nobody has deleted. A row version where `xmax` is not zero may still be visible. That usually means the deleting transaction has not committed yet, or it rolled back.

### MVCC: readers never wait for writers

This is **multi-version concurrency control** (MVCC): keep several versions of a row, and let each query see a consistent one. The PostgreSQL docs say each statement sees a snapshot of the data "as it was some time ago, regardless of the current state of the underlying data". They also say the locks for reading "do not conflict with locks acquired for writing data, and so reading never blocks writing and writing never blocks reading". The [Transactions and Isolation](/learn/backend/04-data/transactions/) lesson compared this with locking. A **lock** is a flag that makes other users wait. A **snapshot** is a note of which transactions had committed when a query started. The query uses the note to decide which row versions it may see. The diagram also shows VACUUM, the cleanup job covered in the next section. Now watch the row versions themselves.

MVCC removes read-write blocking only. Two writers on the same row still queue. A hot row is still a hot row.

The cost of MVCC is **dead row versions**. A version becomes dead when no transaction can see it any more. They take space until something removes them.

### VACUUM cleans up dead versions

**VACUUM** is the cleanup job. The docs give four reasons for it. It recovers or reuses space used by updated or deleted rows. It refreshes the row-count statistics that the query planner uses to pick a fast plan. It updates a small map of pages that have no dead rows, which lets some queries skip reading the table. And it protects against transaction ID wraparound, explained below. The standard `VACUUM` "removes dead row versions in tables and indexes and marks the space available for future reuse". It does not return the space to the operating system, except when pages at the end of the table become completely free. `VACUUM FULL` compacts the table and does return space. But it takes the strictest lock (`ACCESS EXCLUSIVE`), so nobody can read or write the table meanwhile.

You rarely run VACUUM by hand. **Autovacuum** runs it in the background. Your job is to keep it able to finish. The usual blocker is a transaction that stays open for hours. The reason is that VACUUM cannot remove a version that an open snapshot may still read.

Transaction IDs are a fixed-size counter, like a car odometer. When it runs out of numbers it wraps around, and old rows would look like they are from the future. That is **wraparound**, and it makes data invisible. VACUUM prevents it by marking old rows as safe. The docs say every table must be vacuumed "at least once every two billion transactions" to avoid wraparound. The setting `autovacuum_freeze_max_age` defaults to 200 million.

Sentry is an error-tracking service. It writes a lot, and it runs on PostgreSQL with some very large tables. The team knew about wraparound and had tuned autovacuum to avoid it.

1. Autovacuum fell behind. The transaction ID counter got close to its limit. PostgreSQL did what it is built to do. It "will stop accepting commands when there are fewer than one million transactions left", in Sentry's words.
2. The only way out without data loss is to stop writes and vacuum. The site ran read-only from replicas. Incoming events piled up in queues and Redis buffers, so the team flushed that backlog.
3. The team let the running autovacuums finish, because a restart could make the outage longer. After nearly 3 hours, writes were still blocked.
4. One huge table was still unfinished. It mapped events to their rollups and was not critical. The team truncated it (emptied it in one step). Five minutes later the system was fully restored.

</IncidentCard>

Note what PostgreSQL chose. It refused writes rather than let old rows look like the future. That hard stop is the safe failure. Your job is to never reach it.

### The write-ahead log

PostgreSQL follows the rule from the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson: write the log before the page. Changes go to the **write-ahead log** (WAL) first. The WAL is an append-only file on disk, like a ship's logbook: you write the entry before you do the work. The docs say that "only the WAL file needs to be flushed to disk to guarantee that a transaction is committed". Data pages can be written later. After a crash, PostgreSQL replays the WAL from the last safe point to rebuild the pages. The same log supports point-in-time recovery (restore a backup, then replay the log up to a chosen minute) and replication.

### Indexes

The default is B-tree: `CREATE INDEX` makes one unless you ask for another. The other built-in types fit special queries ([the Indexing lesson](/learn/backend/04-data/indexing/)).

| Type | Good for |
|---|---|
| B-tree | Equality and range queries, sorting. The default. |
| Hash | Equality only |
| GIN | Values that hold many items, such as arrays or words in a text. Maps each item to the rows that hold it. |
| GiST, SP-GiST | Shapes, map points, and other custom search types such as "nearest to here" |
| BRIN | Huge tables where values grow in step with the order rows were written, such as a timestamp. Stores only a min and max per group of pages, so it is tiny. |

### Replication

A **standby** is a second PostgreSQL server that replays the primary's WAL. The **primary** is the server that takes the writes. The primary streams its log to the standby as it goes. This is streaming replication. It is asynchronous by default: the primary answers the client without waiting for the standby. With synchronous settings, a commit waits until the standby confirms. The docs say the minimum wait time is "the round-trip time between primary and standby". That is the trade-off from [the Replication lesson](/learn/backend/04-data/replication/), now with PostgreSQL labels. Step through it again and watch the crash.

### One process per connection

Each client connection is a server process. The default `max_connections` is typically 100. A process costs memory and scheduling time. So 5,000 mostly idle connections is a poor design, and raising the limit to 10,000 is not the fix.

The fix is a **connection pooler** such as PgBouncer. Many clients talk to the pooler, and the pooler shares a few server connections among them.

<PgPooler />

PgBouncer has three modes: session, transaction, and statement. In transaction mode a server connection is lent out only for the length of one transaction. That gives the best sharing. The cost: per the PgBouncer docs, transaction mode "breaks a few session-based features". These are features that expect the same server connection to stay yours. Examples are `LISTEN` (get a message when another session sends one), `PREPARE` (save a parsed query on your connection for reuse), and session-level advisory locks (locks your code takes by name).

## When to use it

- You have relational data with relationships between entities, and you need joins, constraints, and multi-row transactions.
- One primary can carry the write rate. Add read replicas for read-heavy load ([the Replication lesson](/learn/backend/04-data/replication/)).
- You do not know all the queries up front. SQL and secondary indexes handle new questions without a redesign.
- You want strong guarantees by default. An **isolation level** says how much one transaction can see of another one's work. The default is Read Committed: each statement sees only committed data. Repeatable Read keeps one fixed view for the whole transaction, and in PostgreSQL it also prevents phantoms (new rows that appear in a repeated query). Serializable prevents all the listed anomalies. Read Uncommitted is accepted but behaves as Read Committed.

## When not to

| Situation | Why PostgreSQL strains | Look at |
|---|---|---|
| Write rate beyond one primary | All writes go to one leader. Sharding is your job ([the Sharding lesson](/learn/backend/04-data/sharding/)). | [Cassandra](/learn/backend/08-technologies/cassandra) or [DynamoDB](/learn/backend/08-technologies/dynamodb) |
| Key-value access at huge scale with fixed query shapes | You pay for SQL features you do not use | [DynamoDB](/learn/backend/08-technologies/dynamodb) |
| Ranked full-text search with filters over a large corpus | Search engines build and score inverted indexes for this | [Elasticsearch](/learn/backend/08-technologies/elasticsearch) |
| Sub-millisecond lookups of hot data | Every query goes through a process, a parser, and disk-backed pages | [Redis](/learn/backend/08-technologies/redis) as a cache |

## Limits that matter

| Limit | Value | Source |
|---|---|---|
| Default `max_connections` | typically 100 | PostgreSQL docs, connection settings |
| Maximum field size | 1 GB | PostgreSQL docs, limits |
| Maximum table size | 32 TB (with the default 8 KB block size) | PostgreSQL docs, limits |
| Maximum columns per table | 1,600 | PostgreSQL docs, limits |
| Database size | unlimited | PostgreSQL docs, limits |
| Vacuum every table at least once per | 2 billion transactions | PostgreSQL docs, routine vacuuming |
| `autovacuum_freeze_max_age` default | 200 million | PostgreSQL docs, routine vacuuming |

A row version must fit in one 8 KB heap page. Large values are moved out of the page and stored in a side table (the feature is called TOAST). The docs do not give one single "maximum row size" number, so do not quote one.

## Interview lens

<Callout type="tip">
Name the reason, not just the product: "Orders and payments need multi-row transactions and constraints, so PostgreSQL. One primary plus read replicas covers the load at this scale. If writes outgrow one primary, I would shard by user ID." Then name the operational cost: "Connections are processes, so I will put PgBouncer in front, and I will watch long transactions because they block VACUUM."
</Callout>

<Callout type="mistake">
Do not say "readers take row locks, so reads block writes". Under MVCC they do not. Do not say the default isolation level is Serializable. It is Read Committed. Do not fix "too many connections" by raising `max_connections` to a large number. And do not say a standby is always up to date. Replication is asynchronous, unless you turn on synchronous commit. With synchronous commit, every commit pays a round trip.
</Callout>

<Callout type="deep" title="Why a hot UPDATE makes bloat">
A counter row updated 1,000 times leaves 1,000 dead versions behind the live one, until VACUUM can remove them. If the row is updated faster than VACUUM can clean up, the table and its indexes grow. The same happens if an old transaction holds the horizon back. This growth happens while the row count stays at one. A common fix is to avoid hot rows: append events and sum them, or keep the counter in Redis and write it back in batches.
</Callout>
