## What it is

Amazon DynamoDB is a managed key-value and document database. Managed means Amazon runs the machines, the partitioning, and the replication for you. A key-value store keeps each record under a name (the key). A document database lets each record hold nested fields, like a JSON object. In on-demand mode it is serverless: you do not rent or size any machines, and you pay per request. You do not choose a node count. You choose a **primary key** and a way to pay for reads and writes.

That trade is the whole product. You give up flexible queries. You get a store that [shards](/learn/04-data/sharding) for you, with no table size limit in practice. A quota is a limit AWS sets on your account or table. The quotas page says there is "no practical limit on a table's size".

## The internal model

### Primary key: partition key plus optional sort key

A table has a primary key. It is either **simple** (a partition key only) or **composite** (a partition key and a sort key). The docs say DynamoDB "uses the partition key's value as input to an internal hash function". The result decides which partition stores the item. This is hash partitioning, as in [lesson 4.7](/learn/04-data/sharding). Items with the same partition key are "stored together, in sorted order by sort key value". Two consequences follow.

- A **Query** names one partition key value and, optionally, a range of sort key values. It reads one slice of one partition. A **Scan** reads the whole table. Scan is the slow path.
- Model related items under the same partition key, so one Query returns them. Examples are a user and the user's orders, and a chat room and its messages. This is the access-pattern-first design of [lesson 4.1](/learn/04-data/data-modeling).

### Secondary indexes

A **global secondary index** (GSI) has a different partition key and sort key from the table. It is a separate copy of the data, with its own partitions. A **local secondary index** (LSI) has the same partition key as the table and a different sort key. The default quota is 20 GSIs and 5 LSIs per table.

Know three rules about GSIs.

1. **Reads are eventually consistent.** The docs say "All reads from GSIs and streams are eventually consistent." A GSI cannot give a strongly consistent read, even if you ask for one.
2. **They cost writes.** Every write to the table also writes to each index that holds the item.
3. **They cannot join back.** A GSI query "cannot fetch attributes from the base table". You must project the attributes you need into the index.

An LSI has a catch. If a table has any LSI, then an item collection cannot exceed 10 GB. An item is one row. An item collection means all items with one partition key value. The docs call 10 GB the maximum partition size for such a table. That cap is why many teams avoid LSIs.

### Consistency

A read is eventually consistent by default. You can ask for a **strongly consistent** read on the table. It returns the result of all writes that succeeded before it. It costs twice as much as an eventually consistent read.

### Capacity: units, modes, and the partition ceiling

DynamoDB meters work in **read units** and **write units**.

- One read unit: one strongly consistent read per second, or two eventually consistent reads per second, of an item up to 4 KB.
- One write unit: one write per second of an item up to 1 KB.
- Transactional reads and writes cost twice as much.
- Item sizes are rounded up. A 10 KB item is billed as 12 KB. A 1.6 KB item is billed as 2 KB.

There are two **capacity modes**. In **on-demand** mode you pay per request. In **provisioned** mode you pay for read and write units per hour. Provisioned is cheaper when the load is steady and predictable. On-demand is simpler when it is not.

The bottom-right card is the most important one. The docs say each partition "is designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second". The table-level default quota is 40,000 units, and you can ask for more. But if every write goes to one partition key, you are held to one partition's ceiling. A **hot partition** throttles (DynamoDB rejects some requests with an error and asks you to retry later) while the rest of the table sits idle. The usual cures:

- Pick a key with many distinct values and even traffic (a user ID, not a country code).
- For an unavoidably hot key, add a **write-shard suffix**. An example is `post#17#3`. The last part is a random number from 0 to 9. Writes spread over ten partitions. The price is that a read must query all ten and merge.

### Streams and transactions

**DynamoDB Streams** records changes to items. Records are removed automatically after 24 hours. You choose what a record holds: `KEYS_ONLY`, `NEW_IMAGE`, `OLD_IMAGE`, or `NEW_AND_OLD_IMAGES`. Order is per item, not across the partition. Streams are how you feed a search index or a cache from the table. This is change data capture (lesson [6.5](/learn/06-async/cdc/)): every change to a row is copied out as an event.

`TransactWriteItems` and `TransactGetItems` give all-or-nothing operations across items and tables. The docs set the limits: up to 100 unique items and 4 MB in one transaction. DynamoDB does two underlying operations per item, one to prepare and one to commit. That is why a transaction costs twice as many units. A transaction cannot use indexes. And it holds only inside one Region, which is one AWS data center area, such as one city or part of a country.

## When to use it

- Access patterns are known and simple: get by key, list by key and range.
- You need to scale with no operations work, with traffic that is spiky or unknown (on-demand).
- Per-user or per-entity data: sessions, carts, user profiles, device state.
- You want an event feed from the table through Streams.

## When not to

| Situation | Why | Look at |
|---|---|---|
| Ad-hoc queries, joins, reports | Every query must fit a key or an index | [PostgreSQL](/learn/08-technologies/postgresql) |
| Large blobs | The item size limit is 400 KB | Blob storage (a service for big files) with the file's address saved in the item |
| Full-text search | No relevance scoring | [Elasticsearch](/learn/08-technologies/elasticsearch) |
| Wide multi-item transactions | At most 100 items, 4 MB, two units per item | [PostgreSQL](/learn/08-technologies/postgresql) |
| Open-source or self-hosted requirement | It is an AWS service | [Cassandra](/learn/08-technologies/cassandra) |

## Limits

All values come from the DynamoDB developer guide ("Constraints" and "Service quotas" pages).

| Limit | Value |
|---|---|
| Item size (names plus values) | 400 KB |
| Partition key value length | up to 2,048 bytes |
| Sort key value length | up to 1,024 bytes |
| `Query` or `Scan` result per call | 1 MB, then use `LastEvaluatedKey` |
| `BatchGetItem` | 100 items, 16 MB |
| `BatchWriteItem` | 25 puts or deletes, 16 MB |
| Items in one transaction | 100 unique items, 4 MB |
| GSIs per table (default) | 20 |
| LSIs per table | 5 |
| Table with an LSI: item collection | 10 GB |
| Per partition, designed capacity | 3,000 read units and 1,000 write units per second |
| Table default quota, provisioned | 40,000 read units and 40,000 write units (adjustable) |
| Stream record retention | 24 hours |

## Interview lens

<Callout type="tip">
Start from the access patterns: "Get a user's orders, newest first. Partition key is the user ID, sort key is the order time. For orders by status I add a GSI, and I accept that it is eventually consistent." Then show you know the ceiling: "One partition tops out near 1,000 writes per second, so I avoid a partition key that a few users dominate."
</Callout>

<Callout type="mistake">
Do not say a GSI can be strongly consistent. Do not say the limit is the table's throughput when a hot key throttles: the limit is per partition. Do not store 1 MB documents in one item: the limit is 400 KB. Do not use Scan in a request path. And do not model it like a relational database and expect joins.
</Callout>

<Callout type="deep" title="A missing item still costs a read">
A read for an item that does not exist still uses read capacity, as if the item was there. The store still has to hash the key, find the partition, and look. It matters for a cache-miss check or a "does this ID exist" call at high volume. It is a cost, even when the answer is empty.
</Callout>
