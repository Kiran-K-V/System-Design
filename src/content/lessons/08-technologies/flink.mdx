## What it is

Flink is an engine that runs computations over **streams** of events that never end. You write a **job**. A job is a graph with a **source** that reads events (often a Kafka topic, the [Kafka](/learn/backend/08-technologies/kafka/) lesson). The job also has **operators** that transform them, and a **sink** that writes results.

What makes it special is **state**. An operator can remember things between events. Examples are a running total per user, the last 10 minutes of clicks, and a half-finished join (matching events from two streams, such as an order and its payment). Flink keeps that state next to the code, on the machine that runs the operator. Reading it costs a local lookup, not a network call to a database.

Flink runs as a small cluster. A **JobManager** schedules tasks, coordinates checkpoints, and coordinates recovery after failures. **TaskManagers** are the workers that run the tasks and move data between them. Each TaskManager offers a fixed number of **task slots**, its smallest unit of scheduling.

Compare with a plain consumer service. A consumer reads one record at a time and keeps state in an outside database. That works until you need "orders per merchant per 5 minutes" with correct results when events arrive late or a machine dies. Flink gives you time, windows, and recovery as built-in tools.

## Internal model

### Event time and watermarks

There are two clocks. **Processing time** is the plain clock time of the machine running the operator. **Event time** is when the event happened at its source, stamped inside the event. Flink's docs say event time gives results that depend on the data, not on machine speed. A job replayed tomorrow gives the same answer. A job on processing time does not.

Events arrive late and out of order. A phone that was offline sends a click minutes after it happened. So how does the job know that a window is complete? It cannot know. It uses a **watermark**. A `Watermark(t)` declares that event time has reached `t`: no more events with timestamp `t` or lower should arrive. It is a promise the job trusts. Events that break it are **late**.

A common watermark rule is "the largest timestamp seen, minus a delay". The delay is your tolerance for disorder. When an operator reads several inputs, its event time is the **minimum** of its inputs' event times. One slow input holds everything back.

### Windows

A **window** groups events so you can aggregate an endless stream. Flink has four window types:

- **Tumbling**: fixed size, no overlap. Each event is in exactly one window.
- **Sliding**: fixed size, moves by a smaller step, so windows overlap and one event can be in several.
- **Session**: no fixed size. A window closes after a gap with no events.
- **Global**: one window per key. You supply a trigger yourself.

The default event-time trigger fires when the watermark passes the end of the window. Late events are dropped by default, because the default **allowed lateness** is 0. You can raise it. The cost is that Flink holds window state longer. Step through three tumbling windows with a 5-second tolerance.

### Keys, parallelism, and state

`keyBy(userId)` splits the stream into logical streams, one per key. Flink spreads keys over parallel tasks, like partitions (the [Sharding](/learn/backend/04-data/sharding/) lesson). Each key's state lives with the task that owns the key. A window on a keyed stream runs in parallel. A window on a stream with no key (`windowAll`) runs in one task, a bottleneck.

### Checkpoints make state safe

State on one machine is lost when the machine dies. Flink saves it with **checkpoints**. A checkpoint is a saved copy of the whole job at one moment, like a save point in a video game. The checkpoint coordinator tells the sources to start checkpoint *n*. Each source records its position and puts a numbered **barrier** into its stream. The barrier flows with the data. When an operator sees the barrier, it saves its state. Checkpoint *n* then holds the effects of every event before barrier *n* and none after it. An operator with two inputs waits for the barrier on both, which is called **barrier alignment**.

<FlinkCheckpoint client:visible />

On a failure, Flink restores every operator from the last complete checkpoint. Flink then **rewinds and replays** the source from the saved position. This needs a **replayable source**. Kafka qualifies, because it keeps the log (the [Pub/Sub and Logs](/learn/backend/06-async/pubsub-logs/) lesson).

Flink's docs define exactly-once carefully. It does not mean each event is processed once. It means each event affects the **state** Flink manages exactly once. Events 121 to 135 in the animation are processed twice, but the restored state counts them once. For results that leave Flink, the docs list two conditions for end-to-end exactly-once. The conditions are replayable sources, and sinks that are **transactional or idempotent**. A transactional sink writes a batch of results all at once or not at all. An idempotent sink gives the same result when the same write arrives twice. Otherwise the output has duplicates. That is the same problem as the [Delivery Semantics](/learn/backend/06-async/delivery-semantics/) lesson.

## When to use it

- **Windowed aggregates** over events: counts, sums, and rates per minute. An aggregate is one number computed from many events.
- **Stateful rules** on a live stream, such as a fraud check that needs the last N events of a card.
- **Stream joins and enrichment**, where two streams meet in state. Enrichment means adding data to each event, such as a user's country.
- **Anything that needs correct time handling** when data is late or replayed.

## When not to use it

- **A stateless transform.** A plain consumer does it with less to run.
- **Small jobs in Kafka only.** The Kafka Streams library may be enough. It is part of your app, with no separate cluster.
- **Ad hoc analysis.** A data warehouse (a database built for big one-off analysis queries) answers one-off queries. Flink is for continuous ones.
- **Request and response.** Flink does not answer calls from other services.
- **A team that cannot run a cluster.** State, checkpoints, and upgrades are real operational work.

## Numbers

The Flink pages I used give **no default numbers** for checkpoint interval, state size, or latency, so I state none. The facts that are safe to say:

| Fact | Value |
|---|---|
| Allowed lateness | 0 by default |
| Late events in a window | Dropped by default |
| Checkpoint contents | Source positions plus operator state at one barrier |
| Without barrier alignment | `AT_LEAST_ONCE` mode. Faster, may count events twice in state |

Size the checkpoint interval from the recovery cost you accept. The interval is the amount of data you may replay after a crash. A longer interval means less checkpoint work in normal running, but a bigger backlog to replay after a failure.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Event time | Same result on replay. Handles disorder | Watermarks delay results | Billing, analytics, anything replayed |
| Processing time | Simple. Lowest delay | Results depend on speed and arrival | Rough monitoring |
| Longer allowed lateness | Fewer dropped events | More state held | Mobile clients with bad networks |
| Exactly-once mode | State counted once | Barrier alignment cost. Needs a transactional or idempotent sink | Money and counters |
| `AT_LEAST_ONCE` | Less overhead | Possible duplicates in state | Approximate metrics |
| Keyed windows | Scale over keys | Hot keys are slow | Many keys, even load |

<Callout type="tip">
Name the clock, the window, and the recovery in one pass: "I use event time with a watermark of 5 seconds, tumbling 1-minute windows keyed by merchant, and allowed lateness of 1 minute. State is checkpointed to durable storage (disks or cloud storage that survive a crash). Source is Kafka, so it can replay. The sink writes with a transaction, or an idempotent upsert (a write that inserts the row if it is new and replaces it if it exists), for end-to-end exactly-once."
</Callout>

<Callout type="mistake">
Do not say "a watermark is the latest timestamp". It is a promise that earlier events are done. Do not use processing time for billing, since a replay would give a different bill. Do not say "Flink is exactly-once end to end by default". It needs a replayable source and a transactional or idempotent sink. And do not use a non-keyed window on a busy stream: it runs in a single task.
</Callout>

<Callout type="deep" title="Why one slow source holds a window open">
An operator with several inputs takes the minimum of their event times. If one Kafka partition goes quiet, its watermark stops. The operator's clock stops with it, and no event-time window closes. The job looks frozen though most data flows. The fix is to mark such an input as idle (`withIdleness` in the watermark strategy). So the others can move on. The lesson is that watermarks are a shared clock, and one bad input can hold it back.
</Callout>
