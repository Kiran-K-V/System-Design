## What it is

Your app stores photos, videos, backups, and logs. Each file is megabytes to terabytes. Where do the bytes go?

- **In the database, as a column.** The database grows huge, backups slow down, and every read of a big value fights with your small, hot queries.
- **On a server's disk.** One disk fills up. One machine dies. You must copy files between machines yourself.

**Blob storage**, also called **object storage**, is built for this. You keep data as **objects** in a flat namespace called a **bucket**. An object has a **key** (its name), the bytes, and some metadata. You put a whole object, get a whole object, or delete it. You do not edit the middle of it. This lesson uses **Amazon S3**, the best-known example. Other clouds have the same model.

There are no real folders. A key like `videos/2026/cat.mp4` is one string. The part before a slash is called a **prefix**, and tools show it as a folder.

A good split is: **bytes in the blob store, facts about them in a database**. The database row holds the owner, the size, the upload time, and the object key. A query finds the row. The key finds the bytes.

## Internal model

### Durability, consistency, and speed

S3 stores each object redundantly. The storage-class page says S3 Intelligent-Tiering is designed for 99.999999999% durability, which is eleven nines. AWS lists the same figure for most classes. Compare that with one disk, which fails far more often (lesson [4.6](/learn/04-data/replication/) on why copies matter).

On 1 December 2020, AWS made S3 **strongly consistent**. GET, PUT, and LIST are strongly consistent, so after a successful write, the next read or list shows it. Older advice that said "S3 is eventually consistent" is out of date (lesson [4.10](/learn/04-data/consistency-models/)).

Speed is moderate. AWS says latency-sensitive applications can get small-object latency of roughly 100 to 200 milliseconds. That is far slower than memory or a local disk (lesson [1.2](/learn/01-one-machine/latency-numbers/)). Blob storage is for capacity and durability, not for tiny fast reads.

### Prefixes and request rates

S3 scales request rates per **prefix**. AWS says an application can achieve at least 3,500 PUT, COPY, POST, or DELETE requests and 5,500 GET or HEAD requests per second per prefix. A bucket can hold any number of prefixes. AWS gives the arithmetic: 10 prefixes can scale reads to 55,000 per second.

Scaling is gradual, not instant. During scale-up you may see `503 Slow Down` errors. So a design that writes 20,000 objects per second under one prefix will be throttled. Spread keys over many prefixes. This is sharding (lesson [4.7](/learn/04-data/sharding/)), and the prefix acts as the shard key. Adding more buckets does not help: the limit is per prefix, not per bucket.

### Large uploads: pre-signed URLs and multipart

Sending a big file through your own API has two problems. The gateway may cap the body (10 MB on Amazon API Gateway, lesson [8.10](/learn/08-technologies/api-gateway/)). And every upload ties up app server connections and bandwidth. So the client uploads **directly** to the store. But the client has no credentials. A **pre-signed URL** solves that: your server signs a URL that allows one action, such as PUT of one key, for a limited time. Signing is local math. It needs no call to S3.

A single PUT can carry at most 5 GB. Beyond that, and for anything above about 100 MB, AWS recommends **multipart upload**. You split the file into numbered **parts**, upload them in any order and in parallel, then call **complete**. Each part's response carries an **ETag**. The complete call lists every part number and ETag, and S3 joins the parts in order. Step through it.

Multipart has three benefits. Parts go in parallel, so throughput rises. A failed part is retried alone. And you can start before you know the final size.

The limits come from the S3 documentation. Parts are numbered 1 to 10,000. Each part is 5 MiB to 5 GiB, except the last, which may be smaller. So the biggest object is 10,000 × 5 GiB, about 48.8 TiB. AWS pages round this to 50 TB, the multipart limits table says 48.8 TiB, and some older pages say 5 TB. Use the table. Try the planner.

Two things to remember. Uploaded parts are billed until you complete or stop the upload, so an abandoned upload costs money. And a pre-signed URL is a **bearer token**: anyone who holds it can use it until it expires. With the AWS CLI or SDKs the expiry can be up to 7 days. With the console it is 1 minute to 12 hours. If you sign with temporary credentials, the URL dies when those credentials do. S3 checks the expiry when the request starts, so a download that began before expiry finishes, but a restart after expiry fails. Keep expiry short and sign one key, not a whole bucket.

### Storage classes

Not every object is read often. A **storage class** trades cost against access speed and fees.

| Class | Fits | Catch |
|---|---|---|
| Standard (default) | Hot data | Highest storage price |
| Standard-IA, One Zone-IA | Rarely read, still needs milliseconds | 30-day minimum, billed for at least 128 KB, retrieval fee. One Zone keeps data in a single zone |
| Intelligent-Tiering | Unknown access pattern | Monitoring fee. Moves objects after 30 and 90 days without access. Objects under 128 KB are not tiered |
| Glacier archive classes | Archives | Longer minimum durations and a restore step before reading |

A **lifecycle rule** moves objects between classes by age. Upload as Standard, move to IA after 30 days.

### A CDN in front

Reading from one Region is slow for far-away users and costs more at high volume. Put a CDN in front (lesson [2.7](/learn/02-networking/cdn-proxies/)). The store is the **origin**. The first request in a region misses the CDN cache and fetches from the origin. Later requests hit the edge. AWS names CloudFront for high-throughput or low-latency reads from S3. The CDN absorbs the read traffic, and the store stays the durable home.

## When to use it

- **Media and user uploads**: photos, video, documents. See lesson 9.6 for the pattern.
- **Backups and archives.**
- **Static website assets**, behind a CDN.
- **Data lakes and logs.** Many files, processed by other systems.

## When not to use it

- **Small values you update often.** A database or cache does this far better. An S3 object is replaced whole.
- **Queries.** There is no "find objects where owner = 7". Keep that index in a database.
- **Millisecond reads on a tight budget.** Typical latency is 100 to 200 ms for small objects.
- **File-system behavior.** There are no true directories, locks, or in-place edits.
- **Writes through your API.** Use a pre-signed URL instead.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Direct upload with pre-signed URL | No app server in the byte path. Scales with S3 | URL is a bearer token. Client must handle parts | Any file above a few MB |
| Upload through your API | Simple. Full control of checks | Body caps. Server bandwidth and time | Tiny files only |
| Many prefixes | Higher request rate | Keys need a spread scheme | High write volume |
| Cold storage class | Low storage price | Minimum durations, retrieval fees, restore time | Backups, old data |
| CDN in front | Fast reads far away. Less origin load | Cache invalidation (lesson [5.5](/learn/05-caching/invalidation-stampede/)) | Public, read-heavy files |

<Callout type="tip">
Say: "The API checks auth and creates a row. It returns a pre-signed multipart upload. The client sends parts straight to S3. Then the API completes the upload and marks the row ready. Reads go through a CDN with S3 as origin. Metadata lives in a database, bytes in S3." If asked about scale, add: "keys spread over prefixes, since limits are per prefix."
</Callout>

<Callout type="mistake">
Do not say "S3 is eventually consistent". It has been strongly consistent since December 2020. Do not push big files through your API or gateway. Do not "add buckets" to raise throughput: the limit is per prefix. And do not use object storage as a database. It cannot query, and it replaces whole objects.
</Callout>

<Callout type="deep" title="Why the upload row needs a status">
Direct upload splits one action into two: the database row and the object. They can disagree. A user may create the row and never upload, or upload and never tell your API. So give the row a status, such as `pending` and `ready`. Set `ready` only when the complete call succeeds (or when S3 sends an event). A cleanup job removes rows that stay `pending` too long, and aborts their multipart uploads so the parts stop costing money.
</Callout>
