## What it is

Many real processes have several steps that take time and can fail: charge a card, reserve stock, ship the order, email the customer. The whole thing may take seconds or days. A crash between two steps must not leave the order half done.

**Temporal** is a **durable execution** engine. You write the process as normal code. Temporal records the progress of that code. So if the machine running it dies, another machine continues from the same point. "Durable" means the progress survives a crash.

## The problem without it

Build the order flow the usual way. You keep an `order_state` column. A queue (lesson [6.1](/learn/06-async/queues/)), a line of messages waiting for a worker, carries a message per step. Each consumer reads the message, calls an API, updates the column, and publishes the next message. Then the failures arrive.

- The consumer charges the card and crashes before it saves the new state. The retry charges again.
- A step needs "retry in 10 minutes, then in an hour, then give up". You write a scheduler for it.
- The customer must pay within 24 hours or the order is canceled. You write a timer job, which is a script that a scheduler such as cron (a tool that runs commands at set times) starts on a clock.
- To see where order 42 stands, you read four tables and three queues.

Each fix is more glue code. The process itself is spread over queues, tables, and cron jobs, and no single place shows what should happen. Retries (lesson [7.2](/learn/07-reliability/timeouts-retries/)) and idempotency (lesson [3.4](/learn/03-api-design/idempotency/)) are still your job on every step.

## Internal model

Temporal splits the work into two kinds of code.

A **workflow** is the orchestration: the order of steps, the branches, the waits. It must be **deterministic**: the same input and the same history give the same sequence of calls. Think of a recipe card. Two cooks who follow it to the letter do the same steps in the same order. A cook who rolls a die to pick the next step breaks the card. Workflow code must follow the card, because Temporal will run it again later and compare. For example, `if (random() > 0.5) chargeCard()` is not deterministic: the second run may skip the charge that the first run made. An **activity** is one piece of work in the outside world: an API call, a database write. Such work is called a side effect, because it changes something outside the program. Activities may do anything, and each result is recorded.

The **Temporal Service** keeps an **event history** for each workflow execution. The history is an ordered log of everything that happened. Examples include workflow started, activity scheduled, and activity completed. The history is the source of truth. It is a write-ahead log (lesson [4.2](/learn/04-data/storage-engines/)) for your program.

**Workers** are your processes. They poll a **task queue**, which means they ask a named waiting line again and again, "is there work for me?" A worker that gets work runs workflow code or activity code. Workers are stateless, which means a worker keeps nothing it cannot rebuild. The Temporal docs say a blocked workflow can be resumed on any worker. That is why a crash is survivable: no worker holds the only copy of anything.

### Replay: how a new worker rebuilds state

Here is the trick. A worker does not store the workflow's variables. When it needs to continue a workflow, it gets the history and **replays** the code from the top. As the code runs, it emits **commands**, such as "schedule activity charge". The SDK (the Temporal library inside your worker) compares each command with the next event in the history. If there is a matching event, the SDK returns the recorded result and does not run the activity again. When the code goes past the end of the history, the command is new and the workflow runs live again.

### Determinism, and what it forbids

Replay only works if the code makes the same commands every time. If the SDK emits a command that does not match the history, the workflow fails with a non-determinism error. So workflow code must not do things that can differ between runs:

- Call an API or a database directly. Put it in an activity.
- Read the local clock or a random number. Use the SDK's own time and random calls, which record their values in the history.
- Reorder, add, or remove commands in a running workflow without **versioning** the change. Versioning means marking the new code so that old running workflows keep following the old steps. Step 9 shows the failure.

This is the main cost of Temporal. The rules are simple but easy to break by accident.

### Failure handling

Activities **retry by default**. The default policy uses backoff, which means each wait is longer than the last, so a struggling service gets room to recover. The settings are an initial interval of 1 second, a backoff coefficient of 2.0, a maximum interval of 100 times the initial interval, and unlimited attempts. Workflow executions do **not** retry by default. The docs advise against retrying a whole workflow. The reason is that replay is deterministic and would fail again the same way.

How does Temporal notice a dead worker? It does not, directly. The docs say the server does not detect a worker crash. It relies on the **start-to-close timeout**, the longest a single attempt may run. When it passes, the attempt counts as failed and the retry policy schedules another. The service has no default for it, and it rejects an activity with neither a start-to-close nor a schedule-to-close timeout. A **heartbeat timeout** gives faster detection for long activities: the activity must report in within that gap.

Because an attempt can finish its side effect and die before reporting, an activity can run more than once. Make activities idempotent (lesson [3.4](/learn/03-api-design/idempotency/)), for example by passing an idempotency key to the payment API.

## When to use it

- **Multi-step business processes** where a failure in the middle needs a defined response: orders, onboarding, payouts. This is the saga pattern in lesson 9.5: a chain of steps where each step has an undo step, such as a refund, that runs if a later step fails.
- **Long-running tasks** that wait for people or for days. Examples are approvals, trials that end in 14 days, and long jobs (lesson 9.7).
- **Retries with backoff** (growing waits between attempts) as a built-in, not as scheduler code.
- **Visibility.** The history shows exactly where a process stands.

## When not to use it

- **One-step background work.** A queue and a worker do it with less machinery.
- **Very high event rates for tiny jobs.** Every command is written to the history. Per-event processing at massive rates belongs to a stream processor, a system that handles an endless flow of events (lesson [8.7](/learn/08-technologies/flink/)).
- **The latency-critical request path.** A workflow adds service round trips. Use it behind the request, not in it.
- **A team that cannot follow determinism rules.** Wrong code fails at replay, sometimes weeks after the change.

## Numbers

| Fact | Value |
|---|---|
| Activity retry: initial interval | 1 second |
| Activity retry: backoff coefficient | 2.0 |
| Activity retry: maximum interval | 100 × initial = 100 seconds |
| Activity retry: maximum attempts | unlimited |
| Event history: warning logged | after 10,240 events |
| Event history: execution terminated | above 51,200 events, 2,000 updates, or 10,000 signals (messages sent into a running workflow) |
| Start-to-close timeout | no default. Set one |

With the defaults, the waits between attempts are 1, 2, 4, 8, 16, 32, 64 seconds. After that, each wait is 100 seconds (the cap). The first seven waits add up to 127 seconds. History grows with every step, so a workflow that loops forever must call **Continue-As-New**. It closes the current execution and starts a fresh one with a new, empty history. The docs recommend doing it periodically. I give no history size in megabytes, because the page I used states none.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Temporal workflow | Crash-safe code. Built-in retries and timers. Visible state | A new service to run. Determinism rules. Versioning | Multi-step, long, or high-stakes processes |
| Queue plus state table | Simple parts you know | Glue for retries, timers, and recovery | One or two steps |
| Short start-to-close | Fast detection of a dead worker | Slow healthy attempts get cut off | Activities with a known short runtime |
| Long start-to-close with heartbeats | Detects crashes in long jobs fast | Activity must send heartbeats | Long activities, such as file processing |
| Many activities per workflow | Fine-grained retry | Larger history | Processes with distinct failure points |

<Callout type="tip">
Say: "The order flow is a workflow. Charge, reserve, and ship are activities with retry policies and an idempotency key. If a worker dies, another replays the history and continues. Failures after charging trigger a compensating refund." Then name the cost: "workflow code must be deterministic, so no direct I/O or clock in it."
</Callout>

<Callout type="mistake">
Do not say "Temporal re-runs the step when the worker crashes right away". It waits for the start-to-close timeout. Do not say "workflows retry by default". Activities do. Do not put an API call in workflow code "because it is faster". Replay would repeat it. And do not forget idempotency: an activity can run twice.
</Callout>

<Callout type="deep" title="Why not just snapshot the variables?">
You could save the program's memory at each step instead of replaying. Replay needs only the small, append-only history, which is cheap to write and easy to inspect. A snapshot of a running program is large. It is tied to one version of the code and hard to move between machines. The price of replay is determinism. The same idea is behind a database write-ahead log and the replicated log in lesson [4.11](/learn/04-data/consensus/). A log of what happened is enough to rebuild the state.
</Callout>
