## What it is

Elasticsearch is a distributed search and analytics engine built on Apache Lucene. Lucene is an open-source library that does the core work of building and reading search indexes. Distributed means the data and the work are spread over many machines. You store **documents** (JSON objects, such as one product or one log line) in an **index** (a named collection of documents, like a table). You search them by words, filters, and ranges, and you get results ranked by relevance. A SQL `LIKE '%word%'` scans every row. Elasticsearch looks the word up in a prebuilt index.

It is a **secondary** store in most designs. The source of truth lives in a database such as [PostgreSQL](/learn/08-technologies/postgresql). A pipeline copies changes into Elasticsearch, often by change data capture (CDC): a tool that reads the database's log of changes and forwards each one. A search request reads from Elasticsearch. This is our design advice, not an Elastic rule. The reason is in the sections below: writes become visible after a delay, and there are no multi-document transactions.

## The internal model

### The inverted index

Search speed comes from the structure you built in [lesson 4.3](/learn/04-data/indexing). An **inverted index** maps each word to the list of documents that contain it. A query looks up the words and intersects the lists, which means it keeps only the document IDs that appear in all of them. It never scans the documents. Think of the index at the back of a textbook: you look up a word and get page numbers, instead of reading every page. A search for "fast" over 3 billion documents becomes one lookup plus a short list.

<InvertedIndexBuild client:visible />

Lucene builds and reads these indexes. Elasticsearch adds the spreading over many machines on top.

### Shards and replicas

An index is split into **shards**. The Elasticsearch docs say "Each shard is a self-contained Apache Lucene index". The docs also say "Every document belongs to exactly one primary shard". The shard is chosen from the document's ID, by default. That is hash partitioning, as in [lesson 4.7](/learn/04-data/sharding).

Each primary shard can have **replica** copies. Replicas "provide redundancy and serve read requests". This is the leader-follower idea of [lesson 4.6](/learn/04-data/replication): a write goes to the primary and then to its replicas. A search can go to either. The replicas also take over if the machine holding the primary dies.

A shard stores its data in **segments**. Segments are small index files. They are immutable: once written, they are never changed. A new document goes into a new segment. This is the same log-structured thinking as the SSTables of [lesson 4.2](/learn/04-data/storage-engines).

### Near-real-time: why a new document waits

Writes do not become searchable at once. Step through the life of one document.

<EsRefresh client:visible />

The docs describe a **refresh**. It is the step that "makes all operations performed on an index since the last refresh available for search". By default Elasticsearch refreshes every second. But Elasticsearch does this only for indices (the plural of index) that "received one search request or more in the last 30 seconds". That is why the system is called near-real-time. Plan for about a second between a write and a search that can see it.

Durability is a separate matter. Durable means the write survives a crash or power cut. A Lucene commit writes all segments to disk for good. It is too expensive to run on every write, and segments sitting only in memory would vanish in a crash. So each shard copy also keeps a **translog**, short for transaction log. It is a file where each operation is added at the end, like a receipt roll. Adding a line is cheap. After a crash, Elasticsearch replays the translog to rebuild what was lost. By default (`index.translog.durability` set to `request`), a write is acknowledged only after the translog is forced onto disk (an operation called fsync, which waits until the disk confirms the data is stored). That happens on the primary and on every replica copy. A **flush** performs a Lucene commit and starts a new, empty translog. The cost is about one disk wait per write. So a write is durable at acknowledgement, and searchable after the next refresh.

### How a search runs: query then fetch

Documents are spread over shards by ID, not by content. Any shard may hold a match. So a search goes to every shard. This is the scatter-gather of [lesson 4.7](/learn/04-data/sharding): send the question to many machines, then collect and combine the answers. It happens in two phases.

<EsSearchFlow client:visible />

1. **Query phase.** The coordinating node is whichever node got the request, and it manages this search. It sends the query to one copy of each shard. Each shard returns only document IDs and scores for its best hits. A score is a number for how well a document matches, and higher is better. The coordinator merges the lists.
2. **Fetch phase.** The coordinator asks only the shards that hold the winners for the document bodies.

Two consequences matter in a design discussion.

- **Latency is set by the slowest shard**, as in any scatter-gather. More shards means more chances for one to be slow.
- **Scores are computed per shard.** The docs say `query_then_fetch` scores with "local term and document frequencies for the shard", which is "usually faster but less accurate". `dfs_query_then_fetch` uses global frequencies, "usually slower but more accurate", because it adds a round trip first.

The default relevance formula is **BM25**, a way to turn "how well does this document match" into a number. Its two parameters have documented defaults: `k1` is 1.2 and `b` is 0.75. In short, a word that is rare across the corpus (all the documents in the index) counts for more. A search for "the database" cares far more about "database" than "the". A word that repeats in a document counts for more, but with diminishing returns (`k1`). A match in a short document counts for more than the same match in a long one (`b`).

### Sizing shards

The sizing guide gives numbers you can use.

- Aim for shard sizes between **10 GB and 50 GB**.
- Keep documents per shard below **200 million**.
- More than **1,000 non-frozen shards per node** is a warning threshold. (Frozen shards are rarely used ones kept on cheap storage.)

The reason: each shard has a fixed cost in memory (the Java heap, the working memory of the Elasticsearch process) and in cluster bookkeeping. Thousands of tiny shards waste that cost. Very large shards are slow to recover and rebalance. The search request itself also has a limit: `max_concurrent_shard_requests` defaults to 5 per node. So a search over many shards runs in waves.

## When to use it

- Full-text search with ranking, typos, and filters: product search, site search, log search.
- Analytics over documents with filters and aggregations (counts, sums, and averages grouped by a field), where seconds of delay are fine.
- A derived, rebuildable index fed from your primary database by change data capture.

## When not to

| Situation | Why | Look at |
|---|---|---|
| System of record | Writes are visible after a refresh, and there are no multi-document transactions (our advice) | [PostgreSQL](/learn/08-technologies/postgresql) |
| Read-your-own-write immediately | Near-real-time, about one second | Read from the primary store |
| Key-value lookups at huge scale | You pay for search features you do not use | [DynamoDB](/learn/08-technologies/dynamodb) |
| Strict transactions and joins | Not its model | [PostgreSQL](/learn/08-technologies/postgresql) |

## Interview lens

<Callout type="tip">
Say where it sits: "The database is the source of truth. Changes flow by CDC into Elasticsearch. Search queries read the index, and I accept about a second of delay." Then say how it scales: "Index split into primary shards of 10 to 50 GB each, with replicas for reads and for failover. A query fans out to every shard and the coordinator merges the top hits."
</Callout>

<Callout type="mistake">
Do not say a write is searchable immediately. It is searchable after the next refresh, about one second by default. Do not say "TF-IDF" when asked what scores results: the default is BM25. Do not make one shard per node because it sounds neat: size shards by data volume. And do not present Elasticsearch as your only copy of important data.
</Callout>

<Callout type="deep" title="Deep paging is expensive">
To return results 9,990 to 10,000, each shard must find and send back its best 10,000 hits. Each shard does this because it cannot know which hits will survive the global merge. The coordinator merges every list and throws most of them away. The cost grows with how deep the page is, and with the number of shards. For deep scrolling, use a cursor-style method (`search_after`, which resumes after the last hit you saw) rather than a large offset, as in the [pagination lesson](/learn/03-api-design/pagination).
</Callout>
