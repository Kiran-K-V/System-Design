## The problem

Lesson [7.5](/learn/07-reliability/observability/) said to measure everything. Think about what "everything" costs.

A company runs thousands of servers. Each exposes dozens of metrics. A small program called a collector reads each metric every few seconds. This read is called a **scrape**. Every metric on every server is its own stream of values over time. That is a million streams, and each one gets a new sample every few seconds. Stored as plain 16-byte samples, this adds up to hundreds of gigabytes per day. Nobody wants to store that, or to scan it.

The workload has an unusual shape.

- Writes are **appends**. New samples always carry the newest time. Old samples never change.
- Reads ask for **one series over a time window**, or an aggregate over many series. For example, "p99 latency of the checkout service, last 6 hours".
- Old data is not wanted. You delete it **by age**.

## The data model

A **time series** is a stream of values for one thing over time. A sample has four parts.

| Part | Example |
|---|---|
| Metric name | `http_requests_total` |
| Tags (also called labels) | `host=web-17`, `endpoint=/pay`, `status=200` |
| Timestamp | `2026-10-14T02:01:02Z` |
| Value | `1873` |

One metric name plus one exact set of tags is one **series**. Change one tag value, or add a tag, and you have a new series. **Prometheus** is a popular open-source tool that collects and stores metrics. Its data model is the one used in this lesson, and we use it as our real example. It says a sample is one number with a timestamp in milliseconds. A number with a decimal point, stored in 64 bits, is called a float64. Each unique label combination is a new series.

## Naive solution: a SQL table

Make a table `(metric, tags, ts, value)` with a B-tree index on `(metric, tags, ts)`. Lesson [4.3](/learn/04-data/indexing/) showed how that index works. It fits the read pattern. It fails on cost.

- **Space.** 16 bytes of data for every sample, plus a row header and index entries.
- **Write path.** Millions of series interleave. New samples land in millions of places in the index. Each insert is a random page write (lesson [4.2](/learn/04-data/storage-engines/)).
- **Deletes.** Dropping data older than 15 days means deleting billions of rows one by one. Then the database must reclaim the space.

A log-structured design (lesson 4.2) fixes the write path. We still pay 16 bytes per sample. We still delete row by row. We need to use what we know about the data.

## The mechanism

Three ideas make a time series database.

1. **Group by series, in time order.** Samples of one series arrive at regular intervals. Neighbors in a series look alike.
2. **Compress using that similarity.** Store the difference to the previous point, not the point.
3. **Cut time into blocks.** A block holds a fixed window of time. Reads open only the blocks that overlap the window. Deleting old data means deleting whole blocks.

### Compression: the Gorilla scheme

Gorilla is a metrics database that Facebook built and described in a 2015 research paper. The paper describes two tricks. Both rest on the same observation: a series moves slowly.

**Timestamps: delta of delta.** A series scraped every 60 seconds has deltas of 60, 60, 59, 61. The **delta of delta** is the change in the delta: 0, −1, 2. It is zero most of the time. The encoding is:

| Delta of delta D | Bits stored |
|---|---|
| 0 | `0` (1 bit) |
| −63 to 64 | `10` + 7 bits = 9 |
| −255 to 256 | `110` + 9 bits = 12 |
| −2047 to 2048 | `1110` + 12 bits = 16 |
| anything else | `1111` + 32 bits = 36 |

The paper reports that about 96% of timestamps compress to a single bit.

**Values: XOR.** XOR ("exclusive or") compares two bit strings. Each result bit is 0 where the two bits match and 1 where they differ. Take the value as a 64-bit float. XOR it with the previous value. If the values match, the result is all zeros: store a single `0` bit. If they differ only a little, the XOR has long runs of zero bits at both ends. Store only the middle part ("the meaningful bits"). Two small numbers say where that part starts and how long it is. About 51% of values in the paper's sample cost one bit.

A tiny block saves little, because it pays for its header and its first raw value. A long block pays them once. The paper's production average is about **1.4 bytes per point**, against 16 bytes raw. That is roughly a tenfold saving.

The cost of this trick: **decoding is sequential**. To read point 500 of a block you decode points 1 to 499. That is why blocks are short.

### Blocks, the head, and retention

Prometheus shows the layout (its TSDB is one real example).

- New samples go to the **head**, a block in memory. A write-ahead log (WAL) on disk (lesson 4.2) protects it from a crash. The WAL is kept in 128 MB segments.
- Every 2 hours, the head is written to disk as an **immutable** (never changed after writing) **block**. A block holds chunks of compressed samples, an index from series to chunks, and metadata.
- **Compaction** merges small blocks into bigger ones, so a read opens fewer files. It stops at the smaller of 10% of retention or 31 days.
- **Retention** is a rule such as "keep 15 days", the Prometheus default. Blocks older than that are deleted as files. No row-by-row delete runs.

Gorilla itself uses the same two-hour block. Gorilla keeps 26 hours in memory as a cache in front of slower storage.

### Downsampling

A graph of 90 days with one point every 10 seconds has nearly a million points per series. A screen shows about a thousand. Old data rarely needs full detail.

**Downsampling** (also called a **rollup**) replaces old raw samples with fewer points. For example, keep one point per 5 minutes. That point holds the count, sum, min, and max of the raw points in that window. Then you can still compute an average or a maximum. A plain average alone hides spikes.

A typical policy is "raw data for a few weeks, rolled-up data for a year". The exact windows are your choice. Do not quote a default: it differs by product.

## Cardinality explosion

Cost follows the **number of series**, not the number of samples you think about. Each unique tag combination is a series. Tag values multiply.

The Prometheus naming guide warns: do not use labels for values with high cardinality. Such values include user IDs or email addresses. Try it. Start at 10 hosts × 5 endpoints = 50 series. Then turn on a `user_id` label.

With a million user IDs the same 50 series become tens of millions. The storage bill explodes. The tag that "made per-user graphs possible" costs more than the whole rest of the system. Put per-user data in logs or events, not in tags.

## Numbers

| Fact | Value | Source |
|---|---|---|
| Raw sample | 16 bytes (64-bit time + 64-bit value) | Gorilla paper |
| Gorilla average | about 1.4 bytes per point, about 12 times smaller | Gorilla paper |
| Prometheus head block | 2 hours, WAL in 128 MB segments | Prometheus docs |
| Prometheus default retention | 15 days | Prometheus docs |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Plain SQL table | One system, joins with other data | 16+ bytes per sample, row-by-row deletes | Under a few thousand samples per second |
| SQL table partitioned by time | Drop a partition to expire data | Still no sample compression | Moderate volume, you want SQL |
| Purpose-built TSDB | 1 to 2 bytes per sample, block deletes, range reads | Another system, limited joins, cardinality limits | High volume metrics |
| Rollups for old data | Small storage, fast long graphs | Lost detail, no exact p99 from averages | Dashboards over weeks or months |

## Interview lens

<Callout type="tip">
Describe the workload first: "append-only, newest timestamps, read by series and window, deleted by age". Then give the design. Say: "group by series, compress with delta-of-delta timestamps and XOR values, cut into 2-hour blocks, drop whole blocks at retention". Quote the number: "Gorilla gets about 1.37 bytes per point instead of 16". Raise cardinality before the interviewer does: "I would keep user IDs out of the tags".
</Callout>

<Callout type="mistake">
Do not say "1.37 bits per point". The paper says bytes. Do not use `user_id` or `request_id` as a tag so you can graph one user. Doing so makes one series per user. And do not say delta-of-delta is always small. It is small only when samples arrive at regular intervals. A collector that scrapes at jittery times pays 9 to 36 bits per timestamp, as the table shows.
</Callout>

<Callout type="deep" title="Why not compress each value alone?">
A float64 has 64 bits of detail, and a **gauge** (a metric that goes up and down, such as CPU temperature) rarely uses them. Two successive readings share the sign, the exponent, and often the first digits of the fraction. XOR turns "shares the top bits" into "starts with many zeros", which a short control code can describe. A general-purpose compressor does not know that the fields line up like this. Gorilla's compression is **lossless**: you get exactly the same numbers back.
</Callout>
