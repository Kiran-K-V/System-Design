## The problem

Three questions come up again and again at scale.

1. **Is this key in this file?** An LSM tree (lesson [4.3](/learn/04-data/indexing/)) holds many files. A read for a missing key would open each one. Each check is a disk read of about 100 µs.
2. **How many unique visitors did we have today?** A set of 1 billion 64-bit IDs takes at least 8 GB. You want that number per page, per day.
3. **Which items are most frequent?** A table of counters for every search query grows with the number of distinct queries.

An exact answer costs memory that grows with the number of items. Give up a little accuracy and memory becomes **small and fixed**. These structures are called **probabilistic**. Each one trades a known, tunable error for a very small size.

## Bloom filter: is it in the set?

A **Bloom filter** answers "is X in the set?" with one of two replies.

- **Definitely not.** Always correct.
- **Possibly yes.** Usually correct. Sometimes wrong. This is a **false positive**.

It has no **false negatives**.

It is an array of **m** bits, all 0, and **k** hash functions. A hash function turns an item into a number. Take it modulo m and you get a bit position.

- **Add** an item: compute its k positions and set those bits to 1.
- **Query** an item: compute its k positions. If any bit is 0, the item is **definitely not** there. If all are 1, it is **possibly** there.

Step through a tiny filter: 12 bits, 3 hashes.

A bit is never reset to 0, so an item that was added always finds its bits set. That is why false negatives cannot happen. Bits are shared, so other items can set all of a new item's bits by accident. That is a false positive.

### The formula

After n items, the false-positive rate is about

**ε ≈ (1 − e^(−kn/m))^k**

For a fixed m and n, the best number of hashes is

**k = (m / n) × ln 2**

For a target rate ε, the bits needed per item are

**m / n = −ln(ε) / (ln 2)²**

Compute one by hand. You want ε = 1% for n = 1,000,000 items.

- m / n = −ln(0.01) / 0.4805 = 4.605 / 0.4805 = **9.585 bits per item**.
- m = 9.585 million bits, which is 1.198 MB. About **1.2 MB**.
- k = 9.585 × 0.693 = 6.64. Hashes come in whole numbers, so use **k = 7**.
- Check: ε = (1 − e^(−7/9.585))^7 = (1 − 0.4818)^7 = 0.5182^7 = **1.0%**.

For ε = 0.1% the cost is 14.4 bits per item. Each 10× drop in error costs about 4.8 more bits per item. Memory grows slowly as you ask for accuracy.

Now try it. Add words, ask about words, and change m and k. Watch the bits fill up and the expected error climb.

<BigBloomLab client:visible />

Two warnings.

- **It cannot delete.** Clearing a bit might also clear it for other items, and then those items would get a false negative. (There are variants with counters that allow deletes.)
- **It must be sized for n.** If you plan for 1 million items and add 2 million to the same filter, the rate changes. With k = 7, the rate is about 16%, not 1%.

Lesson 4.3 showed the main use. Each SSTable file keeps a Bloom filter in memory. A read checks it first and skips files that say "definitely not". Cassandra and PostgreSQL also use Bloom filters to skip disk reads for rows that are not there, as the [Wikipedia article](https://en.wikipedia.org/wiki/Bloom_filter) lists.

## HyperLogLog: how many unique items?

**HyperLogLog** (HLL) estimates the number of **distinct** items in a stream. It uses a fixed memory, and it never stores the items.

The idea is a coin game. Hash each item to a random bit string. A random string starts with 0 half the time. The string starts with 00 a quarter of the time. With k zeros at the start, that happens 1 time in 2^k. If you saw a hash with 10 leading zeros, you probably looked at around 2^10 = 1,000 distinct items.

One lucky hash makes a noisy guess. So HLL keeps **m registers** and splits the items among them.

1. Hash the item.
2. The first p bits pick a register (m = 2^p registers).
3. In the remaining bits, count the leading zeros and add 1. Call this the **rank**.
4. The register keeps the **maximum** rank it has seen.

Do it by hand with p = 2, so 4 registers, and 8-bit hashes.

| Item | Hash | Register (first 2 bits) | Rest | Rank |
|---|---|---|---|---|
| a | `01 000101` | 1 | `000101` has 3 leading zeros | 4 |
| b | `10 110000` | 2 | `110000` has 0 | 1 |
| c | `01 100000` | 1 | `100000` has 0 | 1, register 1 stays 4 |
| d | `00 001000` | 0 | `001000` has 2 | 3 |
| a again | `01 000101` | 1 | same as before | 4, nothing changes |

The registers end as **[3, 4, 1, 0]**. Adding "a" a second time changed nothing. A repeat gives the same hash and the same rank, so it never counts twice. The estimate combines all registers with a harmonic mean, which stops one lucky register from dominating (Flajolet et al., 2007).

The error depends only on the number of registers. The standard error is **1.04 / √m**.

| Registers m | Standard error |
|---|---|
| 64 | 13% |
| 1,024 | 3.25% |
| 16,384 | 0.81% |
| 65,536 | 0.41% |

Four times the registers halves the error. The Redis implementation uses 16,384 registers of 6 bits each. That is 16,384 × 6 / 8 = 12,288 bytes. The result matches the "up to 12 KB" in the Redis docs, with a standard error of 0.81%. It counts up to 2^64 items.

Compare: exact counting of 1 billion IDs takes at least 8 GB. HLL takes 12 KB. That is about 650,000 times smaller (8 GB / 12 KB).

Two more facts. Two HLLs merge by taking the **maximum** of each register pair. The result counts the union, with no loss of accuracy. Redis exposes this as `PFADD`, `PFCOUNT`, and `PFMERGE`. And HLL **cannot answer "did user X visit?"**. It keeps no items, only the maxima.

## Count-Min Sketch: how often?

A **Count-Min Sketch** (CMS) estimates how many times each item appeared. It is a grid of counters with **d** rows and **w** columns. Each row has its own hash function.

- **Add** an item: in every row, add 1 to the counter its hash picks.
- **Query** an item: read its counter in every row and take the **minimum**.

Two different items can share a counter, which only adds to it. So every counter is at least the true count. The minimum is the least inflated one. The result **never underestimates**.

Here is a tiny grid: w = 4, d = 2. We add a three times, b once, and c twice. The hashes put a, b in column 1 of row 1, and a, c in column 0 of row 2.

| | col 0 | col 1 | col 2 | col 3 |
|---|---|---|---|---|
| Row 1 | 0 | 4 (a + b) | 0 | 2 (c) |
| Row 2 | 5 (a + c) | 0 | 1 (b) | 0 |

- Query a: min(4, 5) = **4**. The true count is 3. Over by 1.
- Query b: min(4, 1) = **1**. Exact, because row 2 had no collision.
- Query c: min(2, 5) = **2**. Exact.
- Query an item never added, such as z. The item z hashes to row 1 column 1 and row 2 column 0. Its estimate is min(4, 5) = **4**. The true count is 0.

The guarantee: with width w = ⌈e / ε⌉ and depth d = ⌈ln(1 / δ)⌉, the estimate is at most the true count plus **ε × N**, with probability at least 1 − δ. N is the total of all counts. For ε = 0.01 and δ = 0.01: w = ⌈271.8⌉ = 272 and d = ⌈4.6⌉ = 5. That is 1,360 counters.

The error is relative to the **total** N, not to the item. With N = 1,000,000 the bound is ±10,000. An item seen 50,000 times is measured well. An item seen 50 times is swamped. So CMS is for **heavy hitters**, the items that are frequent. A common design keeps a CMS plus a small heap of the current top items.

## Trade-offs

| Structure | You gain | You pay | Choose when |
|---|---|---|---|
| Exact hash set | Exact answer, can list and delete | Memory grows with n | n is small |
| Bloom filter | ~10 bits per item, one-sided error | No delete, no list, must size for n | "Skip the lookup if surely absent" |
| HyperLogLog | 12 KB for any count, mergeable | Distinct count only, ~1% error | Unique visitors, unique queries |
| Count-Min Sketch | Fixed memory frequencies, never underestimates | Overcounts, weak for rare items | Heavy hitters, rate counting |

## Interview lens

<Callout type="tip">
Match the structure to the question. Name the error type: "Bloom filter for membership: it can say yes wrongly, never no wrongly. HyperLogLog for distinct counts: about 1% error in 12 KB. Count-Min Sketch for frequencies: it only overcounts". Give a size: "10 bits per item for a 1% false-positive rate". Say what happens on a false positive. For example, "we do the real lookup and pay one wasted read, so it is safe".
</Callout>

<Callout type="mistake">
Do not say a Bloom filter has false negatives. Do not use one where a false positive causes harm, for example "this username is taken". Check the real store when the filter says maybe. Do not claim HyperLogLog can tell whether one user visited. And do not forget that Count-Min Sketch never underestimates: the true count is at most the estimate.
</Callout>

<Callout type="deep" title="Why 6 bits per register is enough">
A register holds a rank, which is a count of leading zeros plus 1. With a 64-bit hash and 14 bits used for the register choice, the rank is at most 51. A 6-bit field holds 0 to 63. The Redis source comments that 6 bits are "enough to count up to 63 leading zeroes". A register that stores a small number is why 16,384 of them fit in 12 KB.
</Callout>
