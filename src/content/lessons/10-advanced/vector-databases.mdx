## The problem

A user types "cheap flights to somewhere warm". No document holds those exact words. A keyword index (the [Elasticsearch](/learn/backend/08-technologies/elasticsearch/) lesson) finds documents that contain the words. It does not find documents that **mean** the same thing.

An **embedding** model fixes the input side. It turns a text, an image, or a song into a **vector**. A vector is a list of d numbers, for example d = 768. Each position in the list is a **dimension**. The model is trained so that items with similar meaning get vectors that are close together. Now "find similar" becomes "find the stored vectors nearest to this query vector". That is a **nearest-neighbor search**, and asking for the top k is **k-nearest-neighbors**, or kNN.

A B-tree (the [Indexing](/learn/backend/04-data/indexing/) lesson) cannot help. It sorts one number. A vector has hundreds of dimensions, and "nearest" is not "next in sort order".

## Measuring "close"

Three measures are common. Take a query A = (1, 0) and a stored vector B = (1, 1).

- **Dot product**: A · B = 1×1 + 0×1 = **1**. Higher means more alike.
- **Cosine similarity** is the dot product divided by the two lengths. The result is (A · B) / (|A| |B|) = 1 / (1 × 1.414) = **0.707**. It is the cosine of the angle between the vectors. Range: −1 to 1. **Cosine distance** is 1 − 0.707 = **0.293**.
- **L2 distance** (straight-line): √((1−1)² + (0−1)²) = **1**. Lower means closer.

Cosine looks only at **direction**. Dot product mixes direction and length. L2 looks at the gap. They can disagree. Move B in the widget and watch C = (3, 0) win or lose.

At A = (1, 0) and B = (1, 1), C wins on cosine (it points the same way). C also wins on dot product (it is longer). But **B** wins on L2 (distance 1 against 2). If every vector is scaled to length 1, dot product and cosine give the same ranking. Check what your model outputs and pick the measure it was trained for.

**pgvector** is a free add-on for the PostgreSQL database that stores vectors and searches them. We use it as our real example, and the last sections say more. In its queries you pick the measure with an operator. These are `<->` for L2 distance, `<#>` for negative inner product (the dot product with its sign flipped, so that smaller still means closer), `<=>` for cosine distance, and `<+>` for L1 distance (add up the gaps on each dimension).

## Naive solution: compare to everything

Exact kNN computes the distance from the query to **every** stored vector, then keeps the best k. The cost per query is N × d.

A **float32** is a decimal number stored in 4 bytes. A million vectors of 768 numbers each take a few gigabytes. Every query must read all of it from memory and do hundreds of millions of multiplications. Just streaming that much memory takes a noticeable fraction of a second, before any math.

That is fine for 10,000 vectors, and too slow for 100 queries per second over a million. The result is **perfect**: its recall is 100%. **Recall** is the share of the true top k that you return. pgvector does exact search by default and gets perfect recall.

To go faster we accept an **approximate** nearest neighbor (ANN) search: it may miss a true neighbor. Two index families dominate.

## IVF: look only in the nearest buckets

**IVF** (inverted file) groups vectors into clusters. A clustering step (k-means, which repeatedly moves center points toward the middle of the vectors nearest to them) picks a number of centers. That number is called **lists**. Each vector joins the list of its nearest center. A query finds its nearest `probes` centers and scans only those lists.

In pgvector this is the IVFFlat index. The README suggests `lists` = rows / 1,000 up to 1 million rows, and √rows above that. The default `ivfflat.probes` is 1.

Say the lists are about equal in size. With `probes = 1`, a query compares to the centers and then scans one list. That is a tiny share of the full scan. With `probes = 10` it scans ten lists. That is still a small share of exact, and more accurate.

The miss: a query near a cluster border has its true neighbor in the **next** cluster. With probes = 1 you never look there. More probes raise recall and cost.

## HNSW: a graph with express lanes

**HNSW** (hierarchical navigable small world) is a graph. Each vector is a node linked to some near neighbors. A search starts somewhere and keeps stepping to whichever linked node is closer to the query. This is a **greedy** walk. A single graph walks slowly across a big space. HNSW stacks layers, like the express and local lanes of a metro.

- Every vector is in layer 0. A vector is also placed in layer 1 with probability 1/M, in layer 2 with probability 1/M², and so on. The paper's choice is mL = 1/ln M.
- Each layer holds about one sixteenth of the layer below, for M = 16. A million vectors shrink to a handful of nodes within five layers. The top layer is tiny, so the first steps cross the space fast.
- A search enters at the top, walks greedily to the node closest to the query. The search then drops one layer and repeats from there. On layer 0 it widens the walk with a candidate list of size **efSearch**.

The animation shows the knob that matters most. With efSearch = 1 the walk stopped at point 13, a local minimum. The true nearest, point 5, was two hops away behind a slightly worse point. With efSearch = 3 the search kept that worse point as a candidate and found point 5. This is the **recall versus latency** trade: a bigger candidate list reads more nodes and misses less.

### The three parameters

| Parameter | What it controls | pgvector default | Effect of raising it |
|---|---|---|---|
| `m` (M) | Links per node per layer. The paper allows 5 to 48. Layer 0 may hold up to 2M. | 16 | Better recall, more memory, slower build |
| `ef_construction` | Candidate list size while building the graph | 64 | Better graph and recall, slower inserts and build |
| `hnsw.ef_search` (efSearch) | Candidate list size per query | 40 | Better recall, slower query |

Only efSearch can change per query, with no rebuild. Memory: the paper estimates about 60 to 450 bytes per element for M from 6 to 48. That memory is **on top of** the vector itself. The paper reports that search cost scales roughly logarithmically in tests. That is an empirical result, not a guarantee.

### IVF or HNSW

The pgvector README says IVFFlat builds faster and uses less memory, but gives a worse speed-recall trade-off than HNSW. HNSW is the usual default. IVFFlat needs data first, because its centers come from the data. HNSW can be built on an empty table.

## Filtering breaks the index

Real queries add a condition: "the 10 nearest products **in category 7**". An approximate index is scanned first, and the filter is applied **after** it. If a condition matches only a small share of the rows, most of the scan's candidates fail the filter. Only a few survive. You asked for 10 and get fewer.

pgvector offers three fixes.

- **Iterative index scans**: the index keeps scanning until enough rows pass the filter.
- **A B-tree index on the filter column**, when the filter matches a small share of rows. Postgres then finds those rows by index and sorts them by distance exactly.
- **Partial indexes or partitions** when the filter has few distinct values, or one per tenant (one per customer of your product).

The same trap shows up in every vector store. Ask how it combines the filter with the index.

## Where vectors live

As said above, pgvector adds a `vector` type and these indexes to PostgreSQL (the [PostgreSQL](/learn/backend/08-technologies/postgresql/) lesson). Your vectors sit next to your rows, in the same transaction (a group of changes that succeed or fail together) and the same backup. The `vector` type holds up to 2,000 dimensions in an HNSW index, and `halfvec` up to 4,000. Dedicated vector databases exist too. They add features for spreading data over many machines around the same index ideas.

| Fact | Value | Source |
|---|---|---|
| HNSW graph memory | ~60 to 450 bytes per element, M 6 to 48 | HNSW paper |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Exact scan | 100% recall, no index | N × d work per query | Under ~100,000 vectors, or a small filtered set |
| IVF | Fast build, small index | Recall depends on probes; centers need data | Memory tight, data rarely changes |
| HNSW | Best speed for a given recall | More memory and a slower build than IVF | Default for live search |
| pgvector | Vectors with your SQL rows and transactions | One Postgres node's limits | Up to the scale one database serves |
| Dedicated vector store | Sharding and scale features | A new system to run and sync | Billions of vectors |

## Interview lens

<Callout type="tip">
Explain the pipeline in order: "An embedding model turns items into vectors. I store them with an HNSW index. A query is embedded and I fetch the top k by cosine". Then name the trade-off: "HNSW is approximate. I tune efSearch for recall against latency". Mention filters before you are asked: "I filter by tenant with a partition or an iterative scan, because a post-filter can return fewer than k rows".
</Callout>

<Callout type="mistake">
Do not say HNSW is exact, or that its search is guaranteed O(log N). The paper shows logarithmic scaling in experiments, not a proof. Do not say "raise M to lower latency". M mostly buys recall, at the price of memory. And do not forget that a filtered ANN query can return fewer than k rows.
</Callout>

<Callout type="deep" title="Why not a k-d tree?">
A k-d tree splits space one axis at a time, like a quadtree (the [Proximity Search](/learn/backend/10-advanced/proximity-search/) lesson). It works in 2 or 3 dimensions. In hundreds of dimensions, a query ball touches almost every cell, and the tree degrades toward a full scan. Graph methods like HNSW avoid space cutting. They follow the data's own neighbor structure instead.
</Callout>
