## The problem

You run one database node. It is correct, fast, and doing fine. Then three things happen.

1. **The machine dies.** A disk fails or the operating system crashes (a kernel panic). Your app is down until you rebuild it from a backup. A nightly backup means you lose up to a day of data.
2. **You patch the machine.** Even planned restarts take the app offline.
3. **Reads outgrow it.** The [Numbers to Know](/learn/backend/01-one-machine/numbers-to-know/) lesson says one node handles roughly 10K–50K indexed reads per second. Your product needs 200K.

The answer to all three is the same: **keep copies of the data on other machines.** That is **replication**. Each copy is a **replica**.

Replication does three jobs. It keeps the system **alive** when a machine dies. It adds **read capacity**, because any replica can answer a read. And it can put data **near users**. A replica (say, in Frankfurt) answers European reads with a few ms of network time, not ~100 ms (the [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson).

It does **not** add write capacity. Every replica must apply every write. Seven replicas of a database that tops out on writes still top out at the same rate. Splitting writes is sharding, the next lesson.

It does not replace a backup either. A follower copies a mistake as fast as it copies a good write. In 2017 GitLab lost hours of data that way. [The story](#incident) comes after the trade-offs.

Copies also help availability. If one node is down for a few hours a year, two nodes that fail **independently** are both down together almost never. That assumes a perfect, instant failover. Neither assumption holds in real life. Failover takes time and failures are often correlated. But the direction is right: copies make downtime much rarer.

## Naive: let the app write to both

The first idea is the simplest. The app sends every write to database A and to database B. Watch what two clients can do to it.

<DualWriteRace client:visible />

Two writes to the same row reached the two databases in opposite order. Each database applied them correctly in the order it saw. They ended in different states, forever, with no error.

The root cause: **nothing owns the order of writes.** Any design where several writers push to several copies has this flaw. The fix is to choose one machine to decide the order. Everyone else follows it.

## The mechanism: one leader, one log

In **leader-based replication** (also called primary-replica, or leader-follower):

- One node is the **leader**. It accepts all writes.
- The leader writes each change to its log. This is the write-ahead log from the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson: a file where the database writes every change before it applies it. The log is already an ordered list of every change.
- Other nodes are **followers**. The leader sends them the log. Each follower replays it in order.
- Followers serve reads. They never accept writes.

Because every follower replays the same ordered log, every follower reaches the same state. The ordering problem is gone: the leader's log **is** the order.

This is why the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson ended on "replicas replay the same log". A follower is a database in permanent crash recovery.

### What travels in the log

Systems differ in what a log record contains.

| Format | What is shipped | Example | Catch |
|---|---|---|---|
| Physical log | The raw storage-level change records | PostgreSQL streaming replication | Follower must run the same storage format and version |
| Statement | The SQL text, re-run on each follower | MySQL `STATEMENT` | A function like `UUID()` or `RAND()` can give a different value on each follower |
| Row | The new contents of each changed row | MySQL `ROW` (the default) | Bigger log for large updates |

MySQL's manual states that row-based logging is its default method. It exists because statements can be unsafe to re-run.

### The key choice: when does the leader say OK?

This is the most important decision in replication. After the leader has the write in its own log, does it answer the client **now**, or **wait** for followers? Step through both cases. Each one ends with the same leader crash.

<ReplicationCommit client:visible />

The two designs have names.

- **Asynchronous.** The leader answers after its own fsync (the call that forces data onto the disk, so a power cut cannot lose it). Fast. If the leader dies before shipping the record, an acknowledged write is lost. PostgreSQL's streaming replication is asynchronous by default.
- **Synchronous (or semi-synchronous).** The leader waits until a follower confirms it has the record. MySQL's semi-synchronous mode waits for one acknowledgement by default. The write now lives on two machines before the client hears OK.

Waiting for **every** follower is a trap. One slow or dead follower then stalls every commit. PostgreSQL's manual warns that commits "may never be completed if any one of the synchronous standbys should crash". MySQL's answer: after a timeout (default 10 seconds) the leader gives up waiting and reverts to asynchronous replication. A common design is one synchronous follower plus the rest asynchronous. If the synchronous follower dies, another takes its role.

PostgreSQL also lets you pick **how far** the follower must get. `remote_write` waits until the follower's operating system has the record. `on` waits until it is flushed to the follower's disk. `remote_apply` waits until the follower has replayed it, so a read on the follower will see it.

## Replica lag

Even in the best case followers are behind. The delay between "the leader committed" and "the follower shows it" is **replica lag**. PostgreSQL's manual says it is typically under one second for asynchronous streaming. Aurora (Amazon's managed cloud database) reports lag that is usually much less than 100 ms. It says the lag grows when the write rate is high. Lag is not constant. It spikes under load, big transactions, or a slow follower disk.

Lag is invisible when you look at one machine. It shows up as strange user experiences. A user saves a profile, the page reloads from a follower, and the old profile appears. The write worked. The read was early.

Play with this. Set the user's read delay to 300 ms. Follower 2 is 1,200 ms behind. Then try each routing policy.

<ReplicaLagSim client:visible />

Three fixes for "I cannot see what I just wrote":

- **Read the leader after a write.** For a short window, send that user's reads to the leader. Simple. It adds leader load.
- **Use a position token.** The write returns a log position. A follower answers only if it has reached that position. Cosmos DB (Microsoft's cloud database) does this with a session token, in a mode it calls session consistency. The next lesson names the guarantee: read-your-writes.
- **Wait for the follower.** Use `remote_apply`-style waits (the PostgreSQL setting above) for the few writes that need it.

Lag also causes a second oddity: a user who reads from two followers can see data go **backward** in time. The next lesson calls it a monotonic-reads violation and shows the fix.

## Failover: when the leader dies

A leader will die. **Failover** means promoting a follower to take its place. It sounds easy and has three traps.

One idea helps in the walk below. Each reign of a leader gets a number, called an **epoch**. The first leader has epoch 7, the next one 8. A higher epoch always means a newer leader. Think of a passport with an issue date: when two exist, the newer one wins. Step through the traps.

<Failover client:visible />

1. **Detection is a guess.** You cannot tell a dead leader from a slow network. A short timeout causes false failovers. A long one extends the outage.
2. **Choosing the new leader.** Pick the follower with the longest log. With asynchronous replication the best follower may still lack the last few writes. Those are lost. This is the data-loss window from the first animation.
3. **Split brain.** The old leader may return still thinking it leads. Two leaders accept writes and the data diverges. The defense is **fencing**: every request carries the epoch of the leader that sent it, and everyone rejects a lower epoch than the highest they have seen. Picture a hotel that re-keys a room. The old key card stops working the moment the new one is issued. Here the old leader holds epoch 7. After failover the cluster is on epoch 8. Its writes are refused, so it cannot corrupt the new leader's data.

PostgreSQL promotes a standby with `pg_ctl promote` or `pg_promote()`. Aurora promotes a reader automatically if the writer fails. Aurora notes that during the switch, reads and writes to the old primary fail with an exception. Plan for a brief error window.

One question is left: **who decides** who is leader and hands out those numbers? If one machine decides, that machine is a new **single point of failure**: one machine whose crash stops everything. The [Consensus](/learn/backend/04-data/consensus/) lesson answers it.

## Other layouts

Single-leader is the default. Two other layouts exist.

<ReplicationTopologies />

- **Multi-leader** puts one leader in each region, so writes stay local. The price is conflicts. Two leaders can accept different writes to the same row at once. "Last write wins" keeps the write with the later clock time and silently drops the other. Dynamo-style systems (Dynamo is Amazon's key-value store) instead keep both versions and hand them to the application. The Dynamo paper says both versions "must be kept and presented to a client (upon a read) for semantic reconciliation".
- **Leaderless** sends each write to several nodes and reads from several nodes. A write succeeds after `W` of `N` replicas accept it. A read asks `R` replicas. When `R + W > N`, a read overlaps at least one node that has the latest write. Dynamo describes this and says its common configuration is `(N, R, W) = (3, 2, 2)`. It also uses **hinted handoff**. If a replica is down, another node holds the write. That node hands the write over when the first node returns. The [Consensus](/learn/backend/04-data/consensus/) lesson builds the quorum math.

## Numbers

| Fact | Value | Source |
|---|---|---|
| Replica lag, PostgreSQL async streaming | typically under 1 s | PostgreSQL docs |
| Replica lag, Aurora | usually much less than 100 ms, higher under heavy writes | Aurora docs |
| Replicas per Aurora cluster | up to 15 | Aurora docs |
| MySQL semi-sync default acks | 1 | MySQL docs |
| MySQL semi-sync timeout before async | 10,000 ms | MySQL docs |
| Dynamo common `(N, R, W)` | (3, 2, 2) | Dynamo paper |
| Network round trip, same data center / across an ocean | ~0.5 ms / ~100 ms | The [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson |
| Sync commit to a follower 70 ms away | +~70 ms per write | Derived: one round trip |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Asynchronous | Fast commits. Leader never waits. | Acknowledged writes can be lost in a crash. Lag. | Feeds, analytics, anything you can replay |
| Semi-synchronous (1 follower) | No loss if the leader dies alone | One round trip per write. A slow follower hurts. | Orders, payments in one region |
| Synchronous to a remote region | Region-level durability | Writes cost a cross-region round trip | Rare. Strict durability across regions |
| Read from followers | Read capacity, local reads | Stale reads, lag management | Read-heavy workloads |
| Multi-leader | Local writes in every region | Conflict resolution | Multi-region apps that tolerate merges |
| Leaderless quorum | No failover step. High availability. | Conflicts, tuning `R` and `W` | Always-on key-value stores |

## A real outage: GitLab, 2017

Every idea in this lesson met in one night at GitLab. The company published a full postmortem: the public report a team writes after an outage, with what broke and why.

<IncidentCard
  org="GitLab.com"
  date="31 January 2017"
  title="A follower fell behind. The fix for it erased the leader."
  cost="GitLab.com was down for about 18 hours. Database changes made between 17:20 and 00:00 UTC were lost for good. GitLab's estimate: about 5,000 projects, 5,000 comments, and 700 new user accounts. Git repositories were not affected."
  missing="A follower is not a backup. It copies deletes as faithfully as writes. Keep the leader's log long enough for a slow follower, or archive it somewhere else. Then test a full restore on a schedule. GitLab's own finding: the restore was never tested because nobody owned it."
  source="https://about.gitlab.com/blog/2017/02/10/postmortem-of-database-outage-of-january-31/"
  sourceLabel="GitLab, Postmortem of database outage of January 31"
>

GitLab.com ran one PostgreSQL leader, `db1`, and one follower, `db2`. The follower existed only for failover.

1. **Lag.** A spam attack raised the write load. At about 23:00 UTC the follower started to lag behind.
2. **The follower breaks.** It needed log segments that the leader had already deleted. GitLab did not archive the log anywhere else. So the follower had to be rebuilt from zero. A rebuild starts by deleting the follower's data directory.
3. **The wrong machine.** After several failed tries at the rebuild, an engineer ran the delete on `db1`, the leader. They stopped it after a second or two. About 300 GB was already gone.
4. **The backups.** The follower could not help. It was empty, half way through its rebuild. The nightly export with `pg_dump` (PostgreSQL's export tool) had been failing without anyone knowing. It was version 9.2, and the database was 9.6. The failure emails were rejected by the mail server, so nobody saw them. Cloud disk snapshots were on for other servers, but not for the databases.
5. **Luck.** An engineer had taken a manual disk snapshot about 6 hours earlier, for unrelated work. That copy saved most of the data. Copying it back over slow disks took about 18 hours.

</IncidentCard>

Map it to this lesson. Step 1 is replica lag under a write spike. Step 2 is the opposite of the slot problem in the deep dive below: here the leader kept too **little** log, not too much. Step 4 shows why a replica is not a backup.

## In practice

<Callout type="tip">
Say what replication is **for** before you add it. "I add two followers in other zones (separate data centers in one region) for failover. I read from them for the feed, which tolerates a second of lag. Account balance reads go to the leader." Then name the commit mode: "Semi-synchronous to one follower, so a single machine loss cannot drop an acknowledged write."
</Callout>

<Callout type="mistake">
Do not say "add replicas to scale writes". Every replica replays every write, so write capacity stays the same. Do not say "failover is automatic, so it is solved" either. Name the guess in detection, the lost tail of the log, and split brain with fencing.
</Callout>

<Callout type="deep" title="Why replication slots can fill your disk">
A leader must keep log segments until every follower has them. PostgreSQL's replication slots enforce this. A slot is a marker that remembers how far a follower has read. The manual warns about slots. They "can cause the server to retain so many WAL segments that they fill up the space allocated for pg_wal". WAL means write-ahead log, and a segment is one piece of it. A follower that is down for hours can make the leader run out of disk. Set a cap such as `max_slot_wal_keep_size` and alert on lag.
</Callout>
