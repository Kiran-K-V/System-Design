## The problem

In every design you pick a database. The weakest reasons name a brand: "I would use Mongo." The next weakest repeat a slogan: "SQL for structured data, NoSQL for scale." Neither is an argument.

A real story shows what an argument looks like. Discord stored its chat messages in MongoDB (a database that stores nested, JSON-like records). In its 2017 engineering post, the team says that around November 2015 it reached 100 million stored messages. The team also says that the data and its index could no longer fit in RAM. Lesson 1.2 says RAM (the fast, temporary memory of a machine) is ~1,000x faster than SSD. They needed a store that grows by adding machines. It has predictable reads for one pattern: "give me the recent messages in this channel". They moved to Cassandra, a database built to spread data over many machines. By the time of the post, they ran a 12-node cluster (12 machines working as one database) with replication factor 3. That means every piece of data is stored on 3 of those machines, as in lesson 4.6. They also had more than 120 million messages a day.

Notice what the story does **not** say. It does not say MongoDB is bad. It says one access pattern, at one size, hit one limit.

## Naive: choose by label

Two slogans, and where each fails.

**"NoSQL has no schema."** It has no schema **enforced by the database**. The schema moves into your code. MongoDB's own docs describe a flexible data model where documents in one collection need not share fields. The docs also advise adding schema validation where you need stricter control. Your code still expects `user.name` to exist.

**"SQL does not scale."** One relational server holds more than people think. Lesson 4.3 used a 1-billion-row, 200 GB table. PostgreSQL's limits are a 32 TB table, a 1 GB field, and an unlimited database size. The real limit is not size. It is that all writes go through one primary machine (the leader of lesson 4.6) until you shard (lesson 4.7).

The slogans fail because they sort databases by **what they are**. Sort by **what they are good at answering**.

## The mechanism: five shapes, five bets

Every database answers one kind of question cheaply: its **primary access path**. That is the way you usually ask for data, such as "by this key" or "all rows where this column matches". The data is laid out to make that path fast, like a phone book is laid out for lookup by surname. Questions off the path are slow, awkward, or impossible. That is the bet.

Now the details that decide the choice.

**Relational.** The default, because it keeps every option open. You can add an index later for a question you did not foresee (lesson 4.3). You get multi-row transactions (lesson 4.4). You pay when write volume or data size outgrows one primary machine. Use it for money, inventory, and anything with complex queries.

**Key-value.** Redis maps a key to a value of up to 512 MB. Redis is a fast key-value store that keeps data in memory. Its `INCR` command adds 1 to a number. It is **atomic**, meaning it happens in one indivisible step. The Redis docs state that two clients incrementing one key never race, so no count is lost. DynamoDB is Amazon's managed key-value and document database. It places each item in a **partition** (one slice of the data, held on one machine) chosen by its partition key. Use it for sessions, caches, counters, and rate limits (a cap on how many requests a user may send per minute). Do not expect `WHERE`.

**Document.** MongoDB stores one record as a nested, JSON-like **document**. Its rule: data accessed together should be stored together. You choose per relationship whether to **embed** (nest inside) or **reference** (store the id). Embed what is bounded and read together. Reference what is unbounded or shared. Embedding without a bound has a hard failure. A DynamoDB item may be at most 400 KB. If each post is ~300 B, a user item that embeds all posts overflows. That happens after about 400 KB / 300 B = ~1,300 posts. A prolific user will pass that.

**Wide-column.** Cassandra splits a row's key in two. The **partition key** is hashed to choose the node (by consistent hashing, lesson 4.8). The **clustering key** sorts rows inside a partition. Storage is an LSM tree (lesson 4.3), so writes are cheap. The Cassandra docs show the design method: list your queries first, then create a table for each query. The same data appears in several tables with different keys. This is denormalization (storing the same fact in more than one place so reads need no join, lesson 4.1) made mandatory.

Discord's key shows the care this needs. They first used `(channel_id, message_id)`. A busy channel makes one huge partition, and they saw partitions over 100 MB. So they added a time bucket to the partition key: `((channel_id, bucket), message_id)`. Each bucket holds about 10 days of messages. The goal is to stay under 100 MB. The lesson: **a partition key must bound partition size, or one key becomes a hot, oversized spot**.

Cassandra also lets you choose consistency per request: `ONE` (one replica answers), `QUORUM` (a majority, n/2 + 1), or `ALL`. Why those words matter is lesson 4.6 and lesson 4.10.

**Graph.** Neo4j is a graph database. It stores nodes, typed relationships, and properties. Relationships are stored natively alongside the nodes, so walking an edge (following one relationship) does not need a join. Use it when the question is a path: friends of friends, shortest route, fraud rings. For counts over all data, a relational or column store fits better.

### Know the key-value limits

Wide stores publish hard limits. Use them. DynamoDB delivers at most 1,000 write units and 3,000 read units per second **per partition**. One write unit is one write per second of an item up to 1 KB. A 3 KB item costs 3 write units.

- A high write rate needs many partitions, and only if keys spread evenly.
- One hot key has a hard ceiling on writes per second, and bigger items lower that ceiling. No setting changes this. The fix is a different key.

The docs tell you to design for "uniform activity across all partition keys". That sentence is the partition-key lesson again.

## Choosing: ask in this order

<DecisionFlow />

The order matters. Relational comes first because it is the default that keeps options open. You leave it only for a reason you can state. Notice each exit is a property of the **access pattern**, not of the data's look.

Most real systems use more than one store. A common pattern: relational is the source of truth, a cache sits in front (Module 5), a search index serves text queries (lesson 4.3), and a log of changes keeps them in sync (lesson 6.5). That is called **polyglot persistence**: using several kinds of database, each for what it does best. It works if there is one **source of truth**, the one store whose data is final, and the others can be rebuilt from it.

## Numbers

| Fact | Value | Source |
|---|---|---|
| DynamoDB max item size | 400 KB | AWS FAQ |
| DynamoDB per-partition limit | 3,000 read units/s, 1,000 write units/s | AWS docs |
| 1 write unit / 1 read unit | one write/s up to 1 KB / one strongly consistent read/s up to 4 KB | AWS docs |
| DynamoDB default table throughput | 40,000 read and 40,000 write units (can be raised) | AWS docs |
| Redis max value size | 512 MB | Redis docs |
| PostgreSQL table / field limit | 32 TB (8 kB pages) / 1 GB | PostgreSQL docs |
| Cassandra QUORUM | n/2 + 1 replicas must answer | Cassandra docs |
| Discord, 2017 | 12 nodes, replication factor 3, 120M+ messages/day, partitions kept under 100 MB | Discord blog |

## Trade-offs

| Shape | You gain | You pay | Choose when |
|---|---|---|---|
| Relational | Joins, constraints, transactions, any new query | One primary for writes until sharded | Money, inventory, complex queries. The default. |
| Key-value | Fastest get/put by key; easy to scale by key | No query by value | Sessions, caches, counters |
| Document | One read per aggregate; flexible fields | Copies and app-side joins | Varied records read whole: catalogs, profiles |
| Wide-column | Linear write scale; per-request consistency | Every query must fit a partition key; one table per query | High-volume writes with known access: messages, events |
| Graph | Multi-hop traversal without joins | Weak at bulk aggregates | Relationship-heavy questions |

## In practice

<Callout type="tip">
Say the access pattern before the database: "Suppose the hot read is the latest 50 messages in a channel. The read runs at an assumed 100,000 per second. The hot write is an append. So I would partition by channel and time bucket and sort by message id. That is a wide-column fit." Then say what you give up: "I lose ad hoc queries, so search goes to a separate index." Naming the cost is what makes the choice sound like engineering.
</Callout>

<Callout type="mistake">
Four wrong sentences to avoid. "NoSQL has no schema." "SQL cannot scale", without a number. "DynamoDB can answer any query": it answers by key and by indexes you declare. "Cassandra is always consistent": `ONE` and `QUORUM` trade consistency for latency. And never say "graph database" because the data is connected. Almost all data is connected. Use a graph store only when the **queries** walk many hops.
</Callout>

<Callout type="deep" title="Why wide-column and key-value stores scale by key">
A hash of the key picks the machine. Any request for one key goes to one machine and needs no coordination with the rest. Throughput grows by adding machines, as long as keys spread evenly. A relational query with a join across two tables may need rows from many machines, and a transaction across rows needs agreement between them. Those are the exact features these stores drop. The price of scale is the removal of the features that need coordination.
</Callout>
