## The problem

You run a cache with four servers. A **cache** is a fast store that keeps copies of answers, so your database does not repeat the same work. Each item has a **key**, such as a user id. You must decide which server holds which key.

You use the simplest rule you know: `server = hash(key) % 4`. A **hash function** turns any key into a big, evenly scrambled number. The same key always gives the same number. The `%` sign is the remainder after division, so `% 4` gives 0, 1, 2, or 3. That number picks the server. Load is even.

Then traffic grows. You add a fifth server. The rule becomes `hash(key) % 5`. What happens to your keys?

Almost all of them move. Each moved key is a **cache miss**: the new server does not hold it, so the request falls through to the database. Your database now gets hit by nearly every request at once. A change that should add capacity causes an outage.

The same trap exists for shards of a database (the [Sharding](/learn/backend/04-data/sharding/) lesson: separate slices of one big table, each on its own machine), not only for caches. Any time you place data by `hash % N`, a change in N is a re-shuffle of the whole data set.

## Naive solution: hash % N

The math is simple. A key keeps its server only when `h % N` equals `h % (N+1)`. Over any block of `N × (N+1)` consecutive hashes, that happens for exactly `N` of them. So the share that stays is `1/(N+1)`. The share that moves is `N/(N+1)`.

| Servers | Keys moved with `hash % N` | Keys moved with a ring (ideal) |
|---|---|---|
| 1 → 2 | 50% | 50% |
| 4 → 5 | 80% | ~20% |
| 9 → 10 | 90% | ~10% |
| 99 → 100 | 99% | ~1% |

I checked these on 100,000 simulated keys. The `hash % N` numbers match the formula within 0.3 points.

The goal is clear. When one server joins, it should take its fair share, about `1/(N+1)` of the keys. No other key should move.

## The mechanism: a hash ring

Karger and colleagues at MIT proposed this in 1997. The paper is in the further reading list. The idea has three parts.

1. **Make the hash space a circle.** A 32-bit hash has 2³² possible values. Put them on a circle, from 0 up to 2³²−1, then wrap back to 0.
2. **Hash servers onto the circle.** Hash each server name. That gives each server a position.
3. **Hash keys onto the same circle.** A key belongs to the first server you reach going clockwise from the key's position.

Step through it. Watch what moves when a server joins and when one leaves.

<RingWalkthrough client:visible />

Why does this move so few keys? A new server only takes the arc between itself and its counter-clockwise neighbor. Keys outside that arc still find the same server first. The removal case is the same in reverse. A dead server's arc goes to its clockwise neighbor, and nothing else changes.

The cost of a lookup is small. Keep the server positions in a sorted array. Find the first position at or after the key's hash with a **binary search**. That means you check the middle of the list, throw away the half that cannot hold the answer, and repeat. Even with thousands of points, that is only a handful of comparisons.

## Virtual nodes

One point per server has a flaw. Random points make uneven arcs. In a simulation of 10 servers with one point each, the busiest server held about **3 times the average load**.

A second flaw: when a server dies, all its keys land on **one** neighbor. That neighbor may now hold double its share and may fail next.

The fix is **virtual nodes** (vnodes). Each physical server hashes to many points: `cache-A#0`, `cache-A#1`, and so on. Each point owns a small arc. A server's total share is the sum of many small random arcs. Sums of many random numbers are close to their average.

Measured on the same simulation (10 servers, busiest server vs average):

| Points per server | Busiest server |
|---|---|
| 1 | ~2.9× |
| 16 | ~1.4× |
| 64 | ~1.2× |
| 256 | ~1.1× |

Dynamo (Amazon's key-value database) uses vnodes for this reason, and adds a second benefit: a stronger server can own more points than a weaker one. Cassandra (an open-source database built on the same ideas) uses the same idea. A token is one point on its ring. Its older default was 256 tokens per node, and newer versions use a token allocator that needs far fewer.

## Replication on the ring

Most systems store each key on more than one server, so that one crash does not lose data. This is replication (the [Replication](/learn/backend/04-data/replication/) lesson). On a ring this is cheap: store the key on the owner and on the next `R − 1` **distinct physical** servers clockwise. Cassandra works this way, and it skips virtual nodes that belong to a server it already chose. Dynamo calls this list of servers the key's preference list. Here `R` is the number of copies.

## Numbers

| Fact | Value |
|---|---|
| Keys moved when one server joins (average) | `K / N` (K keys, N servers; Karger et al.) |
| Keys moved with `hash % N` | `K × N / (N+1)` |
| Busiest server, 10 servers, 1 point each | ~2.9× average |
| Busiest server, 10 servers, 256 points each | ~1.1× average |
| Lookup | binary search over sorted points: about log2(V) steps, for V points |

## Trade-offs

| Choice | You gain | You pay | When to choose |
|---|---|---|---|
| `hash % N` | Zero state, trivial code | Almost all keys move when N changes | N never changes |
| Ring, 1 point per server | Few keys move | Uneven load | Demos only |
| Ring with vnodes | Few keys move, even load, spread failure | A sorted table of points to maintain and share | Caches, Dynamo-style stores |
| Fixed hash slots (Redis Cluster: 16,384 slots) | Simple table, move whole slots | Slot table must be kept in sync | You want explicit control of data movement |
| Directory (lookup table) | Any placement, easy to move one key | Table is a new service to run | Large, uneven, or changing workloads |

<Callout type="deep" title="Fixed slots are consistent hashing in disguise">
Redis Cluster (Redis is a popular in-memory store) does not use a ring. It splits the key space into 16,384 slots. A key maps to a slot with a hash function called CRC16, then the remainder after dividing by 16,384, and each node owns a set of slots. Adding a node means moving some whole slots. The goal is the same as the ring: change the owner of only a small share of keys. The slot table makes the movement explicit, and you control which slots move. Notion (the note-taking app) uses the same idea for Postgres, a popular relational database: 480 logical shards sit on 32 physical databases, 15 on each. The fixed number of logical shards lets the cluster grow later without rehashing every row. A later lesson covers this.
</Callout>

## In practice

<Callout type="tip">
Say why in one sentence: "With `hash % N`, adding a server remaps `N/(N+1)` of the keys. With a ring, only about `1/(N+1)` move." Then say "I would use virtual nodes to even out the load and to spread a failed server's keys over many peers." Stop there unless asked for more. Many managed stores (DynamoDB, Cassandra) do this for you. A managed store is one that a cloud vendor runs for you. Name that, and do not reinvent it on the whiteboard.
</Callout>

<Callout type="mistake">
Do not claim consistent hashing fixes hot keys. One celebrity key still hashes to one point and lands on one server. A ring spreads **many keys** evenly. It does not spread **one key's traffic**. For hot keys you need a cache in front, key splitting, or replicas that all serve reads.
</Callout>

Another common slip: saying the ring moves "no" keys. It moves about `K/N`. Data movement is cheaper, not free. A moved key still has to be copied (storage) or re-fetched (cache).
