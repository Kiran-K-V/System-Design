## The problem

The [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson ended with a two-line database: append on write, scan on read. A scan is fine for 1,000 rows. Now take a table of **1 billion orders**. That is hundreds of gigabytes.

Your app asks: `SELECT * FROM orders WHERE order_id = 7351902264`. The answer is one row. To find it without help, the database reads the whole table. A fast SSD (an NVMe disk) reads a few gigabytes per second in a straight line (the [Latency Numbers](/learn/backend/01-one-machine/latency-numbers/) lesson). So the scan takes about **a minute**. Your target is a few milliseconds.

An **index** is the fix. It is a second structure, built from one or more columns, that lets the database jump to the right rows. The index costs disk space and slows every write. You must know how much, and when it is worth it.

## Naive: a sorted file and binary search

Suppose the keys sit in a file, sorted. You find a key by **binary search**: look at the middle, discard half, repeat. For 1 billion keys that is about 30 steps.

Each step lands on a different place in the file. Each is a separate page read. (A **page** is the fixed-size block, here 8 KB, that a database reads from disk in one go. A disk cannot hand you one byte, only a whole page.) Each page read is fast on an SSD, so 30 steps take a few milliseconds. That is far better than a full scan. But two things are wrong.

1. **30 page reads is too many.** Each read returns an 8 KB page, and we use one key from it. Waste.
2. **A sorted file cannot take inserts.** A new key belongs in the middle. Making room means shifting about half the file.

The first problem has a direct fix. Make each step of the search consume a whole page. If one page holds hundreds of keys, one step discards almost all of the data, not just half. This is the idea behind the B-tree.

## The mechanism: the B-tree

A **B-tree** is a tree where every node is exactly one page. A node holds sorted keys and, between them, pointers to child pages. To find a key, read the root. Pick the child whose range contains the key. Read that child, and repeat until you reach a **leaf**. A leaf holds the key and a pointer to the table row. (A pointer is the stored location of the row, like a page number in a book index.)

Most databases use the **B+tree** variant. Only leaves hold row pointers. Leaves are also chained to their neighbors in key order, each leaf pointing to the next. So a range query (`BETWEEN`, for example all orders from 100 to 200) finds the first key and then walks along the leaves. The tree is **balanced**: every leaf is at the same depth. That is the property that keeps lookups predictable.

### Height: why the tree stays shallow

The cost of a lookup is the tree's **height**, because each level is one page read. Height depends on the **fan-out**: how many children a node has. A node is one 8 KB page, so it can hold several hundred keys and pointers. Each level multiplies the number of keys the tree can reach by several hundred.

That growth is fast. Three levels reach tens of millions of keys. Four levels reach tens of billions. So a table of 1 billion keys needs a tree only about 4 levels tall. The top levels are tiny compared with the leaves, because each level is hundreds of times smaller than the one below.

Read the figure from the bottom. The leaves hold almost all of the pages. This agrees with the PostgreSQL docs ("typically, over 99% of all pages are leaf pages"). The upper levels are small enough to stay in RAM on any server, and they are the part every lookup touches. So a real lookup does **no disk reads for the upper levels**. It does one SSD read for the leaf and one for the table page. That is well under a millisecond, against about a minute for the scan.

The answer is not sensitive to the exact node size. Halve the entry size or double it: the height barely moves. Use The Index Luke says real indexes on millions of rows have a depth of 4 or 5, which matches.

### Insert: the split

Inserting a key means finding its leaf and adding it in sorted order. If the leaf has room, one page changes. If the leaf is full, it **splits**. Half the keys move to a new page. The middle key moves up into the parent as a new pointer. If the parent is full it splits too. Splits cascade upward. When the root splits, the tree grows one level taller. That is the only way a B-tree gets taller, so it stays balanced by construction.

Notice how rare a split is. In a real index, a leaf that just split is half full. It takes many more inserts into that leaf before it splits again. A root split happens only a handful of times in the life of a table.

### What an index costs on write

A lookup got cheap. A write got dearer. A row insert touches the table page **and one leaf page in every index** on the table. A table with 6 indexes writes 1 table page plus 6 index leaf pages for each insert. All of these writes happen in place (the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson): each page is overwritten where it sits. They are also recorded in the write-ahead log. An update that changes an indexed column must change that index as well.

That is why the rule is **not** "index every column". Index the columns that the hot queries filter, join, or sort on. Drop the rest.

## Which queries can use an index?

An index on **several columns** is one tree. It is sorted by the first column, then by the second inside each first-column value. It is a phone book: sorted by surname, then by first name. You cannot look someone up by first name alone. Use The Index Luke makes the same point: a two-column index "does not support searching on the second column alone".

Three rules follow. Use the widget to check each one. Pick an index, pick a query, and watch how many of the 200 entries get read.

1. **Leftmost prefix.** The index helps only if the query has a condition on its first column. `age = 30` on an index `(city, age)` reads all 200 entries.
2. **Equality columns first, range column last.** Go left to right. Every `=` condition narrows the range, and the scan continues. The first **range** condition (`>`, `BETWEEN`) narrows the range and ends the narrowing. Columns after it can only filter entries already read. So `city = 'Oslo' AND age > 40` wants `(city, age)`. The reverse order `(age, city)` reads 113 entries to return 23.
3. **Covering index.** If the index holds every column the query needs, the database never visits the table. This is an **index-only scan**. It saves one page read per row returned. The price is a wider index: more memory and more work on each write.

## Another way: the LSM tree

A B-tree updates pages in place. Each insert is a random page write, a write to some spot in the middle of a file. Disks are much faster at writing one long stretch in order than at jumping around. When the write rate is very high, that is the bottleneck. The [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson introduced the other family: log-structured storage. Its index is the **LSM tree** (log-structured merge tree), used by RocksDB, Cassandra, and LevelDB. (These are storage engines and databases built on this idea. RocksDB is a storage library that other databases embed.)

Writes go to a sorted map in RAM, the **memtable**, and to a log for crash safety (the write-ahead log of the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson). A full memtable is flushed as one sorted file that is never edited again (immutable), an **SSTable**. Nothing is edited in place. Old versions pile up in older files. A background job, **compaction**, merges files and drops overwritten and deleted keys. Think of it as merging several sorted piles of index cards into one tidy pile.

A read must check the memtable, then files from newest to oldest. To avoid useless disk reads, each file carries a **Bloom filter**. It is a small in-memory summary that can say "this key is definitely not in this file". It never says "not here" wrongly, but it can say "maybe here" wrongly. RocksDB documents the exchange: 9.9 bits per key gives a 1% false-positive rate, and 15.5 bits gives 0.1%. With many files, each wrong "maybe" costs a disk read, but most reads for a missing key cost none.

The memory cost is real. Filters for a billion keys take on the order of a gigabyte of RAM.

The bill moves, it does not vanish. Compaction rewrites the same data many times. This is called **write amplification**: the ratio of bytes the disk writes to bytes your app wrote. The RocksDB docs say it is "often larger than 10" for leveled compaction. Every byte you write may be written to disk ten times or more, in the background. The disk can become the bottleneck long before your app looks busy.

## Two more index shapes

**Hash index.** It maps a hash of the key to a row location. Lookup by equality is one step. But a hash scatters neighbors, so it cannot do ranges or sorted output. PostgreSQL's docs say a hash index stores a 32-bit hash code and "can only handle simple equality comparisons". A B-tree does equality almost as fast and does everything else. Hash indexes are rare in practice.

**Inverted index.** A B-tree answers "which row has this key?". Search needs the opposite: "which rows **contain** this word?". An inverted index maps each term to a **posting list** of the documents that hold it. PostgreSQL's GIN index (its name for this kind of index) is this, and Lucene is built on it. Lucene is the search library inside Elasticsearch, a popular search server. Watch one get built from three documents.

Location search is a third need. A B-tree sorts one dimension, so a range on latitude still reads a whole band across the planet. Spatial indexes split the plane into regions instead. PostgreSQL provides a framework called GiST for such indexes. The [Proximity Search](/learn/backend/10-advanced/proximity-search/) lesson builds the idea from scratch.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| B-tree | Fast point and range reads, sorted output | A random page write per index per insert; page splits | Read-heavy or mixed OLTP (many small reads and writes, as in an app). The default. |
| LSM tree | Very high write rate; sequential disk writes | Several files per read; Bloom filter memory; compaction I/O | Write-heavy ingest: events, messages, metrics |
| Hash index | One-step equality lookup | No ranges, no ordering | Almost never; a B-tree is nearly as fast |
| Inverted index | Search by contained term | Updates one list per distinct term of each new document | Text search, array contains, tags |
| Composite index | One tree serves several filters | Order matters; wider entries | A hot query filters on 2 or more columns |
| Covering index | No table access | More memory, slower writes | A few very hot read queries |

## In practice

<Callout type="tip">
When you propose an index, say three things. The columns and their order, and why (equality first, then range). What query it serves and how often it runs. What it costs: "this table takes 5,000 inserts per second, and one more index adds one more random page write to each." That last sentence is what separates a staff answer from "add an index".
</Callout>

<Callout type="mistake">
"A lookup is O(log n), so it is cheap" is incomplete. State the page reads: height 4 for a billion keys, and the top levels are cached. Also do not say "index every column". And never promise that an index on `(b, a)` serves `WHERE a = ?`. It does not. Check the leftmost-prefix rule before you draw it.
</Callout>

<Callout type="deep" title="Why not a binary tree in memory, on disk?">
A binary search tree has 2 children per node. On disk each node would be its own page, so 1 billion keys need 30 page reads. The B-tree wins by matching the node size to the disk's unit of I/O. This is the general lesson: when a layer moves data in blocks, design the structure around the block size. The same reasoning explains page-sized buffer pools and sequential log writes (the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson).
</Callout>
