## The problem

The [Replication](/learn/backend/04-data/replication/) lesson ended with an open question. When the leader dies, **who decides** which follower becomes leader, and who hands out the new epoch number? An **epoch** is a counter that goes up each time a new leader takes over, so old leaders can be spotted and ignored. If one machine decides, that machine is a new **single point of failure**: one machine whose crash stops the whole system. If every machine decides alone, two of them may crown themselves.

The same question appears in many places:

- Which server holds this lock right now? (A **lock** lets only one worker run a job at a time.)
- Which node owns shard 7 after a failure?
- What is the one agreed order of these 10 updates?

All three need several machines to **agree on one answer**. Machines must still agree when some crash and some messages are lost or delayed. That problem is **consensus**.

In practice we want more than one answer. We want a stream of them: an agreed, ordered **log** of commands. If every machine applies the same commands in the same order, every machine ends in the same state. This is a **replicated state machine**. It is the write-ahead log of the [How a Database Stores Data](/learn/backend/04-data/storage-engines/) lesson (the file where a database writes each change before it applies it), made fault tolerant.

A consensus algorithm must give two kinds of promise.

- **Safety**: nothing wrong ever happens. Two nodes never decide different values.
- **Liveness**: something good eventually happens. The group does decide.

The FLP result (Fischer, Lynch, Paterson, 1985) shows why you cannot have both for free. In a fully asynchronous system, message delay has no bound. A crashed node also looks the same as a slow one. "Asynchronous" means there is no clock that tells you a message is late. In such a system, no consensus protocol can tolerate even one crash. The paper puts it this way: "no completely asynchronous consensus protocol can tolerate even a single unannounced process death". Real systems escape by adding timeouts. They stay **safe** always. They make progress only when the network behaves well enough.

Consensus can also do its job perfectly and still hurt you. That happened at GitHub in 2018. [The story](#incident) comes after the section on what consensus is for.

## Naive attempts

**Two nodes watch each other.** Node A and node B ping each other. If B stops answering, A promotes itself. Now cut the cable between them. A sees silence and promotes itself. B sees silence and does the same. Two leaders, a **split brain**: two machines both believe they are in charge and accept conflicting writes. The opposite rule, "do nothing if unsure", stalls the system on every glitch. Two nodes cannot tell a crash from a cut cable.

**One referee decides.** A third machine chooses the leader. Now the referee is a single point of failure. You moved the problem.

**Wait for everyone.** Ask all nodes and proceed only when all agree. One crash halts the whole group.

The way out is a **majority**. A majority is more than half of the nodes. Take a group of 5. A majority is any 3. Pick one group of 3 and another group of 3. They hold 6 seats in a group of 5, so at least one node sits in both.

Think of two committees drawn from the same 5 people. Each committee has 3 members. They cannot be fully separate, because 3 + 3 is more than 5. Someone sits on both.

That shared node is the whole trick. It carries the facts from the old decision into the new one. It will not say yes to two conflicting proposals. So two sides of a broken network can never both reach a majority. At most one side can decide.

It also costs little. With 5 nodes you can lose 2 and still have a majority of 3. Waiting for all 5 would stop at the first crash.

## Quorums: the overlap rule

A **quorum** is the number of nodes that must take part in an operation. Say you have `N` copies. A write must reach `W` of them. A read asks `R` of them.

- If `R + W > N`, every read set shares at least one node with every write set. A read therefore meets at least one copy of the latest **completed** write.
- If `2W > N`, any two write sets share a node. Two sides of a network split cannot both complete a write.

A majority satisfies both.

1. **Cassandra's `QUORUM`** (Cassandra is a database that spreads data over many machines) is `n/2 + 1`, rounded down. With 3 replicas and `QUORUM` on both reads and writes, `2 + 2 > 3`. The overlap holds. `ONE`/`ONE` does not overlap. A read can miss the write. That is the knob the [CAP and PACELC](/learn/backend/04-data/cap-pacelc/) lesson mentioned.
2. **Write ALL, read ONE** overlaps, but a single dead replica blocks every write. Tolerance for writes is `N − W = 0`.
3. **Latency is the slowest node you must wait for.** The Dynamo paper (Amazon's key-value store) says the latency of a get or put "is dictated by the slowest of the R (or W) replicas". Assume round trips of 0.5 ms, 1 ms, 70 ms, 70 ms, 150 ms, and so on. Raising W from 2 to 3 of 3 jumps from ~1 ms to ~70 ms.
4. **Odd sizes win.** Compare 5 and 6 nodes. Both tolerate 2 failures. The sixth node adds cost and no safety. The etcd FAQ says it directly. (etcd is a small database that many systems use to store critical shared facts.) An odd-size cluster tolerates the same number of failures as an even-size one. It needs fewer nodes to do so.

| Nodes | Majority | Failures tolerated |
|---|---|---|
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |
| 9 | 5 | 4 |

(Same as the etcd FAQ table. Aurora, Amazon's cloud database, applies the same idea to storage: 6 copies across 3 zones, write quorum 4, read quorum 3.)

A quorum alone is not consensus. It gives overlap for finished writes. It does not choose a single leader, or one order for **concurrent** writes. For that you need a protocol around the quorum.

## The mechanism: Raft

**Raft** is a consensus algorithm designed to be understandable. It splits the job into three parts: electing a leader, replicating a log, and keeping that safe. The Raft site says it is "equivalent to Paxos in fault-tolerance and performance". Paxos is the older, harder-to-learn algorithm. Spanner, Google's globally spread database, runs a Paxos group per replica set. It commits a write once a majority of voting replicas agree.

Four ideas carry Raft.

1. **Terms.** Time is cut into numbered terms. Each term has at most one leader. Every message carries a term. A server that sees a higher term updates itself. A leader that sees a higher term steps down. This is the fencing from the [Replication](/learn/backend/04-data/replication/) lesson (refusing messages from an old leader), built in.
2. **Election.** A follower that hears no **heartbeat** (a small "I am still here" message the leader sends every few milliseconds) for a random **election timeout** becomes a candidate. The candidate adds one to the term and asks for votes. Each server votes for at most one candidate per term. A candidate with a majority wins. Random timeouts make split votes rare. The paper's example range is 150–300 ms.
3. **Replication.** Only the leader accepts writes. It appends each command to its log and sends it to followers in a message called `AppendEntries`. Once a **majority** has stored an entry, the entry is **committed**: the leader applies it and answers the client.
4. **Safety.** A voter refuses a candidate whose log is less up to date than its own. So a new leader always holds every committed entry.

Step through one run on five servers. The run has an election, one committed write, a leader crash, a second election, and a late rejoin.

Two details deserve a second look.

**The client does not wait for everyone.** With five servers the leader needs two follower acknowledgements to reach three copies. It waits for the **second-fastest** follower. The paper notes that a single slow follower will not slow the cluster.

**The new leader is never missing committed data.** Entry 1 was committed on a majority. The election needs votes from a majority. Two majorities share a server, and that server's log contains entry 1. It will not vote for a candidate that lacks it. This is the same overlap rule, used twice.

Raft also keeps one rule for safety that is easy to miss. A leader never commits an entry from an earlier term by counting copies. It commits an entry from its **own** term by counting. Doing so also commits every entry before it. The paper's Figure 8 shows an older entry stored on a majority that is later overwritten.

## Timing

Raft's safety does not depend on timing. Its availability does. The paper states the requirement as `broadcastTime ≪ electionTimeout ≪ MTBF`. Broadcast time is how long a round of messages takes. MTBF (mean time between failures) is how long one server runs, on average, before it fails. The paper says disk writes put broadcast time between 0.5 ms and 20 ms. So the election timeout is likely between 10 ms and 500 ms. When a leader crashes the system is unavailable for roughly one election timeout.

etcd, the store named above, is built on Raft. It ships with a 100 ms heartbeat and a 1,000 ms election timeout. Its tuning guide says the election timeout should be at least 10 times the round-trip time. The guide caps it at 50,000 ms for globally spread clusters.

## What consensus is for

Consensus is slow and small by design. Each committed write needs a majority round trip and a disk sync (an `fsync`, which forces the data onto the disk so a power cut cannot lose it). Everything goes through one leader. The etcd FAQ recommends no more than seven nodes, because "write performance suffers" as you add members.

So use it for **small, critical facts**:

| Use | Example |
|---|---|
| Leader election and failover | Which replica leads shard 7? Epoch numbers |
| Locks and leases (a lease is a lock that expires after a set time) | One worker owns this job |
| Cluster configuration and metadata | Kubernetes (software that runs containers across many machines) keeps all cluster state in etcd. Kafka (a message-streaming system) has controller nodes that need a majority alive, and its docs say admins typically pick 3 or 5. |
| Ordering a small log | Spanner commits writes through a Paxos group per replica set |

Do **not** push bulk data through it. The standard pattern is a small consensus group (3 or 5 nodes). It holds the metadata, such as who is leader of each shard. The data path uses ordinary leader-follower replication (the [Replication](/learn/backend/04-data/replication/) lesson) and the leader is the one the consensus group named. That also answers the [Replication](/learn/backend/04-data/replication/) lesson's open question.

And consensus is a CP choice (the [CAP and PACELC](/learn/backend/04-data/cap-pacelc/) lesson): it keeps answers correct and refuses to answer when it cannot. When a partition leaves fewer than a majority on one side, that side stops accepting writes. The side with the majority carries on.

## A real outage: GitHub, 2018

<IncidentCard

  date="21 October 2018"

>

GitHub kept its metadata (issues, pull requests, logins) in MySQL clusters. Each cluster had one primary for writes and many read replicas. A tool called Orchestrator handled failover. Orchestrator uses Raft to agree on its decisions.

1. At 22:52 UTC, maintenance on network equipment cut the link between GitHub's US East Coast network hub and its main East Coast data center. The link came back after 43 seconds.
2. During the cut, the Orchestrator nodes on the West Coast and in a public cloud still had a majority. They did what they were configured to do. They failed the clusters over, so writes went to new primaries on the West Coast.
3. When the link returned, the apps wrote to the West Coast primaries. But the old East Coast primaries held a few seconds of writes that had never been copied west. Each side now had writes the other lacked. GitHub could not safely fail back.
4. The apps ran on the East Coast. Every write now crossed the country, and many apps could not cope with that delay.
5. GitHub chose correct data over a fast recovery. It restored the East Coast clusters from backups, which took hours. It let them catch up, then failed back. It paused webhooks and GitHub Pages builds until then.

</IncidentCard>

Map it to this lesson. Raft did its job: the majority side picked a leader. The harm came from the parts consensus does not cover. The data path used asynchronous replication, so failover left the unsent writes behind, as in [the Replication lesson](/learn/backend/04-data/replication/). And the new leader sat a cross-country round trip away, the cost in the "spread nodes across regions" row below.

| etcd recommended cluster size | at most 7 | etcd FAQ |

| Commit latency, 5 servers | the 2nd-fastest follower round trip, plus a disk sync | Derived: leader + 2 acks = 3 |

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Consensus group of 3 | Survives 1 failure, simplest | Majority is 2: lose two nodes and it halts | Small metadata, one region or 3 zones |
| Consensus group of 5 | Survives 2 failures | More messages, slightly slower writes | Production control planes |
| Spread nodes across regions | Survives a region loss | Writes wait for a cross-region round trip (~70+ ms) | Region-level durability matters more than latency |
| Consensus per write | No acknowledged write is lost. One agreed order. | Majority round trip plus fsync per write. One leader. | Metadata, locks, config |
| No consensus (async replication) | Low latency | Failover can lose writes or split the brain | Bulk, tolerant data |

## In practice

<Callout type="tip">
When your design needs a lock, a leader, or config, say "a small etcd or ZooKeeper cluster (ZooKeeper is an older tool that does the same job as etcd), 3 or 5 nodes across zones". Say what it holds: "who leads each shard, and the lock for the cron job". Then say what it does **not** hold: "user data never goes through it". Mention the cost: "each write there is a majority round trip, which is fine for rare metadata."
</Callout>

<Callout type="mistake">
Do not say "two nodes give fault tolerance", because a majority of two is two. Do not say "Raft always makes progress". Safety is always held, but progress needs a majority up and a network good enough for heartbeats (FLP). Do not use an even number of nodes "to break ties". It adds cost and no failure tolerance. And do not put application data through the consensus log.
</Callout>

<Callout type="deep" title="Why a leader never counts old-term entries">
Suppose a leader replicates an entry from an older term onto a majority. It looks committed. But the paper's Figure 8 shows that a different server can still win a later election and overwrite that entry. So Raft commits an entry only by counting copies of an entry from the leader's **current** term. When that entry commits, every entry before it commits too. This is why Raft has each new leader commit a blank entry that does nothing (a no-op) at the start of its term, so that older entries can be committed behind it.
</Callout>
