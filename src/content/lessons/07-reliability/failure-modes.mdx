## The problem

[Lesson 4.6](/learn/04-data/replication/) showed that copies make downtime rare. One node that is up 99.9% of the time is down about 8.8 hours a year. Two independent copies with perfect failover are both down about 30 seconds a year. That is a big gain.

Two words in that sentence do a lot of work: **independent** and **perfect**. Real failures break both.

The AWS Builders' Library gives the same sum. Say each server has a tiny chance of failing on a given day. Two servers both failing on the same day is far less likely still, if the failures are independent. But the article then says why this is not the full story. It defines a **correlated failure** as "multiple independent components fail due to the same underlying cause". A bad deploy (a faulty new version of the code, shipped to every server), an expired certificate (the file that proves a server's identity, which stops working on a set date), or a power fault does not pick one server. It takes all of them in the same minute.

In 2017 one mistyped command did this to Amazon S3, and the AWS services built on S3 failed with it. [The story](#incident) comes after the section on containing the damage.

This module is about designing for that. We start with the enemy: how things actually fail.

## Naive model: a server is up or down

The simple picture has two states. A server works or it is dead. A health check ([lesson 2.4](/learn/02-networking/load-balancing/)) is a small test call, a probe, that the load balancer sends to each server on a timer. It finds the dead ones, and the load balancer (written LB below) stops sending them traffic. Replication covers the rest.

This picture is right for one kind of failure, the **crash**. A crash is a failure where the process stops and stays stopped. Engineers call it **fail-stop**. It is the easiest failure to handle because it is loud. Connections are refused, probes fail, and the system routes around it.

Most bad outages come from the other kinds. They are quiet.

## Five failure modes

| Mode | What it is | Who notices | Why it hurts |
|---|---|---|---|
| **Crash** | The process or machine stops | Everyone, fast | Its load moves to the survivors |
| **Slow node** | Still answering, but late | Only callers waiting on it | Calls pile up and hold threads until they time out |
| **Network partition** | The network splits nodes into groups that cannot talk | Each side sees the other as dead | Both sides may be alive and may both act |
| **Gray failure** | Partly broken in a way the system's own checks miss | The apps that use it, not the monitor | It is never removed, so it keeps failing users |
| **Correlated failure** | Many "independent" parts fail for one cause | Everyone at once | Redundancy does not help |

Two of these need more detail.

**A slow node is worse than a dead one.** A dead server fails fast. A slow server accepts the call and then holds the caller. The caller holds a thread ([lesson 1.3](/learn/01-one-machine/throughput-vs-latency/)). The Google SRE book gives an example. Suppose 5% of requests never complete and hold a thread until a long deadline. The frontend can then serve only 19.6% of requests, an 80.4% error rate. A small share of hung calls can use up the whole thread pool. Timeouts ([lesson 7.2](/learn/07-reliability/timeouts-retries/)) exist for this reason.

**Gray failure** is a term from a 2017 paper by Huang and others at Microsoft Research. The paper says a system has a gray failure when at least one app observes that the system is unhealthy. But the system's own observer observes that it is healthy. The authors call this **differential observability**: different observers see different health. Their claim is that the big availability problems in cloud systems "tend to be caused by subtle underlying faults, i.e., gray failure rather than fail-stop failure". An example: a server whose `/health` endpoint answers while its disk is failing. The monitor is green. The users are not.

Try each mode on a small system. S3 gets the fault. Switch between "before the LB reacts" and "after" to see what detection buys you.

What to notice:

1. **Crash** has errors only until the probe threshold is reached (the example in lesson 2.4 had a 60 s window). After that, no user errors, but the survivors run hotter, because they share the lost server's work.
2. **Slow node** and **gray failure** keep the probe green. The LB never removes them. This is why a health check that only asks "is the process up?" is not enough. Real traffic outcomes (error rate, latency) must feed the decision.
3. **Partition** gives no user errors after detection, but S3 is alive. If S3 is a database leader, you now have a leadership question. That is the territory of CAP ([lesson 4.9](/learn/04-data/cap-pacelc/)) and consensus ([lesson 4.11](/learn/04-data/consensus/)).

## How one failure becomes an outage

Failures spread through load. When a server leaves, its work goes somewhere else. Step through a cascade on three servers.

<RelCascadeWalk client:visible />

The key sentence: **the outage was caused by the load that moved, not by the first crash.** Servers that are already busy have no room to lose one. The Google SRE book describes the same trap at larger scale. A service that was healthy can fail when a small rise in load meets some crashes. Recovery may then need the load to drop to far below the old peak, not just back to it. It also describes a two-cluster case. Cluster A takes traffic from a failed cluster B. Its load rises a little, and its successful throughput falls well below what it handled before.

Slow requests and retries feed the loop. A slow server holds threads. Callers time out and retry (lesson 7.2). The retries add load. Load adds slowness.

## Containing the damage

You cannot prevent every failure. You can limit how far it spreads.

- **Keep headroom.** The throughput lesson said to plan for 50 to 70% utilization at peak. Here is the reason: the headroom is what a failure's load lands on.
- **Remove the right nodes.** Use health signals from real traffic, not only a shallow probe. But do not remove too fast: a false positive that evicts a healthy node pushes more load onto the rest.
- **Fail fast and shed load.** Reject extra work early instead of queuing it. Lessons 7.2 to 7.4 give the tools: timeouts, circuit breakers, and rate limits.
- **Limit the blast radius.** The blast radius is how much of the system one fault can hurt. The AWS article describes **cells**: "identical and independent partitions" of a service. A fault or a bad deploy hits one cell, not the fleet. It also describes **shuffle sharding**. It is a technique that makes sure "no two servers in the fleet see the same exact workload". So one bad customer cannot take down everyone.
- **Change things slowly.** Roll out to one cell first. A change that touches every server at once is a correlated failure you scheduled yourself.

## A real outage: Amazon S3, 2017

<IncidentCard
  org="Amazon S3, us-east-1 (Northern Virginia)"
  date="28 February 2017"
  title="One mistyped command removed too many servers, and S3 stopped."
  cost="S3 reads came back at 12:26 PM PST. S3 was fully normal at 1:54 PM PST, about 4 hours and 17 minutes after the command. Other services needed more time to clear the work that had piled up."
  missing="A tool's blast radius must be smaller than the system it works on. AWS changed the tool to remove capacity more slowly and to refuse to take any subsystem below its minimum capacity. It also moved up its plan to split the index into smaller cells, so a restart is small and tested. Our reading of the status page: a tool you need during an outage must not depend on the thing that is down."
  source="https://aws.amazon.com/message/41926/"
  sourceLabel="AWS, Summary of the Amazon S3 Service Disruption"
>

S3 is AWS's file storage service. Inside it, an **index** subsystem knows where every stored object lives. Every read, list, write, and delete needs it.

1. At 9:37 AM PST an engineer followed an established playbook to remove a few servers from a subsystem that S3's billing uses.
2. One input to the command was typed wrong. A much larger set of servers was removed. It included servers of the index subsystem and of the **placement** subsystem, which picks where new objects go.
3. With that much capacity gone, both subsystems needed a full restart. Until they were back, S3 in the region could not serve requests.
4. AWS had not fully restarted these subsystems in its larger regions for many years. S3 had grown a lot since. The restart and its safety checks "took longer than expected".
5. Other AWS services that store data in S3 failed too. They included the S3 console, new EC2 virtual machine launches, and Lambda. Even the AWS status page could not mark the outage, because its admin console depended on S3.

</IncidentCard>

Map it to this lesson. One human input became a correlated failure: it hit every server it named at the same moment. A minimum-capacity check makes the tool fail safe. Cells keep the blast radius, and the restart, small.

## Trade-offs

| Choice | You gain | You pay | Choose when |
|---|---|---|---|
| Fast failure detection | Short error window after a crash | False positives that evict healthy nodes and move load | The cost of errors is above the cost of a spurious eviction |
| Spare capacity (N+1 or more) | The survivors can absorb a loss | Idle hardware you pay for | Always, sized to the failures you must survive |
| Cells | A failure or bad deploy hits a fraction | Routing layer, more to operate | Large fleets, or when one tenant can hurt others |
| Shed load early | The healthy part keeps serving | Some real requests are refused | Overload where queuing would make everything slow |
| More replicas | Tolerates more independent failures | Cost, plus coordination (lesson 4.11) | Failures are independent. It does nothing for correlated ones |

## In practice

<Callout type="tip">
Start a reliability answer by naming the failure mode. Say "a crash is easy, the LB sees it. The risky ones are a slow node and a gray failure, because the health check stays green." Then say what you would watch: error rate and latency per server, not only up or down. Interviewers listen for the difference between failing loudly and failing quietly.
</Callout>

<Callout type="mistake">
Do not say "we have three replicas, so we are safe". Ask what they share: the same zone, the same deploy, the same config, the same certificate. Do not treat a slow server as a dead one, because it holds callers and drags the fleet. And do not say "a partition means a node is down". Both sides can be alive.
</Callout>

- [AWS Builders' Library: Minimizing correlated failures in distributed systems](https://builder.aws.com/content/3Ev2H7t3l2eZa9xBXiZcAjz12JK/minimizing-correlated-failures-in-distributed-systems): cells, shuffle sharding, and the redundancy math.
- [Huang et al., "Gray Failure: The Achilles' Heel of Cloud-Scale Systems" (HotOS 2017)](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf) gives the definition of gray failure. It also covers differential observability.
- [Google SRE book: Handling Overload](https://sre.google/sre-book/handling-overload/): how to reject excess load early.
